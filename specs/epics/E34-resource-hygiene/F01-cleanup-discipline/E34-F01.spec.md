# Automated scratch-dir sweep + role hand-off rules for finished features — Functional Spec

## Context
Every Builder, Reviewer, Fixer, and PR-fixer run writes local scratch state under
`scratchpad/<feature-id>-<role>/` (the namespacing convention already stated in
`agents/builder.md` / `agents/reviewer.md`). Nothing ever removes it once the owning
feature is done. Measured in this repo at intake: `scratchpad/` is 654M total, and its
largest entries (`E31-F02-reviewer` 212M, `E31-F02-builder` 168M, `E28-F02-builder` 92M)
belong to features that finished weeks ago. The only mitigation today is a human
retyping a cleanup instruction into every prompt — not durable, easy to forget, and it
exhausts disk on a machine running many concurrent sub-agents. The user is anyone
running this harness with concurrent sub-agents, and, secondarily, the harness
maintainer repeating the same instruction.

**Scope note (size budget).** The inbox brief and `epic.md`'s own notes flag that the
epic's full scope — scratch files, `progress/` handoff files, and git worktrees/branches
— may exceed `change_size.max_requirements: 12` in one spec, and name artifact kind as
the natural split seam. It does: drafting all three kinds together in one spec produced
14+ candidate requirements before role-file edits were even counted. This spec covers
**only the scratch-directory sweep** — the kind with the largest measured cost (654M,
entirely scratch) and the simplest, already-established liveness signal (TaskStore
status). The `progress/` handoff-file sweep and the git worktree/local+remote-branch
sweep are **follow-on features under E34** (see `## Out of scope` and the epic's Notes),
not silently dropped.

## Business rules
- The sweep is a **backstop**, not a role's own job: a role that writes a namespaced
  scratch directory never removes it itself; removal happens only once the owning
  feature reaches the terminal `done` status, and only the sweep tool performs it.
- **Fail closed.** Whenever the sweep cannot establish, with the TaskStore as the sole
  source of truth, that a scratch directory's owning feature is `done`, it leaves that
  directory untouched and says why. It never guesses and it never removes an
  unrecognized (non-namespaced) path.
- **Terminal means `done`, exactly.** The local TaskStore's feature status enum is
  `pending | spec-ready | in-progress | in-review | done` (`store/tasks.schema.json`);
  there is no other terminal value today. `done` is written only after a feature's work
  has merged (`agents/orchestrator.md` → "Writing `done`"), so by the time a scratch
  directory's feature reads `done`, no role session for that feature is still writing to
  it — the existing `done`-after-merge contract is what makes a status check sufficient
  without a separate live-process check.
- The tool never mutates the TaskStore and never touches anything outside the resolved
  `scratchpad/` directory.

`specs/architecture.md` is absent (no `/sdd-plan` has run in this repo); the ADR set is

## Acceptance criteria (EARS)
> Each is one testable behavior with a stable id. See docs/SPEC-FORMAT.md.

- **R1** — The harness shall provide an executable `tools/sweep-scratch.sh` that scans
  `scratchpad/` and, by default, only reports what it would do (dry-run); it shall mutate
  the filesystem only when invoked with an explicit `--apply` flag.
- **R2** — When scanning `scratchpad/`, the tool shall classify each immediate
  subdirectory whose name matches `<feature-id>-<remainder>` (`feature-id` =
  `E[0-9]+-F[0-9]+` at the start of the name, followed by a hyphen) by that feature id;
  it shall classify every non-matching entry as unrecognized and shall never act on an
  unrecognized entry in any mode.
- **R3** — When a classified subdirectory's feature id resolves to status `done` in the
  local TaskStore, the tool shall report it as eligible for removal in dry-run mode and
  shall remove it (the whole subdirectory) when run with `--apply`.
- **R4** — If a classified subdirectory's feature id is absent from the TaskStore, or its
  status is anything other than `done`, then the tool shall skip that subdirectory in
  every mode, report the specific reason (`not-found` or `status:<value>`), and never
  remove it.
- **R5** — If the TaskStore file cannot be read or parsed, then the tool shall abort the
  entire scan before classifying or removing anything, report the failure, exit
  non-zero, and remove nothing for that invocation — a distinct outcome from R4's
  per-entry skip, because the tool cannot safely evaluate *any* entry without the
  TaskStore.
- **R6** — If a classified subdirectory's resolved real path is not a direct filesystem
  child of the resolved `scratchpad/` directory (for example, a symlink pointing outside
  it), then the tool shall skip it, report the anomaly, and never delete anything through
  it.
- **R7** — The tool shall exit non-zero only for a tool-level error — R5's TaskStore
  failure, or invalid arguments — never merely because one or more subdirectories were
  skipped (R4, R6); it shall print one line per classified entry naming its verdict
  (`removed`, `eligible`, `skipped: <reason>`, or `unrecognized`), and a final summary of
  counts per verdict plus, for an `--apply` run, the total bytes reclaimed across removed
  subdirectories.
- **R8** — The tool shall accept an optional single feature-id argument that scopes the
  scan to only that feature's matching subdirectories, and shall scan every subdirectory
  under `scratchpad/` when no argument is given.
- **R9** — `agents/orchestrator.md`'s "Writing `done`" section shall state that,
  immediately after writing a feature's `done` status, the Orchestrator invokes the
  scratch sweep scoped to that feature id with `--apply`, and that a non-zero sweep exit
  is recorded but never blocks or reverses the `done` write. (The Orchestrator's own
  execution of that documented step is prose an agent follows, the same testing shape
  every other role-file behavioral contract in this harness already uses — see
  `tests/test_scratch_and_disk_preconditions.sh` for the precedent.) This hook's scope
  extends explicitly to the `/sdd-fix-parallel` lane: `agents/fixer.md`'s P7 finalizer
  writes `done` itself and never reaches the Orchestrator main-path hook above, so P7
  shall invoke the same scoped `--apply` sweep directly, once per finalized fix id,
  under the same best-effort/never-blocks/never-reverts contract. The scope extends the
  same way to umbrella mode: the "Integration gate + rollup" step (`## Umbrella mode`)
  persists a feature's derived `done` directly and never traverses the main-path hook
  either, so it shall invoke the same scoped `--apply` sweep immediately after its own
  `done` write, under the same best-effort/never-blocks/never-reverts contract.
- **R10** — `agents/builder.md`, `agents/reviewer.md`, `agents/fixer.md`, and
  `agents/pr-fixer.md` shall each state, in a scratch-file section, that the role never
  removes its own namespaced `scratchpad/<feature-id>-<role>/` directory itself and that
  removal happens only through the sweep once the owning feature reaches `done`.
- **R11** — The installer shall ship `tools/sweep-scratch.sh` executable in both the
  source layout (`tools/sweep-scratch.sh`) and the installed layout
  (`.harness/tools/sweep-scratch.sh`), and this additive capability shall carry a SemVer
  MINOR `VERSION` bump with a matching `CHANGELOG.md` entry.
- **R12** — Before classifying or removing anything, the tool shall read `store.tasks`
  from `harness.config.yaml` (absent key defaults to `local`, per that file's own
  comments); when the resolved value is anything other than `local`, the tool shall
  refuse outright — abort before touching `state/tasks.json` or `scratchpad/`, report
  the unsupported backend by name, and exit non-zero — because this feature's liveness
  check (`## Business rules`, R3-R5) reads TaskStore status directly from
  `state/tasks.json`, which is canonical only under the `local` backend; under
  `obsidian` (`store/obsidian.md`), feature status lives in specs/ frontmatter instead
  and `tasks.json` is only an optional, possibly stale or absent, mirror. Defaulting to
  `local` is only correct when `store.tasks` is genuinely absent — no top-level `store:`
  key anywhere in the file at all, or a `store:` block that is present but itself omits
  `tasks:`. Seven straight rounds of Codex findings in this exact area (five rounds of
  unrecognized `store:` shapes, then two rounds where an ever-expanding whole-document
  shape validator itself false-refused on unrelated YAML content — a block-list under
  `fix_lane.shared_paths:`, round 6; a block scalar under `verification.test_command: |`,
  round 7, Codex #4128789217) settled the parser's final scope: it examines ONLY the
  top-level `store:` key and that key's own `tasks:` child, bounded purely by
  indentation — it never attempts to understand, validate, or classify anything else in
  the document's structure. Concretely: the tool scans for the first line that is a
  top-level `store:` key — "top-level" meaning not nested under any other key, however
  the document indents its own top level, and tracked only by comparing each line's
  indentation against its enclosing frame, never by inspecting what any OTHER line's
  content is. If `store:` is found nested under a key that already carries its own inline
  scalar value, that is invalid document structure around `store:` itself, not "absent",
  and the tool refuses. Once found, `store:`'s own bounded block is every subsequent line
  more indented than `store:`'s own line, up to the first line back at or below it — that
  boundary is pure indentation comparison, not YAML-feature classification. Within that
  block, and among the document's own top-level lines (so a whole-document
  flow-mapping/sequence wrapper, an anchor/alias, or a stray multi-document `---`/`...`
  marker can never make the key search walk past a real `store:` key and misread it as
  absent — Codex #4128053695/#4127549472, rounds 4-5), the tool still refuses on a
  flow-style mapping/sequence, an anchor/alias, a bare scalar directly on the `store:`
  line where a mapping is expected, or any other content that leaves `tasks:` unresolved.
  Content OUTSIDE that bounded scope — no matter what YAML feature it uses, a block
  scalar, a block sequence, a flow mapping, an anchor/alias, a literal `---`/`...`-shaped
  line embedded as some other key's block-scalar content, anything — is never examined,
  classified, or allowed to trigger the fail-closed refusal, so long as `store.tasks`
  remains independently resolvable from `store:`'s own bounded block. A block scalar's
  own header (`key: |`/`>`, with its chomping/indentation indicators in the ordering
  this reader recognizes — a less-common ordering is a disclosed known limitation, not
  a contract this rule makes, per the tool's own header comment) opens a run of
  content that is opaque literal text, full stop: every line more indented than that
  header is never interpreted as structure, never key-matched, and never inspected for
  what it says — including a content line that itself reads like `store:` (round 8,
  Codex #4129040215, after round 7 stopped merely the block scalar's presence from
  disqualifying the document but still key-matched its content against the header's own,
  now-closed, frame) — for as long as it remains outside `store:`'s own bounded block;
  a block scalar opening genuinely inside that bounded block is still scrutinized under
  the same refuse-on-ambiguity rule as any other content there. Round 11 closed two
  remaining real safety holes in this same guard, both in the danger class R12 exists to
  prevent — silently resolving to `local` and proceeding to delete scratch directories
  when the real backend could not actually be established: (1) a MISSING
  `harness.config.yaml` (the file does not exist at all) is a read failure, not "no
  top-level `store:` key found in an existing file" — it can never establish which
  TaskStore backend is authoritative, so the tool now fails closed exactly like any other
  unreadable config, rather than defaulting to local (Codex #4130253950); defaulting to
  `local` remains correct ONLY when the file exists, was read, and genuinely contains no
  top-level `store:` key, or a `store:` block present but itself omitting `tasks:`. (2)
  Within the two scopes this reader ever classifies — the document's own top-level lines,
  and `store:`'s own bounded block, at any depth — a non-blank, non-comment line that
  matches none of the shapes already tolerated there (an ordinary `key:` mapping entry, a
  list item, a document marker, or — at the top level only — content already carried
  through the disqualifying-character check) is genuinely ambiguous, e.g. an explicit-key
  YAML mapping entry (`? tasks` / `: obsidian`); the tool refuses rather than silently
  treating it as irrelevant and walking past it to conclude `store:`/`tasks:` is absent
  (Codex #4130253947). This does not implement explicit-key YAML syntax, or any other new
  YAML feature — it only stops treating "I cannot classify this line" as proof the line
  is safe to ignore. It also does not touch round 7-10's scope-narrowing: content nested
  under some OTHER, unrelated top-level key is still never examined at all. (3) `tasks:`
  found in the `store:` block but resolving, after unquoting, to an explicit EMPTY scalar
  (`tasks: ""`, `tasks: ''`, or a bare `tasks:` with nothing after the colon) is a
  DIFFERENT case than `tasks:` being genuinely absent from the block — someone deliberately
  wrote an empty value, and empty string selects none of `local`/`obsidian`/`jira`/anything
  this tool recognizes; the tool refuses here too, rather than letting the caller's
  `${STORE_TASKS:-local}` shell expansion — which cannot distinguish "unset" from "set to
  empty string" — silently default it to `local` (Codex #4130742436). Defaulting to `local`
  remains correct ONLY for the two genuinely-absent shapes already named above: no
  top-level `store:` key at all, or a `store:` block present but itself omitting `tasks:`.
- **R13** — If an eligible entry's `rm -rf` removal fails (permissions, a read-only
  filesystem, or an I/O error) during an `--apply` run, the tool shall still print that
  entry's `skipped: remove-failed` line and the full final summary — it never stops
  early or skips remaining entries — but the tool's own exit code shall be non-zero,
  distinguishing a failed cleanup from a clean `--apply` run (which stays exit 0) so a
  caller recording only nonzero exits (`agents/orchestrator.md`'s "Writing `done`" sweep
  hook) never silently treats a failed removal as success.
- **R14** — When reading the TaskStore (R5), a feature record whose `id` is missing,
  not a string, or a string that does not match `store/tasks.schema.json`'s
  `^E[0-9]+-F[0-9]+$` pattern, or whose `status` is missing, not a string, or a string
  that is not one of that schema's closed feature-status enum (`pending`, `spec-ready`,
  `in-progress`, `in-review`, `done`), is schema-invalid; the tool shall treat it
  exactly like R5's read/parse failure — abort the entire scan before classifying or
  removing anything, report the failure, and exit non-zero — rather than skip only
  that one record, or let the rest of the board be trusted as if that record never
  existed. A missing key, a JSON `null`, or a non-string type (number, list, object)
  is exactly as schema-invalid as a malformed-but-present string value; none of these
  shapes may fall through to a silent per-record skip. A syntactically valid JSON
  string is not necessarily schema-valid: `status` and `id` are
  read from a well-formed document and printed as one tab-delimited `id<TAB>status` line
  per feature for the shell side to parse, so an unvalidated value containing an embedded
  tab or newline (e.g. a `status` of `pending\nE99-F99\tdone`) could otherwise be split
  into a second, forged `id\tstatus` row naming a feature id that does not exist in the
  TaskStore at all — the schema's enum values are short fixed literals that can never
  contain either character, so validating against it closes the injection outright. Since
  such a record makes the TaskStore itself untrustworthy for every entry, not just the one
  malformed record, skipping only that record is insufficient; the whole scan must abort,
  the same as R5. The same rule reaches every level `store/tasks.schema.json` requires a
  shape at, not just a present feature's `id`/`status` fields: a `features[]` array
  element that is not itself an object (Codex #4131236393), an `epics[]` array element
  that is not itself an object, or an epic's `features` value that is not an array, are
  all exactly as schema-invalid as a malformed `id`/`status`, and each aborts the whole
  scan the same way rather than being silently skipped.
- **R15** — When reading the TaskStore (R5), a feature record that carries a `parked`
  field (`store/tasks.schema.json`: presence means parked, regardless of shape) shall
  never be reported as eligible for removal (R3), even when its `status` scalar reads
  `done` — the tool shall report it exactly like R4's per-entry skip, with reason
  `status:parked`. This is a narrow, targeted guard against the one directly-demonstrated
  cross-field conflict (`done` + `parked`, which `store/tasks.schema.json` itself forbids
  and which the sanctioned write path, `tasks-lock.py`, already refuses to write — so it
  can only reach `state/tasks.json` via a hand-edit or an externally imported board,
  Codex #4131629415) — **not** full cross-field TaskStore schema validation. This tool
  does not validate slice completeness (a sliced feature's `done` requiring every slice
  `done` AND `merged`) or any other cross-field invariant `store/tasks.schema.json`
  expresses beyond the parked check above; a board that reached an inconsistent
  cross-field state by bypassing the guarded write path is already outside this
  harness's supported operating model, and this tool does not attempt to re-derive or
  re-enforce that integrity guarantee.

## Out of scope
- Sweeping `progress/` handoff files (inbox briefs, `topology-handoff.md`, PR-loop round
  caches, or anything using the `consumed:` marker pattern) — a follow-on E34 feature.
- Sweeping git worktrees or local/remote branches, merged or otherwise — a follow-on E34
  feature; this is the general backstop the inbox brief and epic distinguish from E15's
  own worktree-per-fix teardown (`tools/fix-worktree.sh`), and neither is touched here.
- Remote branch deletion of any kind — flagged by the inbox brief as needing its own
  confirmation gate; deferred in full, including deciding what that gate looks like, to
  whichever follow-on feature specs the worktree/branch sweep.
- A new `/sdd-*` slash command. `tools/fix-worktree.sh` (E15-F02) sets the precedent of a
  standalone `tools/*.sh` helper invoked directly by an agent or a human, with no
  dedicated slash command; this feature follows the same shape. A thin `/sdd-*` wrapper
  around the same script remains possible later without revisiting this design.
- Any change to what agents are allowed to write, or where — only what happens to a
  scratch directory after its feature is done.
- Documenting the scratch hand-off contract in role files other than the five the inbox
  brief names (`agents/builder.md`, `agents/reviewer.md`, `agents/fixer.md`,
  `agents/pr-fixer.md`, `agents/orchestrator.md`). Intake-time roles (e.g.
  `agents/driller.md`, `agents/planner.md`) also write namespaced scratch directories in
  practice (e.g. `scratchpad/E34-F01-inception/`), and the sweep mechanism (R1–R8) still
  reclaims those once their feature reaches `done` — only the documentation duty (R9,
  R10) is scoped to the brief's five files.
- Seeding `scratchpad/` into the installer's target-root `.gitignore` (`harness-install.sh`
  `_root_ignores` does not currently list it). That is a pre-existing, unrelated gap in
  what git tracks, not in what accumulates on disk, and this feature does not touch it.

## Open questions
None blocking. The inbox's open questions are resolved as follows:
- **Trigger point(s):** two — (1) an automatic, best-effort hook in
  `agents/orchestrator.md`'s existing "Writing `done`" step, scoped to the one feature
  that just landed; (2) the same `tools/sweep-scratch.sh` is directly runnable on demand,
  unscoped (backfills every already-`done` feature's scratch, addressing the 654M that
  predates this feature) or scoped to one feature id. No new slash command (see `## Out
  of scope`).
- **"Terminal enough to sweep":** `done`, exactly, per the TaskStore's status enum — see
  `## Business rules`. No additional live-process check is needed because `done` is
  already written only after merge.
- **Remote branches:** deferred whole, to a follow-on feature, with its own confirmation
  gate to be decided there (see `## Out of scope`).
- **Split by artifact kind:** yes — this spec is the scratch-directory piece only; the
  `progress/` handoff-file sweep and the worktree/branch sweep are follow-on E34
  features not specced here.
