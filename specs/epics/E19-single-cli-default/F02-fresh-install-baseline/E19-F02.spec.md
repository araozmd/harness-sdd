# Fresh-install pre-check baseline = the detected host — Functional Spec

## Context

E19-F01 built the mechanism — `detect_host`, the marker table, the `host` override token —
and deliberately changed nothing about an install that does not name `host`. This feature
spends that mechanism on the actual problem the epic exists for: **a human who installs the
harness from inside one CLI should not have to know a flag exists** to avoid getting the
other four front-ends' glue.

It is a one-branch change. E19-F01 extracted `precheck_baseline <target>` — the function that
answers "what should the picker pre-check?" — and pointed the interactive picker, the
`--print-agents` diagnostic and the `host` fallback at it. This feature adds one case to that
function: **a target with no existing install and a detectable host pre-checks that host
alone.** Everything else about the function stays as it is.

The user is the engineer running `harness-install.sh` interactively into a repo for the first
time. The `docs/INSTALL.md` re-toggle documentation ships here too, because "how do I change
this later?" is the first question the new default provokes.

## Business rules

- **The narrowing is applied only where a human can correct it.** The implicit baseline is a
  *pre-check*, shown in a picker that is already on screen; one keystroke adds any other
  front-end before confirming. That is what makes a best-effort guess acceptable here and
  unacceptable in a silent run.
- **A non-interactive run with no override still stamps ALL.** CI back-compat is
  non-negotiable, and a scripted run has no human to correct a wrong detection. The narrowing
  axis is *explicit vs implicit*, not interactive vs scripted: F01 already honors an explicit
  `host` everywhere.
- **Upgrades must not silently narrow.** "No existing install" means the target carries **no
  `.harness/.harness-version`** — not merely "no `.harness/.agents`". A pre-E08 install has
  all five front-ends stamped and no persisted selection; host-narrowing its picker baseline
  would turn a plain confirm into a deletion of working glue.
- **The baseline is host-only, never host ∪ `claude`.** Unioning `claude` would re-create the
  exact bug for every non-Claude user (a Gemini CLI user still gets `CLAUDE.md` they never
  asked for) and privileges one vendor in a harness whose premise is "the model is
  interchangeable; the harness is not". When the host *is* Claude Code the union is identical
  anyway.
- **A detection miss keeps today's behavior.** Undetected ⇒ pre-check ALL. Nothing regresses
  for a front-end whose marker is not verified.
- **The `codex` special-case is preserved untouched.** This feature supplies a pre-check set
  and nothing else: it changes no removal authority, weakens no pristine compare, and
  bypasses no `.sdd-pr-loop.owners` ledger (E18-F01).
- POSIX `sh`, zero new dependencies. This changes the installed body ⇒ **MINOR `VERSION`
  bump** + `CHANGELOG.md` entry.

## Architecture alignment

- **`specs/architecture.md` is ABSENT** in this repo (the harness source has never run

  "Graceful degradation": this spec is written from the inbox brief + the epic + E19-F01, and
  fabricates no architecture citation.
- The repo keeps a single ADR namespace, the platform space `specs/adr/`, holding one real
  ADR (`0001-deterministic-next-selection.md`). The inbox brief records no `ADR-NNNN` ids.
- **ADRs touched: none** — ADR-0001 governs how the Orchestrator's `next()` selection is

## Acceptance criteria (EARS)

> Each is one testable behavior with a stable id. See `docs/SPEC-FORMAT.md`.
> "The installer" = `harness-install.sh`. "Detection" = E19-F01's `detect_host`. "ALL" =
> every member of `AGENT_KEYS`. "Existing install" = the target carries
> `.harness/.harness-version`. "Baseline" = the set the interactive picker pre-checks, which
> E19-F01 R23/R26 also expose as `--print-agents`' `baseline=` line.

### The new baseline

- **R1** — While standard input is an interactive TTY, no override is supplied, and the
  target has **no existing install**, when detection resolves to a key, the installer shall
  pre-check **that key alone** — never a union with any other key.
- **R2** — If, under the R1 conditions, detection is undetected, then the installer shall
  pre-check **ALL** keys.
- **R3** — While the target has an **existing install** with a persisted `.harness/.agents`,
  the installer shall pre-check that persisted set, and detection shall not influence it.
- **R4** — While the target has an **existing install** with **no** persisted
  `.harness/.agents` (a pre-E08 install), the installer shall pre-check **ALL** keys, and
  detection shall not influence it.
- **R5** — While standard input is not an interactive TTY and no override is supplied, the
  installer shall resolve the selected set to ALL keys regardless of what detection returns.
- **R6** — The interactive picker's pre-check set and the `--print-agents` `baseline=` value
  shall remain the output of the single shared helper E19-F01 introduced, so the diagnostic
  reports the new default rather than the old one.

### Safety

- **R7** — This feature shall not change how `PRIOR_AGENTS` is computed **for an existing
  install**: it stays that target's persisted `.harness/.agents` when present, else —
  legacy upgrade — `AGENT_KEYS` minus `codex`. (R14 fixes the stamp-less case.)
- **R14** — The definition of "existing install" shall be the same for the baseline and for
  removal authority: while the target carries **no** `.harness/.harness-version`,
  `PRIOR_AGENTS` shall be empty, so a `.harness/.agents` with no stamp (orphan metadata)
  shall cause the installer to remove no front-end glue and to reclaim no global Codex
  prompt. A target the baseline calls "no existing install" cannot be a target whose
  recorded keys are reconciled as deselected.
- **R8** — When a human confirms the host-narrowed baseline on a target with no existing
  install, the installer shall remove no front-end glue and shall neither delete nor modify
  any file in the global Codex prompts directory, including the `.sdd-pr-loop.owners` ledger.
- **R9** — The installer shall not narrow any existing install's selection as a result of
  detection: for a target carrying `.harness/.harness-version`, the resolved set of a
  no-override run shall be independent of every marker variable.

### Documentation

- **R10** — `docs/INSTALL.md` shall document the new fresh-install default: what gets
  pre-checked, that it applies only to an interactive first install, that an upgrade keeps
  its persisted selection, and that an undetected host still pre-checks everything.
- **R11** — `docs/INSTALL.md` shall document that **re-running the installer** is the
  supported way to change the agent selection after install — it re-prompts pre-checked from
  `.harness/.agents` and applies both adds and removes — with a copy-pasteable command. This
  fact currently exists only in the `harness-install.sh` header comment.

### Verification

- **R12** — `tests/test_agents_host.sh` shall be extended with the R1–R5 and R8–R9 cases
  under E19-F01's environment discipline: an explicitly constructed environment (`env -i`
  plus only the variables under test), a sandboxed `CODEX_HOME` on every installer-invoking
  run, no frozen exact `VERSION` string, and no DO-NOT-TOUCH file diffed against `main`.
- **R13** — `VERSION` shall receive a MINOR bump and `CHANGELOG.md` a matching entry.

## Out of scope

- Everything E19-F01 owns: the marker table, `detect_host`, `HARNESS_HOST_AGENT`,
  `--print-agents`, the `host` override token and its two fallbacks. This feature consumes
  them; it does not modify them.
- Adding a marker row for any front-end. If a row is missing, that front-end's users simply
  keep today's all-keys baseline — which is the designed degradation, not a gap this feature
  closes.
- Changing the no-TTY default (R5 pins it to ALL).
- A `/sdd-config` command or any standalone reconfiguration TUI. R11 documents the existing
  re-run path instead.
- Any runtime behavior change; this governs only which glue files land on disk.
- Forking any canonical `agents/*.md` role; touching `store/tasks.schema.json`.

## Open questions — resolved, with rationale

This closes the brief's third open question.

1. **Should the fresh-install baseline be host-only or host-plus-`claude`?** **Host-only**
   (R1). Unioning `claude` re-creates the exact bug for every non-Claude user and privileges
   one vendor in a front-end-neutral harness; when the host *is* Claude Code the union is
   identical anyway; and when it is not, adding `claude` costs one keystroke in a picker that
   is already on screen. Rejected.
2. **What counts as "fresh"?** The absence of `.harness/.harness-version`, not the absence of
   `.harness/.agents` (R4). The pre-E08 case — all five front-ends stamped, no persisted
   selection — is exactly the case where the looser test would cause a confirm-to-delete, and
   it is the one the epic's "upgrades must not silently narrow" constraint is about.
