# Host detection + explicit `--agents=host` — Functional Spec

## Context

E08-F01 made the coding-agent front-ends *selectable*; it never changed what happens when
the human does not choose. On a fresh install the picker pre-checks **all five** keys
(`AGENT_KEYS="claude gemini opencode antigravity codex"`, `harness-install.sh:426`), and a
non-interactive run with no override stamps all five (`resolve_agents`, :979). A human who
works in exactly one CLI therefore gets `GEMINI.md`, `opencode.json`, an Antigravity
`.agents/` tree and global Codex prompts alongside the glue they wanted.

This feature builds the **mechanism**: a way to ask "which CLI is this installer running
in?" and a `host` override token that acts on the answer. It deliberately stops there.
Changing what an unchosen install pre-checks is **E19-F02**, which depends on this one.

The split is what keeps this feature small and fast to merge: **F01 is purely additive.**
An install that passes no `host` token and sets no `HARNESS_HOST_AGENT` behaves exactly as
it does today (R22).

The user is the engineer running `harness-install.sh` from inside their one CLI.

## Business rules

- **`host` is a resolution *mode*, not a sixth agent key.** It is consumed by
  `resolve_agents`, never added to `AGENT_KEYS`, never offered as a picker row, and never
  written to `.harness/.agents` — that file stores concrete keys only.
- **`host` is a best-effort NARROWING that can never stamp less than the caller expects.**
  A detection miss is normal operation, not an error, and never aborts the installer.
- **The undetected fallback is deliberately asymmetric, and both halves are documented.**
  On a target with **no existing install** there is nothing to preserve, so `host` falls
  back to **ALL** keys — byte-identical to today's no-override/no-TTY default. On a target
  that **already carries an install**, `host` falls back to the **persisted
  `.harness/.agents` set** (or ALL when a pre-E08 install persisted none). Widening a
  claude-only target back to five front-ends because detection happened to miss is a
  user-visible regression, so the rule is: *detected ⇒ narrow to the one key the caller
  explicitly asked for; undetected ⇒ never change the shape of the install.*
- **Detection reads *session markers*, never ambient configuration.** A variable counts as
  a marker only when the front-end **injects it into the environment of the process it
  launches**. A variable a human exports in a shell profile — a home-dir path, an API key —
  proves only that the human uses that tool *somewhere*, never that this installer run was
  launched from it. This distinction is the whole reliability story of the feature; getting
  it wrong is how a Claude Code user gets a Codex-only install.
- **Ambiguity is a miss, not a tie-break.** When markers for two or more front-ends are
  present at once, the installer cannot tell which one launched it (nesting is a real case:
  one CLI shelling out to another inherits the outer CLI's markers).
- **The `codex` special-case is preserved untouched.** Codex glue lives in a shared,
  cross-target `${CODEX_HOME:-$HOME/.codex}/prompts` dir, so the legacy-upgrade
  `PRIOR_AGENTS` fallback deliberately excludes `codex` and the gated `/sdd-pr-loop` prompt
  is governed by the `.sdd-pr-loop.owners` ledger (E18-F01). This feature supplies
  `SELECTED` and nothing else: it changes no removal authority, weakens no pristine
  compare, and bypasses no ledger.
- POSIX `sh`, zero new dependencies. This changes the installed body ⇒ **MINOR `VERSION`
  bump** (`0.39.0` → `0.40.0`) + `CHANGELOG.md` entry, and every new behavior is generated
  by `harness-install.sh` **and** asserted in the test suite.

## Detection: the marker set, and how far it is trusted

The brief's first open question was the precise env-marker set per front-end **and their
reliability**. Verified empirically (2026-07-27), inside a live Claude Code session:

| Observation | What it proves |
|---|---|
| `CLAUDECODE=1` and `CLAUDE_CODE_ENTRYPOINT=cli` are set | Claude Code injects a session marker into the shells it spawns. **Trusted.** |
| `CODEX_HOME` is **unset** | It is not injected by anything; it exists only when a human exports it. **Not a marker** — this disproves the brief's premise that it is a confident signal. |
| `CODEX_COMPANION_SESSION_ID` **is** set — to the *Claude Code* session id | A `CODEX_`-prefixed variable can be set by a process that is not Codex. Prefix presence proves nothing. |
| `GEMINI_API_KEY` and `OPENCODE_API_KEY` are both set | Credentials live in shell profiles. **Not markers.** |
| The Antigravity `agy` binary contains the string `GEMINI_CLI` | `GEMINI_CLI` cannot, on its own, discriminate `gemini` from `antigravity` — `agy` derives from the gemini-cli codebase. |
| `opencode` 1.18.5 binary strings: every `OPENCODE_*` token is a read-side config knob | No opencode session marker was found by inspection. |
| `codex` 0.145.0 binary contains `CODEX_SANDBOX` / `CODEX_SANDBOX_NETWORK_DISABLED` | A *lead* only — and by construction absent when Codex runs with the sandbox off. |

The honest conclusion: **exactly one marker is verified today (`CLAUDECODE`).** The design
therefore does not guess. The marker table is declarative data with one mandatory row
(`claude`); every other row is added **only** after the Builder observes the variable
empirically, and a front-end with no verified marker is simply **undetectable** — which
degrades to the fallback, i.e. today's behavior. Shipping with fewer than five rows is an
expected, acceptable outcome, not a defect.

Two safety valves make that acceptable:

1. **A forbidden-marker rule (R6).** No ambient config/credential variable may ever be a
   marker. This is stated as a requirement, not a convention, because the test suite itself
   exports `CODEX_HOME` globally — a `CODEX_HOME` marker would appear to work in CI and be
   wrong on every developer machine.
2. **An explicit declaration escape hatch (R9).** `HARNESS_HOST_AGENT=<key>` lets a user of
   an undetectable front-end declare their host once (in their profile) without the harness
   having to guess a marker.

## Acceptance criteria (EARS)

> Each is one testable behavior with a stable id. See `docs/SPEC-FORMAT.md`.
> "The installer" = `harness-install.sh`. "Agent key" = a member of `AGENT_KEYS`
> (`claude`, `gemini`, `opencode`, `antigravity`, `codex`). "Detection" = the host
> resolution described by R1–R11. "ALL" = every agent key. "Existing install" = the target
> carries `.harness/.harness-version`.

### Host detection

- **R1** — The installer shall resolve the host front-end to **at most one** agent key,
  using only a declarative table of environment-variable markers, one row per agent key.
- **R2** — The installer shall count a marker as present only when the variable is **set and
  non-empty**; a variable set to the empty string shall not contribute to detection.
- **R3** — When exactly one agent key has at least one present marker, detection shall
  resolve to that key.
- **R4** — If no agent key has a present marker, then detection shall resolve to **nothing**
  (undetected).
- **R5** — If two or more distinct agent keys have present markers, then detection shall
  resolve to **nothing** and the installer shall print, **on standard error**, one
  diagnostic line naming the competing candidate keys.
- **R6** — The marker table shall contain only variables that a front-end injects into the
  environment of the processes it launches, and shall contain **no** ambient configuration
  or credential variable — specifically not `CODEX_HOME`, `HOME`, `TERM_PROGRAM`, nor any
  variable whose name ends in `_API_KEY` (including `GEMINI_API_KEY`, `OPENCODE_API_KEY`,
  `ANTHROPIC_API_KEY`).
- **R7** — The marker table shall carry a row mapping `CLAUDECODE` to the `claude` key.
- **R8** — The marker table shall carry a row for a non-`claude` agent key only where that
  key's marker has been empirically verified, and each such row shall record, in an adjacent
  comment, the CLI and version it was observed on; an agent key with no verified marker
  shall carry no row and shall be undetectable.
- **R9** — Where `HARNESS_HOST_AGENT` is set to exactly one known agent key, detection shall
  resolve to that key without consulting the marker table.
- **R10** — If `HARNESS_HOST_AGENT` is set to any other value — an unknown token, several
  tokens, or the literal `host` — then the installer shall print one warning naming the
  value, shall continue as if the variable were unset, and shall not abort.
- **R11** — Detection shall read, write and create no file, shall make no network call, and
  shall never cause a non-zero exit.

### The `host` resolution mode

- **R12** — When the override value (`--agents=host` or `HARNESS_AGENTS=host`) is exactly
  `host` and detection resolves to a key, the installer shall resolve the selected set to
  **that key alone**, without prompting.
- **R13** — If the override value is exactly `host`, detection is undetected, and the target
  has **no existing install**, then the installer shall resolve the selected set to **ALL**
  keys — identical to the no-override, no-TTY default.
- **R14** — If the override value is exactly `host`, detection is undetected, and the target
  **has an existing install**, then the installer shall resolve the selected set to the
  persisted `.harness/.agents` set when present, and to ALL keys when no selection is
  persisted — so an undetected `host` run never widens nor narrows an existing install.
- **R15** — The installer shall honor an explicit `host` override uniformly: on interactive
  and non-interactive runs alike, and on fresh installs and upgrades alike.
- **R16** — If an override value contains the token `host` together with any other token,
  then the installer shall exit non-zero with a message stating that `host` is a resolution
  mode and must be the entire value, and shall make no changes to the target.
- **R17** — `host` shall not be a member of `AGENT_KEYS` and shall never appear as a
  selectable row in either interactive picker.
- **R18** — The installer shall write only concrete agent keys to `.harness/.agents`; the
  token `host` shall never appear in that file.

### Ownership and removal safety

- **R19** — This feature shall not change how `PRIOR_AGENTS` is computed: it stays the
  persisted `.harness/.agents` when present, else — and only on an upgrade — `AGENT_KEYS`
  minus `codex`, else empty.
- **R20** — When a `host`-resolved run installs into a target with no existing install, the
  installer shall remove no front-end glue and shall neither delete nor modify any file in
  the global Codex prompts directory, including the `.sdd-pr-loop.owners` ledger.
- **R21** — When a `host`-resolved run on an existing install excludes a front-end present
  in `PRIOR_AGENTS`, removal shall proceed under exactly the existing rules — by name inside
  harness-owned dirs, byte-pristine compare inside user-owned dirs, and ledger release for
  the gated global prompt — with no rule weakened, skipped, or short-circuited.

### Additivity (the property that makes this feature mergeable on its own)

- **R22** — While no `host` override is supplied and `HARNESS_HOST_AGENT` is unset, the
  installer shall produce exactly the same result as before this feature: a non-interactive
  run with no override shall stamp ALL front-ends, an explicit concrete `--agents=<csv>`
  shall behave unchanged, and the interactive pre-check baseline shall remain the persisted
  `.harness/.agents` when present and ALL otherwise.

### Diagnostics

- **R23** — When invoked as `--print-agents <target>`, the installer shall print to standard
  output exactly two lines, `host=<detected key, or empty>` then
  `baseline=<space-separated sorted keys>`, shall create or modify no file anywhere, and
  shall exit 0 — on both TTY and non-TTY standard input, and whether or not `<target>`
  already carries an install.
- **R24** — If `--print-agents` is combined with `--umbrella`, then the installer shall exit
  non-zero with a usage message and write nothing.
- **R25** — When the `host` mode resolves, the installer shall print one line reporting
  either the detected key or that the host was undetected and which fallback set was used.
- **R26** — The `baseline=` value of R23 and the R13/R14 undetected fallback shall be
  produced by **one shared helper**, so the diagnostic can never disagree with what an
  actual `--agents=host` run resolves — including on a target that carries an orphan
  `.harness/.agents` with no version stamp, where the fallback is ALL. That helper and the
  interactive picker's pre-check set shall in turn obtain the target's persisted shape from
  **one shared helper**, so neither answer exists in two places.

### Documentation, wiring and verification

- **R27** — `docs/INSTALL.md` shall document the `host` mode, `HARNESS_HOST_AGENT`,
  `--print-agents`, the marker set with an explicit statement of which markers are verified,
  and **both** undetected fallbacks (no existing install ⇒ ALL, existing install ⇒
  persisted-else-ALL) with the reason for the asymmetry; and `README.md`, the
  `harness-install.sh` header comment and the generated `.harness/manifest.txt`
  "AGENT SELECTION" block shall each name `host`.
- **R28** — `tests/test_agents_host.sh` shall exist, shall be wired into
  `verification.test_command` in `harness.config.yaml`, and `tests/test_install.sh` shall
  additionally assert `--agents=host` end-to-end and that `.harness/.agents` never contains
  `host`.
- **R29** — Every detection-sensitive test shall run with an explicitly constructed
  environment (`env -i` plus only the variables under test); every installer-invoking test
  shall sandbox `CODEX_HOME` under its own temp dir; no test shall freeze the exact `VERSION`
  string or diff a DO-NOT-TOUCH file against `main`.
- **R30** — The installer shall implement all of the above in POSIX `sh` using only commands
  it already relies on; `init.sh` shall gain no new dependency and a target shall still pass
  `init.sh` with exit 0.
- **R31** — `VERSION` shall receive a MINOR bump and `CHANGELOG.md` a matching entry.

## Out of scope

- **The fresh-install pre-check baseline — that is `E19-F02`**, which depends on this
  feature. This spec deliberately leaves the picker's pre-check set exactly as it is today
  (R22, R26); F02 changes it in one place, inside the shared helper R26 mandates.
- The `docs/INSTALL.md` re-toggle-path documentation — it ships with F02, next to the
  behavior a reader would go looking for.
- Any runtime behavior change. The harness is already single-CLI at execution time
  (`execution.builder.backend: in-session`); this feature governs only which glue files land
  on disk.
- A `/sdd-config` command or any standalone reconfiguration TUI.
- Adding `host` to `AGENT_KEYS`, to the picker, or to `.harness/.agents` (R17, R18).
- Detecting an *editor* or IDE (VS Code, Antigravity's desktop app) as distinct from its
  CLI. Only the CLI front-ends the installer already stamps are detectable.
- Umbrella-specific behavior. A cascade child installs non-interactively, so it resolves via
  the propagated override (R15) or the unchanged ALL default; no umbrella-mode code changes.
- Forking any canonical `agents/*.md` role; touching `store/tasks.schema.json`.

## Open questions — resolved, with rationale

Two of the brief's three open questions are answered here; the third (host-only vs
host-plus-`claude` for the pre-check baseline) belongs to F02 and is answered there.

1. **The marker set and its reliability.** Resolved by the *Detection* section above and
   R1–R11: a declarative table, one verified mandatory row (`claude`/`CLAUDECODE`), a
   forbidden-marker rule that names `CODEX_HOME` and `*_API_KEY` explicitly, a
   multi-front-end match treated as a **miss** (R5), and `HARNESS_HOST_AGENT` (R9) as the
   escape hatch for front-ends we cannot honestly detect. The rejected alternative was
   pinning a plausible-looking variable per front-end — on the author's machine that would
   have produced a `codex` (via `CODEX_HOME`) or `gemini` (via `GEMINI_API_KEY`) verdict
   inside a Claude Code session.
2. **Is `host` honored non-interactively?** **Yes, uniformly** (R15) — it is an explicit
   instruction, exactly like `--agents=claude`, and a mode that worked only interactively
   would be useless in the scripted contexts that most want it. What keeps CI safe is not
   interactive-vs-scripted but **explicit-vs-implicit**: nothing here changes a run that
   does not name `host` (R22).

### Decisions the human made during review — recorded, not to be relitigated

- **Undetected `host` on an existing install falls back to the persisted set, not ALL**
  (R14). The original spec proposed ALL uniformly, on the grounds that it matched today's
  no-override non-TTY behavior byte-for-byte. The human overruled that: re-stamping four
  front-ends onto a claude-only target is a real, user-visible regression, and "never
  silently widen an existing install" is worth carrying a second fallback rule. R27
  therefore requires the asymmetry to be documented, so it reads as intentional.
- **`--print-agents` and `HARNESS_HOST_AGENT` are kept**, both in this feature.
- **`--agents=host,gemini` stays rejected** (R16): keeping `host` outside `validate_csv`'s
  token grammar is the structural guarantee that it can never be persisted.
