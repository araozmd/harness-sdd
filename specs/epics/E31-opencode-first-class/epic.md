# Epic E31 — OpenCode is a claimed, first-class front end

## Business brief

The harness names OpenCode as its third supported front end (`README.md`, `docs/HARNESS.md`,
`docs/INSTALL.md`), but OpenCode is served **by accident**, not by contract. OpenCode
1.18.31 reads the Codex-native shared surface `.agents/skills/*/SKILL.md` (project walk-up
plus `.opencode/{skill,skills}`), maps each skill to a `/`-command, and merges
`opencode.json` for agents. A live probe in this repository on 2026-09-17 (`opencode serve`
→ `GET /command`, `GET /agent`) confirmed it resolves all seven `/sdd-*` commands and six
agents — but through three defects that no specification, test, or ADR currently owns:

1. **The shared skill unit speaks Codex only.** `gen_skill_body`
   (`harness-install.sh:6526`) writes an "Invocation adapter" that says *"Invoke `$sdd-next`
   in Codex … Discover installed skills with `/skills`"* (`:6535`). OpenCode has neither
   `$sdd-*` invocation nor `/skills`, so the one shared body is wrong for half the hosts that
   read it — the exact failure ADR-0003's one-body rule must prevent.

2. **OpenCode's concurrency gate is bypassed.** The installer correctly withholds
   `.opencode/command/sdd-fix-parallel.md` unless `.harness/.opencode-parallel` reads
   `supported` (`:6479-6502`), but the shared unit list `HARNESS_SDD_CMDS`
   (`:1712`) includes `sdd-fix-parallel` and is written **unconditionally** for the shared
   surface (`:6781`). OpenCode reads that unit, so `/sdd-fix-parallel` is reachable on setups
   the gate explicitly marked `sequential` — the worst failure mode E22-F01 was written to
   end ("a command which appears installed and then misbehaves").

3. **The source repo's OpenCode glue is hand-maintained and already stale.**
   `gen_opencode_json` (`:4324`) emits the `builder-heavy` role for every real target, but
   the committed `opencode.json` has six agents and no `builder-heavy` — so on OpenCode
   escalation silently no-ops, the precise failure ADR-0002 was written to prevent. `--self`
   (E26-F01) regenerates only Claude/Codex glue and rejects OpenCode by construction
   (`self_install`, `:7282-7292`), so the E26 "generated-not-hand-maintained" guarantee does
   not cover OpenCode at all.

This epic makes OpenCode a **claimant** of the shared surface (ADR-0003), makes that shared
body host-neutral, restores the capability gate on every surface OpenCode can read, and
brings OpenCode's source glue under the same `--self` + drift-gate discipline as Claude and
Codex.

## Success criteria (epic level)

- OpenCode is in the shared-skill **claiming set**: selecting it installs the units, and
  deselecting it while Codex remains leaves them untouched (ADR-0003's silent-destructive
  failure direction).
- The shared `SKILL.md` body is correct for **both** claimants: it names the Codex
  `$sdd-*` invocation and the OpenCode `/sdd-*` invocation, and never tells OpenCode to use
  a surface it does not have.
- `/sdd-fix-parallel` is unreachable in OpenCode unless `.harness/.opencode-parallel` reads
  `supported`, on **every** surface (not just `.opencode/command/`).
- The source repo's `opencode.json` and `.opencode/` glue are regenerated by
  `harness-install.sh --self` and gated byte-for-byte by E26-F02, so a committed OpenCode
  artifact cannot drift from its emitter.
- OpenCode escalation resolves a model (`builder-heavy`) and the gated `pr-fixer` appears
  when and only when `pr_loop.enabled` is true.

## Non-goals

- **No fourth adapter.** The epic does not fork a second workflow body per command. It adds
  OpenCode to the existing shared unit and, where a native command is needed, reuses the
  existing `$CMDDIR` command body.
- **No relocation of the historical ledger.** `.harness/.codex-skills/` keeps its misleading
  name for ownership-proof continuity (ADR-0003).
- **No change to Codex behavior.** A `codex`-only target must be byte-identical after F01.
- **No new capability probe.** `/sdd-test-concurrency` (E22-F01) is reused as-is.

## Notes

**Probe evidence (2026-09-17, OpenCode 1.18.31, this repo).** `opencode serve` +
`GET /command` returned `sdd-plan, sdd-next, sdd-new, sdd-fix, sdd-drill, sdd-fix-parallel,
sdd-pr-loop` (all `source:"skill"`, i.e. from `.agents/skills/`); `GET /agent` returned
`orchestrator, architect, builder, reviewer, scout, doc-critic` — **no `builder-heavy`, no
`pr-fixer`**. A control project proved project `.agents/skills` and `.opencode/skill` are
both discovered. The only OpenCode binary reference for 1.18.31 is
`External skills (auto-loaded) | ~/.claude/skills/<name>/SKILL.md, ~/.agents/skills/<name>/SKILL.md`
and `Project skills | .opencode/skill(s)/<name>/SKILL.md`; newer documentation also lists
project `.claude/skills` / `.agents/skills`. This version-dependence is why the epic binds
OpenCode's *guaranteed* surface to `.opencode/` (F02) while still claiming the shared units
(F01) so they are never reclaimed out from under it.

**Command precedence is load-bearing.** OpenCode builds its command table as config commands
→ config `command` → MCP prompts → **skills last, with `if (s[o.name]) continue`**: a skill
never overrides a same-named command. A real `.opencode/command/sdd-next.md` therefore
supersedes the Codex-flavored skill for OpenCode, which is why F02 is the clean place to
give OpenCode a host-correct command body. The gated `sdd-fix-parallel` has no
`.opencode/command` copy, so its shared skill is the only surface — hence F01's body-level
self-gate.

**Sequencing.** F01 lands first: the shared body and claiming set must be correct before F02
commits OpenCode glue that depends on them. F02 is `--self` work (E26 family) and should
bump `VERSION` (installer body change) in the same PR. Both features change
`harness-install.sh`, so they must not run concurrently.

**Deferred (not seeded).** Whether `.opencode/command/` should exist at all once the shared
skill is host-neutral, and whether OpenCode should read the shared skills directly instead of
a native command copy, is a genuine architectural question. It is deliberately left out: the
current installer already emits both surfaces for targets, and removing one needs its own
reclaim/migration story (the same reasoning ADR-0003 used to defer `.agents/workflows/`).
