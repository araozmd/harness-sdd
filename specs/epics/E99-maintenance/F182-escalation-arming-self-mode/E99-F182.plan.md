# Escalation arms per front-end — Technical Plan

> Implements ADR-0011 (amends ADR-0002). Every table row cites the `R-id`(s) it serves.
> The arming **file format is frozen** — this feature changes who reads which line, and
> adds one tool that produces the host key. Start from the tool's existing structure; the
> Builder picks internals not pinned here.

## Stack & dependencies

- POSIX `sh` (the tools run under dash on the strict runner), `awk`, `sed`, `grep`. No new
  dependency, no Python, no network.
- Stage: `production` (`specs/product.md`); see `## Deferred`.

**Decision — the key is an argument, not something `builder-role.sh` sniffs.** The tool's
purity contract ("reads its arguments, one config scalar, the arming file") is what makes
"identical inputs, identical answer" testable; reading the environment inside it would make
every existing case depend on the developer's shell. Detection lives in its own tool with
`env -i` tests, and the Orchestrator pipes one into the other.

**Decision — fail closed on a key with no line.** A target installed with `--agents=claude`
and run under Codex has no `codex=` line: escalating there changes nothing (no stamp was
written for Codex), so the gate shuts and says why. Falling back to the first line would
open it when the first line is `armed` — an escalation that provably does nothing.

**Decision — a second copy of the marker rows.** The installer is not present in an installed
target (`.harness/` ships `tools/`, not `harness-install.sh`), so the tool cannot call
`detect_host`. The rows are copied and parity-tested (R8), exactly as E36-F04 copied
`iter_unfenced()` from `tasks-pair-check.py`. Moving `HOST_MARKERS` out of the installer is
out of scope: `tests/test_agents_host.sh` pins its position inside `harness-install.sh`.

## Approach notes

- **Sequencing.** R1 is the walking skeleton: `--frontend claude` against a `blocked` file
  with `claude=raise` prints `builder-heavy`. Then the shut paths (R2, R3), the no-key
  identity (R4), the garbage set (R5), usage (R6); then the detector (R7, R8); then the three
  reporting surfaces (R9 orchestrator prose, R10 init.sh, R11 installer); last docs/version
  (R12).
- **`builder-role.sh` structure.** Keep §2b's existing checks (`! -L`, `-f`, `-r`) as the
  **one shared outer guard** for both paths, then branch on `[ -n "$_frontend" ]`. Compute
  the first line once; for the key path require it to be `armed` or `blocked` **before**
  reading detail lines; take the key's verdict with the single `awk` in *Data model* (first
  match wins, no pipeline). Never normalize whitespace (Codex #3723207550 precedent). Both
  new advisories go through `_escalate` in the branch order pinned in *API*, so the `0` veto
  still wins and the complexity trigger cannot bypass the gate.
- **Pipelines under `pipefail`.** `init.sh` runs `set -euo pipefail`. Do not write
  `cat file | head -n 1` or `sed … | grep … | tr …` where the producer can outlive the
  consumer; one `awk` over the file that prints `first=… raise=… other=…` as three lines
  read by `read` is enough, or three separate `awk` invocations. The R10 large-file case
  (a ~3000-line arming file) pins this.
- **Every git call's status is checked** — this feature makes none at run time (both tools
  are git-free); the Builder's own scripts in the mutation campaign check `git stash` /
  `git checkout` status explicitly.
- **Mutation campaign before hand-off (whole-clause, see `.tests.md`).** Run every named
  mutant; a survivor means rewrite the test, not just re-run it (lesson: a surviving mutation
  is usually an unconstrained degree of freedom). Confirm each mutant applied (non-empty
  diff) before trusting its RED.
- **Test-runner discipline.** One `tools/run-tests.sh` at a time on this machine, `--jobs ≤ 4`;
  touched suites while iterating; the full suite serially once at the end. Another worker may
  hold the slot — wait, never relaunch a killed run.
