# Escalation arms per front-end — Functional Spec

## Context

`harness-install.sh` records, per selected front-end, whether escalating from `builder` to
`builder-heavy` would change the resolved stamp, and writes `.harness/.escalation-arming`
(root `.escalation-arming` under `--self`) as a first line that is the **AND** over every
front-end plus one `<front-end>=<verdict>` line each. `tools/builder-role.sh` reads only the
first line. In this repository the file reads `blocked / claude=raise / codex=neither /
opencode=neither / pi=neither`, so escalation never fires — not even under Claude Code,
where the Builder shims genuinely differ (`sonnet` → `opus`) — and `init.sh` warns on every
run. E36-F06 took three Reviewer rounds on the base Builder for exactly this reason.

The fix is **ADR-0011** (amends ADR-0002): the gate's unit becomes one front-end's own line.
The Orchestrator passes its host's key to `builder-role.sh --frontend <key>`; the key comes
from a new tool, `tools/host-frontend.sh`, which reads the same session markers the
installer's `detect_host` trusts (E19-F01) — so the key is produced, never guessed. An empty
key (no `--frontend`, no marker, or two markers) keeps today's all-front-ends rule, so every
existing consumer behaves exactly as before. The file format does not change.

**Why `complex`.** The feature honors an ADR whose constraints reach across five surfaces
(`tools/builder-role.sh`, `harness-install.sh`, `init.sh`, `agents/orchestrator.md`, the
docs), and speccing it required resolving a recorded contradiction: the installer's comment
that the front-end *cannot* be known at build time versus E19-F01's tested host detection.

**Direction (b) of the brief — a self-mode harvest for OpenCode and pi — is declined** (see
ADR-0011): it does not fix a consumer that installed some front-ends, and in this repo it
arms nothing until vendor model ids exist for those two, which is out of scope.

## Business rules

- **Fail closed on every path.** Nothing added here can open the gate for a front-end whose
  recorded line is not exactly `<key>=raise`. A missing line, a non-`raise` verdict, a
  symlinked / absent / unreadable file, a first line that is neither `armed` nor `blocked`,
  and whitespace variants of a line all keep the gate shut.
- **An empty key is the old rule.** With no `--frontend` (or `--frontend ''`), the decision
  is the first line, byte-for-byte as today. A file whose first line is `armed` therefore
  behaves exactly as today for every existing caller.
- **The key is produced by a tool, not by the Orchestrator's judgment.** `tools/host-frontend.sh`
  prints at most one known key from session markers (or the `HARNESS_HOST_AGENT`
  declaration), nothing when it cannot tell, and always exits 0. Its marker rows are a
  parity-tested copy of the installer's `HOST_MARKERS` (E36-F04 precedent for a second copy).
- **The file format is frozen.** The installer writes the same bytes as before this feature;
  `init.sh` and the installer's summary only *report* more when the AND is `blocked` but
  some line is `raise`.
- **`escalation.after_rejections = 0` stays the hard veto**, `delegate` still never
  escalates, and `raise` still means "the stamp changes", not "the stamp is stronger".
- **Out of scope:** vendor model ids for OpenCode or pi in this repo's shims; any harvest of
  `opencode.json` / `.pi/agents` in self mode; a change to the arming file's format.

## Architecture alignment

- ADR-0002 — `builder-heavy` is a tier, not a second prompt: the choice is still pure routing
  between two role names with one body; this feature only changes *which recorded line* the
  routing reads. Amended by ADR-0011.
- ADR-0011 — Escalation arms per front-end: this feature is that decision's implementation —
  `--frontend <key>`, the key-producing tool, the empty-key fallback, the frozen file format.
- ADR-0009 — Stage-aware NFRs: stage is `production`; nothing is deferred (plan `## Deferred`).

## Acceptance criteria (EARS)

- **R1** — When `tools/builder-role.sh` is invoked with `--frontend <key>`, an escalation
  trigger holds (`complexity=complex`, or `round > after_rejections > 0`), and the arming
  file's first line is `armed` or `blocked` and one of its remaining lines is exactly
  `<key>=raise`, the tool shall print `builder-heavy` and exit 0 — including when the first
  line is `blocked` (this repo's own file with `--frontend claude`).
- **R2** — If `--frontend <key>` is given and the arming file's line for `<key>` is anything
  other than `raise` (`none`, `same`, `neither`, `unstamped`, or any other text), then the
  tool shall print `builder`, exit 0, and write one stderr advisory that contains the literal
  `<key>=<recorded-verdict>` — even when the first line is `armed`.
- **R3** — If `--frontend <key>` is given and no remaining line of the arming file begins
  with `<key>=`, then the tool shall print `builder`, exit 0, and write one stderr advisory
  that contains `no verdict is recorded for front-end '<key>'` — even when the first line is
  `armed`.
- **R4** — While `--frontend` is absent or its value is the empty string, the tool shall
  decide exactly as before this feature: `builder-heavy` iff the first line is exactly
  `armed`, with the existing advisories otherwise, and byte-identical stdout for every
  existing suite case.
- **R5** — If the arming file is absent, is a symlink, is unreadable, has a first line that
  is not exactly `armed` or `blocked`, carries the key only as a whitespace variant
  (`claude=raise ` / ` claude=raise` / `claude = raise`), or carries the key twice with the
  **first** `<key>=` line not `raise` (first line wins; the installer never writes
  duplicates), then the tool shall print `builder` and exit 0 whether or not `--frontend`
  is given, and shall never print `builder-heavy` from such a file.
- **R6** — If `--frontend` is the last argument (no value), or its value is not a bare token
  matching `^[a-z][a-z0-9-]*$`, then the tool shall write a usage error to stderr, print
  nothing on stdout, and exit 4 — the same caller-is-broken treatment a non-numeric round
  gets.
- **R7** — When `tools/host-frontend.sh` runs with exactly one front-end's session marker
  set to a non-empty value (per the installer's `HOST_MARKERS` rows), the tool shall print
  that front-end's key and exit 0; when no marker is set, or a marker is set to the empty
  string only, it shall print nothing and exit 0; when markers of two or more front-ends are
  set, it shall print nothing, write one stderr line containing `ambiguous` and every hit
  key, and exit 0. It reads and writes no file and accepts no positional argument (any
  argument other than `-h`/`--help` ⇒ usage, exit 4).
- **R8** — When `HARNESS_HOST_AGENT` is set to exactly one key that has a marker row
  (`claude`, `codex`, `opencode`, `pi`), `tools/host-frontend.sh` shall print that key
  regardless of markers; when it is set to anything else (unknown token, several tokens,
  `host`, or a key with no marker row such as `antigravity`), the tool shall write one
  stderr warning naming the value and continue with marker detection. The tool's marker rows shall equal the installer's
  `HOST_MARKERS` rows (same keys, same variables, same order), verified by a test that reads
  both files.
- **R9** — The installed `agents/orchestrator.md` (`.harness/agents/orchestrator.md`) shall,
  inside its `### Which Builder` section, show the `builder-role.sh` call passing
  `--frontend "$(sh "$HARNESS_DIR/tools/host-frontend.sh")"`, state that an empty key makes
  the tool apply the all-front-ends rule, and forbid the Orchestrator from supplying a key by
  hand (sentences pinned in the plan).
- **R10** — When `init.sh` runs with `escalation.after_rejections > 0` and the arming file's
  first line is `blocked` while at least one remaining line is `<key>=raise`, `init.sh` shall
  print one `ℹ️` line that names every `raise` key and every non-`raise` key and contains
  `per front-end`, and shall not print the DISARMED warning; when the first line is `armed`,
  or no line is `raise`, or the file is absent / a symlink, the existing ARMED line or
  DISARMED warning shall print unchanged. The block shall read the file without a pipeline
  that can take SIGPIPE under `pipefail`, shall never `eval` text derived from the file (a
  line such as `a$(touch X)=raise` prints no key and creates no file), and shall never
  change `init.sh`'s exit status.
- **R11** — When `harness-install.sh` installs a target, it shall ship
  `.harness/tools/host-frontend.sh` executable and byte-identical to the source copy, and
  `write_escalation_arming` shall — when the AND is `blocked` but at least one selected
  front-end is `raise` — print an `info` line containing `per front-end` that names the
  `raise` keys and the non-`raise` keys, while the file it writes stays byte-identical to the
  pre-feature format (first line, then one `<key>=<verdict>` line per selected front-end in
  `$AGENT_KEYS` order).
- **R12** — `VERSION` shall be the next MINOR over the then-current value on `main` and the
  newest `CHANGELOG.md` section shall name `E99-F182`, `--frontend` and
  `tools/host-frontend.sh`; the installed `docs/WORKFLOW.md` and `docs/INSTALL.md` shall
  state that `builder-role.sh` reads the host front-end's own line and that an empty key
  falls back to the first line, and shall no longer state that one misconfigured front-end
  disables escalation everywhere (sentences pinned in the plan).

## Out of scope

- Choosing vendor model ids for OpenCode or pi in this repo's shims; harvesting
  `opencode.json` or `.pi/agents/*.md` under `--self` (brief direction (b), ADR-0011).
- Any change to the arming file's format, to `escalation_verdict`'s four cells, or to the
  `unstamped` verdict.
- A per-host line in `init.sh` ("this host is armed") — `init.sh` names keys, not the host,
  so its output stays independent of the environment it runs in.
- Antigravity: it has no session marker row and no Builder stamp, so marker detection never
  yields it and `HARNESS_HOST_AGENT=antigravity` takes the "ignoring" path (R8) — an
  Antigravity session is always the empty-key path. Adding a marker row for it is E19's
  call, not this feature's.

## Open questions

None. The only decision point — direction (a) vs (b) vs (c) — is settled by ADR-0011.

`_escalate` branch order is stated in the plan; (4) the three further doc/orchestrator
passages stating the old rule are listed in the plan with anchors; (5) mutants M5b/M1b
redefined to real edits, R3 gains the `xclaude=raise` decoy; (6) duplicate keys: first line
wins, pinned in R5; (7) R2's vacuous distinct-answers guard replaced by a branch-text
assertion. Declined: none.
