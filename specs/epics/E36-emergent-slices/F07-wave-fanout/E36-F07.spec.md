# `/sdd-next --wave` fans out one wave into isolated worktrees — Functional Spec

> R-ids in this document are `R1 … R12`; their fully-qualified form is `E36-F07:R1 … E36-F07:R12`.

## Context

E36-F05 shipped the wave view: `node tools/next-task.mjs --waves --json [--epic E##]` prints
the dependency graph as waves and marks, per feature, whether it is `runnable` and
`autonomous`. The operator still turns that view into work by hand — one `/sdd-next <id>` per
machine or per sub-agent, re-typed every session. `/sdd-fix-parallel` already runs a bounded
batch of isolated autonomous E99 fixes through targeted Orchestrator workers in their own
worktrees (`agents/fixer.md` → "Parallel dispatch mode", `agents/orchestrator.md` → "Targeted
parallel-fix worker mode", `tools/fix-worktree.sh`). That lane is fenced to "one exact
autonomous E99 `sdd: false` fix".

This feature widens that fence to `sdd: true` features and connects it to the wave view:
`/sdd-next --wave [--max N] [--epic E##]` reads the first listed wave from the F05 envelope,
takes its runnable, autonomous, `pending` features up to a bounded count, provisions one branch
and one worktree per feature with the existing helper, and runs each through the normal
Orchestrator loop (Architect → Builder → Reviewer → PR) as a targeted worker. The coordinator
prints a summary table and a serialized merge plan; it runs no `/sdd-pr-loop` and merges
nothing (recorded decision in the brief). The user is the operator who drives several
sub-agents from one board on one machine.

**Machine load is a product requirement here.** On 2026-10-25 parallel workers running the
test suite concurrently made the owner's laptop unusable. `tools/run-tests.sh` now enforces one
run per machine (a second run is refused with exit 5, no waiting, no retrying) and caps
`--jobs` at `HARNESS_TEST_JOBS_MAX` (default 4). This spec states how a wave behaves under
that lock: a bounded worker count with a config key and a conservative default (R2), what a
worker does when the runner refuses (R8), and that a killed run is a stop, not a retry (R8).

### Why `complexity: complex`

Three of `agents/architect.md`'s stated bases hold:

1. **At the size budget.** Exactly 12 R-ids against `change_size.max_requirements: 12`; the
   brief expected ~10 and the two machine-load requirements (R2's cap, R8's lock behaviour)
   were added as product requirements by the Orchestrator's brief.
2. **ADR constraints reach across several files.** ADR-0001 (consume the selector's
   envelope, never re-derive) and ADR-0010 (waves derived, never stored; fan-out inherits the
   fix lane's safety properties and adds no state) bind `agents/orchestrator.md`, the
   `sdd-next` emitter in `harness-install.sh`, `tools/fix-worktree.sh`, `harness.config.yaml`,
   the installer's config migration, `docs/WORKFLOW.md` and four suites at once.
3. **A byte contract compared in more than one place.** The `sdd-next` body is one heredoc
   copied to `.claude/commands/`, `.opencode/command/` and `.agents/skills/` and checked by
   `tests/test_self_drift.sh`; the harness has paid for "a body and its copy diverging"
   before (E26-F01).

## Business rules

- **Consume the F05 envelope exactly; never re-derive a wave (ADR-0001, ADR-0010).** The
  coordinator runs `node tools/next-task.mjs --waves --json [--epic E##]` and branches on
  `outcome` first. The wave it fans out is `waves[0]` — the **first listed** wave, whose
  `wave` number can be above 1 under `--epic` (F05 open-questions note). Nothing about a wave
  is written to the board. No second scheduler, no stored plan, no lease field.
- **Eligibility is four envelope fields, nothing else.** A feature record is eligible iff
  `runnable` is `true`, `autonomous` is `true`, `status` is `"pending"`, and `route` is
  `"architect"` (the selector's route for a `pending` `sdd: true` feature; a `pending`
  `sdd: false` fix routes to `builder` and belongs to `/sdd-fix-parallel`). Every other
  record of the wave is reported with the reason it was skipped, never silently dropped.
- **Critical path first, then ADR-0001 order.** Among eligible records the one equal to
  `critical_path[0]` (when it is in the wave) is selected first; the rest follow in the order
  the envelope lists them (ADR-0001 id order). The first `cap` are selected; the remainder are
  `cap-deferred` and stay `pending` for the operator's next run.
- **Bounded worker count, conservative default.** `cap` = `--max N` when given, else
  `workflow.max_wave` from `harness.config.yaml`, else `3`. Both are positive integers;
  anything else stops the run before any mutation. The key lives under `workflow:` — not under
  `workers:`, which is the inert local-only roster (epic Notes).
- **Reuse the fix lane by reference; widen its fence, do not fork it.** Provisioning is
  `tools/fix-worktree.sh create <id> <slug>` — the one create per feature — and the worker is
  the existing "Targeted parallel-fix worker mode" with the wave variations listed in one new
  Orchestrator section. The helper's id grammar widens from `E99-F<n>` to `E<n>-F<n>`; its
  slug grammar, branch (`feat/<id>-<slug>`) and worktree
  (`<primary>/.claude/worktrees/<id>-<slug>`) shapes are unchanged, so the E99 fix lane
  behaves exactly as before.
- **Workers never share a worktree; board writes go to the worker's own board.** Each worker
  sets `HARNESS_DIR` to its own worktree's harness directory (`<worktree>/.harness` in an
  installed target, the worktree itself in the harness source checkout) and writes every transition through
  `python3 "$HARNESS_DIR/tools/tasks-lock.py"`. The explicit override wins over the helper's
  linked-worktree remap (`tools/tasks-lock.py`, precedence rule 1), so a worker's transitions
  land on its own feature branch — the house pattern for every E36 feature so far — and never
  in the primary checkout's `state/tasks.json`. The coordinator never stages, commits,
  switches, stashes, resets or cleans the primary; the primary must be clean at provisioning
  (the helper enforces it).
- **One test runner per machine.** Workers follow `agents/builder.md` step 5: touched suites
  while iterating, the full `verification.test_command` once as a gate per role phase. A gate
  refused with exit 5 is recorded as `runner-busy` and handed back — never re-invoked by the
  worker, never polled. The coordinator re-runs `runner-busy` workers one at a time after the
  parallel wave settles (the fix lane's "guarded exclusive wave" shape), at most once per
  feature. A killed run (signal) is `interrupted`: terminal for this invocation, never
  relaunched, never queued. Nothing here raises `--jobs`; the runner's cap stands.
- **PRs are opened in parallel, merged serially, by order.** A worker stops after opening its
  PR (feature stays `in-review`); it never merges, never runs `/sdd-pr-loop`, never writes
  `done`, never tears down. The coordinator prints the merge order (the selection order) and
  the per-PR integration rule, because `VERSION`, `CHANGELOG.md`, `progress/history.md` and
  `state/tasks.json` conflict between siblings every time: before `/sdd-pr-loop` on PR *k+1*,
  the updated `main` is integrated into that branch with one merge commit, `VERSION` becomes
  the next MINOR over the then-current `main`, this feature's `CHANGELOG.md` entry is placed
  above `main`'s newest entry under that version, and both sides of `progress/history.md` and
  of `state/tasks.json` are kept. The operator runs `/sdd-pr-loop` per PR in that order;
  `done` and teardown follow the normal post-merge path.
- **Wave 2 is not automatic.** After wave 1 merges, the operator re-runs `/sdd-next --wave`;
  the next run derives the next wave from the updated board (ADR-0010).
- **Every new `/sdd-*` flag is generated and asserted.** `--wave` lives in the `sdd-next`
  heredoc in `harness-install.sh`; the committed copies under `.claude/commands/`,
  `.opencode/command/` and `.agents/skills/` are regenerated with `sh harness-install.sh
  --self`; `tests/test_install.sh` asserts the installed bodies.
- **Installed body changes bump VERSION (MINOR).** This adds a capability to role prose, a
  tool, the installer and the config; the release is recorded in `CHANGELOG.md`. No test
  freezes the exact VERSION.

## Architecture alignment

`specs/architecture.md` is absent in this repository. The ADR set under `specs/adr/` is
present, so citations are required. Single-namespace project; bare ids are used. Seeded from
the brief's constraints (ADR-0001, ADR-0010); ADR-0008 added because this feature's tasks and
worker loop are built on it.

- ADR-0001 — next() selection moves from prose routing to a deterministic tool: the
  coordinator consumes `next-task.mjs --waves --json` and branches on its `outcome`, `waves`,
  `critical_path` and per-feature `runnable`/`autonomous`/`status`/`route` fields; it never
  re-derives a wave, a route or a blocker in prose, and each worker drives one exact id through
  the existing targeted mode that already forbids global `next()`.
- ADR-0010 — Waves and the critical path are derived from `depends_on`; the harness stores no
  second plan: fan-out consumes the computed wave and writes nothing about it to the board;
  it inherits the parallel-fix lane's safety properties (worktree isolation, `HARNESS_DIR`
  board writes, serialized merges) and adds no state of its own; wave 2 is a re-run, not a
  stored plan; cross-machine distribution stays `/sdd-next <id>` (non-goal).
- ADR-0008 — Vertical slices are the unit of decomposition; tasks pair one failing test with
  the code that passes it: this feature's `.tasks.md` is per-R-id red/green pairs, and the
  worker loop it fans out is the ordinary Architect → Builder → Reviewer path whose Builder
  works those pairs.

No divergence from any ADR.

## Acceptance criteria (EARS)

> Each is one testable behavior with a stable id. See docs/SPEC-FORMAT.md.
> Prose contracts are asserted on **installed** files with whole-file `grep -qF`; executable
> seams (`fix-worktree.sh`, `tasks-lock.py`, `run-tests.sh`, the installer, the selector) are
> exercised by running them.

- **R1 — Scope token.** When `/sdd-next` is invoked with `--wave`, optionally followed by
  `--max N` and/or `--epic E##`, the generated `sdd-next` body (installed
  `.claude/commands/sdd-next.md`, `.opencode/command/sdd-next.md` and
  `.agents/skills/sdd-next/SKILL.md`, byte-identical) shall map it to the wave coordinator mode
  of `agents/orchestrator.md`; the body shall state that `--wave` is a closed-scope token
  beside `--mine` and `E##-F##`, that it cannot be combined with either, that `--max` and
  `--epic` are valid only after `--wave`, that `N` must match `^[1-9][0-9]*$` and `E##` must
  match `^E[0-9]+$`, and that any other argument shape selects nothing and changes no state.
  Bare `/sdd-next`, `--mine` and `E##-F##` keep their existing wiring (the existing
  `tests/test_install.sh` assertions stay green).
- **R2 — Preflight and cap.** When the wave coordinator starts, it shall, before any
  mutation, run `init.sh`, require native in-session concurrent sub-agent delegation (stop and
  name the missing capability otherwise), require `execution.builder.backend: in-session`
  (stop naming the incompatible backend, including any unknown value), require
  `umbrella.manifest` empty (stop: umbrella coordinators are out of scope), and resolve
  `cap` = `--max N` when given, else `workflow.max_wave`, else `3`; if the configured
  `workflow.max_wave` is present but not a positive integer, then it shall stop naming the
  key. `cap` is the only brake on concurrent workers — there is no hard ceiling, and the
  operator owns any value above the default (the section states this in one sentence).
  Every stop shall point the operator to `/sdd-next <id>` and exit non-zero with no
  worktree, branch, manifest or board change.
- **R3 — Wave read.** When preflight passes, the coordinator shall run
  `node tools/next-task.mjs --waves --json` (installed: `node .harness/tools/next-task.mjs
  --waves --json`) with `--epic E##` forwarded when given, and branch on `outcome` first: if
  `outcome` is `"error"` or `"blocked"`, then it shall print the envelope's `reason.detail`
  and every `blocked[]` record, mutate nothing and exit non-zero; if `outcome` is `"waves"`
  and `waves` is empty, then it shall print exactly `no runnable wave` and exit 0 with no
  mutation; otherwise it shall fan out `waves[0]` — the first listed wave — and print its
  `wave` number (which can be above 1 under `--epic`), never assuming wave 1.
- **R4 — Eligibility, order and cap.** The coordinator shall classify every record of
  `waves[0].features` as exactly one of: `selected` (eligible and within `cap`),
  `cap-deferred` (eligible, beyond `cap`), or `skipped: <reason>` where eligible means
  `runnable == true && autonomous == true && status == "pending" && route == "architect"` and
  `<reason>` names the first failing predicate (`not-runnable` followed by the record's
  `blocked[]` codes in a format the Builder chooses — only the `skipped: not-runnable` prefix
  is pinned — `not-autonomous`, `status:<status>`, or `route:<route>`); selection order shall be
  `critical_path[0]` first when it is eligible and in the wave, then the remaining eligible
  records in the envelope's listed order; a wave with no eligible record shall print
  `no eligible feature in wave <N>` and exit 0 with no mutation.
- **R5 — Provisioning via the widened helper.** `tools/fix-worktree.sh` shall accept any id
  matching `E<digits>-F<digits>` for `create`, `run` and `teardown` (branch
  `feat/<id>-<slug>`, worktree `<primary>/.claude/worktrees/<id>-<slug>`, same locale pin,
  same slug grammar, same clean-primary and base checks; leading zeros allowed, as today's
  `E99-F01`) while still rejecting `E99-Fx`, `E-F1`, `E1F2`, a lowercase `e1-f2`, `E1-F`,
  `E-F`, `E1x-F1`, `E1-x-F1`, `E1-F2-F3`, `E1/../-F1` — any id with a character outside
  `[0-9EF-]`, more or fewer than one `-F`, or a non-digit on either side of it — and every
  existing invalid slug, with no ref or registration mutated on rejection (the id feeds a
  branch name and a worktree path, so the parse is explicit, not a wildcard glob); the
  coordinator shall call `create <id> <slug>` once per
  selected feature, sequentially, before any manifest or board write, with `<slug>` derived
  from the board's `spec_path` as: the last path component, the leading `F<digits>-` removed,
  lowercased, every run of characters outside `[a-z0-9]` collapsed to one `-`, leading and
  trailing `-` trimmed, and `wave` when the result is empty; a feature whose `create` fails
  shall be classified `provisioning-failed: <helper stderr>`, stay `pending`, and not stop its
  siblings.
- **R6 — Manifest before dispatch.** After every selected `create` has settled and before the
  first worker is spawned, the coordinator shall write
  `progress/wave-<YYYYMMDDTHHMMSSZ>/summary.md` listing the wave number, the `cap` and its
  source (`--max`, `workflow.max_wave` or `default`), and one line per record of `waves[0]`
  with its classification from R4/R5 and, for a provisioned feature, its exact branch and
  worktree; no record of the wave shall be absent from the manifest.
- **R7 — Worker identity and board writes.** The coordinator shall spawn every provisioned
  worker before awaiting any one of them, up to `cap`, each as a clean targeted Orchestrator
  worker given exactly: its feature id, the primary's absolute path to its inbox brief (or
  `-` when `progress/inbox/<id>.md` is absent — the Architect's existing fallback to the
  TaskStore title applies), its pre-provisioned branch and worktree, `HARNESS_DIR` set to
  **that worktree's harness directory** (`<worktree>/.harness` installed, the worktree itself in the
  source checkout), and the manifest path; and `agents/orchestrator.md` shall state that a
  wave worker writes every board transition through
  `HARNESS_DIR="<its worktree's harness dir>" python3 "$HARNESS_DIR/tools/tasks-lock.py"`, commits those
  transitions on its own feature branch, reads the feature's status from its own worktree
  board on entry and resumes at that phase (so a re-spawned worker never restarts the
  Architect), and never stages, commits, switches, stashes, resets or cleans the primary.
  Executed check: with a feature worktree provisioned
  by R5 and `HARNESS_DIR` pointing at it, `tasks-lock.py set-status <id> spec-ready` changes
  that worktree's `state/tasks.json` and leaves the primary's `state/tasks.json` byte-identical.
- **R8 — Test-runner lock behaviour.** `agents/orchestrator.md`'s wave section shall state,
  and the installed copy shall carry verbatim: that a worker runs the full
  `verification.test_command` at most once per role phase as a gate and touched suites while
  iterating; that when the runner refuses with exit 5 the worker records `runner-busy`, does
  not re-invoke the runner, leaves the feature at its current status (the Reviewer never
  approves without a green gate) and returns; that the coordinator, after the parallel wave
  settles, re-spawns each `runner-busy` worker one at a time in selection order (same
  inputs; the worker resumes from its worktree board's status, R7) and records a second
  `runner-busy` as the terminal verdict `stopped: runner-busy twice`; and that a worker
  whose sub-agent or tool call was cancelled or killed, or that returned without a verdict,
  is `interrupted` — a stop, never relaunched, never queued — while a runner exit of 1 is a
  red suite and is never reclassified as a signal (the runner itself exits 1 on HUP/INT/TERM;
  the distinction is observed at the worker boundary, not from the exit code). Executed
  check: `tools/run-tests.sh` invoked with a live-pid lock already present in its `TMPDIR`
  exits 5 without running a suite.
- **R9 — Serialized merge plan.** When every worker has settled, the coordinator shall print
  a summary table with one row per selected feature (`feature | branch | PR | verdict`, verdict
  in `pr-opened | interrupted | stopped: <reason>` — `runner-busy` is a worker-return value
  consumed by the exclusive pass and never a final-table verdict), followed by the merge plan:
  the PR order (selection order) and the per-PR rule from the business rules (integrate the
  updated `main` with one merge commit; `VERSION` = next MINOR over then-current `main`;
  `CHANGELOG.md` entry above `main`'s newest entry; keep both sides of `progress/history.md`
  and `state/tasks.json`); it shall run no `/sdd-pr-loop`, perform no merge, write no `done`,
  and tear down no worktree; exit 0 iff every selected feature's verdict is `pr-opened`.
  Executed check: the installed `agents/orchestrator.md`, the installed `sdd-next` body and
  the installed `docs/WORKFLOW.md` each carry the literals `pr-opened`, `runner-busy`,
  `interrupted`, `next MINOR` and `merge order` (lowercase, exactly as the printed plan's
  `merge order:` line spells it).
- **R10 — Config key.** `harness.config.yaml` shall carry `max_wave: 3` under `workflow:`
  with a comment naming `/sdd-next --wave`, and `harness-install.sh` shall seed the same line
  into a preserved target config whose `workflow:` section lacks `max_wave` (inserted under
  the `workflow:` header when present, appended with a new `workflow:` header otherwise),
  without touching a config that already has it; a fresh install's `.harness/harness.config.yaml`
  shall contain a line matching `^[[:space:]]+max_wave:[[:space:]]+3`.
- **R11 — Role, command and docs prose.** `agents/orchestrator.md` shall gain a section headed
  `## Wave coordinator mode (/sdd-next --wave)` that references `agents/fixer.md`'s
  "Parallel dispatch mode" for provisioning, manifest and fan-out discipline by name (not by
  copy) and lists the wave variations of the targeted worker; its
  `## Targeted parallel-fix worker mode` section's entry guard shall be amended to also admit
  one exact autonomous `sdd: true` feature supplied by `/sdd-next --wave`, keeping that
  section's existing literals (one `tools/fix-worktree.sh create` mention, `never call global
  \`next()\``, `create only its dedicated PR`, `report \`merge-observed\``) unchanged; the
  `sdd-next` heredoc shall reference the new section by its heading; `docs/WORKFLOW.md`'s
  `## Running in waves and across machines` section shall gain a `### Fanning out a wave
  (\`/sdd-next --wave\`)` subsection; the committed generated copies shall be regenerated
  with `sh harness-install.sh --self` so `tests/test_self_drift.sh` stays green. Installed
  `.harness/agents/orchestrator.md`, the three `sdd-next` bodies and
  `.harness/docs/WORKFLOW.md` shall each contain the literal `/sdd-next --wave`.
- **R12 — Release record.** The release shall bump `VERSION` by MINOR from the then-current
  value and add a matching `CHANGELOG.md` entry naming `--wave` and `workflow.max_wave`. The
  suite shall assert only durable facts: `VERSION` equals the newest `CHANGELOG.md` heading
  (derived, never a literal) and **some** `## [x.y.z]` entry mentions `--wave` — never "the top
  entry".

## Out of scope

- Running wave 2 automatically; the operator re-runs after wave 1 merges (brief).
- Running `/sdd-pr-loop`, merging, rolling `done`, or tearing down worktrees from the
  coordinator (recorded decision; the normal post-merge path owns them).
- Owner scoping (`--mine`) under `--wave`, umbrella coordinators (`umbrella.manifest`
  non-empty) and `slices[]` features — preflight refuses umbrella mode; a sliced feature is
  not reachable because it is never `route: architect` at `pending` in a non-umbrella repo.
- Cross-machine distribution and any lease/claim field (ADR-0010 non-goals).
- Changing the E99 fix lane's behaviour (`agents/fixer.md`, `/sdd-fix-parallel`) — the only
  shared change is the helper's id grammar, which is a superset.
- A bookkeeping branch / canonical-`HARNESS_DIR` claim as in the fix lane: the brief's
  recorded choice is per-worker `HARNESS_DIR` and transitions on the feature branch.
- Changing `tools/next-task.mjs`, `tools/tasks-lock.py` or `tools/run-tests.sh`.

## Open questions

None blocking. Two decisions are recorded rather than left implicit:

- **Why no atomic pre-claim.** The fix lane claims `pending → in-progress` under one lock
  because its features skip the Architect. Here the first phase is the Architect and the
  feature's first transition is `pending → spec-ready` inside the worker; a same-machine
  second `/sdd-next` during a wave is the documented ADR-0010 limitation, not a race this
  feature solves.
- **Doc-critic checkpoint (2026-10-26) applied.** Accepted: explicit id parse in the helper
  (wildcard globs admitted `E1x-F1`); `stopped: runner-busy twice` named and `runner-busy`
  removed from the final-table vocabulary; `interrupted` defined at the worker boundary; a
  re-spawned worker resumes from its worktree board; `merge order` literal matched to the
  printed line; `not-runnable` detail format left to the Builder; `env -u HARNESS_DIR` on the
  R7 control; cap stated as the only brake; brief path from the primary with the title
  fallback; README row dropped (YAGNI). Declined: splitting R5 into three R-ids — the spec is
  at the 12-R-id budget and the clauses are enumerated per assertion in `E36-F07.tests.md`
  and T6a instead.
- **Why the exclusive pass instead of a wait.** Waiting on the runner lock is exactly the
  fight the 2026-10-25 rule forbids; a bounded second pass, one worker at a time, is the fix
  lane's existing "guarded exclusive wave" shape and needs no polling.
