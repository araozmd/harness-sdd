# Derived waves and critical path — Test Contract

> The traceability matrix: every R-id in the `.spec.md` maps to a concrete, executable
> test. The Reviewer fails the feature if any R-id lacks a passing test.
>
> New cases live in `tests/test_waves.sh` (POSIX `sh`, `set -eu`, `fail`/`pass`, fixtures
> under `mktemp -d`, `--tasks`/`--config` pointing at the fixture — never the live board).
> JSON is read with the `json_field` python3 helper from `tests/test_next_task.sh`. The
> suite is picked up by `tools/run-tests.sh`'s `tests/test_*.sh` glob and runs under dash;
> `tests/dash-allowlist.txt` gains no entry (it is comment-only today and stays so). Fixtures list features in non-canonical input
> order so an implementation that leaks input order reds.
>
> Notation: `A -> B` in a fixture or chain means "B depends on A" (A unblocks B; chains read
> root first). The cycle witness string (`E1-F1 -> E1-F2 -> E1-F1`) is the selector's own
> `depends_on`-oriented output, reused verbatim.
