# Derived waves and critical path — Technical Plan

> Translates the .spec.md intent into design. Every decision cites the R-id(s) it serves.
> Start high-level; the Builder picks internals not pinned here.

## Stack & dependencies

- Language: Node.js ESM (`tools/next-task.mjs`, `node:` built-ins only), POSIX `sh` tests

## Data model  (serves: R3, R4, R5, R6, R7)

Nothing is stored (ADR-0010). The only new data is the **wave envelope** the tool emits.
It extends the existing `envelope()` shape so generic consumers still find
`schema_version / mode / outcome / selected / reason / blocked / summary`:

| Field | Type | Notes | R-id |
|---|---|---|---|
| `schema_version` | `1` | unchanged | R3 |
| `mode` | `"waves"` | new mode value beside `board`, `mine`, `target` | R1, R3 |
| `outcome` | `"waves"` \| `"blocked"` \| `"error"` | `waves` = valid graph; `blocked` = invalid graph (R6); `error` = existing input/usage error path | R3, R6 |
| `selected` | `null` | always null in waves mode | R3 |
| `reason` | `{code, detail}` | valid: `code: "waves-derived"`, `detail` = the summary; invalid: `code: "invalid-graph"` | R3, R6 |
| `blocked` | array | valid: `[]`; invalid: the offending features' existing `dependency-cycle` / `unmet-dependency` records (`{subject, code, detail}`) | R6 |
| `summary` | string | e.g. `3 waves over 7 features; critical path 3 features` or `waves undefined: dependency graph is invalid; see reasons above` | R3, R6 |
| `scope` | `{ "epic": string \| null }` | `null` = whole board | R4 |
| `wave0` | `string[]` | in-scope `done` ids, ADR-0001 order; `[]` on invalid graph | R3, R6 |
| `waves` | `{ wave: int, features: FeatureRecord[] }[]` | ascending `wave`, non-empty waves only; `[]` on invalid graph | R3, R6 |
| `critical_path` | `string[]` | root first; `[]` when no non-done in-scope feature or invalid graph | R7 |

`FeatureRecord` (R5), exactly these keys:

| Field | Type | Source |
|---|---|---|
| `id` | string | `feature.id` |
| `status` | string | `feature.status` |
| `route` | string \| null | `featureRoute(feature, config.requireApproval)` |
| `autonomous` | boolean | `feature.autonomous === true` |
| `owner` | string \| null | `feature.owner ?? feature.epic.owner ?? null` (same precedence as `--mine`) |
| `runnable` | boolean | `blocked.length === 0 && route !== null` (the selector's `otherwiseActionable`) |
| `blocked` | record[] | `featureBlockers(feature, featureById, cycles, config.requireApproval)` unchanged |

Worked example of the valid-graph envelope (the shape E36-F07 consumes; `--waves --epic E1 --json`
on a board where `E1-F1` is done, `E1-F2` depends on it and is parked, `E1-F3` depends on `E1-F2`):

```json
{"schema_version":1,"mode":"waves","outcome":"waves","selected":null,
 "reason":{"code":"waves-derived","detail":"2 waves over 2 features (+1 done); critical path 2 features"},
 "blocked":[],"summary":"2 waves over 2 features (+1 done); critical path 2 features",
 "scope":{"epic":"E1"},"wave0":["E1-F1"],
 "waves":[
  {"wave":1,"features":[{"id":"E1-F2","status":"pending","route":"architect","autonomous":true,"owner":null,"runnable":false,
    "blocked":[{"subject":"E1-F2","code":"parked","detail":"vendor keys pending [route when unparked: architect]"}]}]},
  {"wave":2,"features":[{"id":"E1-F3","status":"pending","route":"architect","autonomous":true,"owner":null,"runnable":false,
    "blocked":[{"subject":"E1-F3","code":"unmet-dependency","detail":"blocking dependencies: E1-F2=pending (parked: vendor keys pending)"}]}]}
 ],
 "critical_path":["E1-F2","E1-F3"]}
```

The real output is one line; it is wrapped here for reading. `summary` wording is the Builder's
(R3 requires only non-empty); every other value above is pinned by R3–R7.
An `outcome: "error"` envelope (usage/input error) is the existing seven-key shape with none
of the four wave fields; its `mode` is `"board"` when `parseArgs` threw (the catch block sees
the default args) and `"waves"` for an `input-error` raised after parsing (missing epic,
unreadable board). Consumers branch on `outcome` first (R3).

## CLI / interface  (serves: R1, R2, R4, R8)

| Invocation | Result | R-id |
|---|---|---|
| `--waves` | human report for the whole board, exit 0 | R1, R8 |
| `--waves --json` | one JSON wave envelope, exit 0 | R3 |
| `--waves --epic E36 [--json]` | same, filtered to E36's features | R4 |
| `--waves --feature X` / `--waves --mine` / `--epic E1` alone / `--epic` bad value / repeated flag | `usage-error` envelope + stderr diagnostic + usage synopsis, exit 2 | R1, R2 |
| `--waves --epic E77` (epic absent) | `input-error` envelope, exit 1 | R4 |
| `--waves` on a board with a live cycle or a missing `depends_on` id | `outcome: "blocked"`, `reason.code: "invalid-graph"`, exit 0 | R6 |
| any unknown flag (any mode) | stderr gains the usage synopsis line | R2 |

Usage synopsis (one line, the Builder may wrap only if the literal `--waves [--epic E##]`
stays intact):

```
usage: next-task.mjs [--json] [--mine | --feature E##-F## | --waves [--epic E##]] [--tasks <path>] [--config <path>]
```

Emit it on stderr after the existing `next-task: <detail>` line, only when
`code === 'usage-error'`. The JSON `reason.detail` stays the specific message it is today
(Orchestrator consumers parse it; the synopsis is for the human).

Human report (R8) — the JSON is the contract; the text is pinned only by the anchors in the
spec. Reference shape:

```
Waves — whole board                      (or: Waves — epic E36)
Wave 0 (done): 3 features
Wave 1 (2 features, 1 autonomous)
  E36-F01  pending  architect  auto  runnable
  E36-F03  pending  architect  -     [parked] vendor keys pending [route when unparked: architect]
Wave 2 (1 feature, 1 autonomous)
  E36-F04  pending  architect  auto  [unmet-dependency] blocking dependencies: E36-F03=pending
Critical path (2): E36-F03 -> E36-F04
```

Edge lines (R8): `Critical path (0): none` when no non-done feature is in scope;
`Critical path (1): E36-F01` for a one-feature path (no arrow). On an invalid graph (R6)
the human report's first line is `Waves undefined: dependency graph is invalid`, followed by
one `blocked <id> [<code>]: <detail>` line per record (the format `docs/WORKFLOW.md` already
shows for blocked selection), exit 0. Usage/input errors are unchanged: JSON error envelope
on stdout, diagnostic on stderr, in text and `--json` form alike.

Notation used in this plan and in the tests: `A -> B` in a chain or wave fixture means
"B depends on A" (A unblocks B; chains read root first). The cycle **witness** string the
selector emits (`E1-F1 -> E1-F2 -> E1-F1`) follows `depends_on` edges, as `cycleMap` prints
it today — that string is reused verbatim, not re-oriented.

## Approach notes

**Wave assignment (R3).** After `validateBoard`, sort features with `compareIds`, build
`featureById`, compute `cycles = cycleMap(features, 'feature')` and `blockers` per non-done
feature with `featureBlockers`. Validity (R6) first: a non-done feature whose blockers contain
a `dependency-cycle` record, or whose `depends_on` names an id not in `featureById`, makes
the whole graph invalid — return the blocked envelope with exactly those features'
`dependency-cycle` / `unmet-dependency` records and **no other code** (a cyclic feature's
`human-gate` or `parked` record is not a graph fault; the `unmet-dependency` detail already
renders `<id>=missing`). This reuses the selector's E99-F155 gating for free: a stale cycle
has no `dependency-cycle` record because `unmet` is empty, so it is valid and lands in wave 1.
Then waves: memoized `wave(id)` = 0 if done, else `1 + max(wave(dep))` (max over an empty
set is 0). The graph is acyclic at this point, so recursion terminates. Group by wave,
sort ids inside each group, drop empty groups.

**Scope (R4).** Compute everything on the whole board; filter `wave0`, `waves[].features`
and the critical-path candidates to `feature.epic.id === args.epic` when set. Resolve the
epic's existence from `model.epics` before computing anything and throw
`ExpectedError('input-error', ...)` when absent — the same shape as a missing `--feature`
target; this is why a missing epic wins over `invalid-graph` (R4 states the precedence).
Validity is **not** filtered (spec Open questions).

**Invalid-graph `blocked` ordering (R6).** Iterate the sorted feature list; for each
offending non-done feature push its `featureBlockers` records in the order that function
returns them (`dependency-cycle` before `unmet-dependency`). Dependents that are merely
blocked by an offending feature contribute nothing.

**Critical path (R7).** Over the in-scope non-done features, with edges `dep -> feature`
only when both ends are in scope and non-done. Longest path by node count; because the
graph is acyclic, a memoized "best chain starting at node" works: `best(id)` =
`[id]` concatenated with the best chain among in-scope non-done dependents of `id`
(dependents = features whose `depends_on` includes `id`), choosing by (length desc, then
lexicographic `compareIds` position by position). The overall answer is the best over all
roots (features with no in-scope non-done dependency), by the same comparator. Root first
means the chain runs from the lowest wave upward.

**Human report (R8).** Build the envelope first, then format it; never compute twice.
Headings and rows per the shape above; keep the anchors the spec pins.

**No-op `--json` in other modes (R8).** `parseArgs` already records `--json` in `seen`;
return `json: seen.has('--json')` on the args object and consult it only in waves mode.

**Error path.** The catch block already emits `envelope(args.mode || 'board', 'error', ...)`;
leave it and add the synopsis line to stderr when `code === 'usage-error'` (R2).

**Driller prose (R10).** The source repo runs `node tools/next-task.mjs`; an installed
target runs `node .harness/tools/next-task.mjs` — `agents/driller.md` already uses this
two-path pattern for `tasks-lock.py`; follow it. The emitter heredoc speaks only the
installed path. After editing the heredoc, run `sh harness-install.sh --self` and commit
every regenerated file; `tests/test_self_drift.sh` fails otherwise.

**Lessons carried (progress/lessons.md).** Never assert an exact exit code for a lookup
miss (assert `≠ 0` or the documented 1/2); the R2 installer assertion must execute the
installed file (an assertion reachable by `grep` on source proves nothing about the install);
fixtures list features in non-canonical order so an input-order implementation reds; tie
fixtures must discriminate "least by `compareIds`" from "first in input" and from "smallest
root only"; use whole-file `grep -qF` for prose contracts, not the fence-blind section
extractor; never freeze VERSION; never `git diff` a DO-NOT-TOUCH file against `main` — use
`cksum` before/after inside the suite.
