# Derived waves and critical path — Functional Spec

> R-ids in this document are `R1 … R12`; their fully-qualified form is `E36-F05:R1 … E36-F05:R12`.

## Context

The roadmap's parallelism already exists on the board as `depends_on` edges, but only the
deterministic selector (`tools/next-task.mjs`, ADR-0001) consumes it, one feature at a time.
So the operator re-types "build this in waves, critical path first, fan the rest out" into
every session and hand-picks which feature runs on which machine. ADR-0010 decides that waves
are a **projection** of `depends_on`, never stored. This feature ships the projection:

- `node tools/next-task.mjs --waves [--json] [--epic E##]` prints the waves, the critical
  path, and which wave-1 features are `autonomous: true`;
- the Driller's completion report ends with that view for the epic it just seeded, through
  `agents/driller.md` and the `sdd-drill` emitter in `harness-install.sh`;
- `docs/WORKFLOW.md` explains how to run a wave across machines with the primitives that
  already exist (`/sdd-next <id>`, `--mine` with `owner`).

The user is the operator who drives several machines or sub-agents from one board, and
E36-F07, which will consume the JSON to fan out wave 1. Nothing here writes to the board,
spawns anything, or adds a lease/claim field (ADR-0010 non-goals).

### Why `complexity: complex`

Three of `agents/architect.md`'s stated bases hold:

1. **At the size budget.** Exactly 12 R-ids against `change_size.max_requirements: 12`;
   E36-F07 (fan-out) was already split off at the seam "read-only view" vs "the operation
   that spawns workers and writes state".
2. **ADR constraints reach across several files.** ADR-0001 (one selector, one validator,
   reuse the E16-F01 reason vocabulary verbatim) and ADR-0010 (waves derived, never stored)
   bind `tools/next-task.mjs`, `agents/driller.md`, the `sdd-drill` emitter, `docs/WORKFLOW.md`
   and three suites at once.
3. **A byte contract compared in more than one place.** The `sdd-drill` body is one heredoc
   copied to `.claude/commands/`, `.opencode/command/` and `.agents/skills/` and checked by
   `tests/test_self_drift.sh`; the installed `next-task.mjs` is `cmp`'d against source by
   `tests/test_install.sh`. The harness has paid for "a body and its copy diverging" before
   (E26-F01).

## Business rules

- **Wave definition (verbatim with ADR-0010 and shared with E36-F07).** `done` features are
  wave 0; wave N is the set of non-done features whose every dependency is in a wave below
  N; a feature with no dependencies is wave 1. Equivalently: a non-done feature's wave is
  1 + the maximum wave of its dependencies, with `done` dependencies counting as wave 0.
- **One selector, one graph validator (ADR-0001).** Waves are computed inside
  `tools/next-task.mjs` by one new function, reusing the existing `validateBoard`,
  `cycleMap`, `featureBlockers` and `featureRoute`. No second tool, no second graph walk in
  another language. `tools/task-diagnostics.py` is not changed: every reason code the view
  needs already exists.
- **Reason codes, not a second vocabulary.** Parked and gated features keep their computed
  wave and are shown with the exact blocker records the selector already emits (`parked`,
  `gated-owner`, `awaiting-merge`, `gated-epic`, `human-gate`, `unmet-dependency`). The
  view explains why a feature is not runnable without inventing new words for it.
- **Never invent a wave for an invalid graph.** A live dependency cycle or a `depends_on`
  naming an id absent from the board makes the waves undefined. The tool then reports the
  existing cycle-witness / `=missing` records and emits no wave at all. A **stale** cycle,
  whose cyclic feature has every dependency `done` (E99-F155), is not invalid: the selector
  already treats it as actionable, and the view agrees.
- **Critical path.** The longest chain of non-done features by feature count, following
  `depends_on` edges, listed root first; ties broken by ADR-0001 order (`compareIds`,
  position by position). `done` features are wave 0 and never part of the chain.
- **Whole board by default; `--epic` filters.** The brief's open question is resolved as
  proposed: `--waves` alone covers the whole board. `--epic E##` lists only that epic's
  features, but wave numbers are still computed against the whole board (a dependency in
  another epic still counts), because the graph is the board.
- **Read-only, no new state, no new dependency.** No board write, no schema field, no lease.
  `node` is already the selector's only dependency.
- **Generated glue is never hand-edited.** The `sdd-drill` body changes in its emitter in
  `harness-install.sh`; the committed copies under `.claude/commands/`, `.opencode/command/`
  and `.agents/skills/` are regenerated with `sh harness-install.sh --self` and committed.
- **Installed body changes bump VERSION (MINOR).** This adds a capability to an installed
  tool and to role prose; the release is recorded in `CHANGELOG.md`. No test freezes the
  exact VERSION.

## Architecture alignment

`specs/architecture.md` is absent in this repository. The ADR set under `specs/adr/` is
present, so citations are required. Single-namespace project; bare ids are used. Seeded from
the brief's constraints (ADR-0001, ADR-0010).

- ADR-0001 — next() selection moves from prose routing to a deterministic tool: the wave
  view is one more read-only projection computed inside `tools/next-task.mjs`, reusing its
  validator, cycle detection, blocker records and the E16-F01 reason vocabulary verbatim;
  tie-breaks use the selector's own id order; nothing is re-derived in prose.
- ADR-0010 — Waves and the critical path are derived from `depends_on`; the harness stores
  no second plan: the wave definition and the critical-path rule above are the ADR's text;
  nothing about a wave is written to the board; `/sdd-next <id>` per machine stays the
  multi-machine primitive and the "identical boards pick the same feature" limitation is
  documented, not hidden.

No divergence from either ADR.

## Acceptance criteria (EARS)

> Each is one testable behavior with a stable id. See docs/SPEC-FORMAT.md.
> The `--json` output is the contract; `tests/test_waves.sh` asserts it field by field.

- **R1** — When `tools/next-task.mjs` is invoked with `--waves`, optionally with `--epic E##`,
  `--json`, `--tasks <path>` and `--config <path>`, `parseArgs` shall accept the arguments
  and select mode `waves`. If `--waves` is combined with `--feature` or with `--mine`, or
  `--epic` is given without `--waves`, or `--epic`'s value is missing, empty, starts with
  `--`, or does not match `^E\d+$`, or `--waves`/`--epic` is repeated, then the tool shall
  emit the existing `usage-error` JSON envelope (`outcome: "error"`), diagnose on stderr, and
  exit 2. In `board`, `mine` and `target` modes `--json` shall remain an exact no-op
  (regression guard for the existing contract).
- **R2** — If `parseArgs` raises a `usage-error`, then the stderr diagnostic shall include one
  line beginning `usage:` that contains the literal `--waves [--epic E##]` (the JSON
  `reason.detail` keeps today's specific message); the installed copy at
  `.harness/tools/next-task.mjs` shall print the same `usage:` line when run with an unknown
  flag (asserted by executing the installed file, not by reading source).
- **R3** — When `--waves --json` runs against a valid dependency graph, the tool shall emit
  one JSON line with `schema_version: 1`, `mode: "waves"`, `outcome: "waves"`,
  `selected: null`, `reason.code: "waves-derived"`, a non-empty `summary`, a `scope` object
  (R4), `wave0` = the in-scope `done` feature ids, and `waves` = an array of
  `{ "wave": N, "features": [...] }` objects in ascending N, listing only non-empty waves,
  where each non-done feature's N is 1 + the maximum N of its dependencies (a `done`
  dependency counts as 0; a feature with no dependencies is in wave 1), and the ids inside
  `wave0` and inside each wave are in ADR-0001 order regardless of board input order;
  on this path `reason.detail` shall equal `summary`. Verified on a linear chain, a diamond,
  and two independent components. The four wave fields (`scope`, `wave0`, `waves`,
  `critical_path`) exist only when `outcome` is `waves` or `blocked`: an `outcome: "error"`
  envelope keeps today's seven-key shape without them, with `mode: "board"` when `parseArgs`
  itself threw (the catch block sees the default args) and `mode: "waves"` for an
  `input-error` raised after parsing — a consumer (E36-F07) branches on `outcome` first.
- **R4** — The tool shall compute waves over the whole board when `--epic` is absent
  (`scope.epic` = `null`); when `--epic E##` names an existing epic, it shall list in
  `wave0`, `waves` and `critical_path` only that epic's features while keeping each
  feature's board-wide wave number (`scope.epic` = the id); if `--epic` names an epic absent
  from the board, then the tool shall emit the `input-error` envelope and exit 1 — this
  check runs before the graph is examined, so a missing epic wins over R6's `invalid-graph`.
- **R5** — Each feature record in `waves[].features[]` shall carry exactly the fields
  `id`, `status`, `route` (the selector's `featureRoute` result or `null`), `autonomous`
  (`true` only when the board says `autonomous: true`), `owner` (the effective owner —
  feature, then epic, else `null`; carried for the per-machine `--mine`/`owner` choice R11
  documents), `runnable` (`true` only when `blocked` is empty and
  `route` is not `null`), and `blocked` — the exact records `featureBlockers` produces for
  that feature, same `code` and `detail` strings. A parked or gated feature shall keep its
  computed wave and show its records. `runnable` is the selector's feature-level
  `otherwiseActionable` predicate: it does not consult slice readiness (`slicePhase`) or
  `--mine` owner scoping — a consumer (E36-F07) that fans out must apply those itself.
- **R6** — If any non-done feature on the board (in or out of `--epic` scope) carries a
  `dependency-cycle` record or names a `depends_on` id absent from the board, then the tool
  shall emit `outcome: "blocked"`, `reason.code: "invalid-graph"`, the `scope` object, a
  `blocked` array holding — for exactly those offending features (not their mere
  dependents), in ADR-0001 id order and, per feature, in `featureBlockers` record order —
  only their existing `dependency-cycle` and `unmet-dependency` (`<id>=missing`) records (no
  record of any other code, e.g. `human-gate` or `parked`, appears), and empty `wave0`,
  `waves` and `critical_path`, exiting 0. A stale cycle whose cyclic feature
  has every dependency `done` shall not trigger this and shall place that feature in wave 1.
- **R7** — The tool shall emit `critical_path` as the ids, root first, of the longest chain of
  non-done in-scope features linked by `depends_on` edges, measured by feature count; when
  several chains share the maximum length it shall pick the chain that is least in ADR-0001
  order compared position by position; `critical_path` shall be `[]` when no non-done
  feature is in scope.
- **R8** — While `--waves` runs without `--json`, the tool shall print a human report whose
  first line names the scope (`whole board` or the epic id), then one line matching
  `^Wave 0 \(done\): <count>`, then for each non-empty wave a heading matching
  `^Wave <N> \(` followed by one row per feature starting with two spaces and the id and
  whose whitespace-delimited fields are: the id, the `status`, the `route` or `-` when
  `null`, `auto` when `autonomous` is true or `-` otherwise, then `runnable` when `runnable`
  is true or one `[<code>]` field per blocker (tests match fields, never substrings — a
  blocker detail may contain the words `runnable` or `auto`); and a final line matching
  `^Critical path \(<n>\): A -> B` (`Critical path (0): none` when the path is empty; a
  one-feature path prints the bare id). On an invalid graph (R6) the text report shall start
  with `Waves undefined` and print one `blocked <id> [<code>]: <detail>` line per record,
  exiting 0. With `--json` it shall print the JSON line only. Usage and input errors keep
  the JSON error envelope on stdout in both text and `--json` form.
- **R9** — A `--waves` run shall not write to the TaskStore or to any other file (the
  fixture board's `cksum`, and those of `tools/task-diagnostics.py`,
  `store/tasks.schema.json` and `init.sh`, are identical before and after the suite), and
  `tools/next-task.mjs` shall import only `node:` built-in modules: every `import`
  statement line (`^import … from '<spec>'` or `^import '<spec>'`) names a `node:` specifier,
  and the file contains no `import(` and no `require(`. The scan is anchored to statement
  lines, not to the word `from`, which already occurs inside a comment. That the feature diff leaves the three
  protected files unchanged is the Reviewer's check (DO NOT TOUCH list), not the suite's.
- **R10** — `agents/driller.md`'s `## Completion report` section shall instruct the Driller
  to **end** its report with the output of `node tools/next-task.mjs --waves --epic <epic-id>`
  (`node .harness/tools/next-task.mjs ...` in an installed target); the `sdd-drill` heredoc
  in `harness-install.sh` shall carry the same instruction in its final report step; the
  committed generated copies shall be regenerated with `sh harness-install.sh --self` so
  `tests/test_self_drift.sh` stays green; and an installed target's
  `.harness/agents/driller.md` and `.claude/commands/sdd-drill.md` shall both contain the
  literal `--waves --epic` **inside** their completion-report section / report step — the
  line range from the `## Completion report` heading (resp. the `12. **Report**` line) to the
  next `## ` heading (resp. the next numbered step) or end of file.
- **R11** — `docs/WORKFLOW.md` shall gain a section headed
  `## Running in waves and across machines` that states: the wave definition and the
  `--waves [--json] [--epic E##]` invocation; that the operator reads wave 1 and runs
  `/sdd-next <id>` per machine; that `--mine` with `owner` is the alternative scoping; the
  known limitation that bare `/sdd-next` on identical boards picks the same feature; and
  that waves are never stored (ADR-0010).
- **R12** — The release shall bump `VERSION` by MINOR from the current value and add a
  matching `CHANGELOG.md` entry naming `--waves`. The suite shall assert only durable facts:
  `VERSION` equals the newest `CHANGELOG.md` heading (derived, never a literal) and **some**
  `## [x.y.z]` entry mentions `--waves` — never "the top entry", which the next release
  would falsify (permanent-suite anti-pattern).

## Out of scope

- Spawning or fanning out anything, `/sdd-next --wave`, worktrees, board locks (E36-F07).
- Any board write, schema field, stored wave plan, lane assignment, or lease/claim field
  (ADR-0010 non-goals).
- Slice-level waves: the `slices[]` graph is intra-feature and stays with `slicePhase`.
- Changing selection in `board`, `mine` or `target` modes, or any reason-code text.
- Changing `tools/task-diagnostics.py` or `init.sh`'s warn-only cycle sweep.
- A `--help` flag: the usage synopsis rides on the existing `usage-error` path.
- README or `docs/HARNESS.md` edits beyond what the Builder finds necessary to keep
  cross-references true (the required doc is `docs/WORKFLOW.md`).

## Open questions

None remain for approval. The brief's open question is resolved: `--waves` defaults to the
whole board; `--epic` filters the listing while wave numbers stay board-wide (R4). Two
consequences are recorded for E36-F07 rather than left implicit:

- With `--epic`, the listed waves may start above 1 (a dependency in another epic). F07 should
  read the first listed wave, or run without `--epic`.
- Graph validity (R6) is judged board-wide even with `--epic`: a dangling `depends_on` in
  another epic suppresses every wave. This is the strict reading of "never invent a wave for
  an invalid graph"; relaxing it to the scope's transitive closure is a possible later PATCH.
