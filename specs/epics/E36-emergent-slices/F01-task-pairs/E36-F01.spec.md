# Per-requirement red/green task pairs — Functional Spec

> R-ids in this document are `R1 … R12`; their fully-qualified form is `E36-F01:R1 … E36-F01:R12`.

## Context

`specs/_templates/feature.tasks.md` orders a feature as `T1..T4` code steps, then
`T5 — Write tests per <feature>.tests.md`, then `T6 — run green`. `agents/builder.md` tells
the Builder to work that list top to bottom, so every feature is built as one layered chunk
and verified only at the end, by reading. That contradicts the `.tests.md` contract the
Architect writes first, and it is the in-feature cause of the "big horizontal chunks" the
operator sees in review. ADR-0008 decision 2 records the fix; this feature ships it.

The user is anyone running the Architect → Builder → Reviewer loop, in this repo or in a
consumer repo that installed the harness. After this feature, a generated `.tasks.md` lists,
for every `R-id`, one task that writes the failing test named in `.tests.md` (observed RED)
followed by one task that writes the minimal code to pass it (observed GREEN); the Builder
commits after each GREEN; and a small lint, `tools/tasks-pair-check.py`, turns the shape
into an exit code the Reviewer rejects on. Prose is the pointer; the template shape and the
tool are the mechanism (docs/RATIONALE.md, structural over compliance).

**Complexity basis.** `complex`, on two stated signals from `agents/architect.md`:

- the spec sits exactly at `change_size.max_requirements` (12 of 12); the seam I would
  split on (lint vs. prose/template) would ship a tool nothing runs, or prose nothing
  enforces, so it is not split;
- it carries one grammar in more than one place — the lint's definition of a test task, the
  template's example, `docs/SPEC-FORMAT.md`'s description and `agents/architect.md`'s item
  3 — and this feature's **own** `.tasks.md` must satisfy that grammar (dogfood). A
  validator that disagrees with its schema is a defect class the harness has already paid
  for (lessons 2026-09-05, 2026-09-16).

## Business rules

- **Pairs are per `R-id`** — not per file, not per layer (ADR-0008 decision 2). For every
  `R-id` in the `.spec.md`, `.tasks.md` carries `T<n>a (R#)` — write the failing test named
  in `.tests.md`; observe RED — followed by `T<n>b (R#)` — the minimal code to pass it;
  observe GREEN.
- **Order by observability.** Pairs are ordered so the walking-skeleton `R-id` — the thinnest
  end-to-end behavior observable at the product boundary (ADR-0008 decision 1) — comes first.
  The lint does not check order; the Architect and the doc-critic do.
- **Refactor tasks are explicit** and cite the `R-id`s whose tests guard them
  (`**T<n>** (R1, R2) — refactor …`). Setup or verify tasks with no `R-id` are allowed, with
  one exception: a task that cites no `R-id` and reads "write … tests" is the layered shape
  this feature removes, wherever it sits in the list.
- **The lint's grammar is the contract.** Outside fenced code (the CommonMark rule
  `tests/lib/fence.awk` encodes), a spec `R-id` is a line `- **R<n>** …`; a task is a line
  `- [ ] **T<n>[a|b]** (R#, R#) — text` (or `- [x]`), the `T` and the suffix matched in
  either case. Suffix `a`/`A` is a test task, `b`/`B` a code task, none is "other". Cited `R-id`s are the explicit `R<n>` tokens inside the parentheses;
  a range such as `R1–R4` is **not** expanded — cite each id. The `.tests.md` traceability
  table is **not** read by the lint and is unchanged by this feature.
- **Behavioral (Playwright / e2e) requirements** (resolves the brief's open question). An
  `R-id` whose only verification is a behavioral row gets its own pair by default: its RED
  is the e2e spec failing against the running app. Where it exercises the same code path as
  another `R-id`'s pair, the Architect may **group** it by co-citing it on that pair's `a`
  task (`**T2a** (R2, R4) — …`); the lint treats a co-cited `a` task as that `R-id`'s first
  task. A behavioral `R-id` therefore obeys the same first-task rule as every other `R-id` —
  never a code-only first task — and that is all the lint enforces: it cannot tell which
  `R-id`s are behavioral, and whether the e2e RED was actually observed is the Reviewer's
  check #3 (behavior), not item 7. This is Architect guidance recorded in SPEC-FORMAT.
- **A task suffix other than a single `a`/`b`** (any case — e.g. `**T1c**`, `**T1ab**`;
  `**T1B**` is a code task) parses as kind "other" — never silently dropped — so a `T1c (R1)`,
  `T1ab (R1)` or `T1B (R1)` first task is reported as `first-task-not-test R1 <T-id>`, the
  T-id printed as written.
- **Grandfathering (no retro-fit, no ambush).** Reviewer item 7 **rejects** on non-zero only
  for a `.tasks.md` whose first commit is **not older than** the commit that added
  `tools/tasks-pair-check.py` to the repo under review (`git log --diff-filter=A
  --format=%ct -- <path>` on both). A layered `.tasks.md` that predates the tool — an
  in-flight sibling spec'd before this merged, or a consumer repo's open features after an
  upgrade — is **flagged** (advisory, "re-spec to pair form or justify"), not rejected. The
  same git rule works in a consumer repo, where the tool's first commit is the upgrade.
- **Commit per GREEN is a Builder rule here, not a Reviewer-enforced gate.** The pair commit
  is the baseline E36-F06's drift check will diff against; E36-F06 enforces, this feature
  only instructs.
- **`sdd: false` items are exempt**, as they are from the traceability check today: they have
  no `.tasks.md` for the lint to read.
- **Generated glue is never hand-edited.** `.claude/`, `.codex/`, `.opencode/`, `.pi/`,
  `.agents/` are regenerated by `sh harness-install.sh --self`. This feature needs **no**
  emitter change (the Builder shim's "work `tasks.md` top to bottom … write the tests from
  `tests.md`" stays true of pairs, and every shim defers to the canonical role file), so no
  regeneration is expected; `tests/test_self_drift.sh` is the check that this stays true.
- **Installed body changes ⇒ SemVer MINOR bump** (template + three role files + a new tool),
  with a `CHANGELOG.md` entry. The target is the **next MINOR above `main`'s `VERSION` at
  merge time** (`0.98.0` if this is the first W1 feature to merge; W1 siblings bump in
  parallel, so the Builder re-reads `main` before the final rebase). "MINOR, not PATCH" is
  verified by the Reviewer reading the diff — no test pins the literal or its shape; no test
  may freeze the exact `VERSION` literal or diff a DO-NOT-TOUCH file against `main` (lesson
  2026-09-16).

## Architecture alignment

> `specs/architecture.md` is **absent** in this repo (never written; the ADR set exists under
> the single platform space `specs/adr/`). Per `agents/architect.md` graceful degradation the
> section is not strictly required; it is written anyway because the brief records the ADR
> this feature ships, and the Reviewer's ADR-citation clause keys on `sdd: true`.

- platform ADR-0008 — Vertical slices are the unit of decomposition; tasks pair one failing
  test with the code that passes it: this feature **implements decision 2** (per-`R-id`
  red/green pairs, explicit refactor tasks, no trailing "write tests" task, a commit per
  pair) in the template, the three role files, the docs and a lint the Reviewer runs. It
  does **not** implement decision 1 (the Driller's observable-slice rule and walking
  skeleton), which is E36-F02; it only orders pairs walking-skeleton first.

No divergence from any ADR.

## Acceptance criteria (EARS)

> Each is one testable behavior with a stable id. See docs/SPEC-FORMAT.md.

- **R1** — The shipped `specs/_templates/feature.tasks.md` shall express work as
  per-requirement pairs: for each placeholder `R-id` of `specs/_templates/feature.spec.md`
  (`R1`–`R5`) a `**T<n>a** (R#)` task whose text names observing **RED** precedes a
  `**T<n>b** (R#)` task whose text names observing **GREEN**, one explicit refactor task
  cites `R-id`s, and no task matches the write-tests grammar — so that
  `python3 tools/tasks-pair-check.py specs/_templates/feature.tasks.md --spec specs/_templates/feature.spec.md`
  exits `0`.
- **R2** — `agents/architect.md` § `## Your output (the 4-file spec)` item 3 shall describe
  `.tasks.md` as per-`R-id` red/green pairs — `T<n>a` writes the failing test from
  `.tests.md` and observes **RED**, `T<n>b` writes the minimal code and observes **GREEN**,
  refactor tasks are explicit and cite `R-id`s, there is no trailing "write tests" task —
  ordered walking-skeleton `R-id` first, and shall tell the Architect to run
  `tools/tasks-pair-check.py` on the `.tasks.md` before hand-off.
- **R3** — `docs/SPEC-FORMAT.md` shall carry a section `## Tasks — red/green pairs per
  requirement` that states the pair grammar of *Business rules* (task line, `a`/`b`
  suffixes, cited `R-id`s, the write-tests exclusion, fenced code ignored) and the
  behavioral-requirement rule (own pair by default; grouping by co-citation on the `a` task;
  never a code-only first task); and `docs/WORKFLOW.md`'s "One run, end to end" step 5 shall
  describe the Builder working `tasks.md` as red/green pairs with a commit per GREEN.
- **R4** — `agents/builder.md` § `## Loop A — in-session (you implement)` shall instruct the
  Builder to work pairs in order, to write **no** code for a pair whose test it has not
  observed **RED**, and to **commit after each GREEN**, while keeping the step-1
  `in-progress` precondition, the `.plan.md`-files-only / DO NOT TOUCH rule, the `./init.sh`
  self-check and the tick-and-progress step.
- **R5** — When `tools/tasks-pair-check.py <tasks> --spec <spec>` is run on a readable pair
  where every spec `R-id`'s first citing task is a `T<n>a` task and no un-cited task matches
  the write-tests grammar, the tool shall exit `0` and print a line beginning
  `tasks-pair-check: ok` — including when either file contains, inside fenced code, lines
  that would otherwise read as an `R-id` or as an old-style write-tests task.
- **R6** — If any spec `R-id`'s first citing task is not a `T<n>a` task, or no task cites
  it, then the tool shall exit `1` and print one line per offender, exactly
  `tasks-pair-check: first-task-not-test <R-id> <T-id>` or `tasks-pair-check: no-task <R-id>`.
- **R7** — If any task cites no `R-id` and its text matches `write` … `tests`
  (case-insensitive, whole words, in that order), then the tool shall exit `1` and print
  `tasks-pair-check: write-tests-task <T-id>` for each such task, wherever it sits in the
  list.
- **R8** — If `--spec` is absent, either file is missing or unreadable, or the spec yields
  zero `R-id`s, then the tool shall exit `2` with a `tasks-pair-check: error:` line and the
  usage on stderr — never `0`.
- **R9** — `agents/reviewer.md` § `## What you check` shall carry an item **7** that, for an
  `sdd: true` feature, runs `python3 "$HARNESS_DIR/tools/tasks-pair-check.py"` on the
  feature's `.tasks.md` with `--spec` its `.spec.md`, rejects on any non-zero exit, states
  that a `.tasks.md` whose first commit predates the tool's first commit is flagged rather
  than rejected (the git rule of *Business rules*), states that `sdd: false` items are
  exempt, and leaves check #2's traceability text unchanged.
- **R10** — A fresh `harness-install.sh` run shall ship `.harness/tools/tasks-pair-check.py`
  executable and byte-identical to the source, the installer source shall carry the line
  `chmod +x "$H/tools/tasks-pair-check.py"`, `.harness/specs/_templates/feature.tasks.md`
  shall be the pair-form template at its unchanged path, and `.harness/agents/reviewer.md`
  shall name the tool — each asserted in `tests/test_install.sh`.
- **R11** — `docs/RATIONALE.md`'s deletion ledger shall carry a row
  `C9 — Task-pair shape lint` in the *Capability compensation* layer whose "evidence to
  reconsider" cell states the ablation condition under which the lint may be removed, and
  `tests/test_rationale_docs.sh` shall count 22 rows and accept `C1`–`C9`.
- **R12** — `VERSION` shall change from its `main` value (the Reviewer confirms a MINOR step
  from the diff), `CHANGELOG.md` shall carry a `## [<that version>] — <date>` section whose
  body names `E36-F01` and `tasks-pair-check`, and the newest `## [` heading shall equal the
  `VERSION` file's value — read at test time, never as a frozen literal; the section check
  anchors on the historical body text, so a later release prepended above it stays green.

## Out of scope

- Changing `.tests.md`'s traceability table or the Reviewer's check #2 (brief; epic non-goal).
- The test-assertion drift tool and the per-pair commit gate (E36-F06).
- The Driller's observable-slice and walking-skeleton rules and their doc-critic checks
  (E36-F02); the lint does not check pair **order**.
- Verifying that a `T<n>a` is immediately followed by a `T<n>b` with the same `n`, or that
  the test named in a task exists in `.tests.md` — check #2 covers test existence.
- Any change to the generated glue emitters in `harness-install.sh` (the single `chmod +x`
  line of R10 is the only installer edit) or to `init.sh` (no warn-only sweep of `.tasks.md`
  shape at session start).
- Retro-fitting pair form onto `done` features' `.tasks.md` files, or onto in-flight features
  spec'd before this merged — those are grandfathered (flag, not reject) by the git rule in
  *Business rules*.
