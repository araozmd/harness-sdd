# Per-requirement red/green task pairs — Test Contract

> The traceability matrix: every R-id in the `.spec.md` maps to a concrete, executable test,
> and every row names the mutant that kills it. The Reviewer fails the feature if any R-id
> lacks a passing test, or if a named mutant survives.
>
> **Suite.** A new POSIX `sh` suite, `tests/test_tasks_pairs.sh` (TP), `set -eu`,
> `fail`/`pass`, run by `tools/run-tests.sh` under the strictest shell it can probe (dash on
> CI) — assert `rc -eq N`, never a shell-dependent code. `python3` absent ⇒ `fail`, never
> skip (it is a hard harness dependency). Every markdown heading slice loads
> `tests/lib/fence.awk` and calls `fence_delim($0)` first (`tests/test_change_size.sh` R9d
> reds a suite that does not). Fixtures live under `T="$(mktemp -d)"`; `TMPDIR` points
> outside the repo. The suite never reads `VERSION` as a literal, never diffs a DO-NOT-TOUCH
> file against `main`, never writes `state/` or a live spec.
>
> **Fixture writers** (functions in TP):
> - `fx_spec <path> [ids…]` — a minimal `.spec.md` with `- **R1** — …` lines for the given
>   ids (default `R1 R2 R3`); the `--decoys` variant appends a fenced block containing
>   `- **R9** — decoy` (backtick fence) **and** a tilde-fenced block containing
>   `- **R8** — decoy` **and** a 3-space-indented backtick fence containing `- **R7** — decoy`.
> - `fx_tasks_good <path>` — `T1a/T1b (R1)`, `T2a (R2, R3)` + `T2b (R2, R3)` (the grouping
>   form), `T3 (R1) — refactor`, `T4 — Run ./init.sh + sh tools/run-tests.sh` (no R-id, no
>   "write"); the `--decoys` variant appends a fenced block containing the old
>   `- [ ] **T5** — Write tests per feature.tests.md` and a fenced `- [ ] **T9b** (R1) — …`
>   that would otherwise be R1's first task if fences were ignored (it is placed **before**
>   `T1a`, inside a fence).
> - `run_lint <tasks> <spec…>` — `set +e; python3 "$ROOT/tools/tasks-pair-check.py" "$@"
>   >"$T/out" 2>"$T/err"; rc=$?; set -e`.
>
> **Prose slices.** `slice <file> <heading>` = fence-aware extraction of one `##` section up
> to the next `^## ` heading; anchors are two co-occurring tokens over folded newlines inside
> that slice (`tr '\n' ' ' | grep -qiE 'A[^.]{0,80}B'`). Each anchor was confirmed RED on the
> pre-change blob (`git stash` the prose file) before being trusted.

## Behavioral / end-to-end checks (Reviewer)

- Run the lint on **this feature's own** `E36-F01.tasks.md` with `--spec E36-F01.spec.md`:
  exit 0 (dogfood). Then run it on a `done` sibling's layered tasks file, e.g.
  `specs/epics/E35-pi-first-class/F05-pi-subagents-integrity-pin/E35-F05.tasks.md` with its
  spec: expect exit 1 with `first-task-not-test` lines (R6), and confirm item 7's git rule
  classifies that file as **predating** the tool (flag, not reject) — no retro-fit.
- Apply item 7's git rule to this feature's own `E36-F01.tasks.md`
  (`tasks-pair-check.py --grandfathered …`): until this feature merges the tool is not on the
  default branch, so it is in the **flag** class — and the lint passes anyway (exit 0), so
  the flag never comes into play. A W1 sibling's `.tasks.md` (e.g. E36-F06 in its worktree)
  is also flagged now, and stays flagged after this merges, because it was authored before
  the merge.
- Fresh install into an empty temp dir (`sh harness-install.sh <dir>`), then run
  `python3 <dir>/.harness/tools/tasks-pair-check.py <dir>/.harness/specs/_templates/feature.tasks.md --spec <dir>/.harness/specs/_templates/feature.spec.md`
  → exit 0 (the shipped pair is self-consistent in the installed layout).
- `sh harness-install.sh --self` leaves `git status --short` empty of generated-glue paths.

## Non-functional checks

- `sh tools/run-tests.sh` green; summary names the shell (dash in CI).
- `python3 -m py_compile tools/tasks-pair-check.py` clean; `sh -n tests/test_tasks_pairs.sh`
  clean; the suite is **not** added to `tests/dash-allowlist.txt`.
- `sh tests/test_change_size.sh` green standalone right after authoring the suite (R9d
  fence-rule convention for heading slicers).
- `sh tools/change-size.sh` tier recorded in the review (expected `ok`: one ~200-line tool,
  one ~300-line suite, prose).
