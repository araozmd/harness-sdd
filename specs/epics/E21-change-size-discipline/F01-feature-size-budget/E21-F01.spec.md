# Feature-size budget in the Driller and Architect — Functional Spec

## Context
Nothing in the harness bounds the size of a feature. `agents/driller.md` decomposes an epic
into features with no size rule and `agents/architect.md` specs whatever it is handed, so the
sizing decision is made implicitly at drill time and never revisited. `viernes-bookings-api`
E14-F05 came out of a drill carrying R1–R36 / T1–T25 and became one PR of 17,202 additions
whose review did not converge in twelve rounds — a flat blocking-finding rate, meaning the
merge signal the SDD loop depends on had stopped carrying information.

The user harmed is whoever drills the next epic: they have no rule to apply, so they apply
none, and the cost lands three phases later on whoever is waiting for a merge.

This feature adds the rule where the decision is actually made. It is a **grouping** rule, not
a new authoring tier: an EARS `R-id` is already an atomic single-behavior spec (the micro-spec
pattern, already implemented here) and the Reviewer already mandates a test per `R-id`. What
was missing is anything mapping those micro-specs onto a **deliverable**.

## Business rules
- The budget is **advisory in two tiers** — *advise* and *escalate* — and never a hard block.
  Both tiers produce a **recorded decision**; neither refuses work.
- The budget is expressed in **production** lines, not total lines. Tests are a deliberate
  quality choice already enforced elsewhere (a passing test per `R-id`) and must not be
  penalised by the instrument that governs review surface.
- Requirement count is the **drill-time** signal, because it is the only number that exists
  before any code does, and each `R-id` obliges a test.
- The numbers live in `harness.config.yaml`, never hard-coded in an agent prompt: `agents/` is
  harness-OWNED and a target's tuning would be clobbered on the next upgrade.
- An absent `change_size:` block behaves exactly as the documented defaults, matching the
  existing `telemetry:` / `fix_lane:` / `pr_loop:` convention.

## Architecture alignment
ADRs touched: none — this feature adds an advisory decomposition rule and a config block; it
changes no recorded structural decision about stores, front-ends, or the agent topology.

## Acceptance criteria (EARS)

- **R1** — The system shall define a top-level `change_size:` block in `harness.config.yaml`
  carrying `advise_lines`, `escalate_lines`, `advise_files`, `escalate_files` and
  `max_requirements`.
- **R2** — Where a target's `harness.config.yaml` carries no `change_size:` block, the system
  shall behave as if the documented defaults (`1500` / `3000` / `25` / `50` / `12`) were
  written.
- **R3** — When the installer runs against a target whose `harness.config.yaml` has no
  `change_size:` block, it shall append the block; and when the block is already present it
  shall not append a second one.
- **R4** — When the Driller decomposes an epic and a candidate feature's brief implies more
  than `change_size.max_requirements` requirements, it shall split that candidate into sibling
  features sequenced along the intra-epic `depends_on` graph.
- **R5** — When the Driller splits an over-budget candidate, or deliberately declines to split
  one, it shall record that decision and its reason in the epic's `epic.md`.
- **R6** — The Driller shall not treat the budget as a refusal condition: it shall never emit a
  `blocked` record on size alone.
- **R7** — If the Architect is handed a feature whose spec would carry more than
  `change_size.max_requirements` `R-id`s, then it shall stop before writing the four spec files
  and report the over-budget count together with the seams it would split on.
- **R8** — Where the human directs the Architect to proceed over budget, the Architect shall
  write the spec and record an explicit override line naming the reason in the `.spec.md`.
- **R9** — The system shall document the two-tier semantics — what *advise* and *escalate*
  each require, and that neither blocks — in `docs/WORKFLOW.md`.
- **R10** — The installed harness body shall carry the budget rule in both
  `agents/driller.md` and `agents/architect.md`, so a consumer receives it on upgrade.

## Out of scope
- Measuring an actual branch diff. That is E21-F02; this feature governs the *estimate* made
  before any code exists.
- Anything touching `/sdd-pr-loop` (E21-F03 / E21-F04, blocked on E18-F01).
- Retroactively splitting features already on the board.
- Enforcing the budget in CI, or failing an install/init on an over-budget feature.

## Open questions
- The defaults are calibrated from a single 60-PR sample (median 396 additions; largest
  converging PR 7,006 additions in 5 rounds; 17,202 non-converging in 12). They want a second
  calibration against the harness's own merged features before anyone treats them as settled.
- Whether `max_requirements` should scale with a repo's test ratio rather than being a flat
  count. Deferred: a flat count is explainable in a prompt, and an unexplainable rule does not
  get followed.
