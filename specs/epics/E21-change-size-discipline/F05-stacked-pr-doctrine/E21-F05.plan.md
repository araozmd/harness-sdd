## The design decision this feature turns on: how a doctrine statement gets a test

The brief's one open question. **Answer: greppable assertions, anchored on identifiers, extracted
per-section, plus a cross-file agreement check — not prose-only, and not frozen sentences.**

The reasoning, and the cost accepted:

- **Prose-only is disqualified by measurement, not taste.** The predecessor's false claim
  survived four `@codex review` rounds precisely because nothing could fail on it. For a feature
  whose entire deliverable *is* prose, an untested requirement is an unverifiable one, and
  `agents/reviewer.md` (a passing test per `R-id`) would have nothing to check.
- **Freezing whole sentences is the opposite failure.** It makes every legitimate copy-edit a
  red build, and the cheapest way out of a red build is to paste the sentence back — which
  restores the token and loses the meaning.
- **So anchor on identifiers, not on English.** Wherever the requirement has a name the system
  already owns — `verification.test_command`, `baseRefName`, `depends_on`, `gh pr edit --base`,
  `gh pr create`, `pr-stack-guard.sh`, `increments[]` — assert *that*. An editor can reword the
  sentence around a config key freely; they cannot remove the key and still mean the same thing.
  Only three anchors have no identifier available (`this epic does not solve`,
  `one increment at a time`, `last increment`); those are short, declared load-bearing in
  `E21-F05.tests.md`, and each test's failure message says so.
- **Extract the section first.** `agents/builder.md` already mandates this: *"A test that asserts
  a PROSE contract must grep the SECTION it names, not the whole file."* A whole-file grep is
  satisfied by any unrelated occurrence — including one the same change just added elsewhere —
  so the assertion would name a guarantee it cannot detect. Two helpers implement it (below).
- **The cross-file check is what actually closes the stated risk.** R9 asserts the doctrine is
  stated once and *cited* elsewhere. That converts "three files must agree" — unverifiable in
  general — into "two files must contain a pointer and must **not** contain the canonical
  statement's anchor", which is decidable.
- **Two negative sweeps, with their limits stated rather than hidden.** The `atomic` token ban
  (R9) is exact and total *within the lane's sections*: it cannot be satisfied by another path
  and cannot be paraphrased around, because it bans a token rather than a claim. The
  no-restatement sweep (R9) catches a copied entry condition, not a reworded one. Neither claims
  to police arbitrary future prose; what they close is regression to the exact shape that was
  withdrawn.

**Cost accepted, in one line:** a future editor who rewords the lane will occasionally trip a
token assertion that is not a real defect. That is a bounded, visible annoyance; the alternative
failure — a false doctrine that no gate can see — is the one this epic exists because of.

### Section-extraction helpers (both live in `tests/test_stacked_lane.sh`)

```sh
# sect <file> <heading-text> — ONE section body; stops at the next heading of ANY level.
# FENCE-AWARE: `#` is a comment in every shell fence in these docs, so the bare idiom would
# treat `# Increment 1 targets main` as a heading and stop extracting at the first fence.
sect() { awk -v h="$2" '/^```/{f=!f} !f && /^#+ /{k=(index($0,h)>0);next} k' "$1"; }

# span <file> <h2-heading-text> — a WHOLE `## ` section INCLUDING its `###` subsections;
# stops at the next `## `. Used for the lane-wide sweeps (the token ban, the no-restatement
# check), which must see subsection bodies too. Unaffected by the fence problem: no shell
# comment in these docs begins with `## `.
span() { awk -v h="$2" '/^## /{k=(index($0,h)>0);next} k' "$1"; }
```

Both are `awk`, not `grep`, so neither depends on a `grep` dialect (see `tests/test_grep_probe.sh`
for why that distinction is live in this repo).

**Why `sect()` extends the `agents/builder.md` house idiom rather than copying it.** That
principle prescribes `awk 'BEGIN{h="…"} /^#+ /{k=…;next} k'`, which is fence-**blind**. Measured
on the file this feature edits: `sect docs/WORKFLOW.md '### Creating stacked increments'` returns
**three lines** and a `gh pr create` count of **1**, while the real section contains **4** —
extraction dies at the opening ```` ```bash ```` because the next line, `# Increment 1 targets
main (default):`, matches `/^#+ /`. R4's flagship assertion ("exactly one `gh pr create`") would
therefore have passed on a section that still contained the three-PR block it exists to delete:
the expected value reachable by a second path, in the exact shape `agents/builder.md`'s own
Principles warn about. The `/^```/{f=!f}` toggle is the minimum fix and changes nothing for
fence-free sections. Any future prose-contract test in this repo that greps a section containing
a shell fence needs the same guard.

### `agents/builder.md` — the new section's obligations

Short. It carries **only** the Builder's own work, and cites the canonical statement rather than
repeating it (R9):

- Point at `docs/WORKFLOW.md` → `## Stacked-PR lane …` for when the lane applies and what the
  entry condition is. **Do not restate the entry condition** — in particular, the string
  `verification.test_command` must not appear in this section (R9 asserts its absence).
- **Grow the stack, one increment at a time** (R4): finish the increment, then open its PR
  against the parent's branch. Do not create later branches or PRs in advance — that would
  contradict Loop A's own "work the tasks in order, one at a time" and would require knowing
  every seam before any code exists. At most one `gh pr create` appears in this section.
- **Tick as you go** (R7): the Orchestrator reads unticked tasks in `<feature>.tasks.md` as
  "another increment is coming". Loop A step 6 already requires this; the new section names the
  consequence so the Builder knows the tick is load-bearing here.
- **You own the restack** (R5): when a parent takes review fixes after a child branch exists,
  rebase each descendant onto the updated parent *before* that descendant is reviewed further,
  following `docs/WORKFLOW.md` → `### Restack procedure`. The pr-loop detects the base change
  and refuses to continue an unrestacked child; it does not rebase for you.
- One line on inertness (R10): with `pr_loop.enabled: false` there is no stacked lane to work —
  open the ordinary single PR.

### `agents/orchestrator.md` — the new section's obligations

Equally short, and equally a pointer for anything it does not own (R9):

- **Hold `done`** (R7): while any increment PR of the feature is open or unmerged, do not write
  `done`. Write it once, after the last increment's PR is merged. Create no per-increment board
  record and invent no per-increment status.
- **How you know another increment is coming** (R7). R8 deliberately leaves the board with
  nothing recording "increment 2 of 3", so the Reviewer's approval of increment 2 cannot by
  itself tell you whether a third exists. Ask two questions of artifacts that already exist,
  and require *no* to both before writing `done`:
  1. Does the feature's `<feature>.tasks.md` still carry an **unticked** task? The Builder ticks
     as it goes (`agents/builder.md` Loop A step 6), so an unticked task means work remains.
  2. Is any PR whose head branch belongs to this feature still **open or unmerged**?
  For a non-stacked feature both are already `no` at approval time, so this changes nothing on
  the ordinary path — it only makes the stacked case decidable without new state.
- **The between-increment arc** (R7): `in-review` while an increment is under review; set the
  feature back to `in-progress` when the Builder starts the next increment — the same transition
  a Reviewer reject already performs. No new status value, no new schema field.
- **The exception must be stated where the contradicting rule lives** (R7). `### Build↔review
  rounds` step 2 reads "**Approve** → `done`" roughly 100 lines above this new section. Add one
  exception line there — approve routes to `done` **unless** the feature is in the stacked lane
  with work outstanding, in which case see this section. A reader who stops at step 2 must not
  come away with the wrong rule.
- **The board sees one feature** (R8): the increment order lives in the PRs' `baseRefName`.
  Do not reuse `slices[]` for same-repo increments; `increments[]` is deferred to its own
  feature. Selection (`tools/next-task.mjs`) learns nothing new — ADR-0001.
- Cite `docs/WORKFLOW.md` → `## Stacked-PR lane …` for the doctrine; do not restate the entry
  condition (`verification.test_command` must not appear here either).
- One line on inertness (R10): with `pr_loop.enabled: false` this section does not apply.

## Approach notes

### Sequencing

Do `docs/WORKFLOW.md` **first and completely**. It is the single canonical statement; both role
files cite it, and R5's heading is what `harness-install.sh`'s message resolves against. Then the
two role files, then the suite, then `VERSION` + `CHANGELOG.md`.

### The one trap in this feature

Every requirement is satisfiable by writing the right paragraph in the right section — and
*also* by writing a plausible paragraph in the wrong one. The suite extracts by heading for
exactly that reason, so a correct sentence filed under the wrong subheading fails. If a heading
in the table above does not fit the prose you end up writing, change the **spec/plan** through
the Orchestrator rather than the heading in isolation; a heading is part of the contract here.

### Anti-patterns this suite must not commit

- No assertion on a `VERSION` value, in any form.
- No diff of any file against `main`, `origin/main`, or a DO-NOT-TOUCH path.
- No whole-file grep for a prose contract — always `sect`/`span` first, and use the
  **fence-aware** `sect()` above, never the bare house idiom.
- **Never bind a possibly-zero `grep -c` under `set -eu`.** `grep` exits `1` on no match, so
  `n="$(… | grep -c foo)"` **aborts the whole suite silently on the happy path** — which is the
  passing result for R8's "`increments` count is 0" and both of R9's absence sweeps. Verified:
  `sh -c 'set -eu; n="$(printf "a\n" | grep -c zzz)"; echo $n'` exits 1 and prints nothing. Write
  either `n="$(… | grep -c foo || true)"` for counts, or
  `if … | grep -q foo; then fail "…"; fi` for absence assertions. Prefer the `grep -q` form where
  the requirement is "zero occurrences": it says what it means and cannot be misread as a count.
- Every installer-invoking case runs with `HOME` **and** `CODEX_HOME` pointed at per-case temp
  dirs (never the developer's `~/.codex`), matching `tests/test_pr_loop.sh`'s `install_at()`.
- Per-case `mktemp` fixtures and no writes into `state/`, `specs/`, `progress/` — the suite runs
  concurrently under `tools/run-tests.sh`.
