# The stacked-PR lane's doctrine document — Functional Spec

## Context

`docs/WORKFLOW.md`'s `## Stacked-PR lane` section is the only place a reader can learn what
the lane buys, what it does not, and when not to reach for it. Today it states four things
that are **false or dangling on `main`**, and it states its entry condition twice in two
places that disagree. This feature corrects that section — and nothing else.

It is the **first half of a re-drill**. The predecessor spec carried the doctrine *and* the
increment contract (who opens an increment's PR, how a partial increment is reviewed, how an
increment is delimited); specced honestly it came to **13 `R-id`s against
`change_size.max_requirements: 12`**, so the Architect stopped and reported the seams. All
three Codex P1 findings on PR #129, and every role-file contradiction, lived in the contract
half. That half is now **E21-F06** (on the board, `parked` behind a product decision). This
feature is the half that attracts no findings and is worth shipping either way: even a
decision to *deprecate* the lane needs this section to read accurately first.

**Scope, stated once:** `docs/WORKFLOW.md` only, plus one append-only supersession note in
E21-F04's shipped spec, plus the new test suite, plus the `VERSION` bump and its `CHANGELOG.md`
entry that any installed-body change owes. **No role file. No production code.** Where a
correction would oblige a role file, it is named in *Out of scope* and left to E21-F06.

### Why this is tagged `complex`

2. **It names a defect class the harness has already paid for.** The whole deliverable is

## Business rules

- The lane bounds the **size of each review**. It is available only to work that is already
  safely splittable, and it changes nothing about how or when work reaches the default branch.
- Merging an increment publishes that increment's work to the default branch while the later
  increments are still open. Every statement of what the lane does is written in those
  mechanical terms. This spec makes no delivery claim in the withdrawn abstract vocabulary;
  the token `atomic` appears in this feature only as the string a sweep bans (R3).
- A feature whose intermediate states are not safe on the default branch is **not served** by
  this lane. That case is an open problem this epic does not solve, and it is named as such.
- The entry condition is stated **once**, in one subsection. Every other part of the lane
  points at it rather than restating it — a condition stated twice is a condition that will
  disagree with itself, which is defect #4.
- The board's unit is the feature: a stacked feature is **one** feature record, the increment
  order lives in the PRs' `baseRefName`, and the harness writes no per-increment record.
- The lane's *behavior* is gated by `pr_loop.enabled`; its *documentation* ships with the
  harness body either way, because the harness has one body and not a per-flag variant of it.
- A user-facing document names sections, not internal requirement ids. A section name a
  shipped diagnostic points at must resolve to a heading in the file it names.

## Acceptance criteria (EARS)

- **R1** — The system shall state the stacked-PR lane's entry condition in exactly one
  subsection of `docs/WORKFLOW.md` — a `### Entry condition` subsection of the lane — naming
  both conditions checked **before the first increment PR is opened**: every increment is
  independently safe on the default branch, **and** every increment passes
  `verification.test_command` on its own.

- **R2** — If a candidate feature cannot meet both entry conditions, then `docs/WORKFLOW.md`
  shall refuse it the lane: it shall say the feature is not a candidate for stacking, shall
  name feature flags or an aggregate landing strategy as the alternatives in **exactly one
  place** in the lane, and shall record that case as an open problem this epic does not solve.

- **R3** — The system shall state the lane's outcome mechanically in the lane's opening
  paragraphs — merging an increment publishes that increment's work to the default branch
  while the later increments are still open — and the lane section shall contain no form of
  the token `atomic`.

- **R4** — The system shall record, in a `### What the board shows` subsection of the lane,
  that a stacked feature is one feature record on the board, that the increment order lives in
  the PRs' `baseRefName`, and that the harness writes no per-increment board record.

- **R5** — The lane shall carry no citation attributing a decomposition structure to a source
  that does not define one: it shall contain no `wave` vocabulary and no `E21-F01` reference,
  and its seam guidance shall instead point at the lane's own `Entry condition` and at the
  `change_size` budget.

- **R6** — The section name that `harness-install.sh`'s shipped restack diagnostic points
  readers at shall resolve to a heading in `docs/WORKFLOW.md`.

- **R7** — The stacked-PR lane section of `docs/WORKFLOW.md` shall contain no bare
  spec-requirement id of the form `(R<n>)`, in a heading or in prose.

- **R8** — Where `pr_loop.enabled` is `false`, `docs/WORKFLOW.md` shall state that the lane's
  documentation ships with the harness body regardless of the flag and that only the lane's
  behavior is gated by it; and an install performed with the flag off shall carry the lane
  section in its installed `docs/WORKFLOW.md`.

- **R9** — The system shall record, in E21-F04's own shipped `.spec.md`, that E21-F05
  supersedes F04's **R6**, **R7** and **R8** documentation requirements, so a reader of the
  `done` feature is not left with a spec the shipped document contradicts.

**Count: 9 `R-id`s against `change_size.max_requirements: 12`.** The brief scoped "~6". The
delta is deliberate and itemised: the four defects need five requirements (defect #2 is two
distinct failure modes with two distinct tests — a pointer that resolves and an id that leaks
— and folding them would be a budget trick, not a smaller feature), the doctrine the brief
puts in scope needs three (outcome, entry condition, refusal-and-not-served), and the F04
supersession the brief puts in scope needs one. Nine is under budget; no override is claimed.

## Out of scope

Each entry below is something a reader might expect here. Each is named with the reason it is
not, so its absence is a decision rather than an omission.

- **The increment contract — E21-F06.** Who opens an increment's PR, how a partial increment
  is reviewed, and how an increment is delimited. All three PR #129 P1 findings live there.
- **Every role file.** `agents/builder.md`, `agents/orchestrator.md`, `agents/reviewer.md`,
  `agents/architect.md` are untouched. Any correction that would oblige one belongs to E21-F06.
- **When `done` is written for a stacked feature.** The brief's carried decision #2 has two
  halves: the board's unit is the feature (R4 states it, and it is true today — nothing
  records "increment 2 of 3"), and `done` rolls only when the last increment merges. The
  second half **contradicts `agents/orchestrator.md`'s "Approve → `done`" unless that file
  carries an exception line** — which is a role file. Stating it in `docs/WORKFLOW.md` alone
  would ship a rule no contract enforces: the exact defect class this feature exists to
  remove. It is E21-F06's, with its enforcing edit.
- **The `### Creating stacked increments` example block, which opens three PRs together.**
  Rewriting it states *when* an increment's PR is created, which is the increment contract.
  This feature touches that section only to rename the example branches `feat/wave-N` →
  `feat/increment-N`, which R5's vocabulary sweep requires and which asserts nothing about
  ownership or timing. The residual — an example that creates the stack up front, against the
  brief's carried decision #1 — is E21-F06's to fix, and is recorded here so it is not lost.
- **A `### Recovering from a manual retarget` subsection** for the guard's unowned-base
  `exit 6`. Net-new documentation, not one of the four defects; the guard's own header and
  exit-6 message already describe the branch. Deferred to E21-F06, which owns the guard's
  reader-facing surface. This is the **one** item the predecessor's own split table put in
  *this* half and that this feature drops; the drop is deliberate and matches the re-drill
  brief's in-scope list. Consequence, named rather than hidden: if E21-F06's `parked` decision
  deprecates the lane, that documentation gap closes with the lane rather than being filled —
  which is an acceptable outcome, and not one anyone should be surprised by later.
- **`tools/pr-stack-guard.sh`.** Its header comment (lines 5–7) states the doctrine in the
  banned denial form. It is E21-F04's shipped guard and DO NOT TOUCH here, which is exactly
  why R3's sweep is scoped to the lane section and R3 makes no "exactly one place in the repo"
  claim it could not honor.
- **The `/sdd-pr-loop` merge-deferred headline**, which is wrong on the guard's unowned-base
  branch (it prints "parent PR is still open" when the parent has already merged). It lives in
  a DO-NOT-TOUCH file and is worth an `E99` maintenance fix.
- **Any `state/tasks.json` schema change**, including an `increments[]` field. R4 records what
  the board does today; it proposes nothing.
- **Whether the lane should exist at all.** E21-F06 is `parked` on exactly that product
  decision. This section must read accurately either way.
