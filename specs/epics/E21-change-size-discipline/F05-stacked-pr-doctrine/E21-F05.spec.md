# The stacked-PR lane: doctrine, seams, and role contracts — Functional Spec

## Context

E21-F04 shipped the **mechanism**: `tools/pr-stack-guard.sh` (an offline merge-order guard),
base-branch awareness in `/sdd-pr-loop`, base-change detection with an ancestry check, and a
`docs/WORKFLOW.md` section describing the lane. What it did not ship is a lane anyone can be
*routed into*: nothing states the condition a feature must meet before an increment PR is
opened, nothing says who creates the increments or in what order, nothing says what the board
shows while a stack is in flight, and neither role contract (`agents/builder.md`,
`agents/orchestrator.md`) mentions stacking at all. The mechanism has no callers.

This feature writes that doctrine. It is **prose-only**: three harness-owned files plus one
new test suite. It changes no guard, no loop step, no schema, and no selector.

**Why this is a separate feature at all.** E21-F04's predecessor was withdrawn during review of
PR #78 after four `@codex review` rounds and five blocking findings — every one of them on the
claim/doctrine surface, each largely created by the previous round's fix. The salvaged guard was
independently sound. So the mechanism shipped first and alone, and the surface that actually
burned is isolated here, behind the human gate.

**The withdrawn defect, named so it cannot recur.** The predecessor claimed a stacked feature's
increments reach `main` together. They do not: merging increment A publishes A's work
to the default branch while B and C are still open. Stacking is a **review-size tool** for work
that is *already safely splittable*, and nothing more. This spec therefore states every outcome
of the lane **mechanically** — what merging an increment does to the default branch — and
forbids the abstract vocabulary that carried the false claim (R9). A denial ("not X") is one
dropped negation away from the claim it denies; a mechanical sentence has no such failure mode.

### What is already shipped and is NOT re-specified here

Read `specs/epics/E21-change-size-discipline/F04-stacked-pr-lane/` before building. F04 owns and
keeps: the guard's exit codes and fail-closed behavior, `baseRefName`/`baseRefOid` in the round
cache, the merge-order gate and its `needs-human` route, base-change detection and the
restack-ancestry check, and the *existence* of the `## Stacked-PR lane` section in
`docs/WORKFLOW.md`. This feature adds sections to that lane, renames three of its subheadings,
and rewords its outcome statements. It changes no F04 **behavior** — no guard, no loop step, no
exit code — but it does **supersede three of F04's documentation requirements**, listed next.

### Supersedes in E21-F04

E21-F04 is `done`. Superseding a shipped feature's requirements silently is how two specs start
disagreeing about the same file, so each is named here and a task records the supersession in
F04's own spec:

- **F04-R6** (document the lane's purpose, wave-boundary guidance, and an explicit
  incremental-review-not-delivery statement) — **superseded in two parts.** The denial sentence
  is replaced by the mechanical statement (R9's rationale: a denial is one dropped negation from
  the claim it denies). The "wave-boundary guidance" it mandates cites a structure E21-F01 never
  defined, and is replaced by E21-F01's real seam (R3).
- **F04-R7** (document the manual restack procedure) — **retained in substance, renamed.** The
  procedure body is unchanged; the heading loses its leaked `(R7)` id and becomes the name
  `harness-install.sh`'s diagnostic already points readers at, which today resolves to nothing
  (R5).
- **F04-R8** (…"no stacking documentation is stamped" when `pr_loop.enabled` is `false`) —
  **superseded as factually wrong.** The prose tier is copied unconditionally; see Open question
  2. The behavioral half of F04-R8 (no guard invocation, no stacking-specific merge logic) is
  untouched and still holds.

No F04 **test** conflicts: `tests/test_pr_loop.sh`'s E21-F04 block asserts the `/sdd-pr-loop`
command body and the guard's exit codes, and no suite greps any lane subheading (verified).

### Why this is tagged `complex`

Two of the signals `agents/architect.md` requires, both already produced rather than felt:

1. **It pressed against the budget and split.** Specced whole at lane (a)'s scope the work came
   to 19 `R-id`s against `change_size.max_requirements: 12`; the Architect stopped, reported the
   seam, and E21-F04 took the mechanism. What is left here is 10 — inside the budget only
   because the split already happened.
2. **It names a defect class the harness has already paid for: a body and its copy diverging.**
   The deliverable is one doctrine stated across three files that must agree, plus the
   front-end shims that must *not* restate it. That is the same shape as every "the prompt and
   its mirror drifted" finding this repo has fixed before, and R9 exists solely to close it.

Speccing it also required resolving two live contradictions between shipped components (both
recorded under *Open questions*), which is the third listed signal.

## Business rules

- Stacking bounds the **size of each review**. It is available only to work that is already
  safely splittable; it changes nothing about how or when work reaches the default branch.
- Merging increment A publishes A's work to the default branch while B and C are still open.
  Every statement of what the lane does is written in those terms, never in abstract ones.
- A feature whose intermediate states are not safe on the default branch is **not served** by
  this lane and must not be stacked. That case remains an open problem this epic does not solve.
- The stack is **grown**, one increment at a time, by the same Builder loop that works
  `tasks.md` in order. Nobody emits N branches up front.
- Because each increment branches off its parent's *current tip*, a parent that takes review
  fixes after a child exists requires a **manual restack**. That cost is documented, not hidden.
- The board's unit is the feature. A stacked feature is **one** feature on the board; the
  increment order lives in the PRs' `baseRefName`. `done` is written once, after the last
  increment merges.
- The doctrine is stated **once** — in `docs/WORKFLOW.md`. The role contracts carry only their
  own obligations and cite that section; nothing is copied into a front-end agent shim.
- The lane's *behavior* is gated by `pr_loop.enabled`; its *documentation* ships with the
  harness body either way, because the harness has one body, not a per-flag variant of it.

## Architecture alignment

**`specs/architecture.md` is ABSENT in this repo** — no `/sdd-plan` run has produced it, and
`specs/` carries only `product.md`, `glossary.md`, `adr/` and `epics/`. Per
`agents/architect.md` → *Graceful degradation*, the citation rule therefore does **not** bind
and this section is not required. It is written anyway, deliberately, so the omission reads as a
decision rather than an oversight. All four ADRs in `specs/adr/` were read. There is exactly one
ADR namespace (`specs/adr/` = `platform`), so bare ids are used.

- **ADR-0001 — next() selection moves from prose routing to a deterministic tool: honored by
  declining to extend what the selector reads.** Decision #3 of the brief weighs an optional
  `increments[]` on the board and rejects it: selection is code now, a second ordering
  vocabulary would duplicate ~80% of `slices[]` across `store/tasks.schema.json`,
  `store/local.md`, both mirror adapters, `tools/sync-board.mjs` and `tools/next-task.mjs`, and
  it would land inside the exact surface ADR-0001 exists to protect. R8 records that decision
  and forbids the field. This feature adds **no** input to the selector and **no** gate it must
  evaluate — the stacked feature moves through the existing `in-progress` ↔ `in-review` arc.
- **ADR-0004 — a child resolves the harness body through pointer stubs at the same paths:
  honored.** The doctrine is written into the prose tier (`docs/`, `agents/`), which a child
  resolves through pointer stubs rather than copying, so an umbrella child receives it on
  upgrade with no per-child duplicate to diverge. R9's "never restate, never copy into a shim"
  clause is the same principle applied one level down, to the front-end shims.
- **ADR-0002 (`builder-heavy` is a tier, not a second prompt) — not touched.** This feature adds
  a section to `agents/builder.md`, which is the single body both Builder role names resolve to;
  it introduces no behavioral difference between them.
- **ADR-0003 (one shared skill unit per command) — not touched.** No command body, skill unit or
  front-end glue changes here.

No divergence from any recorded decision.

## Acceptance criteria (EARS)

- **R1** — The system shall state, in a dedicated `### Entry condition` subsection of
  `docs/WORKFLOW.md`'s stacked-PR lane, the two conditions a feature must meet **before its
  first increment PR is opened**: every increment is independently safe on the default branch,
  **and** every increment passes `verification.test_command` on its own.

- **R2** — If a candidate feature cannot meet both entry conditions, then the harness contract
  shall refuse the lane for it: `docs/WORKFLOW.md` shall direct that it is not stacked, shall
  name feature flags or an aggregate landing strategy as the alternatives, and shall record that
  case as an open problem this epic does not solve.

- **R3** — The system shall state exactly one rule for where to cut increments — the intra-epic
  `depends_on` sequence E21-F01 already uses to split an over-budget candidate — and shall not
  name a second, stacking-specific seam vocabulary.

- **R4** — When a Builder works a feature in the stacked lane, it shall open an increment's PR
  only after completing that increment, and shall not create the stack's later branches or PRs
  in advance; `docs/WORKFLOW.md`'s `### Growing the stack` shall show **exactly one**
  `gh pr create` invocation, in the growing form, and `agents/builder.md`'s section shall show
  at most one.

- **R5** — When an increment's PR takes review fixes after a later increment's branch already
  exists, the Builder shall restack each descendant onto the updated parent before that
  descendant is reviewed further; `agents/builder.md` shall assign that work to the Builder by
  name and cite the `docs/WORKFLOW.md` restack section, whose heading shall match the section
  name `harness-install.sh`'s restack diagnostic already points readers at.

- **R6** — If `tools/pr-stack-guard.sh` reports `exit 6` for a base branch that is not the
  default branch and that no open PR owns, then `docs/WORKFLOW.md` shall document the recovery:
  retarget the child with `gh pr edit --base` onto the default branch (or the surviving parent)
  and re-run the loop, rather than merging.

- **R7** — While any increment PR of a stacked feature is open or unmerged, **or** while its
  `tasks.md` still carries an unticked task, the Orchestrator shall not write `done` for that
  feature; it shall write `done` only after the last increment's PR is merged, shall create no
  per-increment board record, and shall introduce no status value outside the existing five.
  `agents/orchestrator.md`'s `### Build↔review rounds` step 2 — which today reads
  "**Approve** → `done`" — shall carry an explicit exception line pointing at this lane.

- **R8** — The system shall record that a stacked feature is one feature on the board whose
  increment order lives in the PRs' `baseRefName`, that `slices[]` is not reused for same-repo
  increments, and that an `increments[]` field is deferred to its own feature; and
  `store/tasks.schema.json` shall gain no `increments` property while `repo` remains required on
  a slice.

- **R9** — The stacked-lane doctrine shall exist in exactly one place **in the prose tier** and
  one vocabulary: `agents/builder.md` and `agents/orchestrator.md` shall cite
  `docs/WORKFLOW.md`'s lane section rather than restating the entry condition; no front-end agent
  shim shall carry any of the doctrine; and the lane's sections in those three files shall
  describe outcomes mechanically, containing the word `atomic` in no form. (Carve-out:
  `tools/pr-stack-guard.sh`'s header comment states the doctrine in denial form and is
  DO NOT TOUCH — see Open question 3.)

- **R10** — Where `pr_loop.enabled` is `false`, no role contract shall instruct opening or
  evaluating a stacked PR, and `docs/WORKFLOW.md` shall state that the lane's documentation
  ships with the harness body regardless of the flag while only its behavior is gated by it.

## Out of scope

- The guard, the merge gate, base-change detection and the ancestry check — **E21-F04, shipped**.
  This feature invokes nothing and re-specifies nothing of it.
- Any change to `tools/pr-stack-guard.sh`, `tools/wait-for-codex.sh`, the `/sdd-pr-loop` body in
  `harness-install.sh`, or `.claude/commands/sdd-pr-loop.md`.
- Getting a feature whose intermediate states are unsafe onto the default branch in one visible
  step. Still unsolved, still not seeded, and named as such by R2.
- A `state/tasks.json` schema change of any kind, including `increments[]` (R8 defers it).
- Automating the split of an existing branch, and any third-party stacked-PR tool.
- Retroactively stacking anything already on the board.
- **`agents/reviewer.md`, deliberately.** Its verdict rule ("Approve → tell the Orchestrator to
  set `done`") reads correctly under this lane already, because the Reviewer **recommends** and
  the Orchestrator **writes** — board status is the Orchestrator's sole ownership, and
  `store/local.md`'s rollup precedent is exactly "the coordinator derives and persists `done`,
  the approving role does not set it by fiat". R7's exception therefore belongs where the write
  happens. Adding a fourth file to a doctrine that must stay consistent would enlarge the very
  surface R9 exists to bound.
- **The `/sdd-pr-loop` merge-deferred headline, which is wrong for one branch** (recorded here
  rather than fixed): on the guard's *unowned-base* `exit 6`, the loop prints
  `merge deferred — parent PR is still open`, but that branch means the parent has **already
  merged**, so "deferred" describes a wait that never ends. The guard's own correct message is
  re-emitted immediately after, so the reader is not left with only the wrong line. It lives in
  a DO-NOT-TOUCH file and is worth an `E99` maintenance fix; R6 documents the recovery instead.

## Open questions

Both are contradictions between shipped components that surfaced while speccing. Each is
resolved in the requirements above; they are recorded here because the approval gate should see
the reasoning, not just the outcome.

1. **The brief's decision #2 says the feature "stays `in-review` while any increment PR is
   open". Taken literally that state is unworkable, so this spec carries the decision's
   substance and not its phrasing.** `in-review` routes to the Reviewer
   (`agents/orchestrator.md` step 4), but between increments the work that has to happen is the
   *Builder* writing increment N+1. A feature parked at `in-review` with an open increment PR
   would be re-reviewed instead of built. R7 therefore states the decision's actual content —
   **`done` is not written while any increment PR is open or unmerged, and there is no
   per-increment board record** — and the doctrine puts the between-increment cycle on the
   existing arc: `in-review` while an increment is under review, back to `in-progress` when the
   Builder starts the next one, which is the same transition a Reviewer reject already performs.
   No new status, no new field, no selector change.

   A second premise in that decision is also inexact and should not be repeated in the shipped
   prose: `done-but-unmerged` is a **diagnostic reason string for umbrella slices**, and
   `merged` is a **slice-level** field. There is no feature-level `merged`, and a single-repo
   feature's `depends_on` gate reads the stored feature status only. So "the vocabulary already
   exists" is true of slices and not of features; what actually delivers the sequencing for a
   stacked feature is holding `done` plus `AGENTS.md`'s wait-for-merge rule.

2. **`docs/WORKFLOW.md` currently makes a false statement about the installer, shipped by
   E21-F04, and R10 corrects it.** The lane's closing paragraph says that when
   `pr_loop.enabled` is `false` "no stacking documentation is stamped". It is stamped:
   `harness-install.sh` copies the prose tier — `HARNESS_BODY_PROSE='AGENTS.md agents docs
   specs/_templates specs/glossary.md'` — unconditionally, so every install carries the lane
   section whatever the flag says. The honest statement is the one R10 requires: the
   documentation ships with the body, the *behavior* is gated. Correcting a false sentence is
   not a re-spec of E21-F04's mechanism, which is unaffected.

3. **Not a contradiction, but the approval gate should weigh it:** R9 forbids the word `atomic`
   outright in the lane's sections rather than requiring the denial sentence E21-F04 shipped in
   the lane's opening paragraphs. The trade is deliberate — a
   denial degrades into the withdrawn claim if a single negation is lost in an edit, whereas
   "merging increment A publishes A's work to the default branch while B and C are still open"
   cannot. The ban is scoped to the lane's sections in the three files this feature edits;
   `CHANGELOG.md`, `epic.md`'s Notes and E21-F04's own spec keep their historical wording.

   **The one place the doctrine survives outside the prose tier, named rather than hidden:**
   `tools/pr-stack-guard.sh`'s header comment (lines 5–7) states it in denial form, banned token
   included. That file is DO NOT TOUCH here — it is E21-F04's shipped guard, its header is the
   rationale a maintainer reads before changing exit codes, and rewording it would put an
   unrelated behavioral file in this diff. So R9 claims "exactly one place **in the prose
   tier**", which is true and checkable, rather than "exactly one place", which would not be.
   Aligning the guard's header is a fair `E99` follow-up.

4. **The brief's In-scope says the seams come from "E21-F01's wave boundaries". E21-F01 defines
   none, so R3 substitutes the seam it actually defines — and the gate should see the
   substitution rather than find it in the plan.** `wave` appears zero times under
   `F01-feature-size-budget/`, `agents/driller.md` and `agents/architect.md`. What E21-F01 does
   define (its R4) is: split an over-budget candidate into **sibling features sequenced along
   the intra-epic `depends_on` graph**. R3 reuses exactly that, which is what "rather than
   inventing a second rule" asks for; the word "wave" in the brief traces to the micro-specs
   pattern quoted in the epic brief and to `/sdd-fix-parallel`'s unrelated dispatch waves, not
   to anything E21-F01 shipped. R3 and T8 also remove the term from the lane so a second
   vocabulary does not survive by accident in the example branch names.

## Non-functional

- **Prose + tests only.** No production code, no schema change, no new dependency.
- Installed body changes (`agents/`, `docs/`) ⇒ `VERSION` **MINOR** bump + `CHANGELOG.md` entry,
  per `AGENTS.md` → Versioning. **No test may assert a `VERSION` value**, and no test may diff a
  DO-NOT-TOUCH file against `main` — both are anti-patterns this repo has paid for three times.
- POSIX sh; the new suite is discovered by `tools/run-tests.sh` and must be green under
  `sh tools/run-tests.sh` (the configured `verification.test_command`).
- The new suite must be isolated for concurrent execution: per-case `mktemp` fixtures, no writes
  into `state/`, `specs/` or `progress/`, and a sandboxed `HOME` **and** `CODEX_HOME` on every
  installer-invoking case.
- Budget: `change_size.max_requirements: 12`. This spec declares **10**, the count the brief
  scoped. An eleventh is affordable; a thirteenth would require a split.
