# The stacked-PR lane: doctrine, seams, and role contracts — Test Contract

> The traceability matrix: every `R-id` in the `.spec.md` maps to a concrete, executable test.
> The Reviewer fails the feature if any `R-id` lacks a passing test.

All tests live in **one new suite, `tests/test_stacked_lane.sh`**, discovered automatically by
`tools/run-tests.sh` (the configured `verification.test_command`). `tests/test_pr_loop.sh` is not
edited: its `E21-F04` block is shipped and passing, and this feature adds beside it.

## Two mechanics every assertion depends on

**1. Extract the section first, with a FENCE-AWARE extractor.**

```sh
# sect <file> <heading-text> — ONE section body; stops at the next heading of ANY level.
sect() { awk -v h="$2" '/^```/{f=!f} !f && /^#+ /{k=(index($0,h)>0);next} k' "$1"; }

# span <file> <h2-heading-text> — a whole `## ` section INCLUDING its `###` subsections.
span() { awk -v h="$2" '/^## /{k=(index($0,h)>0);next} k' "$1"; }
```

The `/^```/{f=!f}` toggle is **not** decoration. `agents/builder.md`'s house idiom is
fence-blind, and every shell fence in these docs contains `#` comments — so on the very file this
feature edits, the bare idiom returns three lines instead of the whole section and reports a
`gh pr create` count of **1** where the section really holds **4**. R4's flagship assertion would
then have passed on a section that still contained the three-PR block it exists to delete. A
whole-file grep is forbidden for the same class of reason: it is satisfied by any unrelated
occurrence elsewhere, including one the same change just added.

**2. Never bind a possibly-zero `grep -c` under `set -eu`.** `grep` exits `1` on no match, so
`n="$(… | grep -c foo)"` aborts the suite **silently on the passing path** — which is the passing
path for R8's "`increments` count is 0" and both of R9's absence sweeps. Use
`n="$(… | grep -c foo || true)"` for counts, and `if … | grep -q foo; then fail "…"; fi` for
absence assertions. Every "count is 0" row below means the `grep -q` form.

## Per-test assertions

Shorthands: `WF` = `docs/WORKFLOW.md` (source tree), `IWF` = the **installed**
`.harness/docs/WORKFLOW.md` inside R10's fixture target, `BLD` = `agents/builder.md`, `ORC` =
`agents/orchestrator.md`, `LANE` = the `##` heading text `Stacked-PR lane`.

**`test_entry_condition_stated` (R1)**
- `sect WF '### Entry condition'` is non-empty (the subsection exists).
- That body contains `verification.test_command` — a config key an editor cannot paraphrase.
- That body contains `independently safe` — the safety half of the condition. (`default branch`
  alone is **not** used as an anchor: every sentence in the subsection carries it, so it would
  discriminate nothing.)
- That body contains `first increment PR` — the timing the requirement pins.
- **Fails today**: no `### Entry condition` subsection exists.

**`test_not_served_case_refused` (R2)**
- `sect WF '### Entry condition'` contains `feature flag`.
- It contains the load-bearing phrase `this epic does not solve`.
- It contains a refusal token: `not a candidate` **or** `do not stack`.
- **One list, one place:** `sect WF '### When to use what'` does **not** contain
  `separate independent features` (the row-3 alternative list that disagrees with the one above).
  `grep -q` form.
- **Fails today**: the shipped lane names feature flags but records no refusal and no
  open-problem status, and row 3 carries a competing list of alternatives.

**`test_seam_rule_is_depends_on` (R3)**
- `sect WF '### Where to cut'` is non-empty and contains `depends_on` and `E21-F01`.
- `span WF "$LANE"` contains **no** case-insensitive `wave` (`grep -qi` form). This covers the
  dangling "wave structure" citation, the opening paragraph's "each wave can land on `main`",
  and the `feat/wave-N` example branches in both the growing and restack sections — a
  `wave structure`-only check would have left three of the four.
- **Fails today**: the heading is `### Wave-boundary guidance`, and `wave` appears throughout.

**`test_stack_is_grown_not_prebuilt` (R4)**
- `sect WF '### Growing the stack'` is non-empty.
- Its `gh pr create` count is **exactly 1** — `n="$(sect … | grep -c 'gh pr create' || true)"`,
  then `[ "$n" = 1 ]`. This is the assertion that bites: the shipped block creates three PRs up
  front, which is the up-front creation the doctrine forbids. It only bites with the fence-aware
  `sect`; with the bare idiom it reads 1 today and would pass on an unchanged block.
- `span BLD 'Stacked increments'` contains `one increment at a time`, and its `gh pr create`
  count is **≤ 1** (`at most` in the role file: the example belongs in WORKFLOW, and zero there
  is correct).
- **Fails today**: the section is named `### Creating stacked increments`; extracted correctly it
  holds 4.

**`test_restack_is_builder_owned` (R5)**
- **Cross-file, derived — the strongest assertion in this contract.** Read the section name the
  installer's diagnostic points at rather than freezing it:
  `named="$(sed -n "s/.*docs\/WORKFLOW\.md '\([^']*\)'.*/\1/p" harness-install.sh | head -1)"`.
  Assert `named` is non-empty, and that some `^### ` heading line in `WF` contains it.
- **No literal `^### Restack procedure$` check.** Freezing the heading would fail a *correct*
  future rename that moved heading and installer message together — and the derived check above
  already catches the only failure that matters (the two drifting apart). Stated tradeoff: the
  derived form does not pin the heading's wording, so a Builder could satisfy it with any heading
  the message happens to name; T6 is what pins the wording, and the message is DO NOT TOUCH.
- `span BLD 'Stacked increments'` contains `Restack procedure` and `restack`.
- **Fails today**: the heading is `### Manual restack procedure (R7)`, so the installer's
  `'Restack procedure'` pointer resolves to no heading, and `BLD` has no such section.

**`test_retarget_recovery_documented` (R6)**
- `sect WF '### Recovering from a manual retarget'` is non-empty and contains
  `gh pr edit --base`, `pr-stack-guard.sh`, and `exit 6`.
- **Fails today**: the subsection does not exist. Note the honest framing — this branch is *not*
  undocumented in general (`tools/pr-stack-guard.sh` lines 25–27 and 89–102 explain it, and the
  guard re-emits its own message on exit 6); it is undocumented **in `docs/WORKFLOW.md`**, which
  is where a reader looks. The `exit 6` token is the only discovery path from the loop's output,
  because the guard's message carries no pointer to WORKFLOW and the loop's headline for this
  branch is wrong — both DO NOT TOUCH, both recorded in the spec's Out of scope.

**`test_done_defers_to_last_increment` (R7)**
- `span ORC 'Stacked increments'` is non-empty and contains `last increment` and
  `no per-increment`.
- **The trigger signal is named:** that span contains `tasks.md` (the unticked-task signal). An
  Orchestrator with no signal cannot apply the rule, because R8 deliberately leaves the board
  with nothing recording "increment 2 of 3".
- **No invented status — a real exclusion, not a presence check.** Parse
  `store/tasks.schema.json` with `python3` and assert the **feature** `status` enum is exactly
  `pending, spec-ready, in-progress, in-review, done`. Presence of `in-progress`/`in-review` in
  the prose is *not* used as the exclusion: a section can name both and still invent `in-stack`.
  A new status would have to reach the enum or `init.sh` would reject the board, so this has one
  producing path.
- **The contradicting rule carries the exception:** `sect ORC '### Build↔review rounds'` contains
  `Stacked increments` (the back-reference T13 adds). Without it, a reader who stops at
  "**Approve** → `done`" gets the wrong rule.
- `sect WF '### What the board shows'` also contains `last increment` — the same anchor in both
  files is what makes a one-sided edit fail.
- **Fails today**: `ORC` does not mention stacking at all.

**`test_board_shows_one_feature` (R8)**
- `sect WF '### What the board shows'` contains `baseRefName`, `slices[]` and `increments[]`.
- `store/tasks.schema.json` contains no `increments` property — `grep -q` absence form, never a
  bound `grep -c`.
- The slice item schema still requires `repo`: parse with `python3` and assert `repo` is in the
  slices item's `required` array. Parsed, not grepped — a grep for `repo` in a JSON schema has
  several producing paths.
- **Honesty note:** the two schema assertions are *regression guards*. They pass trivially today;
  their value is that each has exactly one producing path (someone adding the field / relaxing
  the requirement) and an unambiguous failure message. The doc assertions above are what prove
  the decision was recorded, and those fail today.

**`test_doctrine_stated_once_mechanically` (R9)** — four assertions, all on extracted sections:
- **Cited, not copied:** `span BLD 'Stacked increments'` and `span ORC 'Stacked increments'` each
  contain `docs/WORKFLOW.md`.
- **Not restated:** neither span contains `verification.test_command` (`grep -q` absence form).
  This is the direct anti-drift check — a Builder who copies the entry condition into a role file
  fails here.
- **Not in a shim:** for every `.claude/agents/*.md` in this repo, the file contains neither
  `Stacked increments` nor `baseRefName`. *Honesty note, same as R8's:* this is a
  trivially-passing regression guard — the shims are generated pointer stubs, so the expected
  work is zero edits. It is scoped to `.claude/agents/` because that is the only shim tree
  checked into this repo; the `.codex/`, `.gemini/`, `.agents/` and `opencode.json` trees are
  installer-generated and absent here, and `harness-install.sh` is DO NOT TOUCH.
- **Mechanical vocabulary:** no case-insensitive `atomic` in `span WF "$LANE"`,
  `span BLD 'Stacked increments'` or `span ORC 'Stacked increments'` (`grep -qi` absence form).
- **Stated limit:** the token ban is exact and total *inside those sections* — it bans a token,
  not a claim, so it cannot be satisfied by another path and cannot be paraphrased around. It
  makes no promise about prose elsewhere: `tools/pr-stack-guard.sh`'s header states the doctrine
  in denial form with the token, and is deliberately out of scope (spec → Open question 3), which
  is why R9 claims "exactly one place **in the prose tier**".
- **Fails today**: the lane's opening paragraphs carry E21-F04's denial sentence, which contains
  the banned token, and neither role file has a section at all.

**`test_lane_ships_when_pr_loop_disabled` (R10)** — the one installer-invoking case:
- Install into a per-case `mktemp` target with `pr_loop` off (`--pr-loop=false`), under a
  sandboxed `CODEX_HOME` as `tests/test_pr_loop.sh::install_at()` does, **plus** a sandboxed
  `HOME` — which `install_at()` does **not** set, and which matters here because
  `harness-install.sh` falls back to `${HOME}/.codex/prompts` when `CODEX_HOME` is unset and a
  future refactor of that fallback must not reach the developer's home.
- Assert the installed `IWF` **does** contain the `Stacked-PR lane` heading — the documentation
  ships with the body. This is the whole test: it is the positive, non-vacuous half, and it
  fails if anyone makes the installer strip the section under the flag.
- Assert `sect IWF '### Opt-in and inert-when-disabled'` does **not** contain
  `documentation is stamped`, and **does** contain `ships with the harness body`.
- Assert `span BLD 'Stacked increments'` and `span ORC 'Stacked increments'` each contain
  `pr_loop.enabled`.
- **Deliberately NOT asserted here:** that `.claude/commands/sdd-pr-loop.md` is absent under the
  gate. `tests/test_pr_loop.sh::test_stacking_inert_when_disabled` already owns that assertion,
  and duplicating it would buy a second full installer run for a fact another suite proves.
- **Fails today**: the shipped paragraph asserts that no stacking documentation is stamped, which
  the first assertion in this same test disproves.

## Behavioral / end-to-end checks

- **Mutation check, mandatory (task T17).** For each `R-id`, revert its edit in place or perturb
  the single anchor it asserts, run the suite, and confirm it fails **with the symptom the
  failure message names** — not merely that something failed. Restore afterwards. Record the run
  in `progress/<run>/`. Carve-out: R8's two schema assertions and R7's status-enum assertion
  cannot be mutated without editing DO-NOT-TOUCH `store/tasks.schema.json` — mutate a **copy** in
  the fixture dir to prove the assertion discriminates, and record that these are regression
  guards on a file this feature does not change.
- **Fence regression check.** Run R4's count with the bare (fence-blind) idiom and confirm it
  reports `1` on the *unedited* file while the fence-aware form reports `4`. That is the concrete
  demonstration that the extractor, not the count, is what makes the assertion real.
- **Heading-misfile check.** Move one correct paragraph (e.g. the entry condition) under a
  neighbouring heading and confirm its test fails.
- **Installed-target read.** R10 reads `IWF`, not the source tree, so the test describes what a
  consumer receives.

## Non-functional checks

- `sh tools/run-tests.sh` green (the configured `verification.test_command`), including every
  pre-existing suite. `tests/test_pr_loop.sh`'s E21-F04 block must still pass untouched.
- `./init.sh` green.
- `sh tests/test_stacked_lane.sh` passes standalone and under `--jobs` concurrency: per-case
  `mktemp` fixtures, cleanup `trap`, no writes into `state/`, `specs/`, `progress/`.
- `python3` is used unconditionally (schema parsing) and needs no skip guard: `./init.sh`
  hard-fails without it, the precedent being `tests/test_grep_probe.sh`. `jq` is not used.
- **No test asserts a `VERSION` value.** **No test diffs any file against `main`.** **No bare
  `grep -c` is bound under `set -eu`.** All three are anti-patterns this repo has paid for.
- `shellcheck tests/test_stacked_lane.sh` clean if `shellcheck` is available (not a gate — the
  suite must not require it).
