# Stacked-PR lane — Functional Spec

## Context
E21-F01 splits features at drill time; E21-F02 catches what slips through. Both assume the
work *can* be split into independently-mergeable units. Sometimes it cannot: a capability
whose intermediate states are not safely shippable to `main` — a half-wired booking tool that
can commit an appointment but cannot confirm it — is one deliverable however many requirements
it holds.

Today the harness offers one shape for that: one branch, one PR, one review surface, and the
non-convergence E21-F03 now measures. The reviewer's budget is per-PR, so an atomic feature
pays the whole review cost in a single pass that provably cannot cover it.

The answer is to split the **review** rather than the delivery: base each increment on the
previous increment's branch. The reviewer reads only that increment's diff; the feature still
lands atomically with respect to `main`, in order.

## Business rules
- Stacking is **opt-in**. The single-PR default is unchanged.
- Merging a child before its parent is a **correctness bug, not a race**. It must be
  structurally prevented, not documented.
- "Waiting for the parent" is a **normal state**, not a failure and not `needs-human`.
- A parent-merge **retarget is not a review event**: it changes `baseRefName`, not the head.
- No new binary dependency. The harness's ethos is POSIX sh + `git` + `gh` + `jq`; a
  third-party stacking tool (Graphite, `spr`, `git-branchless`) is not justified for one lane.

## Architecture alignment
ADRs touched: none — additive lane over the existing loop; no change to the watcher contract,
the board schema, or the agent topology.

## Acceptance criteria (EARS)

- **R1** — When a PR's base is the repository's default branch, the system shall clear it to
  merge (exit 0).
- **R2** — If a PR's base branch is the head branch of another **open** PR, then the system
  shall refuse the merge with a dedicated exit `6` and shall name the parent PR number.
- **R3** — Where a PR's base is not the default branch and no open PR owns that branch, the
  system shall clear it to merge — the parent has already landed.
- **R4** — If `.baseRefName` cannot be read, then the system shall fail **closed** (exit 4)
  rather than assuming the default branch.
- **R5** — Exit `6` shall be distinct from every existing `/sdd-pr-loop` failure code, so a
  healthy child PR is never labelled `needs-human` while its parent is in review.
- **R6** — The `/sdd-pr-loop` gates shall run the guard before any merge, in **both** the
  source-layout command and the installer-generated body, and the tool shall be installed
  executable.
- **R7** — The system shall document the lane — where to cut (the Driller's wave boundaries),
  the merge order, and that a parent-merge retarget is not a review event.

## Out of scope
- **Automated restacking.** If an increment takes a review fix its children need a rebase; the
  harness does not automate that, deliberately. It is a `git` workflow question and a wrong
  automated restack loses commits. Documented as manual.
- Automating the *split* of an existing branch — choosing seams is a human/Architect decision
  informed by the dependency DAG, not a diff-slicing algorithm.
- A board representation for a stack. A single feature with an ordered increment list is
  probably right, but it is a schema change and `slices[]` already occupies adjacent ground.
- Third-party stacked-PR tooling.

## Open questions
- Whether the `done` rollup should wait for the whole stack (almost certainly yes, since the
  feature is atomic by definition) and how that interacts with the Orchestrator's existing
  `done-but-unmerged` slice logic.
- Whether the loop should *create* the stack, or only be safe in the presence of one. This
  feature does the latter: it makes stacking safe, it does not automate stacking.
