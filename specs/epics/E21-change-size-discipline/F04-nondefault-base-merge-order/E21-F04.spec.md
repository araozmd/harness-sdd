# Merge-order safety for a non-default PR base — Functional Spec

## Context

`/sdd-pr-loop` assumes throughout that a PR's base is the repository's default branch. Its
gates only ever ask *"are the checks green and the threads resolved"* — never *"is my base
branch itself still an open PR"*. Any PR opened against a non-default base can therefore be
merged ahead of the branch it is built on. That is not a race; it is a correctness bug, and
`pr_loop.auto_merge` walks straight into it.

The case is not hypothetical or exotic. It arises for a stack increment, for a release
branch, and for any integration branch — three shapes with one shared property: the base is
something other than the repo default, and merging into it out of order corrupts it.

This feature is **the mechanism only**: an offline merge-order guard, its wiring into the
loop's merge gate, and the loop's non-default-base correctness. It carries **no doctrine**.
When to open a PR against a non-default base, how to cut a stack, who creates the
increments, and what the board shows are **E21-F05**, which depends on this feature.

### The claim that must not come back

An earlier attempt at this work was withdrawn during review of PR #78 because it asserted
that a stacked feature "stays atomic with respect to the default branch". **It does not.**
Merging increment A publishes wave 1 to the default branch while B and C are still open. A
non-default base enforces merge **order**; nothing about it makes waves land together.

The claim was not merely wrong — it was dangerous, because it advertised protection against
exactly the half-wired default branch it could not prevent. The salvaged artifact
(`git show 1873af9:tools/pr-stack-guard.sh`) still carries the sentence verbatim in its
header. Correcting it is **R7**, and it is enforced by a greppable assertion rather than a
prose promise, because prose is how the false claim survived four review rounds.

## Business rules

- **Exit 0 requires proof.** The guard clears a merge only when the PR's base is the merge
  target the caller declared. Every other state — including states the guard cannot fully
  explain — withholds. This is the same fail-closed shape the loop already applies to
  `head_ok`, `merge_ok`, and thread enumeration.
- **Withholding is not an error.** A healthy child PR whose parent is still open is a
  normal, expected state. Reporting it as a failure trains operators to ignore non-zero
  exits, which is how the *real* failures stop being read.
- **A success must never be silent.** Decision 2 makes a withheld merge return success, so
  the non-zero exit that used to make a stuck loop visible is gone. Every withheld state
  therefore has to *say* what it is waiting on and what the operator must do — including
  when the honest answer is "waiting will not clear this; retarget the PR". A success that
  reports nothing is indistinguishable from a loop that has quietly stopped working.
- **The guard is the whole correctness burden.** `auto_merge` stays enabled on a PR with a
  non-default base (human-gate decision 1), so nothing else stands between a stacked child
  and an out-of-order merge. Every leg of the guard is therefore individually
  mutation-proved — see `.tests.md`.
- **The guard is offline.** It evaluates JSON the caller already fetched. No `gh`, no
  network, no `git`, no real stack needed to test it. This is why the artifact survived its
  own feature's withdrawal, and it must not be traded away.
- **Nothing about a non-default base changes how a review is read.** Clean-signal
  detection, the freshness rule (`created_at >= trigger.created_at`) and `max_rounds`
  semantics are untouched by this feature.
- **No file this feature ships or edits may assert or imply that a non-default base
  delivers a feature atomically, simultaneously, or "all at once".** This is a defect
  class, not a style preference.
- **Inert when `pr_loop.enabled` is not `true`.** The guard is invoked only from the
  `/sdd-pr-loop` body, which the installer stamps only when the opt-in gate reads `true`.
  The tool itself ships in the harness body and is simply never called.

## Acceptance criteria (EARS)

### The guard — `tools/pr-stack-guard.sh`

- **R1** — When the PR's base ref equals the merge target supplied by the caller, the guard
  shall exit `0` and report the base as safe to merge.
- **R2** — When the PR's base ref equals the head ref of an open PR, the guard shall exit
  `6` and its message shall name that open PR's number as the PR to merge first.
- **R3** — When the PR's base ref is neither the supplied merge target nor the head ref of
  any open PR, the guard shall exit `6` and its message shall state that the PR has not
  been retargeted and that waiting will not clear it — the operator must retarget the PR or
  declare the merge target.
- **R4** — If no merge target is supplied, **or the supplied merge target is empty**, then
  the guard shall exit `4` naming the missing argument, and the guard shall carry **no
  built-in branch-name default** of any kind.
- **R5** — If an input file is missing, unparseable, yields an empty `.baseRefName`, or
  does not parse as a JSON array where an array is expected (a zero-byte file included),
  then the guard shall exit `4` and shall never exit `0`.
- **R6** — The guard shall reach every verdict from its two input files alone, with neither
  `gh` nor `git` nor any network access available on the host.
- **R7** — The guard's own documentation shall state that it enforces merge **order**, and
  neither it nor any `/sdd-pr-loop` body shall claim that a non-default base delivers a
  feature atomically or simultaneously.

### The loop — `/sdd-pr-loop`

- **R8** — Where `pr_loop.auto_merge` is `true`, the loop shall run the guard against the
  PR's own base and the open-PR list **before** it posts the ready-to-merge summary,
  **before** it resolves any review thread, and **before** either merge path (`--merge` and
  `--squash`), and shall run a merge command **only** on exit `0`.
- **R9** — When the guard exits `6`, the loop shall take the **merge-order-withheld**
  terminal state and return **success**: it shall post one terminal-state comment carrying
  the handover summary and the guard's verdict message verbatim, and shall merge nothing,
  resolve no review thread, apply no `needs-human` label, post no "all gates green"
  comment, start no further round and post no additional `@codex review`; and the loop's
  terminal-states contract shall name it as one of exactly **three** successful outcomes.
- **R10** — While `merge_strategy` is `squash`, the loop shall enumerate the PR's commits
  for the squash message against the **PR's own base ref**, not against the repository's
  default branch.
- **R11** — When the PR's base ref changes because GitHub retargeted it after the parent
  merged, the loop shall re-evaluate the guard rather than treat the change as a review
  event, and no review-signal path — clean-signal detection, the freshness anchor,
  `max_rounds` accounting — shall read the base ref.
- **R12** — The **installed** `/sdd-pr-loop` body — the one `harness-install.sh` generates,
  not only the source-layout copy — shall carry the guard step in front of both merge
  paths, and `tools/pr-stack-guard.sh` shall be installed executable.

## Naming: the terminal state, and the guard's flag

Two names changed after the doc-critic pass; both are recorded here so a reviewer holding
the brief does not read a deviation as drift.

- **`--default-branch` → `--merge-target`** (human-gate decision, 2026-07-29). Under
  decision 3 the flag means "the branch the caller declares it is safe to merge into",
  which on a release-flow repo is *not* the default branch. The old name described the
  value it usually holds rather than the thing it means, and the new one matches the
  `HARNESS_MERGE_TARGET` env knob. The guard's header, usage text, **verdict messages** and
  the escape-hatch comment all move with it.
- **"waiting-for-parent" → "merge order withheld"** (Architect's call; the brief's label
  survives as the common-case wording). Exit `6` has two legs and only one of them has a
  parent to wait for. On R3's leg the parent may have already merged without deleting its
  branch, so *nothing* clears the state by waiting — the operator must retarget. Naming the
  state after the always-true fact (the guard withheld) rather than the sometimes-true one
  removes an operator-facing lie. The R2 leg's message still reads "waiting on parent PR
  #N", so the brief's vocabulary stands where it is accurate.

## Resolved question — should an unowned non-default base withhold or pass?

**It withholds (R3). Confirmed, and the reasoning is stronger under decision 3, not weaker.**

The salvaged guard withheld on the grounds that a child whose parent merged *and was
deleted* is retargeted by GitHub to the default branch anyway, so a base that is
non-default and owned by no open PR means the retarget has not happened yet. Two states
produce it, and both end with the loop reporting success while the PR's commits are nowhere
near the default branch:

1. The parent merged but GitHub has not retargeted the child yet — the parent is already
   gone from the open-PR list while `baseRefName` still names the old branch.
2. The parent merged **without** deleting its branch — then no retarget ever happens and
   the stale base persists indefinitely.

Decision 3 removes the guard's literal `main` fallback and has the caller supply the merge
target. That changes *how the safe branch is known*; it adds no knowledge whatsoever about
an unowned non-default base. So the original argument survives intact. Three things make it
stronger:

- **The declaration is now meaningful.** With a hard-coded `main`, the flag was a
  correction to a wrong guess. Now it is the caller's explicit statement of the branch it
  intends to merge into. A caller that legitimately merges into a release or integration
  branch says so; "no open PR owns this base" is not a statement of intent, and must not be
  read as one.
- **The cost asymmetry moved further.** Under decision 2 a withheld merge is a **success**,
  not a `needs-human` — so a false withhold now costs a hand-back that a human reads once,
  while a false clear costs the feature (commits merged into a dead branch).
- **It makes the caller's own failures fail closed for free.** If `gh pr list` errors, the
  open-PR list comes back empty; under a pass-when-unowned rule that empty list would clear
  a genuinely stacked child. Under R3 it withholds.

**But state 2 never resolves, so the withhold has to say so.** This is the one place where
decision 2 could turn a loud failure into a silent stall: a PR whose base branch was merged
but not deleted withholds on every round, forever, returning success each time. R3 and R9
therefore require the message to name the remedy — retarget the PR, or declare the merge
target — instead of promising that waiting will help.

**Operational consequence for a release/integration flow.** A repo whose PRs legitimately
target a long-lived integration branch would otherwise withhold forever. The escape hatch
is the guard's own argument, surfaced at the loop: the loop resolves its merge target from
`HARNESS_MERGE_TARGET` when set, falling back to the repository default branch. This was
**kept at the human gate** (2026-07-29): env-only, in line with the command's existing
`HARNESS_*` execution knobs, and inert for any repo that does not set it. It costs
documentation in four places — see `.plan.md` — because an env knob documented in one body
and absent from the operator doc is exactly the drift this repo has P1'd before. And
because an unresolvable knob would otherwise hand the guard an empty string, R4 fails
closed on an **empty** merge target, not merely a missing one.
