# Per-round finding trend at the round cap — Technical Plan

## Stack & dependencies
POSIX sh + `jq`. `jq` is already a hard precondition of `/sdd-pr-loop` (step 0 preflight
checks it), so this adds no new dependency to the harness — and `init.sh` must still pass on a
box with neither `gh` nor `jq`, which `tests/test_pr_loop.sh` already asserts.

## Interface  (serves: R1–R6)
`tools/pr-round-trend.sh --cache <.pr-loop/<pr>> [--format text|json] [--window <n>]`

| exit | meaning |
|---|---|
| 0 | reported — at ANY verdict |
| 4 | usage error / unreadable cache |

## Why a tool and not prompt prose  (serves: R8)
The verdict is the whole feature, and a verdict expressed only as instructions in a markdown
command is unverifiable: no test can tell whether a model would have read `1 3 1 2 1 3` as
flat. Extracting it into a script makes the rule executable, testable against fixture round
dirs, and identical across every front-end that gets the command.

## DO NOT TOUCH
- `tools/wait-for-codex.sh` — the exit-code contract (0/1/2/3/4/5), the three clean-signal
  forms, and the `created_at >= trigger` freshness rule are load-bearing and orthogonal. A
  trend feature must not perturb how a clean round is recognised.
- Step 3's `head_ok` fail-closed logic — an unreadable head must keep aborting the round.
- `pr_loop.max_rounds` handling — this feature reports at the cap, it does not move it.

## Approach notes
- **Two edits, not one.** `.claude/commands/sdd-pr-loop.md` is the source-layout copy; the
  installer generates consumers' copies from its own heredoc. Editing only the former is the
  exact wiring gap that has been P1'd in this repo before, so `tests/test_pr_loop.sh` asserts
  against the **installed** body and its failure message names the trap.
- **Window default 3.** Two rounds is too little evidence; four would not have fired until the
  PR had already spent half its budget.
- Concentration comes free: `blocking.json` already carries `.path`, so grouping is one `jq`
  pass over files the loop wrote anyway.
