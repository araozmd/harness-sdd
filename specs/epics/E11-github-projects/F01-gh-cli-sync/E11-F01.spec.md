# GitHub Projects sync via `gh` CLI (no MCP) — Functional Spec

## Context
Teams that live in GitHub Projects want the harness's `state/tasks.json` reflected on
their board so non-CLI stakeholders can see status. The integration must work inside
**MCP-restricted enterprises**, so it uses only the **`gh` CLI** the developer is
already authenticated with — never an MCP server. A one-way board **mirror** for
`github-projects` already exists (`tools/sync-board.mjs`, `store/board-mirror.md`,
`mirror.board` in `harness.config.yaml`): it already projects features onto a Project
via `gh project` / `gh api graphql`, idempotently, inert when unconfigured. This
feature therefore **completes** that existing mirror rather than forking it — it does
**not** introduce a second GitHub code path. Its job is to (a) **pin and enforce** the
supported transport (Projects **v2** via `gh`, with a clear preflight for the required
`gh` version and auth scopes), and (b) **close the installer-wiring gap** so the shipped
harness body's mirror tool is asserted by `tests/test_install.sh`, and (c) **document**
the pinned contract. Inbound ownership / atomic-claim reads and `owner → assignee`
semantics are **out of scope** here — they belong to E10 (E10-F03). F01 projects
**status** only; the pre-existing `assignee` behavior is preserved as-is, not expanded.

## Business rules
- **Transport = `gh` CLI only, never MCP.** All GitHub calls go through `gh` (`gh
  project`, `gh issue`, `gh api`/`gh api graphql`). No MCP server is used or required.
  REST/GraphQL, where needed, is reached via `gh api`.
- **Complete the existing mirror; do not fork it.** There is exactly **one** GitHub
  projection code path — `tools/sync-board.mjs`, `provider: github-projects`. This
  feature extends that file/config; it introduces no parallel tool and no second
  `github-projects` implementation.
- **One-way projection invariant (preserved).** The sync is one-way: `state/tasks.json`
  → board. Agents never **read** the board to decide work; `state/tasks.json` stays the
  single source of truth. Nothing in this feature makes the mirror bidirectional.
- **Projects v2 is the pinned surface.** The supported Project type is **GitHub Projects
  (v2)** — the GraphQL-backed Projects surface that `gh project` / `gh api graphql`
  expose. Classic Projects are **not** supported. This is fixed and documented.
- **No new credential.** Authentication uses the developer's existing `gh auth` session
  (or a token `gh` accepts). No new committed secret and no new credential to provision
  beyond `gh auth`.
- **Config reuse.** All configuration lives in `harness.config.yaml` under the existing
  `mirror.board` shape (`provider` / `owner` / `project_number` / `repo` / `assignee` /
  `status_map`). No new committed config key is introduced by this feature.
- **Inert when unconfigured.** With `mirror.board.provider` empty (the default), the sync
  is a pure no-op that never shells out to `gh` — exactly today's behavior.
- **Idempotent reconcile.** A re-run reconciles (updates the existing project item for a
  feature) and never duplicates: each feature maps to exactly one issue (matched by
  title) and one project item.
- **Status only; ownership deferred to E10.** F01 projects feature **status** onto the
  board. The `owner → assignee` projection and any inbound ownership / atomic-claim read
  are E10's concern (E10-F03). The mirror's pre-existing `assignee` knob is left exactly
  as-is (neither removed nor expanded here).
- **Installed-body change ⇒ VERSION bump (MINOR).** This feature changes the installed
  harness body (the mirror tool preflight, docs, and installer-test assertion), so
  `VERSION` is bumped one SemVer **MINOR** step (additive, backward-compatible).

## Acceptance criteria (EARS)
> Each is one testable behavior with a stable id. See docs/SPEC-FORMAT.md.

- **R1** — When the sync runs with `mirror.board.provider: github-projects` and valid
  config, the system shall project `state/tasks.json` onto the configured GitHub Project
  using **only** the `gh` CLI (`gh project` / `gh issue` / `gh api`), and shall use **no**
  MCP transport of any kind.
- **R2** — The system shall implement the `github-projects` projection through the single
  existing mirror tool `tools/sync-board.mjs`; it shall **not** add a second tool, script,
  or code path that talks to GitHub Projects (exactly one `github-projects` implementation
  exists in the body).
- **R3** — When the sync runs a second time with an unchanged `state/tasks.json`, the
  system shall reconcile existing project items (matched by feature id → issue title →
  project item) and shall create **no** duplicate issue or project item (idempotent
  re-run).
- **R4** — While `mirror.board.provider` is empty or `none` (the default), the system
  shall perform no projection and shall **not** shell out to `gh` (a pure no-op — today's
  inert behavior is preserved).
- **R5** — The system shall read all `github-projects` configuration from
  `harness.config.yaml` under the existing `mirror.board` shape
  (`owner` / `project_number` / `repo`, plus the optional `status_map` / `assignee`), and
  shall introduce **no** new committed config key and **no** new committed secret.
- **R6** — The system shall target **GitHub Projects (v2)** — the GraphQL-backed Projects
  surface reached via `gh project` / `gh api graphql`; it shall **not** target Classic
  Projects.
- **R7** — If the `gh` CLI is absent, or its version is below the minimum required for the
  `gh project` (Projects v2) commands, then the system shall exit non-zero with an
  actionable error that names `gh` and the Projects-v2 / scope requirement, **before**
  attempting any board mutation.
- **R8** — If `provider: github-projects` is selected but a required key
  (`owner` / `project_number` / `repo`) is missing, then the system shall exit non-zero
  with an error naming the missing key(s) **before** shelling out to `gh` (config is
  validated first; the inert path is never a partial mutation).
- **R9** — The system shall project each feature's **status** (via the state-machine →
  board-column mapping, honoring `mirror.board.status_map`) and shall **not** add or
  expand any `owner → assignee` projection in this feature — the pre-existing
  `mirror.board.assignee` behavior is preserved unchanged, and ownership/atomic-claim
  semantics remain E10's (E10-F03).
- **R10** — The mirror shall remain **one-way**: the sync writes only to the board and
  never writes back into `state/tasks.json`, and no agent reads the board to determine
  work.
- **R11** — The system shall provide a `--dry-run` mode that prints the intended board
  changes and mutates nothing (neither the board nor `state/tasks.json`), so a developer
  can preview a projection before applying it.
- **R12** — The harness installer (`harness-install.sh`) shall install the mirror tool
  into the harness body as an **executable** `.harness/tools/sync-board.mjs`, and
  `tests/test_install.sh` shall **assert** that a fresh install ships that executable
  tool.
- **R13** — The documentation (`store/board-mirror.md`) shall state that the supported
  Project type is **Projects v2** (not Classic), name the minimum `gh` version and the
  required `project` + `repo` auth scopes, and reaffirm the `gh`-only / no-MCP transport
  and the one-way invariant.
- **R14** — Because this feature changes the installed harness body (the mirror tool
  preflight, `store/board-mirror.md`, and the `tests/test_install.sh` assertion), the
  `VERSION` file shall be bumped one **MINOR** step (additive, backward-compatible;
  SemVer MINOR, not MAJOR), with a matching `CHANGELOG.md` entry.

## Out of scope
- **Inbound** agent-read of ownership / atomic claims — that is the E10 ownership model
  (E10-F03), not a bidirectional mirror here.
- **`owner → assignee` projection** and any expansion of the ownership semantics. F01
  projects status only; the existing `assignee` knob is preserved, not extended. (E10.)
- **Classic GitHub Projects.** Only Projects v2 is supported.
- **Jira / Monday / Azure Boards.** Their own epics (E12 / E13 / E14); their branches in
  `sync-board.mjs` stay recognized no-op stubs.
- **MCP transport of any kind.**
- **Making the mirror bidirectional** or having any agent read the board.

## Open questions
- None blocking. The three brief open questions are **resolved** as design decisions
  (see `E11-F01.plan.md` → "Resolved open questions"): (1) **Extend, not replace** — F01
  completes the one existing `sync-board.mjs` `github-projects` path (preflight + docs +
  installer-test), avoiding a second GitHub code path; (2) **Projects v2** is the pinned
  supported surface (the mirror already uses the v2 GraphQL / `gh project` surface),
  Classic is unsupported; (3) **assignee/ownership deferred to E10** — F01 projects
  status only and preserves the existing `assignee` knob untouched. A human may revisit
  the minimum-`gh`-version pin (R7) at the approval gate if enterprise fleets ship an
  older `gh`.
