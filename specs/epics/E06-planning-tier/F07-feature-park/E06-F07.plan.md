# Feature-level park — Technical Plan

## Shape

Four touch points, in dependency order. Nothing else changes.

| # | File | Change |
|---|---|---|
| 1 | `store/tasks.schema.json` | Add the optional `parked` object to a feature. |
| 2 | `tools/validate-board.py` | Teach the zero-dep fallback the same rule, so validation agrees with the schema when `jsonschema` is absent. |
| 3 | `tools/next-task.mjs` | One blocker record in `featureBlockers`; one richer `unmet-dependency` detail. |
| 4 | `tools/tasks-lock.py` | `set-status` refuses a transition on a parked feature. |
| 5 | `docs/WORKFLOW.md` | The route/status table gains the park row. |

## 1. Schema

```jsonc
"parked": {
  "type": "object",
  "required": ["reason"],
  "properties": {
    "reason":       { "type": "string", "minLength": 1 },
    "unblocked_by": { "type": "string", "minLength": 1 }
  }
}
```

`reason` required and non-empty is the whole contract: **presence means parked**, and a park
without a legible reason is the defect being fixed. `unblocked_by` is optional — the brief
asks the park to carry "why, and what unblocks it", but a reason that already says so should
not be forced to repeat itself in a second field.

Feature objects do not set `additionalProperties: false`, so an older validator accepts a
board carrying `parked` and simply ignores it. That is the right failure direction: a target
mid-upgrade under-enforces rather than rejecting a board it cannot parse.

## 2. `validate-board.py`

The zero-dep fallback mirrors the slice invariants by hand. Add the same two checks it would
get from the schema: `parked` is an object, and `reason` is a non-empty string. Without this,
`init.sh` on a machine with no `jsonschema` would pass a board the schema rejects — the two
validators disagreeing is worse than either being strict.

## 3. `next-task.mjs` — the park is a blocker, not a route

In `featureBlockers`, beside the `gated-epic` line it mirrors:

```js
if (feature.parked) {
  records.push({ subject: feature.id, code: 'parked', detail: parkDetail(feature) });
}
```

`featureRoute` is **not touched**. That is what makes R2 true by construction: `select()`
computes `otherwiseActionable = ordinary.length === 0 && route !== null`, so a park suppresses
selection through the blocker list alone, and removing it restores the prior route with no
state to restore.

For R5, the existing `unmet-dependency` detail is built from `id=status` pairs; a parked
dependency renders as `id=status (parked: reason)`. One string, no new record, so a dependent
of a parked feature still reports exactly one blocker.

Ordering: the park record is pushed after `gated-epic` and before `unmet-dependency`, so a
feature that is both parked and dependency-blocked lists the park first — the park is the
fact the reader needs.

## 4. `tasks-lock.py` — the park holds against transitions

`set-status` resolves the feature, and before writing:

```
if the feature has a parked object:
    fail: "<id> is parked (<reason>) — unpark it before changing status"
```

Exit non-zero, write nothing. Unparking is an `apply` mutation (the general escape hatch that
already exists), so this adds no new write verb. The refusal names the reason so the operator
does not have to go read the board to learn why their write bounced.

**Blast radius considered:** this repo's own `chore/<ID>-done` flow calls `set-status`. Those
features are never parked, so the flow is unaffected — but a parked feature can no longer be
rolled `done` without an explicit unpark, which is the intended meaning of a park.

## 5. `docs/WORKFLOW.md`

One row in the route/status table plus a short subsection: how to park, how to unpark, and
that a park composes with every status rather than replacing one.

## Risks

- **A park that hides work.** Mitigated only partially — see spec decision 4. The gap is
  documented, not closed.
- **Two validators drifting.** Addressed by touching both in the same change (plan step 2) and
  by a test that runs the fallback path explicitly.
- **`set-status` refusal breaking an existing flow.** Bounded: the only in-repo caller is the
  board-transition chore, which never targets parked features.
