# Doc-critic: advisory review pass over harness-generated docs — Technical Plan

> Translates the .spec.md intent into design. Every decision cites the R-id(s) it
> serves. This feature ships prose + a new role contract + installer wiring + tests;
> there is no application code outside the harness itself.

## Stack & dependencies
- Markdown prose only: create `agents/doc-critic.md`; modify `agents/planner.md`,
  `agents/driller.md`, and `agents/architect.md`; modify `harness-install.sh` and
  `tests/test_install.sh`; update `docs/WORKFLOW.md`; bump `VERSION` and
  `CHANGELOG.md`.
- Verification: POSIX sh + grep (`tests/test_doc_critic.sh`), wired into
  `verification.test_command`. Static contract assertions over the new role and the
  checkpoint wiring in the three generating-agent contracts; one `./init.sh` exit-0
  run.
- New dependencies: **none**.
- Reused, unchanged: `store/tasks.schema.json`, the feature state machine, the
  existing human gates, existing test suites (other than `test_install.sh` additions).

## Data model  (serves: R17)
**No schema change.** The doc-critic is a review pass; it persists no new state in
`state/tasks.json`. Any notes go under `progress/<run>/` markdown, which is already
part of the DocStore. The R17 test asserts the live schema is unchanged.

## API / interface  (serves: R2, R3, R5, R6, R7)
The critic is invoked as a **sub-agent**, not as a command or API. The generating
agent spawns it with a clean context and a `target-type` argument.

| Invocation | Caller | Target-type | Inputs reviewed | R-id |
|---|---|---|---|---|
| Spawn doc-critic after writing plan artifacts | Planner | `plan-output` | `specs/vision.md`, `specs/architecture.md`, `specs/adr/NNNN-*.md`, every seeded `specs/epics/<id>-<slug>/epic.md` | R3, R9, R10 |
| Spawn doc-critic after drilling an epic | Driller | `epic-decomposition` | target `epic.md`, feature table, `progress/inbox/<E##>-F<NN>.md` briefs, appended ADR deltas | R3, R11 |
| Spawn doc-critic after drafting a four-file spec | Architect | `feature-spec` | `<feature>.spec.md`, `<feature>.plan.md`, `<feature>.tasks.md`, `<feature>.tests.md` | R3, R12 |

The spawn contract:
- Pass only `agents/doc-critic.md`, the `target-type`, and the file paths just written.
- The critic returns advisory findings; the generating agent applies fixes inline.
- On critic error/timeout, the generating agent proceeds and appends a note to
  `progress/<run>/`.

## Approach notes
- **One role, parameterized.** A single `agents/doc-critic.md` with a `target-type`
  argument avoids three diverging contracts. The generating agent passes the type and
  the paths; the critic selects its scope from that type.
- **Sub-agent, not command.** The critic is spawned by the Planner/Driller/Architect
  after they write their outputs. This fits the existing model (agents hand off to
  files, sub-agents get clean contexts) without forking the Orchestrator or adding a
  new slash command.
- **Advisory + best-effort protects autonomy.** Because the critic cannot block, a
  timeout or error must never halt the autonomous run. The progress note is the audit
  trail.
- **Installer wiring is the critical integration.** `harness-install.sh` copies the
  whole `agents/` dir, so adding `agents/doc-critic.md` to the source is mostly
  sufficient; the explicit test assertions in `test_install.sh` close the recurring
  Codex finding that new role files are shipped but not asserted.
- **Sequencing:** `agents/doc-critic.md` first (so the other roles can reference it),
  then `agents/planner.md`, `agents/driller.md`, `agents/architect.md`, then
  `harness-install.sh`, then tests, then docs, then `VERSION`/`CHANGELOG` last.
- **Portability.** The contract lives in `agents/*.md` and is copied into
  `.harness/agents/`; no `.claude/`-specific behavior is required. The test asserts
  the role file is installed and references are portable.

## Risks
- **Critic becomes a gate.** If a generating agent waits for human input on critic
  findings, autonomy is lost. Mitigation: R5/R6 pin advisory-only, inline-fix,
  best-effort behavior.
- **Critic scope creep / token burn.** If the critic reviews everything at each
  checkpoint, costs explode. Mitigation: R3 narrowly scopes each `target-type` to the
  just-written docs; R4 limits flags to real downstream problems.
- **Drift between three invocation points.** If Planner, Driller, and Architect each
  describe the spawn differently, behavior diverges. Mitigation: one shared role file
  and tests that grep for consistent `target-type` invocation strings in all three
  contracts.
- **Installer misses the new role.** Mitigation: R13 + R14 assertions in
  `tests/test_install.sh`.
- **False positives slowing autonomous runs.** Mitigation: R4's calibration rule
  (only real downstream problems) and the explicit exclusion of stylistic preferences.
