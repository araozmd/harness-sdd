# Doc-critic: advisory review pass over harness-generated docs — Functional Spec

## Context
The harness generates a lot of documentation before any code is written — vision,
architecture, and ADRs from `/sdd-plan`; epic decompositions and inbox briefs from
`/sdd-drill`; and the four-file feature spec from the Architect. Today none of those
documents is reviewed before they drive downstream work. The human operator is the
sole QA layer, so defects such as placeholders, internal contradictions, ambiguous
requirements, scope creep, or YAGNI either reach the human's desk or slip straight
into implementation. The user is the harness operator who wants to seed a plan and
let it run autonomously for hours: catching doc defects early means fewer bad
autonomous runs and less gate babysitting.

This feature introduces an **automated, advisory doc-critic** that reviews
harness-generated documents at defined checkpoints, flags only issues that would
cause real downstream problems, and lets the generating agent fix them inline
before proceeding. No new human gate is added; the existing `spec-ready` gate does
less work because obvious defects are already gone.

## Business rules
- **Advisory only.** The doc-critic is automated and never blocks. Its findings are
  recommendations; the generating agent applies fixes inline and proceeds.
- **No new human gate.** The critic must not introduce any pause, approval step, or
  hand-off to a human. Autonomous runs remain autonomous.
- **Calibrated severity.** Flag only issues that would cause real downstream problems
  (omitted success criteria, contradictions between ADR and spec, ambiguous scope
  boundaries, YAGNI additions, missing cross-epic dependencies). Minor wording or
  stylistic preferences are not issues.
- **Review documents, not code.** The critic reviews planning-tier docs and feature
  specs. Production code review remains the Reviewer's job (E05).
- **Defined checkpoints only.** The critic runs after `/sdd-plan`, after `/sdd-drill`,
  and after the Architect drafts a four-file spec (before the `spec-ready` gate). It
  does not re-review all docs on every harness command.
- **Best-effort failure posture.** If the critic itself errors or times out, the
  generating agent proceeds and appends a short note to `progress/<run>/` so the
  skipped pass is auditable.
- **Traceability note.** In addition to inline fixes, the generating agent appends a
  brief progress note summarizing what the critic changed.
- **Installed body change.** Adding a new role file and wiring it into existing role
  contracts touches the installed body (`agents/*.md`, generated CLI glue), so this
  change warrants one SemVer MINOR `VERSION` bump in the same PR.

## Architecture alignment
> `specs/architecture.md` does not exist and `specs/adr/` is empty in this repo.
> Under graceful-degradation rules this feature proceeds from the inbox brief alone;
> no fabricated ADRs are cited.

- ADRs touched: none — this feature adds a cross-cutting doc-quality mechanism that
  does not constrain or alter any existing recorded architecture decision.

## Acceptance criteria (EARS)
> Each is one testable behavior with a stable id. See docs/SPEC-FORMAT.md.

### The portable doc-critic role contract
- **R1** — `agents/doc-critic.md` shall exist and shall define an advisory doc-critic
  reviewer contract written for any AGENTS.md-compatible CLI.
- **R2** — `agents/doc-critic.md` shall require the critic to accept a `target-type`
  argument whose allowed values are `plan-output`, `epic-decomposition`, and
  `feature-spec`.
- **R3** — `agents/doc-critic.md` shall require the critic to apply the review scope
  matching the `target-type`: `plan-output` reviews `specs/vision.md`,
  `specs/architecture.md`, the ADRs at `specs/adr/NNNN-*.md`, and each seeded
  `specs/epics/<id>-<slug>/epic.md`; `epic-decomposition` reviews the target
  `epic.md`, its feature table, the per-feature inbox briefs under
  `progress/inbox/`, and any ADR deltas appended by the drill; `feature-spec`
  reviews the four files (`.spec.md`, `.plan.md`, `.tasks.md`, `.tests.md`) for one
  feature.
- **R4** — `agents/doc-critic.md` shall require the critic to flag only issues that
  would cause real downstream problems, evaluated across completeness, consistency,
  clarity, scope, and YAGNI.
- **R5** — `agents/doc-critic.md` shall state that critic recommendations are
  **advisory only** and never block the generating agent; the generating agent shall
  apply fixes inline and then proceed.
- **R6** — `agents/doc-critic.md` shall state that if the critic invocation errors
  or times out, the generating agent shall proceed best-effort and append a note to
  `progress/<run>/` recording the skipped or failed review.
- **R7** — `agents/doc-critic.md` shall state that the critic writes a short progress
  note under `progress/<run>/` summarizing the issues it found and the inline fixes
  applied, in addition to the inline fixes themselves.
- **R8** — `agents/doc-critic.md` shall state that the critic reviews **documents**
  only and does not review production code.

### Planner checkpoint (/sdd-plan output)
- **R9** — `agents/planner.md` shall require the Planner, after writing the
  `/sdd-plan` artifacts (`specs/vision.md`, `specs/architecture.md`, ADRs,
  `state/tasks.json` draft epics, and `epic.md` files) and before reporting success,
  to spawn the doc-critic with `target-type=plan-output` and apply any advisory
  fixes inline.
- **R10** — `agents/planner.md` shall require the Planner checkpoint to enforce that
  every `draft` epic is independently drillable: each seeded `epic.md` must carry
  (1) a business brief, (2) epic-level success criteria (outcomes), (3) technical
  considerations / restrictions / non-goals, (4) cross-epic dependencies and
  boundaries, and (5) pointers to the relevant shared ADRs in `architecture.md`.

### Driller checkpoint (/sdd-drill output)
- **R11** — `agents/driller.md` shall require the Driller, after decomposing the epic
  (feature entries, `epic.md` feature table, inbox briefs, ADR deltas) and before
  reporting success, to spawn the doc-critic with
  `target-type=epic-decomposition` and apply any advisory fixes inline.

### Architect checkpoint (before spec-ready gate)
- **R12** — `agents/architect.md` shall require the Architect, after drafting a
  feature's four-file spec and before handing off to the `spec-ready` gate, to spawn
  the doc-critic with `target-type=feature-spec` and apply any advisory fixes inline.

### Installer wiring and versioning
- **R13** — `harness-install.sh` shall copy `agents/doc-critic.md` into the installed
  `.harness/agents/` body on every install or upgrade run.
- **R14** — `tests/test_install.sh` shall assert that `.harness/agents/doc-critic.md`
  is installed and that the installed Planner, Driller, and Architect glue/contracts
  reference the doc-critic role.
- **R15** — The repository shall record this installed-body change as one SemVer
  MINOR `VERSION` bump with a matching `CHANGELOG.md` entry describing the new
  doc-critic role and the three checkpoint wirings.

### Documentation
- **R16** — `docs/WORKFLOW.md` shall document the three doc-critic checkpoints (after
  `/sdd-plan`, after `/sdd-drill`, before the `spec-ready` gate) and that the critic
  is advisory, inline-fixing, and best-effort.

### Boundaries / no schema change
- **R17** — `store/tasks.schema.json` shall be unchanged by this feature; the critic
  adds no new TaskStore fields or status values.
- **R18** — This feature shall not add or modify any human gate, approval mechanism,
  or feature/epic status value beyond the existing `spec-ready` pause.

## Out of scope
- Reviewing production code — that is E05 (Reviewer).
- Re-reviewing all docs on every harness command — the critic runs only at the three
  defined checkpoints.
- Per-developer calibration or customization of the critic — that is the sibling
  feature E09-F02.
- Authoring ADR deltas or changing the ADR file format/numbering.
- Retro-fitting critic reviews to already-written specs or plans.
- Making the critic a standalone slash command or an Orchestrator-driven phase — it
  is invoked inline by the generating agent (Planner/Driller/Architect) as a
  sub-agent.

## Open questions
- None. The brief's open questions are resolved as follows:
  - **One reviewer or three?** One parameterized role (`agents/doc-critic.md`) with a
    `target-type` argument to avoid drift.
  - **Who invokes it?** The generating agent (Planner, Driller, Architect) spawns the
    critic as a sub-agent after writing its outputs.
  - **Failure posture?** Best-effort/never-blocking; proceed with a `progress/<run>/`
    note on error or timeout.
  - **Where do findings go?** Inline fixes plus a brief progress note under
    `progress/<run>/`.
