# Actionable reports — Functional Spec

## Context

Maintainers cannot investigate metadata-only issues. A separate public evidence
payload must describe a verified harness defect while raw session notes stay local.
The user authorized autonomous execution and filing as soon as findings are ready,
without further permission prompts. The inbox brief is `progress/inbox/E32-F06.md`.
Complexity is `complex`: this changes a privacy boundary and synchronizes an emitter,
its generated copies, and tests that currently enforce the opposite behavior.
There are 12 requirements, within `change_size.max_requirements: 12`.

## Business rules

- Preserve exactly four triggers and their existing exclusions. No project bugs,
  transient network/auth failures, or correctly caught agent mistakes qualify.
- Public details are deliberately composed from verified harness source/behavior
  and synthetic examples. Never copy raw notes, project contents, environment dumps,
  credentials, customer names, private repository identifiers, or unrelated logs.
  The deterministic filters catch a defined unsafe corpus; they cannot establish
  that arbitrary prose is confidential or factually correct. The owner must inspect
  the draft against direct evidence before calling the tool. If uncertain, keep local.
- JSON schema and bounds are in the plan. Required prose describes facts, not merely
  a command/version/phase/trigger or a restatement of a field name. No invented
  reproduction, exit status, or recurrence is allowed. Source inspection evidence
  is valid when execution would be unavailable or inappropriate.
- Filing is single-writer: only the session-owning Orchestrator, Fixer, Inception,
  Planner, or Driller invokes the reporter. Subagents persist evidence for that owner.
- Ordinary incomplete findings can be completed and re-submitted by the owner with
  the same session token; there is no background retry queue or consent step.
- **Supersession:** E32-F06 R1–R6 replace E32-F02 R7's metadata-only body and expand
  R8's fixed redaction boundary; R7 replaces F02 R6 and the title identity in R9.
  E32-F06 R9–R10 replace E32-F03 R3, the end-only duty in R5, and R8's prohibition
  on public prose; R10 expands F03 R4's minimal ledger. All other F02/F03 guarantees
  remain unless explicitly replaced here. Historical specs remain unchanged.

## Acceptance criteria (EARS)

- **R1** — When an enabled report is submitted, the reporter shall require a distinct
  `--details-file` JSON payload conforming to the plan's closed, bounded schema
  before any `gh` invocation.
- **R2** — If required public text is missing, blank, a defined placeholder, only
  metadata, or unusable after sanitation, then the reporter shall withhold publication
  with field-specific local diagnostics.
- **R3** — When public details are validated, the reporter shall require the exact
  trigger-specific evidence fields defined in the plan in addition to common fields.
- **R4** — If details contain any member of the plan's unsafe corpus or forbidden
  control/marker syntax, then the reporter shall retain the report locally without
  invoking `gh` or emitting any of that content upstream.
- **R5** — When drafting or assembling a public report, the reporting command and tool
  shall keep `--notes-file` content exclusively local and use only accepted structured
  metadata plus validated, sanitized public details for outbound artifacts.
- **R6** — When a complete safe report passes existing configuration and metadata
  gates, the reporter shall create a body with the unchanged single v1 marker,
  accepted metadata, and clearly labeled common and trigger-specific evidence sections.
- **R7** — When checking duplicates, the reporter shall compare exact titles containing
  a deterministic fingerprint of accepted finding details as defined in the plan, so
  distinct findings sharing trigger/symptom/file can file separately and the same
  canonical finding cannot create another open issue or comment.
- **R8** — While processing a report, the reporter shall retain existing opt-out,
  ownership validation, session identity, cap, local-copy, and non-blocking fallback
  behavior in source, standalone installed, and thin-child layouts.
- **R9** — When a verified report has complete safe evidence at any phase, the
  session owner shall invoke sdd-report automatically at the next control opportunity,
  without a user permission prompt or waiting for task completion, then resume the
  authorized workflow unless an existing stop gate applies.
- **R10** — When a subagent encounters a reportable finding, the subagent shall append
  evidence sufficient for the owner to assess the public-detail contract to the local
  feedback ledger, leaving publication to the owner and never inventing missing facts.
- **R11** — If init exits non-zero due to a harness malfunction, then the session
  shall preserve the existing at-most-one reporting-only exception followed by a hard
  stop with no repair, board write, or continued work; missing evidence shall only
  change that attempt's outcome to local-only.
- **R12** — When this capability ships, the harness shall expose the same updated
  contract in canonical prompts, generated host surfaces, current documentation, and
  release 0.90.0, with configured verification and independent Reviewer evidence.

## Out of scope

New triggers/symptoms, labeler or triage redesign, automatic defect repair, board
schema changes, rewriting historical specs, reopening earlier ambiguous issues,
background retries, fuzzy cross-wording deduplication, and semantic secret detection.
