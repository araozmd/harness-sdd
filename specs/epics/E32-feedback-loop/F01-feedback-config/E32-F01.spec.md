# `feedback:` config block + opt-out notice — Functional Spec

> R-ids in this document are `R1 … R11`; their fully-qualified form is `E32-F01:R1 … E32-F01:R11`.

## Context

E32 makes an installed harness file a scrubbed GitHub issue upstream when one of four narrow
triggers fires. Before anything reports, every installed harness needs **one visible
switch** for it, and the operator must be told the switch exists at the moment reporting
becomes possible. This feature ships that switch: a top-level `feedback:` block in
`harness.config.yaml` that is **on by default** (user decision, 2026-09-25). It is seeded
on a fresh install. An upgrade of an install that predates the block seeds the same block.
Both paths print a one-line notice that names the upstream repo and how to turn it off.
The reporter (F02) and the prompts that call it (F03) come later. Until F03 lands the
switch is accurate but inert: nothing reads it yet except the installer's notice.

The users are the operators of every target repo. They see the notice and own the switch.
The later E32 features are also users: they consume the resolution contract this feature
documents.

**Complexity basis (`complex`).** The block lives in two copies that must stay
byte-identical: the seed template `harness.config.yaml`, which a fresh install copies, and the
`migrate_config` heredoc, which an upgrade appends. A drift between a seed block and its
migration heredoc is a defect class this harness has already paid for. See the `models:`
and `workers:` convergence lessons in `progress/lessons.md`, where a one-sided desync
survived all 47 suites. The feature also has to honor ADR-0004's config tiering across the
installer, the umbrella cascade, and two docs.

## Business rules

- **Default ON, with transparency.** The shipped values are `enabled: true`,
  `repo: github.com/araozmd/harness-sdd`, and `max_per_session: 3`. Seeding the block
  without printing the notice is not allowed. That is how reporting stays visible to the
  operator.
- **Host-qualified repo.** `feedback.repo` uses the grammar `[HOST/]OWNER/REPO`. The shipped
  default is host-qualified (`github.com/...`), so a target checked out from GitHub
  Enterprise still reports to the public upstream and not to its own enterprise host. A
  value that leaves out `HOST` means `github.com`. The reporter's auth check targets the
  resolved host (`gh auth status --hostname <host>`). F02 implements that check; this
  feature fixes the grammar.
- **The operator's block is never overwritten.** If any column-0 line starts with
  `feedback:`, the installer treats the block as the operator's. That covers a block-style
  header with a trailing comment, any values, or missing keys, and also the one-line flow
  form (`feedback: { enabled: false }`, `feedback: null`). It adds no key, rewrites no value, and appends no
  second block.
- **Opting out means `enabled: false`, not deleting the block.** A missing block is
  re-seeded (ON) on the next upgrade, with the notice. The documented opt-out is
  `feedback.enabled: false`.
- **Resolution contract (for every consumer, F02/F03 included):**
  - `enabled`: after a trailing `# comment` is removed, only the bare, unquoted,
    lower-case token `true` enables reporting. A missing block, a missing key, an empty
    value, a quoted `"true"`, `True`, and any other value all mean OFF. This matches the
    `workers.roster` wording. The default is fail-closed because this is a privacy switch.
  - `repo`: must be 2 or 3 `/`-separated parts, each non-empty and matching
    `[A-Za-z0-9._-]+`. Two parts mean `OWNER/REPO` on `github.com`. Three parts mean
    `HOST/OWNER/REPO`. A missing or empty value resolves to the shipped default. Anything
    else is malformed and turns reporting OFF: a scheme (`https://`), a leading or trailing
    `/`, an empty part, four or more parts, or any other character. The consumer never
    guesses a repo.
  - `max_per_session`: a non-negative integer (`[0-9]+`). `0` means nothing is filed
    upstream in that session. A missing value, and any value that is not a non-negative
    integer (negatives included), resolves to `3`.
- **Umbrella children (resolves the brief's open question, ADR-0004).** A child's
  `harness.config.yaml` is in the **standalone** (program-read) tier, so a child's
  **own** `feedback:` block governs sessions rooted in that child. A child does not
  inherit from the coordinator's block, and the coordinator does not override it. The same
  rule applies to the coordinator: its own block governs sessions rooted at the umbrella.
  The cascade seeds each target's block separately and prints each target's notice, so the
  operator is told once per repo that can report. The local fallback directory (F02's
  `progress/feedback/`) is the `progress/feedback/` directory **under the governing harness
  dir**. That is `<child>/.harness/progress/feedback/` for a child, `.harness/progress/feedback/`
  for any installed target, and `progress/feedback/` in the harness source repo. It is never
  the umbrella's directory. Reason: a child entered on its own (CI, a lone clone, a
  reviewer's checkout) must still resolve both the switch and the fallback, and
  `progress/` is always a local, never-stubbed project workspace.
- **Where the notice prints (resolves the brief's second open question).** The notice
  prints on the installer's **stdout**, inside the install output of the target whose
  config was just seeded. It is one line per seeded target, and the cascade adds no summary
  of its own. A run that seeds nothing prints no notice.
- **Source repo.** This repo's root `harness.config.yaml` **is** the seed template (see
  `progress/lessons.md`, 2026-09-05), so the source repo gets the block because it is
  written there directly, with the shipped default. `--self` never writes
  `harness.config.yaml`. Its temporary consumer install is discarded, so it prints no
  notice. *Deviation from the brief:* the brief says the source repo gets the block "via
  `--self`". That can't happen, because `--self` never touches the config, so the direct
  write replaces it. As a result, the source repo carries `enabled: true` and its `repo`
  points at itself. This is intended, since the harness's own sessions are real harness
  users. Whether a source-repo session should file at all is left to E32-F03, which owns
  when reporting fires.

## Architecture alignment

`specs/architecture.md` is **absent** in this repo; the ADR set is present and cited below.

- ADR-0004 — Umbrella resolved body via pointer stubs: `harness.config.yaml` stays in the
  standalone (full local copy) tier, so each child's own `feedback:` block governs and the
  fallback path resolves under the child's own harness dir; nothing about the block is
  stubbed or read from the umbrella (R8, R10).
- ADR-0005 and ADR-0006 are not touched: this feature emits no source-only surface and
  defines no report body or marker.

## Acceptance criteria (EARS)

- **R1** — The shipped seed template `harness.config.yaml` shall carry exactly one top-level
  `feedback:` block whose keys are `enabled: true`, `repo: github.com/araozmd/harness-sdd`
  and `max_per_session: 3`, placed as the file's final block (after `workers:`).
- **R2** — When the installer seeds a fresh target (no `.harness/harness.config.yaml`
  exists), the target's config shall carry the `feedback:` block with the three R1 values.
- **R3** — When the installer upgrades a target whose preserved config has no top-level
  `feedback:` header, the installer shall append a `feedback:` block that is both
  mapping-equal and byte-identical (comment header included) to the block a fresh install
  seeds.
- **R4** — If the preserved config already has a column-0 line starting `feedback:` (block
  style with or without a trailing `# comment`, or the one-line flow form), then the installer shall leave every line of
  that config's `feedback:` section unchanged and shall not append a second `feedback:`
  header, on this run and every later run.
- **R5** — When the installer seeds the `feedback:` block, by either the fresh-install path
  or the upgrade path, it shall print on stdout exactly one line that contains the resolved
  `feedback.repo` value, the literal `feedback.enabled: false`, and the path of the config
  file it seeded.
- **R6** — If the target's config already had a column-0 line starting `feedback:` before the run,
  then the installer shall print no feedback notice line for that target.
- **R7** — While running in `--self` mode, the installer shall print no feedback notice line
  and shall leave the source repo's `harness.config.yaml` byte-identical.
- **R8** — When an umbrella cascade installs a coordinator and its children, the installer
  shall seed a `feedback:` block into each target's own `.harness/harness.config.yaml` that
  lacked one, and shall print one notice line per seeded target naming that target's config
  path.
- **R9** — `docs/INSTALL.md` shall document, in a dedicated `feedback:` section, the
  shipped defaults, the notice, and the resolution contract: only the bare token `true`
  enables; the `[HOST/]OWNER/REPO` grammar (2 or 3 parts of `[A-Za-z0-9._-]+`, an omitted
  host meaning `github.com`, anything else malformed ⇒ OFF); the `max_per_session`
  semantics (non-negative integer, `0` files nothing upstream, anything else resolves to
  `3`); and that the opt-out is `feedback.enabled: false` because a deleted
  block is re-seeded on upgrade.
- **R10** — `docs/INSTALL.md` and `docs/CONFIG-LAYERING.md` shall each state that a child's
  own `harness.config.yaml` `feedback:` block governs sessions rooted in that child (no
  inheritance from the coordinator), and `docs/INSTALL.md` shall state that the local
  fallback directory is `progress/feedback/` under the governing harness dir.
- **R11** — The change shall bump `VERSION` by one MINOR step from `0.84.4` to `0.85.0`,
  and shall add a `CHANGELOG.md` `## [0.85.0]` entry that names the `feedback:` block, its
  default-on `enabled: true`, the default `repo`, the one-line install notice, and the
  `feedback.enabled: false` opt-out.

## Out of scope

- The reporter tool, redaction, the body marker, duplicate search, cap enforcement, and
  writing to the fallback directory (all E32-F02). F02 also decides whether
  `progress/feedback/` is gitignored.
- The reporting rule, the triggers, and `/sdd-report` (E32-F03).
- An interactive install-time prompt or a `--feedback=` flag. The switch is changed by
  editing the config value.
- Inheriting or overriding `feedback.*` from the coordinator in an umbrella (decided
  against above).
- Converting an operator's existing `feedback:` block, or filling in its missing keys.

## Open questions

- None blocking. Both open questions in the brief are resolved above: umbrella-child
  resolution and fallback location, and where the notice prints.
