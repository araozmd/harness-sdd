# `feedback:` config block + opt-out notice — Technical Plan

> Every decision below cites the R-id(s) it serves. The Builder picks the internals that
> are not pinned here.

## Stack & dependencies
- POSIX `sh` plus `grep`/`awk`/`sed`, the same toolset `migrate_config` already uses. Test
  suites must run under dash (see `tests/dash-allowlist.txt` and the lessons on bashisms).
- New dependencies: none.

## Data model — the `feedback:` block  (serves: R1, R2, R3)

The block is appended as the **last** block of the seed template `harness.config.yaml`,
after `workers:`. The comment header's first line is the stable anchor
`# Harness feedback (E32-F01)`. That line is the anchor tests use to extract the block.

| Key | Type | Shipped value | Resolution when missing/invalid (contract, R9) |
|---|---|---|---|
| `feedback.enabled` | bool | `true` | comment stripped, only the bare token `true` enables; quoted/other-case/anything else is OFF |
| `feedback.repo` | string `[HOST/]OWNER/REPO` | `github.com/araozmd/harness-sdd` | 2 or 3 parts of `[A-Za-z0-9._-]+` (2 ⇒ host `github.com`); missing/empty ⇒ shipped default; anything else (scheme, stray `/`, empty part, 4+ parts) ⇒ OFF |
| `feedback.max_per_session` | non-negative int `[0-9]+` | `3` | missing, negative, or any non-`[0-9]+` value ⇒ `3`; `0` ⇒ nothing filed upstream |

The comment header should be short, 10 to 15 lines. It should say: default ON, and what
reporting sends (allow-listed harness fields only, see E32); the opt-out is
`enabled: false`, and deleting the block does not opt out because the next upgrade
re-seeds it; the repo grammar and why the default is host-qualified; the cap; and that
the child's own block governs in an umbrella. Keep the header free of interior blank
lines, because the block extractors bound on the first blank line (lessons 2026-09-16).

## Installer changes  (serves: R2–R8)

1. **`migrate_config` (harness-install.sh, the table of top-level blocks near the `workers:`
   entry)** — add a `feedback` entry **after** the `workers:` entry. Use the same
   shape, but with a **wider** presence check than its siblings:
   `if ! grep -Eq '^feedback:([[:space:]]|$)' "$_cfg"; then cat >> "$_cfg" <<'EOF' … EOF; fi`.
   This check also matches the one-line flow form `feedback: { enabled: false }`. The
   narrow sibling pattern would miss that form, append a second `enabled: true` block, and
   many YAML parsers keep the last duplicate key, so the operator's opt-out would silently
   flip ON. Use the same pattern for the §2 before/after probe (R4, R6).
   The heredoc must be **byte-identical** to the seed template's block, blank separator
   line and comment header included. The ordering matters too: the tail-anchored `prl_block`
   extractor in `tests/test_installer_toggles.sh` / `tests/test_pr_loop.sh` captures
   everything from `# Codex PR review loop` to EOF. A stripped-and-migrated config
   re-appends pr_loop → change_size → escalation → workers → feedback, so the heredoc
   order must match the template's order (R3, R4).
2. **Detect "seeded this run" in §2 of `install_one`** (the seed/preserve stage, around
   `harness-install.sh:3800`). The fresh branch (`cp` + `seed_pr_loop_optin`) always seeds
   the block. On the preserve branch, record `grep -Eq '^feedback:([[:space:]]|$)'` **before**
   `migrate_config` runs. The block was seeded this run only when that probe missed and the
   header exists afterwards. `migrate_config` stays a pure file transform and prints
   nothing. That keeps its many existing callers and tests unchanged (R5, R6).
3. **Notice** — for a seeded target and outside `SELF_MODE`, print one line on stdout via
   `info` (stdout, never stderr). Read the repo value back from the file with a new reader,
   `_cfg_feedback_value <file> <key>`. Model it on `_cfg_pr_loop_value`: top-level section
   only, trailing comment stripped. Canonical text:

   `feedback: harness defects may be auto-reported as issues on <repo> — to opt out set feedback.enabled: false in <config-path>`

   `<config-path>` is `$H/harness.config.yaml`, the target's harness dir. Tests pin the
   tokens R5 names, not the exact wording (R5).
4. **`--self`** — guard the notice with `[ "${SELF_MODE:-0}" != 1 ]`. `self_install`
   already never writes `$SRC/harness.config.yaml`. R7 pins that this stays true (R7).
5. **Cascade** — no cascade-specific code. Each `install_one` (coordinator plus each child)
   runs §2 separately, so R8 follows from 2 and 3. Do **not** add a cascade summary line.

## Approach notes
- **Existing suites that may shift.** The tail-anchored `prl_block` now also covers the
  feedback block. That is intended and stays green only if template and heredoc are
  byte-identical and in the same order. Search the tests for anything that assumes
  `workers:` is the last block or counts top-level keys, and fix those assertions to the
  new tail (not by removing coverage).
- **VERSION literal sweep.** Before trusting a green run, grep the tests for `0.84.4` as a
  bare literal (lesson 2026-09-16 on `test_codex_native.sh`).
- **Extractor for tests.** Bound the block structurally: anchor `# Harness feedback
  (E32-F01)` through EOF (it is the last block). Add a length floor and a semantic
  `key=value` comparison next to `cmp`, as `test_workers_block_seeded_migrated_converge`
  does. Copy that test's shape. `require_same_mapping` and `require_no_interior_blank` are
  local to `tests/test_install.sh` (lines ~93/116) — copy them into the new suite; `tests/lib/`
  holds no shell helpers to source. For the cascade fixture, `build_umbrella` in
  `tests/test_cascade.sh` is the shape to copy.
- Capture stdout alone (`2>/dev/null`) for every notice assertion (lesson: "exactly one
  line ON STDOUT").
- Use a neutral, disk-backed `TMPDIR` outside any git work tree for the cascade fixture.
