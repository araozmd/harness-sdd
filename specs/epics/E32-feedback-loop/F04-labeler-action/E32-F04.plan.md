# Source-repo GitHub Action that labels marker-carrying issues — Technical Plan

> Translates the `.spec.md` intent into design. Every decision below cites the R-id(s) it
> serves. The Builder picks the internals that are not pinned here.

## Stack & dependencies
- One GitHub Actions workflow (YAML) plus one **POSIX `sh`** script, like the rest of the
  harness's shell surfaces. The suite runs under dash (`tools/run-tests.sh`).
- No new runtime dependency. `gh` is preinstalled on `ubuntu-latest`; the script is also
  driveable from tests with a stubbed `gh` on `PATH`.
- `actions/checkout` (the only action) pinned by full commit SHA (R3); Dependabot already
  tracks `github-actions` weekly (`.github/dependabot.yml`). The suite asserts the 40-hex
  form, not a specific SHA — pinning *which* SHA is a review-time decision recorded in a
  trailing comment beside the `uses:` line.

## Workflow — `.github/workflows/harness-feedback-labeler.yml`  (serves: R1, R2, R3)

The `on:` and `permissions:` blocks are pinned **exactly** (after dropping blank and comment
lines); the suite asserts full-string equality, which is a stronger, live predicate than a
"does not contain `edited`" negative.

```yaml
name: harness-feedback labeler

on:
  issues:
    types: [opened]

permissions:
  issues: write
  contents: read

jobs:
  label:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<40-hex SHA of a released v4 tag>  # v4.x.y — kept current by Dependabot
      - name: Label marker-carrying issue
        env:
          GH_TOKEN: ${{ github.token }}
          GH_REPO: ${{ github.repository }}
          ISSUE_NUMBER: ${{ github.event.issue.number }}
        run: sh .github/scripts/feedback-labeler.sh label-issue "$ISSUE_NUMBER"
```

- **Why `.number` and not the body (R2).** `github.event.issue.number` is an integer and
  `github.repository` is the repo itself; neither is issue-controlled text. The body is fetched
  by the script through the API and never appears in a `${{ }}` expression or a `run:` line.
  `run:` references only `$ISSUE_NUMBER` — an env var, quoted, never interpolated.
- **Why `contents: read` (R3).** `actions/checkout` needs it under explicit `permissions:`;
  without it checkout fails. No other permission is requested.
- **`opened` only (R1).** No `edited`, no `reopened`, no `workflow_dispatch`. An edit cannot
  reclassify an issue.

## Script — `.github/scripts/feedback-labeler.sh`  (serves: R4–R9, R11)

Two modes; both read `GH_REPO` from the environment, `label-issue` also needs `GH_TOKEN`.

```
feedback-labeler.sh parse <body-file>
    → prints the label set, one name per line, in the fixed order
      `harness-feedback` then the category label; prints nothing when the body is not a
      report. Exit 0 in every case. No GitHub access.

feedback-labeler.sh label-issue <issue-number>
    → reads the issue body into a temp file from the `opened`-event snapshot when an event
      payload is present, falling back to a GitHub API fetch only when it is not; then (if the
      marker is valid) ensures the labels exist and adds them. Exit 0 when it labels or
      deliberately no-ops; non-zero only when a required read or `gh` operation fails, so the
      failure surfaces in the Actions log. Never posts a comment.
```

### Strict marker parse  (serves: R4, R5, R7)

Grammar — **copied verbatim from `E32-F02.spec.md` R1 / `E32-F02.plan.md`**, which is the
authority (ADR-0006). Do not re-derive it; cite it in a comment.

```
^<!-- harness-feedback:v1 host=[A-Za-z0-9._-]+ version=[0-9]+\.[0-9]+\.[0-9]+ trigger=(harness-malfunction|contradictory-instruction|workaround|missing-capability) -->$
```

Algorithm (the Builder may choose a POSIX `sed`/`awk`/`case` implementation, but must keep
these properties):

1. Read the body file. Take the **first line** (`sed -n '1p'`). Match it with the anchored ERE
   above; a non-match is "not a report".
2. Require that **no line after the first** contains the substring `harness-feedback:`. The
   anchored first-line match already excludes extra content on line 1, so this makes "exactly
   one marker" total. (A `grep -c` over the whole file is not enough by itself and a
   line-oriented charset guard is a known trap — E32-F02 F5. Extract, then compare whole
   strings.)
3. Extract `trigger` from the validated first line (e.g. a `case "$first" in
   *" trigger=<value> -->")` arm, or a `sed` capture) and map it with the table below. The
   line already matched the full grammar, so the capture is trust-on-validated-input.
4. Never source, `eval`, `sh -c`, or shell-expand the body or any line of it.

### Label mapping  (serves: R6, R8)

| trigger (from the marker) | category label | always |
|---|---|---|
| `missing-capability` | `enhancement` | `harness-feedback` |
| `harness-malfunction` | `bug` | `harness-feedback` |
| `contradictory-instruction` | `bug` | `harness-feedback` |
| `workaround` | `bug` | `harness-feedback` |

Fixed values used **only when creating** a missing label (R8); an existing label is never
updated:

| label | color | description |
|---|---|---|
| `harness-feedback` | `5319e7` | `Machine-reported harness feedback (E32)` |
| `bug` | `d73a4a` | `Something isn't working` |
| `enhancement` | `a2eeef` | `New feature or request` |

### Fetch + apply  (serves: R2, R8, R9)

The `gh issue edit` and `gh label create` calls pass `--repo "$GH_REPO"` explicitly so a stub
(and CI) sees the target; the two `gh api` calls carry the repo in the request path
(`repos/$GH_REPO/...`) — `gh api` has no `--repo` flag.

1. Validate the issue number against `^[0-9]+$`; a malformed argument is a loud non-zero exit
   (it can only be a workflow bug, never issue text).
2. Read the body into a temp file, never into a shell word, preferring the `opened`-event
   snapshot so a later edit cannot reclassify the issue (R1's intent):
   - when `GITHUB_EVENT_PATH` is set and readable,
     `jq -r '.issue.body // ""' "$GITHUB_EVENT_PATH" > "$body_file"`;
   - otherwise fall back to `gh api "repos/$GH_REPO/issues/<n>" --jq .body > "$body_file"` for
     a local run with no event payload.

   In both arms the body is redirected to a file; it never enters an argv or a `${{ }}`.
3. Run the parse algorithm on the file. Empty label set ⇒ remove the temp file, exit 0, and
   make **no** `gh issue edit`, `gh label create`, or `gh issue comment` call (R5).
4. For each label in the set, probe existence **and distinguish "absent" from "error"**. Only a
   definitive `404 Not Found` means absent and leads to creation; any other failure (401/403,
   5xx, network, empty response) aborts with a loud non-zero exit, matching R9's "a label
   mutation fails → exit non-zero" and keeping the create-only-the-absent predicate honest.
   `gh api` exits non-zero for every error, so it cannot make that distinction alone — the
   Builder picks one of:
   - read the HTTP status line from `gh api --include "repos/$GH_REPO/labels/<name>"`
     (`200` ⇒ present, `404` ⇒ absent, anything else ⇒ abort), or
   - list and exact-match instead: `gh label list --repo "$GH_REPO" --search "<name>"
     --json name` and require an exact `"name"` match for "present" (an empty list is
     definitive absent; a non-zero `gh` exit is an abort).

   On a definitive absent, create with
   `gh label create "<name>" --repo "$GH_REPO" --color "<hex>" --description "<text>"`.
   The probe's expected non-zero/empty branch is guarded with `if`, never a bare `&&`.
5. Add the set in one call: `gh issue edit "<n>" --repo "$GH_REPO" --add-label "<l1>,<l2>"`.
6. No comment path exists anywhere in the script (R9).

## Approach notes

- **Exactness over negatives (R1, R2, R3).** The suite pins `on:`/`permissions:` as whole
  extracted blocks (blank/comment lines dropped) and asserts the only `github.event.issue.*`
  token in the workflow is `.number` via `sort -u` equality. Each negative carries a positive
  control on its own shape (the block extracts non-empty; the file does contain a `uses:` line,
  `${{`, and at least one `github.event` reference), per the dead-two-stage-negative lesson.
- **Test the script, not GitHub.** The suite stubs `gh` on `PATH`, recording argv one token per
  line, and drives the body read by both arms: a fixture JSON event payload with
  `GITHUB_EVENT_PATH` set (asserting no issue-refetch is attempted), and `GITHUB_EVENT_PATH`
  unset with `gh api .../issues/N --jq .body` serving a fixture body. The label probe is stubbed
  to yield a definitive present (HTTP 200 / an exact `label list` hit), a definitive absent
  (404 / an empty list), or a hard error (500 / non-zero), so create-vs-existing-vs-abort is
  distinguishable; `label create` and `issue edit` are recorded. No network.
- **Fixture bodies live in the suite's `mktemp` tree, never `tests/fixtures/`.** Every valid,
  malformed, and injection body is written under the suite's `mktemp -d` at run time (F02's
  `tests/test_feedback_report.sh` precedent); nothing is committed under the frozen
  `tests/fixtures/**` tree.
- **Injection fixtures prove non-execution with a canary.** A fixture body containing
  `$(touch "$CANARY")`, backticks, `;`, and `${{ }}` must leave the canary absent, while a
  positive control asserts the canary string is present in the fixture file (so the search for
  it is not dead). Also assert the label set is still exactly the first-line marker's set.
- **Dash-clean, `set -eu` safe.** Never `source` or `eval` the body. Guard `gh` probes with
  `if`, never a bare `[ … ] &&`, and put `|| true` on any assignment whose RHS command can
  legitimately find nothing (lessons 2026-09-16/17). Use `${GH_REPO:?}` / `${GH_TOKEN:?}`.
- **Executable bit + declaration.** `.github/scripts/feedback-labeler.sh` is a tracked `*.sh`
  outside `tests/`, so the repo's executable-bit rule (E99-F164) covers it: commit it `+x`,
  assert both the worktree bit and the tracked `100755`, **and** append its path to
  `_sse_expected` in `tests/test_install.sh` — that suite equality-checks the derived set, so an
  undeclared new script reds with "undeclared script(s)".
- **No VERSION/CHANGELOG pin to sync.** Because there is no bump, there is no current-version
  literal to sweep. Do not add one.
- **Reviewer residual (record, do not paper over).** The suite cannot prove *which* action SHA
  is trusted; it proves the shape is a 40-hex SHA. That choice stays a review-time decision.
