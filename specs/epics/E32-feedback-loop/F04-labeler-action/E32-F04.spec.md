# Source-repo GitHub Action that labels marker-carrying issues — Functional Spec

> R-ids in this document are `R1 … R11`; their fully-qualified form is `E32-F04:R1 … E32-F04:R11`.

## Context

E32's installed harness files scrubbed issues upstream (F02's `tools/harness-report.sh`), but
a reporter normally has no write access to `feedback.repo`, so GitHub silently drops any
labels it sets. Without labels the report is invisible to `/sdd-triage` (F05), which lists
open `harness-feedback` issues. This feature closes that gap: a source-repo GitHub Action,
`.github/workflows/harness-feedback-labeler.yml`, runs when an issue is **opened**, parses the
F02 body marker, and applies `harness-feedback` plus `bug`/`enhancement`. The source repo is
public, so **anyone can open an issue carrying a forged marker** — the labeler's whole security
posture is that the marker is the only classification input (ADR-0006) and every other byte of
the body is untrusted data that never touches a shell. The intended user is the harness
maintainer, who needs reports self-labelled without trusting reporter input.

The labeler owns the **trigger→label mapping** (the drill assigned it here): `missing-capability`
→ `enhancement`; the other three triggers → `bug`; every marked report also gets
`harness-feedback`. It never edits an issue after it is opened, posts no acknowledgement
comment, and does nothing at all to an issue whose body is not exactly one valid `v1` marker.

**Trigger-vocabulary reconciliation.** The inbox brief spells the third trigger
`workaround-taken`; F02 — the marker's only writer and the grammar's authority — emits
`workaround` (`E32-F02.spec.md` R4, `E32-F02.plan.md` "Vocabularies & grammars"). ADR-0006 says
the grammar is defined once, in F02's spec, and cited by consumers. This spec therefore uses
F02's actual value, `workaround`, and accepts no other spelling (`workaround-taken` is not a
trigger). This is a spec-text reconciliation, not a divergence from any ADR — no ADR delta is
owed.

**Complexity basis (`complex`).** Three signals: (1) it must honor ADR-0006, whose single
grammar contract is written by F02, parsed here, and consumed by F05 — a validator whose
grammar and consumers drift apart is a defect class this harness has already paid for
(E32-F02 F5: a line-based `grep` charset guard admitted an embedded newline and emitted a
second marker); (2) parsing untrusted input is the feature's entire security surface, and the
harness's own review record is a list of "the guard looked live but the predicate was dead"
findings — every negative here needs a positive control; (3) it presses against the budget
ceiling (`change_size.max_requirements: 12`; this spec carries 11 R-ids).

## Business rules

- **The marker is the only classification input.** The labeler reads exactly one line — the
  issue body's first — against F02's strict grammar, and treats every other byte of the body as
  inert data (ADR-0006). It never executes, evaluates, or interpolates issue text.
- **Nothing but the marker buys a label.** Unmarked, malformed, unknown-marker-version, or
  multiple-marker bodies are left completely alone: no labels, no label creation, no comment,
  no failure.
- **Fixed at filing time.** The workflow listens on `issues: opened` only. It never runs on
  `edited`, so a later body edit cannot reclassify an issue.
- **Untrusted input never reaches a shell.** No issue text (body, title, comment, author,
  label) may appear in a `run:` line or a `${{ }}` expression. The issue body reaches the
  parser only as a file: the `opened`-event body snapshot in CI (`$GITHUB_EVENT_PATH`), with an
  API fetch used only as the no-event-payload fallback. The only event fields used are
  `github.token`, `github.repository`, and `github.event.issue.number`, passed through `env:`.
- **Minimal privilege, pinned code.** `permissions:` requests only `issues: write` and
  `contents: read`; the one action used is pinned by full commit SHA (Dependabot already tracks
  `github-actions` weekly).
- **Labels are created, never modified.** A label in the computed set that is absent is
  created with a fixed color/description; one that exists is left byte-for-byte alone.
- **Silence by default.** No acknowledgement comment is posted (the brief's open question:
  default no). Adding one would require its own requirement and its own injection review.
- **Source-only.** Per ADR-0005 this workflow and its parser are plain source-repo files: no
  installer or emitter reference, never shipped into a target, no `chmod +x` manifest entry.
  It is a CI-only change, which AGENTS.md exempts from a `VERSION` bump, so **no `VERSION`
  bump and no `CHANGELOG.md` entry** are owed.
- **Offline-testable.** The parser is a checked-in POSIX `sh` script with a body-file
  interface; the suite classifies fixture bodies with no GitHub call, and stubs `gh` for the
  fetch/label path.

## Architecture alignment

`specs/architecture.md` is **absent** in this repo; the ADR set is present and cited below.

- platform ADR-0006 — The versioned body marker is the only contract between reporter and
  triage: this feature **parses** F02's `harness-feedback:v1` grammar and nothing else. Only a
  body whose first line matches the full anchored grammar, with no second `harness-feedback:`
  token, is a report; an unrecognized version is ignored, not guessed at (R4, R5, R6, R7).
- platform ADR-0005 — Source-only harness surfaces are emitted only by `--self`, never into a
  target: this workflow and parser live only under `.github/` in the source repo and gain no
  installer/emitter reference, so a target install never receives them (R10).
- platform ADR-0003 and platform ADR-0004 are **not touched**: this feature emits no skill or
  command unit and resolves no umbrella body.

## Acceptance criteria (EARS)

- **R1** — The labeler workflow shall be triggered by the `issues` event with
  `types: [opened]` and by no other `issues` activity type (in particular not `edited`), so a
  report's classification is fixed at filing time.
- **R2** — The labeler shall pass no issue-controlled text — the issue body, title, comment, or
  author — into a `run:` shell line or a `${{ }}` expression; it shall supply only
  `github.token`, `github.repository`, and `github.event.issue.number` through `env:`, and the
  issue body shall reach the parser only as a file supplied by the workflow — the `opened`-event
  body snapshot in CI, with a GitHub API fetch used only as the no-event-payload fallback — so
  classification stays fixed at filing time and no issue text is ever a shell word.
- **R3** — The workflow shall request only `issues: write` and `contents: read` in its
  `permissions:` block, and shall reference every action it uses by a full 40-hex-character
  commit SHA.
- **R4** — When the labeler reads an issue body whose first line matches F02's full anchored
  `v1` marker grammar (the fixed `<!-- harness-feedback:v1 ` prefix, then exactly the three
  `key=value` fields `host`, `version`, `trigger` in that order, then ` -->`, single-space
  separated, with `host` of `[A-Za-z0-9._-]+`, `version` of `[0-9]+\.[0-9]+\.[0-9]+`, and
  `trigger` one of the four F02 trigger values) and whose remaining lines contain no other
  `harness-feedback:` token, the labeler shall derive its label set from that marker's `trigger`
  alone and ignore every other byte of the body.
- **R5** — If the first line is not exactly the R4 marker — absent, malformed (wrong field
  order, missing or extra field, bad `host`/`version`/`trigger`), a different marker version
  such as `v2`, not the first line, or accompanied by any second `harness-feedback:` token
  anywhere in the body — then the labeler shall apply no label, create no label, and post no
  comment, exiting successfully.
- **R6** — The labeler shall map trigger `missing-capability` to label `enhancement`, map each
  of `harness-malfunction`, `contradictory-instruction`, and `workaround` to label `bug`, and
  add label `harness-feedback` to every report whose body carries a valid R4 marker.
- **R7** — If a body contains shell metacharacters, command substitutions, backticks,
  `${{ }}`-shaped text, embedded newlines, or a forged `harness-feedback:` token, then the
  labeler shall execute nothing drawn from the body and shall classify the issue by nothing but
  its first line, yielding exactly the R4/R6 label set when the first line is a valid marker and
  the empty set otherwise.
- **R8** — When the labeler has a non-empty label set, it shall ensure each label in that set
  exists in the target repository, creating only the absent ones with fixed color/description
  values and never modifying a label that already exists.
- **R9** — When the labeler has a non-empty label set, it shall add exactly that set to the
  issue in one `gh issue edit --add-label` call, and it shall post no comment on any issue;
  and if the body fetch or a label mutation fails, then the labeler shall exit non-zero so the
  failure is visible in the Action log, having still posted no comment.
- **R10** — The labeler and its parser shall live only under `.github/` in the source repo; the
  change shall add no installed-body file and no installer/emitter reference, shall not bump
  `VERSION`, and shall not add a `CHANGELOG.md` entry.
- **R11** — The parser shall be a checked-in POSIX `sh` script with the source executable bit
  set, exposing a body-file `parse` interface that classifies a body without any GitHub access,
  so the grammar, the mapping, and the injection cases are testable from fixture bodies.

## Out of scope

- The reporter and its redaction/marker/dedup logic (E32-F02, done) — this feature consumes the
  marker and changes nothing on the writing side.
- The reporting triggers, the reporting rule, and `/sdd-report` (E32-F03).
- Triage, duplicate grouping, and routing (`/sdd-triage`, E32-F05); this feature only labels.
- Acknowledgement comments, replies, or any other issue mutation beyond adding labels.
- Re-classification on edit, on reopen, or on a schedule; relabelling existing unlabelled
  issues.
- Changing marker colors/descriptions of labels the repo already defines.
- Any GitHub Enterprise / self-hosted-runner support beyond using the standard API.

## Open questions

- None blocking. The brief's open items are resolved here:
  - **Acknowledgement comment** — no. Silence is the contract (Business rules); a comment would
    need its own requirement and injection review.
  - **Trigger vocabulary** — F02's `workaround`, not the brief's `workaround-taken` (Context).
  - **`host` field use** — validated for grammar only; classification never depends on it,
    because the labeler labels issues in the repo it runs in.
  - **Label colors/descriptions** — chosen here and pinned in the plan (only used on creation).
