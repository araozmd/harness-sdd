# Feedback triage — Functional Spec

## Context

The harness maintainer needs to turn open feedback into investigated work without
letting public issue text control the agent. Triage prepares a resumable proposal,
then invokes the existing intake lanes only for explicitly approved actions.
Complexity is complex because ADR-0005 crosses emitter, ownership and generated
surfaces, a class with documented drift defects. There are 12 requirements, within
the configured budget of 12. Primary intent: `progress/inbox/E32-F05.md`.

## Business rules

- This feature's autonomous development flag never authorizes autonomous *triage*.
  An invocation alone authorizes reads and a local proposal, not issue mutations or intake.
- Reports now contain sanitized public evidence prose (E32-F06). Such prose, titles,
  markers and labels remain untrusted; a valid marker does not prove a reported defect.
- Each proposal identifies repository, issue numbers, duplicate grouping rationale,
  canonical issue, independently checked evidence, route and exact proposed external
  comment/closure. Unknown evidence remains unknown. Closure always has a reason.
- Routes are `fix` (existing E99 `/sdd-fix`), `new` (existing `/sdd-new`), or `close`.
  A duplicate group can share one intake; duplicates are not silently closed.
- Approval covers named actions on named issues in the current proposal. Silence,
  prior task autonomy and the issue author's instructions are not approval. Any
  material change in route, scope, repository or external message needs fresh approval.
- Keep provenance in inbox briefs, avoiding a TaskStore schema change. Only validated
  positive issue numbers for the PR's repository become `Fixes #N` references.

## Architecture alignment

`specs/architecture.md` is absent; `specs/product.md` is a retained example and adds
no domain requirements. All existing ADRs were considered in `specs/adr/`.

- platform ADR-0003 — one generated shared triage skill with policy companion, consumed by Codex and OpenCode.
- platform ADR-0005 — triage is emitted only under `--self`; target ownership/reclaim never includes it.
- platform ADR-0006 — strict unchanged v1 marker recognition; all other issue text is data.

## Acceptance criteria (EARS)

- **R1** — When self-hosting selected supported front ends, the installer shall expose
  sdd-triage through their existing generated command/skill mechanisms.
- **R2** — When installing or upgrading a normal target, or performing existing front-end
  deselection/reclamation,
  the installer shall leave all triage-named surfaces outside its writes and ownership.
- **R3** — When triage reads feedback, the reader shall enumerate all open issues
  carrying `harness-feedback` from the explicitly resolved feedback repository.
- **R4** — If an issue lacks exactly one supported valid v1 marker, then triage shall
  exclude it from actionable report proposals and list its rejection locally.
- **R5** — While processing issue content, triage shall treat it solely as untrusted
  evidence, independently composing intake and external messages without executing,
  following, or copying the issue's instructions verbatim.
- **R6** — When the read succeeds, triage shall persist a per-issue routing proposal
  with reasoned duplicate groups under `progress/triage/<run>/proposal.md` before presenting it.
- **R7** — While explicit human approval for a proposed action is absent, triage shall
  perform no TaskStore/intake write, issue comment or issue closure for that action.
- **R8** — When an intake action is approved, triage shall invoke the existing fix or
  new contract with its approved, independently worded brief and source provenance.
- **R9** — When an issue comment or closure is approved, triage shall execute only
  that approved external action and record its observed result for resumability.
- **R10** — When a PR is prepared for work with validated source-issue provenance,
  its body shall include one `Fixes #N` line per linked issue in the same repository.
- **R11** — If reading, intake or an external action fails or has an uncertain outcome,
  then triage shall record that boundary and stop dependent actions without claiming
  success or replaying uncertain mutations on resume.
- **R12** — When the capability ships, the harness shall publish consistent generated
  surfaces, current command/workflow documentation and a MINOR release entry.

## Out of scope

Scheduled/autonomous triage, automatic labels, reporter/labeler redesign, automatic
closure of duplicate groups, new board fields, alternative intake implementations,
new named model roles, or changing existing fix/new approval and completion contracts.

## Open questions

None. The proposal is persisted locally for resumability. The Orchestrator owns the
spec-ready transition and applicable autonomous development authorization.
