# `tools/harness-report.sh` — Technical Plan

> Translates the `.spec.md` intent into design. Every decision below cites the R-id(s) it
> serves. The Builder picks the internals that are not pinned here.

## Stack & dependencies
- POSIX `sh`, like the rest of `tools/`. Test suites run under dash
  (`tools/run-tests.sh` picks the strictest probeable shell; `tests/dash-allowlist.txt`).
- No new runtime dependency. `gh` is required only for the upstream path; its absence is a
  handled outcome (R11). `python3` is already required by `init.sh` and may be used for JSON
  parsing, but a pure-`sh` parse of the stub's output is acceptable if it stays dash-clean.
- Tests stub `gh` on `PATH`; no test touches the real GitHub API.

## Interface (`tools/harness-report.sh`)  (serves: R1–R11)

```
harness-report.sh \
  --trigger   <harness-malfunction|contradictory-instruction|workaround|missing-capability> \
  --symptom   <one of the nine fixed symptom codes> \
  [--file     <harness-relative-path>]... \
  [--command  <name>]       # harness command name (R4): tools/ body basename,
                            # init.sh, harness-install.sh, or a shipped sdd-* unit
  [--exit-code <n>]         # [0-9]{1,3}
  [--role     <role>]       # enumerated below
  [--phase    <phase>]      # enumerated below
  [--session-id <token>]    # [A-Za-z0-9._-]{1,64}; env HARNESS_FEEDBACK_SESSION_ID also read
  [--notes-file <path>]     # free-form text; LOCAL COPY ONLY

harness-report.sh redact          # reads stdin, writes the redacted body to stdout (R8)
```

- The tool has **no non-zero exit path**: a missing `--trigger`/`--symptom` or any
  out-of-allow-list value is treated like a rejected field — no upstream issue, the local
  report written (R11), exit 0 (R4). `redact` exits 0. No invocation of a report the caller
  asked to file fails the caller's task.
- `--file` may repeat. `--notes-file` supplies the free-form text; its content is never an
  input to the title, body, or search query.

## Vocabularies & grammars  (serves: R1, R4, R6, R10)

| Field | Allow-list |
|---|---|
| trigger | `harness-malfunction`, `contradictory-instruction`, `workaround`, `missing-capability` |
| symptom | `init-failure`, `install-failure`, `tool-failure`, `board-write-failure`, `gate-unsatisfiable`, `instruction-conflict`, `doc-conflict`, `workflow-gap`, `state-corruption` |
| role | `orchestrator`, `architect`, `builder`, `builder-heavy`, `reviewer`, `scout`, `driller`, `fixer`, `planner`, `inception`, `doc-critic`, `pr-fixer` |
| phase | `inception`, `architect`, `builder`, `reviewer`, `scout`, `slice-dispatch`, `handoff`, `install` |
| command | a harness command name: a basename of a regular file under `$H/tools/`, `init.sh`, `harness-install.sh`, or a shipped `sdd-*` command unit (`<root>/.agents/skills/<name>/`, `<root>/.claude/commands/<name>.md`, `<root>/.opencode/command/<name>.md`) |
| exit code | ERE `^[0-9]{1,3}$` |
| session id | ERE `^[A-Za-z0-9._-]{1,64}$` |
| harness file | harness-owned per `tools/harness-owned-paths.sh` (R5) |

- **Role** includes `builder-heavy` because `agents/builder-heavy.md` ships and `complex`
  builds start on that tier (ADR-0002) — excluding it would silently drop a report from
  exactly the tier a hard build runs on.
- **Phase** is the harness's established telemetry phase set
  (`tools/telemetry-report.py:30` / `orchestrator.md`: `inception`, `architect`, `builder`,
  `reviewer`, `scout`, `slice-dispatch`) **plus** `handoff` and `install`, which are added
  because early-stop reporting fires at handoff and an installer-driven session is a real
  reporting point. F03 emits from these names; keep them in sync with F03.
- **Command** is a *semantic* allow-list, not a charset: it must resolve to something the
  installed body actually ships, so a project-specific token cannot ride the field upstream.
  The tool derives the accepted set from `$H/tools/*` (regular files), the two root scripts,
  and the `sdd-*` units present. An unrecognized name is a rejected field (R4), never a
  redaction problem.

An out-of-allow-list value for any supplied field ⇒ **reject**: no upstream issue, local
report written, exit 0 (R4). A missing `--trigger`/`--symptom` takes the same reject path.
There is no usage-error exit code; the tool never exits non-zero.

## The marker grammar — defined here, parsed by F04/F05  (serves: R1)

Exactly one line, the body's first line:

```
<!-- harness-feedback:v1 host=github.com version=0.86.0 trigger=harness-malfunction -->
```

Strict grammar (pin the emitted line to this; F04/F05 parse it with the same allow-list):

```
^<!-- harness-feedback:v1 host=[A-Za-z0-9._-]+ version=[0-9]+\.[0-9]+\.[0-9]+ trigger=(harness-malfunction|contradictory-instruction|workaround|missing-capability) -->$
```

- `v1` is the marker schema version. A change to field order, names, or separators is a new
  marker version (`v2`), per ADR-0006; consumers keep reading `v1` until reporters upgrade.
- `host` is the resolved `feedback.repo` host; `version` is the resolved `VERSION` file
  (trimmed); `trigger` is the accepted trigger.
- **Non-semver `VERSION` guard (R1).** `VERSION` is SemVer by AGENTS.md, so the field's
  `[0-9]+\.[0-9]+\.[0-9]+` grammar normally holds. If the trimmed `VERSION` does not match it,
  the tool must **not** file upstream: it writes a local report (outcome `rejected`, reason
  `version`) instead of emitting a marker its own grammar rejects, which F04/F05 would drop.
- No other `harness-feedback:` marker may appear anywhere in the body (R1).

## The upstream body  (serves: R7)

After the marker, one `Label: value` line per accepted field, in this fixed order, omitting
absent optional fields (a `File:` line repeats once per accepted file):

```
Harness version: <VERSION>
Trigger: <trigger>
Symptom: <symptom>
File: <harness-relative-path>
Command: <command>
Exit code: <n>
Role: <role>
Phase: <phase>
```

No free-form text, no project path, no commentary (R7). The title is:

```
[harness-feedback] <trigger> <symptom-code> in <first accepted harness file>
```

## Data model — local files  (serves: R10, R11)

Governing harness dir `H` = the script's grandparent dir
(`$(CDPATH= cd -- "$(dirname -- "$0")/.." && pwd -P)`) — `.harness/` in an installed target,
the repo root in the harness source. This is the same convention as
`tools/change-size.sh` / `tools/telemetry-report.py`, and it is exactly F01's "governing
harness dir" (R3, R11; ADR-0004).

| Path | Contents | Notes |
|---|---|---|
| `$H/progress/feedback/<UTC timestamp>.md` | header, the accepted structured fields, the free-form notes verbatim, and the outcome (`filed`/`duplicate`/`capped`/`no-session`/`rejected`/`fallback`) | timestamp `date -u +%Y%m%dT%H%M%SZ`; on collision append `-2`, `-3`, … until free (R11) |
| `$H/progress/feedback/.session-count` | one line `<session-id> <created-count>` | keyed by session token; a different token resets the count (R10) |

Both live under `progress/feedback/`, which is already gitignored in both layouts — the
source `.gitignore` has `progress/*/` and the installer seeds `progress/*/` into
`.harness/.gitignore` (E99-F06). **No ignore change is needed** (resolves the F01
out-of-scope note that F02 decides this). The local copy holds free-form text, so this
matters: it must never be committed.

## Config resolution  (serves: R2, R3, R10)

Read `$H/harness.config.yaml` top-level `feedback:` block, applying F01's resolution contract
verbatim (do not re-invent it — `docs/INSTALL.md` → `## Harness feedback` documents it):

- `enabled` — after stripping a trailing `# comment`, only the bare token `true` enables;
  anything else (missing block/key, empty, `"true"`, `True`) ⇒ off (R2).
- `repo` — 2 or 3 `/` parts of `[A-Za-z0-9._-]+`; missing/empty ⇒ shipped default
  `github.com/araozmd/harness-sdd`; malformed ⇒ off (R3).
- `max_per_session` — `[0-9]+`, missing/invalid ⇒ `3`, `0` ⇒ no upstream (R10).

Implementation may copy the reader shape `_cfg_feedback_value` added by F01
(`harness-install.sh`), but the tool must not source the installer; implement a small local
reader (top-level section only, trailing comment stripped).

## Harness-owned file validation  (serves: R5)

1. Normalise each `--file` candidate to a **harness-relative** path
   (`^[A-Za-z0-9._-]+(/[A-Za-z0-9._-]+)*$`); reject absolute paths and any `..` segment.
2. Compute the project-relative form: `pfx=".harness/"` when `H`'s basename is `.harness`,
   else `pfx=""`; project root = `$(dirname "$H")` in the first case, `$H` in the second.
3. Ask the authority: `"$H/tools/harness-owned-paths.sh" body "$H"`, drop the empty
   pathspec line, then
   `git -C "$PROJECT_ROOT" ls-files --cached --others --exclude-standard -z -- <pathspecs>`.
   Accept `"$pfx$cand"` iff it is in that listing.
4. `--others` is deliberate: the tool validates an untracked (freshly written) file too, so
   tests and pre-commit runs work. If the authority or `git` is unavailable, drop the
   candidate (fail-safe: no file accepted ⇒ R5's local-only branch).

In the source layout the authority's first pathspec is empty, so acceptance is "everything
minus the project-owned excludes"; that is the authority's answer and the tool inherits it.

## Redaction pass  (serves: R8)

Run over the assembled upstream body's `Label: value` lines immediately before
`gh issue create` (and as the whole of `redact` mode); the **marker line is left byte-exact**,
because a corpus collision with an allow-listed marker field (the host, say) would break the
sole reporter↔triage contract. Fixed corpus; replace with fixed tokens:

| Shape | Example | Replacement |
|---|---|---|
| GitHub tokens | `ghp_…`, `gho_…`, `ghu_…`, `ghs_…`, `ghr_…`, `github_pat_…` | `[REDACTED-SECRET]` |
| Generic keys | `sk-…`, `AKIA` + 16 upper-alnum | `[REDACTED-SECRET]` |
| Emails | `user@example.com` | `[REDACTED-EMAIL]` |
| Absolute paths | `/home/…`, `/Users/…`, `/tmp/…`, `/private/…` | `[REDACTED-PATH]` |

This is a second layer only (R8); the primary guarantee is the allow-list (R4–R7). A corpus
test exercises it through `redact` mode, and on the create path with a fixture-created
harness-owned file whose basename is token-shaped (it passes R5, then is redacted in the
`File:` line) while the marker line stays byte-exact.

## Duplicate search & creation  (serves: R9)

- `GH_HOST="$host" gh issue list --repo "$owner/$repo" --state open --search "in:title $title" --json number,title --limit 50`
  where `$title` is the R6 fixed title. `gh --search` is full-text, so it is only a candidate
  filter: scope it with `in:title`, then treat the report as a duplicate **only when a
  returned `title` equals `$title` exactly** (a client-side exact comparison). An issue whose
  body or comments merely mention the words must not suppress a distinct report.
- Duplicate ⇒ no `gh issue create`, **no comment** (R9), still write the local copy (R11).
- Create: `GH_HOST="$host" gh issue create --repo "$owner/$repo" --title "$title" --body-file <tmp>`
  where `<tmp>` holds the redacted body. Only on a successful create does the ledger count
  increment (R10).

## Approach notes
- **Dash-clean, `set -eu` safe.** Lessons: a bare `var="$(pipeline-that-can-match-nothing)"`
  aborts the whole script under `set -e`; use `|| true` on any such assignment. End loops
  with an `if`, not a bare `[ … ] && echo`. Never invoke a bash-shebang script through `sh`.
- **Stub `gh` for tests.** A scratch dir on `PATH` first, with a `gh` that records argv to a
  log (including any `--body-file` target) and returns configurable output/exit. "`gh`
  missing" is a PATH without it.
- **Fixture is an installed target.** Build `<tmp>/proj/.harness/{tools,harness.config.yaml}`
  (`tools/` copied so both `harness-report.sh` and `harness-owned-paths.sh` resolve), `git
  init` it, and run the tool as `.harness/tools/harness-report.sh`. This makes R5's project
  vs harness path distinction clean. Accessibility: the script is run via its path, so it
  must not require `+x` to be tested — but R12 pins `[ -x ]` on the **source** file.
- **VERSION literal sweep.** Grep `tests/` for a bare `0.85.0` before trusting a green run
  (lesson 2026-09-16, `test_codex_native.sh`), and sync any current-version pin.
- **Timestamp collision.** Tests run calls within one second; the `-2`/`-3` suffix rule is
  what keeps R10/R11's multiple calls distinct. Tests glob the directory rather than pin the
  name.
- **`gh` host selection.** Use `GH_HOST="$host"` plus `--repo "$owner/$repo"`; the stub
  asserts the `--repo` and `--search` values, not the env var. Real `gh` resolves the
  hostname from `GH_HOST`.
