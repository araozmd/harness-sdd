# `tools/harness-report.sh` — Functional Spec

> R-ids in this document are `R1 … R12`; their fully-qualified form is `E32-F02:R1 … E32-F02:R12`.

## Context

E32 makes an installed harness file a scrubbed GitHub issue upstream when one of four narrow
triggers fires. F01 shipped the `feedback:` config switch. This feature ships the tool that
does the filing: `tools/harness-report.sh`. It is **deterministic and testable by design** —
the prompts (F03) decide *when* to call it; this tool decides *how*, so the privacy contract
is enforced in one auditable place rather than in prose that three front ends must each
re-discover.

The caller is F03's reporting rule (the only invoker of this tool); F04 (the labeler) and F05
(triage) **consume the marker** this tool writes, and the harness maintainer triages what it
files. The problem it solves: automatic filing is privacy-sensitive and runs
with no human review, so **nothing project-specific may ever be transmitted**. Every outbound
field (issue title, body, duplicate-search query) is built only from allow-listed structured
fields; free-form text (the agent's summary and expected/observed notes) stays only in the
local `progress/feedback/` copy. The redaction pass is a **second layer**, not the guarantee.

**Complexity basis (`complex`).** Three signals, all from this feature's own design:
(1) it presses against the budget ceiling — 12 R-ids of the configured
`change_size.max_requirements: 12`, so it nearly split at drill time; (2) it defines the
marker grammar and allow-list that F04 (the labeler) and F05 (triage) must parse, and a
validator whose grammar and consumers disagree is a defect class this harness has paid for;
(3) the privacy contract is literally a "a body and its copy diverge" contract — the
upstream body and the local copy must differ exactly at the free-form boundary, and a
one-sided leak in either direction is the whole risk.

## Business rules

- **Deterministic tool, not policy.** The tool never decides whether to report; it only
  decides how. A given set of structured inputs yields the same outbound artifacts.
- **Allow-list, not redaction, is the privacy guarantee.** Every field the tool transmits
  is validated against a fixed allow-list (enum, grammar, or harness ownership). A value
  outside its allow-list never reaches `gh`. Free-form text is never an input to title,
  body, or search query. Redaction runs afterward as defense in depth.
- **Nothing project-specific upstream.** The body names harness files only. A candidate
  path that is not harness-owned is dropped, not transmitted, and not used in the title.
- **Fixed title and marker.** The title is exactly
  `[harness-feedback] <trigger> <symptom-code> in <harness-file>` and the body starts with
  exactly one marker line `<!-- harness-feedback:v1 host=<host> version=<VERSION> trigger=<trigger> -->`.
  The marker grammar is defined here (ADR-0006) and parsed by F04/F05; changing it means a
  new marker version.
- **Fixed trigger vocabulary** (the four E32 triggers): `harness-malfunction`,
  `contradictory-instruction`, `workaround`, `missing-capability`.
- **Fixed symptom vocabulary:** `init-failure`, `install-failure`, `tool-failure`,
  `board-write-failure`, `gate-unsatisfiable`, `instruction-conflict`, `doc-conflict`,
  `workflow-gap`, `state-corruption`.
- **Bounded filing.** The tool searches for an open duplicate first
  (`gh issue list --search`); a duplicate means **no new issue and no comment**. A
  per-session cap (`feedback.max_per_session`) bounds new issues; `0` files nothing.
- **Session identity is caller-supplied.** Only the session-owning top-level role calls the
  tool (E32 drill decision), so there is a single writer. The session is an opaque token the
  caller supplies (`--session-id`, or `HARNESS_FEEDBACK_SESSION_ID`); the tool counts new
  issues in a local ledger keyed by that token and resets when the token changes. A missing
  or invalid token cannot enforce the cap, so the tool fails closed: local copy, no upstream
  issue. F03 owns where its session token comes from; F02 defines and validates the contract.
- **Never block or fail the caller.** A report that the caller asked to file never makes the
  caller's task fail: `gh` missing, unauthenticated, or erroring, a duplicate, a capped
  session, a supplied value outside its allow-list, or a missing required field all result in
  exit 0 and (where applicable) a local copy. The tool has no non-zero operational exit path.
- **The local copy is the durable artifact.** For every enabled report the tool writes
  `progress/feedback/<timestamp>.md` under the governing harness dir, with the structured
  fields and the free-form text verbatim, whether or not an issue was created.
- **Host-qualified repo.** Reporting targets the host in resolved `feedback.repo` (F01
  grammar `[HOST/]OWNER/REPO`; omitted host means `github.com`), and the auth check targets
  that resolved host. A malformed repo turns reporting off.

## Architecture alignment

`specs/architecture.md` is **absent** in this repo; the ADR set is present and cited below.

- platform ADR-0006 — The versioned body marker is the only contract between reporter and
  triage: this spec **defines** the marker grammar (`harness-feedback:v1` carrying schema
  version, host, harness `VERSION`, and trigger) that F04 and F05 parse; the tool emits
  exactly one such marker and treats the rest of the body as allow-listed structured fields
  only (R1, R7).
- platform ADR-0004 — A child resolves the harness body through pointer stubs at the same
  paths: `tools/` is in the **standalone** (program-read) tier, so the tool resolves its
  governing harness dir from its own location and therefore reads that target's **own**
  `feedback:` config and writes its local fallback under that target's own
  `progress/feedback/` — never the umbrella's (R2, R3, R10, R11).
- ADR-0003 and ADR-0005 are not touched: this feature emits no skill unit or source-only
  command surface (that is F03).

## Acceptance criteria (EARS)

- **R1** — When the tool creates an issue, the body it passes to `gh` shall begin with
  exactly one marker line whose bytes are the HTML comment
  `<!-- harness-feedback:v1 host=<host> version=<harness-version> trigger=<trigger> -->`
  (the fixed `harness-feedback:v1` token followed by three `key=value` fields — `host`,
  `version`, `trigger` — in that order, single-space separated, all present), where `<host>`
  is the host part of the resolved `feedback.repo`, `<harness-version>` is the resolved
  `VERSION`, and `<trigger>` is the accepted trigger value; no other `harness-feedback:` marker
  shall appear anywhere in the body. If `VERSION` does not match `[0-9]+\.[0-9]+\.[0-9]+`, then
  the tool shall not file upstream and shall write the local report (R11) instead — a marker
  that violates its own grammar is never emitted.
- **R2** — While `feedback.enabled` does not resolve to the bare, unquoted, lower-case token
  `true` (F01 contract), the tool shall make no `gh` invocation and write no report file,
  and shall exit 0.
- **R3** — The tool shall resolve `feedback.repo` per F01's grammar (`[HOST/]OWNER/REPO`, two
  or three parts of `[A-Za-z0-9._-]+`; missing or empty resolves to the shipped default; two
  parts mean host `github.com`), derive the marker `host` and the `gh` target from it, and
  check `gh auth status --hostname <host>` against that host; if the value is malformed
  (scheme, stray `/`, empty part, four or more parts, other characters), then the tool shall
  turn reporting off exactly as R2 describes.
- **R4** — The tool shall accept `--trigger` only from the four-value trigger vocabulary,
  `--symptom` only from the symptom vocabulary, `--role` and `--phase` only from their
  enumerated vocabularies, `--command` only when it is a harness command name (a basename of a
  regular file in the installed body's `tools/`, `init.sh`, `harness-install.sh`, or a shipped
  `sdd-*` command unit present in the installed body), and `--exit-code` only when it matches
  `[0-9]{1,3}`; if `--trigger` or `--symptom` is missing, or any supplied value is outside its
  allow-list, then the tool shall create no upstream issue and shall write the local report
  (R11), exiting 0.
- **R5** — For each `--file` value, the tool shall accept it only when `tools/harness-owned-paths.sh`
  reports the corresponding path as part of the harness body; it shall drop every other value
  (absolute paths, `..` escapes, and project-owned paths) from the title, the body, and the
  duplicate-search query, and if no supplied value is accepted then it shall create no
  upstream issue and write the local report (R11) instead.
- **R6** — The issue title shall be exactly
  `[harness-feedback] <trigger> <symptom-code> in <harness-file>` — fixed prefix and fixed
  separators, the three variables taken only from accepted allow-listed fields, and
  `<harness-file>` the first accepted harness-owned path (R5).
- **R7** — The upstream body shall contain only the R1 marker and `Label: value` lines for
  the accepted structured fields (harness version, trigger, symptom, each accepted harness
  file, command, exit code, role, phase); it shall never contain the free-form text, and
  shall never name a path that R5 dropped.
- **R8** — The tool shall run a redaction pass over the assembled upstream body's
  `Label: value` lines immediately before `gh issue create`, replacing each shape of the fixed
  corpus named in the plan (GitHub/generic token, email address, and absolute path under the
  named prefixes) with its fixed `[REDACTED-…]` token; the marker line shall be left
  byte-exact — redaction never rewrites the marker that is the sole reporter↔triage contract. A
  `redact` mode reading stdin and writing stdout shall expose the same pass. The corpus is
  fixed; extending it is out of scope.
- **R9** — Before creating an issue, the tool shall run `gh issue list --search` on the
  resolved repo with a query built only from R6's fixed title and scoped to the title field
  (`in:title`), and shall treat the report as a duplicate only when a returned issue's title
  equals R6's title exactly (a client-side exact comparison, not a substring); on a duplicate it
  shall create no issue and post no comment, and shall exit 0.
- **R10** — Where `feedback.max_per_session` resolves to `N` (F01 contract: a non-negative
  integer; missing or invalid resolves to `3`; `0` means nothing upstream), the tool shall
  create at most `N` new upstream issues per session, where the session is the validated
  token from `--session-id`/`HARNESS_FEEDBACK_SESSION_ID` and the created-issue count is kept
  in a local ledger under `progress/feedback/`; when the cap is reached, or the token is
  missing or fails `[A-Za-z0-9._-]{1,64}`, the tool shall create no upstream issue and write
  the local report (R11); a different token shall reset the count.
- **R11** — For every enabled report the tool shall write a local copy to
  `<governing-harness-dir>/progress/feedback/<timestamp>.md` containing the structured fields
  and the free-form text verbatim, whether or not an upstream issue was created; and if `gh`
  is missing, unauthenticated on the resolved host, or any `gh` call fails, then the local
  copy is the only output and the tool shall exit 0 — it shall never block or fail the
  caller's task.
- **R12** — The change shall add the executable `tools/harness-report.sh` to the installed
  body (source `+x` and a `chmod +x` entry in `harness-install.sh`), bump `VERSION` by one
  MINOR step from `0.85.0` to `0.86.0`, add a `CHANGELOG.md` `## [0.86.0]` entry naming the
  tool, and replace the `docs/INSTALL.md` `## Harness feedback` sentence
  `**No reporter ships yet** — this block is accurate but inert until **E32-F02** … and
  **E32-F03** … land.` with a sentence that states the report tool ships (E32-F02) and that
  reporting is inert until E32-F03's triggers land.

## Out of scope

- The triggers, the reporting rule, the end-of-task/early-stop wording, and `/sdd-report`
  (E32-F03). This tool is inert until F03 calls it.
- The labeler GitHub Action and the `harness-feedback` label mapping (E32-F04); `/sdd-triage`
  (E32-F05).
- Any change to the `feedback:` config block or its resolution contract (E32-F01).
- Auto-retry of a report that fell back to `progress/feedback/`; retry is a documented
  non-goal of the epic.
- Any front-end glue / emitter change (F03).
- Adding new redaction patterns beyond the corpus this spec names; the corpus is a fixed
  starting set, not an arms race.

## Open questions

- None blocking. The brief's open questions are resolved:
  - **Duplicate key** — the R6 fixed title (built only from accepted categorical fields),
    never free-form text.
  - **Symptom vocabulary** — the nine fixed codes in Business rules; R4 pins them.
  - **Per-session cap / session id** — caller-supplied opaque token
    (`--session-id`/`HARNESS_FEEDBACK_SESSION_ID`), counted in a local ledger keyed by that
    token; single writer, so no locking. F03 owns the token's origin.
- Carried to F03 (not blocking): which session token F03 supplies and how it obtains it on
  each front end.
