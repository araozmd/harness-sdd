# Jira sync via REST API + PAT (no MCP) — Technical Plan

> Translates the `.spec.md` intent into design. Every decision cites the R-id(s) it
> serves. The mirror framework already exists — this plan **fills the recognized `jira`
> stub** in `tools/sync-board.mjs` against Jira REST + PAT; it does not fork a second Jira
> path and does not redesign the mirror.

## Fill-the-stub decision  (serves: R1, R2, R13)

**Decision: FILL the existing `jira` stub branch of `tools/sync-board.mjs`. Do NOT fork a
second Jira code path.**

Rationale (the load-bearing part of this plan):

- `tools/sync-board.mjs` already dispatches on `mirror.board.provider`; the `jira` branch
  (currently at the `if (provider === 'jira' || provider === 'azure-boards')` block that
  prints "NOT IMPLEMENTED" and exits 0) is the **single** recognized Jira entry point. The
  brief and `store/board-mirror.md` → "Implementing a stub provider" explicitly direct us
  to implement that branch, honoring the same provider-neutral config keys (`status_map`,
  `assignee`), one-way and idempotent.
- Forking a separate tool would create the exact defect the epic family warns against —
  two divergent provider code paths — and lose the mirror's tested inert-default,
  `status_map`, and one-way behavior (`tests/test_mirror.sh`).
- Therefore F01's deliverable is: (a) split the shared `jira`/`azure-boards` stub so
  `azure-boards` stays a no-op stub while `jira` runs the new REST+PAT projection; (b) add
  a PAT resolver + preflight (env → gitignored file); (c) implement the Jira REST reconcile
  (create/update issue per feature, transition status); (d) pin the contract in docs; (e)
  seed config + gitignore in the installer and assert it; (f) VERSION bump.

## Resolved open questions  (serves: R5, R6, R10, R11)
1. **Jira Cloud vs Server/Data Center** → **Server / Data Center Bearer PAT** is the F01
   supported auth (`Authorization: Bearer <PAT>`), matching the brief's "Personal Access
   Token". **Jira Cloud** (Basic `email:api-token`) is **out of F01 scope**, documented as
   a future extension (would add a `mirror.board.auth: bearer|basic` selector and a Basic
   header path). (R5)
2. **Field mapping** → **configurable, sane defaults.** epic→Jira **Epic**, feature→Jira
   **Story** via `mirror.board.issue_type_map` (overridable); feature status→Jira workflow
   state via the existing provider-neutral `mirror.board.status_map` (identity default).
   Nothing hard-coded. (R10, R11)
3. **Where the PAT lives** → **`JIRA_PAT` env var, else gitignored `pat_file`** (default
   `.harness/jira.pat`); **env var wins** when both are set. Aligned with the E09-F02
   personal layer and `docs/CONFIG-LAYERING.md`. Never committed, never in `tasks.json`
   or config. (R6, R8)

## Stack & dependencies
- Language: Node.js (existing `tools/sync-board.mjs`, ESM, dependency-free). Jira REST
  calls use Node's built-in `fetch` (or the existing `child_process` + `curl` fallback
  ethos — Builder's call, but **no new npm package** and **no MCP**).
- External surface: the target Jira **Server / Data Center** REST API over HTTPS,
  authenticated by a PAT the developer provisions. No new committed dependency, no MCP, no
  new CLI binary required by the harness.
- Test harness: POSIX `sh` suites (`tests/test_mirror.sh`, `tests/test_install.sh`), run
  from `verification.test_command`. Jira REST is exercised via a **fake HTTP endpoint /
  stubbed transport** (a local recording server or an injected fetch shim), never a live
  Jira — same "record every call, assert dispatch" ethos as the fake-`gh` cases.

## Data model  (serves: R3, R6, R10, R11)
No new persistent schema in `state/tasks.json`. The projection maps existing entities onto
Jira issues. New **config** keys are added under the existing `mirror.board` block; the
PAT is **not** config — only a *path* to it and/or the env var.

| Entity | Field | Type | Notes |
|---|---|---|---|
| feature (from tasks.json) | `id` / `title` / `status` | string | `id` is the reconcile key stored on the Jira issue (label/summary prefix) (R3) |
| epic (from tasks.json) | `id` / `title` | string | maps to a Jira **Epic** issue (R10) |
| mirror.board config | `provider` | scalar | `jira` selects this branch; empty ⇒ inert (R4) |
| mirror.board config | `base_url` | string (URL) | Jira Server/DC base, e.g. `https://jira.acme.internal` (R1, R9) |
| mirror.board config | `project_key` | string | target Jira project key, e.g. `HAR` (R1, R9) |
| mirror.board config | `pat_file` | string (path) | gitignored PAT file; default `.harness/jira.pat` (R6) |
| mirror.board config | `issue_type_map` | map | `epic`/`feature` → Jira issue type; defaults Epic/Story (R10) |
| mirror.board config | `status_map` | map | existing provider-neutral status→workflow-state map, identity default (R11) |
| mirror.board config | `assignee` | string | existing provider-neutral knob; **no-op for jira in F01** (R12) |
| secret (NOT config) | `JIRA_PAT` env / `pat_file` contents | string | PAT; never committed, never logged, never in tasks.json (R6, R8) |

## Interface / behavior  (serves: R1, R5, R7, R9, R14, R15)
No harness HTTP API. The interface is the existing CLI command's exit contract, extended
for the `jira` provider:

| Invocation | Behavior | R-id |
|---|---|---|
| `node .harness/tools/sync-board.mjs` (provider jira, configured, PAT present) | project tasks.json → Jira via REST+Bearer PAT | R1, R3, R5, R10, R11 |
| `node .harness/tools/sync-board.mjs --dry-run` (provider jira) | print intended Jira changes; mutate nothing | R14 |
| provider empty/`none` | no-op, exit 0, no Jira network call | R4 |
| provider jira, no PAT resolvable | exit non-zero, names `JIRA_PAT` + pat_file, before any network call | R7 |
| provider jira, missing `base_url`/`project_key` | exit non-zero, names missing key, before any network call | R9 |
| Jira REST returns 401/403 | exit non-zero, actionable message, PAT not echoed | R15 |

## PAT resolution + secret hygiene  (serves: R6, R7, R8)
Resolution order (first hit wins):
1. `JIRA_PAT` environment variable (non-empty) — **precedence**.
2. `mirror.board.pat_file` contents (default `.harness/jira.pat`), trimmed of trailing
   newline; only if the file exists and is readable.
3. Neither ⇒ fail closed (R7): exit non-zero naming `JIRA_PAT` and the pat_file path,
   **before** any network call.

Hygiene rules the Builder must honor:
- The resolved PAT value is **never** written to `state/tasks.json`, `harness.config.yaml`,
  logs, or any committed file (R8). Only the *path* (`pat_file`) and the env-var *name*
  appear in config/docs/errors — never the value.
- The default `pat_file` path is appended to the installer-seeded `.gitignore` so a fresh
  install can't accidentally commit it (R16).

## DO NOT TOUCH
- `state/tasks.json` — the source of truth; the mirror is one-way and never writes it
  (R13). No test may diff it against `main`.
- The `github-projects` branch of `tools/sync-board.mjs` — E11's territory; leave its
  preflight/reconcile logic unchanged (only the stub split for `jira` is in scope).
- The `azure-boards` branch — it stays a recognized no-op stub (E13/E14). Do not implement
  it here.
- The store **backend** contract in `store/jira.md` (`tasks: jira`, the TaskStore
  operations) — F01 is a **mirror**, not a backend; only add the cross-reference.
- Any MCP glue — none exists and none is added (R1).
- The Orchestrator / `/sdd-next` / ownership (`workflow.identity`, `owner`) code paths —
  E10's territory (R12); F01 touches none of it. `assignee` stays a no-op for jira.
- Do **not** pin an exact `VERSION` string in any permanent test, and do **not** diff any
  DO-NOT-TOUCH file (esp. `state/tasks.json`) against `main` in a permanent test (recurring
  anti-pattern).

## Approach notes
- **REST transport (R1) is the Builder's call**, within the constraint: HTTPS to
  `base_url` with `Authorization: Bearer <PAT>`, dependency-free (built-in `fetch` or a
  `curl` shell-out — no new npm package, no MCP). All Jira endpoints (`/rest/api/2/...`
  search / create / transition) are reached this way.
- **Idempotency (R3):** store the feature id on the issue (a label like `harness:E12-F01`
  or a summary prefix) and reconcile by searching for it (JQL `project = <KEY> AND labels =
  harness:<id>`), updating the existing issue's status transition instead of creating a
  duplicate. Keep the match key stable and documented.
- **Fail-closed ordering (R7, R9):** validate config (`base_url`/`project_key`) and resolve
  the PAT **before** the first network call, so a misconfigured or unauthenticated run never
  half-mutates Jira. The inert-default early return (empty provider) must still fire before
  any config read that would error.
- **Secret hygiene tests (R8):** assert the PAT value never appears in the tool's stdout /
  stderr, never in the seeded config, and never in the fixture `tasks.json` after a run;
  assert the seeded `.gitignore` covers the PAT file. Use a sentinel PAT value in fixtures
  and grep for its absence.
- **Installer assertion (R16):** reuse the E11-F01 shape
  (`[ -x "$T/.harness/tools/sync-board.mjs" ]`) and add a `.gitignore` grep for the PAT
  path. Sandbox `CODEX_HOME` for any installer-invoking case (existing suite guard).
- **Test ethos (R18):** assert **behavior**; for the VERSION bump assert the **shape**
  (`VERSION` parses as SemVer `MAJOR.MINOR.PATCH` + a matching `CHANGELOG.md` entry
  exists), the same shape-only form used by sibling suites — never compare the working tree
  to `HEAD`/`main`, never hard-code the exact new string.
