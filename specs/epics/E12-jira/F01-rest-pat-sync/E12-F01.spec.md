# Jira sync via REST API + Personal Access Token (no MCP) — Functional Spec

## Context
Teams that live in **Jira** want the harness's `state/tasks.json` reflected on their Jira
project as issues, so non-CLI stakeholders get a familiar view and (once E10 ownership
lands) assignment sync. The integration must work inside **MCP-restricted enterprises**,
so it uses only the **Jira REST API authenticated with a Personal Access Token (PAT)** —
the standard IT-approved scripting path — and **never an MCP server**.

A one-way board **mirror** framework already exists (`tools/sync-board.mjs`,
`store/board-mirror.md`, `mirror.board` in `harness.config.yaml`) and already projects
features onto GitHub Projects, idempotently, inert when unconfigured. It carries a
recognized **`jira` stub** that currently prints "not implemented" and exits 0. This
feature **fills that stub** — it wires the `jira` provider branch of the existing mirror
against Jira REST + PAT, rather than forking a second Jira code path. It preserves the
mirror's **one-way** invariant (agents never read the board; `state/tasks.json` stays the
single source of truth) and its inert-by-default behavior. F01 projects **status** onto
Jira issues; inbound ownership / atomic-claim reads (E10-F03) and `owner → assignee`
projection are **out of scope** and deferred.

## Business rules
- **Transport = Jira REST API + PAT only, never MCP.** Every Jira call is an HTTPS request
  to the configured Jira REST API, authenticated by a PAT. No MCP server is used or
  required, so the mirror works inside MCP-restricted enterprises.
- **Server / Data Center Bearer PAT is the supported auth (F01).** Jira **Server / Data
  Center** Personal Access Tokens are sent as an `Authorization: Bearer <PAT>` header
  (the IT-approved scripting path the brief names). **Jira Cloud** (which authenticates
  with Basic `email:api-token`) is **out of F01 scope** and documented as a future
  extension — see Open questions and `E12-F01.plan.md`.
- **Fill the existing `jira` stub; do not fork it.** There is exactly **one** Jira
  projection code path — the `jira` branch of `tools/sync-board.mjs`, `provider: jira`.
  This feature implements that branch; it introduces no parallel tool and no second Jira
  implementation.
- **One-way projection invariant (preserved).** The sync is one-way: `state/tasks.json`
  → Jira. Agents never **read** Jira to decide work; `state/tasks.json` stays the single
  source of truth. Nothing in this feature makes the mirror bidirectional or writes back
  into `state/tasks.json`.
- **Secret hygiene — PAT is never committed.** The PAT is read from the environment
  variable **`JIRA_PAT`** or, if that is unset, from a **gitignored personal file**
  (`.harness/jira.pat` by default, path overridable via config). The PAT is **never**
  written into `state/tasks.json`, the mirror config, logs, or any committed file. Env var
  takes precedence over the file when both are present.
- **Config lives in `harness.config.yaml` under `mirror.board`.** The Jira provider adds
  Jira-scoped keys under the existing `mirror.board` block (`base_url`, `project_key`,
  `issue_type_map`, `pat_file`), reusing the provider-neutral `provider`, `status_map`,
  and `assignee` keys. No secret is ever stored in config — only the *path* to the PAT
  file and/or reliance on the env var.
- **Configurable field / status mapping (not hard-coded).** Harness concepts map to Jira
  objects via config with sane defaults: epics → Jira **Epic** issue type, features →
  Jira **Story** (both overridable via `mirror.board.issue_type_map`), and feature status
  → Jira workflow state via the existing provider-neutral `mirror.board.status_map`
  (identity default). Nothing about issue types or workflow states is hard-coded.
- **Idempotent reconcile.** A re-run reconciles: each feature maps to exactly one Jira
  issue (matched by a stable key stored in the issue, e.g. the feature id in a labeled /
  summary-prefixed field), and re-running updates that issue's status in place rather than
  creating a duplicate.
- **Inert when unconfigured.** With `mirror.board.provider` empty or `none` (the default),
  the sync is a pure no-op that makes **no** network call — exactly today's behavior. This
  preserves the existing inert-default contract shared by all providers.
- **Status only; ownership deferred to E10.** F01 projects feature **status** onto Jira.
  The `owner → assignee` projection and any inbound ownership / atomic-claim read are
  E10's concern (E10-F03). The provider-neutral `assignee` knob stays a recognized no-op
  for `jira` in F01 (documented as deferred), not wired to Jira's assignee field here.
- **Installed-body change ⇒ VERSION bump (MINOR).** This feature changes the installed
  harness body (the mirror tool's `jira` branch, docs, config seed, and installer-test
  assertion), so `VERSION` is bumped one SemVer **MINOR** step (additive,
  backward-compatible), with a matching `CHANGELOG.md` entry.

## Acceptance criteria (EARS)
> Each is one testable behavior with a stable id. See docs/SPEC-FORMAT.md.

- **R1** — When the sync runs with `mirror.board.provider: jira` and valid config, the
  system shall project `state/tasks.json` onto the configured Jira project using **only**
  the Jira REST API authenticated by a PAT, and shall use **no** MCP transport of any
  kind.
- **R2** — The system shall implement the `jira` projection through the single existing
  mirror tool `tools/sync-board.mjs` (the `jira` provider branch); it shall **not** add a
  second tool, script, or code path that talks to Jira (exactly one `jira` implementation
  exists in the body).
- **R3** — When the sync runs a second time with an unchanged `state/tasks.json`, the
  system shall reconcile existing Jira issues (matched by feature id → stored issue key)
  and shall create **no** duplicate issue (idempotent re-run).
- **R4** — While `mirror.board.provider` is empty or `none` (the default), the system
  shall perform no projection and shall make **no** Jira network call (a pure no-op —
  today's inert behavior is preserved).
- **R5** — The system shall authenticate to Jira using a **Server / Data Center** PAT sent
  as an `Authorization: Bearer <PAT>` header, and shall **not** require or use Jira Cloud
  Basic (`email:api-token`) authentication in F01.
- **R6** — The system shall read the PAT from the environment variable **`JIRA_PAT`** when
  set, otherwise from the gitignored PAT file (`mirror.board.pat_file`, default
  `.harness/jira.pat`); when both are present the **env var takes precedence**.
- **R7** — If `provider: jira` is selected but no PAT can be resolved (neither `JIRA_PAT`
  nor a readable `pat_file`), then the system shall exit non-zero with an actionable error
  naming `JIRA_PAT` and the PAT-file path, **before** making any Jira network call.
- **R8** — The system shall **never** write the PAT into `state/tasks.json`, the mirror
  config, or any committed file, and shall **not** print the PAT value in its logs or
  error output (secret hygiene).
- **R9** — If `provider: jira` is selected but a required config key (`base_url` or
  `project_key`) is missing, then the system shall exit non-zero with an error naming the
  missing key(s) **before** making any Jira network call (config validated first; the
  inert path is never a partial mutation).
- **R10** — The system shall map harness **epics** to the Jira **Epic** issue type and
  harness **features** to the Jira **Story** issue type by default, and shall honor
  `mirror.board.issue_type_map` overrides for either mapping (issue types are configurable,
  not hard-coded).
- **R11** — The system shall map each feature's **status** to a Jira workflow state via the
  provider-neutral `mirror.board.status_map` (identity default), and shall transition the
  reconciled issue to the mapped state; nothing about the workflow-state names is
  hard-coded.
- **R12** — The system shall project feature **status** only and shall **not** wire the
  `owner → assignee` projection for `jira` in F01 — the provider-neutral
  `mirror.board.assignee` knob remains a recognized no-op for `jira` (documented as
  deferred to E10-F03), and no inbound ownership / atomic-claim read is added.
- **R13** — The mirror shall remain **one-way**: the sync writes only to Jira and never
  writes back into `state/tasks.json`, and no agent reads Jira to determine work.
- **R14** — The system shall provide a `--dry-run` mode for `jira` that prints the intended
  Jira changes and mutates nothing (neither Jira nor `state/tasks.json`), so a developer
  can preview a projection before applying it.
- **R15** — If a Jira REST call returns an authentication/authorization failure (HTTP 401
  or 403), then the system shall exit non-zero with an actionable message that names the
  PAT / scope requirement and does **not** echo the PAT, without leaving a partially
  applied projection un-reported.
- **R16** — The harness installer (`harness-install.sh`) shall install the mirror tool
  (with its implemented `jira` branch) into the harness body as an **executable**
  `.harness/tools/sync-board.mjs`, shall seed the Jira `mirror.board` keys in the
  generated `harness.config.yaml` (inert defaults), and shall append the default PAT-file
  path to the seeded `.gitignore`; `tests/test_install.sh` shall **assert** that a fresh
  install ships that executable tool and gitignores the PAT file.
- **R17** — The documentation (`store/board-mirror.md` and `store/jira.md`) shall state
  that the `jira` **mirror** provider uses Jira **Server/DC** REST + Bearer PAT (Cloud out
  of F01 scope), name the `JIRA_PAT` env var and the gitignored `pat_file` convention and
  their precedence, describe the epic/feature issue-type map and the `status_map` workflow
  mapping, and reaffirm the REST+PAT-only / no-MCP transport and the one-way invariant.
- **R18** — Because this feature changes the installed harness body (the mirror tool
  `jira` branch, `store/board-mirror.md`, `store/jira.md`, the config seed, and the
  `tests/test_install.sh` assertion), the `VERSION` file shall be bumped one **MINOR** step
  (additive, backward-compatible; SemVer MINOR, not MAJOR), with a matching `CHANGELOG.md`
  entry.

## Out of scope
- **Inbound** agent-read of ownership / atomic claims — that is the E10 ownership model
  (E10-F03), not a bidirectional mirror here.
- **`owner → assignee` projection** for `jira` and any expansion of ownership semantics.
  F01 projects status only; the `assignee` knob stays a recognized no-op for `jira`. (E10.)
- **Jira Cloud** auth (Basic `email:api-token`). Only Server / Data Center Bearer PAT is
  supported in F01; Cloud is documented as a future extension.
- **Jira as a store backend** (`store/jira.md`'s `tasks: jira` — where Jira is the source
  of truth via `next()`). This feature is a **mirror** only; it does not implement the
  TaskStore contract.
- **Sub-task / requirement (T#, R#) projection.** F01 projects epics + features only, not
  Jira sub-tasks or per-requirement objects.
- **GitHub Projects / Monday / Azure Boards** — their own epics (E11 / E13 / E14); their
  branches in `sync-board.mjs` are unaffected.
- **MCP transport of any kind.**
- **Making the mirror bidirectional** or having any agent read Jira.

## Open questions
> None blocking. The three brief open questions are **resolved** as documented design
> decisions (see `E12-F01.plan.md` → "Resolved open questions"); the human gate may
> revisit any of them at approval.
- **(1) Cloud vs Server/DC — resolved: Server/DC Bearer PAT in F01; Cloud out of scope.**
  The brief specifies "Personal Access Token", which is the Server / Data Center Bearer
  model. F01 supports Server/DC only; Cloud Basic auth is deferred to a future feature and
  documented as such. A human may pull Cloud into scope at the gate if the target fleet is
  Cloud-first (would add a `mirror.board.auth` selector + Basic header path).
- **(2) Field mapping — resolved: configurable, with sane defaults.** epic→Epic,
  feature→Story via `mirror.board.issue_type_map` (overridable); status→workflow via the
  existing `mirror.board.status_map` (identity default). Not hard-coded. A human may pick
  feature→Task instead of Story at the gate (a config default change only).
- **(3) PAT location — resolved: `JIRA_PAT` env var, else gitignored `pat_file` (default
  `.harness/jira.pat`); env wins.** Aligned with the E09-F02 personal layer and
  `docs/CONFIG-LAYERING.md`. A human may rename the env var or default path at the gate.
