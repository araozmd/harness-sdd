# `execution.builder.backend` prompt in the installer picker — Functional Spec

## Context

The installer asks a human exactly one question — *which front-ends should I stamp?* Every
other install-shaping choice is a hand-edit of `.harness/harness.config.yaml`, discovered by
reading source comments. `execution.builder.backend` is the most consequential of them: it is
the single seam an external executor plugs into (`in-session` vs `delegate`), and nothing at
install time hints that it exists.

This feature builds the installer's **second-question surface** — a plain follow-up prompt
asked after the front-end picker confirms — and lands exactly **one** toggle on it:
`execution.builder.backend`. E20-F02 will add `pr_loop.enabled` to the same surface by adding
one more prompt behind the same resolver/writer pair. This feature deliberately builds **no
framework for N toggles**: one concrete toggle, with the seam visible.

The user is the engineer running `harness-install.sh` into a repo, interactively or from a
script. The value is discoverability, not new capability — the key is settable today by
editing YAML.

## Business rules

- **The config file is never rewritten wholesale.** The value is written by replacing the
  scalar on one line, in place; every comment, blank line and unrelated hand-edit survives.
  `harness.config.yaml` is heavily commented **by design** and those comments are the
  harness's load-bearing documentation of its own knobs.
- **Defaults are unchanged for anyone pressing Enter.** `in-session` stays the default, on a
  fresh install and on an upgrade alike.
- **Non-interactive runs are unaffected absent an explicit override.** CI keeps today's
  behavior exactly: no prompt, no value change.
- **`delegate` is only meaningful with a non-empty `delegate_cmd`** — see the ruling in *Open
  questions*, resolved as **warn-and-proceed**.
- **The front-end picker is not modified.** Its raw-mode/numbered/override ladder is the
  highest-risk code in the installer (stty state, EXIT/INT traps, raw Ctrl-C bytes) and has
  already absorbed two Codex P2s. This feature adds a prompt *after* it and changes nothing
  inside it.
- **Every interactive decision must be testable without a pty.** The answer→value mapping
  lives in a self-contained, side-effect-free function so a POSIX suite can extract and
  exercise it directly (R2). This repo has rejected features for assertions that could not
  fail; "the prompt is inspected by eye" is not a test.
- **Do not use the word "drift" anywhere in `harness-install.sh`** — `tests/test_drift_check.sh`
  greps the installer case-insensitively for it and fails the chain. Say "diverge".
- POSIX `sh`, zero new dependencies. This changes the installed body ⇒ **MINOR `VERSION`
  bump** + `CHANGELOG.md` entry.

- **`specs/architecture.md` is ABSENT** in this repo (the harness source has never run

## Acceptance criteria (EARS)

> Each is one testable behavior with a stable id. See `docs/SPEC-FORMAT.md`.
>
> **Definitions.** "The installer" = `harness-install.sh`. "The config" =
> `<target>/.harness/harness.config.yaml`. "The backend key" = the `backend:` scalar inside
> the **top-level** `execution:` section's `builder:` mapping. "Legal values" =
> `in-session` and `delegate`. "Override" = the `--builder-backend=<value>` flag or the
> `HARNESS_BUILDER_BACKEND=<value>` environment variable. **"Current effective value"** =
> the backend key's value in the target's config when that file exists, else the built-in
> default `in-session` (which is the case on a fresh install, where the config has not been
> seeded yet at prompt time).

### The second question

- **R1** — While standard input is an interactive TTY and no override is supplied, after the
  front-end picker has resolved its selection and before anything is written into the target,
  the installer shall ask exactly one line-oriented follow-up prompt for the builder backend,
  offering both legal values and naming the current effective value as the default. The
  prompt's text shall carry a **stable, greppable marker phrase** so its absence on a
  non-interactive run is assertable.
- **R2** — The prompt's answer→value mapping shall be a **self-contained, side-effect-free
  shell function** of `(answer, current-effective-value)` that prints the resolved value and
  nothing else, resolving: an empty answer → the current effective value; `1` or `in-session`
  → `in-session`; `2` or `delegate` → `delegate`; **any other answer** → the current effective
  value. It shall be extractable and sourceable by a `sed` range from its `name() {` line to
  the next line that is exactly `}`, so a POSIX suite can exercise it without a pty.
  > *Why a typo is forgiving here and fatal in a flag (R5):* a human at a prompt sees the
  > outcome reported on the next line and re-runs; a typo'd flag in a script is silent, so it
  > must abort. Same asymmetry the harness already applies to `--agents` (an unknown key
  > aborts) versus the picker (an out-of-range number is ignored with a note).
- **R3** — The follow-up prompt shall be the same line-oriented prompt on a raw-capable and a
  non-raw-capable TTY; `AGENT_KEYS`, `tui_capable`, `tui_select` and `toggle_select` shall
  gain no builder-backend behavior, and the front-end selection a run resolves shall be
  identical with and without this feature's inputs.

### Scripted installs

- **R4** — Where `--builder-backend=<legal value>` or `HARNESS_BUILDER_BACKEND=<legal value>`
  is supplied, the installer shall resolve the backend to that value and ask no prompt; the
  flag shall win over the environment variable, and an **empty** value shall mean "no
  override" (fall through to the prompt / no-op), matching `--agents=`.
- **R5** — If an override supplies a value that is neither `in-session` nor `delegate`, then
  the installer shall exit non-zero with a message naming the offending value and both legal
  values, **before** creating or modifying any file in the target.

### Back-compat

- **R6** — While standard input is not an interactive TTY and no override is supplied, the
  installer shall ask nothing and shall not change the backend key's value, on a fresh install
  and on an upgrade alike. (R9's migration may still append a missing `execution:` block to a
  config that predates it — that is a pre-existing upgrade behavior, not a value change.)
- **R10** — A fresh install with no override shall seed the config with the backend key set to
  `in-session`.

### Writing the value

- **R7** — When the resolved backend differs from the config's current value, the installer
  shall replace **only the scalar** on the existing backend-key line, preserving that line's
  indentation and any trailing comment, and leaving every other byte of the file unchanged —
  including every comment, blank line and unrelated hand-edited value.
- **R8** — When the resolved backend equals the config's current value, the installer shall
  leave the config **byte-identical**; and applying the same resolved value on a second run
  shall leave the config byte-identical (idempotent).
- **R9** — `migrate_config` shall append a default `execution:` block (carrying
  `builder.backend: in-session` and `builder.delegate_cmd: ""`) at EOF of a preserved config
  that carries no **top-level** `execution:` header, shall leave a config that already carries
  one untouched, and shall append nothing on a second run.

### `delegate` without a `delegate_cmd`

- **R11** — Where the resolved backend is `delegate` and `execution.builder.delegate_cmd`
  resolves to empty, the installer shall still write `delegate`, shall **not** abort, and
  shall print a warning naming `execution.builder.delegate_cmd` and the config's path; where
  `delegate_cmd` is non-empty it shall print no such warning.

### Reporting

- **R12** — The installer shall print exactly one line per target reporting the resolved
  backend and how it was resolved (override / prompt / unchanged), carrying a **stable,
  greppable prefix** and sourced from the same resolver every path feeds; and
  `--print-agents` shall keep printing exactly **two** stdout lines
  (`tests/test_agents_host.sh` asserts that count — do not add a third).

### Documentation, verification, release

- **R13** — `docs/INSTALL.md` and the installer's own summary/header text shall document the
  prompt, the `--builder-backend=` / `HARNESS_BUILDER_BACKEND` twin, both legal values, the
  `delegate_cmd` requirement and its warn-and-proceed behavior, and that **re-running the
  installer** is how the value is changed later.
- **R14** — A new suite `tests/test_installer_toggles.sh` shall carry every check in
  `E20-F01.tests.md` and be wired into `verification.test_command`. Every installer invocation
  shall go through **one gateway** that runs it under `env -i` with a sandboxed `HOME` and
  `CODEX_HOME`; **no check shall freeze the exact `VERSION` string, compare against a
  hard-coded previous version, or diff any file against `main`**; and
  `tests/test_install.sh` shall not be modified by this feature — a property the Reviewer
  asserts from the PR diff, never from a permanent test.
- **R15** — `VERSION` shall receive a MINOR bump and `CHANGELOG.md` a matching
  `## [<VERSION>]` entry naming this feature.

## Out of scope

- **`pr_loop.enabled`** — E20-F02 owns it, and adds it to this feature's surface as a second
  prompt behind the same resolver/writer pair. Do not generalize the surface for it here.
- A raw-mode (arrow-key) variant of the backend prompt. A two-option enum does not justify
  duplicating the `stty`/trap/Ctrl-C dance; see *Open questions* #1.
- Prompting for `execution.builder.delegate_cmd` itself. It is a free-text value, it would be
  a second question, and R11 makes the missing-command case loud instead.
- A `/sdd-config` command or any reconfiguration path other than re-running the installer.
- Caching the answer across an `--umbrella` cascade. The backend prompt fires per target,
  exactly like the front-end picker already does; changing that is a picker-wide UX question,
  not this feature's.
- Turning any other `harness.config.yaml` key into a prompt.
- Any change to `detect_host`, `precheck_baseline`, `resolve_agents`, `--print-agents`,
  `seed_pr_loop_optin`, `pr_loop_enabled`, `store/tasks.schema.json`, or any `agents/*.md`.

## Open questions — resolved, with rationale

1. **Extend `tui_select` into a mixed list, add a second screen, or ask a plain follow-up
   prompt?** **Plain follow-up prompt — the brief's suggestion is confirmed.** Three reasons:
   (a) `tui_select`/`toggle_select` are keyed on `AGENT_KEYS` and emit through
   `normalize_keys`; every row is an on/off agent key and the output contract is a sorted key
   list. An enum row has no `[x]`/`[ ]` meaning and no place in that output. (b) The raw-mode
   path is the installer's highest-risk code — terminal restoration, EXIT/INT traps, raw
   byte-3 handling — and regressing it would break the *front-end* picker for everyone, a
   strictly worse blast radius than a new, separate prompt. (c) A line-oriented `read` prompt
   works on **both** interactive rungs, so this toggle needs no second fallback ladder: the
   degradation contract the epic asks for is satisfied because the picker keeps its
   raw-mode/numbered ladder untouched and the follow-up prompt is uniform above it, with the
   override as the non-interactive rung (R3, R4, R6). E20-F02 adds its question by appending
   one more prompt — a linear seam, not a framework.

2. **Does this need a flag/env twin?** **Yes — `--builder-backend=<value>` +
   `HARNESS_BUILDER_BACKEND`.** This is not speculative surface: (a) the epic's own constraint
   ("non-interactive runs unaffected *absent an explicit override*") presupposes that an
   override exists; (b) it is the only way to exercise the write path — the append-only,
   value-preserving, idempotent config write that is the riskiest part of this feature —
   without a pty, and this repo has rejected features for unfalsifiable assertions; (c) it is
   exactly symmetric with `--agents` / `HARNESS_AGENTS`, so it introduces no new concept for a
   human to learn. E20-F02 reuses the same seam (`HARNESS_PR_LOOP_ENABLED` already exists).

3. **What should `delegate` do when `delegate_cmd` is empty? (RULING: warn and proceed —
   R11.)** Refusing would create an unbreakable chicken-and-egg: `delegate_cmd` is a config
   value the installer does not own and does not prompt for, so "you may not select
   `delegate` until a command is wired" means the prompt can never be used to turn delegation
   on. Silently downgrading to `in-session` would make the installer lie about what the human
   chose. So the installer **writes what was chosen and says loudly what is still missing**,
   naming `execution.builder.delegate_cmd` and the file to edit. Three things make this safe:
   the harness's existing precedent for an armed-but-not-yet-usable knob is warn-and-proceed
   (`pr_loop` documents that the Codex App "can be installed after the harness");
   `agents/builder.md` already **stops and reports** when `backend: delegate` meets an empty
   `delegate_cmd`, so the broken install fails at the one place a human can act on it; and the
   warning is a falsifiable assertion in both directions (R11 requires it to be **absent**
   when `delegate_cmd` is non-empty), not a comment.
