# `execution.builder.backend` prompt in the installer picker — Test Contract

> The traceability matrix: every R-id in the `.spec.md` maps to a concrete, executable check.
> The Reviewer fails the feature if any R-id lacks a passing check.
>
> All checks land in **`tests/test_installer_toggles.sh`**, a new flat POSIX-`sh` suite (so
> `tests/test_install.sh` stays out of the diff), wired into `verification.test_command`. The
> "test name" is the section label its `pass "…"` line carries.
>
> **Environment discipline (mandatory, inherited from `tests/test_agents_host.sh`).** Every
> installer invocation goes through **one** gateway, `hrun`, which runs
> `env -i PATH="$PATH" HOME="$X/home" CODEX_HOME="$X/ch" [VARS…] sh "$SRC/harness-install.sh" …`.
> `CODEX_HOME` is sandboxed on **every** run (never the developer's `~/.codex`). No check
> freezes the exact `VERSION` string. No check diffs a DO-NOT-TOUCH file against `main`.

## How the interactive path is tested — read this first

A POSIX suite cannot supply a pty, so the prompt cannot be *typed into*. This feature is
designed so that almost nothing hides behind that limitation, in three layers:

1. **The decision is a pure function, and the suite calls it for real.** R2 requires
   `builder_backend_answer <answer> <current>` to be self-contained and `sed`-extractable.
   The suite does
   `sed -n '/^builder_backend_answer() {$/,/^}$/p' "$INST" > "$T/fn.sh" && . "$T/fn.sh"`
   and then asserts every answer→value pair by invoking it. This is a genuine unit test that
   fails on wrong logic — the same block-extraction technique `tests/test_agents_host.sh`
   already uses for `marker_table`. **Every branch of the prompt's semantics is covered here.**
2. **The write path is driven end-to-end by the override.** `--builder-backend=` /
   `HARNESS_BUILDER_BACKEND` feed the *same* resolver and the *same* writer the prompt feeds,
   so the risky half of this feature — the append-only, value-preserving, idempotent config
   write — is exercised behaviorally, on real files, with real byte comparisons.
3. **The gating is asserted in the negative, behaviorally.** A non-TTY run must ask nothing
   and change nothing; an override must suppress the prompt. Both are real, failing-when-broken
   checks.

The only residue is `read -r` itself and the two menu `printf`s. Those are covered by the
Reviewer's by-hand checklist at the bottom, plus a structural check that the prompt function
contains nothing but the menu, the `read`, and a call to `builder_backend_answer` (so logic
cannot migrate out of layer 1 into the untestable part).

## Concrete check sketches

**`answer_mapping_unit` (R2)** — extract the function with the documented `sed` range into a
temp file and `.`-source it (fail loudly if the extraction is empty or the source fails —
that is itself the R2 shape assertion). Then assert, by invocation:
`"" in-session ⇒ in-session`, `"" delegate ⇒ delegate` (the empty answer follows the
**current** value, not a hard-coded default — this is the check that catches "Enter always
means in-session"), `1 delegate ⇒ in-session`, `in-session delegate ⇒ in-session`,
`2 in-session ⇒ delegate`, `delegate in-session ⇒ delegate`, `banana delegate ⇒ delegate`,
`banana in-session ⇒ in-session`. Also assert the function emits **nothing on stderr** and
creates no file (side-effect-free).

**`prompt_gating` (R1)** — (a) a non-TTY install (stdin `< /dev/null`) with no override
prints no prompt marker on stdout or stderr and exits 0; (b) an install with
`--builder-backend=delegate` likewise prints no prompt marker; (c) source: the interactive
branch of `resolve_builder_backend` is reached only under `[ -t 0 ]`, the call to
`resolve_builder_backend` appears **after** the `resolve_agents` call in `install_one`, and
`builder_backend_prompt`'s body contains a `read -r` plus a call to `builder_backend_answer`
and no other decision logic (no `case` on the answer, no config read, no file write) — this is
what keeps layer 1 authoritative.

**`picker_unaffected` (R3)** — install with `--agents=claude,gemini --builder-backend=delegate`
into one target and `--agents=claude,gemini` into an identical target; assert both
`.harness/.agents` files are byte-identical and list exactly those two keys. Source: neither
`tui_select`, `toggle_select`, `tui_capable` nor the `AGENT_KEYS` definition mentions
`backend`, `builder` or `BUILDER_BACKEND`; `AGENT_KEYS` still holds exactly the five
front-end keys.

**`override_precedence` (R4)** — on one installed target: `HARNESS_BUILDER_BACKEND=delegate`
⇒ config reads `delegate`; then `HARNESS_BUILDER_BACKEND=delegate --builder-backend=in-session`
⇒ config reads `in-session` (flag beats env); then `--builder-backend=` (empty) on a non-TTY
run ⇒ config still reads `in-session` and the file is byte-identical to before that run. Read
the value back with an independent one-line `awk`/`sed` in the test, **not** by calling the
installer's own helper.

**`illegal_override_aborts` (R5)** — `--builder-backend=turbo` into an **empty** dir exits
non-zero, the message names `turbo` and both legal values, and the dir is still empty (no
`.harness/`). Repeat via `HARNESS_BUILDER_BACKEND=turbo`.

**`non_interactive_is_inert` (R6)** — (a) fresh install, no override, non-TTY ⇒ config reads
`in-session`; (b) then hand-edit the config to `delegate` **and** add a distinctive comment
line, re-run with no override and no TTY ⇒ `cmp` the file against a copy taken before the
re-run: byte-identical. This is the CI-back-compat guard and the strongest single check in
the suite. Note the setup deliberately uses an **installed** config, whose `execution:` block
is already present, so R9's migration has nothing to append and `cmp` is a fair test of this
feature's writer alone.

**`write_preserves_everything_else` (R7)** — install, then hand-edit the config: change
`workflow.identity` to a sentinel, append a `# HUMAN NOTE …` comment at EOF, and add a
trailing comment on the `backend:` line itself. Re-run with `--builder-backend=delegate`.
Assert: the backend line's value is now `delegate`, its indentation and its trailing comment
survive verbatim, the sentinel and the EOF note are intact, and a `diff` of before/after shows
**exactly one changed line**.

**`write_is_idempotent` (R8)** — with the config already at `delegate`, run
`--builder-backend=delegate` twice; `cmp` the file before and after each run — byte-identical
both times. Then run with no override, non-TTY, twice — still byte-identical.

**`migration_seeds_execution_block` (R9)** — install, then delete the whole top-level
`execution:` block from the config (leaving the rest intact) and re-run: the block is back at
EOF with `backend: in-session` and `delegate_cmd: ""`, and every other line is unchanged. Run
again: `cmp` byte-identical (nothing appended twice). Separately, a config that already
carries `execution:` gets no second block — assert exactly one line matches
`^execution:[[:space:]]*(#.*)?$`.

**`fresh_default_unchanged` (R10)** — fresh install into an empty dir, no override, non-TTY ⇒
the seeded config's backend value is exactly `in-session`.

**`delegate_without_cmd_warns` (R11)** — install with `--builder-backend=delegate` on a config
whose `delegate_cmd` is `""`: exit 0, config reads `delegate`, and the combined output
contains a warning naming `execution.builder.delegate_cmd`. Then set `delegate_cmd` to a real
value by hand, re-run with `--builder-backend=delegate`: exit 0 and **no** such warning. Both
directions are required — the negative is what makes the positive falsifiable.

**`reports_once` (R12)** — a single-target install prints exactly one line matching the
report marker (count with `grep -c`). And `--print-agents <target>` still prints exactly two
stdout lines — the E19 contract this feature must not break.

**`docs_document_backend_prompt` (R13)** — `docs/INSTALL.md` mentions
`execution.builder.backend`, `--builder-backend`, `HARNESS_BUILDER_BACKEND`, both legal
values, and `delegate_cmd`; the `harness-install.sh` text mentions `--builder-backend` and
`HARNESS_BUILDER_BACKEND`. Also assert `grep -qi 'drift' harness-install.sh` finds **nothing**
(the `tests/test_drift_check.sh` trap, re-asserted locally so this suite catches it first).

**`suite_wiring_and_hygiene` (R14)** — `verification.test_command` in `harness.config.yaml`
names `tests/test_installer_toggles.sh`; every `harness-install.sh` invocation in this suite
goes through `hrun` (no bare call outside it); `hrun` sets `CODEX_HOME`; the suite contains no
frozen `VERSION` literal and no `git diff` against `main`.

> **Deliberately NOT automated:** "`tests/test_install.sh` is unmodified" is a property of
> **this PR's diff**, not of the repo forever. A permanent-suite check that diffed it against
> `main` would be meaningless the moment this merges and would break every later feature that
> legitimately touches that file — the exact anti-pattern this repo has hit three times. The
> Reviewer asserts it by reading the PR diff (see the by-hand checklist).

**`version_and_changelog` (R15)** — `VERSION` parses as semver and `CHANGELOG.md` carries a
`## [<VERSION>]` heading; separately, a stable marker for this feature
(`--builder-backend` or `execution.builder.backend`) appears **somewhere** in `CHANGELOG.md`,
not coupled to the top section. Never freeze the literal version string and never compare
against a hard-coded previous version — the MINOR-vs-PATCH judgement is the Reviewer's.
(Shape copied from `tests/test_drift_check.sh`'s `R19_version_changelog`.)

## Behavioral / end-to-end checks (Reviewer, by hand)

These cover the `read -r` plumbing that no POSIX suite can drive.

- From a real terminal, run the installer interactively into a scratch repo. Confirm the
  front-end picker appears **first** and behaves exactly as before, then that a single
  backend prompt follows it, naming `in-session` as the default.
- Press Enter ⇒ `.harness/harness.config.yaml` reads `backend: in-session`.
- Re-run interactively, answer `2` ⇒ the file reads `backend: delegate`, a warning names
  `execution.builder.delegate_cmd`, and every comment in the file is still present.
- Re-run interactively a third time and confirm the prompt now offers **`delegate`** as the
  default (pre-selected from the current value); press Enter ⇒ the file is unchanged.
- Answer with garbage (`xyzzy`) ⇒ the current value is kept and the installer proceeds; it
  does not loop or abort.
- Ctrl-C at the backend prompt leaves the terminal usable (this prompt never enters raw mode).
- Run the same install through a terminal where raw mode is unavailable (so the numbered
  `toggle_select` fallback is used for the picker) and confirm the backend prompt is
  identical.
- **Read the PR diff and confirm `tests/test_install.sh` is not in it** (R14) — this is the
  check deliberately left out of the permanent suite; see the `suite_wiring_and_hygiene`
  note above.
