# `pr_loop.enabled` prompt in the installer picker — Functional Spec

## Context

This is the toggle the human asked for at the start of this work stream: *"during the
install the user is the one who marks the pr-loop enablement."*

E18-F01 introduced `pr_loop.enabled` and, at the human's direction, made it **opt-in
(default `false`)**. Today turning it on is a one-line hand-edit of
`.harness/harness.config.yaml`, discoverable only by reading source comments. This is not a
preference like a theme: `/sdd-pr-loop` only functions on a repo that has the **Codex GitHub
App** installed plus an authed `gh` (and `jq`). On any other repo the correct value is
`false`, and the human is the only one who knows which repo is which — so the question
belongs at install time, asked out loud.

E20-F01 built the installer's **second-question surface** (a plain line-oriented follow-up
prompt asked after the front-end picker confirms) and landed `execution.builder.backend` on
it. This feature adds **one more prompt behind the same resolver/writer pair** — a linear
seam, deliberately **not** a framework for N toggles. It is the last feature of the epic.

The user is the engineer running `harness-install.sh` into a repo, interactively or from a
script. The value is discoverability, not new capability: the key is settable today by
editing YAML.

## Business rules

- **The opt-in default stays `false`.** This feature adds a prompt; it does not change the
  default, on a fresh install or an upgrade. Pressing Enter never turns the loop on.
- **The config file is never rewritten wholesale.** The value is written by replacing the
  scalar on one line, in place; every comment, blank line and unrelated hand-edit survives.
  `harness.config.yaml` is heavily commented **by design** and those comments are the
  harness's load-bearing documentation of its own knobs.
- **A fresh install can never inherit the harness source repo's own `enabled: true`.**
  E18-F01 R15 forbids that, and `seed_pr_loop_optin` enforces it. This feature keeps
  `seed_pr_loop_optin` **unmodified** and applies the resolved value **after** it, so the
  only thing that can leave a fresh install at `true` is an explicit human answer or an
  explicit flag — never inheritance (R9).
- **Non-interactive runs are unaffected absent an explicit override.** CI keeps today's
  behavior exactly: no prompt, no value change, no new file bytes.
- **`HARNESS_PR_LOOP_ENABLED` is E18-F01's territory and keeps its exact meaning.** It is a
  **per-run** gate override (the same family as `HARNESS_AUTO_MERGE` / `HARNESS_MAX_ROUNDS`),
  read by `pr_loop_enabled`. This feature must not turn it into a persisting override — see
  the ruling in *Open questions* #2.
- **The gate-off reclamation contract is E18-F01's and is reused untouched.** Its §7b pass,
  its R1 (the `sdd-pr-loop` body is generated into `CMDDIR` on **every** run, gate or no
  gate, because reclamation byte-compares against it) and its `.sdd-pr-loop.owners`
  cross-target ledger all keep working when the gate flip comes from a prompt instead of a
  hand-edit.
- **The front-end picker and the E20-F01 backend prompt are not modified.** The picker's
  raw-mode/numbered/override ladder is the highest-risk code in the installer and has
  already absorbed two Codex P2s; the backend prompt shipped last week. This feature adds a
  prompt *after* both and changes nothing inside either.
- **Every interactive decision must be testable without a pty.** The answer→value mapping
  lives in a self-contained, side-effect-free function so a POSIX suite can extract and
  exercise it directly (R2). This repo has rejected features for assertions that could not
  fail; "the prompt is inspected by eye" is not a test.
- **Do not use the word "drift" anywhere in `harness-install.sh`** —
  `tests/test_drift_check.sh:259` greps the installer case-insensitively for it and fails the
  chain. Say "diverge".
- POSIX `sh`, zero new dependencies. **The installer must not shell out to `gh` or `jq`** —
  see *Open questions* #1. This changes the installed body ⇒ **MINOR `VERSION` bump** +
  `CHANGELOG.md` entry.

## Acceptance criteria (EARS)

> Each is one testable behavior with a stable id. See `docs/SPEC-FORMAT.md`.
>
> **Definitions.** "The installer" = `harness-install.sh`. "The config" =
> `<target>/.harness/harness.config.yaml`. "The gate key" = the `enabled:` scalar inside the
> **top-level** `pr_loop:` section. "Legal values" = the literals `true` and `false`.
> "Override" = the `--pr-loop=<value>` flag (or its `--pr-loop <value>` two-token form).
> **"Current effective value"** = `true` when the gate key in the target's config reads
> exactly `true`, and `false` in every other case (absent file, absent block, absent key,
> empty or malformed value) — the normalization E18-F01 R18/R18b already defines.
> **"Resolved value"** = what this feature's resolver produces for a target: the override if
> one is supplied, else the prompt's answer on an interactive TTY, else the current effective
> value.

### The third question

- **R1** — While standard input is an interactive TTY and no override is supplied, after the
  E20-F01 builder-backend prompt has resolved and before anything is written into the target,
  the installer shall ask exactly one line-oriented follow-up prompt for the PR review loop,
  offering both legal values, naming the current effective value as the default, and stating
  that the loop requires the Codex GitHub App plus an authed `gh`. The prompt's text shall
  carry a **stable, greppable marker phrase** so its absence on a non-interactive run is
  assertable.
- **R2** — The prompt's answer→value mapping shall be a **self-contained, side-effect-free
  shell function** of `(answer, current-effective-value)` that prints one of the two literal
  legal values and nothing else, resolving: an empty answer → the current effective value;
  `1` or a case-insensitive `n` / `no` / `false` → `false`; `2` or a case-insensitive `y` /
  `yes` / `true` → `true`; **any other answer** → the current effective value. It shall be
  extractable and sourceable by a `sed` range from its `name() {` line to the next line that
  is exactly `}`, so a POSIX suite can exercise it without a pty.
  > *Why a typo is forgiving here and fatal in a flag (R4):* a human at a prompt sees the
  > outcome reported on the next line and re-runs; a typo'd flag in a script is silent, so it
  > must abort. Same asymmetry E20-F01 already applies.
- **R3** — The E20-F01 backend prompt and the front-end picker shall gain no PR-loop
  behavior: `AGENT_KEYS`, `tui_capable`, `tui_select`, `toggle_select`,
  `builder_backend_answer`, `builder_backend_prompt`, `resolve_builder_backend` and
  `set_builder_backend` shall be unmodified, and the front-end set and the builder backend a
  run resolves shall be identical with and without this feature's inputs.

### Scripted installs

- **R4** — Where `--pr-loop=<legal value>` is supplied, the installer shall resolve the gate
  to that value and ask no prompt; an **empty** value (`--pr-loop=`) shall mean "no override"
  (fall through to the prompt / no-op), matching `--agents=` and `--builder-backend=`; and if
  the value is neither `true` nor `false`, then the installer shall exit non-zero with a
  message naming the offending value and both legal values, **before** creating or modifying
  any file in the target.
- **R5** — `HARNESS_PR_LOOP_ENABLED` shall remain a **per-run** override with exactly its
  E18-F01 semantics: it shall never change any byte of the config, and it shall keep winning
  over the config for what the run itself stamps (E18-F01 R20). When it is set and its
  normalized value differs from the resolved value, the installer shall print exactly **one**
  warning naming the variable and stating that it was not persisted; when it is unset, or
  agrees with the resolved value, it shall print no such warning.

### Back-compat

- **R6** — While standard input is not an interactive TTY and no override is supplied, the
  installer shall ask nothing and shall leave the config **byte-identical**, on a fresh
  install and on an upgrade alike.

### Writing the value

- **R7** — When the resolved value differs from the current effective value, the installer
  shall write it into the **top-level** `pr_loop:` section only: replacing **only the scalar**
  on an existing gate-key line — preserving that line's indentation and any trailing comment
  text verbatim — or, where the section exists but carries no `enabled:` key at all,
  inserting the canonical gate-key line immediately after the section header. Every other
  byte of the file shall be unchanged, including a same-named `enabled:` key under any other
  section, every comment, every blank line and every unrelated hand-edited value.
- **R8** — When the resolved value equals the current effective value, the installer shall
  not invoke the writer at all and the config shall be **byte-identical**; and applying the
  same resolved value on a second run shall leave the config byte-identical (idempotent).

### The fresh-install seed interaction

- **R9** — `seed_pr_loop_optin` shall be unmodified and shall still force the freshly copied
  config's gate key to `false` **before** the resolved value is applied, so a fresh install
  with no override ends at `false` regardless of the value the harness source repo carries
  (E18-F01 R15), and a fresh install with `--pr-loop=true` ends at `true` because of the
  explicit choice and nothing else.
- **R10** — For the same resolved value, the top-level `pr_loop:` block of a freshly seeded
  target and of an upgraded target whose block came from `migrate_config` shall be
  **byte-identical** (E18-F01 R17 preserved under this feature's writer).

### Driving E18-F01's reconciliation from the prompt

- **R11** — When the resolved value is applied, it shall take effect **within the same run**:
  a run resolving `true` on a target that had the gate off shall stamp `/sdd-pr-loop` and the
  `pr-fixer` artifacts into every selected front-end, and a run resolving `false` on a target
  that had it on shall reclaim all of that glue through E18-F01's existing §7b pass and
  announce it. The `sdd-pr-loop` body shall still be generated into `CMDDIR` on **every** run
  regardless of the resolved value (E18-F01 R1), and a global Codex prompt still claimed by
  another target in `.sdd-pr-loop.owners` shall be left in place with the existing warning.

### Reporting

- **R12** — The installer shall print exactly one stdout line per target reporting the
  resolved value and how it was resolved (override / prompt / unchanged), carrying a
  **stable, greppable prefix** and sourced from the same resolver every path feeds; and
  `--print-agents` shall keep printing exactly **two** stdout lines
  (`tests/test_agents_host.sh` asserts that count — do not add a third).

### Documentation, verification, release

- **R13** — `docs/INSTALL.md`, the installer's own header/summary text, and the `pr_loop:`
  comment block in `harness.config.yaml` (both the source copy and the one `migrate_config`
  appends, kept byte-identical per R10) shall document the prompt, the `--pr-loop=` flag, the
  opt-in default, that `HARNESS_PR_LOOP_ENABLED` is per-run and **not** persisted, that no
  install-time preflight is run, and that **re-running the installer** is how the value is
  changed later.
- **R14** — Every check in `E20-F02.tests.md` shall be added to the existing
  `tests/test_installer_toggles.sh` (already wired into `verification.test_command` by
  E20-F01). Every installer invocation shall go through that suite's single `hrun` gateway
  under `env -i` with a sandboxed `HOME` and `CODEX_HOME`; **no check shall freeze the exact
  `VERSION` string, compare against a hard-coded previous version, or diff any file against
  `main`**; and neither `tests/test_install.sh` nor `tests/test_pr_loop.sh` shall be modified
  by this feature — a property the Reviewer asserts from the PR diff, never from a permanent
  test.
- **R15** — `VERSION` shall receive a MINOR bump and `CHANGELOG.md` a matching
  `## [<VERSION>]` entry naming this feature.

## Out of scope

- **Introducing or changing the `pr_loop` config block, its other four keys, the `/sdd-pr-loop`
  body, the pr-fixer role, the watcher, or the §7b reclamation logic.** E18-F01 owns all of
  it; this feature only sets `enabled` earlier in the same run.
- **Changing the opt-in default.** It stays `false`.
- **Any install-time preflight** (`gh` / `jq` / Codex App probing) — see *Open questions* #1.
- **An env twin for the new flag**, and any change to `HARNESS_PR_LOOP_ENABLED`'s meaning or
  to `pr_loop_enabled`'s precedence — see *Open questions* #2.
- Prompting for `auto_merge`, `max_rounds`, `blocking_severities` or `merge_strategy`.
- A general N-toggle framework, a `/sdd-config` command, or any reconfiguration path other
  than re-running the installer.
- Caching the answer across an `--umbrella` cascade. The prompt fires per target, exactly
  like the picker and the E20-F01 backend prompt already do.
- Any change to `detect_host`, `precheck_baseline`, `resolve_agents`, `--print-agents`,
  `store/tasks.schema.json`, or any `agents/*.md`.

## Open questions — resolved, with rationale

1. **Should an install that enables the loop run E18-F01's preflight and warn when the Codex
   GitHub App is absent? (RULING: no install-time preflight — say the precondition in the
   prompt text and let the first `/sdd-pr-loop` run report it.)** Four reasons, the first
   decisive: (a) E18-F01's preflight is a **loop-runtime** check that shells out to `gh` and
   `jq` and talks to GitHub. The installer is POSIX `sh` with **zero dependencies** and never
   invokes `gh`; adding that would make installing the harness depend on network reachability
   and on tools `docs/INSTALL.md` explicitly promises are *not* install-time requirements
   ("`init.sh` gains no new gate, so a target with neither `gh` nor `jq` still passes"). (b)
   It would be untestable in the permanent suite without a network or a `gh` stub, and this
   repo rejects assertions that cannot fail. (c) The App can legitimately be installed
   **after** the harness — the `pr_loop` block already documents that — and the target may not
   even have a remote yet, so a "missing App" warning would routinely be wrong. (d) The
   harness precedent for an armed-but-not-yet-usable knob is warn-and-proceed, which E20-F01
   applied to `delegate` without `delegate_cmd`; the cheap, dependency-free form of that here
   is to state the precondition **in the prompt itself** (required by R1, so it is
   falsifiable) and let E18-F01's fail-fast (exit `5`, naming the failed check and its
   remedy) carry the diagnosis at the one moment it can be accurate.

2. **Does this need a flag/env twin, and can it reuse `HARNESS_PR_LOOP_ENABLED`? (RULING:
   `--pr-loop=<true|false>` flag, and NO env twin — `HARNESS_PR_LOOP_ENABLED` is left exactly
   as E18-F01 defined it.)** The flag half is not speculative, for E20-F01's reasons applied
   unchanged: the epic's constraint ("non-interactive runs unaffected *absent an explicit
   override*") presupposes an override, and the flag is the only pty-free way to exercise the
   write path — the value-preserving, idempotent config write that is the riskiest part of
   this feature. The env half was **checked, not assumed**, and reusing the existing name is
   wrong on three counts: (a) **Semantics.** `HARNESS_PR_LOOP_ENABLED` is documented in
   `harness.config.yaml`, `docs/INSTALL.md`, `README.md` and the `/sdd-pr-loop` body as one of
   five **per-run** overrides (`HARNESS_AUTO_MERGE`, `HARNESS_MAX_ROUNDS`, …). Making one
   member of that family persist, while the other four stay per-run, is an inconsistency a
   reader cannot infer from the name. (b) **Footgun.** `HARNESS_PR_LOOP_ENABLED=false
   ./harness-install.sh <target>` today means "don't stamp on this run"; if it persisted it
   would silently and permanently disable a target's configured loop. (c) **Blast radius on
   DO-NOT-TOUCH files.** `tests/test_install.sh:24` exports `HARNESS_PR_LOOP_ENABLED=true`
   **suite-wide**, and `tests/test_pr_loop.sh`'s `install_on` helper exports it on every
   install; a persisting override would start rewriting target configs underneath both suites
   (`tests/test_pr_loop.sh` R15/R17 assert a seeded `false`), forcing edits to files this
   feature must keep out of its diff (R14). So the layering is: **the flag/prompt persists,
   the env var overrides the run**, and R5 makes that visible with one warning when the two
   disagree instead of leaving it a silent surprise. A second env name (`HARNESS_PR_LOOP`)
   was rejected as strictly more confusing than none.
