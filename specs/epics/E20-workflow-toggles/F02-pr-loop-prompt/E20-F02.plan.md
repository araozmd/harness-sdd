# `pr_loop.enabled` prompt in the installer picker — Technical Plan

> Every decision cites the R-id(s) it serves. Start high-level; the Builder picks
> internals not pinned here.

## Stack & dependencies

- POSIX `sh` + `grep`/`awk`/`sed` only — the installer's existing ethos. **No new
  dependencies**, and in particular **the installer's own logic must never invoke `gh` or
  `jq`** (spec *Open questions* #1). Note the installer *generates* the `/sdd-pr-loop` body,
  which is full of `gh`/`jq` calls — that is loop runtime, not install time, so this rule is
  verified behaviorally (`no_install_time_preflight`), never by grepping the installer.
- Line numbers below are from `harness-install.sh` at `VERSION` 0.42.0 and are hints, not
  contracts — locate by function name.

## Design in one paragraph

Add a **third question** to the installer, as one more prompt behind E20-F01's
resolver/writer pair. After `resolve_builder_backend` resolves, `resolve_pr_loop` resolves one
boolean with the precedence *flag override → interactive prompt → current effective value*,
storing it in a global. Later, in the **same §2b config block** E20-F01 already added, once
the file exists and `seed_pr_loop_optin` / `migrate_config` have run, `set_pr_loop_enabled`
writes it by replacing **one scalar on one line**. Because §2b runs long before §5 (glue
generation) and §7b (gate-off reclamation), the new value is what `pr_loop_enabled` reads for
the rest of that run — so a prompt answer stamps or reclaims the glue immediately, through
E18-F01's existing machinery, with no change to it. `migrate_config` gains **no new entry**
(the `pr_loop:` block entry already exists). `seed_pr_loop_optin` is **not modified**.

## Interface  (serves: R4, R5, R12)

| Surface | Form | Behavior |
|---|---|---|
| flag | `--pr-loop=<value>` / `--pr-loop <value>` | override; empty value ⇒ no override (R4) |
| legal values | `true`, `false` | anything else aborts non-zero before any write (R4) |
| env | `HARNESS_PR_LOOP_ENABLED` | **unchanged** — per-run gate override, never persisted (R5) |
| report | one stdout line per target, e.g. `   pr_loop.enabled: true (explicit --pr-loop)` | R12 |
| warning | one stderr line when `HARNESS_PR_LOOP_ENABLED` disagrees with the resolved value, carrying the stable token `PER-RUN override` | R5 |

There is **no** `--pr-loop-enabled` alias and **no** new env var. `--print-agents` output is
frozen at two lines — `tests/test_agents_host.sh` asserts the exact stdout line count; that
flag exits before `install_one`, so nothing here reaches it (R12).

## Config write shape  (serves: R7, R8, R9, R10)

Target region in `harness.config.yaml` (source lines ~229–235):

```yaml
pr_loop:
  enabled: false                 # ← only this scalar is ever rewritten
  auto_merge: true               # ← read-only for this feature
  max_rounds: 4
  blocking_severities: "P0,P1"
  merge_strategy: "merge"
```

- The writer replaces **only the value token** on the gate line, preserving indentation and
  everything after the value (spacing + any trailing comment) — the same shape
  `set_builder_backend` uses (R7).
- Where the top-level `pr_loop:` section exists but has **no** `enabled:` key (E18-F01 R18b
  constructs exactly that config), the writer inserts the **canonical** line — byte-identical
  to the one `seed_pr_loop_optin` and `migrate_config` emit, modulo the value — immediately
  after the section header. Without this, resolving `true` on such a config would silently do
  nothing (R7).
- When the resolved value already equals the current effective value the writer is **not
  invoked at all**, so the file is trivially byte-identical, mtime included (R8).
- Section scoping is mandatory in both directions: an `enabled:` key under **any** other
  top-level section must never be read or written (E18-F01 R19 for the read side;
  `_cfg_pr_loop_value` already does this). This is also the decoy fixture the E20-F01 note at
  `harness-install.sh:486` asked a follow-up feature to add — note that F01's forward
  reference to "a second mapping under `execution:`" was **inaccurate** (this feature adds
  nothing under `execution:`), but the falsifiability point stands and R7 discharges it for
  the `pr_loop:` side.
- **No `migrate_config` change.** The `pr_loop:` entry already exists (`harness-install.sh`
  ~:285). Its appended text and the source config's block are already byte-identical, so R10
  holds as long as the writer treats both identically — which it does, because both start
  from the same canonical line. Do not "improve" either copy without editing the other.

## Ordering  (serves: R9, R11)

The whole feature turns on where the write sits in `install_one`:

```
resolve_agents            (§ front-end picker,   E08/E19)
resolve_builder_backend   (§ second question,    E20-F01)
resolve_pr_loop           (§ THIRD question,     THIS FEATURE)   ← resolve only, no write
  …body copy…
fresh:   cp config → blank verification cmds → seed_pr_loop_optin   (forces enabled: false)
upgrade: migrate_config                                             (appends the block if absent)
§2b      set_builder_backend (E20-F01)  +  set_pr_loop_enabled (THIS FEATURE)  ← the write
  …
§5       pr_loop_enabled → stamp /sdd-pr-loop + pr-fixer   (reads the value just written)
§7b      ! pr_loop_enabled → reclaim that glue             (reads the value just written)
```

- **Fresh install (the subtle case, R9).** At resolve time the config does not exist, so the
  current effective value is the built-in `false` — which is also what the prompt pre-selects
  and what the seeded file will contain. `seed_pr_loop_optin` still normalizes the copied
  source value (the harness repo runs with `enabled: true`) down to `false`, and only then
  does §2b apply the resolved value. So "no answer ⇒ off" is enforced **twice**, and the sole
  route to `true` on a fresh install is an explicit `2`/`yes`/`--pr-loop=true`. Do **not**
  delete or condition `seed_pr_loop_optin` — E18-F01 R15 is asserted by
  `tests/test_pr_loop.sh`, which this feature must not touch.
- **Same-run effect (R11).** Because §2b precedes §5 and §7b, the flip is reconciled inside
  the same run with **zero** changes to E18-F01's code: turning it on stamps, turning it off
  runs the §7b reclamation (including the `.sdd-pr-loop.owners` ledger release and the
  "still claimed by another target" warning). §5's unconditional `CMDDIR` generation
  (E18-F01 R1) must stay unconditional — it is the pristine reference §7b compares against.

## Approach notes

- **Three questions, one seam.** The resolve block and the §2b apply block each grow by one
  call. That is the whole structural change; anything larger (a table of toggles, a loop over
  keys, a shared `resolve_toggle`) is the framework this epic deliberately refused.
- **`true`/`false` are written as literals, never echoed from the answer.** E18-F01 R18b makes
  `yes`, `1`, `True` all resolve OFF, so `pr_loop_answer` must map those *inputs* to the
  literal *output* `true`/`false` — never pass the raw answer through to the file.
- **Report-line marker collision.** The §7b reclamation warning contains the phrase
  `pr_loop.enabled is not true` on **stderr**. Pick a report prefix that cannot collide when
  counted on stdout (e.g. `pr_loop.enabled: ` with the colon) and count on stdout only (R12).
- **The `read -r` residue.** Only the literal keystroke plumbing (`read -r` and the menu
  `printf`s) is outside automated reach; every decision it feeds is in `pr_loop_answer`, which
  the suite extracts and unit-tests (R2). Keep the prompt function that thin — a structural
  check fails if logic migrates into it.
- **Umbrella cascade.** `install_one` runs for the coordinator (`install_one "$UMB"`) and for
  each child, so the prompt fires per target exactly like the picker and the E20-F01 prompt.
  The flag applies to every target in the cascade. No caching.
- **Non-interactive means silent.** In the no-TTY / no-override path the resolver must not
  merely resolve to the same value — the writer must not be invoked at all, so the file's
  bytes and mtime are untouched (R6, R8).
