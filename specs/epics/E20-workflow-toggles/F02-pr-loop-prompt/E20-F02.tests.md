# `pr_loop.enabled` prompt in the installer picker — Test Contract

> The traceability matrix: every R-id in the `.spec.md` maps to a concrete, executable check.
> The Reviewer fails the feature if any R-id lacks a passing check.
>
> All checks are **added to the existing `tests/test_installer_toggles.sh`** (already wired
> into `verification.test_command` by E20-F01), so `tests/test_install.sh` and
> `tests/test_pr_loop.sh` stay out of the diff. The "test name" is the section label its
> `pass "…"` line carries.
>
> **Environment discipline (mandatory, already established by that suite).** Every installer
> invocation goes through its **one** gateway, `hrun`, which runs
> `env -i PATH="$PATH" HOME="$X/home" CODEX_HOME="$X/ch" [VARS…] sh "$SRC/harness-install.sh" …`.
> `CODEX_HOME` is sandboxed on **every** run (never the developer's `~/.codex` — the `codex`
> front-end writes global prompts, and `/sdd-pr-loop` is one of them). No check freezes the
> exact `VERSION` string. No check diffs a DO-NOT-TOUCH file against `main`.
>
> **New helper:** `cfg_pr_loop <config>` — an independent, section-scoped `awk` that prints
> `pr_loop.enabled`, beside the existing `cfg_backend`. Deliberately **not** the installer's
> own `_cfg_pr_loop_value`: a reader that shares code with the writer can agree with it while
> both are wrong.

## How the interactive path is tested — read this first

A POSIX suite cannot supply a pty, so the prompt cannot be *typed into*. This feature is
designed so that almost nothing hides behind that limitation, in three layers (the same
three E20-F01 established):

1. **The decision is a pure function, and the suite calls it for real.** R2 requires
   `pr_loop_answer <answer> <current>` to be self-contained and `sed`-extractable. The suite
   does `sed -n '/^pr_loop_answer() {$/,/^}$/p' "$INST" > "$T/fn.sh" && . "$T/fn.sh"` and then
   asserts every answer→value pair by invoking it. This is a genuine unit test that fails on
   wrong logic. **Every branch of the prompt's semantics is covered here.**
2. **The write path is driven end-to-end by the `--pr-loop=` flag.** It feeds the *same*
   resolver and the *same* writer the prompt feeds, so the risky half of this feature — the
   value-preserving, idempotent config write, and the same-run stamp/reclaim it triggers — is
   exercised behaviorally, on real files, with real byte comparisons.
3. **The gating is asserted in the negative, behaviorally.** A non-TTY run must ask nothing
   and change nothing; the flag must suppress the prompt. Both are real,
   failing-when-broken checks.

The only residue is `read -r` itself and the menu `printf`s. Those are covered by the
Reviewer's by-hand checklist at the bottom, plus a structural check that the prompt function
contains nothing but the menu, the `read`, and a call to `pr_loop_answer` (so logic cannot
migrate out of layer 1 into the untestable part).

## Concrete check sketches

**`pr_loop_answer_mapping_unit` (R2)** — extract the function with the documented `sed` range
into a temp file and `.`-source it (fail loudly if the extraction is empty or the source
fails — that is itself the R2 shape assertion). Then assert, by invocation:
`"" false ⇒ false`, `"" true ⇒ true` (the empty answer follows the **current** value, not a
hard-coded default — this is the check that catches "Enter always means off"),
`1 true ⇒ false`, `no true ⇒ false`, `NO true ⇒ false`, `false true ⇒ false`,
`2 false ⇒ true`, `y false ⇒ true`, `YES false ⇒ true`, `true false ⇒ true`,
`banana true ⇒ true`, `banana false ⇒ false`. Also assert the function emits **nothing on
stderr**, creates no file, and never prints anything but the two literals (feed it `Yes` and
confirm the output is exactly `true`, not `Yes` — the E18-F01 R18b trap).

**`pr_loop_prompt_gating` (R1)** — (a) a non-TTY install (stdin `< /dev/null`) with no
override prints no prompt marker on stdout or stderr and exits 0; (b) an install with
`--pr-loop=true` likewise prints no prompt marker; (c) source: the interactive branch of
`resolve_pr_loop` is reached only under `[ -t 0 ]`; the call to `resolve_pr_loop` appears
**after** the `resolve_builder_backend` call in `install_one`; the prompt's text names both
`gh` and the Codex GitHub App (the *Open questions* #1 ruling, made falsifiable); and
`pr_loop_prompt`'s body contains a `read -r` plus a call to `pr_loop_answer` and no other
decision logic (no `case` on the answer, no config read, no file write).

**`f01_and_picker_unaffected` (R3)** — install with `--agents=claude,gemini --pr-loop=true`
into one target and `--agents=claude,gemini` into an identical target; assert both
`.harness/.agents` files are byte-identical and that `cfg_backend` reads `in-session` in both
(this feature's input changed neither). Source: neither `tui_select`, `toggle_select`,
`tui_capable` nor the `AGENT_KEYS` definition mentions `pr_loop`, `PR_LOOP` or `pr-loop`;
`AGENT_KEYS` still holds exactly the five front-end keys; and `builder_backend_answer`'s body
is unchanged in shape (its `sed`-extraction still sources and still returns `delegate` for
`2 in-session` — E20-F01 R2 re-asserted from here, so a refactor of the shared area is caught).

**`pr_loop_override_contract` (R4)** — on one installed target: `--pr-loop=true` ⇒
`cfg_pr_loop` reads `true`; `--pr-loop=false` ⇒ reads `false`; `--pr-loop=` (empty) on a
non-TTY run ⇒ the value is unchanged **and** the file is byte-identical to before that run;
the two-token form `--pr-loop true` works identically. Then `--pr-loop=maybe` into an
**empty** dir exits non-zero, the message names `maybe` and both legal values, and the dir is
still empty (no `.harness/`). Read the value back with `cfg_pr_loop`, **not** by calling the
installer's own helper.

**`env_is_per_run_not_persisted` (R5)** — on a target whose config reads `false`, run with
`HARNESS_PR_LOOP_ENABLED=true` and no flag: `cmp` the config before/after ⇒ **byte-identical**
(the env persisted nothing), `.claude/commands/sdd-pr-loop.md` **exists** (E18-F01 R20 still
holds: the env still gates the run), and the combined output contains exactly one line with
the `PER-RUN override` token naming `HARNESS_PR_LOOP_ENABLED`. Then run with
`HARNESS_PR_LOOP_ENABLED=true --pr-loop=true`: the config now reads `true` and **no** such
warning is printed (they agree). Then run with no env at all and `--pr-loop=false`: no
warning. All three directions are required — the negatives are what make the positive
falsifiable.

**`pr_loop_non_interactive_is_inert` (R6)** — (a) fresh install, no override, non-TTY ⇒
`cfg_pr_loop` reads `false`; (b) then hand-edit the config to `true` **and** add a
distinctive comment line, re-run with no override, no TTY and no `HARNESS_*` env ⇒ `cmp` the
file against a copy taken before the re-run: byte-identical. This is the CI-back-compat guard
and the strongest single check for this half of the suite. The setup deliberately uses an
**installed** config, whose `pr_loop:` block is already present, so migration has nothing to
append and `cmp` is a fair test of this feature's writer alone.

**`pr_loop_write_is_surgical` (R7)** — install, then hand-edit the config: add a trailing
comment on the `enabled:` line itself, append a `# HUMAN NOTE …` comment at EOF, change
`workflow.identity` to a sentinel, **and add a decoy top-level section carrying its own
`enabled: false` key**. Re-run with `--pr-loop=true`. Assert: the `pr_loop.enabled` line's
value is now `true`, its indentation and its trailing comment text survive verbatim, the
decoy section's `enabled:` is still `false`, the sentinel and the EOF note are intact, and a
`diff` of before/after shows **exactly one changed line**. Then, separately, delete the
`enabled:` line from an installed config (leaving the rest of the `pr_loop:` block) and run
`--pr-loop=true`: the canonical `enabled: true` line is present directly under the `pr_loop:`
header, the other four keys are unchanged, and the run stamps the glue.

**`pr_loop_write_is_idempotent` (R8)** — with the config already at `true`, run
`--pr-loop=true` twice; `cmp` the file before and after each run — byte-identical both times.
Then run with no override, non-TTY, twice — still byte-identical.

**`fresh_seed_interaction` (R9)** — (a) fresh install into an empty dir, no override,
non-TTY ⇒ `cfg_pr_loop` reads exactly `false`, even though `$SRC/harness.config.yaml` reads
`true` (assert that source value in the same check, so the test states *why* it matters
without freezing anything version-dependent). (b) fresh install into a **second** empty dir
with `--pr-loop=true` ⇒ reads `true` and the glue is stamped. (c) source: `seed_pr_loop_optin`
is still called on the fresh-seed branch, and the call to the new writer appears **after** it
in the file.

**`seeded_migrated_block_converge` (R10)** — install target A fresh with `--pr-loop=true`.
For target B: install fresh with no override, strip the whole top-level `pr_loop:` block from
its config, then re-run with `--pr-loop=true` so `migrate_config` re-appends the block and the
writer then edits it. Extract the `pr_loop:` block from each config (header line through the
last indented line) and `cmp` them — byte-identical. Repeat the pair with `--pr-loop=false`.
This is E18-F01 R17 re-asserted under this feature's writer, and it is the check E20-F01 got a
review finding for omitting.

**`same_run_stamp_and_reclaim` (R11)** — one target, `--agents=claude,codex`, all runs
through `hrun` (so `CODEX_HOME` is sandboxed). (a) install with `--pr-loop=true`:
`.claude/commands/sdd-pr-loop.md`, `.claude/agents/pr-fixer.md` and
`$CODEX_HOME/prompts/sdd-pr-loop.md` all exist. (b) re-run the **same** target with
`--pr-loop=false`, single run: all three are gone, the config reads `false`, and stderr
carries the existing `pr_loop.enabled is not true — reclaimed` announcement — i.e. the flip
reconciled without a second install. (c) re-run with `--pr-loop=true`: the glue is back and
byte-identical to (a). (d) the owners ledger is honored: with the target's gate on, create a
second directory holding a `.harness/` subdir (an entry is "live" only when
`<entry>/.harness` exists — see `_owners_live`) and append its **absolute** path as a line to
`$CODEX_HOME/prompts/.sdd-pr-loop.owners`, then re-run with `--pr-loop=false` — the global
prompt is **left in place**, the ledger still names the foreign owner, and the "still claimed
by another harness target" warning is printed. Removing that foreign line and re-running with
`--pr-loop=false` then *does* reclaim it — both directions, so the ledger check can fail.
(e) source: the `sdd-pr-loop` body generation into
`CMDDIR` in §5 is not nested inside any `pr_loop_enabled` guard (E18-F01 R1), asserted by
locating the generation line and checking the enclosing guard, not by eye.

**`pr_loop_reports_once` (R12)** — a single-target install prints exactly one **stdout** line
matching the report marker (`grep -c` on the captured stdout only — the §7b warning lives on
stderr and must not be counted). And `--print-agents <target>` still prints exactly two
stdout lines — the E19 contract this feature must not break.

**`docs_document_pr_loop_prompt` (R13)** — `docs/INSTALL.md` mentions `pr_loop.enabled`,
`--pr-loop`, both legal values, that `HARNESS_PR_LOOP_ENABLED` is per-run/not persisted, and
re-running the installer as the change path; `harness-install.sh`'s own text mentions
`--pr-loop`. Also assert `grep -qi 'drift' harness-install.sh` finds **nothing** (the
`tests/test_drift_check.sh` trap, re-asserted locally so this suite catches it first) — this
check already exists for E20-F01; extend rather than duplicate it.

**`pr_loop_suite_hygiene` (R14)** — every `harness-install.sh` invocation added by this
feature goes through `hrun` (no bare call outside it); the suite still contains no frozen
`VERSION` literal and no `git diff` against `main`.

**`no_install_time_preflight` (R14, and the *Open questions* #1 ruling made falsifiable)** —
a **behavioral** check, not a grep. Grepping `harness-install.sh` for `gh `/`jq ` is
impossible: the installer *generates* the `/sdd-pr-loop` command body from a heredoc
(`harness-install.sh` ~:2640) and that body legitimately contains dozens of `gh` and `jq`
invocations. Instead: create `$X/stub/gh` and `$X/stub/jq`, each a `#!/bin/sh` script that
does `touch "$X/PREFLIGHT_RAN"` and `exit 1`, `chmod +x` them, then run
`( PATH="$X/stub:$PATH"; hrun "$X" -- --pr-loop=true "$t" )` — a subshell so the stubbed
`PATH` reaches `hrun`'s `env -i PATH="$PATH"`. Assert: exit 0, `cfg_pr_loop` reads `true`,
the glue is stamped, and **`$X/PREFLIGHT_RAN` does not exist**. This fails the moment anyone
adds an install-time `gh`/`jq` probe. (Precedent: `tests/test_pr_loop.sh:1642` already guards
the same boundary for `init.sh` — `grep -qE '\bgh\b|\bjq\b' "$SRC/init.sh" && fail`. That file
has no generated body, so a grep works there; this one does, so it does not.)

> **Deliberately NOT automated:** "`tests/test_install.sh` and `tests/test_pr_loop.sh` are
> unmodified" is a property of **this PR's diff**, not of the repo forever. A permanent-suite
> check that diffed them against `main` would be meaningless the moment this merges and would
> break every later feature that legitimately touches them — the exact anti-pattern this repo
> has hit three times. The Reviewer asserts it by reading the PR diff (see the by-hand
> checklist).

**`version_and_changelog` (R15)** — extend E20-F01's existing check: `VERSION` parses as
semver, `CHANGELOG.md` carries a `## [<VERSION>]` heading, and a stable marker for **this**
feature (`--pr-loop` or `pr_loop.enabled` prompt) appears **somewhere** in `CHANGELOG.md`, not
coupled to the top section. Never freeze the literal version string and never compare against
a hard-coded previous version — the MINOR-vs-PATCH judgement is the Reviewer's.

## Behavioral / end-to-end checks (Reviewer, by hand)

These cover the `read -r` plumbing that no POSIX suite can drive.

- From a real terminal, run the installer interactively into a scratch repo. Confirm the
  order: front-end picker → builder-backend prompt → PR-loop prompt, each unchanged from the
  last release except for the new third one.
- Press Enter ⇒ `.harness/harness.config.yaml` reads `enabled: false` and **no**
  `/sdd-pr-loop` glue exists anywhere (including `$CODEX_HOME/prompts/`).
- Re-run interactively, answer `2` ⇒ the file reads `enabled: true`, `/sdd-pr-loop` and
  `pr-fixer` are stamped into the selected front-ends, and every comment in the file is still
  present.
- Re-run interactively a third time and confirm the prompt now offers **`true`** as the
  default (pre-selected from the current value); press Enter ⇒ the file is unchanged and the
  glue stays.
- Re-run and answer `1` ⇒ the file reads `false` and the glue is reclaimed **in that run**.
- Answer with garbage (`xyzzy`) ⇒ the current value is kept and the installer proceeds; it
  does not loop or abort.
- Ctrl-C at the PR-loop prompt leaves the terminal usable (this prompt never enters raw mode).
- Run the same install through a terminal where raw mode is unavailable (so the numbered
  `toggle_select` fallback is used for the picker) and confirm both follow-up prompts are
  identical.
- **Read the PR diff and confirm `tests/test_install.sh` and `tests/test_pr_loop.sh` are not
  in it** (R14) — the check deliberately left out of the permanent suite.

## Non-functional checks

- Lint: `verification.lint_command` is empty — n/a. The installer must stay POSIX `sh` with
  zero dependencies, and must not *itself* invoke `gh` or `jq` (the generated `/sdd-pr-loop`
  body legitimately does — that is loop runtime, not install time; see
  `no_install_time_preflight`).
- Types: `verification.typecheck_command` is empty — n/a.
- `./init.sh` exits 0 in the harness source repo and in an installed target.
