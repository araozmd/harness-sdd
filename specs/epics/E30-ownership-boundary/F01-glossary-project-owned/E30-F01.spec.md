# `specs/glossary.md` becomes project-owned — Functional Spec

> R-ids in this document are `R1 … R12`; their fully-qualified form is `E30-F01:R1 …
> E30-F01:R12`. `.plan.md`, `.tasks.md` and `.tests.md` cite the short form.

## Context

`harness-install.sh:703` lists `specs/glossary.md` in `HARNESS_BODY_PROSE`, so every run of
the installer overwrites `<target>/.harness/specs/glossary.md` with the shipped example —
chatbot-handoff terms for an unrelated domain. Every other authority in the harness says the
file belongs to the project: its own second line invites the edit ("Add terms as the project
grows"), `agents/planner.md:51-55` pairs it with `specs/product.md` as the project's term
index, `docs/SPEC-FORMAT.md:16` files it under the project's domain model, and the
installer's **own header** (`harness-install.sh:59-62`) enumerates both ownership classes
and puts `specs/glossary.md` in **neither**.

This is not theoretical. On 2026-09-16 an upgrade of `previta/protocolos` to v0.79.0
destroyed a 90-line Protocolos domain glossary (commit `9e08fe0`). The run printed no
warning; the file was recovered only because it happened to be committed.

The fix is a reclassification, not a new feature: `specs/glossary.md` leaves the harness body
and joins the seed-once/preserve class that `specs/product.md` (`harness-install.sh:3755`),
`init.project.sh` and `progress/lessons.md` (`harness-install.sh:3809`) already occupy, with
a byte-identity comparison against the shipped example so a never-touched install still
tracks the example.

### Why `complexity: complex`

Four of `agents/architect.md`'s stated bases hold; this is the basis, not a feeling.

1. **It lands exactly on the size budget** — 12 requirements against `max_requirements: 12`.
   Stated honestly: **R7, R9 and R12 are regression locks**, not new capability. R7 and R9
   exist because removing one word from `HARNESS_BODY_PROSE` silently changes four umbrella
   code paths, and a lock without a requirement is a lock the Reviewer cannot check.
2. **It honors an ADR whose constraints reach across several files** — `ADR-0004`'s tier line
   is written down in `harness-install.sh` §1, `manifest.txt`, `docs/UMBRELLA.md`,
   `docs/CONFIG-LAYERING.md`, `docs/INSTALL.md` and the seeded `harness.config.yaml` comment
   at once. Every one of them names this path today.
3. **It re-enters a defect class the harness has already paid for** — a byte contract compared
   in more than one place. `prose_tier_blockers`, `remove_if_pristine`, the skill-unit stamps
   and now the glossary comparison are four byte-identity comparisons in one script.
4. **Speccing it required resolving a contradiction between two existing components** —
   `docs/UMBRELLA.md:101` makes this path a pointer stub in a thin child, which a
   project-owned file cannot be. See *Recorded decision D1*.

## Business rules

- **Three states, one rule, no option.** On every run, for every target:
  **absent** ⇒ seed the shipped example; **byte-identical to the shipped example** ⇒ pristine,
  leave it identical to that example; **anything else** ⇒ preserve, byte for byte. There is no
  flag, no config key, no prompt and no `.dist` side file to choose between them
  (`docs/RATIONALE.md`'s ablation doctrine — this is a rule, not a preference).
- **"Pristine" means byte-identical, never identity-modulo-whitespace.** The comparison is
  `cmp`-grade byte identity against the `specs/glossary.md` that **this** installer ships. A
  trailing space is a project edit.
- **One exception, and it is the existing ownership signal.** A file at that path whose
  **first line is exactly `<!-- harness:umbrella-stub -->`** was written by the harness, not
  by the project, so it is not project content and is replaced by the shipped example. That
  sentinel is already documented (`harness-install.sh:706`) as *the only* signal used to tell
  a stub from a real body file — never file size, never a grep for prose.
- **Never destroy what the installer cannot classify (R3).** If the path exists but is not a
  regular file (a symlink, a directory), the installer preserves it and says so. It never
  unlinks, never follows, never replaces it. This is the boundary every other ownership path
  in this installer already draws.
- **Fresh installs stay byte-identical to today**, and every run is idempotent: the same
  target, run twice, ends in the same bytes with the same reported verdict.
- **The path does not move.** `agents/planner.md` and `docs/SPEC-FORMAT.md` name
  `specs/glossary.md` literally.
- **One documented owner per path.** The reclassification is not done until the installer
  header's ownership-class list, `manifest.txt`, `docs/INSTALL.md`, `docs/CONFIG-LAYERING.md`,
  `docs/UMBRELLA.md` and the seeded `harness.config.yaml` comment all agree with the code.
  Prose being out of step with `HARNESS_BODY_PROSE` is what produced this defect.

### Recorded decision D1 — a thin child owns a **real** glossary

`docs/UMBRELLA.md:101` and `ADR-0004` list `specs/glossary.md` in the stub-able prose tier.
**This feature removes it from that tier**: in every layout — single repo, coordinator,
full-copy child, thin child, `--standalone` — `.harness/specs/glossary.md` is a real,
project-owned file, and an existing pointer stub at that path is replaced by the shipped
example on the next run.

Rationale:

- "Project-owned" and "pointer stub" are contradictory by construction. A stub is content the
  harness writes and rewrites; the whole point of this feature is that the harness stops
  writing this path.
- The glossary's siblings settle it. `specs/product.md`, `specs/epics/`, `state/tasks.json`
  and `progress/` are already **real and local** in a thin child — the thin layout has only
  ever thinned the harness **body**, never the project's own content. The glossary is joining
  its siblings, not leaving its tier.
- A child repo is a separate repo because it has its own domain. One shared vocabulary across
  every child is the wrong default, and sharing remains available without a mechanism: a
  child's own glossary can reference the coordinator's in prose.
- The cost is bounded and desirable: `prose_tier_blockers` stops comparing this path, so a
  child whose only divergence is an edited glossary now **converts** under `--thin` — correct,
  because the conversion no longer touches the glossary at all (R9).
- ADR-0004's *decision rule* — "tier by consumer, not by duplication" — is untouched. What
  changes is that this path is no longer harness body at all, so the tier question does not
  reach it. See *Architecture alignment*.

### Recorded decision D2 — no seed stamp; the fail-safe is accepted and guarded

**Question.** A glossary byte-identical to v0.70's shipped example but not v0.79's reads as
"edited" under a single comparison and is preserved forever. Does that need a recorded stamp
(`.harness/.codex-skills/`, `.harness/.opencode.stamp` and `.harness/.model-agents/` are the
existing byte-copy stamp precedents)?

**Decision: no stamp in F01.** Accept the fail-safe, and add a tripwire (R12) so the
assumption it rests on cannot be broken silently.

- The residual failure is that an **untouched example stops being refreshed**. It costs
  nothing functional: the shipped glossary is illustrative prose that no code and no role
  prompt parses. The failure a stamp would prevent is strictly smaller than the failure this
  feature exists to fix.
- **Deferring the stamp is free, and only while the example does not change.** At the moment
  F01 lands, every install's glossary is byte-identical to the example of the version it last
  installed, and that example has not changed since the repo's first commit (`b9921c9`). So
  every pristine install is correctly detected by a single comparison today, and would be
  equally detectable on the day a stamp is introduced — **provided the shipped example is not
  edited first**. R12 makes editing it a loud, deliberate act rather than a silent one.
- A stamp is a **new path under `.harness/`** with its own ownership, drift-guard, manifest
  and thin-child questions — in the one epic whose subject is that every path have exactly one
  documented owner. Adding an ambiguous path here to fix a cosmetic refresh is the wrong
  trade, and it would push this feature over the size budget.
- Adding the stamp later is non-breaking; removing one is not. This is the cheapest reversible
  choice.
- **Named seam for the follow-up (E30, not F01):** if the shipped example must change, add
  `.harness/.glossary-seed` as a byte copy of the example the installer last wrote (the
  `.opencode.stamp` pattern verbatim), classify it in the manifest, and extend the pristine
  test to `identical to the shipped example OR identical to the stamp`.

**Honest consequence, stated for the approval gate:** with a single comparison, the "refresh"
arm is a no-op *within* a version and degrades to "preserve" the moment the example changes.
R2 therefore specifies what is actually observable — the outcome bytes and a distinct
**verdict** — not a refresh that no test could falsify.

**The epic criterion this partially defers, named so the gate can see it.**
`specs/epics/E30-ownership-boundary/epic.md:36-37` promises that *"a pristine install … keeps
receiving the refreshed example, so the seed is not frozen at install date"*, and the inbox
brief says the same. D2 delivers that criterion **only while the shipped example is
unchanged**: from the first version that edits the example, a pristine install *is* frozen,
because a single comparison cannot tell "pristine but older" from "project-edited" and this
feature always fails toward preserving. That deferral is the whole content of D2, R12 is the
tripwire that keeps it from happening by accident, and `.harness/.glossary-seed` is the named
follow-up that would discharge the criterion in full. A human who wants the criterion met
unconditionally should reject D2 here rather than at implementation time.

## Architecture alignment

`specs/architecture.md` **does not exist in this repository** (it was never planned with
`/sdd-plan`); this absence is recorded deliberately, and no citation is fabricated from it.
The platform ADR namespace `specs/adr/` holds four real ADRs and **is** present, so the ADR
citation rule applies. The inbox brief recorded no `ADR-NNNN` ids; the one below is added
because the design plainly touches it.

- **ADR-0004 — a child resolves the harness body through pointer stubs at the same paths:**
  **intentional divergence, recorded here.** The ADR's *Decision* enumerates
  `specs/glossary.md` among the resolvable (stub) tier. This feature **removes that path from
  the body altogether**, so it is neither tier: it becomes project-authored content that a
  child keeps locally, like `specs/product.md`. Nothing else in ADR-0004 departs — the tier
  line is still drawn by *what reads the file*, a body path is still redirected rather than
  absent, the umbrella is still located explicitly via `umbrella.root`, symlinks are still not
  used, and standalone entry still works. The divergence is one entry in the tier enumeration,
  and it is corrected because the ADR classified a file the harness should never have owned.
  Per `agents/architect.md`, the Architect records the divergence here and does **not** author
  an ADR delta; `specs/adr/0004-*.md` is on the plan's DO NOT TOUCH list as a historical record.

## Acceptance criteria (EARS)

> Each is one testable behavior with a stable id. See `docs/SPEC-FORMAT.md`.
> "The shipped example" = the `specs/glossary.md` in the running installer's own source tree
> (`$SRC/specs/glossary.md`). "The glossary" = `<target>/.harness/specs/glossary.md`.

- **R1** — When the installer runs against a target where the glossary does not exist, the
  installer shall create it byte-identical to the shipped example.
- **R2** — When the glossary exists and is byte-identical to the shipped example, the
  installer shall leave it byte-identical to the shipped example and report the **pristine**
  verdict, distinct from the preserved verdict of R3.
- **R3** — If the glossary exists, differs from the shipped example by at least one byte, and
  its first line is not the umbrella stub sentinel, then the installer shall leave it exactly
  as found — byte-for-byte when it is a regular file, and **neither followed, unlinked nor
  replaced** when it is not (a symlink, a directory) — and report the **preserved** verdict.
- **R4** — When an upgrade runs against a target whose glossary was deleted after a previous
  install, the installer shall re-seed it byte-identical to the shipped example.
- **R5** — The installer shall print exactly one glossary verdict line per target per run, on
  stdout, naming the path `specs/glossary.md` and the outcome it took.
- **R6** — When the installer is run a second time against an unchanged target, the second run
  shall leave the glossary byte-identical to what the first run left, report the same verdict,
  and create no additional file at or beside that path.
- **R7** — The installer shall never write, overwrite, delete or stub the glossary from a
  harness-body path: not in the single-repo arm, not under `--standalone`, not in the thin
  maintenance arm, and not in the full-copy-child arm.
- **R8** — Where the target resolves an umbrella (the thin body layout), the installer shall
  leave the glossary a real file whose first line is not the umbrella stub sentinel —
  replacing a stub found at that path with the shipped example — and shall govern it by
  R1–R4 exactly as in a single-repo install.
- **R9** — When `--thin` is evaluated against a full-copy child whose only divergence from the
  umbrella is its glossary, the installer shall not name that path as a conversion blocker,
  shall convert the child's prose tier, and shall leave the child's glossary byte-for-byte
  unchanged.
- **R10** — The system shall classify `specs/glossary.md` as project-owned in
  `tools/harness-owned-paths.sh`, so that an uncommitted edit to it alone fails neither
  `init.sh`'s drift gate nor the installer's post-cascade landing audit.
- **R11** — The system shall describe `specs/glossary.md` as project-owned (seeded once,
  preserved on upgrade) in these six authorities — the `harness-install.sh` header
  ownership-class list, the generated `manifest.txt`, `docs/INSTALL.md`,
  `docs/CONFIG-LAYERING.md`, `docs/UMBRELLA.md` and the seeded `harness.config.yaml` comment —
  and **none of those six** shall list it as harness-owned body or as a stub-able prose-tier
  path. **Historical records are explicitly outside that set** — ADRs, already-shipped
  `CHANGELOG.md` entries and already-shipped feature specs record what was true when they were
  written and are never retro-fitted (see the plan's DO NOT TOUCH list).
- **R12** — If the bytes of the shipped `specs/glossary.md` change, then `tools/run-tests.sh`
  shall fail with a message that states that every pristine install would silently stop
  tracking the example and that names the `.harness/.glossary-seed` stamp follow-up recorded
  in D2.

## Out of scope

- Moving or renaming `specs/glossary.md` — `agents/planner.md` and `docs/SPEC-FORMAT.md` name
  that path literally.
- Any config key, CLI flag, prompt or `.dist` side file to select the behaviour.
- Auditing the other `HARNESS_BODY_PROSE` members — the epic names `specs/_templates/` as the
  next suspect. That is a follow-up under E30, seeded only if an audit substantiates it, and
  the brief's third open question is answered: **F01 fixes the proven instance alone.**
- Recovering glossaries already destroyed by past upgrades.
- The `.harness/.glossary-seed` stamp (D2's named seam) and any per-file "offer this rule to
  other body files" generalisation — per-file classification is the correct granularity while
  exactly one file has field proof.

## Open questions

- None outstanding. The brief's two design forks are answered in *Recorded decision D1* (thin
  children own a real glossary) and *Recorded decision D2* (no stamp, fail-safe accepted,
  guarded by R12); the third (blast radius) is answered under *Out of scope*.
- **For the approval gate:** D2 is the one decision a human may want to overturn. Overturning
  it adds roughly two requirements and a new `.harness/` path, which takes this feature over
  `change_size.max_requirements` and should be a separate E30 feature rather than an
  amendment to this one.
