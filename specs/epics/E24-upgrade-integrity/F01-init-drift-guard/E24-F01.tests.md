> Every R-id maps to a concrete, executable test. All tests live in
> `tests/test_init_drift_guard.sh` and are auto-discovered by `sh tools/run-tests.sh`.

## Fixture shape
Each case builds a real target: `mktemp -d`, `git init`, then
`CODEX_HOME="$T/ch" HOME="$T/home" sh "$SRC/harness-install.sh" "$T"`, then a commit of
everything the installer wrote. From there each case perturbs exactly one thing and runs
`sh "$T/.harness/init.sh"`, capturing stdout+stderr and the exit code.

This is a **behavioral** suite, not a prose-grep suite. The feature is executable logic in
`init.sh`, so — unlike the doc-and-contract features that `test_drift_check.sh` and
`test_architect_adr.sh` verify by required-phrase grep — assertions run the gate and read
its exit code.

## Anti-tautology requirements
Three of these requirements assert an **absence** (R6, R7 silent skip) or a **pass**
(R4, R10). An assertion of absence is satisfied by a guard that does nothing at all, so
each one is paired with a positive control proving the guard was live and would have fired:

- **R6** — the same target, same perturbation (a modified `.harness/agents/builder.md`),
  asserted **twice**: with `.harness-version` present ⇒ fails; with it removed ⇒ passes
  silently. Only the stamp differs. A guard keyed on the `*/.harness` suffix instead of
  the stamp passes the second assertion and fails this pair.
- **R7** — install into a target, commit, modify a harness-owned file, assert failure;
  then `rm -rf .git` and assert silent pass. Only git-ness differs.
- **R4** — in one target, assert that modifying `.harness/harness.config.yaml` alone
  passes **and** that modifying `.harness/agents/builder.md` in the same tree fails. A
  guard that excludes everything passes the first and fails the second.
- **R10** — the clean-pass assertion is paired with R2's failure on the same fixture, so
  "passes" is not reachable by a guard that never runs.

Rationale: an expected value with more than one producing code path proves nothing (this
has recurred in this repo — see `progress/history.md`, E99-F07).

## Specific assertions worth naming
- **R9 ordering** — build a target whose `.harness/` exists but is entirely **untracked**
  (install, then `git init` but never `git add`). Assert exit **zero** and a warning. This
  is the case that fails if the implementation runs `git status` before `git ls-files`:
  `git status --porcelain -- .harness/` reports `?? .harness/`, which a status-first
  implementation reads as drift and hard-fails. The test exists to pin the order.
- **R3 cap** — perturb more than 10 harness-owned files, assert the output contains at
  most 10 path lines and contains `git` + `status --porcelain` as the listing command.
- **R5** — perturb `.claude/agents/builder.md` (a root-level generated file, not under
  `.harness/`) and assert failure. Guard against an implementation that only ever looks
  inside `.harness/`.
- **R8** — assert both that the drifted target passes under
  `HARNESS_SKIP_DRIFT_CHECK=1` **and** that the output contains a skip line. A silent
  skip fails this test.

## Suite-wide constraints
Carried from the existing suites (`tests/test_drift_check.sh` header documents the same
list; these have recurred repeatedly in this repo):

- Never assert an exact `VERSION` literal — read it at runtime if needed at all.
- Never couple a `CHANGELOG.md` assertion to the current top version; grep the whole file
  for the feature marker.
- Never `git diff` a DO-NOT-TOUCH file against `main`.
- Never mutate the live `state/tasks.json`, `specs/`, or `progress/` — every fixture is
  under its own `mktemp -d`.
- Sandbox `CODEX_HOME` **and** `HOME` on every `harness-install.sh` invocation, for the
  whole suite.

## Non-functional checks
- Full suite green: `sh tools/run-tests.sh` (not just the new file — `init.sh` is on the
  hot path of several other suites).
- `bash -n init.sh` parses clean.
- The clean-target path adds at most two `git` invocations per `init.sh` run.
