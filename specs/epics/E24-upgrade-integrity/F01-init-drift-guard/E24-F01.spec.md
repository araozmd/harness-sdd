# `init.sh` drift guard: refuse to run on an unlanded harness — Functional Spec

## Context
`harness-install.sh` stamps `VERSION` into `<target>/.harness/.harness-version`
(`harness-install.sh:2194`). Exactly one caller reads it: the *next* installer run,
deciding upgrade-vs-fresh (`harness-install.sh:1794`). At runtime it is dead metadata —
`init.sh` contains no reference to the stamp, to `VERSION`, or to whether the installed
body is committed.

The consequence is that an upgrade written but never landed is indistinguishable, at
runtime, from one that was landed. The v0.50.x cascade across five `~/repos/viernes`
children left 26–29 uncommitted files in each. Every Builder and Reviewer spawned there
since has read agent prompts that no commit records; three children ran the change-size
classifier against a committed `harness.config.yaml` with no `change_size` block while
`migrate_config()` had already appended that block to the working tree. Nothing failed.

This feature makes `init.sh` — the gate every agent runs before every piece of work
(`AGENTS.md` rule 1) — notice. It is the consumer-side half of the fix; E24-F02 closes the
producing side.

## Business rules
- **The guard reports; it never repairs.** No auto-commit, no auto-reinstall, no writes of
  any kind. A gate that mutates the repo to satisfy itself has stopped being a gate.
- **Ownership decides scope, not diff size.** Only harness-owned paths count. Project-owned
  paths (`harness-install.sh:2245`) are *expected* to differ every session; a guard that
  trips on them would be disabled within a week.
- **False positives are the dominant risk.** `init.sh` runs before every agent step, so a
  misfire halts the whole harness. Every ambiguous case degrades to silence or a warning,
  never to a failure.
- **Skipping is loud; inertness is silent.** A target where the guard cannot apply (no
  install, no git) says nothing. An operator who *overrides* the guard is told they did.

### Resolved during specification
The brief asked whether a version-stamp mismatch is a second check with its own severity.
It is not, and this is a genuine simplification worth recording: `.harness/.harness-version`
is itself a **tracked file inside the harness-owned tree**, and every upgrade rewrites it.
A half-applied upgrade therefore shows up as an uncommitted change to the stamp *by the
same dirty-tree check* that catches the prompts. There is no second signal available at
runtime — `init.sh` has no access to the harness *source* it was installed from, so it
cannot compare "installed version" against "latest version" at all. One check, not two.

## Acceptance criteria (EARS)

- **R1** — Where `init.sh` is running from an installed harness (its own directory ends in
  `/.harness` and `.harness-version` exists beside it) and the project root is inside a git
  work tree, the system shall check the harness-owned paths for uncommitted changes.
- **R2** — If any harness-owned path has an uncommitted change — modified, staged, or
  untracked — then the system shall fail the gate with a non-zero exit and a message that
  names the number of drifted paths and states that the installed harness is not committed.
- **R3** — The failure message shall list the drifted paths, capped at a bounded number,
  and when the cap elides any path it shall print the git command that lists them all.
- **R4** — The system shall exclude the project-owned paths — `harness.config.yaml`,
  `init.project.sh`, `specs/product.md`, `specs/epics/`, `state/`, `progress/` — from the
  check, so an uncommitted change confined to those never fails the gate.
- **R5** — The harness-owned paths the system checks shall include both the installed body
  under `.harness/` and the generated front-end glue at the project root
  (`.claude/agents/`, `.claude/commands/`, `.agents/`, `.codex/agents/`, `.gemini/agents/`,
  `opencode.json`).
- **R6** — Where `init.sh` is not running from an installed harness (no `.harness-version`
  beside it — the self-hosted source checkout), the system shall skip the check and print
  nothing about it.
- **R7** — Where the project root is not inside a git work tree, the system shall skip the
  check and print nothing about it.
- **R8** — If the environment variable `HARNESS_SKIP_DRIFT_CHECK` is set to a non-empty
  value, then the system shall skip the check and print one line stating that the drift
  check was skipped by request.
- **R9** — Where every harness-owned path is untracked or ignored by git (the installed body
  is not version-controlled at all), the system shall print a warning that drift cannot be
  verified and shall not fail the gate.
- **R10** — When the check runs and finds no drift, the system shall print one success line
  and allow the gate to continue to its remaining checks.

## Out of scope
- Any change to what `harness-install.sh` writes or when — E24-F02.
- Any change to where the harness body lives — E24-F03.
- Auto-committing, auto-repairing, or re-running the installer.
- Comparing the installed version against the harness source's `VERSION` — impossible at
  runtime, see *Resolved during specification*.
- Single-target vs umbrella distinction: the guard is per-target and behaves identically in
  both; the umbrella's own `.harness/` is just another installed target.

## Open questions
None blocking. The brief's two open design questions resolved during specification: the
stamp check collapses into the dirty check (above), and the escape hatch is an environment
variable rather than a flag because role prompts invoke a bare `./init.sh` and cannot pass
one.
