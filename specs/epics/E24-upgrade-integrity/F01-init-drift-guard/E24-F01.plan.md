# `init.sh` drift guard — Technical Plan

## Stack
POSIX-compatible bash (`init.sh` is already `#!/usr/bin/env bash`, `set -euo pipefail`)
plus `git`. No new dependencies — consistent with the harness's "minimal tools" rule.

## Where the check lives
A new numbered section in `init.sh`, placed **immediately after section 1** (structural
checks) and **before section 2** (TaskStore validation). Rationale (R1, R10): the
structural checks prove the files exist; the drift check proves they are the *committed*
files. Everything after section 1 — schema validation, the ADR sweep, the project hook —
reads harness-owned files, so drift must be reported before any of them produce output
that an operator might act on.

## Resolution of "is this an installed harness?" (R1, R6)
`init.sh` already computes both roots at `init.sh:14-18`:

```sh
HARNESS_DIR="$(CDPATH= cd -- "$(dirname -- "$0")" && pwd)"
case "$HARNESS_DIR" in
  */.harness) PROJECT_ROOT="$(dirname "$HARNESS_DIR")" ;;
  *)          PROJECT_ROOT="$HARNESS_DIR" ;;
esac
```

Reuse them verbatim. The installed-harness test is `[ -f "$HARNESS_DIR/.harness-version" ]`.

**Do not** key the test on the `*/.harness` suffix alone. In this repo `HARNESS_DIR` is the
source checkout and there is no stamp, so the stamp is the discriminator that makes the
guard inert here (R6) — but the suffix and the stamp are two different facts and the tests
must not be able to pass on the wrong one (see `.tests.md` → *Anti-tautology*).

## The path set (R4, R5)
Expressed as an **exclusion inside `.harness/` plus an inclusion list at the project root**,
never as an enumeration of the ~29 owned files. Enumerating the owned set would duplicate
`harness-install.sh`'s knowledge in a second place and drift from it on the next feature
that adds a body file; the project-owned set is short, stable, and already documented at
`harness-install.sh:2245`.

Git pathspecs, evaluated from `PROJECT_ROOT`:

```
.harness/
:(exclude).harness/harness.config.yaml
:(exclude).harness/init.project.sh
:(exclude).harness/specs/product.md
:(exclude).harness/specs/epics/
:(exclude).harness/state/
:(exclude).harness/progress/
.claude/agents/ .claude/commands/ .agents/ .codex/agents/ .gemini/agents/ opencode.json
```

Notes:
- `umbrella.manifest.yaml` at the project root is project-owned and is simply never listed.
- `.harness/telemetry.jsonl` needs no exclusion — the installer seeds `.harness/.gitignore`
  for it, so it is invisible to `git status` already. Do not add a redundant exclusion; a
  reader would reasonably infer the file is otherwise tracked.
- Root-level inclusions are listed unconditionally. `git status --porcelain -- <pathspec>`
  does not error on a pathspec that matches nothing, so an install that selected only one
  front-end needs no conditional path filtering. **Verify this before relying on it** — it
  is the one assumption in this plan that a git version could falsify.

## The check itself (R2, R9)
Two git invocations against `git -C "$PROJECT_ROOT"`, **in this order**:

1. `git ls-files -- <pathspec>` — how many harness-owned paths are tracked at all.
   **Zero ⇒ R9**: warn that drift cannot be verified, and stop there.
2. `git status --porcelain -- <pathspec>` — non-empty ⇒ drift (R2, R3); empty ⇒ R10.

**The order is load-bearing, not stylistic.** In a repo where nothing is tracked,
`git status --porcelain -- .harness/` reports `?? .harness/` — non-empty. Running `status`
first would classify an un-version-controlled install as *drift* and hard-fail it, which is
precisely the false positive R9 exists to prevent. Verified against git 2.55.0; both
behaviors (the `??` on the untracked directory, and `ls-files` returning zero) are
reproduced in the test suite so a future refactor that swaps the order fails loudly.

Verified likewise: `:(exclude)` pathspecs suppress project-owned files correctly, a
pathspec matching nothing is not an error, and an untracked file inside a tracked tree
reports as `??`. That is the whole implementation; resist adding a third invocation.

## Failure output (R2, R3)
```
❌ init: the installed harness is not committed — 29 harness-owned path(s) differ from
   what this branch records. Agents would run on a body no commit describes.
     .harness/agents/builder.md
     … 9 more …
   List them:  git -C <root> status --porcelain -- <pathspec>
   Land them, or re-run with HARNESS_SKIP_DRIFT_CHECK=1 to proceed anyway.
```
Uses the existing `fail()` helper (`init.sh:21`) for the final line so the exit contract
and the `❌ init:` prefix stay uniform.

## Escape hatch (R8)
`HARNESS_SKIP_DRIFT_CHECK` — a per-invocation environment variable. Chosen over a CLI flag
because role prompts invoke a bare `./init.sh` and cannot pass one; chosen over a
`harness.config.yaml` key because a config key gets set once during a bad afternoon and
silently disables the guard forever. Under `set -u` the read must be `${HARNESS_SKIP_DRIFT_CHECK:-}`.

The skip prints one line (R8) rather than staying silent — an overridden gate that says
nothing is a gate nobody remembers overriding.

## DO NOT TOUCH

## Risks
- **False positive halts the harness.** Mitigated by the exclusion list (R4) and by every
  ambiguous case degrading to skip/warn (R6, R7, R9). This is the risk to weight above all
  others in review.
- **Linked worktrees.** `git -C "$PROJECT_ROOT" status` is correct inside a linked worktree
  without special handling — unlike the board path, which needed `HARNESS_DIR` remapping
  (see the precedence commentary at the top of `tools/tasks-lock.py`) because it must reach
  the *canonical* board. Drift is a property of *this* working tree, so no remapping is
  wanted. Stated explicitly because the adjacent problem was solved the opposite way and a
  reviewer will reasonably ask.
- **Cost on the hot path.** Two `git status`/`ls-files` calls over a bounded pathspec, once
  per `init.sh`. Acceptable; do not add a cache.
