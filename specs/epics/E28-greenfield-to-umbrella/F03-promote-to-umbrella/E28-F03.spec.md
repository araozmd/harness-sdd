# Installer promotion — Functional Spec

## Context

There is no supported path from a single-target install to an umbrella coordinator.
`--umbrella` only **discovers** existing depth-1 git children; it never creates one. So once
E28-F02's `/sdd-plan` says "three repos" and writes
`.harness/umbrella.manifest.draft.yaml`, the owner is back to hand-creating directories,
`git init`-ing them, copying the manifest and re-running the cascade — the exact toil this
epic exists to remove. This feature adds **promotion**: one installer invocation turns the
existing single install into the coordinator, creates each missing child from the draft,
runs the optional opaque `scaffold_cmd` inside the ones it creates, re-bases the draft's
`path:` values into the live root manifest, and then reuses the existing cascade (child
install, manifest population, landing audit). The user is the harness owner who has just
planned a multi-repo product.

**Complexity: `complex` (E17-F03, routes round 1 to `builder-heavy` per ADR-0002).** Two of
the stated bases apply:
1. *It presses the change-size budget.* It carries 11 R-ids against
   `change_size.max_requirements: 12`; it nearly split, and the seams (creation vs
   manifest transform vs docs/tests) are decomposition decisions, not spec-writing ones.
2. *The plan names a defect class this harness has already paid for — "the same fact in two
   places".* The draft's `path:` base (the harness directory, `.harness/`, so
   `../<child>`) and the live manifest's base (the umbrella root, `./<child>`) express the
   same filesystem location, and E28-F02's resolved Q1 flagged the re-base as a promotion
   obligation (R3). The feature also has to keep a never-promoted single install
   **byte-identical** to a plain cascade's child result (R7, R10) — the body-and-copy
   divergence class `progress/lessons.md` records.

## Business rules

- **Promotion is explicit and inert by default.** It runs only when `--from-manifest` is
  passed with `--umbrella`. Without it, single-target mode and the plain `--umbrella`
  cascade behave exactly as today; the draft file's presence is never a switch.
- **The live manifest is the switch.** Promotion seeds `<umbrella>/umbrella.manifest.yaml`
  and the cascade points `umbrella.manifest` at it, exactly as the existing cascade does.
  The draft stays derived and project-owned.
- **Reuse the cascade; never reimplement it.** Promotion creates the missing children and
  seeds the live manifest; the existing depth-1 discovery, child install, manifest
  upsert, and landing audit do the rest ("reimplementing a tool invites a bug per feature",
  `progress/lessons.md`). No new `/sdd-*` command, config key, status value, or tool.
- **Local git only.** Promotion runs `git init` on the children it creates; it never adds a
  remote, a branch protection, or Codex App setup. The promotion documentation states this
  and names the remote work the human still owes.
- **`scaffold_cmd` is opaque.** The harness never interprets it; only promotion runs it,
  only inside a child it just created, best-effort and named loudly on failure.
- **Every gate fails closed.** A missing/invalid manifest, a child path outside the
  umbrella, a path the cascade cannot discover, a declared child that already exists but is
  not a git work tree, or an unlanded child aborts non-zero with the path named. A gate
  that fires writes nothing before it fires.
- **The installer never writes git state.** Promotion never stages, commits, or branches;
  the existing landing audit (exit `3`, never commits) is the gate — there is no separate
  dirty-tree refusal (see the resolved Q2 below).
- **The root keeps its own board.** The promoted root's `.harness/state/tasks.json`,
  `specs/`, `progress/` and config values are carried over, so the root's board remains the
  umbrella board; promotion writes no child-local board.

## Architecture alignment

- ADR-0001 — next() selection is deterministic code: promotion only seeds the manifest the
  existing `tools/next-task.mjs` reads; it changes no routing, no gate and no reason-string
  vocabulary. A draft that is never promoted is inert.
- ADR-0004 — a child resolves the harness body through pointer stubs and *no umbrella is
  not a broken environment*: promotion reuses the cascade's child install, so a created
  child records `umbrella.root` exactly as a discovered one does (R5); a single install that
  never promotes keeps its full local body and standalone entry unchanged (R10); local git
  only, with no implicit remote, honors the decision's "explicit, boring" stance.

## Acceptance criteria (EARS)

- **R1** — When `--umbrella <dir>` is combined with `--from-manifest <file>`, the installer
  shall enter promotion mode against the existing single-target install at `<dir>`. It
  shall reject `--from-manifest` non-zero **before any write** when used without
  `--umbrella`, in single-target mode, with an empty value (`--from-manifest=` or a missing
  argument), or together with `--self`, `--standalone`, `--thin`, or `--print-agents`; when
  `--from-manifest` is given it shall refuse non-zero if `<dir>` holds no existing install
  (no `<dir>/.harness/.harness-version`), naming the target. A plain `--umbrella` run
  without `--from-manifest` shall still accept a fresh directory. `--dry-run` and
  `--shared-repo` shall compose with promotion. The invocation shall be documented on
  `harness-install.sh`'s usage header, `docs/UMBRELLA.md`, and `docs/INSTALL.md`, with the
  composition and the fail-closed boundaries stated in `docs/UMBRELLA.md`.

- **R2** — If the named manifest is missing, unreadable, or has no non-empty top-level
  `repos:` mapping, then the installer shall abort non-zero before creating or writing
  anything, naming the manifest path and the reason.

- **R3** — Promotion shall re-base every entry's `path:` from the draft manifest's own
  directory (the harness directory, `.harness/`) to the live manifest's directory (the
  umbrella root), so each child resolves to the same filesystem location — `../<child>` in
  the draft becomes `./<child>` in the live manifest — and the live entry carries the
  entry's `init`, `test_command`, `delegate_cmd` and optional `scaffold_cmd` unchanged.

- **R4** — If an entry's `path:` resolves outside the umbrella root, does not name a direct
  child directory whose basename **equals the entry's `repos:` key** and matches
  `^[a-z0-9-]+$`, or names an existing path that is not a directory or not a git work tree
  (`<dir>/.git` absent), then promotion shall abort non-zero before creating or writing
  anything, naming the offending path, the reason, and the remedy (rename the directory to
  the key, or re-run `/sdd-plan` to reconcile the draft).

- **R5** — When an entry names a child directory that does not yet exist, promotion shall
  create it and initialise a local git repository in it (no remote); the existing cascade
  shall then install the normal child profile into it. Before the cascade runs, promotion
  shall seed the live root manifest (`<umbrella>/umbrella.manifest.yaml`) with one `repos:`
  entry per manifest-declared deployable, keyed by the entry's key and carrying the re-based
  `path`, without overwriting an entry that already exists under `repos:` — a pre-existing
  key is preserved verbatim, so promotion must run **before** a plain cascade on the same
  root if the draft's fields are to reach the live manifest.

- **R6** — Where an entry carries a non-empty `scaffold_cmd`, promotion shall run it inside
  the child it just created as an opaque best-effort command, and shall **not** run it for a
  child that already existed. On a non-zero exit it shall print a warning naming the child
  and the command to **stderr** and continue, so the child still receives a valid harness
  install; the harness shall never interpret the command.

- **R7** — While every manifest-declared child already exists and is a git work tree,
  promotion shall create no directory, run no `scaffold_cmd`, and neither duplicate nor
  overwrite an existing manifest entry, so a re-run leaves each child's installed harness
  byte-identical to the same child's result under a plain `--umbrella` cascade.

- **R8** — Where `--dry-run` is combined with promotion, the installer shall preview every
  child it would create and `git init`, every `scaffold_cmd` it would run, and every `path:`
  it would re-base, and shall write nothing (no directory, no `.git`, no live manifest, no
  harness body).

- **R9** — After promotion, the existing landing audit shall run over the coordinator and
  every child the run touched; it shall exit `3` naming each target whose harness-owned paths
  are unlanded, report a target that is not a git work tree without counting it as unlanded,
  and commit nothing. Promotion shall add no other git-state gate: a target that is already
  dirty — including the uncommitted state a previous promotion left — shall remain
  promotable, and the audit shall be the gate.

- **R10** — The installer's single-target behavior and its plain `--umbrella` cascade
  (without `--from-manifest`) shall run no promotion step and create no child from a draft;
  a single install that never promotes shall carry no live manifest, and the existing
  single-target and cascade contracts (`tests/test_install.sh`, `tests/test_cascade.sh`)
  shall stay green.

- **R11** — When promotion converts an existing single-target install into the coordinator,
  the installer shall carry over the target's project-owned state unchanged —
  `state/tasks.json`, `specs/`, `progress/`, and config values — so the root's own board
  remains the umbrella board (the draft epics and later slices live there) and promotion
  writes no child-local board.

## Out of scope

- GitHub remotes, branch protection, Codex App, and any language/framework scaffolding
  logic — the harness owns none of `scaffold_cmd` (E28 epic non-goals).
- Reimplementing discovery or child install: the existing depth-1 discovery, `install_one`
  child path, `manifest_upsert`, `set_umbrella_root`, and `audit_one` are reused unchanged.
- The Planner's topology rule and the draft artifact (E28-F02, done); the greenfield
  single-repo documentation path (E28-F01, done).
- Any change to `tools/next-task.mjs`, `init.sh`, `store/`, `harness.config.yaml`'s shipped
  `umbrella.manifest: ""`, the `--thin`/`--standalone` layout logic, or `agents/*.md`.
- Any new `/sdd-*` command, status value, or interactive prompt.

## Open questions — resolved in this spec (the human gate may overturn)

- **Q1 — Coordinator conversion and the board.** **Resolved: the promoted root keeps its own
  `.harness/state/tasks.json` as the umbrella board.** The root is upgraded by the ordinary
  install/upgrade path, which preserves every project-owned path (`state/`, `specs/`,
  `progress/`, config values), so the draft epics `/sdd-plan` seeded there stay there and
  later cross-repo slices are written into that board exactly as the coordinator loop
  expects. Children get their own fresh child-local boards; the coordinator seeds a child's
  slice state at dispatch time (`docs/UMBRELLA.md`), not at promotion. Promotion writes no
  slices and no child board. This is R11.
- **Q2 — Should promotion refuse a dirty working tree, given the landing audit?**
  **Resolved: no separate dirty-tree refusal; the landing audit is the gate.** Promotion
  never commits, so it *always* leaves the targets uncommitted — a refusal would reject the
  very state its own prior run creates and make idempotent re-run impossible (R7). The audit
  scopes to harness-owned paths and exits `3` naming unlanded targets, so pre-existing
  unrelated work elsewhere is not misattributed, and a pre-existing uncommitted harness edit
  is correctly reported. This is R9.
- **Q3 — The draft's `path`/key split and the cascade's name-keyed discovery.**
  **Resolved: promotion requires each entry's re-based child basename to equal its `repos:`
  key and match `^[a-z0-9-]+$` (R4).** The reused cascade discovers children by directory
  name and `manifest_upsert` keys them by that same name, so a key/directory divergence
  (E28-F02's `api-v2` / `path: ../api.v2` form) would create a duplicate or inconsistent
  live entry, and a non-key directory would be created and then silently skipped — a
  half-wired child. Promotion refuses the shape up front, naming the path, rather than
  produce that. The coordinator runtime still supports the split for hand-maintained
  manifests; only promotion requires the aligned, cascade-discoverable shape. This
  **qualifies E28-F02's hand-off note** that "F03 consumes whatever draft exists": F02 can
  emit a draft whose `path` basename is dotted or uppercase (a valid coordinator-runtime
  split) that promotion refuses, so the remedy is a `/sdd-plan` amend (or renaming the
  directory) before promotion.
