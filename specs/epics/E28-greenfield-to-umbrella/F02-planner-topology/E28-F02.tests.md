# Planner topology output — Test Contract

> The traceability matrix: every `R-id` in `E28-F02.spec.md` maps to a concrete, executable
> test. The Reviewer fails the feature if any `R-id` lacks a passing test.
>
> **Conventions inherited from the suites this one sits beside** (read them before writing):
> zero dependencies; POSIX `sh` only — `tools/run-tests.sh` executes every suite under the
> strictest shell it can probe, and `local` / `[[ ]]` / arrays parse fine under `dash` and
> fail at runtime; each suite builds its fixture under its own `mktemp -d` and never touches
> `state/`, `specs/`, `progress/`, or the developer's `~/.codex`; `fail()` messages state the
> **consequence**, not just the symptom.
>
> **Constants discipline (`progress/lessons.md`).** No test below asserts a literal
> `VERSION`. Every string a test greps is a pinned anchor named in `E28-F02.plan.md`
> §"Docs/platform content contract" and shipped verbatim by `E28-F02.tasks.md`. Any span a
> test extracts is bounded **structurally** (a `## ` heading → the next `## `; the
> `cat > "$CMDDIR/sdd-plan.md"` heredoc → its closing `^EOF$`), asserted non-empty, and
> given a line-count floor — never bounded on a line that happens to be last today.
>
> **Positive controls are mandatory.** Every ordering claim asserts both anchors are
> present first; every negative is paired with a positive shape from the same extraction, so
> a predicate that can match nothing cannot pass as a test.

### R2 — `test_role_and_body_name_the_draft_and_keys`
- In both the role span (as R1) and the emitted command-body span (as R8), assert the
  anchor `umbrella.manifest.draft.yaml` and the key anchors `path`, `init`,
  `test_command`, `delegate_cmd`, `scaffold_cmd` are present.
- Assert the shape sentence states one entry **per deployable** (`one` + `per deployable`
  in the same folded span), so "a manifest" without the per-deployable rule reds.
- **Coordinator-grammar key rule (Reviewer finding 4043038790).** On **every** surface the
  step lives on (role, emitted body, `.claude/commands`, `.agents/skills`), isolate the
  sentence naming `logical name` (positive control) and require it to carry
  `[a-z0-9-]+` (the slice-id suffix grammar — `store/tasks.schema.json` and
  `tools/next-task.mjs`'s `SLICE_RE` both end slice ids in `[a-z0-9-]+`, so an underscore
  or uppercase key cannot be referenced by a schema-valid slice), the worked example
  `api-v2`, `directory` and `path` — the key is a coordinator-safe logical name and
  the actual directory lives in `path`. Keying by a dotted directory (`api.v2`) is a
  `malformed repos entry` the coordinator refuses, and a hand-edit that drops the rule on
  one surface must red there (the R8 full-anchor-set lesson). The fixture's draft keys its
  third deployable `api-v2` with `path: ../api.v2`, so the run-2 coordinator parse also
  proves a slice-grammar key + dotted directory is accepted.
- **Collision-safe keys (Reviewer findings 4043129416 and 4043241872).** On the same four
  surfaces, isolate the sentence naming `unique` (positive control) and require it to carry
  `normalizing`, `collide`, `-2`, `-3`, `order` and `manifestRepos` **plus** the
  full-set-probe anchors `complete set`, `already assigned` and the resolved example
  `api!` ⇒ `api-2-2` (`api`, `api!`, `api-2` allocate `api`, `api-2`, `api-2-2`) — two
  deployable names (`api.v2` and `api-v2`) normalize to one key, and `manifestRepos()`
  rejects duplicate repository keys, so the contract must allocate unique keys with a
  **stated deterministic order** that probes the complete set of keys already assigned
  (the first-incumbent rule alone re-collides when a later deployable's bare normalized
  name equals a suffix already handed out). The grammar sentence alone does not name
  `unique`, so it cannot satisfy this; the `-2`/`-3`+`order` pair in one sentence is the
  anchor for the disambiguation rule, and `manifestRepos` names the consequence. `-3` is
  pinned alongside `-2` because the worked example `api-2-2` contains `-2`, so a `-2`-only
  check survives deleting the explicit sequence; `api!` and `api-2-2` are reachable only
  through the full-set probe, so each reds on the pre-change first-incumbent text.

### R11 — `test_amend_is_append_only`
- **The defects this closes (Reviewer findings 4042914412, 4043129426, 4043241876 and
  4043241880).** A topology change is a `/sdd-plan` amend, but the amend contract is
  append-only and never rewrites the original `specs/architecture.md`; without an appended
  delta and a trigger that reads past the original section, an amendment that adds a
  deployable still sees the original one-deployable architecture and writes neither
  artifact. The amend's delta is a **complete replacement snapshot**: the latest delta
  names the full effective set and earlier deltas are superseded, so removal AND rename are
  expressible, not just add — a pure union (or a latest-wins-per-name reading) preserves a
  deployable that a later delta renamed or removed, so the `>1` trigger stays true and the
  draft keeps repositories that no longer exist. Every set-changing amend **always appends**
  the new repo-topology ADR, including a collapse to one deployable (or none) — the previous
  round's "writes no new repo-topology ADR" clause contradicted the append-only amendment
  contract — and when the effective set falls to one deployable (or none) the Planner
  additionally removes the derived draft.
- On **every** surface the step lives on (role, emitted body, `.claude/commands`,
  `.agents/skills`), each check bounded to a sentence only this rule carries:
  1. the sentence naming `topology change` (positive control) carries `/sdd-plan`,
     `amend`, `append-only`, `reconciles the draft`;
  2. the sentence naming `## Repo topology` carries `append-only`, `dated`, `delta`,
     `specs/architecture.md`, `ADR` (the append-only delta + new above-max ADR);
  3. the sentence naming `complete replacement snapshot` carries `full`, `superseded`,
     `latest delta` and `original` — the latest delta names the FULL effective set and
     earlier deltas are superseded;
  4. the sentence naming `rename` carries `add`, `remove`, `naming`, `removes` and
     `frontend` — add, remove and rename are all expressed the same way, by naming the
     resulting set (Reviewer finding 4043241876; the union wording could not express
     removal or rename);
  5. the sentence naming `effective set` carries `trigger`, `one deployable`, `removes`,
     `umbrella.manifest.draft.yaml` and `reconciles` — the trigger reads the effective
     set, and when it falls to one deployable (or none) the Planner **removes** the
     derived draft (the committed repo-topology ADRs are preserved, append-only and never
     deleted), so a consolidation/removal cannot leave a stale multi-repo draft behind;
  6. the sentence naming `collapse` carries `always`, `appends`, `repo-topology ADR`,
     `removal` and `one deployable` — every set-changing amend always appends the new ADR,
     including a collapse, so the ADR rule and the draft-removal rule agree (Reviewer
     finding 4043241880). Additionally, no sentence naming `collapse` or `effective set`
     may carry `writes no new` (the old contradictory clause), asserted as a bounded
     negative with its own positive control.
- Bounding to the sentence is load-bearing: the role/body also contains step-8's
  `append-only` remark, so a span-wide `append-only` token check would be satisfied by it
  and the amend path could be deleted with the suite green. Likewise the draft-removal
  sentence's `removes` + `one deployable` + `umbrella.manifest.draft.yaml` trio is
  asserted in **one** sentence: each token alone is satisfied elsewhere in the span
  (the no-op sentence has `umbrella.manifest.draft.yaml`, and other prose has
  `removes`/`one deployable`).
