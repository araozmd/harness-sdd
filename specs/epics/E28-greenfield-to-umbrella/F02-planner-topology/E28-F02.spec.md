# Planner topology output — Functional Spec

## Context

Repo topology (one repo vs an umbrella of N child repos) is decided by hand **before the
harness exists**, with no ADR and no artifact a tool can consume. The Planner is already
the step that writes `specs/architecture.md` and the ADRs — and that is where the
deployables are named. This feature makes the topology an explicit **output of planning**:
when the architecture names more than one deployable, the Planner also writes one
**repo-topology ADR** and a **draft manifest** on disk; when it names one (or none), it
writes neither and the run is otherwise unchanged. The draft is deliberately **inert** —
F03's promotion is what turns it into a live coordinator, so the artifact is a file F03 can
consume without an LLM. The user is the harness owner starting a new product.

**Complexity: `complex` (E17-F03, routes round 1 to `builder-heavy` per ADR-0002).** Two of
the stated bases apply:
1. *The plan names a defect class this harness has already paid for.* The `/sdd-plan` body
   is emitted from one heredoc in `harness-install.sh` and reconciled into a shared
   `.agents/skills/` unit plus source-mode `.claude/` glue; the Planner rule also lives in
   the portable `agents/planner.md`. A rule added to one surface and not the others is the
   "a body and its copy diverging" class (`progress/lessons.md`), so R8 pins all three
   surfaces to the same anchors.
2. *It must honor an ADR whose constraints reach across several files.* ADR-0003's
   one-shared-unit rule claims `.agents/skills/sdd-plan/SKILL.md` for `{codex, opencode}`
   from a single generated body, and ADR-0004's inert/standalone principle decides where the
   draft may live. Both reach across the role file, the installer heredoc and the
   reconciled glue.

## Business rules

- **Topology is an output of planning, never an input to it.** The Planner decides it from
  the architecture it just wrote; no new intake, no new prompt, no new `/sdd-*` command
  (`docs/RATIONALE.md` — never accrete).
- The **only** umbrella switch is `umbrella.manifest` in `harness.config.yaml` pointing at
  an existing manifest file. A file named otherwise, present anywhere, is inert.
- The draft is **derived, not durable**: the Planner is its single writer and may reconcile
  it on an amend run — and removes it when the effective topology falls to one deployable
  (or none); that removal is the **one carve-out** from the amend's no-deletion rule, since
  the draft is a derived, project-owned artifact and not a committed one. An amend never
  rewrites `specs/architecture.md`, an ADR, or an epic;
  a topology change is recorded **append-only** (a dated `## Repo topology` delta section
  plus a new repo-topology ADR above the maximum — always, including a collapse), and the
  topology trigger reads the **effective** deployable set from the amend's **complete
  replacement snapshot**: the latest delta names the full set and earlier deltas are
  superseded, so a renamed or removed deployable does not survive in the draft.
- The Planner **never creates a repo or directory, never runs the installer, and never
  `git init`s anything** — F03 owns promotion.
- `scaffold_cmd` is **opaque**: the harness never interprets it (only F03's promotion runs
  it), and it is optional per entry.
- `/sdd-drill` neither creates nor amends the draft; a topology change is a `/sdd-plan`
  amend.
- The draft is **project-owned for drift purposes**: `tools/harness-owned-paths.sh` excludes
  `umbrella.manifest.draft.yaml` from the harness-owned path set, so an untracked draft — the
  state between `/sdd-plan` and the planning-baseline commit that the install docs place
  after `/sdd-drill` — does not fail `init.sh`'s drift guard, while a genuine harness-body
  edit still does.
- The re-run guard and the append-only ADR/id allocation rules are unchanged; the
  repo-topology ADR is an ordinary ADR allocated above the current maximum.

## Architecture alignment

- ADR-0001 — next() selection is deterministic code: this feature adds no routing and no
  gate. The draft never sets `umbrella.manifest`, so `next-task.mjs`'s manifest gate stays
  exactly as recorded, and presence of the draft is not an implicit switch.
- ADR-0003 — one shared skill unit per command, claimed by `{codex, opencode}`: the
  `/sdd-plan` step is added once to the generated command body, so both claimants receive
  the same bytes from one writer (R8); no per-host fork of the rule.
- ADR-0004 — a child resolves the harness body through pointer stubs, and *no umbrella is
  not a broken environment*: the draft is inert and the single-repo install is untouched, so
  a project that never promotes keeps the full local body and standalone entry.

## Acceptance criteria (EARS)

- **R1** — When `specs/architecture.md` names more than one deployable, the Planner shall
  write exactly one repo-topology ADR at `specs/adr/NNNN-<slug>.md` — a single decision that
  names each repo and why it is separate — allocated strictly above the maximum existing ADR
  number (4-digit, no reuse) and referenced from `specs/architecture.md`'s ADR index by its
  `ADR-NNNN` id (the index rule **reuses** the existing Planner contract; only the ADR's
  existence, path and allocation are new).
- **R2** — When `specs/architecture.md` names more than one deployable, the Planner shall
  write a draft manifest at `umbrella.manifest.draft.yaml` in the harness directory with one
  `repos:` entry per deployable. Each entry key shall be a coordinator-safe logical name
  matching `[a-z0-9-]+` — the slice-id suffix grammar (`store/tasks.schema.json`'s
  `^E[0-9]+-F[0-9]+@[a-z0-9-]+$` and `tools/next-task.mjs`'s `SLICE_RE`), so a valid
  slice's `repo` can equal the key — never a raw directory name the coordinator grammar
  cannot consume (a dotted `api.v2` key is a `malformed repos entry`) — with the actual
  directory carried in `path` (`api.v2` ⇒ key `api-v2`, `path: ../api.v2`); the keys
  shall be **unique** after normalization, and when two deployable names collide on one
  candidate key (e.g. `api.v2` and `api-v2` both yield `api-v2`) the Planner shall allocate
  them deterministically in the architecture's naming order while probing the complete set
  of keys already assigned — take the normalized name when that candidate is unused,
  otherwise append `-2`, `-3`, … and take the smallest suffix whose candidate is not
  already assigned (so `api`, `api!`, `api-2` allocate `api`, `api-2`, `api-2-2`) —
  because `manifestRepos()` rejects duplicate repository keys and any collision leaves a
  deployable unreachable; each entry shall carry
  `path`, `init`, `test_command`, `delegate_cmd` (empty string), and optionally
  `scaffold_cmd`.
- **R3** — If `specs/architecture.md` names exactly one deployable (or none), then the
  Planner shall write neither a repo-topology ADR nor a draft manifest.
- **R4** — The Planner shall not set or change `umbrella.manifest` in
  `harness.config.yaml` and shall not write `umbrella.manifest.yaml`, so the draft's
  presence alone does not engage umbrella mode.
- **R5** — The draft manifest shall carry a header that marks it a DRAFT and states it is
  inert, and each `path:` shall be written relative to the draft file's own directory (the
  child repo sibling).
- **R6** — The draft entry key `scaffold_cmd` shall be optional and opaque: no harness
  component interprets it, and only the E28-F03 promotion runs it.
- **R7** — The portable Planner contract (`agents/planner.md`) shall carry the
  topology-output rule: the trigger, both artifacts, the draft path and shape, the inert
  rule, and the single-writer rule.
- **R8** — The `/sdd-plan` command body emitted by `harness-install.sh` and the source-mode
  command artifacts (`.claude/commands/sdd-plan.md`,
  `.agents/skills/sdd-plan/SKILL.md`) shall all carry the same topology-output step, so the
  role contract and the command body cannot diverge. They shall also carry the same
  explicit **first-run/greenfield** and **amend** branches: the amend branch **skips** the
  greenfield template writes of `specs/vision.md`/`specs/architecture.md` and never
  rewrites them (a branch stated only in the re-run guard, while the write steps stay
  unconditional, either overwrites committed planning artifacts or depends on the model
  silently ignoring earlier ordered steps).
- **R9** — The shipped manifest documentation (`umbrella.manifest.example.yaml` and
  `docs/UMBRELLA.md`'s Manifest reference) shall document `scaffold_cmd` as an optional,
  harness-opaque key while retaining the four required entry keys (`path`, `init`,
  `test_command`, `delegate_cmd`).
- **R10** — The Planner shall be the single writer of the draft manifest; `/sdd-drill`
  shall neither create nor amend `umbrella.manifest.draft.yaml` and shall not make the
  topology decision itself. When a decomposition reveals that the deployable set changes —
  a new, removed, or renamed deployable — the Driller shall **STOP** and record the change
  as a required `/sdd-plan` amend, keeping its existing ADR-delta authority for the
  non-topology decisions the decomposition forces; a topology change shall be a
  `/sdd-plan` amend. The stop-and-hand-off check shall run **immediately after the intake
  Q&A and before any seeding write** (feature entries, the epic feature table, inbox
  briefs, and ADR deltas), so a topology-dependent feature is never persisted before the
  amend has reconciled the draft. The stop-and-hand-off rule shall live on the Driller role
  (`agents/driller.md`) **and** the `/sdd-drill` command surfaces
  (`harness-install.sh`'s `$CMDDIR/sdd-drill.md` body, `.claude/commands/sdd-drill.md`,
  `.agents/skills/sdd-drill/SKILL.md`), because the Driller's clean context does not receive
  the Planner contract that states the rule.
- **R11** — When an amend changes the deployable set, the Planner shall record the change
  **append-only** — a dated `## Repo topology` delta section appended to
  `specs/architecture.md` plus a new repo-topology ADR allocated above the maximum existing
  ADR number, never rewriting the original section. Every amend that changes the deployable
  set **always appends** that new repo-topology ADR, including a collapse or removal that
  leaves one deployable (or none). The amend's delta shall be a **complete replacement
  snapshot**: it names the full effective deployable set as it stands after the change, and
  earlier deltas are superseded, so the effective set is exactly the deployables the latest
  delta names (the original architecture's set when no delta has been appended) and add,
  remove and rename are all expressible by naming the resulting set. The topology trigger
  shall read that effective set, not the original section alone: when it is still more than
  one the Planner shall reconcile the draft to exactly the effective set; when the effective
  set falls to one deployable (or none) the Planner shall additionally **remove** the
  derived `umbrella.manifest.draft.yaml` — the **one carve-out** from the amend's
  no-deletion rule, because the draft is derived and project-owned — while the
  already-committed repo-topology ADRs are preserved (append-only, never deleted), so the
  amend path both produces and removes the artifact. The amend shall be an **explicit
  branch**, not a permission to continue: the Planner shall detect the mode from the
  existing `specs/vision.md`/`specs/architecture.md` (or an explicit amend opt-in), and an
  amend run shall **skip** the greenfield template writes of `specs/vision.md` and
  `specs/architecture.md`, performing only the append-only delta work above — it never
  rewrites committed vision, architecture, or ADR artifacts. The amend branch shall touch
  the topology artifacts **only** when it **detects a deployable-set change** — a
  deployable added, removed, or given a new name: only then shall it append the dated
  topology delta and the new repo-topology ADR and reconcile (or remove) the derived
  draft. An amend that only adds roadmap epics or non-topology ADR deltas shall **not**
  touch the topology artifacts, so an ordinary re-plan manufactures no redundant topology
  decision.
- **R12** — The draft manifest `umbrella.manifest.draft.yaml` shall be treated as a
  **derived, project-owned** artifact by the installed-body drift guard: it shall be
  excluded from the harness-owned path set so an untracked or uncommitted draft never fails
  the gate — the documented flow commits the planning baseline only after `/sdd-drill` —
  while a genuine harness-body edit still fails it. The exclusion shall be expressed in the
  single ownership definition, `tools/harness-owned-paths.sh`, and resolve in both the
  installed (`.harness/`-prefixed) and source layouts.

## Out of scope

- Creating any repo or directory, `git init`, running or changing the installer's promotion
  path, manifest auto-population, per-child scaffolding execution, or the landing audit —
  E28-F03.
- Any new `/sdd-*` command, flag, config key, interactive prompt, or status value.
- Adding a `Deployables` section or any other change to `specs/_templates/architecture.md`;
  the deployables are named in the architecture's system shape and the judgment stays with
  the Planner.
- Any change to `tools/next-task.mjs`, `init.sh`, `store/`, or the Orchestrator's umbrella
  loop. `agents/driller.md` gains **only** R10's stop-and-hand-off rule (a pointer at the
  `/sdd-plan` amend, no manifest write and no topology decision); its ADR-delta rules and
  authority for non-topology decisions are unchanged.
- GitHub remotes, branch protection, Codex App, and any language/framework scaffolding
  logic (the harness owns none of `scaffold_cmd`).
- Docs beyond the one-line `scaffold_cmd` addition to `docs/UMBRELLA.md`'s Manifest
  reference; the promotion narrative is F03's.

## Open questions — resolved in this spec (the human gate may overturn)

- **Q1 — draft manifest name/location so it cannot be mistaken for the live switch.**
  **Resolved: `umbrella.manifest.draft.yaml`, in the harness directory** (beside
  `harness.config.yaml`; `.harness/umbrella.manifest.draft.yaml` in an installed target).
  Rationale: (a) the live manifest sits at the umbrella root named by `umbrella.manifest`
  — a different directory *and* a different filename; (b) the Planner never writes
  `umbrella.manifest.yaml` and never touches the config key, so the switch cannot be
  flipped as a side effect (R4); (c) it sits next to the shipped
  `umbrella.manifest.example.yaml` it copies the shape from, and a `path: ../<child>`
  resolves from the harness dir to the sibling layout F03 will create; (d) promotion is an
  explicit F03 step, not a file rename the Planner does; (e) **promotion must re-base each
  `path:`** — the draft's base is the harness dir (`.harness/`, so `../<child>`), while a
  live manifest at the umbrella root uses `./<child>`, so F03 transforms rather than merely
  moves the file.
- **Superseding note (drill delta, not an Architect edit).** `specs/epics/E28-greenfield-to-umbrella/epic.md`
  lines 29/42 still name the draft `umbrella.manifest.yaml`. **This spec supersedes that
  name** (`umbrella.manifest.draft.yaml`); the Driller reconciles the epic's feature-index
  line on its next delta. The Architect does not edit `epic.md` (per-epic deltas are F03's).
- **Q2 — may `/sdd-drill` amend the draft manifest when an epic adds a repo?**
  **Resolved: no — the Planner is the single writer** (R10). Rationale: the brief bounds
  this feature to a Planner delta, and a second writer would put the topology in two
  places and let the artifact drift from the architecture that justified it. An epic that
  surfaces a new deployable is a plan-level change: the Driller records it in its epic/ADR
  delta and the human re-runs `/sdd-plan` (amend), which reconciles the draft. The amend
  appends its topology delta (R11) rather than rewriting the architecture, so the trigger
  still sees the new deployable and the draft is produced. F03 consumes whatever draft
  exists.
