# Greenfield single-repo path — Functional Spec

## Context

Someone starting a **new product** today opens a clean agent session in an empty folder and
hand-prompts the repo layout *before the harness exists*: the topology is chosen at the moment
of least knowledge, outside the harness, with no ADR and no test. The single-repo greenfield
path already works — a v0.78.1 install into an empty, non-git directory succeeds without
complaint, and `/sdd-plan` already carries the whole-project brainstorm (vision + architecture
+ ADRs + draft epics). What is missing is that nothing documents it as **the front door** and
nothing tests it, so it is not trusted and gets bypassed.

The user is the harness owner starting a new product. The deliverable is **documentation +
a test** of the existing behavior, plus the smallest installer message tweak that points a
greenfield target at `/sdd-plan`. No topology decision, no umbrella creation and no new
command are in scope — those are E28-F02/F03.

**Complexity: `complex` (E17-F03, routes round 1 to `builder-heavy` per ADR-0002).** Two of
the stated bases apply, and both are visible in this spec:
1. *Speccing required resolving a contradiction between two existing components.*
   `docs/INSTALL.md`'s `## Bootstrap (first run)` section tells a new product to run
   `/sdd-next` to "draft epics", while `/sdd-plan` is the whole-project inception that
   produces the roadmap. The brief itself names them "two competing stories"; R3/R4 exist to
   collapse them into one.
2. *The plan names defect classes this harness has already paid for* (`progress/lessons.md`):
   a fixture copied from the repo inheriting the artifact under test, a negative predicate
   that can never match, and a suite freezing the repo's current `VERSION` literal. The new
   suite is exactly where all three recur, so R7, R10 and the tests contract pin against them.

## Business rules

- The front door for a new product is **install first, plan second**: the installer is the
  choke point, `/sdd-plan` is the brainstorm. No pre-harness intake and no second intake are
  added (`docs/RATIONALE.md` #2 — never accrete).
- The single-repo greenfield install (empty, non-git directory) is a **supported path**, not
  a degraded mode. It must be documented and covered by a suite.
- Exactly **one** front-door story may exist across `docs/INSTALL.md`. Two competing stories
  are a defect: a model re-interprets them every session, and the cheaper-to-read one wins.
- The installer does **not** own version control: it never runs `git init` on a single target.
  The human does that (documented, not prompted).
- Zero new interactive prompts; where behavior is deterministic it lives in code/tests, not
  in prose asking an agent to behave (ablation doctrine, `docs/RATIONALE.md` #1/#4).
- A single-target install that never promotes (E28-F02/F03) must behave exactly as today,
  except for the "Next steps" banner text.

## Architecture alignment

- ADR-0001 — next() selection is deterministic code: the documented front-door sequence is
  `/sdd-plan` (seeds `draft` epics) → `/sdd-drill` (flips an epic `planned`) → `/sdd-next`
  (executes). The docs describe the selector's draft-epic gate; this feature changes no
  routing.
- ADR-0003 — one shared skill unit per command, claimed by `{codex, opencode}`: the front
  door is invoked as `/sdd-plan` (Claude/OpenCode) or `$sdd-plan` (Codex) from the **same**
  per-command unit. The docs name the host-neutral `/sdd-plan`, and the suite asserts the
  artifact for the selected front-end rather than assuming a host-specific path.
- ADR-0004 — a child resolves the harness body through pointer stubs, and *no umbrella is not
  a broken environment*: the greenfield single-repo install is ADR-0004's additive case
  (`umbrella.root` unset ⇒ full local body, standalone entry). The suite asserts the
  standalone entry works (`init.sh` passes) instead of assuming an umbrella.

## Acceptance criteria (EARS)

- **R1** — The `docs/INSTALL.md` documentation shall contain a section headed
  `## Starting from nothing (new product)` that presents the new-product front-door sequence
  in order: an empty directory → `harness-install.sh` → `git init` → `/sdd-plan` →
  `/sdd-drill` → `/sdd-next`.
- **R2** — The "Starting from nothing" section shall state that the install target may be an
  empty, non-git directory; that the installer does not create a git repository; and that
  `git init` plus a commit is the human's step, so `init.sh`'s drift guard can verify the
  committed body (a non-git target is supported: the guard skips, and an untracked body
  warns — it never fails).
- **R3** — The `docs/INSTALL.md` documentation shall present exactly one front-door order for
  a new product — `/sdd-plan` before `/sdd-next` — in **both** the "Starting from nothing"
  section and the `## Bootstrap (first run)` section.
- **R4** — The `## Bootstrap (first run)` section shall document the seeded `E00-F01`
  bootstrap task as the step routed by `/sdd-next` **after** `/sdd-plan` (its
  command-detection role), and shall retain the heading text `Bootstrap (first run)` so
  `README.md`'s anchor `docs/INSTALL.md#bootstrap-first-run` continues to resolve.
- **R5** — When a fresh single-target install completes, the installer's `Next steps` banner
  shall name `/sdd-plan` before `/sdd-next`.
- **R6** — The installer shall not create a `.git` directory in a single-target install
  target (no VCS initialization is performed by the installer).
- **R7** — `tests/test_greenfield.sh` shall install the harness via
  `sh "$SRC/harness-install.sh"` into a fixture directory that the suite has asserted is
  empty and **not** a git work tree, and shall fail the suite when the install exits non-zero.
- **R8** — The greenfield suite shall assert the installed layout is usable: `AGENTS.md`,
  `.harness/`, a non-empty seeded board at `.harness/state/tasks.json`, and the selected
  front-end's `/sdd-plan` command artifact (with the suite's explicit Claude selection,
  `.claude/commands/sdd-plan.md`) are present.
- **R9** — The greenfield suite shall run the installed `.harness/init.sh` from inside the
  installed target and require exit `0`.
- **R10** — The greenfield suite shall derive any expected installed version from
  `$SRC/VERSION` at run time and shall not embed a literal version string.

## Out of scope

- Any topology decision, umbrella creation, promotion path, `umbrella.manifest.yaml`, or
  `git init`-ing of children — E28-F02/F03.
- Any Planner or Driller change (the topology-emitting planner is E28-F02).
- Any new `/sdd-*` command or interactive Q&A; `/sdd-plan` already exists.
- Changing the seeded `E00-F01` board entry, `tests/test_install.sh`, `init.sh`, `store/`,
  `tools/`, `harness.config.yaml`, or any generated front-end glue.
- Auto-`git init` by the installer (see Open questions Q1 below).

## Open questions — resolved defaults (the human gate may overturn)

- **Q1 — should the installer `git init` an empty non-git target itself, or only tell the
  human?** **Resolved: only tell the human; the installer stays out of version control.**
  Rationale: the brief's constraint is "must not change single-target install behavior beyond
  the banner text", and auto-init is a new filesystem mutation with a wrong-directory hazard
  (installing into a subdirectory of an existing repo would nest a repo). The harness already
  gates `git init` behind an explicit flag on the umbrella path
  (`harness-install.sh` → only `--shared-repo` initializes), so "never automatic" is the
  recorded precedent. R2 documents the command; R6 pins that the installer does not run it.
- **Q2 — where does the seeded `E00-F01` bootstrap task sit relative to `/sdd-plan` on a
  greenfield target: keep both, or make `E00-F01` point at `/sdd-plan`?** **Resolved: keep
  both, and document `/sdd-plan` as the front door with `E00-F01` routed by `/sdd-next`
  afterwards** (R3/R4). Rationale: `/sdd-plan` owns roadmap/epic authoring; the `E00-F01`
  task's remaining job is adapting test/lint/typecheck commands, which happens under
  `/sdd-next`. Changing the seeded board entry itself is install behavior beyond the banner
  text and is out of scope; the reconciliation is therefore documentation plus the banner.
