# Greenfield single-repo path — Technical Plan

> Translates `E28-F01.spec.md` into design. Every decision cites the `R-id`(s) it serves.
> The deliverable is docs + one new test suite + a one-block installer banner edit.

## Stack & dependencies

- Language/framework: the harness's own POSIX `sh` test convention, Markdown docs, and the
  existing `harness-install.sh` shell installer.
- New dependencies: **none**. Zero-dep POSIX `sh` + `grep` + `python3` (already required by
  the local TaskStore).
- No new command, flag, config key, or interactive prompt.

## Data model

None. This feature adds no table, schema field, or config key.

## Docs content contract (serves: R1, R2, R3, R4)

The suite greps **pinned anchors**, so the plan pins them here and `.tasks.md` ships them.
Never assert an anchor that is not in this list (and never assert a `VERSION` literal).

### New section — `## Starting from nothing (new product)`

Required in the section's extracted span:
- the heading text `Starting from nothing`;
- the ordered anchors, each present and in first-occurrence order:
  `harness-install.sh` → `git init` → `/sdd-plan` → `/sdd-drill` → `/sdd-next`;
- the tokens `empty` and `non-git`;
- the tokens `commit` and `drift` (the guard that motivates the commit step);
- the pinned sentence, verbatim: **`The installer does not create a git repository.`**

The section's prose must not mention `/sdd-next` or `/sdd-drill` before the `/sdd-plan` step
(first-occurrence order is what the suite asserts). A short numbered list is the natural shape.

### Reconciled section — `## Bootstrap (first run)`

- Heading text retained exactly: `## Bootstrap (first run)`.
- The span must contain `/sdd-plan`, `E00-F01`, and `/sdd-next`, with the first `/sdd-plan`
  occurring before the first `/sdd-next`.
- The `E00-F01` task is described as what `/sdd-next` routes (adapting test/lint/typecheck
  commands) **after** `/sdd-plan`; it is not presented as the front door for a new product and
  is not described as the thing that drafts the project's epics (that is `/sdd-plan`'s job).

### Banner — fresh install

Required in the `Next steps:` block of the fresh-install stdout:
- the block is non-empty and at least 2 lines (structural length floor);
- it contains both `/sdd-plan` and `/sdd-next`, with `/sdd-plan` first.

## Suite design — `tests/test_greenfield.sh` (serves: R5, R6, R7, R8, R9, R10)

Structure mirrors `tests/test_install.sh` / `tests/test_agents_host.sh`: `#!/bin/sh`,
`set -eu`, `SRC` resolved from `$0`, a suite-scoped `mktemp -d` with `trap 'rm -rf' EXIT`,
`fail()` / `pass()` helpers whose `fail()` messages name the **consequence**, and `pass`
lines labelled with the R-id.

Hard requirements the Builder must honour (each maps to an earned lesson in
`progress/lessons.md`):

1. **The fixture is genuinely empty and non-git (R7).** `TGT="$(mktemp -d)"`, then assert
   `[ -z "$(ls -A "$TGT")" ]` (or an equivalent emptiness check) and `[ ! -e "$TGT/.git" ]`
   *before* installing. **Never** point the fixture at the source repo or a copy of it — a
   fixture copied from the repo inherits the artifact under test (2026-09-05 lesson).
2. **Invoke the installer as `sh "$SRC/harness-install.sh"`** (2026-09-16 lesson: the suites
   run the installer via `sh`, so the executable-bit class is invisible — this suite is not
   the place to change that convention), with the non-interactive overrides that suppress
   every pre-existing prompt: `--agents=claude --builder-backend=in-session --pr-loop=false`.
   Sandbox `HOME` and `CODEX_HOME` under the suite temp dir. Capture **stdout** separately
   (`>"$T/install.out" 2>"$T/install.err"`) so the banner assertion reads the real stream.
3. **Positive control on every extracted shape.** Any span extraction (a docs section, the
   banner block) must assert the extraction is non-empty **and** has a line-count floor, then
   assert the anchors inside it. A negative predicate whose middle stage can match nothing is
   decoration, not a test (2026-09-16 lesson) — so every negative is paired with a positive
   anchor asserted from the same extraction.
4. **No `VERSION` literal (R10).** The version assertion reads `$SRC/VERSION` at run time and
   compares the installed `.harness/.harness-version` against it. Do not copy
   `tests/test_codex_native.sh`'s bare-literal comparison (the permanent-suite anti-pattern
   the 2026-09-16 lesson names).
5. **Isolation.** The suite writes only inside its own `$T`; it must not touch `state/`,
   `specs/`, `progress/`, or the developer's `~/.codex`.
6. **`init.sh` is run through its own shebang**: `( cd "$TGT" && ./.harness/init.sh )`
   (installed `init.sh` is `chmod +x`-ed by the installer). Never `sh init.sh` — it is a
   bash-shebang script and `sh` is dash on some hosts (2026-09-05 lesson).
7. **Front-end artifact (R8).** The suite selects `claude` explicitly and asserts
   `.claude/commands/sdd-plan.md` exists. Do not assume host-specific paths across
   front-ends (ADR-0003's shared unit is a different path for Codex/OpenCode).

## Approach notes

- **Q1 (git init) is implemented as documentation + a pin.** The installer's single-target
  path is untouched; R6 is a *regression pin* of existing behavior, not a new branch. Any
  temptation to add a `git init` call is out of scope and fails R6.
- **The banner stays unconditional.** It is shown for a fresh install regardless of whether
  the target was empty or an existing project. `/sdd-plan` is valid advice on both, and adding
  a "was the target empty?" probe would add a second behavior axis (and a brownfield surface)
  for one message. The empty-dir specifics live in the docs section. Record this choice in the
  PR body.
- **One story means one order, twice.** The reconciliation is not "add a section"; the
  Bootstrap section must itself state the `/sdd-plan`-then-`/sdd-next` order (R3), which is
  what reds on today's text.
- **The banner's `/sdd-plan` line must name the command the docs name.** Use the
  host-neutral `/sdd-plan` spelling in prose; the per-host line already varies the invocation
  for Codex/OpenCode, so keep the command name in the trailing shared description line if
  that keeps the ordering assertion simple.
- **Sequencing.** T1–T3 (docs) and T4 (banner) can be done independently of T5 (suite); do
  T5 last so the anchors it greps are on disk. T6 (VERSION/CHANGELOG) after the code change.
  Run the new suite **alone** first (`sh tools/run-tests.sh tests/test_greenfield.sh`), then
  the full gate.
- **Residual risk, stated.** The docs order assertion is a prose first-occurrence check; a
  later re-wrap or reordering that moves `/sdd-drill` after `/sdd-next` in prose would red it
  even if the numbered steps are correct. That is the intended trade: one front-door order is
  the feature's contract.
