# Worker roster: invocable CLIs as versioned data — Functional Spec

## Context

The operator runs several coding CLIs in parallel, but the harness only knows about the one
it is running inside. Any external kit that wants to route work across them — the epic names
`multi-cli-orchestrator` — has to rediscover what is installed, every time. This feature
writes that answer down **once**, as versioned data, and stops there.

### The brief's premise is half wrong, and the spec is built on the correction

The brief says *"the installer already probes the environment to pick front-ends. Nothing
consumes that knowledge afterwards."* The second half is true. The first half is not, and
building on it would have produced a feature that reuses the wrong machinery.

`grep -n "command -v" harness-install.sh` returns four hits and **not one is a front-end
CLI**: `stty`, `node` (inside a commented example), and `git` twice. The installer has never
asked whether a coding CLI is installed. What it has is two other things:

1. **`detect_host` + `HOST_MARKERS`** (`harness-install.sh` §host detection) answers *"which
   front-end launched this installer run"*, from **session environment markers only**.
2. **The picker** answers *"which front-ends should I stamp glue for"*. `AGENT_KEYS` is a
   fixed constant — the set of *legal tokens*; what the human toggles is the **selection**
   (`--agents` / `HARNESS_AGENTS` / the TUI, resolved into `SELECTED`). That is **intent**,
   not presence, and the distinction matters again at R5 below.

So presence-detection is new code. More importantly it is a **different evidence class**, and
the difference is load-bearing. The `HOST_MARKERS` block's **session-markers-only rule**
(the first unnumbered bullet, not R6 — R6 is the separate forbidden-by-*name* blacklist)
rejects ambient environment variables precisely because *"a variable a human exports in a
shell profile proves they use that tool somewhere; it never proves THIS installer run was
launched from it."* For a roster the question **is** "can this machine invoke it" — so a
`PATH` lookup is exactly the right evidence, and the thing that rule excludes for host
detection is the thing the roster wants. Stated here because a reviewer who knows the
`HOST_MARKERS` discipline will otherwise read the new probe as a violation of it.

### Why `complexity: complex`

On a stated basis, per `agents/architect.md`: it names a defect class the harness has already
paid for — the capability table is a **second table describing the same front-ends** as
`AGENT_KEYS` and `HOST_MARKERS`, and a body diverging from its copy is the failure mode
E17-F05 spent two review rounds on. R5 and R7 are written to pin that seam rather than leave
it to the Builder's discretion, and the plan's DO-NOT-TOUCH list pins the placement that
keeps `tests/test_agents_host.sh`'s own guard able to fail.

It also **landed on the size budget** — 12 R-ids against `change_size.max_requirements: 12`.
Roster JSON validity is **not** a thirteenth requirement that was demoted to fit: it is
*entailed* by R4, R5 and R7, each of which requires parsing the file. It is carried as an
unnumbered row in the test contract because a direct parse failure is a clearer diagnostic
than three simultaneous R-id failures. (Relabelling a requirement as a test row would not
remove one line from the eventual diff, which is what the budget is a proxy for — so it is
not a way to get under it.)

## Business rules

- **The harness never executes a rostered CLI.** It resolves a name on `PATH` and writes a
  file. This is the epic's own boundary — *"without the harness core ever executing it"* —
  and it is what keeps the roster safe to ship: a data file cannot spawn a process. Version
  *detection* stays out for the same reason, since asking a CLI its version means running it
  (this is why `agy >= 1.1.5` is documented in `harness.config.yaml` rather than checked).
- **The roster is a public contract the moment anything reads it**, so it carries `schema: 1`
  from the first write and a consumer can detect a format change instead of guessing.
- **The roster describes THIS MACHINE**, so it is local-only and gitignored — the same
  treatment `telemetry.jsonl` gets, and for the same reason: committing it would put one
  developer's local CLI set into a shared repo.
- **The installer owns the file outright.** It is derived data, not an operator artifact, so
  it is regenerated on every run. That ownership rule is stated (R10) rather than left
  implicit, because "regenerating overwrites anything a human edited" is only acceptable when
  the file was never theirs to edit.
- **Capabilities are facts the harness already holds, not opinions about the CLIs.** The
  vocabulary is closed and declared in the file itself (R7), so a consumer can match on it and
  can see the whole vocabulary alongside the data. The corollary is a naming rule, and it is
  the one this vocabulary is most likely to break: **a tag's name must not claim more than the
  fact it is derived from.** A tag derived from the selection may say *selected*; only a tag
  derived from a write outcome may say *written* or *stamped*.
- **Presence is a property of the machine, not of this install's selection.** A CLI the
  operator did *not* select as a harness front-end still belongs in the roster — telling a
  router about it is the whole point. Selection is recorded as a *capability*
  (`harness-selected`), never as a filter on which entries exist. This is the one place the
  roster deliberately departs from `write_escalation_arming`, which does filter. The tag says
  *selected*, not *stamped*, because selection is all the roster can prove — see Open
  question 3.
- **The roster includes the host CLI.** The epic's success criterion says *"non-host CLIs"*,
  and this is a deliberate, stated departure: excluding the host would mean consulting
  `detect_host`, re-coupling presence to host identity — the exact coupling this feature
  exists to avoid. A consumer that cares which one is the host can compare against
  `--agents=host` itself.
- **The roster is per-target**, like `telemetry.jsonl`. An umbrella cascade installs into each
  repo, so it writes one roster per target, each describing the same machine; a consumer reads
  the roster of the target it is operating in.

## Acceptance criteria (EARS)

- **R1** — Where the roster is enabled in `harness.config.yaml`, the installer shall write the
  roster to `.harness/workers.json`.
- **R2** — Where the roster is not enabled — the key absent, `false`, empty, or any
  unrecognized value — the installer shall write no roster file, and shall add no roster
  artifact to the target beyond the two documented always-present items: the default
  `workers.roster: false` config key and the `.harness/.gitignore` entry (R11).
- **R3** — When the installer runs against a target that has a roster file while the roster is
  not enabled, the installer shall remove that file and report the reclamation.
- **R4** — The roster shall carry a top-level `schema` key whose value is the integer `1`, and
  under `schema: 1` the declared `capability_vocabulary` shall be **exactly** the three tags R7
  names — `harness-selected`, `host-detectable`, `non-interactive` — sorted, with no fourth tag
  and none missing. Introducing, renaming or removing a tag is a format change and requires a
  `schema` bump.
  (**Why the fixedness lives in R4 and not R7.** R7 owns each tag's *derivation rule* — when it
  is present and when it is absent — and it constrains only the tags it names, so an emitter
  that invented a fourth tag, declared it in `capability_vocabulary` and stamped it on every
  entry would satisfy R7's closure and R7's per-tag rules both. What such an emitter breaks is
  the *version number*: `schema` exists so a consumer can know the format without guessing, and
  a vocabulary free to grow inside a fixed `schema` makes `schema: 1` promise nothing. That is a
  statement about what the version guarantees, so it belongs to the requirement that owns the
  version. R4 fixes the set's identity; R7 governs membership of each entry within it.)
- **R5** — The roster shall carry exactly one entry per agent key in `AGENT_KEYS` whose
  invocation command resolves on `PATH` — **whether or not that key is selected for this
  install** — and each entry shall name the key it describes, the invocation command that
  resolved, and the **canonicalized absolute path** that command resolved to: a value
  beginning with `/`, usable from any working directory. (The absoluteness is stated in the
  requirement, not left to the plan, because `command -v` does not provide it — a relative
  `PATH` component makes it return a relative value under `dash` and `bash` alike. See the
  plan's *`command -v` does not promise an absolute path*.)
  **The value a JSON parser recovers from `path` shall be byte-identical to that resolved
  path, except that a pathname whose final byte is a newline is out of contract** — the
  canonicalization step captures `pwd -P` through a command substitution, which strips *all*
  trailing newlines, so the byte is lost before any escaping runs (measured: a 108-byte
  directory name captured as 107). A sentinel capture (`x=$(pwd -P; printf x)`, then strip the
  `x`) would preserve it, and is deliberately **not** required: it hardens the one pathname
  shape that cannot occur in a real CLI install against a cost paid on every read of this
  code. What is NOT acceptable is claiming the guarantee and not delivering it —
  `agents/reviewer.md` (3c) rates prose overstating a guarantee at the same severity as the
  missing enforcement, because the next reader trusts it and stops looking. The exclusion is
  therefore stated here rather than discovered later.
  The roster's *encoding* is part of this requirement, not only its content: `"`, `\`
  and the C0 control class (U+0000–U+001F) are all legal in a POSIX directory name, so an
  emitter that interpolates the path into JSON unescaped either produces a file no consumer can
  parse or silently hands back a mangled path — and a requirement that constrains only the
  logical field leaves both outcomes conformant. This is stated rather than left to the plan
  because the harness has already shipped this exact bug once: **E99-F08** was a fix for
  `_json_escape` in `tools/change-size.sh` handling only the control characters that had been
  reported. Escape the class, not the characters someone happened to hit.
- **R6** — If an agent key's invocation command does not resolve on `PATH`, then the roster
  shall carry no entry for that key.
- **R7** — Each roster entry shall carry a `capabilities` list drawn from the closed
  vocabulary the roster declares as a top-level key — a set R4 fixes to exactly three tags for
  `schema: 1`, so "drawn from the declared vocabulary" is also "drawn from those three" —
  containing `harness-selected` exactly when
  that key is selected for this install, `host-detectable` exactly when that key has a
  `HOST_MARKERS` row, and `non-interactive` exactly when the invocation table records a
  verified entrypoint for it.
- **R8** — The installer shall determine each CLI's presence by `PATH` resolution alone, and
  shall execute no rostered CLI at any point.
- **R9** — When the installer runs twice against the same target with identical **roster
  inputs**, the second roster shall be byte-identical to the first. The roster inputs are
  exactly three, and the roster shall be a function of these and nothing else: (a) the value of
  the roster gate in `harness.config.yaml`; (b) the resolved selection `SELECTED`; and (c) for
  each key in `AGENT_KEYS`, the canonicalized absolute path its invocation command resolves to
  under the run's `PATH`, or the fact that it resolves to none. Note (c) is a *resolved path*,
  not "the command is present somewhere": two `PATH` entries can both hold `claude`, so
  reordering them changes input (c) even though the set of available commands is unchanged.
  R9 binds only the identical-input case — where any of (a)–(c) differs between two runs, R5,
  R7 and R10 govern the output and R9 requires no identity, so a roster that changes because
  `--agents` or `PATH` ordering changed satisfies R9 rather than violating it.
- **R10** — When the installer runs against a target whose roster file already exists and the
  roster is enabled, the installer shall overwrite it from freshly detected state.
- **R11** — The installer shall ensure the roster path is ignored by `.harness/.gitignore`,
  on every install, gate or no gate. (Deliberately **ubiquitous**, not gated: `_ignores` is
  unconditional and `.harness/.gitignore` is append-only on upgrade, so a *gated* line could
  never be removed once the gate had been on — a gate here would be incoherent rather than
  conservative.)
- **R12** — If `.harness/workers.json` exists and is a symlink, then the installer shall write
  no roster, shall leave both the link and its target unchanged, and shall warn.

## Out of scope

- **Any consumer of the roster.** `multi-cli-orchestrator` is a separate kit.
- **Executing a rostered CLI**, for any purpose, including version detection.
- **Model routing, escalation, and the Builder variants** (E17-F02 / F03). Same epic, none of
  that machinery.
- **Roster entries for anything that is not a harness agent key.** A general "what CLIs are on
  this box" inventory is a different feature with a different evidence standard.

## Open questions

> These are the drill's three open questions. Each is **answered** below — the answer is the
> Architect's to settle — with the reasoning stated so the approval gate can overturn any of
> them cheaply. The third is the one worth the human's attention.

1. **Where does the roster live?** → `.harness/workers.json`. Machine-written and
   machine-read, which argues against the hand-edited `harness.config.yaml`; gitignored and
   resolved under `HARNESS_DIR`, matching `telemetry.jsonl` exactly. Settled.
2. **Is detection re-run on upgrade?** → Yes, every run, overwriting (R10). The file is
   derived data the installer owns; a roster that goes stale as the operator installs and
   removes CLIs is worse than useless, because a consumer cannot tell stale from current.
   Settled.
3. **What is the capability vocabulary?** — *the feature's central design question, and the
   one this spec would most like challenged.* The answer taken is a **closed set of three
   tags, each backed by a fact the harness already holds**, rather than a taxonomy of what
   each CLI is good at:

   | tag | means | the harness's evidence |
   |---|---|---|
   | `harness-selected` | this install selected this CLI as a harness front-end | the key is in `SELECTED`, the same set persisted to `.harness/.agents` |
   | `host-detectable` | `--agents=host` can recognize a session this CLI launched | the key has a `HOST_MARKERS` row |
   | `non-interactive` | the CLI has a scriptable, prompt-in entrypoint | a recorded, verified entry in the invocation table |

   **`harness-selected` is derived from the selection, not from `AGENT_KEYS`** — and that is a
   correction worth stating, because the obvious version of this tag is worthless. R5 already
   restricts entries to `AGENT_KEYS` members, so a tag meaning "is a possible harness
   front-end" would be true of **every row in the file** and would discriminate nothing.
   Derived from `SELECTED` it means "this install asked for it", which varies per target and is
   the thing a router would act on. Membership in the roster already carries the weaker claim.

   **Why the name is `harness-selected` and not `harness-stamped`.** The tag was briefly named
   for the *stamp* rather than the *selection*, and that over-claimed: selection is intent, and
   the installer has refusal branches that leave a selected front-end's glue unwritten — a
   hand-edited `opencode.json` is left in place with a warning, and so is an edited or
   symlinked Codex role file. A router reading `harness-stamped` on a front-end whose
   installation was explicitly refused would treat it as ready. Renaming is the honest fix,
   not a wording nit: the closed vocabulary's whole defence is that each tag points at a fact
   the harness already holds, and `SELECTED` is that fact — no more.

   **Why not derive the stronger claim from the installer's outcome ledger.** There is a
   ledger — `mark_unstamped` / `fe_unstamped` over `$_UNSTAMPED_FILE` — and it is the right
   shape, but it does not answer this question and promising that it does would be inventing a
   mechanism. Three reasons, each checked against `harness-install.sh`: it is scoped to
   **model-routing artifacts**, not to a front-end's glue as a whole (Codex is narrowed further
   still, to `builder`/`builder-heavy`); its own comment records that **only `codex` and
   `opencode` can reach it**, so the other three keys would be unstamped-by-silence rather than
   by evidence; and it is `rm -f`'d at §6b, before the roster would be written, so it is not
   even in scope at roster-write time. Widening it into a general per-front-end write ledger is
   a real feature with its own requirements — and it is a change to the installer's stamping
   paths, not to a data file that describes them. If that ledger ever exists, this tag can grow
   a companion (`harness-stamped`, meaning what it says) under a `schema` bump; until then the
   roster reports the fact it has.

   **Why not "what each CLI is good for":** the harness would be asserting things it has not
   measured, in a file it stamps as a versioned contract. Every tag above is something it can
   point at. **What this costs:** a router asking "which of these reasons best about
   architecture?" gets no answer here. The claim is that the two questions a router has to
   answer first — *can I drive this headlessly* and *did this install ask for it as a harness
   front-end* — are exactly `non-interactive` and `harness-selected`.

   Under this vocabulary an unselected `gemini` gets **no tags at all** — it has no
   `HOST_MARKERS` row (the CLI was never installed on the verification machine) and no
   verified non-interactive entrypoint. A roster entry with an empty capability list is a
   meaningful answer, not a bug: *this machine can invoke it, and the harness can vouch for
   nothing further.* That is the closed set refusing to guess, which is the whole design.

4. **Should an entry carry the resolved absolute path?** This spec says yes (it is the
   strongest evidence of "invocable", and the file is local-only). It does mean the roster
   contains a home-directory path. Cheap to drop at the gate if that is unwanted — it changes
   R5's entry shape and nothing else.

   **Escalation-round evidence, and the reason this question is now the gate's most
   consequential one.** Across three `@codex review` rounds this PR drew six blocking
   findings. **Four of them were about this one field** and nothing else: `command -v` returns
   a relative value under `dash`/`bash` (round 1); reordering two `PATH` entries changes the
   resolved path, which R9's byte-identity did not admit (round 2); the path is JSON *content*,
   so `"`/`\`/C0 must be escaped (round 2); and a trailing-newline pathname cannot survive the
   `pwd -P` capture at all (round 3). Each fix was correct and each one exposed the next — the
   pattern this repo names as "rewrite the rule, not patch it a fourth time".
   The field is a **convenience, not the feature's purpose**: "which CLIs can this machine
   invoke" is answered by `key` and `command`; a consumer that wants the path can run its own
   `command -v`, and must anyway, because the roster is a snapshot. **Dropping `path` deletes
   four findings' worth of contract surface — the canonicalization, the escaping obligation,
   the R9 input clause and this exclusion all go with it.** The spec does not take that
   decision unilaterally, because the field was in scope from the brief and removing it is the
   gate's call, not the Architect's.

   **The gate has two options here, not three.** "Carry whatever `command -v` printed" is not
   one of them and has been removed: that value is relative whenever the matching `PATH`
   component is, so it is only meaningful relative to the installer's working directory — a
   directory no consumer of a local-only data file knows. So either the entry carries a path
   the harness has canonicalized to an absolute value (R5, three lines of shell builtins,
   already the installer's idiom), or it carries no path at all and R5 keeps just the key and
   the command. Dropping the field is still cheap; keeping it un-canonicalized is not on the
   table.
