# Worker roster: invocable CLIs as versioned data — Technical Plan

> Every decision cites the R-id(s) it serves. The shape is deliberately modelled on
> `write_escalation_arming` (E17-F05), which is the closest existing precedent: a gated write
> of a derived verdict into `.harness/`, with a symlink guard, deterministic ordering, and
> reclamation when the gate goes off.

## Stack & dependencies

- Language: POSIX `sh` inside `harness-install.sh`; tests are POSIX `sh` under `tests/`.
- New dependencies: **none**. `command -v` is a shell builtin; the roster is written with
  `printf`. No `jq`, no `python3` on the write path.

## Data model — the roster file (serves: R4, R5, R6, R7)

`.harness/workers.json`, one JSON object:

| Key | Type | Notes |
|---|---|---|
| `schema` | integer | Always `1` for this feature (R4). Bump only on a format change. |
| `generated_by` | string | `harness-install.sh` — marks the file as derived, not operator-owned (R10). |
| `capability_vocabulary` | array of string | The **closed** set, sorted, declared in the file so a consumer can read the vocabulary alongside the data (R7). |
| `workers` | array of object | One entry per present CLI (R5), emitted in `AGENT_KEYS` order (R9). |

Each `workers[]` entry:

| Field | Type | Notes |
|---|---|---|
| `key` | string | The agent key — the same token `AGENT_KEYS`/`.harness/.agents` use. |
| `command` | string | The invocation name that was looked up (e.g. `agy` for `antigravity`). |
| `path` | string | The absolute path `command -v` resolved to (R5). |
| `capabilities` | array of string | Subset of `capability_vocabulary`, sorted (R7, R9). |

Illustrative output (values depend on the machine):

```json
{
  "schema": 1,
  "generated_by": "harness-install.sh",
  "capability_vocabulary": ["harness-frontend", "host-detectable", "non-interactive"],
  "workers": [
    {"key": "claude", "command": "claude", "path": "/opt/homebrew/bin/claude",
     "capabilities": ["harness-frontend", "host-detectable", "non-interactive"]},
    {"key": "gemini", "command": "gemini", "path": "/opt/homebrew/bin/gemini",
     "capabilities": ["harness-frontend"]}
  ]
}
```

## The invocation table — the one new declarative table (serves: R5, R6, R7, R8)

A `WORKER_INVOKE` block beside `AGENT_KEYS` / `HOST_MARKERS`, one row per agent key:

```
<agent-key> <command-name> [<capability> …]
```

Rows carry only the capabilities that are **not derivable**. `harness-frontend` is derived
from membership in `AGENT_KEYS` and `host-detectable` from having a `HOST_MARKERS` row — the
Builder **derives both, and must not restate them in the table**. This is the divergence seam
the spec's Context calls out: three tables describing the same five front-ends is exactly the
body-and-its-copy defect class the harness has already paid for, so only `non-interactive`
(and the command name, which is genuinely new information) is written down.

Seed rows, and the evidence for each `non-interactive` claim — the same discipline
`HOST_MARKERS` R8 imposes, recorded in an adjacent comment:

| key | command | `non-interactive`? | evidence |
|---|---|---|---|
| `claude` | `claude` | yes | `claude -p` |
| `codex` | `codex` | yes | `codex exec` — the entrypoint `HOST_MARKERS` provenance already records |
| `opencode` | `opencode` | yes | `opencode run` — ditto |
| `antigravity` | `agy` | yes | `agy -p` — ditto |
| `gemini` | `gemini` | **no** | nothing verified; the CLI is not installed on the verification machine (the same reason it has no `HOST_MARKERS` row) |

`gemini`'s empty claim is deliberate and must survive review: adding an unverified row is the
failure `HOST_MARKERS` R8 exists to prevent.

## Config surface (serves: R1, R2)

```yaml
workers:
  roster: false   # true ⇒ the installer writes .harness/workers.json (gitignored, local-only)
```

- **Opt-in, seeded `false`**, exactly like `pr_loop.enabled` (`seed_pr_loop_optin`). Only the
  literal `true` enables it; absent / `false` / empty / unrecognized all mean off (R2).
- Added to `migrate_config` as its own append-only block, following the `telemetry:` case —
  a preserved pre-roster config keeps working and an upgrade grows the discoverable knob.

## DO NOT TOUCH

- **`HOST_MARKERS` and its provenance block.** The roster reads it to derive
  `host-detectable`; it never edits it. `tests/test_agents_host.sh` parses that block and
  fails the build on an unrecorded variable — and the roster is not a reason to add one.
- **`AGENT_KEYS`.** The roster is a consumer of the key list, never an author of it.
- **`detect_host` / the picker.** Presence and host-identity are different questions on
  different evidence (see the spec's Context); merging them is the mistake this plan avoids.
- **`tools/` and `tests/test_install.sh`'s existing assertions** beyond the additive ones above.

## Approach notes

- **Write order is `AGENT_KEYS` order, capabilities sorted** — not detection order, not
  `PATH` order. R9's byte-identity is otherwise at the mercy of directory iteration, which is
  how `write_escalation_arming` already justifies its own ordering rule.
- **The symlink guard comes first**, before the gate and before any detection, mirroring
  `escalation_arming_is_symlinked`. A symlinked roster is left entirely alone — no write, no
  reclaim (R12); reclaiming through a symlink would delete something outside `.harness/`.
- **Reclamation (R3) is the ungated path, not an error path.** Gate off + file present ⇒
  remove and `info` it, exactly as `write_escalation_arming` does when nothing resolves.
- **R8 is a negative requirement**, so it needs a test that could actually catch a violation —
  see the test contract. Asserting "the installer exited 0" proves nothing about it.
- **Presence is `command -v <name> >/dev/null 2>&1`**, and the resolved path is that command's
  stdout. One lookup per key, no execution, no `--version`.
- The Builder picks the JSON emission style. Two constraints only: it is valid JSON (tested),
  and it is byte-stable across runs (R9).
