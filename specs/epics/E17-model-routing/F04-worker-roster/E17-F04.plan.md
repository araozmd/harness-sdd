# Worker roster: invocable CLIs as versioned data — Technical Plan

> Every decision cites the R-id(s) it serves. The shape is modelled on
> `write_escalation_arming` (E17-F05), the closest existing precedent: a gated write of a
> derived verdict into `.harness/`, with a symlink guard, deterministic ordering, and
> reclamation when the gate goes off.
>
> **Read the precedent's one disqualifying difference before copying it.**
> `write_escalation_arming` opens its loop with `agent_selected "$_ea_k" || continue`. The
> roster **must not** — see *Approach notes* → *The `agent_selected` trap*. Carrying that
> line across is the single most likely way to build this feature wrong, and it fails
> silently on any machine where everything is selected.

## Stack & dependencies

- Language: POSIX `sh` inside `harness-install.sh`; tests are POSIX `sh` under `tests/`.
- New dependencies: **none**. `command -v` is a shell builtin and the roster is written with
  `printf`. No `jq`, no `python3` on the write path — `python3` *is* a hard prerequisite of
  `init.sh`, so reaching for it would have been legal, and it is still the wrong tool: it would
  put an interpreter spawn on a code path that needs one builtin and a `printf`.

## Data model — the roster file (serves: R4, R5, R6, R7)

`.harness/workers.json`, one JSON object:

| Key | Type | Notes |
|---|---|---|
| `schema` | integer | Always `1` for this feature (R4). Bump only on a format change. |
| `generated_by` | string | The **fixed literal** `harness-install.sh` — marks the file as derived, not operator-owned (R10). It is a literal, **never `$0`** or any other expansion: `$0` is an invocation-dependent path, so it would be both environment-derived content in the JSON and a fourth input to R9's byte-identity (`./harness-install.sh` vs an absolute path give different bytes for the same three inputs). |
| `capability_vocabulary` | array of string | The **closed** set, sorted, declared in the file so a consumer can read the vocabulary alongside the data (R7). Always the full vocabulary, never just the tags this machine happened to produce — **and, under `schema: 1`, always exactly the three tags below, a fixed literal in the emitter (R4)**. "Full vocabulary" and "fixed vocabulary" are different claims: the first stops the emitter from listing only what it emitted, the second stops it from growing the set without a `schema` bump. |
| `workers` | array of object | One entry per present CLI (R5), emitted in `AGENT_KEYS` order (R9). |

Each `workers[]` entry:

| Field | Type | Notes |
|---|---|---|
| `key` | string | The agent key — the same token `AGENT_KEYS`/`.harness/.agents` use. |
| `command` | string | The invocation name that was looked up (e.g. `agy` for `antigravity`). |
| `capabilities` | array of string | Subset of `capability_vocabulary`, sorted (R7, R9). |

**There is no `path` field, and that is a decision, not an omission** — see the spec's
*Recorded decision 4*. Do not add one: it is a `schema` change, and it re-imports the entire
canonicalize/escape/round-trip surface that decision deleted.

Illustrative output (values depend on which CLIs the machine has):

```json
{
  "schema": 1,
  "generated_by": "harness-install.sh",
  "capability_vocabulary": ["harness-selected", "host-detectable", "non-interactive"],
  "workers": [
    {"key": "claude", "command": "claude",
     "capabilities": ["harness-selected", "host-detectable", "non-interactive"]},
    {"key": "gemini", "command": "gemini", "capabilities": []}
  ]
}
```

**Every string this file contains is a harness-authored literal.** `key` comes from
`AGENT_KEYS`, `command` from the `WORKER_INVOKE` table, the capability tags from the fixed
vocabulary — all `[a-z-]+` tokens spelled out in `harness-install.sh` — and `generated_by` is
the fixed literal `harness-install.sh`. **Nothing environment-derived reaches the JSON**, which
is why no value can hold `"`, `\` or a control character. That invariant is what retires the
escaping obligation below; it holds only while the entry shape stays as above and while
`generated_by` stays a literal.

## The invocation table — the one new declarative table (serves: R5, R6, R7, R8)

A `WORKER_INVOKE` block placed **after the closing `"` of `HOST_MARKERS`** — never above it,
and its comment header must **not** begin `# PROVENANCE` (use `# WORKER_INVOKE PROVENANCE`).
Placement is a correctness constraint, not tidiness: see DO NOT TOUCH. One row per agent key:

```
<agent-key> <command-name> [<capability> …]
```

Rows carry only the capabilities that are **not derivable**. `harness-selected` is derived
from membership in `SELECTED` and `host-detectable` from having a `HOST_MARKERS` row — the
Builder **derives both, and must not restate them in the table**. This is the divergence seam
the spec's Context calls out: three tables describing the same five front-ends is exactly the
body-and-its-copy defect class the harness has already paid for, so only `non-interactive`
(and the command name, which is genuinely new information) is written down.

Seed rows, and the evidence for each `non-interactive` claim — the same discipline
`HOST_MARKERS` R8 imposes, recorded in an adjacent comment:

| key | command | `non-interactive`? | evidence |
|---|---|---|---|
| `claude` | `claude` | yes | `claude -p` |
| `codex` | `codex` | yes | `codex exec` — the entrypoint `HOST_MARKERS` provenance already records |
| `opencode` | `opencode` | yes | `opencode run` — ditto |
| `antigravity` | `agy` | yes | `agy -p` — ditto |
| `gemini` | `gemini` | **no** | nothing verified; the CLI is not installed on the verification machine (the same reason it has no `HOST_MARKERS` row) |

`gemini`'s empty claim is deliberate and must survive review: adding an unverified row is the
failure `HOST_MARKERS` R8 exists to prevent.

## Config surface (serves: R1, R2)

```yaml
workers:
  roster: false   # true ⇒ the installer writes .harness/workers.json (gitignored, local-only)
```

- **Opt-in, seeded `false`**, exactly like `pr_loop.enabled` (`seed_pr_loop_optin`). Only the
  literal `true` enables it; absent / `false` / empty / unrecognized all mean off (R2).
- Added to `migrate_config` as its own append-only block, following the `telemetry:` case —
  a preserved pre-roster config keeps working and an upgrade grows the discoverable knob.
- **The block `migrate_config` appends must be BYTE-IDENTICAL to the block a fresh install
  seeds.** This is an enforced convention here, not a nicety: `migrate_config`'s own `models:`
  block says so ("so a FRESH install ... and an UPGRADED install ... converge on the same
  text"), `seed_pr_loop_optin` says so, and `tests/test_installer_toggles.sh` tests it. A
  fresh install copies the config verbatim while an upgrade only migrates, so the two texts
  diverge the moment they are maintained separately — and this feature's own justification for
  `complexity: complex` is that exact defect class. Do not reintroduce it in the one place the
  plan would otherwise leave unguarded.

## DO NOT TOUCH

- **`HOST_MARKERS` and its provenance block — and the text ABOVE it.** The roster reads the
  block to derive `host-detectable`; it never edits it. The subtle part is placement:
  `tests/test_agents_host.sh` finds that block by a **positional range**, `sed -n '/^#
  PROVENANCE/,/^HOST_MARKERS="$/p'`, and its awk helper treats **any** `#   <agent-key> …`
  line inside that range as host evidence for that key. T2's roster provenance is exactly
  that shape — one `#   <key> …` line per key. Put it above `HOST_MARKERS="` and it is
  absorbed into the host-evidence range, at which point the R8 guard can be satisfied by text
  that is not host evidence at all, and the guard this plan keeps citing as its discipline
  model stops being able to fail. A second `# PROVENANCE` header makes it worse, because the
  range starts at the FIRST match. Hence: after the closing quote, and a header that
  `/^# PROVENANCE/` does not match.
- **`AGENT_KEYS`.** The roster is a consumer of the key list, never an author of it.
- **`detect_host` / the picker.** Presence and host-identity are different questions on
  different evidence (see the spec's Context); merging them is the mistake this plan avoids.
- **`tools/` and `tests/test_install.sh`'s existing assertions** beyond the additive ones above.

## Approach notes

- **The `agent_selected` trap — the most important line in this plan.**
  `write_escalation_arming` filters its `AGENT_KEYS` loop with `agent_selected "$_ea_k" ||
  continue`. **The roster must not filter.** R5 rosters every key whose command resolves,
  selected or not, because a router's whole reason to read this file is to learn about CLIs
  this install did *not* wire up. Selection is recorded as the `harness-selected` capability
  instead — a field, never a filter. Note the tag name: it reports membership in `SELECTED`
  and nothing more, because the installer can refuse to write a selected front-end's glue
  (edited `opencode.json`, edited/symlinked Codex role) and the roster has no ledger that
  would know — see the spec's Open question 3. The danger is that this fails **silently**: on a machine
  where every front-end is selected, a filtered roster and a correct one are byte-identical,
  so only the R5 selection fixture (install with `--agents=claude`, stubs for other keys on
  `PATH`, assert they still appear) can catch it.
- **Write order is `AGENT_KEYS` order, capabilities sorted** — not detection order, not
  `PATH` order. R9's byte-identity is otherwise at the mercy of directory iteration, which is
  how `write_escalation_arming` already justifies its own ordering rule.
- **R9's byte-identity is scoped to the three roster inputs, and ordering is what makes it
  hold.** The roster is a function of the gate, `SELECTED`, and each key's *presence* — a
  per-key boolean — and nothing else. Everything the emitter does beyond reading those three
  (the `AGENT_KEYS` write order, the sorted capability list) exists to remove the degrees of
  freedom that are **not** inputs, so that equal inputs give equal bytes.
  **Since the `path` field was dropped, `PATH` ordering is no longer an input**, and R9 got
  *stricter*, not looser: two runs whose `PATH` differs only in the order of two components
  that both hold a rostered command must now produce byte-identical files. Nothing the emitter
  writes depends on which component won, so an implementation that satisfies this by
  construction is the expected one — there is no work to do here, only work to avoid
  introducing. The converse still stands where it applies: a different `--agents` changes
  `harness-selected` (R7) and installing or removing a CLI changes which entries exist (R5/R6),
  and both are supposed to move the bytes. So the Builder must not "stabilize" the output by
  pinning it against the selection; that would break R7 in the name of R9.
- **The symlink guard comes first**, before the gate and before any detection, mirroring
  `escalation_arming_is_symlinked`. A symlinked roster is left entirely alone — no write, no
  reclaim (R12); reclaiming through a symlink would delete something outside `.harness/`.
- **Reclamation (R3) is the ungated path, not an error path.** Gate off + file present ⇒
  remove and `info` it, exactly as `write_escalation_arming` does when nothing resolves.
  **The trigger is the gate, and only the gate — "no CLI resolved" is not a reclaim
  condition.** This is the precedent's second disqualifying difference (after the
  `agent_selected` trap): `write_escalation_arming` reclaims when its detection comes back
  empty, because an empty arming file means nothing. An empty roster means something — *this
  machine can invoke none of the harness's front-ends* — and a consumer must be able to tell
  that from "the roster was never written". So gate on + nothing resolves ⇒ write the file with
  a well-formed `"workers": []`, per R1 (write it) and R5 (one entry per resolving key, hence
  none). The `roster_is_valid_json` case covers that shape deliberately, because the empty array
  and the last-entry separator are where a hand-rolled `printf` emitter breaks.
- **R8 is a negative requirement**, so it needs a test that could actually catch a violation —
  see the test contract. Asserting "the installer exited 0" proves nothing about it.
- **Presence is `command -v <name> >/dev/null 2>&1`, and its stdout is discarded.** One lookup
  per key, no execution, no `--version`. With no `path` field the lookup is used **only** as a
  boolean — the Builder never captures, canonicalizes or stores what `command -v` printed.
  That is deliberate, and it is the whole benefit of the spec's *Recorded decision 4*: that
  stdout is a **relative** value whenever the matching `PATH` component is relative (both
  `dash` and `bash` print `bin/claude` for `PATH=bin:…`; macOS `/bin/sh` does not, so it cannot
  even be observed there), it is environment-derived JSON content, and it can hold bytes a JSON
  string cannot represent. Discarded, none of that is this feature's problem. A Builder who
  "helpfully" records it re-opens all six review findings that decision closed.
- **JSON emission.** The Builder picks the style. **Two** constraints: the output is valid JSON
  (tested), and it is byte-stable across runs with identical inputs (R9).
  **There is deliberately no third, escaping constraint — the deletion is reasoned, not
  silent.** An earlier revision of this plan required every emitted string to be escaped so a
  parser recovered it byte-for-byte, because `path` was environment-derived. With `path` gone
  (spec → *Recorded decision 4*), every string in the file is a harness-authored literal from a
  closed set (see *Data model*): `key` from `AGENT_KEYS`, `command` from `WORKER_INVOKE`, the
  tags from the fixed vocabulary, and `generated_by` the fixed literal `harness-install.sh` —
  none holding `"`, `\` or a control character, none reachable by the operator or the
  environment. An escaper
  over inputs that provably need no escaping is **untestable code**: no fixture could tell it
  from its absence, so it would ship as an unverified guard, which is the shape this repo
  already refuses elsewhere. It is therefore not required.
  What replaces it is the **invariant**, and the Builder owes it as a comment beside the
  emitter: *every value emitted here is a harness-authored literal; a field carrying
  environment-derived content re-incurs class-wide JSON escaping* (`"`, `\`, and C0
  U+0000–U+001F), following `tools/change-size.sh`'s `_json_escape` — the artifact **E99-F08**
  shipped after a hand-rolled emitter handled control characters one reported bug at a time —
  and never `tools/pr-round-trend.sh`'s `sed` version, which covers only `\` and `"`. Adding
  such a field is a `schema` change anyway, so the obligation lands where a fixture can test it.
  **The valid-JSON constraint is not made redundant by that invariant.** A hand-rolled `printf`
  emitter still gets *structure* wrong independently of content — a trailing comma after the
  last `workers[]` entry, or a malformed `"workers": []` when no CLI resolves — which is the
  workload the `roster_is_valid_json` case retains.
