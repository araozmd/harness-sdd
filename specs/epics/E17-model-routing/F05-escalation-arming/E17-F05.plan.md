## 1. The verdict, in the installer

`resolve_model <front-end> <role>` is called **as-is**. The verdict function does nothing but
compare its two return values:

```sh
# escalation_verdict <front-end> — print raise|none|same|neither for that front-end.
# It calls resolve_model and compares; it re-derives NOTHING. That is the feature.
escalation_verdict() {
  _ev_b="$(resolve_model "$1" builder)"
  _ev_h="$(resolve_model "$1" builder-heavy)"
  if [ -n "$_ev_h" ] && [ "$_ev_h" != "$_ev_b" ]; then echo raise
  elif [ -z "$_ev_h" ] && [ -n "$_ev_b" ];          then echo none
  elif [ -z "$_ev_h" ] && [ -z "$_ev_b" ];          then echo neither
  else                                                   echo same
  fi
}
```

Four cells, total over the (empty × empty) product — no fifth case exists, so no default arm
can silently absorb a combination.

> **POSIX-sh hazard:** `_ev_b` / `_ev_h` are globals like every other shell variable here.
> Names are prefixed to avoid the clobbering that cost a debugging cycle in E17-F03.

## 2. The write site

Placed in `install_one` **after** §5e/§5f/§6 — every per-front-end artifact has been generated,
so `resolve_model`'s run-scoped warn-once ledger has already emitted its diagnostics and the
verdict adds no duplicate stderr.

```
for each selected front-end:      verdict := escalation_verdict(fe)
armed := (every verdict = raise) and (at least one front-end was selected)
gate  := any selected front-end has models_any → write, else remove
```

`models_any <fe>` is the existing gate `.gemini/agents/` uses; reusing it is what makes
"a fully-`inherit` target grows nothing" true by the same construction that already holds
elsewhere, rather than by a parallel condition that can diverge from it.

**Write** = `armed|blocked` on line 1, then `fe=verdict` lines in the fixed `$AGENT_KEYS`
order (deterministic content — the same target re-installed yields a byte-identical file).
**Remove** = `rm -f` only when the path is not a symlink and the file exists.

**Symlink guard** — same shape as `opencode_stamp_is_symlinked`:

```sh
escalation_arming_is_symlinked() { [ -L "$H/.escalation-arming" ]; }
```

On true: warn (`⚠️  .harness/.escalation-arming is a symlink — escalation arming verdict not
written`) and **return without writing or removing**. Never `rm` through it either: deleting
the symlink would silently un-arm a target on a path the operator did not ask about.

## 3. The second gate, in `tools/builder-role.sh`

The tool's purity contract is preserved by *locating* the artifact rather than searching for
it: `--arming <path>` if given, else `$(dirname "$_config")/.escalation-arming`. With no
`--config` there is no artifact and escalation is off — which is already the R7 behavior for a
missing config, so the two agree instead of interacting.

```
_armed=0
if [ -n "$_arming" ] && [ ! -L "$_arming" ] && [ -f "$_arming" ]; then
  case "$(head -n 1 "$_arming" | tr -d '[:space:]')" in armed) _armed=1 ;; esac
fi
```

`head -n 1` + whitespace strip mirrors `opencode_parallel_wanted`. Anything that is not exactly
`armed` — `blocked`, an empty file, garbage, an unreadable file — leaves `_armed=0`. The safe
direction is the *only* direction; there is no error path that can arm.

Escalation then requires `_threshold -gt 0` **and** `_armed -eq 1`. Both triggers pass through
the existing `_escalate` helper, so the complexity trigger cannot bypass the new gate — the
E17-F03 review already established that `0` must silence both, and the artifact is a second
switch of the same kind.

## 4. The two decline advisories

`_escalate` today emits one message. It gains a second, chosen by *why* it declined:

- threshold is 0 → the existing message, unchanged (the operator turned it off on purpose).
- artifact absent → `ℹ️  … no escalation verdict recorded — re-run harness-install.sh after
  giving models.builder-heavy a tier that resolves on your front-end`.
- artifact `blocked` → the same, plus the offending lines read back from the file, e.g.
  `blocked by: codex=none opencode=none`.

Reading the detail lines is the one place the tool parses more than a word, and it is
**advisory-only**: the decision was already made from line 1. A malformed detail line can
change the wording of a message and nothing else.

## 5. The default flip

`harness.config.yaml` and the `migrate_config` heredoc both move to `after_rejections: 2`.
`migrate_config` seeds only when the block is **absent**, so this changes fresh installs and
targets that never had the block — never an existing `0`. The E17-F03 test that asserts the
*upgrade* path re-seeds the key is re-based on `2`.

Order matters: the `escalation:` block's position in the `migrate_config` append sequence must
stay where E17-F03 put it, or `test_pr_loop.sh` R17's byte-identity contract (fresh install ≡
upgraded install) fails.

## 6. The prose sweep

The claim that changes is **"the harness deliberately does NOT try to infer this for you"** —
it now does, by asking the component that owns the answer. That sentence, or a paraphrase of
it, is in `harness.config.yaml`, `harness-install.sh`'s migrate heredoc, `tools/builder-role.sh`,
`agents/orchestrator.md`, `docs/WORKFLOW.md`, `CHANGELOG.md`, and the E17-F03 spec set. The
spec set is a **historical record and is not edited**; the other six are operator-facing and
must all move together.

E17-F03's lesson is explicit here: *a claim repeated in six files is six defects*. The sweep is
`grep -rn` for the claim's distinctive phrases across the installed body, not a walk of the
files this plan happens to list.
