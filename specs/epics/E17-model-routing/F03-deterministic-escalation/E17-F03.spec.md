# Deterministic escalation to `builder-heavy` — Functional Spec

## Context

E17-F02 shipped a heavier Builder. **Nothing calls it.** An operator who wants a struggling
task retried on a stronger model is still doing it by hand — noticing the struggle, then
re-running the session — which is exactly the gap E17 exists to close.

The epic is explicit that this must be **deterministic, never ad-hoc judgment**: the harness
escalates on a rule evaluable from recorded state, not on an agent's opinion that a task
"looks hard".

**ADR-0002 is binding and not revisited.** Escalation is routing: this feature chooses a role
*name*. It changes nothing about what `builder-heavy` does.

### What the wiring already provides

- **The round counter exists.** `agents/orchestrator.md` defines `round` = 1 on the first
  build, +1 on every `in-review → in-progress` bounce, recorded as a line in
  `progress/history.md` and stamped on `builder`/`reviewer` telemetry records. The brief is
  explicit: reuse it, do not invent a second source of truth.
- **The Architect writes specs, not the board.** `agents/architect.md` ends with *"tell the
  Orchestrator the feature is ready and let it set the status to `spec-ready`"*. The Architect
  has no board-write path at all.
- **Nothing machine-parses spec frontmatter today.** Agents read spec files; tools read
  `state/tasks.json`.
- **The harness already has a "deterministic tool the prose calls" pattern** —
  `pr-gate.sh`, `pr-stack-guard.sh`, `pr-round-trend.sh`, `change-size.sh`.

### Resolved during specification

**The rule ships as an executable tool, not as prose.** This is the load-bearing decision.
`tests/test_reviewer.sh` documents the alternative honestly: for a prose-only feature,
verification is *"grep the role files for the required clauses"*, and the one behavioral
criterion becomes **a documented manual check**. A grep proves a sentence exists; it cannot
prove two Orchestrator runs on the same recorded state pick the same role — which is the
epic's entire success criterion. A rule that only a language model evaluates is not
deterministic in any sense the epic would accept.

So the rule becomes `tools/builder-role.sh`: inputs in, role name out, no access to the
spec's prose and no judgment available to it. `agents/orchestrator.md` calls it and obeys the
answer. That makes the requirement genuinely testable and mutation-testable, and it matches
four existing tools rather than inventing a pattern.

**The complexity tag lives in the feature spec's frontmatter.** The brief left this open
between spec frontmatter, `tasks.md`, and the TaskStore, "with the cost stated". The
TaskStore is the better-validated home in the abstract — schema-governed, so a typo is caught
by `init.sh` — but **the Architect cannot write it**. Choosing the TaskStore would force one
of two changes well outside this feature:

- give the Architect a board-write path, a role-boundary change the harness has deliberately
  avoided (every board write goes through the Orchestrator); or
- have the Orchestrator transcribe the tag from spec to board, creating a second copy that
  can disagree with the first — and the harness has recorded what a body and its copy
  diverging costs (E99-F07).

The spec file is the artifact the Architect actually produces, so that is where the tag goes.
**The cost, stated:** the tag is not schema-validated, so a typo cannot be caught at
validation time. It is mitigated, not ignored — the vocabulary is closed, and any value that
is not exactly `complex` resolves to `standard` (R2): the safe direction, never a failure,
and reported so a typo is visible rather than silent.

**`escalation.after_rejections`, defaulting to 0, where any positive value enables.** One key
does both jobs — master switch and threshold — and this feature needs an off-switch because it
changes which model runs your builds, which costs money. Why the default is `0` rather than
`2` is the story below.

The usual objection is the universality invariant: shouldn't an unconfigured target keep
today's behavior, i.e. never escalate?

**The first version of this spec answered "it does, by construction" and that answer was
wrong.** The reasoning was: `models.builder-heavy: inherit` resolves to key omission, so on an
unconfigured target the heavy role resolves to the same model and escalating is a no-op. That
holds only for a **fully** unconfigured target. Codex found the counterexample (#3716706727),
reproduced on a real installed Claude target: set `models.builder: standard` and leave
`builder-heavy: inherit`, and the `builder` shim gets `model: sonnet` while `builder-heavy`
gets **no model key at all**. Escalating there abandons the operator's configured Builder
model for the session default — precisely when the build was struggling. A **downgrade**
wearing an escalation's name.

The first fix was to arm on the heavy role having a non-`inherit` tier. **That was also
wrong**, and the second review round found it (#3716777878): on `codex` and `opencode` a tier
stamps *nothing* without a matching `pin.<front-end>.<tier>`, so `models.builder: standard` +
`pin.codex.standard` + `builder-heavy: reasoning` with no `pin.codex.reasoning` gives
`builder.toml` a model and `builder-heavy.toml` none — the same downgrade, one level deeper.

Two findings on one function is the signal to **rewrite the rule, not patch it again**. Both
attempts were this tool re-deriving a subset of the installer's `resolve_model`, which owns
per-front-end alias tables and pin requirements; reproducing that here would keep producing a
new defect per front-end.

**So the tool stopped inferring. Escalation is an explicit opt-in, shipped OFF**
(`escalation.after_rejections: 0`, R12). A positive value turns it on with that threshold; `0`
disables **both** triggers. Enabling it is the operator asserting they configured a heavier
tier that actually resolves on their front-end — something the harness cannot verify from
here, and now says so in the docs instead of pretending to.

**Stated plainly, this is a scope reduction.** The brief's success outcome was "a task that
fails review twice is retried by `builder-heavy` automatically, without a human noticing".
It now requires a one-line opt-in first. That is the honest trade: the alternative shipped a
default that silently downgraded a struggling build on two of the five front-ends, and the
machinery is unchanged for anyone who turns it on.

**The threshold reads the round, not a count of `reject` lines.** `round` already means "one
more than the number of rejections": round 1 is the first build, round 3 is the first build
after two rejections. So the rule is `round > after_rejections`, which reuses the existing
counter exactly as the brief demands, instead of re-deriving the same number by pattern
matching prose in `progress/history.md`.

**Persistence across sessions falls out of that.** `progress/history.md` is durable and
committed, and `round` is carried on it. A feature whose first two rounds ran last week still
evaluates to round 3 today. The rule reads durable state only and has no session memory (R8).

**Telemetry keeps `phase: "builder"`.** The obvious move — emit `phase: "builder-heavy"` — is
wrong twice over, and `tools/telemetry-report.py` says so in code:

- `PHASES` is a **whitelist** and `phase not in PHASES → continue` (line 129), so every heavy
  build would be silently **dropped** from the report;
- the build↔review round count is `max(round)` over `phase in ("builder","reviewer")`
  (line 299), so a feature whose later rounds all ran heavy would report a **lower** round
  count than it actually took.

Adding `"builder-heavy"` to `PHASES` fixes the dropping but splits the Builder's duration
across two rows, so "how long did building take" becomes wrong for every consumer that does
not know to sum both. Instead the record keeps `phase: "builder"` and carries the actual role
in a separate field: additive, ignored by existing consumers, and the choice stays
recoverable (R11).

**Under `delegate`, escalation is a no-op — and says so.** `execution.builder.backend:
delegate` means the Builder writes no code; it invokes `<delegate_cmd> <feature-id>
<abs-spec-path>` and the external executor chooses its own model. The harness resolves no
model on that path, so "escalating" would change nothing while recording that it had. The
rule therefore returns `builder` under `delegate` and reports escalation as **inapplicable**,
so the history never claims an escalation that could not have happened (R9).

**Demotion stays unsolved, deliberately.** The brief puts it out of scope. Note that one-way
escalation is not an extra mechanism here — `round` only increases and the tag does not
change mid-feature, so monotonicity is a property of R3 rather than a rule beside it. Pinned
by a test anyway, so a future refactor cannot quietly introduce flapping.

## Requirements (EARS)

| R-id | Requirement |
|---|---|
| **R1** | A feature spec's frontmatter may carry `complexity:` with the closed vocabulary `standard \| complex`; when the key is absent the complexity shall be `standard`. |
| **R2** | When `complexity` carries a value outside the vocabulary, the resolved complexity shall be `standard` and the discrepancy shall be reported; it shall never fail the build. |
| **R3** | The builder role shall be `builder-heavy` when the complexity is `complex` **or** the current round exceeds `escalation.after_rejections`, and `builder` otherwise. |
| **R4** | The rule shall be evaluated by a deterministic tool with no access to spec prose: identical inputs shall always yield the identical role name. |
| **R5** | The round input shall be the **existing** build↔review counter; this feature shall add no second counter, no status value, and no TaskStore schema field. |
| **R6** | `escalation.after_rejections` shall default to `0` and be seeded in **both** the shipped `harness.config.yaml` and the installer's `migrate_config` block; `0` shall disable escalation entirely, and a positive value shall both enable it and set the threshold. |
| **R7** | While a target has no `escalation:` block and a spec carries no `complexity`, routing shall select `builder` with no warning and no failure. |
| **R8** | The rule shall read durable recorded state only, so a feature whose earlier rounds ran in a previous session shall resolve identically. |
| **R9** | While `execution.builder.backend` is `delegate`, the rule shall return `builder` and report escalation as inapplicable rather than as an escalation. |
| **R10** | The `progress/history.md` line for a build shall name the role spawned and which trigger selected it. |
| **R11** | The telemetry `phase` value shall remain `builder`; the record shall carry the spawned role in a separate field, leaving `PHASES` filtering and the max-round computation unchanged. |
| **R12** | Escalation shall be opt-in and ship disabled (`escalation.after_rejections: 0`); while it is disabled **neither** trigger shall escalate, a declined `complexity: complex` tag shall be reported without failing the build, and the rule shall not infer from model configuration whether escalating would help. |

## Out of scope

- Creating the role — E17-F02, already shipped in v0.56.0.
- Any change to what `builder-heavy` does (ADR-0002).
- **Demotion** back to the standard Builder, and any cost-based policy.
- The worker roster (E17-F04).
- Giving the Architect a board-write path (rejected above, with reasons).

## Non-functional

- **Backward compatible by construction** (R7), and inert until `models.builder-heavy` is
  given a tier (R12) — never merely because the two roles happen to resolve alike.
- Installed body ⇒ `VERSION` **MINOR** bump + CHANGELOG.
- POSIX sh / `dash`; green under `sh tools/run-tests.sh`.
- Budget: `change_size.max_requirements: 12`. This spec declares **12** — at the ceiling. R12
  was added during review to close the downgrade above; a thirteenth would require a split.

## ADR

No new ADR. This feature **applies** `ADR-0002` — escalation is routing, which is precisely
what the ADR settled — and adds no architectural decision of its own.
