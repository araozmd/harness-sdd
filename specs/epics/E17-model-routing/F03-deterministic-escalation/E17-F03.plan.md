The rule is the feature. Everything else points at it.

## 1. `tools/builder-role.sh` — the rule

```
tools/builder-role.sh <complexity> <round> [--backend <in-session|delegate>] [--config <path>]
  → stdout: `builder` | `builder-heavy`
  → stderr: one advisory line when a value was coerced (R2) or escalation was inapplicable (R9)
  → exit 0 always for a resolvable answer; non-zero only on usage error
```

Deliberately **pure**: it reads its inputs and, optionally, `escalation.after_rejections`
from the config. It never reads `progress/history.md`, never reads the spec body, never calls
`git`. That is what makes R4 testable — a tool that could consult prose could not be proven
deterministic.

Resolution order, and the reason for each step:

1. **Backend.** `delegate` ⇒ print `builder`, advise "escalation inapplicable", stop. Checked
   **first** so no other input can produce a heavy answer the executor would ignore (R9).
2. **Complexity.** Exactly `complex` ⇒ heavy. Empty/absent ⇒ standard, silently (R1, R7).
   Anything else ⇒ standard **plus an advisory line** (R2) — the coercion is safe, and the
   typo must not be.
3. **Round vs threshold.** `after_rejections` = the config value, else `2`. `0` disables the
   round arm entirely — not "escalate on every round", which is what a naive `round > 0`
   would do and is the opposite of what `0` means to an operator turning this off.
   Non-numeric or negative ⇒ fall back to `2` with an advisory, same safe direction as (2).
4. Otherwise `builder`.

Threshold arithmetic, stated once so it is not re-derived: `round` is **one more than the
number of rejections** (round 1 = first build, round 3 = first build after two rejections).
So "after two rejections" is `round > 2`, i.e. `round > after_rejections`.

`escalation.after_rejections` is parsed with the same shell-only scalar reader the config
already uses for other keys — no new dependency, and `dash`-safe.

## 2. Config, both copies

The E17-F02 lesson applies verbatim: `migrate_config` seeds a block only when the block is
**absent**, and the shipped `harness.config.yaml` is copied verbatim on a fresh install.
Missing either makes a fresh target and an upgraded target diverge. A mutation in the test
contract pins it, because that is exactly the defect that was caught last feature.

New top-level block, append-only at EOF, matching the `models:`/`pr_loop:` shape:

```yaml
escalation:
  # After this many Reviewer rejections, subsequent builds go to `builder-heavy`.
  # 0 disables rejection-based escalation. INERT until models.builder-heavy is set:
  # while it is `inherit`, builder-heavy resolves to the same model as builder.
  after_rejections: 2
```

## 3–4. The tag and who writes it

`specs/_templates/feature.spec.md` gains `complexity: standard` with the vocabulary in a
trailing comment, beside the existing `sdd:`/`autonomous:` scalars.

`agents/architect.md` gains the instruction to set `complex` **on a stated basis**, not a
vibe — the epic forbids judgment as the *routing* mechanism, and a tag chosen by feel would
reintroduce it one step earlier. The wording ties it to signals the Architect already
produces (R-id count against the budget, an ADR the feature must honor, a spec that needed
splitting), so the tag is defensible from the spec itself.

## 5. `agents/orchestrator.md`

At the `in-progress` dispatch, before spawning:

```sh
role="$(sh "$HARNESS_DIR/tools/builder-role.sh" "<complexity>" "<round>" \
          --backend "<execution.builder.backend>" --config "$HARNESS_DIR/harness.config.yaml")"
```

Then spawn `$role`. Two properties are stated as prose *because the tool cannot enforce them*:
the Orchestrator must pass the **spec's** complexity and the **existing** round, and must not
substitute its own opinion for the tool's answer.

Recording (R10, R11):

- history line names the role and the trigger, e.g.
  `E17-F03 in-progress → in-review (builder-heavy round 3: escalated after 2 rejections)`;
- the telemetry `phase` record keeps `phase: "builder"` and adds `"role": "builder-heavy"`.

## 6–7. Docs and tests

`docs/WORKFLOW.md` documents the rule, the knob, the `0` off-switch, that it is inert until
`models.builder-heavy` is configured, and the delegate no-op.

`tests/test_escalation.sh` exercises the **tool** directly — a truth table over
(complexity × round × threshold × backend) — plus the installer-level config seeding. The
prose in `agents/*.md` gets the repo's role-content-assertion treatment, and the test contract
states plainly what that does and does not prove.

## Risks

- **The prose half is weakly testable and must not be over-claimed.** Grepping
  `agents/orchestrator.md` for "call `builder-role.sh`" proves the sentence is present, not
  that a running Orchestrator obeys it. Recorded in the test contract as a named gap rather
  than dressed up as coverage; putting the rule in a tool is what shrinks that gap to the
  call site instead of the whole rule.
- **`0` is the interesting boundary.** `round > 0` is true for every round, so a naive
  implementation turns the off-switch into always-escalate. Covered by its own case and its
  own mutation.
- **The threshold is off-by-one bait.** `round > n` vs `round >= n` differ by exactly one
  rejection. Pinned with the round-3 boundary asserted from both sides.
