# Per-role model selection — Functional Spec

## Context

Every sub-agent the Orchestrator spawns today inherits whatever model the host CLI
session is running. The Architect's design work and the Builder's mechanical execution
of an already-approved `tasks.md` therefore cost the same per token, and there is no
place to express *"Architect on the reasoning tier, Builder on the standard tier, Scout
on the cheap tier"*. The user is the harness operator who pays for several agent
subscriptions at once (Claude Code Max, ChatGPT Pro via Codex, OpenCode Go) and wants
each SDD role on the model that fits its job.

This feature adds a **front-end-agnostic** `models:` block to `harness.config.yaml` and
teaches `harness-install.sh` to stamp the resolved model into the **native
agent-definition convention of each selected front-end**. The config schema is generic;
the stamping is per-front-end and correct for each, because Claude Code, Codex,
OpenCode, Antigravity and Gemini each configure agents differently and their value
vocabularies are mutually incompatible (verified — see `progress/E17-F01-cli-model-surfaces.md`).

Nothing here is dynamic: config → generated file, and a target that configures nothing
behaves exactly as it does today.

## Business rules

- **BR1 — Opt-in and inert by default.** The seeded `models:` block resolves every role
  to `inherit`. An absent block, an empty block, and an all-`inherit` block are all
  behaviorally identical to the pre-feature installer. This is the harness's
  single-CLI universality invariant: model configuration is never mandatory.
- **BR2 — Tier aliases are the currency; pinned ids are the escape hatch.** The tier
  vocabulary is `reasoning | standard | cheap | inherit`. Built-in tier→model mappings
  use only each vendor's **floating** alias (`opus`/`sonnet`/`haiku`, `pro`/`flash`), so
  a new model release is picked up without a harness change. The harness ships **no
  frozen model id** as a default.
- **BR3 — Omission beats guessing.** "Use the session default" compiles to **key
  omission** on all five front-ends — the literal string `inherit` is never written,
  because it is an error on OpenCode and unknown on Codex. Where a tier cannot be
  resolved without inventing a value, the key is omitted and the operator is told how
  to pin one.
- **BR4 — Only selected front-ends are stamped.** The existing E08-F01 selection
  (`resolve_agents` / `agent_selected` / `.harness/.agents`) is the sole gate. A
  front-end the operator did not select is never written to.
- **BR5 — Stamping is a deterministic pure function** of (config file contents, role,
  front-end). Deselection reclaims harness-generated files by byte-comparing them
  against a *freshly regenerated* reference, so any non-determinism would make
  previously-installed files permanently unremovable.
- **BR6 — Reclamation never deletes a user-edited file; regeneration always overwrites
  one.** These are two different paths with two different rules, and this feature changes
  neither. **Deselection (reclamation)** deletes only byte-pristine harness output — an
  artifact the operator edited is left in place with a warning (R23). **Re-install
  (regeneration)** unconditionally rewrites every harness-generated artifact from the
  current config, including one the operator edited, exactly as `.claude/agents/*.md` and
  `.agents/agents/*.md` have always behaved (R26). The pristine byte-compare guards the
  *delete* path only; it has never guarded re-stamping. Every artifact this feature adds
  inherits both rules unchanged. The one exception is `opencode.json`, which is a
  *shared* file the harness does not solely own and therefore keeps its own explicit
  never-clobber rule on the regeneration path too (R20).
- **BR7 — The tier vocabulary is forward-compatible.** An unrecognized tier is a
  warning, not a fatal error, so a config written for a newer harness never blocks an
  upgrade on an older installer.

## Architecture alignment

**ADRs touched: none.** ADR-0001 governs how `next()` selects the next task
(deterministic selection in `tools/next-task.mjs`). This feature changes only the
installer's generated glue and `harness.config.yaml`; it does not touch task selection,
Orchestrator routing, `store/tasks.schema.json`, or the status vocabulary. It does,
however, adopt ADR-0001's *spirit* in BR5/R21: the stamped output is deterministic code,
not a model judgment call.

## Acceptance criteria (EARS)

> Tier vocabulary: `reasoning | standard | cheap | inherit`.
> Roles (6, matching what the installer already emits): `orchestrator`, `architect`,
> `builder`, `reviewer`, `scout`, `doc-critic`.
> Front-end keys (5, the existing `$AGENT_KEYS`): `claude`, `gemini`, `opencode`,
> `antigravity`, `codex`.

### Config schema & migration

- **R1** — When the installer performs a fresh install, the seeded
  `.harness/harness.config.yaml` shall contain a top-level `models:` block carrying
  `default: inherit` and an `inherit` entry for each of the six roles.
- **R2** — When the installer upgrades a target whose existing
  `.harness/harness.config.yaml` has no `models:` block, `migrate_config` shall append
  the same block at end-of-file while leaving every pre-existing line (values **and**
  comments) byte-for-byte intact.
- **R3** — When the installer runs against a config that already contains a `models:`
  block, it shall leave `.harness/harness.config.yaml` byte-identical (no duplicated
  block, no duplicated key), including when the `models:` line carries a trailing
  comment.

### Resolution (config → native value)

- **R4** — The installer shall resolve a role's tier by taking `models.<role>` when it
  is non-empty, otherwise `models.default` when it is non-empty, otherwise `inherit`.
- **R5** — Where a role resolves to the tier `inherit`, the installer shall **omit** the
  model key from that role's agent definition on every front-end, and shall never write
  the literal string `inherit` into any generated artifact.
- **R6** — Where a role resolves to `reasoning`, `standard` or `cheap` and no pin
  applies, the installer shall write that front-end's built-in **floating alias** for
  the tier on `claude` and `gemini`, and shall write **no model id that
  is version-pinned by the harness**. (Antigravity routing retired — see **A2**.)
- **R7** — If a role resolves to `reasoning`, `standard` or `cheap` on `codex` or
  `opencode` and no pin applies, then the installer shall omit the model key for that
  role on that front-end and shall emit exactly one informational message naming the
  front-end and the `models.pin.<front-end>.<tier>` key the operator must set.
- **R8** — Where `models.pin.<front-end>.<tier>` is non-empty, the installer shall write
  that value **verbatim** into that front-end's artifact for every role on that tier,
  overriding any built-in alias.
- **R9** — If a role's tier is not one of `reasoning`, `standard`, `cheap`, `inherit`,
  then the installer shall write a warning to stderr naming the role and the
  unrecognized tier, resolve that role as `inherit`, and complete the install with exit
  status 0.
- **R10** — If a pin for the `opencode` front-end does not contain a `/` separator, then
  the installer shall write a warning to stderr, omit the model key for the affected
  roles from `opencode.json`, and never write that value into `opencode.json`.

### Backward compatibility

- **R11** — While `.harness/harness.config.yaml` contains no `models:` block, or while
  every role resolves to `inherit`, the installer shall produce a target tree
  byte-identical (excluding `.harness/harness.config.yaml` itself) to a run with the
  block absent: no model key in any `.claude/agents/*.md`, no `model` member in
  `opencode.json`, no model key in any `.agents/agents/*.md`, and no `.gemini/agents/`
  or `.codex/agents/` directory created.

### Stamping — front-ends that already have a per-role artifact

- **R12** — Where `claude` is selected and a role resolves to a concrete value, the
  installer shall emit `model: <value>` as a frontmatter key in
  `.claude/agents/<role>.md`, alongside the existing `name`, `description` and `tools`
  keys.
- **R13** — Where `antigravity` is selected and a role resolves to a concrete value, the
  installer shall emit `model: <value>` as a frontmatter key in
  `.agents/agents/<role>.md`, alongside the existing `description` key.
- **R14** — Where `opencode` is selected and a role resolves to a concrete value, the
  installer shall emit a `"model": "<value>"` member inside that role's
  `agent.<role>` object in `opencode.json`.

### Stamping — front-ends that need a new native per-role artifact

- **R15** — Where `gemini` is selected and at least one role resolves to a concrete
  value, the installer shall create `.gemini/agents/<role>.md` for each of the six
  roles, each carrying markdown frontmatter with a `name`, a `description`, and a
  `model:` key for the roles that resolved, and a body that points at the canonical
  `.harness/agents/<role>.md` without duplicating it.
- **R16** — Where `codex` is selected and at least one role resolves to a concrete
  value, the installer shall create `.codex/agents/<role>.toml` **inside the target
  repository** for each of the six roles, each carrying a `model = "<value>"` key for
  the roles that resolved, and shall write **no** per-role agent file into
  `$CODEX_HOME` / `$HOME/.codex`.
- **R17** — While no role resolves to a concrete value for `gemini` (resp. `codex`), the
  installer shall not create `.gemini/agents/` (resp. `.codex/agents/`) at all.

### Selection gating

- **R18** — While a front-end key is not in the resolved selection, the installer shall
  create none of that front-end's agent artifacts and shall stamp no model for it, even
  when the `models:` block names a tier for every role.

### Idempotent re-stamping

- **R19** — When the installer is re-run after the operator changes a tier or a pin, it
  shall update the stamped value in every regenerated artifact
  (`.claude/agents/*.md`, `.agents/agents/*.md`, `.gemini/agents/*.md`,
  `.codex/agents/*.toml`) to the new value, with exactly one model key per role
  definition.
- **R20** — When `opencode.json` already exists, the installer shall regenerate it in
  place **only** when it is byte-identical either to `.harness/.opencode.stamp` (the
  byte copy of the last opencode.json the installer generated) or to a freshly
  generated model-free body; otherwise it shall leave the file untouched and warn that
  model changes were not applied.
- **R21** — When the installer is run twice with an unchanged `.harness/harness.config.yaml`
  and an unchanged selection, every artifact it stamps shall be byte-identical between
  the two runs.
- **R26** — When the installer is re-run while a role resolves to a concrete value, the
  installer shall regenerate that role's stamped per-role artifact on every selected
  front-end (`.claude/agents/<role>.md`, `.agents/agents/<role>.md`,
  `.gemini/agents/<role>.md`, `.codex/agents/<role>.toml`) from the current configuration
  **even when that file carries a user edit**, matching the pre-existing generated-glue
  contract for `.claude/agents/` and `.agents/agents/`. `opencode.json` is excluded (R20
  governs it), and R23 — an edited artifact survives *deselection* — holds unchanged.

### Deselection

- **R22** — When a previously-selected front-end is deselected on a re-run while
  `.harness/harness.config.yaml` is unchanged, the installer shall reclaim that
  front-end's stamped per-role artifacts through the existing pristine byte-comparison,
  leaving no orphaned stamped file and no empty harness-created directory.
- **R23** — If a stamped per-role artifact has been edited by the user, then on
  deselection the installer shall leave that file in place and warn, deleting only
  byte-pristine files.

### Documentation & release

- **R24** — The installer shall record every artifact type it can generate for models
  (`.gemini/agents/*`, `.codex/agents/*`, `.harness/.opencode.stamp`) in the generated
  `.harness/manifest.txt`, and `docs/INSTALL.md` shall document the `models:` block, the
  tier vocabulary, and the per-front-end value rules.
- **R25** — The repository `VERSION` shall be bumped by a SemVer **MINOR** increment and
  `CHANGELOG.md` shall carry a corresponding entry describing the `models:` block.

## Out of scope

- The dual Builder (`builder-heavy`) and the escalation rules (Architect complexity tag,
  two-rejection promotion) — **E17-F02**. This feature deliberately keys tiers off role
  *names*, so adding a second Builder variant later is a new role name in the same
  one-level map: **no config migration required**.
- The worker roster and any invocation of non-host CLIs — **E17-F03**.
- `pr-loop` migration — a separate epic.
- Any runtime model switching by the Orchestrator mid-session.
- Validating a pinned model id against a vendor's model list. The installer cannot know
  those lists (only the syntactic OpenCode `provider/model` guard in R10 is applied).
- Detecting the installed version of any front-end CLI. The Antigravity `model:`
  frontmatter needs `agy` ≥ 1.1.5 and is inert below it; this is documented, not probed.
- Choosing the model of the **host session** itself. The Orchestrator drives the session
  the operator launched; `models.orchestrator` only applies where the orchestrator is
  spawned as a sub-agent (Claude) or is the configured primary agent (OpenCode).
- Per-developer local model overrides (the E09-F02 layering question) — not added here.

## Open questions

- **Scope size.** Five front-ends, two of which need a brand-new artifact type, is a
  large single feature. `E17-F01.plan.md` § *Recommended split* proposes cutting it at a
  clean seam (R1–R14 + R18–R25 first; R15–R17 second) that needs **no** config
  migration to complete later. The human should confirm one-shot vs split before the
  Builder starts.
- **Unconfirmed vendor surfaces (accepted risk, recorded).** Project-local
  `.codex/agents/` discovery, Gemini's exact required frontmatter keys, and Antigravity's
  acceptance of anything beyond `inherit|flash|pro` are all unconfirmed
  (`progress/E17-F01-cli-model-surfaces.md`). In every case the failure mode of being
  wrong is an **inert file**, never a broken run — which is why omission-over-guessing
  (BR3) and the OpenCode format guard (R10) are the load-bearing safety rules.
- **Upstream reliability.** Two open upstream issues allege that Codex and OpenCode
  sub-agents ignore configured models. Neither reproduced during research. The harness
  is responsible for writing the correct configuration, not for the vendor honoring it.

## Amendments

### A1 — BR6 disambiguated; R26 added (2026-07-27, PR #61)

**What was ambiguous.** The Codex review of PR #61 raised a P1 against the re-stamp path
([`#61 (discussion_r3655261138)`](https://github.com/araozmd/harness-sdd/pull/61#discussion_r3655261138)):
re-running the installer overwrites an edited `.gemini/agents/<role>.md` or
`.codex/agents/<role>.toml`, which it read as violating BR6. The original BR6 admitted
**two** readings and that was the real defect:

1. *Sentence 1 literal* — "a user-edited file is never destroyed" forbids overwriting an
   edited file on **any** run, so `.gemini`/`.codex` should diverge from their siblings.
2. *Sentence 2 governs* — the existing contracts extend **unchanged**, and the existing
   contract for harness-generated role glue is overwrite-on-reinstall.

**Adjudication (human, on PR #61): reading 2 governs. The shipped behavior is correct.**
Three facts decided it:

- **Established precedent.** Harness-generated role glue has always been regenerated on
  every install. Verified empirically on this branch: appending a line to
  `.claude/agents/architect.md` and re-running the installer wipes the edit;
  `.agents/agents/*.md` behaves identically. `.gemini/agents/` and `.codex/agents/`
  overwriting on re-install is therefore consistent with every sibling artifact, not a
  divergence.
- **The pristine compare guards deletion, not regeneration.** `remove_if_pristine` is
  what stops the installer *deleting* a file it does not own on the **deselection** path.
  It has never gated re-stamping.
- **Reading 1 would break R19.** R19 requires a re-run after a tier or pin change to
  update the stamped value in every regenerated artifact. Skipping edited files would
  silently freeze that role's model stamp forever — the same silent-staleness class as
  the round-1 P1 the same reviewer correctly caught.

**What changed.** BR6 was rewritten so only one reading survives (reclamation ≠
regeneration), and **R26** was added to pin the re-stamp side of the contract explicitly
so the ambiguity cannot return. **No behavior changed**: R19, R20 and R23 are untouched,
and no installer code was modified by this amendment. R26 needs a new test (see
`E17-F01.tests.md`), which is the only Builder work it creates.

### A2 — Antigravity model routing retired (2026-07-30, PR #87)

**What happened.** E99-F09 (PR #87) migrated the Antigravity glue to the Agent Skills
layout, and an early round of its review kept per-role routing by stamping `model:` into
`.agents/skills/<role>/SKILL.md`. A later round
([`#87 (discussion_r3682228770)`](https://github.com/araozmd/harness-sdd/pull/87#discussion_r3682228770))
established that this surface does not exist: **Agent Skills frontmatter defines no
`model:` key** — a skill is procedural context, not an agent execution configuration —
and a schema-validating consumer may reject the unknown key outright. No other
workspace-local Antigravity surface carries per-role models (the bare-subagent path is
unconfirmed per the E07 research), so there is nothing to route through.

**Adjudication: R6/R13 are retired for `antigravity`.** The installer emits **no**
`model:` key in any `.agents/skills/` artifact, for any role, and `models.*` tiers have
no Antigravity surface to land on. The built-in antigravity rows in `model_alias` remain
**only** so the frozen ≤0.47.0 legacy-persona emitter can reproduce old bytes for the
upgrade reclaim; no live artifact resolves an antigravity model. Tests R6/R13/R19/R26 in
`tests/test_model_routing.sh` assert the **absence** of the key; `docs/INSTALL.md`'s
tier and landing tables no longer list the front-end.
