# Installer-stamped escalation arming — Functional Spec

## Context

E17-F03 shipped the escalation machinery and then had to ship it **off**
(`escalation.after_rejections: 0`). Its brief's success outcome was *"a task that fails review
twice is retried by `builder-heavy` automatically, **without a human noticing**"*. Today it
needs a one-line opt-in first. This feature buys the default back.

It shipped off because two review findings, both reproduced on real installed targets, showed
that escalating can **downgrade** the very build that is struggling:

- **#3716706727** — `models.builder: standard` with `models.builder-heavy: inherit` (the
  shipped default) gives the Builder shim `model: sonnet` and the heavy role **no model key**.
  Escalating abandons the operator's configured Builder model for the session default.
- **#3716777878** — arming on "the heavy tier is not `inherit`" fails on `codex` and
  `opencode`, where a tier stamps **nothing** without a matching `pin.<front-end>.<tier>`. So
  `builder: standard` + `pin.codex.standard` + `builder-heavy: reasoning` (unpinned) gives
  `builder.toml` a model and `builder-heavy.toml` none — the same downgrade, one level deeper.

Both attempts were `tools/builder-role.sh` **re-deriving a subset of the installer's
`resolve_model`**, which owns the per-front-end alias tables (`model_alias`) and the pin rules.
Two findings on one function is the signal to rewrite the rule, not patch it a third time.

**ADR-0002 remains binding.** Escalation is routing: this feature still only chooses a role
*name*, and changes nothing about what `builder-heavy` does.

### Resolved during specification

**The installer answers the question, because the installer is the only thing that can.**
`install_one` already calls `resolve_model <front-end> <role>` for every role × selected
front-end while generating `.gemini/agents/`, `.codex/agents/`, `opencode.json` and the
Antigravity personas. It therefore already knows, for each front-end it just stamped, exactly
what `builder` and `builder-heavy` resolved to. The verdict is a **byproduct of a call that
already happens** — not a reimplementation, which is the whole point of the feature. If it
could not be produced this way, the right outcome would be to abandon the feature rather than
approximate `resolve_model` a third time.

**The verdict is a file, not a config key.** `harness.config.yaml` is operator-owned. Writing a
*derived* value into it means the installer rewrites a line the operator can also edit: their
edit looks authoritative, is stale the moment a pin changes, and is silently clobbered on the
next run. The cost of the file instead is one more `.harness/` artifact with a write path, a
symlink guard and a removal rule — bounded, and the same cost `.harness/.opencode.stamp` and
`.harness/.model-agents/` already pay. `.harness/.opencode-parallel` is the closest precedent:
a marker whose content is a *verdict the installer computed*, read later by a decision.

**Shape: `.harness/.escalation-arming`, first line the verdict, then one line per front-end.**

```
blocked
claude=raise
codex=none
```

The first line is exactly one word — `armed` or `blocked` — so the consuming rule needs no
parser. The remaining lines exist for one reason: a decline has to be **legible**. "Escalation
is off" is not actionable; "`codex=none`" tells the operator which front-end lacks a
`pin.codex.<tier>` and is one edit from fixed.

Per-front-end vocabulary, derived from what `resolve_model` returned for the two roles
(`B` = builder's value, `H` = builder-heavy's, either possibly empty):

| verdict | condition | meaning |
|---|---|---|
| `raise` | `H` non-empty and `H ≠ B` | escalating actually changes the model |
| `none` | `H` empty, `B` non-empty | **the downgrade** — both review findings are this cell |
| `same` | `H = B`, both non-empty | escalating is a no-op that still records a role change |
| `neither` | `H` and `B` both empty | both inherit the session model — a no-op, no downgrade |

**Only `raise` arms.** The brief left `same`/`neither` open. They are not *harmful* — neither
downgrades — but arming on them spends a build round, a `progress/history.md` line and a
telemetry record announcing an escalation that **provably cannot change the outcome**: the
build re-runs on the identical model and fails the identical way, while the operator reads
that a heavier Builder was tried. A misleading record is worse than a legible decline, and the
decline (`same` / `neither`) names exactly what to configure. So the rule arms only where it
can state something true.

**The honest limit, stated rather than hidden: the verdict proves the model *changes*, not
that it is *stronger*.** `resolve_model` returns opaque vendor strings and the harness cannot
rank them — `pin.claude.reasoning: haiku` reads as `raise`. Ranking lives in the tier
vocabulary the operator chose (E17-F01), which is their assertion to make. What this feature
eliminates is the **downgrade-to-nothing** case — which is the one both findings named, and
the one an operator cannot see coming. It does not claim to police model strength, and no doc
may say it does.

**Conservative AND across the selected front-ends, not a per-front-end answer at build time.**
`tools/builder-role.sh` runs inside the Orchestrator's session and **cannot know which
front-end it is running under**: the config does not say, and the five front-ends are chosen at
install time, not at build time. Passing the front-end as an argument would only move the guess
into `agents/orchestrator.md`, where it is prose and untestable. So the artifact carries one
answer covering every selected front-end: `armed` iff **every** selected front-end is `raise`.

**The cost, stated:** a mixed target where four front-ends would raise and one is missing a pin
gets no escalation *anywhere*, not even under the four that are configured. That is deliberate
— the AND never downgrades anyone, which is the invariant both review rounds were about — and
the `blocked` line names the offending front-end, so the fix is one pin and one re-run.

**An absent artifact means escalation is off.** Two situations produce absence: a target that
has not re-run the installer since this release, and a target where model routing resolves
nothing at all (every role `inherit` — the shipped default). Both have the same remedy —
configure `models.builder-heavy` and re-run `harness-install.sh` — so folding them together
costs nothing and the advisory is correct in both. Escalating on absence would be exactly the
unverified guess this feature exists to delete.

**A verdict must describe what the front-end will RUN, not what the config asks for.** Those
diverge exactly where the installer declines to rewrite a live artifact it does not own: an
edited `opencode.json` (§6 leaves it untouched and says *"model routing changes were NOT
applied"*), or a foreign, edited, or symlinked `.codex/agents/builder*.toml`. In each case
`resolve_model` still reports the *desired* model while the role on disk keeps whatever it had
— so the verdict would read `armed` for a front-end that runs the build with no heavy model at
all. The same downgrade, through a different door.

So the installer keeps a **stamp ledger** and records such a front-end as `unstamped`, which
blocks. Enumerated rather than assumed: only `codex` and `opencode` have refusal branches at
all — `claude`, `gemini` and `antigravity` write their per-role artifacts unconditionally — and
within `codex` there are four distinct refusal paths, not the two the finding named. The ledger
is a **file**, not a shell variable, because §5f iterates `ag_personas | while … read`, a
pipeline whose body POSIX sh runs in a subshell; a variable set there would die at `done` and
the ledger would silently always read empty, failing *open*. It is scoped to `builder` and
`builder-heavy`: a hand-edited `scout.toml` says nothing about whether escalating raises the
Builder's model, and blocking on it would be a guard firing on the wrong signal.

**Gating the write on "model routing resolved something" is what keeps an unconfigured target
unchanged.** A fresh install with every role on `inherit` must not grow a file a
never-configured target lacks — the constraint `.gemini/agents/` already obeys via
`models_any`. Same gate here; and when an operator switches every role back to `inherit`, the
next run **removes** the artifact rather than orphaning a stale `armed`. That is the
reclamation `reclaim_model_agents` performs for the per-role stamps.

**A symlinked artifact is never followed, on either side.** The installer refuses to write
through it and warns, leaving it untouched; the rule treats it as **absent**, i.e. escalation
off. This is the `.opencode.stamp` / `.model-agents` rule (E17-F02 R20), and here it is
load-bearing rather than hygienic: a followed symlink is a path by which something outside
`.harness/` could assert `armed` and change which model runs a build.

**The default returns to `2`, and escalation now needs two independent yeses.**
`escalation.after_rejections` keeps its E17-F03 vocabulary — it is still both threshold and
master switch, and `0` is still the operator's hard off-switch. What changes is the shipped
value and the addition of a second gate: escalation fires only when the threshold is positive
**and** the artifact says `armed`. The operator's `0` can veto a correctly-armed target; the
artifact can veto a positive threshold. Neither alone suffices.

**Upgrade note, which is a real behavior gap and not a footnote.** `migrate_config` seeds a
block *only when the block is absent*. A target already carrying `escalation.after_rejections:
0` from v0.57.0 keeps its `0` — the installer will not rewrite an operator-owned value it
cannot distinguish from a deliberate off-switch. Those targets get automatic escalation only
after editing the key themselves. Fresh installs get `2`. This is stated in the CHANGELOG
rather than solved, because the alternative — rewriting a `0` the operator may have chosen — is
worse than the gap.

## Requirements (EARS)

| R-id | Requirement |
|---|---|
| **R1** | The installer shall derive the arming verdict from `resolve_model`'s own return values for `builder` and `builder-heavy`; this feature shall contain no second implementation of model resolution, alias lookup, or pin handling. |
| **R2** | The verdict shall be recorded at `.harness/.escalation-arming`, whose first line is exactly `armed` or `blocked` and whose remaining lines are `<front-end>=<raise\|none\|same\|neither>`, one per front-end selected on that run. |
| **R3** | The first line shall be `armed` only when every selected front-end's verdict is `raise`; any `none`, `same`, or `neither` shall yield `blocked`. |
| **R4** | The artifact shall be written on an install run where at least one selected front-end resolves at least one role to a concrete model, and removed on a run where none does, so a fully-`inherit` target never grows it. |
| **R5** | Neither the installer nor the rule shall follow a symlinked `.harness/.escalation-arming`: the installer shall warn and leave it unchanged, and the rule shall treat it as absent. |
| **R6** | `tools/builder-role.sh` shall escalate only when the artifact's first line is `armed`; an absent, symlinked, unreadable, or `blocked` artifact shall route to `builder`. |
| **R7** | Escalation shall require **both** a positive `escalation.after_rejections` and an `armed` artifact; either one alone shall route to `builder`, and this shall hold for the complexity trigger as well as the round trigger. |
| **R8** | A declined escalation shall report a reason distinguishing "no verdict recorded" from "blocked", naming the blocking front-ends in the latter case, without failing the build. |
| **R9** | `escalation.after_rejections` shall default to `2` in **both** the shipped `harness.config.yaml` and the installer's `migrate_config` block; `0` shall remain the operator's hard off-switch, disabling both triggers. |
| **R10** | The rule shall stay pure: its inputs shall be its arguments, one config scalar, and this artifact only — never `progress/`, the spec body, or `git`. |
| **R11** | Every operator-facing statement of the escalation default or its preconditions shall agree with the shipped config and with the tool's behavior under it. |
| **R12** | While the installer declines to rewrite a selected front-end's live model-routing artifact, that front-end's verdict shall be `unstamped` and the overall verdict shall be `blocked`, so a verdict never describes a model the front-end will not run. |

## Out of scope

- Any change to `resolve_model`, `model_alias`, or the tier vocabulary (E17-F01).
- Any change to what `builder-heavy` does — **ADR-0002 still binds**.
- Ranking model strength; see the stated limit above.
- Demotion, cost-based policy, and the worker roster (E17-F04).
- Rewriting an existing target's `after_rejections: 0` on upgrade (stated above, deliberately
  not solved).

## Non-functional

- **An unconfigured target is unchanged** (R4): no new file, and escalation off exactly as
  today.
- Installed body ⇒ `VERSION` **MINOR** bump + CHANGELOG.
- POSIX sh / `dash`; green under `sh tools/run-tests.sh`.
- Budget: `change_size.max_requirements: 12`. This spec declares **12** — at the ceiling. R12
  was added under review (Codex #3717508457) to close the case where the config's answer and
  the artifact on disk diverge; a thirteenth would require a split.

## ADR

No new ADR. This feature **applies** `ADR-0002` (escalation is routing) and the E17-F01
resolver ownership it already established; it adds no architectural decision of its own.
