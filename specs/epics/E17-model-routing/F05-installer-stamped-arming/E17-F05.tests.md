## Anti-tautology

- **"Blocked routes to builder" is also satisfied by escalation being broken outright.**
  Every artifact-negative case runs its **positive control in the same invocation set**: the
  identical complexity/round/threshold with an `armed` artifact must return `builder-heavy`
  first. Without it the whole suite passes against a tool that lost the ability to escalate.

- **"No artifact written" is also satisfied by the installer failing.** `artifact_written_and_reclaimed`
  asserts the install **exited 0** and that a *configured* run in the same test **did** write the
  file. Absence only means something once presence has been demonstrated on the same code path.

- **Reclamation is also satisfied by never writing.** The removal leg installs configured
  (file exists — asserted), then re-installs with every role `inherit`, then asserts the file
  is gone. Asserting only the final absence would pass against an installer that never wrote it.

- **The symlink case is absence-shaped twice over.** It asserts (a) the symlink still exists and
  still points where it did, (b) its **target file is byte-unchanged** — a sentinel written
  before the run survives, and (c) a warning was emitted. "The sentinel survived" alone is
  also satisfied by the installer never writing anything at all, so the case pairs it with a
  non-symlinked run in the same test that *does* rewrite the artifact.

- **The four-cell table can be faked by a constant.** `verdict_truth_table` requires all four
  distinct verdict words to have been **observed** across its configs, and fails if the set of
  distinct values it saw is not exactly `{raise, none, same, neither}`. A function returning a
  constant, or collapsing `same` into `raise`, cannot produce the required set.

- **`same` vs `raise` is the cell a lazy implementation merges.** Checking only "heavy resolves
  to something" passes every case except this one. The table includes a config where `builder`
  and `builder-heavy` resolve to the **identical** value via different routes (a tier alias on
  one, an explicit `pin` spelling the same model on the other) — so the implementation must
  compare values, not merely test non-emptiness.

- **`neither` vs `none` is the other one.** They differ only in whether `builder` resolved.
  Both are `blocked`, so an implementation that confused them would pass any test that only
  checked the first line. The table asserts the **detail line**, which is what distinguishes
  them and what the operator acts on.

- **The AND can be faked by reading only the first front-end.** `and_across_front_ends` runs
  the `raise` front-end **second** in `$AGENT_KEYS` order in one config and **first** in
  another, asserting `blocked` both times. A first-wins or last-wins bug passes exactly one.

- **R1's "no second resolver" needs a behavioral assertion, not a grep.** Grepping the diff for
  `model_alias` proves nothing about a hand-rolled copy. Instead the case changes **only**
  `pin.codex.reasoning` between two installs — a value no verdict logic could know without
  going through `resolve_model` — and asserts the verdict flips `none → raise`. Paired with the
  inverse (removing the pin flips it back) so a hardcoded answer fails.

- **R11 must not pass by the docs going missing.** The doc sweep keeps E17-F03's positive
  control: at least one operator-facing file must still *describe* the current rule, so
  deleting the documentation cannot turn the check green.

- **R12's "blocked" is also satisfied by that front-end never arming.** Both legs assert the
  **positive control first**, on the same target: a pristine `opencode`/`codex` install reads
  `raise` and `armed`, and only then is the artifact edited. Both also assert a **fixture
  precondition** — that the installer actually printed its "left untouched" / "foreign or
  edited" warning. If it rewrote the file there is no divergence to detect and the case would
  prove nothing while still passing.

- **Over-blocking is a failure mode too, so it gets its own leg.** A guard that disarms the
  target because `scout.toml` was edited fires on the wrong signal — it would satisfy every
  assertion about `builder-heavy` while making escalation unreachable for an unrelated reason.
  Leg 3 edits `scout.toml`, asserts the installer declined *that* file, and requires the
  verdict to stay `raise`/`armed`.

- **The default flip must not be provable from the config alone.** `docs_agree_with_the_shipped_default`
  reads `2` from the shipped `harness.config.yaml` **and** asserts the tool escalates at round 3
  with that config plus an armed artifact, and does not at round 2. A doc-only change cannot
  satisfy both halves.

## Named gap — the prose half, and one more

Carried forward from E17-F03: `prose_records_the_choice` and half of `telemetry_contract_intact`
are **role-content assertions** — they grep `agents/*.md` for required clauses. That proves the
instruction is present, **not that a running Orchestrator obeys it**.

New to this feature, and stated rather than implied: **the suite proves the verdict is
computed from `resolve_model`, not that `resolve_model` is right about any real vendor model.**
It cannot — the installer has no model list, and E17-F01 settled that it must not invent one.
So a wrong `pin.opencode.reasoning` still produces `raise` and still arms. The feature closes
the *downgrade-to-nothing* hole; it does not and cannot verify that a configured model exists
or is stronger. No doc may claim otherwise (R11), and that claim is itself pinned by
`no_doc_claims_the_harness_cannot_check`'s converse: the docs must state the limit.

`python3 -c` for any patch with nested quotes — two E17-F03 mutations silently failed to apply

**Result: 24 mutations applied, 24 killed, 0 survived** (20 before review, 4 added with R12).
The variable-instead-of-file mutation is the one worth naming: §5f iterates
`ag_personas | while … read`, a pipeline whose body POSIX sh runs in a **subshell**, so a
ledger held in a shell variable reads empty in the caller and the guard fails **open** —
`armed` — which is the one direction that must never happen silently.

**Result of the first pass: 20 mutations applied, 20 killed, 0 survived.** Each was confirmed to have landed via
`git diff --stat` before the suite was run — and that check earned its keep: three patches
initially failed to apply (two carried a trailing space in the anchor, one referenced an
uninitialised variable and died under `set -u` during setup rather than at the assertion).
Without the check all three would have read as "killed" while testing nothing. They were
corrected and re-run; all three then failed the intended case.

A surviving mutation is treated as a signal that the **rule** is under-specified, not merely
that the test is thin — an unconstrained degree of freedom is usually a real defect.
