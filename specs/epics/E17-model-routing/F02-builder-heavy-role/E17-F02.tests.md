## Anti-tautology

Five specific ways these cases could pass while proving nothing, and what stops each:

- **A count of seven is satisfied by any seventh file.** Every amended count assertion is
  therefore paired, in the same run, with a by-name check that `builder-heavy.<ext>` is the
  seventh — and, in `deselect_reclaims_builder_heavy`, with the assertion that `builder.toml`
  survived, so "reclaimed builder-heavy" cannot be satisfied by removing the wrong file.
  **Measured caveat:** in the two amended suites this pairing proved redundant — see the R10
  note under Mutation proof. It is kept for legibility, not claimed as the guard.

- **R5's "no warning" is an absence assertion.** Its positive control is
  `opencode_edited_file_is_still_refused`, run against the **same** installer in the **same**
  suite: one target upgraded clean, one target with a real user edit refused with the warning
  and left byte-identical. Without the second case, deleting the pristine check entirely would
  pass R5.

- **A not-byte-exact legacy candidate fails exactly like the bug.** During specification the
  first hand-built legacy body differed by one blank line, and the run was indistinguishable
  from the fix not working — same warning, same six roles. `opencode_upgrade_gains_the_new_role`
  therefore asserts the *positive* outcome (seven roles by name, stamp created, regeneration
  message) rather than merely the absence of the warning, so a silently-wrong candidate cannot
  pass by producing no output.

- **R5's fixture must genuinely be a previous-release file.** A fixture hand-written to look
  six-role proves nothing about what the shipped installer produced. It is therefore a
  **frozen byte copy** of the `opencode.json` that v0.55.0 (`970bd35`) actually wrote for an
  all-`inherit` opencode target, generated by running that installer and committed at
  `tests/fixtures/opencode-pre-builder-heavy.json`. Each case asserts the precondition — six
  `agent:` keys, no `builder-heavy`, no stamp — **before** upgrading, so a wrong fixture fails
  rather than silently testing nothing.

- **The fixture must not be derived from git history.** The first version of this suite built
  it from `git merge-base HEAD origin/main`, which is self-defeating twice: the suite
  hard-fails in any checkout without `refs/remotes/origin/main` (shallow clone, tarball
  export, fresh CI fetch), and the moment this branch lands `origin/main` **is** this commit,
  so the "previous release" becomes the seven-role installer and the six-role precondition
  fails on `main`. Since `run-tests.sh` auto-discovers this suite, that would make the
  mandatory gate depend on remote-ref state. Caught by Codex (#3714870609); the committed
  fixture is verified byte-identical to what the installer's own legacy derivation produces,
  and the suite is verified green in a tree with **no `.git` at all**.

  **A future mismatch here is a signal, not a flake.** The legacy candidate is the current
  model-free body minus the `builder-heavy` line, so a release that changes any *other*
  `agent:` member stops covering pre-0.56 targets. The response is a decision — keep covering
  them, or declare them out-of-support and delete these cases — never a fixture refresh.

- **R1 could pass on an empty file.** "Contains no instruction text" is trivially true of a
  stub. The case asserts both directions: the file **does** name `agents/builder.md`, and it
  does **not** contain a body line that `agents/builder.md` also contains — computed against
  the real Builder body in the same run, not a hardcoded string that drifts.

- **Naming a file is not resolving to it.** The first pointer body wrote
  ``[`builder.md`](./builder.md)``, which every generated wrapper resolves against
  `.harness/` — to `.harness/builder.md`, which does not exist — so the role would have run
  having never loaded the body it exists to share. The ADR link was dead the same way
  (`specs/adr/` is not in `HARNESS_BODY_PROSE`). R1 therefore asserts the **rule** rather
  than the two instances: no `](./…)`/`](../…)` syntax survives into the body, and every
  harness-root path the **installed** body names must exist under `.harness/`. That sweep
  carries its own positive control (`_seen >= 1`) — without it, a body with no recognisable
  paths would satisfy the assertion by inspecting nothing, which the mutation run confirms.
  (Codex #3714991251.)

- **R3 could pass because nothing resolved at all.** The case's positive control is the same
  config with `default: cheap`: `builder-heavy` must then resolve to the cheap alias, proving
  the fall-through path is live and not merely silent. It then asserts the re-run left
  `harness.config.yaml` byte-identical.

## Mutation proof (required before the PR is opened)

Each mutation is applied to the **committed** implementation, one at a time, `git diff --stat`
checked to confirm it actually applied, the suite run, then reverted with `git checkout --` and
`git status` verified clean before the next.

| mutation | must fail |
|---|---|
| drop the derived legacy candidate from the §5g pristine test | R5 |
| drop the derived legacy candidate from the §7 removal test | R6 |
| revert the `.opencode.stamp` write to the `grep -q '"model":'` conditional | R5 (second run / idempotence) |
| widen the pristine test to accept anything (`true` in place of the `cmp` chain) | R5a |
| drop the `builder-heavy` member from `gen_opencode_json` | R4, R5 |
| drop the `builder-heavy` row from `ag_personas` | R4 (codex/gemini/antigravity), R7 |
| drop `builder-heavy` from `MODEL_ROLES` | R9 |
| drop `builder-heavy` from `HARNESS_CLAUDE_SHIMS` | R7 (claude) |
| drop the `emit_agent builder-heavy` call | R4 (claude) |
| omit `builder-heavy: inherit` from the `migrate_config` seed heredoc | R2 |
| make `resolve_model` return the `builder` tier for `builder-heavy` | R9 |
| rename the seventh role so the count stays 7 but the name is wrong | R10 — **see the note below** |
| write the pointer as `[`builder.md`](./builder.md)` (the Codex #3714991251 form) | R1 |
| point the body at a harness-root path that does not exist in a target | R1 |
| strip every backticked path so the reference sweep has nothing to inspect | R1 (sweep positive control) |

A surviving mutation is treated as a signal that the **rule** is under-specified — an
unconstrained degree of freedom in the implementation — not merely that the test is thin.

### Note on R10: the by-name checks are redundant, and that is recorded honestly

R10 requires every amended count assertion to also name `builder-heavy`, on the reasoning
that a bare `= "7"` is satisfied by any seventh file. **That reasoning is sound in isolation
but the by-name checks turned out not to be load-bearing here**, and the mutation run says so:
renaming the seventh role (count stays 7, name is wrong) is caught either way, because both
suites already iterate a role-name list — `ROLES` in `test_model_routing.sh`, the
`MODEL_ROLE_NAMES` persona loop in `test_install.sh` — and those fire first.

No mutation was found that **only** the added checks catch. They are kept as
defense-in-depth, not claimed as proof: a count assertion that does not say what it is
counting is the anti-pattern R10 exists to prevent, and if a later refactor removes those
name loops the counts still name their subject. Stated here so a reader does not inherit a
belief in teeth that were not demonstrated.
