# The `builder-heavy` role — Functional Spec

## Context

E17-F01 gave every role a configurable model tier, but there is still exactly **one** Builder.
An operator who wants a struggling task retried on a more capable model has no way to say so:
promoting `models.builder` promotes it for *every* task, so the cost falls on the many easy
tasks rather than the few hard ones.

This feature adds the **capability** — a second Builder role name with its own tier. It does
not decide *when* to use it; that is E17-F03.

**ADR-0002 is binding and is not re-derived here.** `builder-heavy` is a distinct role name
with the **same instruction body**; the two variants differ **only** by the model tier
`resolve_model` returns. Escalation is therefore a pure routing decision and no front-end
needs a per-spawn model override. The two rejected alternatives (its own prompt body; no new
role plus a per-spawn override) and why they lose are recorded in the ADR.

### The wiring, as it actually stands

Seven sites decide the emitted role set. Three of them are already generic and cost nothing:

- `ag_personas()` — one `<role>\t<description>` table that **already** drives Codex, Gemini
  and Antigravity emission *and* their reclaim-on-deselect compares. One row covers all three
  front-ends in both directions.
- `MODEL_ROLES` — the flat list `resolve_model`/`models_any` iterate. One name.
- `HARNESS_CLAUDE_SHIMS` — the reclaim ledger for `.claude/agents/`. One name.
- `harness.config.yaml` — one `models:` key.
- `emit_agent` — Claude's shims are seven **explicit calls**, not a loop. One more call.
- `gen_opencode_json` — OpenCode's `agent:` map is a **literal seven-key JSON body**, not a
  loop. One more member, plus one `_oc_model` line.
- The "exactly six" assertions in `tests/` and the installer's own manifest prose.

Adding a *file* is safe on the four per-file front-ends: `emit_agent` writes unconditionally,
and `install_codex_agent`/`gen_gemini_agent`/`gen_ag_persona` all treat a non-existent
destination as safe to create. Only OpenCode is different, and that difference is a defect.

### Resolved during specification

**The OpenCode upgrade path silently refuses this feature. Reproduced, not assumed.**
`opencode.json` is a single generated file, so adding a seventh role changes its bytes for
*every* target, configured or not. The installer decides whether it may rewrite that file by
comparing the on-disk copy against `.harness/.opencode.stamp` — but E17-F01 keeps that stamp
**only when the body carries a `model` member**, on the reasoning that "a model-free body is
already reproducible from `gen_opencode_json`". Adding a role falsifies that premise: a
model-free body is reproducible only by the *same installer version*.

Reproduced against `HEAD` with a minimally patched source tree (install with `--agents=opencode`,
add a seventh `agent:` member, re-run):

```
⚠️  opencode.json differs from the generated stamp (edited) — left untouched;
    model routing changes were NOT applied
after:  ['orchestrator','architect','builder','reviewer','scout','doc-critic']
```

So an **untouched, unconfigured** OpenCode target is misreported as user-edited and never
receives `builder-heavy`. The identical comparison at the deselect site (§7) fails the same
way, leaving a stale `opencode.json` behind and calling it "edited". The configured case is
fine — its stamp exists — which makes this an asymmetry that only bites the majority.

**Decision: two complementary changes. Neither works alone — verified, not reasoned.**

The obvious fix is to make the stamp unconditional and be done. It is **inert**. A target
upgrading from a released version sees both changes at once: on-disk is the six-role body, no
stamp exists yet, and the freshly generated reference is the seven-role body. Neither arm of
the pristine test matches, so the file is refused, so it is never written, so it never gains
the stamp that would let it be written. Reproduced against the merge-base installer with both
changes applied together — the target stays at six roles permanently.

1. **Accept the shape the previous release generated.** This is the migration, and it is what
   actually delivers the feature. The legacy candidate is **derived** from the current
   model-free body rather than constructed beside it:

   ```sh
   grep -v '"builder-heavy":' "$_oc_free" > "$_oc_legacy"
   ```

   Byte-exact by construction, because the two shapes differ by exactly that one line. A
   hand-built legacy body is the error-prone path: the first attempt at one during
   specification left a stray blank line and failed *identically to the bug it was fixing*.

2. **`.harness/.opencode.stamp` becomes unconditional** — written on every run that writes
   `opencode.json`, not only when a model key is present. This is the mechanism Codex's role
   TOMLs already use, for the reason the code itself states: *"a fresh body cannot prove that
   a same-named file is ours."*

The two are not alternatives. **(1) without (2)** is the growing hack — every future role
addition would add another legacy candidate. **(2) without (1)** is inert, as above. Together
this is the **last** time a legacy shape is ever needed: once every target carries a stamp, a
future shape change is recognised by the stamp alone.

Verified on the merge-base installer with both applied — pristine target upgrades and gains
the role and the stamp; a **genuinely edited** `opencode.json` is still refused and left
byte-identical; a second run is silent and idempotent. The edited-file control is what proves
(1) widened the pristine test by one known-good shape rather than defeating it.

Rejected: *leave it, and let OpenCode targets miss the role.* That ships a feature which does
not reach the front-end it is emitted for, silently, with a warning that blames the operator.

**Known gap, named rather than closed.** A target still on the pre-`doc-critic` five-role
shape (E09 and earlier) stays stuck — that addition carried this same defect, so those targets
have been warning for many releases. One legacy candidate covers every actively-upgraded
target; adding a second would start exactly the unbounded list (2) exists to prevent. A
five-role straggler can delete `opencode.json` and re-run.

**This revises E17-F01 R11** ("an unconfigured target grows no new file") in exactly one
clause: an unconfigured OpenCode target now carries `.harness/.opencode.stamp`. Recorded here
rather than absorbed silently. What R11 protects is preserved: the stamp is
harness-owned metadata inside `.harness/` alongside `.agents` and `.harness-version`, it is
already removed on deselect, and R11's strongest assertion — that an all-`inherit` target is
`diff -r`-identical to one whose `models:` block was stripped — still holds, because both
grow the same stamp. The clause that changes is the explicit `[ -f .opencode.stamp ] && fail`
line, and it changes because its premise was wrong, not because it is inconvenient.

### The two open questions, decided

1. **Does `builder-heavy` get its own `ag_personas` description, or reuse the Builder's
   verbatim?** — **Its own.** That table is the human-facing picker text on three front-ends;
   two identical descriptions make the menu ambiguous at exactly the moment the operator is
   choosing between them. The wording states the pointer relationship explicitly — same
   discipline, heavier tier — so it documents ADR-0002 where a reader will actually meet it.
   ADR-0002 constrains the *instruction body*, not the menu label.

2. **Ship `builder-heavy` at a non-`inherit` default?** — **No: `inherit`, like every other
   role.** A shipped `reasoning` default would stamp a `model` key into every fresh target's
   artifacts, which is precisely the universality invariant E17 exists to protect and which
   E17-F01 R11 asserts. The config line carries the `# try: reasoning` hint the block already
   uses for `architect`, so the intent is advertised without being imposed. The consequence is
   accepted and stated: **the heavy builder is not heavier until someone configures it.**

**No per-key config migration.** `migrate_config` seeds the whole `models:` block only when the
block is absent, so an already-installed target will not grow a `builder-heavy:` line. That is
correct and deliberate: the map is flat and an unlisted role falls through to `models.default`,
so an upgraded target and a fresh one behave identically while differing in config bytes. The
alternative — per-key seeding — would edit a file the operator owns to write a value that
changes nothing.

## Requirements (EARS)

| R-id | Requirement |
|---|---|
| **R1** | `agents/builder-heavy.md` shall be a thin pointer at `agents/builder.md` that duplicates no instruction text, so a change to the Builder body reaches both variants (ADR-0002). |
| **R2** | The shipped `harness.config.yaml` shall carry `models.builder-heavy: inherit` within the existing `models:` block. |
| **R3** | When a target's `models:` block carries no `builder-heavy` key, resolution shall fall through to `models.default` exactly as for any other unlisted role, and no config migration shall add the key. |
| **R4** | While a front-end is selected, the installer shall emit a `builder-heavy` role definition for it alongside the six existing roles — on **all five** front-ends (Claude, Codex, Gemini, Antigravity, OpenCode). |
| **R5** | When an existing `opencode.json` is byte-identical either to the last body the installer wrote or to the body **a previous release** generated for that configuration, the installer shall regenerate it — so a role added by a later release reaches an already-installed, unconfigured target — and shall record the bytes it wrote regardless of whether they carry a `model` member. |
| **R5a** | When an existing `opencode.json` matches neither, it shall be left **byte-identical** with the "edited" warning; widening the pristine test shall not weaken it. |
| **R6** | When `opencode` is deselected and `opencode.json` is byte-identical to the last body the installer wrote **or to a previous release's body**, it shall be removed; a target installed by an earlier release shall not be misreported as edited. |
| **R7** | When a front-end is deselected, the `builder-heavy` artifact shall be reclaimed on the same pristine-only terms as the six existing roles, and its ownership stamp dropped with it. |
| **R8** | While every role resolves to `inherit`, no `builder-heavy` artifact on any front-end shall carry a model key, and an all-`inherit` target shall remain `diff -r`-identical to one whose `models:` block was stripped. |
| **R9** | `models.builder-heavy` shall resolve independently of `models.builder`: pinning either shall leave the other's resolved value unchanged. |
| **R10** | Every assertion that fixes the emitted role set at six shall assert seven **and name `builder-heavy` explicitly**, so a count alone can never satisfy it. |

## Out of scope

- **When** to escalate — the Architect's complexity tag and the two-rejection rule (E17-F03).
- Any change to the Builder's instruction body. A heavy variant that needs different
  *behavior* rather than a different *model* contradicts ADR-0002 and must return through the
  human gate as a re-spec, not a patch.
- The worker roster (E17-F04).
- Per-key `models:` migration for already-installed targets (decided above).
- This repo's own `.claude/agents/` dev mirror, which is a partial convenience copy — it
  already omits `doc-critic` — and is not installed body. Nothing escalates to `builder-heavy`
  until E17-F03, so the mirror gains nothing today.

## Non-functional

- **Absent configuration reproduces today's model behavior exactly** (R8) — E17's universality
  invariant, with the one stamp-file revision recorded above.
- Installed body ⇒ `VERSION` **MINOR** bump (new backward-compatible capability) + CHANGELOG.
- POSIX sh / `dash` for the installer and tests; green under `sh tools/run-tests.sh`.
- Budget: `change_size.max_requirements: 12`. This spec declares **11**.

## ADR

No new ADR. This feature **implements** `ADR-0002`; it does not revisit it. The
`.opencode.stamp` revision is a correction to an E17-F01 requirement whose premise this change
falsifies, recorded in this spec rather than in a new ADR because it settles a mechanism, not
an architecture.
