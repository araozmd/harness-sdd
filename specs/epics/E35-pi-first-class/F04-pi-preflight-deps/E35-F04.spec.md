# pi environment preflight + approval-gated pinned `pi-subagents` install — Functional Spec

> R-ids in this document are `R1 … R12`; their fully-qualified form is `E35-F04:R1 … E35-F04:R12`.

## Context

E35-F01..F03 install pi glue: shared skills, `.pi/prompts/`, `.pi/agents/<role>.md` for the
community `pi-subagents` package, and the pi escalation verdict. Three things still fail
silently on a real machine:

- pi skips untrusted project resources, so the installed prompts, skills and role agents
  do nothing until the project is trusted;
- the role agents need `pi-subagents`. It is a 0.x third-party package that releases every
  1–5 days, so it must be pinned, and nothing installs it;
- pi's own *example* `subagent` extension registers a conflicting `subagent` tool, and
  nothing reports it.

The user asked the installer to "validate the PI installation and install the plugins
needed, with the right approval". This feature adds a **read-only preflight report**
whenever `pi` is selected. It installs the pinned backend **only with explicit approval**:
an interactive `y`, or `--pi-deps=install`.

**Complexity basis.** `complex`, on three stated signals:

- the spec is at the `change_size.max_requirements` budget (12 of 12);
- it depends on a third-party surface: pi's CLI output, trust store and settings writer.
  This is the defect class E35-F03 paid five Codex rounds for (lessons 2026-10-16);
- it guards a filesystem shape matrix over paths a third-party tool writes. This is the
  class E35-F01 paid six review rounds for (lessons 2026-10-14).

### Verified facts (pi 1.2.0 binary + `@earendil-works/pi-coding-agent/dist` + `pi-subagents` 0.78.0 source, 2026-10-16)

These facts bind the design. Each was checked against the binary or the source, not the
docs.

1. **Version.** `pi --version` prints exactly `1.2.0` and one newline, then exits 0. It
   returns before any extension loads.
2. **Install syntax.** The syntax is `pi install <source> [-l] [--approve|-a|--no-approve|-na]`.
   `-l` writes the project `.pi/settings.json`, run from the **process cwd** (pi has no
   `--cwd`). An npm source installs into `<cwd>/.pi/npm/`. pi creates
   `.pi/npm/package.json` and `.pi/npm/.gitignore` (`*\n!.gitignore\n`) only when they are
   absent, then runs `npm install <spec> --prefix <cwd>/.pi/npm --legacy-peer-deps`. npm
   lifecycle scripts are not disabled. npm also writes `package-lock.json` (or updates an
   existing `npm-shrinkwrap.json`) in that prefix, in place through a symlink or a hard link
   (Reviewer-reproduced, round 1). pi installs the package **before** it persists the
   settings entry.
3. **What `-l` writes into `.pi/settings.json`.** pi reads the file, applies its migrations
   (`queueMode`→`steeringMode`, `websockets`→`transport`), and sets **only** the
   top-level `packages` field. It appends `npm:pi-subagents@0.78.0`, or rewrites an entry
   with the same package identity in place. It then writes
   `JSON.stringify(merged, null, 2)`, with no trailing newline, in place via
   `writeFileSync`. That call follows a symlink and writes through a hard link. pi
   **never adds or touches a `subagents` key** and preserves every other key. If the file
   is unparsable when pi loads it, pi installs the npm package but **skips the settings
   write**, prints a warning and exits 0. The package is then not configured, and the
   success is false.
4. **Install needs trust.** Without `-a`, `pi install -l` on an untrusted project exits 1
   with `Project is not trusted. Use --approve to modify local package config.` With no
   `-a`/`-na`, and when the project holds trust-requiring resources (`.pi/settings.json`,
   `.pi/prompts`, `.agents/skills` …), pi first **loads extensions** to ask them about
   trust, and then **prompts on a TTY**. The prompt saves its answer to the trust store.
   An explicit `-a` or `-na` skips both. `-a` is per-command: pi neither reads nor writes
   the trust store.
5. **`pi list`.** The syntax is `pi list [-a|-na]`. It exits 0 when it lists. On a bad
   option or a thrown error it exits 1, with the message on stderr. Its stdout is exactly
   one of:
   - `No packages installed.`;
   - a `User packages:` and/or a `Project packages:` section. A blank line separates the
     two. Each entry is a line of two spaces + the source string, plus ` (filtered)` for
     an object entry. When the package is on disk, the entry is followed by a
     four-space-indented installed-path line.

   Colours come from chalk, which is off when stdout is not a TTY. A settings parse error
   is a stderr warning, not a non-zero exit, and the list then omits that scope. `-na`
   hides project packages entirely. `-a` lists them without loading extensions or
   prompting.
6. **Side effects of a "read-only" pi command.** Every `pi` run reads the user and project
   `settings.json` files. For each file that exists, it takes a transient
   `proper-lockfile` lock directory (`<file>.lock`). `pi list` may also spawn
   `npm root -g`. `PI_OFFLINE=1` / `--offline` disables startup network work.
7. **Trust store.** The store is `<agent dir>/trust.json`. The agent dir is
   `$PI_CODING_AGENT_DIR`, with a leading `~` expanded, else `~/.pi/agent`. This is the
   same resolution E35-F03's `pi_user_agent_dir` performs. The file is a JSON object of
   `path → true | false | null`, read with a leading BOM stripped. Any other value, a
   non-object or a parse error makes pi **throw**. The lookup takes `realpath(cwd)` and
   walks to the filesystem root: the **nearest** key whose value is `true` or `false`
   decides, and `null` is skipped. An absent file means no decision. With no decision,
   pi's user setting `defaultProjectTrust` (`ask` by default, or `always`/`never`)
   applies.
8. **Example-extension conflict.** pi discovers `<agent dir>/extensions/*.ts|*.js` and
   `<agent dir>/extensions/<dir>/{package.json with pi.extensions, index.ts, index.js}`.
   The example extension installs as `<agent dir>/extensions/subagent/index.ts`
   (+ `agents.ts`), with sample agents under `<agent dir>/agents/`. `pi-subagents` 0.78.0
   uses the **same** directory for its own `config.json` and reads user agents from
   `<agent dir>/agents/`. A dangling `index.ts` is not loaded (`existsSync` is false), but
   it still occupies the shared directory.
9. **This host.** `~/.pi/agent/extensions/subagent/{index.ts,agents.ts}` and
   `~/.pi/agent/agents/*.md` are **dangling** symlinks into a non-existent
   `/home/araozmd/packages/coding-agent/…`. They are reported only and never modified.
10. **`pi-subagents` 0.78.0.** The npm package is `pi-subagents`, MIT. It has no `scripts`
    and five runtime dependencies. Its pi manifest carries `extensions`, `skills` and
    `prompts`.

## Business rules

- **Approval is explicit and on the command line or at a real terminal.** Only
  `--pi-deps=install` or a `y`/`yes` typed at a terminal approves the install. No
  environment variable, pipe, default or prior run counts as approval.
- **Warn-only.** pi environment problems never fail the harness install. The one exception
  is `--pi-deps=install`, given explicitly, when the install does not end verified.
- **The installer itself never writes under the pi agent dir** (ADR-0007). pi's own
  transient `<file>.lock` lock directories (fact 6) are expected and are not installer
  writes. A probe killed at its time bound may leave one behind. The installer reads `trust.json`
  and lists extension and agent paths. The only `pi` commands it runs are `--version`,
  `list -a` and, with approval, `install -l -a`.
- **One pin, one floor.** The pin is `PI_SUBAGENTS_PIN=0.78.0` and the version floor is
  `PI_VERSION_FLOOR=1.0.0`, each a single installer constant.
- **Blunt, fail-closed rules over modelling pi key by key** (lessons 2026-10-16). If
  anything cannot be classified, the report says `unknown`, and an install is not
  attempted on an unsafe or unknown precondition.

## Architecture alignment

`specs/architecture.md` is absent in this repository. The platform ADR set
(`specs/adr/`) is present, so the touched decisions are cited:

- ADR-0007 — pi sub-agent backend = pinned `pi-subagents`, `pi -p` fallback. This feature
  implements decisions 3 and 4. The installer validates read-only by default. It runs
  `pi install -l … npm:pi-subagents@<pin>` only on an explicit interactive yes or an
  explicit flag, with the pin a single constant. It reports the example extension (A) as a
  conflict and never edits `~/.pi/agent`. **Stated refinement:** the command is
  `pi install -l -a …`. The ADR's form omits `-a`, and without it pi loads extensions and
  may prompt to persist trust (fact 4). The approval this feature collects is the
  approval for that one per-command trust, and the installer refuses when the user has
  explicitly distrusted the project, or when its trust store is unreadable (R9).
- ADR-0002 — `builder-heavy` is a tier. The pi escalation verdict stays correct after an
  install. The F03 overridden check is re-evaluated after any install attempt and before
  `.harness/.escalation-arming` is written (R10), so arming never reflects a pre-install
  snapshot.
- ADR-0005 — source-only surfaces emit only under `--self`. Conversely, `--self` never runs
  the preflight or any `pi` command (R2): the source repo is not a pi deployment target.

## Acceptance criteria (EARS)

- **R1** — The installer shall accept `--pi-deps=<check|install|skip>` and
  `--pi-deps <value>`, seeded from `HARNESS_PI_DEPS`, with the flag winning over the env.
  An empty value means "no override", and the default is `check`. An illegal value from
  either source shall abort non-zero before any target write. The abort message shall name
  the three legal values and shall not echo a rejected value holding characters outside
  `[A-Za-z0-9._-]`. Where `--umbrella` is given, `--pi-deps=install` shall abort the
  same way: a cascade has no single target to approve.
- **R2** — While `pi` is selected for a target, the installer shall run the preflight once
  for that target, after every file this run writes under `.pi/` and before
  `.harness/.escalation-arming` is written. With mode `skip`, the preflight is exactly one
  `pi preflight: skipped (--pi-deps=skip)` line, and no `pi` is executed. The installer
  shall neither print a preflight line nor execute `pi` when `pi` is not selected, or
  under `--self`.
- **R3** — When the preflight runs, the installer shall resolve `pi` with `command -v` and
  report one of `pi: not found on PATH`, `pi <x.y.z> (>= 1.0.0)`,
  `pi <x.y.z> is below the 1.0.0 floor` or `pi version: unknown`. `unknown` covers a
  non-zero exit, a timeout, more than 64 KiB of output, and any stdout that is not one line
  of `MAJOR.MINOR.PATCH` with an optional `-`/`+` suffix. A missing pi, or one below the
  floor or of unknown version, shall skip the `pi list` probe.
- **R4** — When the preflight runs, the installer shall classify the target's trust from
  `<agent dir>/trust.json` with pi's rule (fact 7) as `trusted`, `distrusted`, `undecided`
  or `unknown`, and report it. Every state other than `trusted` comes with the fix:
  `/trust` in an interactive pi session (then `/reload`), or `-a` on headless runs.
  `unknown` covers:
  - an unresolvable agent dir;
  - a `trust.json` that, after following symlinks, is not a regular file;
  - an unreadable file, or one over 1 MiB;
  - a file that does not parse to a JSON object of `true`/`false`/`null` values.
- **R5** — When the `pi list -a` probe runs, the installer shall report the backend as:
  - `pinned (<user|project>)` only when an unfiltered entry line equals exactly
    `npm:pi-subagents@<PIN>`, is followed by an installed-path line, and that package's
    `package.json` `version` is exactly `<PIN>`. For the **project** scope the path line must
    equal `<realpath target>/.pi/npm/node_modules/pi-subagents`. For the **user** scope pi
    falls back to `npm root -g` for a legacy install (fact 5a, `getNpmInstallPath`), so any
    absolute printed path ending `/node_modules/pi-subagents` is accepted (the managed
    path included, so no agent-dir normalisation is needed: a `//` or `/./` in
    `PI_CODING_AGENT_DIR` cannot cause a false mismatch). Because pi prints a
    settings source string verbatim, three independent layers keep a forged listing from
    reading `pinned`: (1) the installer reads both settings files the way pi does (one BOM
    stripped, invalid UTF-8 replaced): a control character (newline included) in any
    `packages` string, or a settings file that exists (symlinks followed, a dangling link
    counts as absent) yet is not a readable regular file holding a JSON object, makes the
    status `unknown`; (2) a repeated `User packages:` or `Project packages:` heading, or
    `Project` before `User`, makes it `unknown`; (3) a user-scope path must equal its own
    realpath, must not start with `/proc/` and must lie outside the target, else the entry
    is a mismatch;
  - `mismatch` when any entry line containing `pi-subagents` is not such a pinned entry,
    in either scope, **even if a pinned entry is also present** (fail closed). A mismatch
    in the **user** scope is reported as `mismatch (user scope)`: `pi install -l` rewrites
    only the project scope and cannot fix it, so no install is attempted
    (`not attempted: user-scope mismatch`);
  - `absent`;
  - `unknown` for an unreadable installed `package.json` of an otherwise pinned entry, a
    non-zero exit, a timeout, or stdout with any line outside the shapes in
    fact 5.
- **R6** — When the preflight runs and the agent dir resolves, the installer shall report
  `conflict: pi example subagent extension` when any of the following exists as any node
  type, a dangling symlink included:
  - `<agent dir>/extensions/subagent/index.ts`, `index.js` or `package.json`;
  - `<agent dir>/extensions/subagent.ts` or `subagent.js`;
  - the same five names under the project's `<target>/.pi/extensions/` (pi's loader
    discovers project-local extensions first).

  The line is `conflict: a subagent extension (pi example or legacy pi-subagents clone) that
  registers a conflicting subagent tool at <path>`: the legacy `pi-subagents` installer
  clones into the same directory, so the two cannot be told apart reliably.

  A dangling entry is labelled `(dangling symlink)`. The installer shall separately report
  the number of dangling symlinks directly under `<agent dir>/agents/` and under `~/.agents/`
  (both user-agent locations `pi-subagents` reads; the `~/.agents/` location is taken from
  the Reviewer's reading of `src/agents/agents.js`, not re-verified offline). An agent dir or
  HOME holding a control character is treated as unresolvable and never echoed. `pi-subagents`
  reads user agents from that directory (fact 8), and the line tells the user to remove
  the broken links. It shall never
  create, modify, remove or follow-write any of those paths.
- **R7** — The installer shall run every `pi` command:
  - with the target as cwd;
  - with stdin from `/dev/null`;
  - in its own process group, killed as a group when its time bound expires (probes 15 s,
    install 600 s);
  - for each probe, with `PI_OFFLINE=1` and its stdout and stderr captured, never echoed.

  The report shall contain only installer-authored text, with no pi output or
  untrusted file content in it. Without `python3` the preflight is a single
  `pi preflight: skipped (python3 not on PATH)` line, plus
  `install: not attempted: python3 missing` under the flag `install` (R9, R11).
- **R8** — When the backend status is `absent` or `mismatch`, the installer shall attempt
  the install only:
  - with mode `install` from the flag; or
  - with mode `check`, stdin and stderr both TTYs, no `--umbrella`, and a y/N prompt
    (default N) answered `y` or `yes`, case-insensitive.

  Every other case shall not install and shall print the exact command:
  - a pipe or closed stdin;
  - a TTY on stdout only;
  - `HARNESS_PI_DEPS=install` without the flag, outside a terminal.

  `HARNESS_PI_DEPS=install` without the flag is downgraded to `check`. One notice, printed
  inside the preflight and behind R2's gates, says the env cannot approve. After the
  downgrade the ordinary `check` rules apply, so on a real terminal the prompt is shown
  and only a typed `y` installs. When the status is `unknown`, or was `not probed`, the
  installer shall neither prompt nor install, and shall print
  `install: not attempted: <reason>`.
- **R9** — If, at the moment of an approved install, any precondition fails, then the
  installer shall report `not attempted: <reason>` and shall not run `pi install`. The
  preconditions are:
  - pi is present and at or above the floor;
  - the backend status is `absent` or `mismatch`;
  - `python3` is present;
  - trust is neither `distrusted` nor `unknown` (fail closed: pi throws on a `trust.json`
    it cannot read, fact 7);
  - every path in the target shape matrix (plan §Shape matrix) is safe: the entire existing
    `.pi/npm/` tree, at any depth and without following links, holds only real directories
    and regular files of link count 1, except symlinks directly inside a `.bin` directory
    that resolve inside `.pi/npm/` (npm's own bin links);
  - the backend status is not a user-scope mismatch;
  - `.pi/settings.json` is absent, or Node-parses (strict, no BOM) to a JSON object whose
    `packages` key, if present, is an array.
- **R10** — When an approved install runs, the installer shall run
  `pi install -l -a npm:pi-subagents@<PIN>` and then verify with a fresh `pi list -a` probe.
  Success is reported only when that probe reports `pinned (project)` or `pinned (user)`.
  After any install attempt, the installer shall re-evaluate E35-F03's
  `pi_builder_overridden` and mark pi `unstamped` when it holds. This happens before the
  arming verdict is written.
- **R11** — If mode `install` came from the flag and the install was not attempted (R9),
  exited non-zero, timed out or failed verification, then the installer shall finish every
  remaining step and exit with status 5. In every other case pi problems shall leave the
  exit status unchanged, an interactively approved install that failed included. A pin
  already `pinned` under `--pi-deps=install` is a success with no `pi install`.
- **R12** — The installer shall document the feature in five places: `docs/INSTALL.md`'s
  pi section, the installer header usage, the `.harness/manifest.txt` heredoc,
  `CHANGELOG.md` `## [0.95.0]` and `VERSION` `0.95.0`. The documentation shall cover the
  flag, the env downgrade, the report lines, the exit status 5 and the exact command.
  The pi section shall drop its claim that the installer "never touches … `.pi/settings.json`".

## Out of scope

- Installing or upgrading pi itself; `pi update`; `pi remove` on deselection. A deselected
  pi leaves `.pi/settings.json` and `.pi/npm/` as they are, and they are the user's to
  remove.
- Writing `trust.json`, or anything else under the agent dir. Changing the example
  extension or the dangling links.
- Modelling `defaultProjectTrust`. A target with no trust entry reports `undecided` even
  when the user's setting is `always`. The report line names that setting as a possible
  cause, so the line is a warning, not a lie.
- MCP or Playwright configuration; any network check; upper version bounds.

## Open questions

None blocking. Two decisions are recorded for the human gate:

- **Exit status 5.** This is a new code, distinct from `die`'s 1 and the cascade's 3, so
  that CI can tell "the harness install broke" from "the approved pi install did not land".
- **No env approval.** `HARNESS_PI_DEPS` can choose `check` or `skip` but cannot approve.
  This follows the `--pr-loop` precedent, which deliberately has no env twin with
  persistent effect. Here the effect is executing third-party code.
