# pi front-end key — Test Contract

> The traceability matrix: every R-id in the `.spec.md` maps to a concrete, executable
> test. The Reviewer fails the feature if any R-id lacks a passing test.
>
> All new cases live in `tests/test_pi_front.sh` (POSIX `sh`, `set -eu`, the `fail`/`pass`
> helpers). Each one installs into its own `mktemp -d` target, under
> `env -i PATH="$SANDBOX_PATH" HOME="$T/home" CODEX_HOME="$T/ch"`.
> `SANDBOX_PATH` is the real PATH with every component holding a `pi` executable removed,
> so the real pi on the developer machine cannot leak in.
> No case runs `pi`, a model, or the network.

## Behavioral / end-to-end checks (Reviewer)

- `sh harness-install.sh --agents=pi /tmp/x`, then inspect `.pi/prompts/sdd-next.md` by
  eye against the plan's exact template.
- Optional, manual, never in CI: where pi is installed and authenticated, run
  `cd /tmp/x && pi -a -p "/sdd-next"` and confirm that pi expands the template and reads
  the shared unit. Record the result in `progress/`. Do not gate on it.
- Run `sh harness-install.sh --self` twice: the second run is a no-op, and
  `git status --porcelain` is clean apart from the intended regenerated units.
