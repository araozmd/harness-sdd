# pi model routing — Functional Spec

> R-ids in this document are `R1 … R12`; their fully-qualified form is `E35-F03:R1 … E35-F03:R12`.

## Context

E35-F01 made `pi` a front end. E35-F02 gave each harness role its own pi file,
`.pi/agents/<role>.md`, plus a fallback dispatcher, `tools/pi-dispatch.sh`. Those role
files still carry no `model:` and no `thinking:` line, so on pi:

- every role runs on the session's model;
- the ADR-0002 tiers (`reasoning | standard | cheap | frontier`) have no effect;
- `builder-heavy` is the same as `builder`, so escalation cannot help;
- pi is left out of `.harness/.escalation-arming` (E35-F01 R11).

This feature makes the tiers work on pi. It mirrors the Codex precedent (E99-F161 and
E99-F163):

- **Model.** An explicit `models.pin.pi.<tier>` sets the role's model. It must be in
  `provider/id` form and is guarded like OpenCode's pin (E31). pi has no floating alias,
  so the harness never invents a model id.
- **Thinking level.** A built-in tier→`thinking` ladder sets the level. It works the way
  `codex_effort_alias` does: no separate config key, and it applies even when no model is
  pinned.
- **Escalation.** `escalation_verdict` and `write_escalation_arming` treat pi as they treat
  Codex. A difference in thinking level alone is enough to arm `builder-heavy`.

ADR-0007's consequence is a hard constraint here: one resolver feeds both the role-file
frontmatter and the dispatcher's flags. The installer writes the resolved values into the
role file, and the dispatcher reads them back from that file. So the generated role file is
the only output of the resolver.

Verified facts this spec relies on (pi 1.2.0 `dist/core/model-resolver.js` and `--help`;
`pi-subagents` 0.78.0 `src/agents/frontmatter.ts` and `src/runs/shared/child-tool-plan.ts`):

- pi's `--model` takes `provider/id`, optionally followed by `:<thinking>`.
  - `--thinking` takes `off | minimal | low | medium | high | xhigh | max`.
  - An explicit `--thinking` wins over a `:<level>` suffix on `--model`.
  - A last-colon suffix that is **not** one of those seven levels is treated as part of the
    model id. Real ids look like this: OpenRouter `…:free`, Bedrock `…-v1:0`.
- `pi-subagents` parses each frontmatter line as `^([\w-]+):\s*(.*)$`, and a repeated key
  replaces the earlier one (the last one wins).
  - Its `applyThinkingSuffix` adds `:<thinking>` to the model **only when the model has no
    known-level suffix yet**. If `model:` already ends in `:<level>`, the frontmatter
    `thinking:` is ignored.
  - Combined with the `--thinking` precedence above, a pin with its own suffix would run at
    one level through `pi-subagents` and at another through `pi-dispatch.sh`. That is
    exactly the drift ADR-0007 forbids, so such a pin is rejected (R3).
- With no `model:`, `pi-subagents` inherits the parent session's model and still applies
  `thinking:`. `pi -p --thinking <t>` with no `--model` does the same.

### Why `complexity: complex`

Three of `agents/architect.md`'s stated bases hold:

1. **The feature is at the size budget.** It has exactly 12 R-ids against
   `change_size.max_requirements: 12`. Environment preflight is already split out (E35-F04).
2. **It contains a validator that must agree with a second validator.** The installer's pin
   guard and the dispatcher's role-file guard are separate code in separate files, because
   `tools/` scripts cannot source the installer. If the installer stamps a value the
   dispatcher rejects, every dispatch fails with exit 3. R6 pins the two together with one
   shared table of input shapes.
3. **It contains a byte contract compared in more than one place.** The role-file bytes now
   depend on the config, and they are compared at install, at deselect, at pr-loop gate-off,
   by `--self` reconciliation, and by the new pi `unstamped` probe (R9).

**Change-size note.** The production diff is small: about 150 lines in the installer and 30
in the dispatcher. The touched-file count stays under `advise_files: 25`. `--self` rewrites
only the root `.escalation-arming` and `.claude/.glue-manifest`; the committed
`.pi/agents/*.md` do not change (R12).

## Business rules

- **pi has no built-in model alias.** An unpinned tier stamps no `model:`. Like Codex and
  OpenCode, the harness invents no model id.
- **The thinking level rides the tier.** Built-in ladder: `cheap→low`, `standard→medium`,
  `reasoning→high`, `frontier→xhigh`.
  - `off`, `minimal` and `max` are never emitted (compare Codex's `ultra`).
  - `inherit` stamps neither key.
  - There is no operator-facing thinking override, for the same reason Codex has no effort
    knob: a second dial could disagree with the tier.
- **A pin is a model, never a thinking level.** A pin that ends in `:<one of the seven
  levels>` is rejected, because it would make the `pi-subagents` path and the dispatcher
  path diverge. A last-colon suffix that is not a level is part of the model id and is
  accepted.
- **A bad pin never fails the install.** Like the OpenCode guard, a rejected pin warns once
  per tier and stamps no `model:`. The role file is still written, and its `thinking:` still
  comes from the ladder.
- **What the installer stamps, the dispatcher accepts.** The installer's accepted pin set is
  a subset of what the dispatcher's role-file guard accepts. The dispatcher stays the looser
  of the two on purpose. It guards argv safety and B/C agreement, not the `provider/id`
  shape, because `pi-subagents` loads a hand-edited `model: sonnet` too.
- **The other front ends do not change.** For claude, codex, opencode and antigravity the
  generated artifacts and their `.escalation-arming` lines are byte-identical. A
  `pin.pi.*` key affects nothing outside pi.
- **The root `harness.config.yaml` is the seed template.** It stays all-`inherit`; this
  feature changes only its comments. The `migrate_config` heredocs stay byte-identical to it.
- **The `builder-heavy` description string is not touched.** It mentions the Codex effort
  only. Rewording it would rewrite every front end's glue, which would break the
  byte-identity rule above.

## Architecture alignment

`specs/architecture.md` is absent in this repository. The ADR set under `specs/adr/` is
present, so citations are required. This is a single-namespace project, so bare ids are
used.

- ADR-0007 — pi sub-agent backend: the installer resolves `model`/`thinking` once and writes
  both into `.pi/agents/<role>.md`. `pi-dispatch.sh` forwards exactly those values as
  `--model`/`--thinking`, so B (`pi-subagents`) and C (the dispatcher) share one resolver
  output. A pin that would make them disagree is rejected at install (R3), and the
  dispatcher refuses the same shape in a hand-edited file (R6). This completes the "staged,
  not divergent" item E35-F02 recorded against ADR-0007 §1.
- ADR-0002 — `builder-heavy` is a tier: on pi, escalation remains a pure routing decision.
  The heavy role differs from `builder` only by its resolved stamp (`model` plus `thinking`),
  computed by the same resolvers that write the file. `escalation_verdict` compares those
  values and re-derives nothing (R8). No second Builder body is introduced.
- ADR-0005 — source-only surfaces are emitted only by `--self`: `--self` keeps resolving pi
  from this repo's seed config. The committed `.pi/agents/*.md` therefore stay free of model
  keys, and `.escalation-arming` gains an honest `pi=neither` line (R12). No new source-only
  surface.
- ADR-0004 — resolved body via pointer stubs: the body of each role file is unchanged. Only
  frontmatter lines are added, and the pointer is never inlined.

## Acceptance criteria (EARS)

- **R1** — The installer shall map a resolved tier to a pi thinking level through exactly
  one built-in table:

  | tier | thinking level |
  |---|---|
  | `cheap` | `low` |
  | `standard` | `medium` |
  | `reasoning` | `high` |
  | `frontier` | `xhigh` |

  `inherit` (and an unrecognized tier, already normalized to `inherit`) shall map to
  nothing. The tier comes from the existing `_model_tier_resolve` cascade (own → umbrella →
  `inherit`).

  If a table value is not one of `off minimal low medium high xhigh max`, then the installer
  shall warn once per tier per run, stamp no `thinking:` for any role on that tier, and
  continue with exit 0.
- **R2** — When a role's tier is not `inherit` and the effective
  `models.pin.pi.<tier>` passes the pin grammar, `resolve_model pi <role>` shall print that
  pin verbatim. The effective pin is the target's own pin, else the umbrella coordinator's
  same key. The pin grammar is:
  - 1–256 bytes;
  - every byte in `A-Za-z0-9._:/@-`;
  - a provider before the first `/` matching `[A-Za-z0-9][A-Za-z0-9._-]*`;
  - a non-empty id after it that neither begins nor ends with `/` or `:` and contains no
    `//`;
  - no final `:<level>` for any of the seven thinking levels.

  When no pin is set, it shall print nothing and emit the existing once-per-tier
  "no built-in alias" notice. `model_alias pi <tier>` shall print nothing for every tier.
- **R3** — If an effective `models.pin.pi.<tier>` is non-empty and fails the R2 grammar,
  then the installer shall:
  - print exactly one warning for that tier per run, naming `models.pin.pi.<tier>` and the
    failed rule;
  - echo the value only when it passed the length and charset rules;
  - stamp no `model:` for any role on that tier, while still stamping that role's R1
    `thinking:`;
  - continue with exit 0.

  A pin of `inherit` shall keep the existing "tier name, not a model id" warning and
  omission. This holds for every row of the plan's hostile-pin table whose installer
  verdict is `length`, `charset`, `form` or `suffix`. Those rows cover:
  - whitespace;
  - a missing slash;
  - an empty provider or id;
  - a leading `-`;
  - shell metacharacters;
  - a literal backslash-n;
  - 257 bytes;
  - a known-level suffix, and a doubled known-level suffix.

  An empty pin is absent (R2), so it gets no warning.
- **R4** — While `pi` is selected, each `.pi/agents/<role>.md` frontmatter shall carry
  `model: <R2 value>` only when that value is non-empty, and `thinking: <R1 value>` only
  when that value is non-empty. Both lines go immediately after `description:` and before
  `tools:`, in that order. Every other F02 line and the body are unchanged.

  For an all-`inherit` config, every role file shall be byte-identical to E35-F02's output.
  A re-install with an unchanged config shall be byte-idempotent.
- **R5** — When the config changes between installs, the installer shall rewrite each
  pristine role file to the new stamp, and its `.harness/.pi-agents/` stamp with it. A
  pristine role file is one byte-equal to its stamp, including a model-free file written by
  E35-F02. The changes covered:
  - tier → tier;
  - pin → different pin;
  - pin → invalid pin;
  - tier → `inherit` (both lines removed).

  The E35-F02 pristine-only rules shall still hold:
  - an edited role file is left unchanged with the F02 warning;
  - deselecting `pi` after a config change still removes every pristine role file.
- **R6** — When a role file carries `model:` and/or `thinking:`, `tools/pi-dispatch.sh`
  shall pass `--model <m>` and/or `--thinking <t>` exactly as F02 R7 specifies.

  If that role file has any of these, then the dispatcher shall exit 3 with a
  `pi-dispatch:` diagnostic, empty stdout, and no `pi` invocation:
  - a `model:` value longer than 256 bytes, or one beginning with `-`;
  - a `model:` that ends in `:<known level>` while a `thinking:` line is also present;
  - more than one `model:` line, or more than one `thinking:` line.

  Every pin that R2 accepts shall pass the dispatcher's guard unchanged. Each row of the
  plan's parity table shall get exactly the dispatcher verdict that row records. A
  hand-written value that is only "not `provider/id`" (for example `sonnet`) stays
  accepted, as F02 accepts it and as `pi-subagents` does. Values outside the charset, an
  overlong value, a suffix conflict and a duplicate key are rejected.
- **R7** — `models_any pi` shall succeed iff at least one role resolves a non-empty pi
  `model` **or** a non-empty pi `thinking`.
- **R8** — `escalation_verdict pi` shall compare the pair (`resolve_model pi`, pi thinking)
  for `builder` and `builder-heavy`, using the existing four arms
  (`raise | none | same | neither`) exactly as it does for Codex's pair (`model`, effort).
  For example, `builder: standard` / `builder-heavy: reasoning` with no pin shall give
  `raise`.

  For claude, codex, opencode and antigravity the verdict function shall be unchanged.
- **R9** — While `pi` is selected and some selected non-antigravity front end resolves
  anything, `.harness/.escalation-arming` shall:
  - carry a `pi=<verdict>` line, in `AGENT_KEYS` order (last);
  - include pi in the `armed` AND;
  - count pi in its `models_any` gate.

  The verdict shall be `pi=unstamped` when `.pi/agents/builder.md` or
  `.pi/agents/builder-heavy.md` has an unsafe path component or is not byte-equal to freshly
  generated bytes after §5f-pi. A pi-only, all-`inherit` target shall still get no arming
  file. This supersedes E35-F01 R11.
- **R10** — While `pi` is not selected, every generated artifact and the
  `.escalation-arming` file shall be byte-identical between a config with and a config
  without `models.pin.pi.*` keys. The comparison covers the claude, codex, opencode and
  antigravity selections.

  When `pi` is added to a selection, the per-front-end `<fe>=` lines of
  `.escalation-arming` other than `pi=` shall be unchanged. The first line may change,
  because pi joins the AND (R9).

  Every existing model-routing and escalation suite shall pass unchanged, with three
  exceptions:
  - `tests/test_self_mode.sh`'s ordered-set assertion, which gains `pi` (forced by R12's `pi=neither`);
  - `tests/test_pi_front.sh`'s R11 case, which this feature replaces;
  - `tests/test_pi_agents.sh`'s F02 R1 no-`model:` assertion, which is narrowed to the
    all-`inherit` install.
- **R11** — The seed `harness.config.yaml` `models:` comments and its `escalation:` comments
  shall document:
  - `pin.pi.<tier>` (`provider/id`, no `:<thinking>` suffix);
  - the pi thinking ladder;
  - the pi arming rule.

  Each of the seed's `models:` lines shall still read `inherit`. The `models:` and
  `escalation:` blocks in `migrate_config` shall stay byte-identical to the seed's. A
  commented `# pin.pi.<tier>: "<value>"` line shall never resolve.

  The following shall describe pi model routing:
  - `docs/INSTALL.md`: the tier table gains pi `model` and pi `thinking` columns, plus a pi
    section;
  - `docs/WORKFLOW.md`;
  - `agents/orchestrator.md`;
  - the installer's manifest text for `.escalation-arming`;
  - the `CHANGELOG.md` `[0.94.0]` entry.

  `VERSION` shall read `0.94.0`. No doc shall still say pi role files carry no
  `model:`/`thinking:` "(E35-F03)".
- **R12** — When `harness-install.sh --self` runs with `pi` selected, it shall:
  - resolve pi from the source seed config, not a harvest;
  - regenerate `.pi/agents/*.md` byte-identical to the files committed before this feature
    (no `model:`/`thinking:` line);
  - write `pi=neither` into the root `.escalation-arming`, with the first line unchanged
    (`blocked`);
  - include `.pi/agents/builder.md` and `.pi/agents/builder-heavy.md` in the source
    `unstamped` probe.

  This repository shall commit the regenerated `.escalation-arming` and glue manifest, and
  `tests/test_self_drift.sh` shall stay green.

## Out of scope

- An operator thinking override, such as `models.thinking.*` or a split `:<level>` suffix.
  This was rejected; see Business rules.
- Model-list or strength checks. `raise` still proves change, not strength.
- Harvesting pi values from the committed `.pi/agents` in `--self`.
- Rewording the `builder-heavy` description.
- Changing `_cfg_models_value`. Its known `#`-inside-quotes truncation is shared by every
  front end and is left as is.
- pi environment preflight and the `pi-subagents` install (E35-F04).
- `excludeTools`, `modelProvider`, `modelScope` and other `pi-subagents` keys.
