# pi role sub-agents — Test Contract

> The traceability matrix: every R-id in the `.spec.md` maps to a concrete, executable
> test. The Reviewer fails the feature if any R-id lacks a passing test.
>
> New cases live in `tests/test_pi_agents.sh`, a POSIX `sh` suite with `set -eu` and the
> `fail`/`pass` helpers. Every installer run goes through an `inst` helper:
> `env -i PATH="$SANDBOX_PATH" HOME="$T/home" CODEX_HOME="$T/ch"`, into its own
> `mktemp -d` target. `SANDBOX_PATH` is built as in `tests/test_pi_front.sh`: the real
> PATH minus every directory that holds a `pi` executable. The suite asserts that `pi`
> does not resolve on that PATH.
>
> **The stub `pi`** lives in `$T/stubbin/pi` and is prepended to `SANDBOX_PATH` only for
> dispatcher cases. It writes three things:
> - each argv element to `$STUB_LOG/argv`, NUL-separated (`printf '%s\0'`);
> - `pwd -P` to `$STUB_LOG/cwd`;
> - a copy of the file that follows `--append-system-prompt` to `$STUB_LOG/appended`.
>
> It then prints `STUB-STDOUT` and exits `${STUB_RC:-0}`. No case runs the real `pi`, a
> model, or the network.

## The shape-matrix test (R5, R6): required structure

`test_pi_agent_shape_matrix` is driven by **one** data table in the suite. It is a
here-doc of rows `component shape op expected_outcome expected_warning_substring`, with
one row per cell of the plan's matrix (L1–L3, S1, S2 × each shape × I, G+, D, G-). A
helper builds each row's fixture and asserts the outcome code. Requirements:

- **Coverage is checked.** A guard counts the rows per `(component, op)`. It fails when
  any `(component, shape)` from the plan is missing for any of I, G+, D or G-. That way a
  dropped row reds instead of silently shrinking coverage.
- **Every Sv row plants a byte-fresh victim**, generated by the same installer into a
  scratch target, so a delete-through or write-through is observable. The L1 Sv rows run
  twice: once with a victim file, once with an empty `agents/` (the prune victim).
- **Warning counts are asserted**, not just substrings: KD/KK rows assert the exact count
  per the plan's outcome codes; KD0 rows assert zero pi-agent warnings.
- **Upgrade row.** One row installs a 0.92.0-shaped pi target (`.pi/prompts/` present, no
  `.pi/agents/`, no `.harness/.pi-agents/`) and re-installs: all role files written,
  `.pi/prompts/` cksum unchanged (the plan's `L2 A` row).
- **Every row also asserts the four invariants:**
  - exit 0;
  - the canary role is processed;
  - `.pi/prompts/` cksum is unchanged;
  - no out-of-scope path changed.
- **Mutation evidence for the Reviewer.** Each guard must red at least one row when
  mutated. The mutations: drop the `[ -L ]` test in `pi_node_unsafe` (via a copied
  installer), swap the stamp/live precedence, and replace `rmdir` with `rm -rf`. Record
  the mutants and results in `progress/<run>/`.

## Behavioral / end-to-end checks (Reviewer)

- Run `sh harness-install.sh --agents=pi --pr-loop=true /tmp/x`. Read
  `.pi/agents/architect.md` and `.pi/agents/scout.md` by eye against the plan's exact
  bytes.
- Run `PATH=/tmp/stub:$PATH /tmp/x/.harness/tools/pi-dispatch.sh scout /tmp/task.md` with
  a stub that echoes its argv. Confirm the argv by eye.
- Optional, manual, never in CI: where pi is installed and authenticated, run
  `cd /tmp/x && .harness/tools/pi-dispatch.sh scout <task>` for a trivial read-only task,
  and confirm a non-empty answer with exit 0. Where `pi-subagents` is installed, also run
  `/reload` and check that the `subagent` tool lists the harness roles. Record the results
  in `progress/`. Do not gate on them.
