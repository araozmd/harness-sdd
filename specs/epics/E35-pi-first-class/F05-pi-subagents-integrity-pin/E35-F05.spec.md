# Integrity-pin the `pi-subagents` install — Functional Spec

> R-ids in this document are `R1 … R12`; their fully-qualified form is `E35-F05:R1 … E35-F05:R12`.

## Context

E35-F04 installs the backend with `pi install -l -a npm:pi-subagents@0.78.0` and reports
`pinned` when pi lists that entry and the installed `package.json` says `0.78.0`. That pins
**name@version** only. On a project the operator trusts, files committed under `.pi/` can
make npm install other code than the official tarballs, and npm runs that code's lifecycle
scripts **during** the install (pi passes no `--ignore-scripts`). `pinned` can then certify
an install that is not the official code. `docs/INSTALL.md` documents this today as "not an
integrity pin".

The human chose option (c) in the intent brief (`progress/inbox/E35-F05.md`): guards both
**before** the install (refuse anything that would steer npm) and **after** it (`pinned`
needs byte-verifiable proof). The people affected are harness operators who select pi and
approve the install.

**Complexity basis.** `complex`, on three stated signals:

- the spec is at the `change_size.max_requirements` budget (12 of 12);
- it depends on third-party surfaces, namely npm's resolution inputs and pi's settings merge.
  E35-F03 paid five Codex rounds for this class and E35-F04 four review rounds (lessons
  2026-10-16/17);
- it adds a byte contract, the tree digest, that is computed in more than one place: the
  installer, the test fixture and the plan's reproduction recipe.

### Verified facts (offline, 2026-10-17: pi 1.2.0 source, npm 11.20.0, node 26.11.1, the official `pi-subagents@0.78.0` tarball)

Each fact was reproduced with real npm against scratch prefixes, served by a local
registry. The plan's §Empirical findings lists the commands. pi was **not** run; its
behaviour comes from `@earendil-works/pi-coding-agent/dist/core/*.js`, and the settings
facts come from loading pi's own `SettingsManager` against scratch dirs.

1. **The install argv.** pi runs `npm install npm-spec --prefix <cwd>/.pi/npm --legacy-peer-deps`
   (`package-manager.js:1530`, `getNpmInstallArgs`). The cwd is inherited, so it is the target.
   There is no `--ignore-scripts`.
2. **`npmCommand`.** `getNpmCommand()` returns `[...settings.npmCommand]` for **any truthy**
   value of the merged (user ⊕ project) settings. A string is spread into characters, and
   `[]` falls back to `npm`. The value also chooses the argv flavour: npm, pnpm or bun. No
   other pi setting reaches the install path: the package manager reads only `npmCommand`,
   `packages`, and trust.
3. **Settings forms pi accepts.** All of these make pi return the attacker's command:
   - a leading BOM;
   - invalid UTF-8 elsewhere in the file;
   - the key spelled with escapes (`npm\u0043ommand`);
   - duplicate keys (last one wins);
   - **`{"__proto__": {"npmCommand": [...]}}`**. pi's `deepMergeObjects` assigns
     `result["__proto__"] = …`, which sets the merged object's prototype, so the override
     arrives with no top-level `npmCommand` key at all.

   `{"constructor": {"prototype": …}}` has no effect.
4. **An explicit spec is re-resolved.** For `npm install pi-subagents@0.78.0`, npm ignores a
   lockfile entry for `node_modules/pi-subagents` that is steered, whether by URL or by URL
   plus integrity. It fetches the registry tarball (0 requests to the steered URL).
5. **Lockfiles steer dependencies.** The following all made npm fetch a dependency's tarball
   from an attacker URL (`jiti` in the probe):
   - a `resolved` in `.pi/npm/package-lock.json`;
   - the same in `npm-shrinkwrap.json`;
   - a v1 lockfile that has only a `dependencies` section;
   - the **last** of two duplicate `packages` keys;
   - a lockfile with a BOM and invalid UTF-8;
   - an entry with no `integrity`.

   In a v2 lockfile, `packages` wins over `dependencies`. A steered dependency's
   `postinstall` **ran during the install** (canary written; npm 11.20 only warns).
6. **`yarn.lock`.** A `.pi/npm/yarn.lock` steers a dependency, and its `postinstall` runs.
7. **`.pi/npm/package.json`.** Three keys steer a dependency or run its scripts:
   - `overrides` and a URL in `dependencies` steer a dependency and run its `postinstall`;
   - `workspaces` runs a workspace package's `postinstall`.

   Two do nothing for this install: root `scripts` do **not** run for `npm install <spec>`,
   and a URL `dependencies` entry for `pi-subagents` itself loses to the explicit spec.
   `overrides` of `pi-subagents` fails with `EOVERRIDE`.
8. **An existing `node_modules` is trusted by npm.** Take a dependency directory with tampered
   contents and its real version in its `package.json`. If its dependent is also present,
   it **survives** `npm install` byte-for-byte. This holds with both lockfiles, with only
   `node_modules/.package-lock.json`, and with no lockfile at all. The same holds for
   `pi-subagents` itself. The hidden lockfile is ignored only when the directories it lists
   are missing.
9. **`.npmrc`.** `.pi/npm/.npmrc` is honoured (F04 already refuses it). `<target>/.npmrc` is
   **not** read under `--prefix`.
10. **npm writes nothing extra into the package dir.** A fresh install of `pi-subagents@0.78.0`
    holds exactly the tarball's 1331 regular files, byte-identical, with no links. File modes
    follow the umask (`0600` under `umask 077`), so modes are not part of the contract. npm
    records `"pi-subagents": "^0.78.0"` in `package.json` and writes a v3 lockfile (`packages`
    only).
11. **Pin data.** All values come from the npm registry:
    - `dist.integrity` is
      `sha512-AsOvPL1xaVFV4bqIlheQKNI2LmAoiAKTPXXxi39/BsWJTdMJIqAkZJ3iLi6bTsh2PZHG7Ur08b7VJOtgAMIAig==`;
    - the tarball is `https://registry.npmjs.org/pi-subagents/-/pi-subagents-0.78.0.tgz`;
    - the scoped form is `https://registry.npmjs.org/@js-temporal/polyfill/-/polyfill-0.5.1.tgz`;
    - the tree digest (plan §Tree digest) of the extracted package is
      `ca6eb868eaf496af797e4ad17485c37d7e97199c30deb50072217d95b724fc87`, identical from the
      tarball, from two npm installs and under `umask 077`.
12. **Nothing writes into the package dir at run time.** This is source-read, not run. The
    `pi-subagents` code resolves its own directory only to *read* `package.json`,
    `CHANGELOG.md`, `agents/` and `prompts/`. Its `install.mjs` is a legacy `bin` that npm
    never runs; it writes under `~/.pi/agent`. jiti's filesystem cache goes to
    `<dir of the importing file>/node_modules/.cache/jiti` only when that `node_modules`
    exists, and otherwise to `os.tmpdir()/jiti`. A verified tree has no nested `node_modules`
    (R9), so a used install stays digest-stable.

### What the facts change in the brief

- **Fact 8 defeats the lockfile rule on its own.** A canonical lockfile, or no lockfile, plus
  a committed tampered `node_modules/<dep>` installs and runs attacker code. So the install
  is refused while `.pi/npm/node_modules` exists (R2). That also makes the hidden lockfile
  moot: it lives inside `node_modules`.
- **Facts 6 and 7 are steering inputs the brief did not list.** They lead to the `.pi/npm`
  entry allow-list (R3) and the `package.json` content rule (R4).
- **Fact 3's `__proto__` form** is not a top-level `npmCommand` key, and R1 covers it.
- **Fact 4 makes the brief's pre-install "pi-subagents `integrity` == pin" sub-rule an
  equivalent mutant.** npm never uses that entry for the explicit spec, so the rule is
  dropped. The integrity is checked **after** the install instead (R8), where it guards what
  a *later* npm run in this prefix would install.

## Business rules

- **Refuse before npm runs.** Every steering input is checked at the moment of an approved
  install, before `pi install` is executed (lifecycle scripts run during the install, fact 5).
  A refusal is `install: not attempted: <fixed reason>`.
- **`pinned (project)` means byte-verified.** The lockfile entry carries the pinned integrity,
  and the files on disk hash to the pinned tree digest.
- **Fail closed.** Anything unreadable, ambiguous, oversized or of an unexpected node type
  refuses (before) or reads `unverified` (after). It never reads `pinned`.
- **Read as leniently as the consumer, then judge strictly** (lessons 2026-10-17). Every
  re-read of a file that pi or npm reads strips one BOM and replaces invalid UTF-8, as they
  do. Duplicate keys are never resolved silently.
- **One guard per hazard, one fixed reason word per refusal.** The F04 refusals stay intact
  and keep precedence (R7).
- **The installer still never writes under `.pi/npm` or the pi agent dir.** It reads only.
  Removing a refused `node_modules` is the operator's call.

## Architecture alignment

`specs/architecture.md` is absent in this repository. The platform ADR set (`specs/adr/`)
is present, so the touched decisions are cited:

- ADR-0007 — pi sub-agent backend = **pinned** `pi-subagents`, `pi -p` fallback. This feature
  strengthens decision 3, "pinned". The pin becomes name@version **plus** the registry
  integrity **plus** a tree digest, each a single installer constant beside
  `PI_SUBAGENTS_PIN` (R11). The install stays approval-gated and read-only by default, and
  the installer still never writes under `~/.pi/agent` (business rules).
- ADR-0002 — `builder-heavy` is a tier. F04's R10 re-check of `pi_builder_overridden` after
  any install attempt is untouched. A refusal added here happens **before** any attempt, so
  the arming verdict is computed from unchanged settings.
- ADR-0005 — source-only surfaces emit only under `--self`. Unchanged: `--self` still runs no
  preflight and no `pi` (F04 R2).

## Acceptance criteria (EARS)

- **R1** — If, at the moment of an approved install, the **project** `.pi/settings.json`
  contains a key named `npmCommand` or `__proto__` at **any** depth, then the installer shall
  not run `pi install`. It shall report
  `install: not attempted: npm command override (project settings)`. The key is detected:
  - in **every** occurrence, duplicate keys included, whatever its value (`null`, `[]` and
    `""` included);
  - after JSON escape decoding, so `npm\u0043ommand` counts.

  The file is read per R6. F04's strict content check runs first (R7), so a BOM'd, invalid
  UTF-8 or unparsable project file is already refused as `unsafe .pi/settings.json content`.

  A `npmCommand` in the **user** `<agent dir>/settings.json` is the operator's own, trusted
  choice, and shall **not** refuse. F05 neither reads nor writes the user file; F04's
  existing layer-1 read of it is unchanged. The user file's `__proto__` route needs no
  handling for two reasons. It is the operator's file. It is also inert: pi's merge spreads
  the user settings as the base, which copies `__proto__` as a plain own property. Verified
  with pi's `SettingsManager`, it yielded no `npmCommand`.

  **Consequence.** When the user's `npmCommand` selects a non-npm manager (pnpm, bun, or a
  wrapper), the npm-specific guards R3–R5 may not cover that manager's inputs. pnpm, for
  example, reads `pnpm-lock.yaml`, which R3 does refuse, but its semantics are not modelled.
  The post-install verification (R8, R9) therefore decides `pinned`. An install that does not
  produce the expected npm lockfile entry, or a flat real-file package dir, reads
  `unverified` and exits 5 under the flag (R10).
- **R2** — If, at the moment of an approved install, `.pi/npm/node_modules` exists as any
  node type (an empty directory included), then the installer shall not run `pi install`. It
  shall report `install: not attempted: existing .pi/npm/node_modules`, followed by one
  `fix:` line saying that npm keeps whatever is already there, and that removing
  `.pi/npm/node_modules` lets npm reinstall every listed package from the registry.
- **R3** — If, at the moment of an approved install, `.pi/npm` has a direct child whose name
  is not one of `package.json`, `.gitignore`, `package-lock.json`, `npm-shrinkwrap.json`
  (and `node_modules`, which R2 handles first), then the installer shall not run
  `pi install`. It shall report the fixed text `install: not attempted: unexpected entry in .pi/npm`
  and never echo the name.
- **R4** — If, at the moment of an approved install, `.pi/npm/package.json` exists and fails
  any of the rules below, then the installer shall not run `pi install` and shall report
  `install: not attempted: unsafe .pi/npm/package.json content`. The rules:
  - it is read as a JSON object (R6) with no duplicate key at any depth;
  - its top-level keys are a subset of `name`, `private`, `dependencies`;
  - `dependencies`, when present, is an object whose every value matches
    `^[~^]?MAJOR.MINOR.PATCH(-prerelease)?(+build)?$`.

  The last rule refuses URLs, `file:`, `git…`, `npm:` aliases, tags, ranges with spaces and
  `||`. The first two refuse `overrides`, `workspaces`, `devDependencies`,
  `optionalDependencies` and every other key.
- **R5** — If, at the moment of an approved install, `.pi/npm/package-lock.json` or
  `.pi/npm/npm-shrinkwrap.json` exists and fails any of the rules below, then the installer
  shall not run `pi install` and shall report `install: not attempted: lockfile <file> <word>`.
  `<file>` is the fixed file name, and the first file checked is `package-lock.json`. The
  rules, with their reason words:
  - **`unreadable`** — the file reads as a JSON object (R6) whose `packages` value is an
    object. An absent `packages` refuses; that is the v1 form, fact 5;
  - **`ambiguous`** — the file has no duplicate key at any depth;
  - **`not canonical`** — every `packages` key other than `""` matches
    `node_modules/<name>(/node_modules/<name>)*`, where `<name>` is `[A-Za-z0-9._~-]+` or
    `@[A-Za-z0-9._~-]+/[A-Za-z0-9._~-]+`. Each such entry has a string `version` that
    fully matches `MAJOR.MINOR.PATCH(-prerelease)?(+build)?`, **checked before the URL is
    built**. That grammar has no `/`, so a `version` such as
    `2.7.0/../../../evil/-/evil-1.0.0` cannot make the formula below name another package.
    The entry also has a `resolved` **exactly equal to**
    `https://registry.npmjs.org/<name>/-/<leaf>-<version>.tgz`, where `<name>` is the key's
    last segment and `<leaf>` is that name's part after any `@scope/`.

  The `not canonical` rule therefore also refuses `link` entries, `inBundle` entries without
  `resolved`, aliases and mirror URLs.
- **R6** — Wherever this feature re-reads a JSON file that pi or npm reads (R1, R4, R5, R8),
  the installer shall:
  - read it only when it is a regular file (by `lstat`, never following a link) of at most
    4 MiB;
  - strip one leading UTF-8 BOM;
  - decode invalid UTF-8 with U+FFFD replacement;
  - reject `NaN`, `Infinity` and `-Infinity`;
  - see every occurrence of a duplicate key.

  A file that fails any step is "unreadable" for the requirement that reads it.
- **R7** — When an approved install reaches F04's precondition step, the installer shall
  evaluate the checks in this order and report only the first failure:
  1. F04's checks: pi version, trust, `pi_install_paths_safe`, which includes
     `.pi/npm/.npmrc` and the link/hard-link tree walk;
  2. R1;
  3. R2;
  4. R3;
  5. R4;
  6. R5.

  A refusal is evaluated in the main shell, so under `--pi-deps=install` from the flag the
  run finishes every remaining step and exits **5** (F04 R11). In every other mode a refusal
  leaves the exit status unchanged. A refusal from R1–R5 shall execute no `pi` and no `npm`
  after the `pi list -a` probe.
- **R8** — When the backend probe would report `pinned (project)` under F04 R5, the installer
  shall additionally require the **effective lockfile** to carry a `packages` entry
  `node_modules/pi-subagents` with `version` equal to `PI_SUBAGENTS_PIN` and `integrity`
  equal to `PI_SUBAGENTS_INTEGRITY`. The effective lockfile is `.pi/npm/npm-shrinkwrap.json`
  when it exists, else `.pi/npm/package-lock.json` (npm's own precedence). It is read per R6,
  and a duplicate key fails the check. Otherwise the status shall be
  `pi-subagents: unverified (lockfile)`.
- **R9** — When the backend probe would report `pinned (project)` and R8 holds, the installer
  shall additionally require the tree digest (plan §Tree digest) of
  `<realpath target>/.pi/npm/node_modules/pi-subagents` to equal `PI_SUBAGENTS_TREE_SHA256`.
  The walk does not follow links. Every entry must be a directory, or a regular file with
  link count 1 whose relative path holds no control character. A newline in a name could
  otherwise merge lines and make a reduced tree reproduce the official digest. Otherwise the
  status shall be `pi-subagents: unverified (files)`.
- **R10** — While the backend status is `unverified`, the installer shall neither prompt nor
  install.
  - On the status probe it shall report `install: not attempted: backend unverified`,
    followed by R2's `fix:` line, which under the flag exits 5 (R7).
  - On the post-install verify probe (F04 R10) it shall report `install: failed: not verified`,
    which under the flag exits 5.

  `pinned (user)` keeps exactly F04's rule. The user scope is not byte-verified, and the
  report shall not claim it is.
- **R11** — The installer shall hold `PI_SUBAGENTS_INTEGRITY` (fact 11's sha512) and
  `PI_SUBAGENTS_TREE_SHA256` (fact 11's digest) as single constants beside
  `PI_SUBAGENTS_PIN`. Each literal value shall appear exactly once in `harness-install.sh`
  outside comments. The tree-digest algorithm shall be exactly the one in plan §Tree digest:
  sha256 over the sorted `<sha256-hex><2 spaces><relpath>\n` lines.
- **R12** — The installer shall document the feature in `docs/INSTALL.md`'s pi section,
  `CHANGELOG.md` `## [0.96.0]` (naming E35-F05) and `VERSION` `0.96.0`.
  - In the pi section (≈ lines 135–150), the sentence "The pin is `name@version` resolved
    through npm, not an integrity pin: on a project you trust, a committed lockfile can steer
    the tarball URL." shall be replaced.
  - The replacement shall state that `pinned (project)` means byte-verified (integrity plus
    tree digest), and that `pinned (user)` is not byte-verified.
  - It shall list the new refusals with their fix, among them the R2 "remove
    `.pi/npm/node_modules`" fix and the mirror-registry consequence of R5.
  - It shall state the residual: dependencies of an install the harness did not run are not
    re-verified.

## Out of scope

- Pinning the integrity or a tree digest of the six dependencies. They are protected on the
  install the harness runs: `node_modules` is absent (R2), so npm fetches each one from a
  canonical URL (R5) or the registry, and checks its lockfile integrity. Dependencies of an
  install the harness did not run are a documented residual (R12).
- Byte-verifying the **user**-scope install (R10). It is operator-owned, and its legacy
  `npm root -g` layout nests dependencies inside the package dir, which an exact-file-set
  rule would always reject.
- Changing pi's or npm's behaviour; deleting or repairing anything under `.pi/npm`.
- The operator's own npm configuration (`~/.npmrc`, global npmrc, `npm_config_*` env, a
  mirror `registry`). The operator is trusted. A mirror makes an *existing* lockfile
  non-canonical (R5), which is fail-closed.
- `pnpm` / `bun` support. A user-scope `npmCommand` is honoured, but the pre-install guards
  model npm only. A non-npm install is judged solely by R8/R9, and normally reads
  `unverified` (R1 consequence).

## Open questions

None blocking. These decisions are for the human gate (they depart from or extend the brief):

1. **R2 refuses an existing `.pi/npm/node_modules`, including a legitimate prior install.**
   An upgrade or re-install now needs `rm -rf .pi/npm/node_modules` first. Fact 8 shows that
   no lighter rule protects the dependencies.
2. **Resolved at the gate (2026-10-17).** R1 is project-scope only. A user-scope
   `npmCommand` is trusted, and R8/R9 decide `pinned` for a non-npm manager.
3. **A single tree-digest constant replaces the brief's shipped per-file manifest.** It is
   equally strong: an extra, missing or changed file changes the digest. It avoids a
   1331-line file that `tools/` would copy into every target, at the cost of per-file
   diagnostics.
4. **The brief's pre-install "pi-subagents `integrity` == pin" sub-rule is dropped** as an
   equivalent mutant (fact 4). Its protection moves to R8.
5. **R3 and R4 are allow-lists, not deny-lists.** A hand-added `README` in `.pi/npm`, or a
   `version` key in its `package.json`, refuses.
