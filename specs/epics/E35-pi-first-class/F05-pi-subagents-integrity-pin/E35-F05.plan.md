## Tree digest  (serves: R9, R11)

The digest proves the package dir's exact file set and contents. It is computed as follows.

1. Walk `D` (the package dir) without following links, collecting every non-directory
   entry. Each must be a regular file with `st_nlink == 1`. Its path relative to `D` is
   joined with `/`, encoded as UTF-8 bytes, and must hold no byte in `\x00-\x1f\x7f`.
   Anything else ⇒ `unverified (files)`. The control-character rule is load-bearing: a file
   named `a\n<hash-of-b>  b` holding `a`'s bytes yields the same line stream as the two
   files `a` and `b`. Without the rule, a reduced or renamed tree could match the digest.
2. For each file, form the line `<sha256 hex of the bytes, lowercase>` + two spaces +
   `<relpath>` + `\n`.
3. Sort the lines by relpath bytes. Directories contribute nothing, so an extra empty
   directory is harmless.
4. The digest is `sha256(concatenation of the lines)`, as lowercase hex.
5. Any `OSError` ⇒ `unverified (files)`. There is deliberately no file-count or size bound.
   An oversized tree already fails the digest, so a bound would be an equivalent mutant (one
   guard per hazard).

The format equals `sha256sum` output lines sorted by path. The digest is not portable across
pin bumps: a new pin needs a new constant (see §Reproduction).

**Reproduction (for a future pin bump; not run by tests, it needs the network).** Fetch the
tarball into an empty directory, then check its sha512 against the registry:

```
npm pack pi-subagents@<pin>
npm view pi-subagents@<pin> dist.integrity
```

Then extract it with `tar -xzf` and compute the digest over `package/` with the algorithm
above. A tarball member is always a regular file (fact 10). The values above were obtained
this way and cross-checked against two real npm installs (§Empirical findings).

## Design

### 1. `pi_install_npm_safe` — the new pre-install guards  (serves: R1–R7)

- **What it is.** A new sh function with one `python3 -I` here-doc, defined beside
  `pi_install_paths_safe`. It takes `$TARGET` and the agent dir (`$PI_AD`, already resolved
  by F04's §2). It sets `PI_UNSAFE_REASON` to one fixed reason (table above) and returns 1,
  or it returns 0.
- **Where it is called.** It is called **only** in `pi_preflight`'s step 5, as the line right
  after the existing `pi_install_paths_safe` call:
  `if [ -z "$_pf_why" ] && ! pi_install_npm_safe; then _pf_why="$PI_UNSAFE_REASON"; fi`.
  That gives the R7 order. F04's existing `pi_preflight_flag_fail` path then gives exit 5.
  The F04 "backend status unknown" branch keeps calling only `pi_install_paths_safe`. Do not
  add the new function there: it is not an install moment.
- **The python checks, in R7 order. The first failure prints its reason and exits 1.**
  - **R1.** Check `$TARGET/.pi/settings.json`, then `<agent dir>/settings.json`. A file that
    does not exist is skipped; for the user file, a dangling link counts as not existing, as
    with pi's `existsSync`. Read the file with the §2 reader, which uses an
    `object_pairs_hook` that records every key at every depth.
    - Any recorded key equal to `npmCommand` or `__proto__` ⇒ that file's
      `npm command override (…)` reason.
    - A user file the reader rejects ⇒ `unreadable user settings`.
    - A project file the reader rejects ⇒ `unsafe .pi/settings.json content`, a defensive
      fallback. F04's strict content check has already refused such a file (R7 step 1), so
      this branch is not separately mutation-tested. Comment that in the code.
  - **R2.** `os.lstat("$TARGET/.pi/npm/node_modules")` succeeds ⇒ `existing .pi/npm/node_modules`.
    The shell prints the `fix:` line after the `not attempted` line.
  - **R3.** For each name in `os.listdir(.pi/npm)`, when `.pi/npm` exists: a name outside
    the four allowed ones ⇒ `unexpected entry in .pi/npm`.
  - **R4.** `package.json`, when present, is read with the §2 reader:
    - a rejected read, or any duplicate key ⇒ refuse;
    - top-level keys must be ⊆ {`name`, `private`, `dependencies`};
    - `dependencies` must be a dict whose every value is a str fully matching
      `[~^]?(0|[1-9]\d*)\.(0|[1-9]\d*)\.(0|[1-9]\d*)(-[0-9A-Za-z.-]+)?(\+[0-9A-Za-z.-]+)?`.
    - Use `re.fullmatch`, never `re.match` with `$`, because `$` matches before a trailing
      `\n`.
  - **R5.** For `package-lock.json`, then `npm-shrinkwrap.json`, when present:
    - reader rejection, a non-dict, or `packages` missing or not a dict ⇒ `unreadable`;
    - any duplicate key ⇒ `ambiguous`;
    - else, for each key ≠ `""`:
      - the key must `re.fullmatch` the R5 path grammar, with
        `NAME = (@[A-Za-z0-9._~-]+/)?[A-Za-z0-9._~-]+`. Allow upper case: legacy npm names
        exist, and URL equality still governs;
      - the value must be a dict;
      - `version` must be a str matching R4's grammar without the `~`/`^` prefix. Check it
        **before** building the URL: the grammar has no `/`, and that is what stops a
        `version` like `2.7.0/../../../evil/-/evil-1.0.0` from making a URL that passes the
        equality check and normalizes to another package;
      - `resolved` must be a str equal to the canonical URL.
      - Any failure ⇒ `not canonical`.

      Canonical: `"https://registry.npmjs.org/" + name + "/-/" + name.split("/")[-1] + "-" + version + ".tgz"`,
      where `name` is the key's last `node_modules/` segment.
- **No per-entry special case for `pi-subagents`** (spec Context, fact 4).
- **Not checked, on purpose.** Each of these would be a guard with no hazard behind it (an
  equivalent mutant):
  - a lockfile's `integrity` field: a canonical URL serves registry bytes, and a wrong
    integrity only makes npm fail `EINTEGRITY`;
  - the root `""` entry: npm takes the root from `package.json`;
  - a v2 lockfile's `dependencies` section next to `packages`: fact 5 shows `packages` wins;
  - `.pi/npm/.gitignore`'s contents;
  - `.`/`..` name segments in R5 keys. The resulting URL normalizes to a registry path that
    does not exist, so it cannot be exploited;
  - R2's "any node type" beyond a directory. F04's walk already refuses a file, link or FIFO
    named `node_modules`, so an `isdir`-instead-of-`lstat` mutant is accepted as equivalent.

### 2. The lenient JSON reader  (serves: R6)

This is one python function, `load_lenient(path, follow_links) -> (obj, dup_seen)`, or a
raise.

- **File checks.** With `follow_links` it uses `os.stat`, otherwise `os.lstat`. The node
  must be `S_ISREG` with `st_size <= 4 MiB`.
- **Decoding.** Read the bytes, drop one leading `EF BB BF`, then
  `decode("utf-8", errors="replace")`.
- **Parsing.** Call `json.loads` with:
  - `parse_constant` raising, to reject NaN/±Infinity, which Node's `JSON.parse` also
    rejects;
  - an `object_pairs_hook` that records every key at every depth into a set, sets
    `dup_seen` when a key repeats inside one object, and returns `dict(pairs)`. That is
    last-wins, the same as `JSON.parse`, and fact 5's duplicate case shows npm is last-wins
    too.
- **Where it lives.** Define it **once**. The two here-docs that need it,
  `pi_install_npm_safe` and `pi_list_status`, should share it, for example as a shell
  variable holding the function's source that both pass to `python3 -I -c`. If the Builder
  keeps two copies instead, each copy gets its own BOM, invalid-UTF-8 and duplicate-key rows
  (tests.md R6). This is the "byte contract in more than one place" class.

### 3. `pi_list_status` — `pinned (project)` becomes byte-verified  (serves: R8–R10)

In PYLIST, where a project-scope entry has `okp` and `version_state(exp) == "ok"`, it
currently does `pinned.add("project")`. Replace that with:

1. **R8.** The effective lockfile is `<target>/.pi/npm/npm-shrinkwrap.json` if it exists
   (`os.path.lexists`), else `package-lock.json`. It is read with the reader
   (`follow_links=False`).
   - The check fails when: the read fails; `dup_seen` is set; `packages` is not a dict; the
     `node_modules/pi-subagents` entry is missing or not a dict; or the entry's `version` or
     `integrity` differs from argv's pin or integrity.
   - On failure: `unverified.add("lockfile")`.
2. **R9.** Only when R8 passed: compute the §Tree digest of `exp`. If it does not equal
   argv's tree sha, `unverified.add("files")`.
3. Otherwise `pinned.add("project")`.

Pass the two new constants as extra argv, after `ad`. Output precedence, extending F04's:

```
mismatch-user > mismatch > unknown > unverified-lockfile > unverified-files > pinned-project > pinned-user > absent
```

`unverified` ranks below `unknown` and above every `pinned`. So a project entry that fails
verification is never masked by a `pinned (user)`, which fails closed.

In sh, the status `case` accepts `unverified-lockfile|unverified-files`, and `pi_preflight`
handles them as follows:

- **§3, the report.** Print
  `info "pi preflight: pi-subagents: unverified (lockfile)"` or `… (files)`.
- **§4, the decision.** Add a `case` arm `unverified-*)` that prints
  `install: not attempted: backend unverified` plus R2's `fix:` line, calls `pi_preflight_flag_fail` and returns.
  It sits beside the `mismatch-user` arm, and so before any prompt (R10).
- **§6, the verify probe.** It already maps anything but `pinned-*` to
  `failed: not verified`. That is unchanged, and it now covers `unverified-*` (R10).

The user scope is unchanged (R10, spec Out of scope).

### 4. Test seam: a fixture copy with synthetic constants  (serves: R8–R11, tests)

The real constants describe the real 2.4 MB tarball, which no test may fetch. So the tests
**never** add a runtime knob. Instead the suite builds one fixture copy of the repo at setup,
copying `cp -R` of every top-level entry except `.git`, `scratchpad`, `node_modules` and
`progress` (≈35 MB, once per suite). In that copy it rewrites the two constant lines to the
values of a **synthetic** package tree that the stub writes.

- Compute the synthetic integrity and digest in the test with an independent implementation
  of §Tree digest; do not extract it from the installer.
- Print the applied diff and require it to have exactly two changed lines (lesson 2026-09:
  a void `sed` reads as a pass).
- Point `TMPDIR` outside the repo (lesson 2026-09-28).

The F04 suite's `pi` stub, in `install real`, the `add-subagents` modes and `setsid-real`,
must then write a realistic `.pi/npm`:

- `package.json` = `{"name":"pi-extensions","private":true,"dependencies":{"pi-subagents":"^<ver>"}}`;
- `package-lock.json`, v3, with a `node_modules/pi-subagents` entry: the version, the
  canonical `resolved`, and the synthetic integrity;
- the synthetic files under `node_modules/pi-subagents/`, including its `package.json` with
  the version.

Every F04 row that expects `pinned (project)` or `installed and verified` runs the fixture
installer. One F05 row runs the **unpatched** installer against the same synthetic tree, and
must read `unverified (files)` or `(lockfile)`. That proves the shipped constants are not the
synthetic ones.

## Approach notes

- **Ordering is behaviour (R7).** The new function runs after `pi_install_paths_safe`, so
  every F04 shape row keeps its F04 reason. Tests pin the precedence with cells where two
  hazards hold at once (tests.md R7).
- **A refusal is at the install moment, not the status moment.** A target with
  `.pi/npm/node_modules` and status `pinned` never reaches step 5: it prints
  `install: not needed`. The R2 rule therefore only bites when an install would actually run.
- **Reaching `unreadable user settings`.** F04's layer 1 (PYLIST) re-reads the user
  settings **after** the `pi list -a` probe and accepts `NaN`, while the R6 reader rejects
  it, as Node does. So a user file holding `NaN` is the reachable row for this fail-closed
  branch. A file corrupted *during* the probe reads `unknown` first, and never reaches R1.
- **Lessons applied.**
  - Write every hostile table in round 1 (2026-10-14, 2026-10-16).
  - One guard per hazard; the plan lists what is deliberately not checked (2026-10-13).
  - Read as leniently as pi and npm (2026-10-17).
  - Validate whole-string with `re.fullmatch`, never a line-based match (2026-09-25).
  - A shape claim needs a byte-pristine victim (2026-10-13). The reader must not follow a
    link under `.pi`; F04's walk refuses links first anyway.

**Answers to the brief's open questions.**

1. **Does npm reuse a lockfile's `resolved`/`integrity` for the explicit spec?** No (Q1a,
   Q1b). It does for every dependency (Q1c–f).
2. **Does npm honour the hidden lockfile?** Only when the directories it describes exist
   (Q2 vs Q4c), and R2 makes that state unreachable.
3. **Does npm add or rewrite files in the package dir?** No (Q3).
4. **Is an existing lockfile that lists other project pi packages accepted?** Yes, when every
   entry is canonical (R5), once `node_modules` is gone (R2).
5. **Reason words and exit mapping?** The table above, and R7.
