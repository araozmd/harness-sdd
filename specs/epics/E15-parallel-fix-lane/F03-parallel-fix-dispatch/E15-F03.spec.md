# /sdd-fix-parallel dispatch with shared-path conflict guard and installer wiring — Functional Spec

## Context
The lightweight E99 lane can seed several independent autonomous fixes, but the
normal Orchestrator executes them one at a time. This feature gives a maintenance
operator one Fixer-family command that claims a bounded batch and drives isolated
Builder→Reviewer→PR chains concurrently. It builds on E15-F01's canonical locked
board and E15-F02's per-fix worktrees; it does not generalize parallelism to normal
SDD features.

## Business rules
- **Only ready autonomous quick fixes participate.** Candidates come only from E99
  and must be `pending`, `sdd: false`, `autonomous: true`, with every
  `depends_on` id resolving to a `done` feature. Candidate and dependency facts are
  re-checked while the selected batch is claimed under the board lock.
- **One deterministic bounded batch.** Ready candidates are ordered by numeric
  E99 feature id and the first `N` form the batch. `N` is
  `fix_lane.max_parallel`; its safe default is `3`. Every ready candidate after
  the first `N` remains pending and is reported as deferred by the cap.
- **Static guard, safe defaults, extension-only configuration.** The built-in
  shared-path patterns are `harness-install.sh`, `tests/test_install.sh`, and
  `tools/*`. `fix_lane.shared_paths` may append repo-relative exact paths or
  directory-prefix patterns ending in `/*`; it never removes the built-ins.
  A selected fix whose brief names a matching path is guarded. A missing brief,
  missing expected-path declaration, or ambiguous/unsafe path is guarded rather
  than guessed parallel-safe.
- **Parallel means overlapping agent chains, not background shell prompts.** The
  coordinator uses the host's native in-session sub-agent delegation, creates a
  clean targeted Orchestrator worker for each fix, starts all parallel-safe
  workers before awaiting any one result, and keeps guarded workers one-at-a-time
  with no overlap with any other fix. It does not name or require a
  vendor-specific Task API and does not launch code-agent prompts as shell
  background jobs. If native concurrent delegation is unavailable, it fails
  before claiming work and explains that `/sdd-fix` remains the serial fallback.
- **Parallel dispatch requires the in-session Builder.** If
  `execution.builder.backend` is `delegate`, the command fails before creating a
  manifest, provisioning, or claiming and points to serial `/sdd-fix`; a delegate
  may own PR/review timing and cannot satisfy local-review-before-PR.
- **Every chain stays isolated.** Each claimed fix is provisioned through
  `tools/fix-worktree.sh` exactly once before claim; its worker keeps that worktree
  and branch throughout. The coordinator passes the canonical main harness
  directory as explicit `HARNESS_DIR` to the worker environment, and the worker
  uses the F01 helper for every board write.
- **Full per-fix lifecycle.** A targeted worker drives only its assigned fix
  through Builder and Reviewer rounds, opens that fix's PR after local approval,
  runs the review loop for that PR alone, and leaves the fix `in-review` until the
  PR is merged. It reports that merge without setting `done` or tearing down.
- **Shared truth has one serialized Git owner.** After one-time F02 provisioning,
  the coordinator switches the clean canonical primary to a dedicated bookkeeping
  branch, commits the locked claim, and remains the sole owner of primary Git
  operations and serialized history. After all workers settle, it atomically marks
  only merge-observed fixes `done`, commits all final board/history state, and
  persists it through a coordinator bookkeeping PR. After observing that merge it
  fetches, switches to the local base, advances it `--ff-only`, proves the primary
  clean/on the updated base/exact captured commit, and then calls exact non-forced
  F02 teardown only for merged fixes. It never stashes, resets, cleans, force-deletes,
  or otherwise hides shared board changes.
- **Failures do not cancel siblings.** A provisioning, build, review, PR, merge,
  or cleanup failure is recorded against that fix and preserves recoverable
  work. Other selected workers continue. The batch report identifies every
  success, active/recoverable failure, guarded serialization, and cap deferral.
- **No work is a clean no-op; partial failure is still failure.** With no ready
  candidate the command writes no batch directory, provisions/claims nothing,
  reports “no ready E99 fixes,” and exits zero. Cap-only deferrals do not make an
  otherwise successful batch fail. If any selected fix has a provisioning or
  recoverable worker failure, the command still waits for all siblings and then
  exits non-zero with every outcome preserved in the manifest.
- **Fix briefs declare expected paths.** Serial `/sdd-fix` remains behaviorally
  unchanged except that its adaptive intake records a normalized
  `## Files expected to change` list in the one inbox brief. This list feeds the
  static guard; it is planning metadata, not a promise that dynamic diff analysis
  occurs.

## Acceptance criteria (EARS)
> Each requirement is one observable, testable behavior.

- **R1** — When `/sdd-fix-parallel` discovers candidates, the coordinator shall
  consider only E99 features that are `pending`, `sdd: false`,
  `autonomous: true`, and whose every `depends_on` id resolves to a `done`
  feature; it shall never select an `sdd: true`, gated, non-pending, or
  dependency-blocked feature.
- **R2** — When more than one ready candidate exists, the coordinator shall order
  candidates by numeric E99 feature id and select the first
  `fix_lane.max_parallel` candidates, defaulting that value to `3` when the key is
  absent.
- **R3** — If `fix_lane.max_parallel` is present but is not a positive integer, or
  if `fix_lane.shared_paths` is not a list of non-empty string entries already in
  canonical repo-relative form, then the coordinator shall exit non-zero before
  creating a worktree or changing board state and shall name the invalid key or
  value; config entries containing absolute paths, `.`, `..`, empty/repeated/
  trailing separators, control characters, a leading `./`, or a wildcard other
  than one terminal `/*` are non-canonical and shall be rejected rather than
  normalized.
- **R4** — After selected fixes are provisioned while the canonical primary is
  still clean, when the coordinator claims the successfully provisioned subset it
  shall use
  `tools/tasks-lock.py apply` with the canonical main `HARNESS_DIR`, re-check all
  R1 predicates on the freshly locked board, and atomically move every selected
  provisioned fix from `pending` to `in-progress`; if any fix in that subset no
  longer qualifies, the whole claim shall fail without a partial status change
  and all still-safe unclaimed worktrees shall be torn down.
- **R5** — The coordinator shall always treat `harness-install.sh`,
  `tests/test_install.sh`, and `tools/*` as shared-path patterns and shall append,
  rather than replace, valid patterns from `fix_lane.shared_paths`.
- **R6** — When a selected fix's brief declares an expected repo-relative path
  matching a shared-path exact entry or directory-prefix `/*` entry, the
  coordinator shall classify that fix as guarded; if the brief or expected-path
  declaration is absent or a declared path is unsafe/ambiguous, it shall classify
  the fix as guarded with the reason recorded.
- **R7** — When a batch contains parallel-safe fixes, the coordinator shall use
  native in-session sub-agent delegation to start every parallel-safe targeted
  worker before awaiting any one worker's completion, up to the configured batch
  cap.
- **R8** — While a guarded fix is running, the coordinator shall run no other fix
  worker; multiple guarded fixes in one batch shall run one-at-a-time in numeric
  feature-id order after the parallel-safe wave has settled.
- **R9** — If the host cannot provide concurrent in-session sub-agent delegation,
  or `execution.builder.backend` is `delegate`, then `/sdd-fix-parallel` shall exit
  non-zero before creating a manifest, claiming, or provisioning fixes, report the
  incompatible capability/backend, and direct the operator to serial `/sdd-fix`;
  it shall not invent a vendor API or execute agent prompts as shell background
  processes.
- **R10** — Before dispatch, the coordinator shall write a batch manifest under
  `progress/` that lists every ready candidate and marks it as parallel-selected,
  guarded-selected with reason, or cap-deferred; after execution it shall append
  each selected fix's terminal or recoverable outcome, so no candidate is silently
  truncated, serialized, or lost.
- **R11** — Before the board claim dirties the canonical primary, when
  provisioning a selected fix the coordinator shall call the F02 helper for that
  exact fix id/slug exactly once and shall keep that branch/worktree through
  Builder, Reviewer, PR, merge, and reconciliation; only successfully provisioned
  fixes enter the later claim, and a provisioning failure shall be recorded
  without changing its `pending` status or preventing siblings from proceeding.
- **R12** — When a targeted worker runs, the coordinator shall set explicit
  `HARNESS_DIR` to the canonical main harness directory in that worker's
  environment, and every worker board write shall use F01's
  `tools/tasks-lock.py`, independent of standard, separate-git-dir, or submodule
  Git layout.
- **R13** — When a targeted worker receives a fix, it shall drive only that id
  through the existing Builder→Reviewer multi-round contract using a clean context
  per role and file-based feedback; one worker's non-zero/failure outcome shall
  not cancel, roll back, or overwrite another worker's progress.
- **R14** — When a fix passes local Reviewer verification, its targeted worker
  shall keep its pre-provisioned branch/worktree, create only a dedicated PR, keep
  the feature `in-review`, run `/pr-loop` for that PR alone, and report only an
  observed merge. After all workers settle, the coordinator shall atomically set
  only merge-observed fixes `done`, persist claim/final board and serialized history
  through its bookkeeping branch/PR, observe that merge, fast-forward the clean
  canonical local base to the updated remote base, prove F02's exact primary
  preconditions, and then safely tear down only those merged fixes without force or
  disturbance to unrelated state/resources.
- **R15** — While `/sdd-fix-parallel` operates, the system shall introduce no new
  TaskStore status, schema field, or `state/tasks.json` shape and shall not select
  work outside E99 or any `sdd: true` feature.
- **R16** — When serial `/sdd-fix` seeds a new fix, its existing one-brief intake
  shall additionally record a non-empty `## Files expected to change` list of
  normalized repo-relative paths, while preserving the serial command's existing
  E99 allocation, `sdd:false`, autonomous/gated, and handoff behavior.
- **R17** — The installer shall generate `sdd-fix-parallel` from the same command
  body for every selected Claude, OpenCode, Antigravity, and global Codex
  front-end, shall include it in ownership cleanup, and
  `tests/test_install.sh` shall assert its presence and role resolution in a fresh
  install.
- **R18** — Because this feature changes the installed command/role/config/docs
  body, the system shall bump `VERSION` one SemVer MINOR step, add a matching
  `CHANGELOG.md` entry, document the new command/config/guard semantics, and add
  its permanent suite to the configured full verification command.
- **R19** — If no ready E99 candidate exists, then the coordinator shall exit
  zero after reporting `no ready E99 fixes`, without creating a batch manifest or
  worktree and without changing board state.
- **R20** — When every selected fix has settled, the coordinator shall exit zero
  only if every selected fix completed successfully (cap-only deferrals are not
  failures); if any selected fix has a provisioning or recoverable chain failure,
  it shall first await and record every sibling outcome and then exit non-zero.

## Out of scope
- General parallel `next()` selection, any `sdd: true` feature, umbrella slices,
  or ownership-based work claiming.
- Dynamic Git diff/content conflict detection, predicting merge conflicts outside
  the static path list, or automatic merge-conflict resolution.
- Distributed or multi-host locks, a daemon, persistent worker registry, job
  queue, or new external executor dependency.
- Changes to F01's lock implementation, F02's lifecycle implementation, TaskStore
  schemas/statuses, or ADR-0001's general selector.
- Aggregating several fixes into one branch, worktree, PR, or `/pr-loop`.

## Open questions
None blocking. The inbox questions are resolved as follows:
- Concurrent chains use the host's existing native in-session sub-agent abstraction
  with an explicit capability preflight. This is the same portable “spawn a clean
  sub-agent” contract already used by the Orchestrator; no unavailable runtime API
  or shell-background code-agent process is invented.
- `fix_lane.shared_paths` is extension-only. The three safe built-ins cannot be
  disabled, and missing/ambiguous expected-path metadata serializes fail-safe.
- Serial and parallel lanes share the Fixer brief contract and the existing
  Builder/Reviewer roles. Parallel dispatch adds targeted Orchestrator workers; it
  does not fork selection/seeding or create a second implementation role.
