# Board write lock: flock-guarded read-modify-write on tasks.json — Functional Spec

## Context
The harness backend (`store/local.md`) mutates `state/tasks.json` with a plain
read-modify-write and **no locking**. That is safe today only because work runs
strictly serially. Epic E15 introduces concurrent E99 fix chains (F03) that each
transition board state, so two near-simultaneous writers can silently lose an
update (last-writer-wins clobber) — one chain reads the board, a second chain
reads-mutates-writes, then the first chain writes back its stale copy and erases
the second chain's committed transition. This feature gives the `set_status`
persist path a **mutual-exclusion primitive** so concurrent writers are safe. The
users are the harness's own agents (Orchestrator and Builders running in parallel
worktrees), not humans. A normal serial `/sdd-next` run must behave exactly as
before — the lock must be uncontended and invisible there.

## Business rules
- **One advisory lock guards every persisted board write.** Each `set_status` /
  board-persist operation acquires an **advisory** lock on the sibling lockfile
  `state/tasks.json.lock` (resolved with `cwd = HARNESS_DIR`) before touching
  `state/tasks.json`, and holds it across the whole critical section.
- **Re-read INSIDE the lock is mandatory.** The critical-section sequence is
  fixed: acquire lock → **re-read `state/tasks.json` from disk** → apply the single
  mutation to that fresh copy → validate → write → release. Reading *inside* the
  lock (never read-once-then-lock) is the entire point — it prevents the lost-update
  clobber. A writer must never persist a copy of the board it read before acquiring
  the lock.
- **Validation stays fail-stop; no torn file.** Before the on-disk file is
  replaced, the mutated content is validated (`json.load` parse **and**
  `store/tasks.schema.json` schema check). On validation failure the operation
  aborts with a non-zero exit and a clear error, releases the lock, and leaves the
  **original** `state/tasks.json` intact — never a partially-written or truncated
  file.
- **Bounded acquisition, never a silent hang.** Lock acquisition is bounded by a
  timeout. If the lock cannot be acquired within the bound, the operation aborts
  with a non-zero exit and an actionable error that names the lockfile and the
  timeout — it does **not** block forever and does **not** silently proceed
  unlocked.
- **No-op for serial callers.** For a single (serial) caller the lock is always
  uncontended, so it is acquired immediately and the observable behavior of
  `/sdd-next` and every existing test is unchanged. The lock adds no new required
  config, no new status, and no schema field.
- **`on_write_command` fires AFTER release.** The best-effort post-write sync hook
  (`store.on_write_command`) runs **after** the lock is released, exactly as its
  existing best-effort/never-blocking contract requires (a non-zero hook exit never
  rolls back `state/tasks.json`, never blocks). The hook is never invoked inside the
  critical section, so it can never hold the board lock.
- **Single-host scope.** The lock guards concurrent chains **within one host**.
  Cross-terminal / cross-machine coordination is explicitly out of scope (single
  `flock`-family advisory lock only).
- **No new status/enum values, no schema change.** This feature introduces **no**
  new status value and makes **no** change to `store/tasks.schema.json`. The write
  *content* is byte-for-byte what it was; only the concurrency discipline around
  the write changes.
- **Installed-body change ⇒ VERSION bump (MINOR).** The lock protocol lands in the
  installed harness body (`store/local.md` and a new lock helper shipped under
  `tools/`), so `VERSION` is bumped one SemVer **MINOR** step (additive,
  backward-compatible), with a matching `CHANGELOG.md` entry, and the installer
  wiring is asserted in `tests/test_install.sh`.

## Acceptance criteria (EARS)
> Each is one testable behavior with a stable id. See docs/SPEC-FORMAT.md.

- **R1** — When two writers attempt to persist a board mutation near-simultaneously
  under the lock, the system shall serialize them so that **neither writer's
  committed transition is lost** — the second writer, having re-read inside the
  lock, applies its mutation on top of the first writer's result (no last-writer-wins
  clobber).
- **R2** — When a writer acquires the lock, the system shall **re-read
  `state/tasks.json` from disk inside the lock** and apply its mutation to that
  freshly-read content, so it never persists a copy of the board read before the
  lock was held.
- **R3** — The system shall acquire the advisory lock on the sibling lockfile
  `state/tasks.json.lock` (resolved with `cwd = HARNESS_DIR`) for the entire
  critical section and release it before returning.
- **R4** — If the mutated board content fails validation (JSON parse **or**
  `store/tasks.schema.json` schema check), then the system shall abort with a
  non-zero exit and a clear error, release the lock, and leave the **original**
  `state/tasks.json` unchanged (fail-stop; never a partially-written or truncated
  file).
- **R5** — If the lock cannot be acquired within the bounded timeout, then the
  system shall abort with a non-zero exit and an actionable error naming the
  lockfile and the timeout, and shall **not** block indefinitely nor proceed with
  the write unlocked.
- **R6** — While a single serial caller runs (the uncontended case), the system
  shall acquire the lock immediately and complete the write with behavior
  observationally identical to the pre-lock read-modify-write, so `/sdd-next` and
  existing tests are unchanged.
- **R7** — The system shall run the best-effort `store.on_write_command` sync hook
  (when non-empty) **only after** the lock has been released, never inside the
  critical section, preserving the hook's existing best-effort/never-blocking
  contract.
- **R8** — The system shall introduce **no** new status/enum value and make **no**
  change to `store/tasks.schema.json`; the persisted write content is unchanged and
  only the concurrency discipline around it is added.
- **R9** — The system shall implement the lock with a **portable** advisory-lock
  primitive available wherever the harness already runs (it depends only on
  `python3`, already required for the existing re-validation step) — it shall **not**
  hard-depend on the Linux-only `flock(1)` binary, which is absent on the macOS dev
  platform.
- **R10** — The harness installer (`harness-install.sh`) shall install the lock
  helper into the harness body under `.harness/tools/` as an **executable**, and
  `tests/test_install.sh` shall **assert** that a fresh install ships that
  executable helper.
- **R11** — Because this feature changes the installed harness body (`store/local.md`
  and the new lock helper under `tools/`, plus the `tests/test_install.sh`
  assertion), the `VERSION` file shall be bumped one SemVer **MINOR** step
  (additive, backward-compatible; not MAJOR), with a matching `CHANGELOG.md` entry.
- **R12** — When the helper resolves the board file and its lockfile, canonical
  board+lock resolution shall be, in strict precedence and **fail-safe**:
  **(i)** an explicit `HARNESS_DIR` override [**highest precedence**; the F03
  `/sdd-fix-parallel` coordinator sets it to the canonical main harness directory
  for every worktree worker]; **(ii)** else **best-effort auto-discovery** for the
  **standard `.git` worktree layout** — resolve the single canonical location in the
  main working tree (via `git rev-parse --git-common-dir` → the main worktree) and
  **accept it only when the canonical board exists there** (`<canonical>/state/tasks.json`),
  so every worker in any standard-layout worktree reads/writes the **same**
  `state/tasks.json` and contends on the **same** `state/tasks.json.lock` inode
  (this makes R1's no-lost-update guarantee hold in the parallel-worktree context
  the epic targets, not only within a single directory); **(iii)** else, when the
  helper is running **inside a linked git worktree** but auto-discovery did not
  yield an existing canonical board — as happens under **exotic layouts**
  (`git init --separate-git-dir`, submodules) where the main worktree path is
  **provably unrecoverable** from a linked worktree — the system shall **FAIL
  LOUDLY** (non-zero exit + an actionable message demanding an explicit
  `HARNESS_DIR`) and shall **never** silently write the linked worktree's own board
  (a wrong-board write that would defeat the shared-board guarantee). When the repo
  is **not a git worktree at all** (the ordinary single-repo / serial `/sdd-next`
  case, or git is unavailable), the helper falls back to its own self-location as
  before. **Cross-layout correctness for `separate-git-dir` / submodules is
  guaranteed by the F03 coordinator injecting `HARNESS_DIR`, not by auto-discovery.**
  (Refines R3: the lockfile is the canonical one, not a per-worktree sibling.)
- **R13** — When applying a minimal-diff status write, the system shall locate the
  addressed entry's `status` field by resolving the target **object structurally by
  its `id`** (not by assuming textual key order), so a board whose objects order
  `status` before `id` cannot cause the wrong task to be transitioned. The write shall
  still change only the addressed entry's status token, leaving all other bytes intact
  (serves R6), and validate the reparsed result before the atomic replace (serves R4).

## Out of scope
- **Cross-terminal / cross-machine coordination.** Only single-host advisory
  locking is provided; distributed locks are E15's non-goal.
- **Any change to the write content or the schema.** No new status value, no
  `store/tasks.schema.json` change, no reshaping of `state/tasks.json`.
- **The worktree isolation helper (F02) and the parallel dispatch command (F03).**
  This feature provides only the lock primitive those features build on.
- **Locking `write_spec` / `append_progress` / `append_history` and other DocStore
  writes.** Only the `state/tasks.json` board-persist path is guarded here (those
  markdown writes are not the lost-update surface E15 introduces).
- **Auto-merge-conflict resolution** or any retry that merges conflicting hunks.

## Open questions
> None blocking. The two brief open questions are resolved as documented design
> decisions (see `E15-F01.plan.md` → "Resolved open questions").
- **(1) Lock scope — resolved: the narrowest correct boundary is the `set_status` /
  board-persist helper** (the single write path per `store/local.md`), not a broader
  board-mutation entry point. A human may widen it at the gate if F02/F03 surface a
  second write path.
- **(2) Acquisition behaviour — resolved: bounded wait with a clear timeout error,
  not block-forever.** A default timeout is pinned in the plan (a bounded retry-poll
  under the advisory lock). A human may tune the default at the gate; the requirement
  is only that it is bounded and errors clearly (R5), never a silent hang.
