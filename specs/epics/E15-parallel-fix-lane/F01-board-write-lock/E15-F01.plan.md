# Board write lock: flock-guarded read-modify-write on tasks.json — Technical Plan

> Translates the .spec.md intent into design. Every decision cites the R-id(s) it
> serves. Start high-level; don't over-specify internals that might be wrong.

## Stack & dependencies
- Language/framework: **POSIX sh + `python3`** — the exact stack the harness body
  already uses. The existing `set_status` re-validation is `python3 -c "import json;
  json.load(...)"` (see `store/local.md` line 29), so `python3` is already a hard
  dependency of the write path.
- New dependencies: **none.** The advisory lock uses Python's stdlib
  **`fcntl.flock`** (`fcntl` is in the CPython stdlib on every POSIX platform the
  harness targets). *(serves: R9)*

### Where the write actually happens today (the real target)
There is **no shared executable** that persists board state today. `set_status(id,
status)` is a **prose contract** in `store/local.md` (lines 28–36) that the agents
(`agents/orchestrator.md`, `agents/fixer.md`, `agents/driller.md`,
`agents/planner.md`, `agents/inception.md`) execute inline: edit `state/tasks.json`,
then re-validate with `python3 -c "import json; json.load(open('state/tasks.json'))"`.
The installer copies `store/` and `tools/` into `.harness/` (`harness-install.sh`
lines 635–636). Therefore the write path is defined by the **`store/local.md`
contract** + a **helper script the contract points at**. This feature (a) adds a
real, testable advisory-lock helper to `tools/`, and (b) amends the `store/local.md`
`set_status` contract to mandate running the persist through that helper.

## Data model  (serves: R3, R8)
No schema change. The only new on-disk artifact is a **zero-byte advisory
lockfile**, not board data:

| Entity | Field | Type | Notes |
|---|---|---|---|
| lockfile | `state/tasks.json.lock` | file (sibling of `state/tasks.json`) | Advisory `fcntl.flock` target, resolved with `cwd = HARNESS_DIR`. Created on first lock, never contains board data. Gitignore-eligible (runtime lock, per `docs/CONFIG-LAYERING.md`). Serves R3. |

`store/tasks.schema.json` is **unchanged**; `state/tasks.json` shape is unchanged. *(serves: R8)*

## API / interface  (serves: R1–R7, R9)
The lock helper is a small CLI the `set_status` contract invokes. It owns the whole
critical section so the lock cannot be split across processes.

| Invocation | Behavior | R-id |
|---|---|---|
| `python3 tools/tasks-lock.py <mutator> [args…]` (name illustrative; Builder may finalize) | Acquire `fcntl.flock` on `state/tasks.json.lock` (bounded wait) → **re-read** `state/tasks.json` → run `<mutator>` on the fresh content → validate (parse + schema) → atomically replace the file → release. | R1, R2, R3, R4, R9 |
| bounded-acquire | Poll-with-timeout on the advisory lock; on timeout exit non-zero with a message naming the lockfile + timeout. | R5 |
| uncontended acquire | Immediate acquire; observable result identical to today's read-modify-write. | R6 |
| on exit | Release the lock and return; the caller runs `on_write_command` **after** this returns. | R7 |

> The mutator boundary (how `set_status`'s single status edit is expressed to the
> helper) is left to the Builder — the contract is only: *the read, the mutate, the
> validate, and the write all happen inside one held lock, in one process.* The
> default acquisition timeout is pinned below; the atomic-replace mechanism
> (write-temp-then-`os.replace`) is the Builder's call as long as R4's no-torn-file
> guarantee holds.

## DO NOT TOUCH
- `store/tasks.schema.json` — **no schema change** (R8). The lock adds concurrency
  discipline, not data shape.
- `state/tasks.json` (the live board) — this feature must not mutate the repo's own
  live board; the lock behaviour is exercised against **temp-file fixtures** in the
  test (permanent-suite anti-pattern), never the live file.
- The **status enum / any status values** — no new status is introduced (R8).
- `store.on_write_command`'s existing best-effort/never-blocking semantics
  (`store/local.md` "Post-write sync" section) — F01 only fixes its **ordering**
  (after release, R7); it does not change what the hook does or its exit handling.
- `agents/orchestrator.md`, `agents/fixer.md` decision logic beyond pointing their
  `set_status` writes at the `store/local.md` lock protocol — no behavioural gate
  change (the lock is invisible to serial callers, R6).
- The `flock(1)` Linux binary — deliberately **not** used (absent on macOS, R9);
  the Python `fcntl.flock` primitive is used instead.

## Resolved open questions
- **(1) Lock scope → the `set_status` / board-persist helper** (the single write
  path per `store/local.md`), the narrowest correct boundary. Not a broader entry
  point: `next()`/`get()`/`list()` are reads and need no lock; DocStore writes are
  out of scope. *(serves: R3, R6)*
- **(2) Acquisition → bounded wait, not block-forever.** Pinned default: a
  **bounded poll of ~10s** (short enough to surface a stuck holder, long enough that
  a normal held critical section — a re-read + small JSON write — never times out
  under legitimate 2–3-way contention). On timeout: non-zero exit + error naming the
  lockfile and the timeout (R5). The exact default seconds are a one-line constant a
  human may tune at the gate; the **requirement** is only *bounded + clear error*,
  never a silent hang. *(serves: R5)*
- **(3) `flock` primitive → Python `fcntl.flock`, not `flock(1)`.** The brief says
  "advisory flock" (the `flock(2)`-family primitive), not the Linux CLI. `flock(1)`
  is **absent on the macOS dev platform**; `python3 -c "import fcntl"` works there
  and is already a write-path dependency, so the lock is genuinely testable on the
  dev machine. *(serves: R9)*

## Approach notes
- **Atomicity (R4).** Write the mutated JSON to a temp file in the same directory,
  validate it (parse + schema), then `os.replace()` it over `state/tasks.json` — an
  atomic rename on POSIX. If validation fails, the temp file is discarded and the
  original is never touched. This is what guarantees "never a torn/partial file"
  even if the process is killed mid-write.
- **Re-read placement (R2).** The re-read of `state/tasks.json` MUST happen *after*
  `flock` returns success, in the same process that holds the lock — otherwise the
  lost-update window reopens. The test proves this by construction (two writers, both
  must survive).
- **Uncontended invisibility (R6).** For one caller the lock is acquired with zero
  wait; the resulting `state/tasks.json` is byte-equivalent to today's
  read-modify-write, so no existing test needs to change.
- **Hook ordering (R7).** The helper's job ends at release; the Orchestrator's
  existing "run `on_write_command` after a persisted write" step already sits
  *after* the write returns, so keeping the hook out of the helper naturally places
  it after release. The `store/local.md` amendment states this explicitly.
- **Test strategy avoids the permanent-suite anti-pattern.** `test_board_lock.sh`
  runs the helper against **temp-dir fixtures**, launches two concurrent writers,
  and asserts *both mutations survive* and *the file always parses + validates*. It
  does **not** freeze a VERSION string and does **not** diff DO-NOT-TOUCH files
  against `main` — it tests the locking *behaviour*.
