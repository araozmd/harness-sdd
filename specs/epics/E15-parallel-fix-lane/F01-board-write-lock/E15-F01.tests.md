# Board write lock: flock-guarded read-modify-write on tasks.json — Test Contract

> The traceability matrix: every R-id in the .spec.md maps to a concrete,
> executable test. The Reviewer fails the feature if any R-id lacks a passing test.
>
> All behavioural tests run the lock helper against **temp-dir fixtures**, never the
> live `state/tasks.json`, and assert *behaviour* — never a frozen VERSION string and
> never a diff of DO-NOT-TOUCH files against `main` (permanent-suite anti-pattern).

## Behavioral / end-to-end checks
- **R1/R2 (the core guarantee).** In a temp dir, seed a valid two-feature
  `tasks.json`. Launch **two** helper invocations concurrently, each transitioning a
  **different** feature (e.g. `E01-F01 → in-progress` and `E01-F02 → in-review`).
  After both finish, assert the final `tasks.json` reflects **both** transitions —
  proving no last-writer-wins clobber and that the re-read happened inside the lock.
  Repeat under a small loop to shake out timing.
- **R3.** Assert the helper creates/uses `state/tasks.json.lock` as a sibling of the
  target and that the lock is released after the call (a subsequent immediate call
  in the same dir succeeds without timeout).
- **R4.** Feed a mutator that would produce schema-invalid content (or corrupt JSON);
  assert the exit is non-zero, the on-disk `tasks.json` is byte-identical to before,
  and the lock is released (a following valid call succeeds).
- **R5.** Hold the lock from a helper background process (or a small python holder),
  then invoke the helper with the target already locked; assert it exits non-zero
  within a small multiple of the timeout (not hanging) and the error text names the
  lockfile and the timeout.
- **R6.** Run one serial mutation through the helper and, separately, apply the same
  mutation with a trivial read-modify-write; assert the resulting `tasks.json` bytes
  match (normalizing only for the write formatting the helper itself uses).
- **R7.** Configure a marker `on_write_command`-style hook and assert it is only
  observable after the helper has released the lock (e.g. the hook can itself acquire
  the lock without timing out — proving the critical section is already closed).
- **R8.** Assert `store/tasks.schema.json` is unchanged by the feature and that a
  serial write introduces no unexpected status value; validate the serial-write
  output against the schema.
- **R9.** Assert the helper runs and passes on a platform with **no** `flock(1)` on
  `PATH` (the macOS dev box), and that `python3 -c "import fcntl"` is its only lock
  dependency.
- **R10.** In `tests/test_install.sh`, after a sandboxed install, assert
  `.harness/tools/tasks-lock.py` exists and is executable.
- **R11.** Assert `VERSION` parses as a valid SemVer and is **greater than** the
  pre-feature value (compare, do not freeze the literal), and that `CHANGELOG.md`
  gained an entry — behaviour, not a pinned constant.
- **R12.** Create standard source and installed-layout linked worktrees and assert
  writes from each land on the main worktree's board and contend on its one lock.
  In a separate-git-dir linked layout where the canonical board cannot be safely
  recovered, assert the helper exits non-zero without touching either board, then
  assert an explicit `HARNESS_DIR` override lands on the intended main board.
- **R13.** Seed a valid board whose target object orders `status` before `id` and
  assert only that target changes. Also assert colliding ids outside the canonical
  `epics[]`/`features[]` paths are ignored and a duplicate `status` member fails
  stop without changing the board.

## Non-functional checks
- Lint/shellcheck: `tests/test_board_lock.sh` is POSIX sh, zero non-stdlib deps
  (matches `init.sh` / `test_sdd_fix.sh` ethos: POSIX sh + grep + `python3`).
- The suite **never** mutates the live `state/tasks.json` — every case uses a temp
  dir with `HARNESS_DIR` pointed at it.
