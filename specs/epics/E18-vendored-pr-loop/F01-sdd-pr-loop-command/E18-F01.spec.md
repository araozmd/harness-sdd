# `/sdd-pr-loop` command + vendored Codex watcher — Functional Spec

## Context

The harness tells its own agents to run `/pr-loop` in three places
(`agents/orchestrator.md:102`, `CLAUDE.md:20`, `docs/WORKFLOW.md:325`) but **ships no such
command**. `/pr-loop` is a *global user skill* installed by the separate
multi-cli-orchestrator (MCO) project at `~/.agents/skills/pr-loop/`. The human is
uninstalling those skills, and a fresh consumer who installs the harness alone never had
them. The moment they are gone, the harness's documented review workflow points at a
command that does not exist, and the vendored watcher's hardcoded
`~/.agents/skills/pr-loop/scripts/wait-for-codex.sh` path is dangling.

This feature vendors the review loop into the harness as a first-class,
installer-generated **`/sdd-pr-loop` command** plus a harness-owned watcher script and a
canonical `pr-fixer` sub-agent role, so a harness install drives the full Codex review
cycle with no external skill on disk. The loop is opt-out via a new `pr_loop:` config
block, because it only functions on a repo that has the Codex GitHub App installed and an
authed `gh`.

The user is the **Orchestrator** (and the targeted parallel-fix worker), which invokes the
loop explicitly after a PR is opened. The human is the beneficiary: their existing review
cycle must feel identical after the MCO skills are removed.

## Business rules

- **The loop is a command, not a skill.** The installer has zero skill-emission
  machinery. The command path reuses `HARNESS_SDD_CMDS`, the neutral `CMDDIR` mirror, and
  the deselection/removal ledger, which already keep all five front-ends byte-identical.
- **`pr_loop.enabled` is the master gate.** When false, no `/sdd-pr-loop` command and no
  `pr-fixer` agent artifact is stamped into any front-end. Default is **true** — the
  harness's own prose already directs agents to run the loop, so `true` preserves today's
  behavior; a repo without the Codex GitHub App sets it false.
- **`pr_loop.auto_merge` defaults true**, preserving exactly today's MCO behavior.
- **Clean break on env vars.** Only `HARNESS_*` names are read. No `MCO_*` fallback, no
  `MCO_*` string anywhere in the harness body.
- **Config carries project policy; env carries per-run overrides.** `enabled`,
  `auto_merge`, `max_rounds`, `blocking_severities` and `merge_strategy` are reviewable
  per-project policy and live in `harness.config.yaml`. Poll cadence, the first-response
  window and dry-run are execution knobs of a single invocation and are env-only, so the
  watcher never has to parse YAML.
- **Cost caps are dropped.** The source runbook's `MCO_TOKEN_BUDGET_USD` terminal
  condition has no equivalent: this harness explicitly does not do token/USD accounting
  (`harness.config.yaml` → telemetry: "cost accounting is OUT of scope"), so an
  unenforceable knob is not carried over. `max_rounds` remains the only round cap.
- **The loop's external dependencies (`gh`, `jq`) are scoped to the loop.** They are
  required only when `pr_loop.enabled` is true and only at loop runtime; `init.sh` gains
  no new gate, so a target without them is unaffected.
- **Codex signals a clean review in three forms** — a 👍 reaction on the trigger comment,
  a review summary banner naming the head commit, or that same banner delivered as an
  issue comment. All three are load-bearing; missing any one stalls a genuinely clean PR
  to the ceiling.
- **Freshness is judged by `created_at`/`submittedAt` versus the trigger comment's
  timestamp, never by `commit_id` alone.** GitHub re-stamps stale unresolved threads'
  `commit_id` to each new head, so a `commit_id`-only test lets old threads masquerade as
  this round's findings.
- **The trigger comment id is derived from the URL `gh pr comment` prints**, never from a
  separate list call — a non-paginated `GET issues/<n>/comments` returns only the first 30
  (oldest) comments, so on a busy PR the lookup returns a stale id or `null`, silently
  disabling the freshness filter.
- **All three comment sources are required.** `gh pr view` alone returns neither Codex's
  inline findings (`pulls/<n>/comments`) nor a clean banner posted past the first 100
  issue comments.
- **Never auto-resolve a human's review thread.** Only threads whose every participant is
  the Codex bot may be resolved; any unresolved non-Codex thread routes to `needs-human`
  and blocks the merge.

## Acceptance criteria (EARS)

> Each is one testable behavior with a stable id. See `docs/SPEC-FORMAT.md`.

### Command generation, gating and removal

- **R1** — The installer shall generate a `sdd-pr-loop` command body into the neutral
  `CMDDIR` on **every** run, regardless of `pr_loop.enabled`, so the pristine-compare
  reference needed by removal always exists.
- **R2** — Where `pr_loop.enabled` is true, the installer shall mirror `sdd-pr-loop.md`
  into every selected front-end's command surface — `.claude/commands/`,
  `.opencode/command/`, `.agents/workflows/`, and `${CODEX_HOME:-$HOME/.codex}/prompts/` —
  each copy byte-identical to the `CMDDIR` source and to each other.
- **R3** — While `pr_loop.enabled` is false, the installer shall stamp no `sdd-pr-loop`
  command and no `pr-fixer` agent artifact into any front-end, and shall exit 0.
- **R4** — When a front-end that previously held `sdd-pr-loop` glue is deselected, the
  installer shall remove that front-end's `sdd-pr-loop` command and `pr-fixer` artifact
  under the same ownership rules the other `/sdd-*` commands already use: by name inside
  harness-owned workspace dirs, byte-pristine-compare inside the user-owned global Codex
  prompts dir and the Antigravity `.agents/` tree.
- **R5** — When `pr_loop.enabled` changes from true to false while a front-end remains
  selected, the installer shall reclaim that front-end's `sdd-pr-loop` command and
  `pr-fixer` artifact under the same ownership rules as R4.
- **R6** — If an `sdd-pr-loop` or `pr-fixer` file inside a user-owned namespace (the global
  Codex prompts dir, `.agents/`) differs byte-for-byte from a freshly generated body, then
  the installer shall leave that file in place and emit a warning naming it.
- **R7** — The installer shall never delete a file it did not generate in the affected
  dirs, and shall prune a `.claude/`, `.opencode/`, or `.agents/` directory only when it is
  left empty.
- **R8** — When `pr_loop.enabled` is flipped false and then true again with no other
  change, the installer shall restore glue byte-identical to the original stamp
  (idempotent round-trip).

### The `pr-fixer` sub-agent

- **R9** — The harness body shall carry exactly one canonical, front-end-neutral
  `agents/pr-fixer.md` role (one comment, one fix, one commit, one return; no push, no
  merge, no thread resolution, no full test suite), and no existing canonical
  `agents/*.md` role file shall be forked or rewritten to carry it.
- **R10** — Where `pr_loop.enabled` is true and `claude` is selected, the installer shall
  emit `.claude/agents/pr-fixer.md` through the existing `emit_agent` path, pointing at
  `.harness/agents/pr-fixer.md` and never duplicating the role body.
- **R11** — Where `pr_loop.enabled` is true and `opencode` is selected, the installer shall
  emit `.opencode/agent/pr-fixer.md` carrying `mode: subagent`, and shall leave the
  generated `opencode.json` body unchanged.
- **R12** — The generated `opencode.json` and the presence/absence of
  `.harness/.opencode.stamp` shall be independent of `pr_loop.*`: two targets that differ
  only in `pr_loop.enabled` shall have byte-identical `opencode.json` files and the same
  stamp presence.
- **R13** — Where `pr_loop.enabled` is true and `antigravity` is selected, the installer
  shall emit `.agents/agents/pr-fixer.md` through the existing persona emitter, pointing at
  `.harness/agents/pr-fixer.md`.
- **R14** — The installer shall create no `pr-fixer` artifact for the `codex` or `gemini`
  front-ends, shall add no row to the model-routing role map (`MODEL_ROLES`,
  `ag_personas`), and the command body shall state that a front-end with no `pr-fixer`
  sub-agent applies fixes in-session under the same one-fix-one-commit discipline.

### Configuration

- **R15** — A fresh install shall seed a top-level `pr_loop:` block carrying
  `enabled: true`, `auto_merge: true`, `max_rounds: 4`,
  `blocking_severities: "P0,P1"`, and `merge_strategy: "merge"`.
- **R16** — When a preserved `harness.config.yaml` lacks a `pr_loop:` block, the config
  migration shall append the block without altering any existing value, key order or
  comment; a second run shall write nothing (idempotent).
- **R17** — The `pr_loop:` block a migration appends shall be byte-identical to the block a
  fresh install seeds.
- **R18** — If the `pr_loop:` block or any of its keys is absent at read time, then the
  installer and the command shall behave as if `enabled: true`, `auto_merge: true`,
  `max_rounds: 4`, `blocking_severities: "P0,P1"`, `merge_strategy: "merge"`.
- **R19** — The installer and the generated command shall read a `pr_loop` key only from
  the top-level `pr_loop:` section, so a same-named key nested under another section never
  changes behavior.
- **R20** — The harness body shall contain no `MCO_`, `.mco-cache`, `~/.agents/skills`,
  `route-task`, or `start-feature` token; the loop shall read only `HARNESS_*` env names,
  with precedence env override → config value → built-in default.

### The vendored watcher

- **R21** — The harness shall ship `tools/wait-for-codex.sh` as a POSIX-`sh` script
  (`#!/bin/sh`, no bashisms), installed by the existing `copy tools` step and made
  executable by the installer, and every reference to it in the harness body shall be a
  harness-relative path.
- **R22** — When invoked as `wait-for-codex.sh <pr-number> <trigger-comment-id>
  <round-dir>`, the watcher shall poll in wait mode and exit `0` for fresh findings on
  head, `3` for a clean review, `2` for ceiling timeout, and `4` for a usage/precondition
  error — the source contract's four codes, unchanged.
- **R23** — While polling, the watcher shall write `pr.json`, `review-comments.json`,
  `issue-comments.json`, and `reactions.json` into the round dir on every poll, and shall
  persist the resolved trigger timestamp to `trigger-ts.txt` once at startup.
- **R24** — If a trigger comment id is supplied but its timestamp cannot be resolved after
  retries, then the watcher shall exit `4` with a diagnostic rather than proceed with the
  freshness filter silently disabled.
- **R25** — The watcher shall count an inline Codex comment as this round's finding only
  when its `commit_id` equals `headRefOid` **and** its `created_at` is at or after the
  trigger timestamp.
- **R26** — The watcher shall exit `3` for each of the three clean signals independently:
  a fresh Codex review whose body contains `Reviewed commit` and the 7-char head prefix; a
  fresh Codex **issue comment** containing the same banner; a `+1` reaction by the Codex
  bot on the trigger comment.
- **R27** — The watcher shall identify the Codex bot by **prefix** match on
  `chatgpt-codex-connector`, so both the GraphQL login and the REST `…[bot]` login match.
- **R28** — If the ceiling is reached with no resolution, then the watcher shall exit `2`
  and shall never report a timeout as clean.
- **R29** — When invoked as `wait-for-codex.sh evaluate <round-dir>`, the watcher shall
  evaluate the already-written round files **offline** (invoking no `gh` and no network)
  and exit `0` findings / `3` clean / `1` pending, applying exactly the R25–R27 rules.
- **R30** — When invoked as `wait-for-codex.sh preflight <pr-number>`, the watcher shall
  verify that `gh` is on `PATH`, that `gh auth status` succeeds, that `jq` is on `PATH`,
  that the repo slug resolves, and that the PR exists and is open; it shall exit `0` when
  all hold.
- **R31** — If any preflight check fails, then the watcher shall exit `5` immediately with
  a single-line diagnostic naming the failed check and its remedy, and shall post nothing
  to GitHub.
- **R32** — If, in wait mode, no Codex activity of any kind (any reaction on the trigger
  comment, any bot issue comment, any bot review) is observed within
  `HARNESS_FIRST_RESPONSE` seconds (default `180`), then the watcher shall exit `5` with a
  diagnostic naming the Codex GitHub App as the likely cause, instead of polling to the
  ceiling.
- **R33** — While `HARNESS_FIRST_RESPONSE` is `0`, the watcher shall disable the
  first-response probe entirely and behave exactly as R22 describes.
- **R34** — The watcher shall honor `HARNESS_POLL_INTERVAL` (default `60`) and
  `HARNESS_POLL_CEILING` (default `900`) and shall read no `MCO_*` variable.
- **R35** — The loop's round cache shall live at `<HARNESS_DIR>/.pr-loop/<pr>/round-<n>/`,
  and `.pr-loop/` shall be ignored by both the installer-seeded `.harness/.gitignore` and
  the harness source repo's own `.gitignore`.

### The generated command body (`/sdd-pr-loop`)

- **R36** — The generated command body shall instruct the agent to run the watcher's
  `preflight` mode **before** posting any `@codex review` comment, and to STOP and report
  the diagnostic on a non-zero preflight.
- **R37** — The generated command body shall derive the trigger comment id from the URL
  `gh pr comment` prints (`…#issuecomment-<id>`) and shall explicitly forbid deriving it
  from a separate comment-list call, stating the pagination reason.
- **R38** — The generated command body shall instruct the agent to launch the watcher in
  the background at its harness-relative path and to branch on its exit code (`0`/`2`/`3`/
  `4`/`5`), and shall forbid hand-polling.
- **R39** — The generated command body shall classify severity from the freshness-filtered
  inline findings plus review bodies plus issue comments, matching `P0|P1|P2|nit`
  case-insensitively anywhere in the body (so the shields.io badge form matches), first
  match wins, defaulting to `P2`, then filter to the configured blocking severities.
- **R40** — The generated command body shall detect a stall (a blocking comment id present
  in both this round and the previous round) and escalate to round-3 behavior immediately,
  regardless of the current round number.
- **R41** — The generated command body shall branch by round: every round below
  `max_rounds - 1` spawns one `pr-fixer` per blocking comment then pushes; the
  `max_rounds - 1` round builds one combined fix prompt and escalates to a different
  worker (or, where no router exists, one combined in-session pass); reaching
  `max_rounds` labels the PR `needs-human`, posts the handover summary, and returns
  failure. At the default `max_rounds: 4` this is the source runbook's 1–2 / 3 / 4+
  behavior exactly; a `max_rounds` below `3` simply has no per-comment fixer rounds.
- **R42** — If any unresolved review thread has a non-Codex participant, then the command
  shall route to the `needs-human` terminal state, resolve no thread, and not merge.
- **R43** — Where `pr_loop.auto_merge` is true and every gate is green and every remaining
  unresolved thread is Codex-owned, the command shall resolve those Codex threads and merge
  with the configured `merge_strategy`, deleting the remote branch in the same call.
- **R44** — While `pr_loop.auto_merge` is false, the command shall stop after posting the
  all-gates-green summary and hand back to the human without merging.
- **R45** — The command shall perform local branch cleanup only after the merge command
  itself succeeded, never merely because thread eligibility was satisfied.
- **R46** — The command shall write a handover summary (rounds run, worker totals,
  round-by-round breakdown, blocking comments resolved, cache path) into the cache and
  post it on both terminal states.
- **R47** — Where `HARNESS_DRY_RUN` is `1`, the command shall skip the real `gh pr comment`
  post and synthesize stub review data instead.

### Documentation, prose and wiring

- **R48** — Every `/pr-loop` reference in the harness body (`agents/orchestrator.md`,
  `CLAUDE.md`, `docs/WORKFLOW.md`) shall name `/sdd-pr-loop` and shall be phrased by
  **availability** ("if `/sdd-pr-loop` is installed…"), with an explicit alternative when
  it is not; no per-install prose templating mechanism shall be introduced.
- **R49** — The harness source repo shall carry source-layout copies of the new glue
  (`.claude/commands/sdd-pr-loop.md`, `.claude/agents/pr-fixer.md`) whose paths resolve
  from the repository root, matching the existing source-layout `.claude/` dialect.
- **R50** — `README.md`, `docs/INSTALL.md`, `docs/WORKFLOW.md`, and `docs/HARNESS.md`
  shall list `/sdd-pr-loop`, state the Codex-GitHub-App + authed-`gh` + `jq` precondition,
  and document the `pr_loop:` config block and the `HARNESS_*` env knobs.
- **R51** — `tests/test_pr_loop.sh` shall exist and shall be wired into
  `verification.test_command` in `harness.config.yaml`; it shall sandbox `CODEX_HOME` for
  every installer-invoking run, shall assert no exact `VERSION` string, and shall diff no
  DO-NOT-TOUCH file against `main`.
- **R52** — `tests/test_install.sh` shall assert that `/sdd-pr-loop` is generated into each
  selected front-end and removed on deselection, alongside the existing `/sdd-*` command
  assertions.
- **R53** — `init.sh` shall gain no new hard dependency: a target with neither `gh` nor
  `jq` installed shall still pass `init.sh` with exit 0.
- **R54** — `VERSION` shall receive a MINOR bump and `CHANGELOG.md` a matching entry,
  because the installed body gains a new capability.

## Out of scope

- Surfacing `pr_loop.enabled` in the installer TUI — that is E20-F01. This feature
  introduces and honors the key; hand-editing it is acceptable until E20 lands.
- Vendoring `route-task` or `start-feature`. `/sdd-next` and `/sdd-new` already cover them.
- Any change to `store/tasks.schema.json`, and any fork of an existing canonical
  `agents/*.md` role.
- Per-role model routing for `pr-fixer` beyond the inherited `models.default` fallback: no
  `.gemini/agents/pr-fixer.md` and no `.codex/agents/pr-fixer.toml` are created.
- Token/USD budget caps (`MCO_TOKEN_BUDGET_USD`) — deliberately not carried over.
- Squash-message generation via a `@codex summarize` round is carried over as command
  prose only; it gets no dedicated automated test beyond the body assertion.

## Open questions

Resolved during specification — recorded here so the decisions are auditable:

1. **Conditional prose (confirmed, not overruled).** The harness body is copied verbatim
   (`copy agents`, `copy docs`), and `agents/orchestrator.md` is a canonical role file that
   must stay byte-identical between source and every install. Introducing marker-block
   templating for one paragraph would add install, removal and pristine-compare surface
   used by nothing else, and would make the installed role file differ from its source —
   breaking the "no fork" invariant. Resolution: keep the prose unconditional and phrase it
   by availability (R48); the absent command is the signal.
2. **Watcher location + `pr-fixer` emission.** Watcher goes to `tools/wait-for-codex.sh`
   (already covered by `copy tools`, already the home of every executable helper, already
   next to the `chmod +x` list; a one-file subdir buys nothing). The four vendored
   `pr-fixer` bodies are ~95% identical prose, so they collapse into **one canonical
   `agents/pr-fixer.md`** plus the harness's existing per-front-end shim emitters (R9–R14).
   `codex/pr-fixer.toml` is deliberately **not** carried over: `.codex/agents/*.toml` exists
   today only as a conditional model-routing artifact, and creating it unconditionally would
   break E17-F01's "an unconfigured target grows no new directory" guarantee. OpenCode gets a
   file-based `.opencode/agent/pr-fixer.md` (the vendored source's own shape) rather than an
   `opencode.json` entry, which keeps the E17-F01 stamp machinery untouched (R12).
3. **Config vs env.** `enabled`, `auto_merge`, `max_rounds`, `blocking_severities`,
   `merge_strategy` are project policy → config. `HARNESS_POLL_INTERVAL`,
   `HARNESS_POLL_CEILING`, `HARNESS_FIRST_RESPONSE`, `HARNESS_DRY_RUN` are single-invocation
   execution knobs → env only, so the POSIX-sh watcher never parses YAML. The three policy
   knobs also accept a matching `HARNESS_*` env override for a one-off run (R20).
4. **Decomposition (declined, seam preserved).** F01 stays one feature; the task list is
   ordered so the natural seams — (a) config + watcher, (b) command body + mirror + gate,
   (c) `pr-fixer` role + per-front-end shims, (d) de-MCO prose + docs — are contiguous
   blocks, so a later split would be a clean cut rather than a rewrite.

Left for the human at the approval gate:

- **`pr_loop.enabled` defaults to `true`.** This preserves today's behavior and matches the
  epic's "harness self-sufficiency" goal, at the cost that every fresh install of the
  harness into a repo *without* the Codex GitHub App grows a command that will fail its
  preflight. The mitigation is R31's fail-fast diagnostic plus the documented off switch.
  Say so now if you prefer `false`-by-default.
