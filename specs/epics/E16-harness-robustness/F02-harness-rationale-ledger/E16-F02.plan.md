# Harness rationale and deletion ledger — Technical Plan

> This is a documentation-only installed-body feature. Every change cites the
> requirement ids it serves; no runtime or role behavior changes are permitted.

## Stack & dependencies
- Portable CommonMark/GitHub-flavored Markdown and POSIX shell test assertions.
- Existing `harness-install.sh` whole-directory `copy docs` behavior.
- New dependencies: none.
- External source links are references only; permanent tests do not require
  network access.

## Document model (serves: R1–R8, R12–R13)
Create one `docs/RATIONALE.md` with this fixed human-first sequence:

1. **Why a harness** — cold-reader definition, audience, prompt-only failure
   boundary, and the shifting-bottleneck thesis.
2. **Two layers, one decision rule** — operational definitions, mixed-mechanism
   primary-purpose rule, evidence standard, and retain-by-default posture.
3. **Deletion ledger** — one Markdown table with the exact columns
   `Mechanism | Layer | Why it exists now | Evidence to reconsider or remove |
   Repository pointers`.
4. **How to use the ledger** — retest on a materially different model/runtime or
   observed failure change; compare a representative task set before/after;
   predeclare quality/safety/time/cost thresholds; remove only after Reviewer's
   normal evidence and human approval.
5. **Evidence and limits** — descriptive links and bounded paraphrases.

The table contains these exact baseline rows; a row may name coupled
submechanisms but may not merge two rows below:

| # | Mechanism/group | Layer | Minimum removal evidence |
|---|---|---|---|
| C1 | `init.sh` structural preflight | compensation | Repeated representative runs detect no unique pre-work failures after equivalent checks are moved earlier or become guaranteed by the runtime. |
| C2 | Curated clean contexts, `context_reset_threshold`, file handoffs | compensation | Long-task evals across a materially newer model/runtime meet the same completion and coherence thresholds without resets; durable file state remains. |
| C3 | Role-scoped `DO NOT TOUCH` plus minimal-tool instructions | compensation | Scope-violation and tool-misuse rates remain below a predeclared threshold when the instructions are removed, while authorization boundaries remain enforceable. |
| C4 | Read-only Scout discovery | compensation | Cold-start repository tasks achieve equivalent context recall and path accuracy without a separate discovery pass. |
| C5 | Doc-critic advisory checkpoint | compensation | Controlled specs without the pass show no material increase in completeness, contradiction, ambiguity, scope, or YAGNI defects reaching Builder/Reviewer. |
| C6 | Reviewer cross-file consistency audit | compensation | Independent review data shows models reliably detect repository-contract contradictions through simpler deterministic checks or another retained control. |
| C7 | Multi-round Builder↔Reviewer correction | compensation | First-pass approval rates and escaped-defect rates meet predeclared thresholds over representative changes; independent verification remains. |
| C8 | Model interpretation of prose `next()` routing | compensation | E16-F03's deterministic selector is reviewed, shipped, parity-tested, and consumed; the human-readable gate policy remains as specification. |
| D1 | EARS specs and R-id traceability | durable | Remove only if the team no longer needs explicit intent-to-evidence mapping or a replacement preserves it. |
| D2 | File-backed TaskStore, specs, progress, and history | durable | Remove only if a replacement preserves durable, reviewable, resumable, tool-neutral state and audit history. |
| D3 | Role separation and independent review | durable | Remove only if accountability and independent challenge are no longer required or another control supplies equivalent independence. |
| D4 | Human approval and autonomous gates | durable | Remove only under an explicit governance decision that changes who may authorize work, with equivalent authorization controls. |
| D5 | Deterministic tests, lint/type checks, and behavioral evidence | durable | Remove only if the project no longer needs objective correctness evidence or a replacement proves the same properties. |
| D6 | Board write locking and isolated Git worktrees | durable | Remove only when concurrent mutation/isolation risks cannot occur or another mechanism proves atomicity and branch isolation. |
| D7 | Dependency diagnostics and deterministic selection | durable | Remove only if dependency/routing ambiguity cannot occur or a simpler deterministic mechanism preserves named, testable outcomes. |
| D8 | Architecture/ADR alignment and epic drift checks | durable | Remove only if durable design decisions and rolling-plan validity are no longer governed or a replacement preserves both. |
| D9 | Telemetry | durable | Remove only if maintainers explicitly stop using phase/round/gate evidence or another observable record preserves it. |
| D10 | Ownership and scoped selection | durable | Remove only if shared work allocation is no longer needed or another source of truth preserves fail-closed scoping. |
| D11 | Umbrella contracts, slice rollups, integration gates | durable | Remove only if cross-repo work is unsupported or another mechanism preserves one seam, per-slice evidence, merge state, and integration proof. |
| D12 | Store/execution/mirror seams with local truth | durable | Remove only if portability/replaceability is no longer a goal or a replacement preserves authoritative-state direction and safe failure posture. |
| D13 | Repository portability, config layering, versioned install | durable | Remove only if the harness ceases to be shared/upgraded across CLIs and repos or a replacement preserves ownership and compatibility boundaries. |

The source section requires these primary publisher pages and cautious
attribution (serves: R8):

- Anthropic, [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
  and [Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps):
  evidence about the named Claude/model versions, context/session handoffs,
  evaluator separation, and methodical component removal.
- OpenAI, [Harness engineering: leveraging Codex in an agent-first
  world](https://openai.com/index/harness-engineering/): an account of one
  agent-first repository using repository knowledge, constraints, structural
  checks, and review/test loops.
- LangChain, [Improving Deep Agents with harness
  engineering](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering):
  a reported Terminal Bench harness experiment emphasizing context delivery,
  verification, and tracing.
- Thoughtworks, [Feedback sensors for coding
  agents](https://www.thoughtworks.com/en-us/radar/techniques/feedback-sensors-for-coding-agents):
  practitioner guidance on deterministic feedback and reviewer-agent loops.
- METR, [Measuring the Impact of Early-2025 AI on Experienced Open-Source
  Developer Productivity](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/):
  a scoped early-2025 RCT snapshot, not evidence that AI universally slows
  developers or that one harness design is universally correct.

No exact outcome number, universal-consensus claim, or long quotation is required.

## DO NOT TOUCH
- `harness-install.sh` — it already copies the entire `docs/` directory; no
  explicit enumeration or production change is necessary.
- `agents/*.md` — no role responsibility, prompt, routing, gate, or review
  contract changes.
- `init.sh`, `tools/**`, `store/**`, `state/**`, `specs/adr/**`, and
  `store/tasks.schema.json` — this feature adds no runtime behavior, data shape,
  selector, or ADR delta.
- Existing feature specs outside the assigned E16-F02 folder.
- `progress/history.md`, telemetry logs, live TaskStore status, branches,
  commits, PRs, tags, or releases — the Orchestrator owns them.
- A second rationale/ledger document, docs-site generator, YAML/JSON ledger,
  parser, scheduled benchmark, or deletion automation.

## Implementation sequence and verification
Use documentation-first TDD: add focused failing assertions for the source
document and exact inventory, write the minimum document/navigation changes,
then add fresh-install coverage and version/config wiring. Permanent tests assert
semantics and stable mechanism labels, not exact paragraphs, current top-level
version, publication dates, or network availability.

The Reviewer must also inspect the Builder-owned final diff to prove R13: only
the files in the Files-to-change table and the four feature specs may differ.
Orchestrator-owned lifecycle metadata (`state/tasks.json`,
`progress/history.md`, telemetry, and role progress reports) is excluded from
that Builder-scope comparison but must contain no schema or status-semantics
change. Offline tests cannot establish absence of role/runtime changes by
comparing against an ever-moving branch, so this remains an explicit review gate
in addition to static checks.

## Alternatives considered
- **Selected: one rationale with an embedded ledger.** The classification rule
  and inventory evolve together and remain understandable from one cold entry.
- **Rejected: `RATIONALE.md` plus `DELETION-LEDGER.md`.** It adds navigation and
  consistency cost without a separate consumer or lifecycle.
- **Rejected: YAML frontmatter or a separate machine-readable ledger.** No tool
  consumes it; stabilizing a schema would be scope beyond explanatory docs.
- **Rejected: fold all content into `docs/HARNESS.md`.** That file is a compact
  conceptual introduction. Expanding it into an operational inventory would
  weaken both reading paths and duplicate its existing role.
