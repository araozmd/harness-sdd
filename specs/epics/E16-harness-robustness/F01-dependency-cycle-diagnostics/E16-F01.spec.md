# Dependency-cycle detection and no-actionable-work diagnostics — Functional Spec

## Context
A malformed `depends_on` graph can make features or umbrella slices permanently
unselectable while the Orchestrator reports only that no work is actionable. The
same opaque result occurs when every unfinished candidate is behind an epic gate,
an unmet dependency, a human gate, or `/sdd-next --mine` ownership filtering.
This feature gives operators deterministic, named explanations without changing
the TaskStore or turning planning-state problems into a failing environment gate.

## Business rules
- Dependency diagnostics operate on two disjoint graphs: all feature ids form the
  feature graph and all slice ids form the slice graph. A dependency is an edge
  only when it resolves to a node in the same graph.
- A missing or cross-kind dependency remains an unmet dependency for selection
  diagnostics; it is not invented as a graph node and cannot participate in a
  reported cycle.
- Cycle paths and no-selection reasons use canonical ids, deterministic numeric
  epic/feature ordering, lexical repository-suffix ordering for slices, and stable
  reason codes so repeated runs over equivalent boards are byte-identical.
- `init.sh` warnings and no-selection explanations are informational. They never
  mutate state, introduce a new status, or make an otherwise schema-valid board
  fail initialization.
- Selection policy does not change. Diagnostics explain the existing epic,
  dependency, human, status, slice, and owner gates after selection produces no
  result; they do not relax a gate or choose a fallback task.

## Architecture alignment
`specs/architecture.md` is absent, so there is no complete planning-tier

- **ADR-0001 — next() selection moves from prose routing to a deterministic

## Acceptance criteria (EARS)
> Each requirement is one observable, testable behavior.

- **R1** — When the feature `depends_on` graph contains a cycle, the diagnostic
  helper shall report a closed full witness path whose first and last ids are
  identical, including every edge in the witness, and shall use the stable reason
  code `dependency-cycle` with graph kind `feature`.
- **R2** — When the slice `depends_on` graph contains a cycle, the diagnostic
  helper shall report a closed full witness path using canonical slice ids and
  shall use reason code `dependency-cycle` with graph kind `slice`.
- **R3** — If a feature or slice depends on itself, then the diagnostic helper
  shall report the two-id closed path `<id> -> <id>` for that graph kind.
- **R4** — When equivalent dependency graphs are represented with different JSON
  array or `depends_on` ordering, the diagnostic helper shall emit byte-identical
  cycle records ordered by graph kind, numeric epic/feature id, lexical slice
  repository suffix, and canonical closed path; a missing or cross-kind
  dependency shall be excluded from cycle traversal and retained as an unmet
  dependency for selection diagnostics.
- **R5** — When `init.sh` validates a board containing one or more feature or
  slice cycles, the environment gate shall print one warning per deterministic
  cycle record with its full path and shall still exit zero if every existing
  structural and project-specific check succeeds.
- **R6** — Where the local TaskStore contains no `depends_on` fields, only empty
  dependency arrays, no epics, or no features, the diagnostic helper and
  `init.sh` cycle check shall emit no cycle warning, shall raise no exception,
  and shall preserve the existing successful gate behavior.
- **R7** — If the standalone diagnostic helper cannot read or parse its requested
  TaskStore, then it shall exit non-zero with an actionable error naming the
  requested path; when called from `init.sh`, this case shall remain subordinate
  to the existing structural validator and shall not replace its fail-stop
  contract.
- **R8** — When normal or `--mine` selection returns no task, the Orchestrator
  shall emit deterministic per-candidate diagnostic records in the form
  `blocked <id> [<reason-code>]: <human text>`, followed by one no-actionable-work
  summary exactly `no actionable work: selection blocked; see reasons above`,
  without changing state or converting the informational result into a hard
  command failure.
- **R9** — While an unfinished feature belongs to a `draft` epic, a no-selection
  diagnostic shall classify it as `gated-epic` and shall name the parent epic id
  and its `draft` status.
- **R10** — While an unfinished feature or slice has unresolved, non-`done`, or
  for a slice non-merged upstream dependencies, a no-selection diagnostic shall
  classify it as `unmet-dependency` and shall name every blocking dependency in
  canonical order, distinguishing `missing`, current status, and
  `done-but-unmerged`; if it participates in a cycle, the diagnostic shall also
  emit `dependency-cycle` with the canonical full path.
- **R11** — While a feature is parked at `spec-ready` without an autonomous
  bypass, or is `pending` with `sdd: false` and `autonomous: false`, a
  no-selection diagnostic shall classify it as `human-gate` and shall name the
  parked status or gated quick-fix condition.
- **R12** — Where `/sdd-next --mine` is active, the no-selection diagnostic shall
  classify an otherwise actionable non-matching or unowned candidate as
  `owner-excluded` and name its effective owner, and shall classify a failed
  identity resolution under subject `--mine` as `owner-unresolved`, rendering an
  absent/empty value as `workflow.identity=<empty>` and a failed dynamic lookup
  as `workflow.identity=<@me|self> lookup failed`; bare `/sdd-next` shall emit
  neither ownership reason.
- **R13** — When selection has no unfinished candidate because the board is empty
  or every feature is `done`, the Orchestrator shall emit the stable reason code
  `no-candidates` with human text distinguishing `board has no features` from
  `all features are done`, and shall not fabricate a blocked candidate.
- **R14** — The installed harness shall ship the executable stdlib-only
  diagnostic helper and the same init/Orchestrator vocabulary as the source
  harness; its permanent tests shall exercise at least 2,000 acyclic nodes within
  five seconds, schema/status invariance, graceful empty/no-dependency behavior,
  and the complete R1–R13 traceability surface without adding a package
  dependency.

## Out of scope
- Implementing `tools/next-task.mjs`, changing which task wins selection, or
  replacing the Orchestrator's prose routing table; those belong to E16-F03.
- Rejecting cycles through JSON Schema, adding referential-integrity constraints,
  adding statuses or TaskStore fields, or automatically repairing dependencies.
- Enumerating every simple cycle inside a densely connected strongly connected
  component. One deterministic full witness per cyclic component is sufficient.
- Cross-kind feature-to-slice edges, dependencies outside the current TaskStore,
  graph visualization, an interactive repair command, or telemetry schema changes.

## Open questions
None blocking. The inbox choices are resolved as follows:
- The helper is a small Python 3 standard-library module/CLI because the local
  backend already requires Python 3 and both source and installed `init.sh` can
  call it directly. It introduces no third-party dependency.
- The helper emits one deterministic closed witness for each cyclic strongly
  connected component rather than every possible simple cycle. It anchors at the
  component's lowest canonical node, chooses that node's lowest in-component
  neighbor, and uses canonical breadth-first search back to the anchor, avoiding
  exponential output while pinning one complete repairable path.
- The stable reason codes are `dependency-cycle`, `gated-epic`,
  `unmet-dependency`, `human-gate`, `owner-excluded`, `owner-unresolved`, and
  `no-candidates`. E16-F03 must preserve these spellings and associated human
  meanings.
