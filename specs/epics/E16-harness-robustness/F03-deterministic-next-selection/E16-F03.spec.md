# Deterministic next-task selection — Functional Spec

## Context
The Orchestrator currently re-interprets the most consequential TaskStore routing
logic from prose on every run. The interaction among epic state, feature status,
dependencies, human approval, ownership, and umbrella slices is large enough that
a small interpretation difference can silently select the wrong work. Operators
and maintainers need one deterministic, read-only selector whose behavior is
fixture-testable while the existing prose remains the human-auditable policy.

## Business rules
- Selection changes no gate and writes no file. The TaskStore and configuration
  remain the inputs; the Orchestrator remains the only owner of state transitions.
- Feature selection and slice selection are separate phases. A feature must first
  pass the existing epic, dependency, status, approval, and optional owner gates;
  only an already-active sliced feature in configured umbrella mode proceeds to
  slice selection.
- Canonical ordering is numeric by epic and feature, feature before slice, then
  lexical by slice repository suffix, with the complete literal id as a final
  tie-breaker for numerically equivalent ids.
- E16-F01's blocked-reason codes, human text, ordering, and two no-result
  activation paths are compatibility contracts, not wording suggestions.
- Node.js is an optional execution upgrade. Its absence never makes the harness
  unusable because the Orchestrator retains the prose selection fallback.

## Architecture alignment
`specs/architecture.md` is absent, so there is no complete planning-tier
architecture document to consume. The repository does contain the accepted
selection decision below, which this feature directly touches.

- **ADR-0001 — next() selection moves from prose routing to a deterministic
  tool:** this feature implements the zero-dependency, read-only selector, keeps
  the prose as its acceptance oracle, and permits no routing-policy change at
  introduction.

## Acceptance criteria (EARS)

- **R1** — When `tools/next-task.mjs` is invoked with no arguments or with
  `--json`, the selector shall emit exactly one newline-terminated JSON object on
  stdout using schema version 1; it shall accept optional `--mine`,
  `--feature <id>`, `--tasks <path>`, and `--config <path>`, shall reject unknown,
  duplicate, missing-value, positional, or mutually exclusive `--mine` and
  `--feature` arguments, and shall treat `--json` as an explicit alias for the
  default JSON format; the `/sdd-next E##-F##` command contract shall translate
  its positional feature id to selector arguments `--feature E##-F##`.
- **R2** — Where `--tasks` or `--config` is absent, the selector shall resolve
  `state/tasks.json` and `harness.config.yaml` relative to its own harness
  directory in both source and installed `.harness/` layouts, independent of the
  caller's current working directory.
- **R3** — When evaluating a feature, the selector shall preserve the documented
  route table exactly: skip `done`; block every feature under a `draft` epic;
  require every feature dependency to exist and have stored status `done`;
  route `pending+sdd:true` to Architect, autonomous
  `pending+sdd:false` to Builder, approved/autonomous `spec-ready` to Builder,
  `in-progress` to Builder, and `in-review` to Reviewer; non-autonomous
  `pending+sdd:false` and approval-required non-autonomous `spec-ready` shall
  remain parked.
- **R4** — When more than one feature passes the ordinary gates, the selector
  shall choose the lowest canonical id independent of epic, feature, or
  dependency-array input order; numeric components shall sort numerically, and
  distinct numerically equivalent ids shall use their complete literal ids as a
  deterministic final tie-breaker.
- **R5** — When a feature dependency is missing, cross-kind, cyclic, or not
  `done`, the selector shall not select that feature and shall preserve
  E16-F01's exact `dependency-cycle` and `unmet-dependency` blocker semantics,
  including canonical complete blocker lists and closed cycle witnesses.
- **R6** — Where `--mine` is active, the selector shall resolve
  `workflow.identity` as empty/unresolved, literal, or dynamic `@me`/`self` via
  the authenticated `gh` login; it shall apply ownership only after all ordinary
  gates, use feature owner before epic owner, fail closed without widening, and
  emit E16-F01's exact `owner-excluded` or `owner-unresolved` records; bare and
  `--feature` selection shall ignore ownership and shall never claim work.
- **R7** — When board-wide or scoped feature selection produces no result while
  unfinished candidates exist, the selector shall return every applicable
  E16-F01 blocked record in exact subject/reason order; when targeted selection
  produces no result, it shall return records only for the requested feature and
  shall not fall through to or diagnose other board candidates. Every mode shall
  use the
  verbatim codes and human templates `dependency-cycle`, `gated-epic`,
  `unmet-dependency`, `human-gate`, `owner-excluded`, and
  `owner-unresolved`, followed by the exact summary
  `no actionable work: selection blocked; see reasons above`, with a successful
  informational exit.
- **R8** — When the board has no features or all features are `done`, the
  selector shall emit no fabricated blocked subject and shall return exactly the
  corresponding E16-F01 `no-candidates` summary:
  `no actionable work [no-candidates]: board has no features` or
  `no actionable work [no-candidates]: all features are done`, before attempting
  mine-mode identity resolution; when a targeted feature exists and is already
  `done`, the selector shall instead return `outcome:"complete"`, reason code
  `target-complete`, and summary `target <id> is already done`, regardless of
  other board candidates.
- **R9** — Where `umbrella.manifest` is empty or resolves to no file, the
  selector shall preserve single-repo feature routing even when a feature carries
  `slices`; where the configured manifest exists, the selector shall parse the
  repository keys under `repos:`, resolve the path relative to the harness
  directory, and shall refuse a selected slice whose `repo` has no manifest
  entry with an actionable error naming that repository.
- **R10** — While a selected feature is `in-progress` and active umbrella mode
  applies, the selector shall choose slice work deterministically: first surface
  the lowest canonical `failed` slice as a halted result; otherwise prefer the
  lowest canonical `done` but unmerged slice for merge observation; otherwise
  select the lowest canonical `pending`, `spec-ready`, `in-progress`, or
  `in-review` slice whose every exact same-kind dependency is `done` and
  `merged`; and when every slice is `done` and merged, select the parent feature
  for its existing integration/rollup step.
- **R11** — When top-level selection succeeds for an active sliced parent but no
  slice is selectable while unfinished slices remain, the selector shall emit
  E16-F01 diagnostics only for that parent's unfinished slices, distinguishing
  missing, non-done, failed, and `done-but-unmerged` blockers, and shall not emit
  records for other features or slices or retry whole-board selection.
- **R12** — The schema-version-1 result shall have fixed top-level fields
  `schema_version`, `mode`, `outcome`, `selected`, `reason`, `blocked`, and
  `summary`; a selected record shall identify feature id, optional slice id,
  selected kind, stored status, and one route from `architect`, `builder`,
  `reviewer`, `slice-loop`, `slice-review`, `observe-merge`, or `integration`;
  equivalent inputs shall produce byte-identical compact JSON.
- **R13** — If CLI arguments, TaskStore JSON/shape, configuration scalar syntax,
  configured manifest syntax, duplicate exact ids, ids inconsistent with their
  containing epic/feature, or required record fields are invalid, then the
  selector shall emit a schema-version-1 `outcome:"error"` JSON object on stdout,
  an actionable diagnostic naming the bad input on stderr, set a non-zero exit
  code, and perform no write; a failed dynamic identity lookup is instead the
  successful informational `owner-unresolved` result defined by R6.
- **R14** — If Node.js is unavailable or selector execution fails, then the
  Orchestrator shall state the fallback and execute the preserved prose routing
  contract; when Node.js is available and the selector succeeds, the
  Orchestrator shall trust the returned route and shall not re-derive a different
  selection, while the prose table remains explicitly marked as the behavioral
  oracle; permanent verification shall statically assert this Markdown contract,
  and the Reviewer shall manually check absent-Node and malformed-output fallback
  decisions because the Orchestrator is not an executable adapter.
- **R15** — The installed harness shall include executable
  `tools/next-task.mjs`, the updated Orchestrator/store/workflow contract, and
  permanent selector tests; the feature shall carry the required compatible
  MINOR `VERSION` and `CHANGELOG.md` entry, and installation tests shall compare
  the source and installed selector without freezing future versions.
- **R16** — The permanent suite shall use a table-driven prose-contract oracle
  independent of the selector implementation to compare all documented feature
  and slice routes, blocked records, targeted and owner modes, manifest
  present/absent behavior, malformed inputs, read-only snapshots, and reordered
  equivalents, and shall select from at least 2,000 acyclic features within five
  seconds on Node.js 18 or newer.
- **R17** — The feature shall make no change to
  `store/tasks.schema.json`, status enums, TaskStore records, dependency meaning,
  human-gate policy, owner precedence, umbrella merge/rollup policy, E16-F01
  reason vocabulary, or the Python cycle helper's behavior.

## Out of scope
- Writing status, owner, slice, merge, history, telemetry, or board data from the
  selector.
- Replacing JSON Schema validation, changing the TaskStore schema, repairing bad
  dependencies, or adding claim-on-select behavior.
- Making Node.js a requirement of `init.sh`, adding npm metadata or packages, or
  invoking network services other than the existing `gh api user` identity lookup.
- Polling PRs, running Builders/Reviewers, executing integration checks, or
  applying the selected route; those remain Orchestrator responsibilities.

## Open questions
None blocking. The CLI and result contract are pinned by R1 and R12. `init.sh`
will not smoke-run the selector: doing so would turn optional Node execution into
an environment gate and would produce selection output during an unrelated
structural check.
