# Intent — Jira sync via REST API + Personal Access Token (no MCP)

## Problem / who
Teams on Jira want the harness's `tasks.json` reflected as Jira issues for visibility
and (with E10 ownership) assignment sync. The integration must work in
**MCP-restricted** enterprises, so it uses the **Jira REST API authenticated with a
Personal Access Token** — the standard IT-approved scripting path — and never an MCP
server.

## Success outcome
Running the sync projects the current `tasks.json` onto a configured Jira project as
issues, idempotently, authenticated by a PAT read from a gitignored/personal location,
with no MCP dependency.

## Success outcome — evidence
- A sync command/hook writes harness state to Jira via REST + PAT, no MCP.
- The PAT is read from an env var or gitignored file — never committed, never written
  into `tasks.json` or the mirror config.
- Re-running reconciles (maps feature id → Jira issue key) without creating
  duplicates.
- Inert when no Jira project is configured (matches today).

## Scope / boundaries
**In scope**
- Outbound projection of `tasks.json` → Jira issues via REST + PAT.
- Idempotent reconcile (feature id ↔ issue key mapping).
- Secret handling via the personal layer; config via `harness.config.yaml`.
- Docs + installer wiring + `tests/test_install.sh` assertions.

**Out of scope**
- Inbound agent-read ownership / atomic claims — E10-F03.
- GitHub / Monday / Azure — their own epics.
- MCP transport of any kind.

## Chosen options
- Provider-per-epic structure (human's explicit choice).
- Transport = Jira REST + Personal Access Token, no MCP.

## Constraints
- **REST + PAT only, never MCP** (enterprise MCP blocks).
- **Secret hygiene.** PAT from env var / gitignored file, aligned with the E09-F02
  personal-overrides layer and `docs/CONFIG-LAYERING.md`. Never committed.
- **Fill the existing `jira` mirror stub** in `store/board-mirror.md` rather than
  inventing a parallel path; preserve the mirror's one-way invariant.
- **Installed-body change** → **VERSION bump** (MINOR). Installer wiring asserted in
  `tests/test_install.sh`.

## Open questions
- **Jira Cloud vs Server/Data Center.** Auth differs: Cloud = Basic (email + API
  token); Server/DC = Bearer PAT. Which target(s) does F01 support? (The user said
  "Personal Access Token" — likely Server/DC Bearer; confirm.)
- **Field mapping.** How do epic/feature/status map to Jira issue types + workflow
  states? Configurable status map (like the mirror's `status_map`) or fixed?
- **Where does the PAT live?** Env var name vs gitignored file path — pin the
  documented convention.
