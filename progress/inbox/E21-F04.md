# Intent — Stacked-PR lane for an atomic feature that exceeds the budget

## Problem / who
E21-F01 splits features at drill time and E21-F02 catches what slips through. Both assume the
work *can* be split into independently-mergeable units. Sometimes it cannot: a capability whose
intermediate states are not safely shippable to `main` — a half-wired booking tool that can
commit an appointment but cannot confirm it — is one deliverable no matter how many micro-specs
it contains.

Today the harness offers exactly one shape for that: one branch, one PR, one review surface,
and the non-convergence documented in `E21-F03`. The reviewer's budget is per-PR, so an atomic
feature pays the whole 17k-line review cost in a single pass that provably cannot cover it.

## Success outcome
A feature that must land atomically can still be **reviewed** in budget-sized increments. Each
increment is a PR whose base is the previous increment's branch, so the reviewer reads only
that increment's own diff, converges on it, and the stack merges in order. The feature stays
atomic with respect to `main`; the review does not.

## Scope / boundaries
**In scope**
- A documented stacked-PR lane: how the Builder produces increments, how each PR's base is set,
  and the merge order.
- `/sdd-pr-loop` awareness of a non-`main` base — the round cache, the gates, and the merge step
  currently assume the default branch.
- Rebase/restack handling when an earlier increment takes review fixes after a later one exists.
- Guidance on where to cut the stack (the wave boundaries from `E21-F01`).
- Test coverage in `tests/test_pr_loop.sh`.

**Out of scope**
- Automating the split of an existing branch. Choosing the seams is a human/Architect decision
  informed by the dependency DAG, not a diff-slicing algorithm.
- Any third-party stacked-PR tool (Graphite, `git-branchless`, `spr`). The harness's ethos is
  POSIX sh + `git` + `gh`; a new binary dependency for one lane is not justified.
- Changing the single-PR default. Stacking is opt-in for the case that needs it.

## Chosen options
- **Stacked PRs over one big PR with partitioned reviewers.** Partitioning the review across N
  reviewers was the other candidate and it is attractive on paper — same tokens, ~4× the wall
  clock speed, exhaustive coverage per partition. It does not survive contact with the Codex
  GitHub App, which reviews a whole PR and has no partition knob. Stacking gets the same
  partitioning using a mechanism GitHub already has: the base branch.
- **Base-branch stacking, not `main` + feature flags.** Feature-flagging the intermediate states
  onto `main` is the other way to keep increments shippable, but it puts half-built behavior in
  the production branch and leaves flag debt behind. The stack keeps `main` clean.

## Constraints
- **E18-F01 has merged**; this still sequences after E21-F03, which adds the per-round
  trend data a stack's review reporting builds on.
- The pr-loop's clean-signal detection, freshness rule (`created_at >= trigger.created_at`) and
  `max_rounds` semantics must be unchanged by the presence of a non-`main` base.
- Merging an increment must not silently retarget the rest of the stack — GitHub retargets a
  child PR when its base is deleted, and the loop must not mistake that for a review event.
- `auto_merge` needs a defined meaning in a stack: merging increment 2 before increment 1 is a
  correctness bug, not a race. Order must be explicit.
- Must stay inert when `pr_loop.enabled: false`.
- Do not freeze an exact VERSION or diff DO-NOT-TOUCH files against `main` in any test added to
  `verification.test_command`.

## Open questions
- Whether the stack is created up front (Builder emits N branches) or grown as the Builder
  finishes each wave. Growing it matches the existing one-task-at-a-time Builder loop and gets
  increment 1 into review while increment 3 is still being written — which is most of the
  wall-clock win.
- Whether the harness should hold the `done` rollup until the whole stack merges, or roll each
  increment. The feature is atomic by definition, so the rollup should almost certainly wait —
  but that interacts with the `done-but-unmerged` slice logic the Orchestrator already has.
- How the board represents a stack. Sub-features would duplicate `slices[]` semantics; a single
  feature with an ordered increment list is probably right but is a schema change.
