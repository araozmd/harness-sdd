# Intent — Merge-order safety for a non-default PR base

> **This brief was rewritten on 2026-07-29.** The original — a "stacked-PR lane for an atomic
> feature" — was withdrawn mid-review of PR #78 because its central premise was false. The
> history is preserved in the epic's Notes and in `progress/inbox/E21-F05.md`. Read the
> correction below before anything else.

## The premise that was wrong, and must not come back

The withdrawn brief claimed a stacked feature "stays atomic with respect to `main`". **It does
not.** Merging increment A publishes wave 1 to `main` while B and C are still open. A stack
enforces merge **order**; nothing in it makes the waves land together.

So stacking buys incremental **review** and nothing else. The claim was not merely wrong, it
was dangerous — it invited exactly the half-wired `main` it appeared to prevent. Four
`@codex review` rounds on PR #78 produced five blocking findings, **every one on this feature's
surface**, each largely created by the previous round's fix.

**No requirement, comment, doc line or commit message in this feature may assert or imply
atomic delivery.** That includes the header of the artifact being resurrected (below), which
still carries the false sentence verbatim.

## Problem / who

`/sdd-pr-loop` assumes throughout that a PR's base is the default branch. Its gates only ever
ask "are the checks green and the threads resolved" — never "is my base branch itself still an
open PR". Any PR opened against a non-default base — a stack increment, but equally a
release or integration branch — can therefore be merged ahead of the branch it is built on.

That is not a race. It is a correctness bug: merging increment 2 before increment 1 corrupts
the target branch, and `pr_loop.auto_merge` walks straight into it.

## Success outcome

`/sdd-pr-loop` refuses to merge a PR whose base is another open PR, names the parent it is
waiting for, and reports that state as a **normal, successful** outcome rather than a failure.
A repo whose default branch is not `main` behaves identically.

## Scope / boundaries

**In scope**
- Restore `tools/pr-stack-guard.sh` (`git show 1873af9:tools/pr-stack-guard.sh`) as the
  offline merge-order guard: default base ⇒ exit 0; base is an open PR's head ⇒ exit 6 naming
  the parent; base is a non-default branch nobody owns ⇒ exit 6 (withhold — the child has not
  been retargeted); unreadable input ⇒ exit 4, fail closed. **Correct its header comment**: it
  still asserts "The feature stays atomic with respect to the default branch."
- Run the guard before **both** merge paths (`merge` and `squash`) in the command body, and
  keep the source copy, the installer-generated copy and the installed executable in agreement.
- A distinct **merge order withheld** terminal state: exit 6 merges nothing, starts no further
  round and posts no additional `@codex review`. (Renamed from "waiting-for-parent" at spec
  time: exit 6 also fires when there is NO parent — an unowned non-default base — where nothing
  will ever arrive to wait for, so the old name made a promise the state cannot keep.)
- Non-default-base correctness elsewhere in the loop: the squash message enumerated against the
  PR's own base rather than the default branch; a GitHub **retarget** (which happens
  automatically when a base branch is deleted) not mistaken for a review event; the change-size
  check measured against the increment's own base.
- Inert when `pr_loop.enabled: false`.
- Test coverage in `tests/test_pr_loop.sh`.

**Out of scope**
- The lane doctrine, the seam guidance, the Builder/Orchestrator role contracts and the board
  representation — all of that is **E21-F05**, which depends on this feature.
- Atomic delivery of an unsafely-intermediate capability. Stacking does not solve it; a feature
  flag or an aggregate landing strategy would. Not seeded, still unsolved.
- Automating the split of an existing branch, and any third-party stacked-PR tool (Graphite,
  `git-branchless`, `spr`). The harness ethos is POSIX sh + `git` + `gh`.

## Decisions taken at the human gate (binding — do not re-open in the spec)

1. **`auto_merge` stays enabled on a child PR, gated by the guard.** The alternative considered
   was forcing it off whenever the base is non-default. The chosen design keeps automation and
   places the entire correctness burden on the guard — so the guard's own tests carry that
   weight and must be mutation-proved on every leg.
2. **The withheld-merge state returns success.** `/sdd-pr-loop`'s terminal-states contract currently
   says every path that does not merge returns failure, with the `auto_merge: false` hand-back
   as the sole exception. A healthy child whose parent is still open is a **third** legitimate
   unmerged outcome and gets its own explicit bullet. Rationale: a non-zero that callers are
   told to ignore trains operators to ignore all non-zeros. This edits a contract a reviewer has
   already policed twice — expect scrutiny there.
3. **The literal `default_branch="main"` fallback in the salvaged guard is a defect and must
   go.** `tools/change-size.sh` resolves `origin/HEAD` first precisely because hard-coding
   `main` is wrong on a `develop`/`trunk` repo; on such a repo the guard would read **every** PR
   as stacked ⇒ exit 6 ⇒ the loop merges nothing, ever. The caller resolves the default branch
   and passes it.

## Constraints

- The pr-loop's clean-signal detection, the freshness rule (`created_at >= trigger.created_at`)
  and `max_rounds` semantics must be **unchanged** by the presence of a non-`main` base.
- The guard must stay **offline**: it evaluates JSON the caller already fetched, so it is
  testable without `gh`, without a network and without a real stack.
- `change_size.max_requirements: 12`. This feature specced out at **12 R-ids** — at the ceiling. The two withhold legs are deliberately NOT folded: each must be individually mutation-provable. If the spec grows
  past 12, stop and report rather than squeezing scope.
- Do not freeze an exact `VERSION` string, and do not diff DO-NOT-TOUCH files against `main`,
  in any test added to `verification.test_command`.
- `tools/pr-stack-guard.sh` becomes installed body ⇒ `VERSION` bump + `CHANGELOG` entry.

## Open questions

- ~~Whether "base is a non-default branch nobody owns" should really withhold (exit 6) or pass.~~
  **RESOLVED at spec time: it withholds.** Decision 3 makes the reasoning stronger, not weaker —
  it changes only *how* the safe branch is known and adds no knowledge about an unowned base, so
  the two original failure states (retarget lag; parent merged without deleting its branch)
  survive intact. Three further arguments: the `--merge-target` declaration is now the caller's
  statement of intent, and "no open PR owns this base" is not one; under decision 2 a false
  withhold costs a hand-back a human reads once while a false clear costs the feature; and a
  failed `gh pr list` yields an empty array, so a pass-when-unowned rule would clear a genuinely
  stacked child on the caller's own failure. The operational cost — a repo that legitimately
  merges into a long-lived integration branch — is met by `HARNESS_MERGE_TARGET`.
