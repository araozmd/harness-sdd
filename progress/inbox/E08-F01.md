# Intent — Interactive agent-target selection (checkbox + re-prompt on update)

## Problem / who
`harness-install.sh` currently stamps **every** supported coding-agent front-end
unconditionally (`CLAUDE.md` + `.claude/`, `GEMINI.md`, `opencode.json`, and — via
E07 — an Antigravity `.agent/` tree). The user — an engineer installing the harness
into a repo — may use only one or two of these agents, yet gets all of them, with no
supported way to add or drop a target later. They want to **choose** which agents to
support, and to **revise that choice on a later run** without hand-editing files.

## Success outcome
- On install, the user is presented an interactive **checkbox-style selection** of the
  supported agents (Claude, Gemini, OpenCode, Antigravity) and only the chosen targets
  get stamped.
- On any **re-run / update**, the installer **re-prompts with the current selection
  pre-checked**, so the user can **add or remove** an agent — and this works **even
  when `VERSION` did not change** (selection is decoupled from upgrade detection).
- Non-interactive (CI) runs keep working unchanged.

## Scope / boundaries
**In scope:**
- An interactive selection UI in `harness-install.sh` listing the supported agents,
  with the current/previous selection pre-checked on re-run.
- **Conditional stamping:** only selected agents' front-ends + glue are written
  (Claude → `CLAUDE.md` + `.claude/`; Gemini → `GEMINI.md`; OpenCode → `opencode.json`;
  Antigravity → the E07 `.agent/` tree).
- **Persisting the selection** so a later run can pre-check it and reconcile (the
  prior selection is the baseline for add/remove).
- **Re-prompt-on-update** decoupled from version-bump detection: a re-run always
  offers reconciliation, not only when `VERSION` changed.
- **Non-interactive override + safe default:** honor `--agents=<csv>` and/or
  `HARNESS_AGENTS=<csv>`; with no TTY and no override, default to **ALL** agents
  (preserves today's behavior).
- A `tests/test_install.sh` assertion group covering: selected-only stamping,
  non-interactive ALL default, explicit override, and add/remove on re-run.

**Out of scope:**
- Forking or rewriting any canonical `agents/*.md` role file.
- Changing the portable core (`init.sh`, the markdown TaskStore, `progress/` handoffs,
  the 4-file spec format) or `store/tasks.schema.json` / status enums.
- The Antigravity glue *itself* — that is E07-F01. This feature only makes Antigravity
  **one selectable target**; E07-F01 supplies what gets stamped when it is selected.

## Chosen options
- **Placement: new epic E08** "Installer: selectable agent targets" (cross-cutting
  installer capability, not Antigravity-specific) — human chose this over E07-F02 or
  folding into E07-F01.
- **Sequencing: selection lands first.** `E07-F01` (currently always-stamps Antigravity,
  parked at the gate) has been wired `depends_on: ["E08-F01"]`; its always-stamp must
  become **stamp-if-selected**. See *Constraints* — that rework is an Architect re-spec
  of E07-F01, not part of this feature.
- **CI behavior: flag/env override + default ALL.** `--agents` / `HARNESS_AGENTS`
  override; no TTY + no override ⇒ stamp ALL (back-compatible).

## Constraints
- **Back-compatibility is non-negotiable:** existing CI that calls the installer with
  no args must keep stamping all agents (the no-TTY ALL default delivers this).
- Mirror the existing per-tool stamping structure in `harness-install.sh` — do not
  invent a parallel install path; gate each tool's existing stamp block on selection.
- **Installer contract (repo `CLAUDE.md`):** this touches the installed body, so it
  requires a **`VERSION` bump** (MINOR — new capability) + a `CHANGELOG.md` entry, and
  **every new command/behavior must be generated by `harness-install.sh` AND asserted
  in `tests/test_install.sh`**.
- Selection persistence should live with the installed harness metadata (e.g. under
  `.harness/`), consistent with how `.harness/.harness-version` is already stamped —
  exact mechanism is the Architect's call.
- Keep the harness lean (AGENTS.md rule 5).
- **E07-F01 coordination:** `E07-F01` is `spec-ready` with an approved spec that
  predates this selection model. Its dependency edge is now wired, but its spec still
  says "always stamp Antigravity." That spec must be **re-specced by the Architect**
  (always-stamp → stamp-if-selected) before E07-F01 is built — Inception did not and
  cannot edit that spec. Flag this at the E08-F01 spec gate.

## Open questions
- **Selection UI mechanism in POSIX/bash:** `whiptail`/`dialog` if present with a
  numbered-`read` fallback, vs. a pure-`read` numbered toggle list (no extra deps)?
  Lean toward zero-dependency to honor harness leanness — Architect's call.
- **Where to persist the chosen set** so re-runs can pre-check it: a dedicated file
  under `.harness/` (e.g. `.harness/agents`), a key in the version sidecar, or derive
  it from which front-end files already exist in the target? (Deriving avoids a new
  state file but can't distinguish "deselected" from "never installed".)
- **Remove semantics on re-run:** when a user unchecks a previously-installed agent,
  should the installer **delete** that agent's stamped files/glue, or just stop
  updating them and warn? Deletion is cleaner but riskier if a user hand-edited them.
- **Agent registry:** should the selectable set be a hard-coded list or a small
  declarative table in the installer, so adding a future agent (beyond these four) is
  one entry? A table would make E07's Antigravity target a natural row.
