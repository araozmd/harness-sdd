# Intent — the harness cannot run its own mandatory doc-critic checkpoint

## Problem / who

`agents/architect.md` makes the Doc-critic a **mandatory** step:

> ## Doc-critic checkpoint before `spec-ready` (R12)
> After drafting the four spec files … and before handing off, spawn the **Doc-critic**
> (`agents/doc-critic.md`) as a sub-agent with `target-type=feature-spec`.

`tests/test_install.sh` enforces that every **installed** target can do it:

```
[ -f "$T/.claude/agents/doc-critic.md" ] \
  || fail "E09: .claude/agents/doc-critic.md shim not emitted (critic cannot be spawned)"
grep -qE '^tools:.*\bWrite\b' "$T/.claude/agents/doc-critic.md" \
  || fail "E09: doc-critic shim lacks the Write tool — cannot record its progress/ note (R7)"
```

**This repository has no such shim.** `agents/doc-critic.md` exists; `.claude/agents/` holds
`architect.md`, `builder.md`, `orchestrator.md`, `pr-fixer.md`, `reviewer.md`, `scout.md` —
and no `doc-critic.md`. So the checkpoint cannot be spawned here, and R12 is silently skipped
on every spec the harness writes **for itself**, while `tests/test_install.sh` stays green
because it only ever inspects a freshly installed target.

**This is not hypothetical and it is not cheap.** On E17-F04 the checkpoint was skipped at
`spec-ready`; run afterwards by hand it returned **14 findings**, including a requirement
(`R2`) whose test, as written, would have *failed a correct implementation*, and a capability
tag that was true of every row by construction. On E21-F05 the checkpoint — again run by
hand — returned a **not gate-ready** verdict with two blocking findings that were reproduced
by executing them: a section-extraction helper blind to fenced code, and `set -eu` + `grep -c`
aborting the suite on its own passing case.

## Success outcome

The Doc-critic is spawnable in the harness source checkout, so `agents/architect.md`'s R12
runs where the harness writes its own specs — and a test fails if that stops being true.

## Scope / boundaries

**In scope**
- The `.claude/agents/doc-critic.md` shim in **this repo**, matching the shape of the sibling
  shims (they point at the canonical `agents/*.md`; the installed variant resolves against
  `.harness/` — the source variant must resolve against the source tree, so **check the
  existing shims rather than copying the installer's heredoc verbatim**).
- The shim needs the tools its role file requires: it writes
  `progress/<run>/doc-critic-<checkpoint>.md`, so **Write** is mandatory (the installed-target
  test already asserts exactly this).
- A test asserting the SOURCE repo's shim set — the gap exists because every existing
  assertion targets an installed tree.

**Out of scope**
- Any change to `agents/doc-critic.md` itself, or to the checkpoint's advisory-only semantics.
- The installer's generation of consumer shims — that path is correct and tested.
- Registering the other non-mirrored role files (`builder-heavy`, `driller`, `fixer`,
  `inception`, `planner`). **Enumerate them and say which are genuinely spawned as sub-agents
  by another role file** before deciding; the same "asserted for consumers, absent at source"
  gap may exist for more than one, and E17-F05's review found a missed path in three
  consecutive rounds by assuming an enumeration was complete.

## Constraints

- The new test must run under `verification.test_command` (`sh tools/run-tests.sh`, which
  auto-discovers `tests/test_*.sh`), and must **not** freeze an exact `VERSION` string and must
  **not** diff DO-NOT-TOUCH files against `main` — both are recurring anti-patterns here.
- Do not assert a source shim is *byte-identical* to the installed one: they resolve against
  different roots by design, so that assertion would be wrong rather than strict.
- POSIX sh / `dash`; green under `sh tools/run-tests.sh` and `./init.sh`.

## Open questions

- **Which direction should the test assert?** "Every `agents/*.md` that another role file
  spawns as a sub-agent has a `.claude/agents/` shim" is the general rule and would catch the
  next occurrence; "`doc-critic.md` exists" is the specific one and cannot. The general rule
  needs a reliable way to identify *spawned* roles — decide whether that is derivable or
  whether a maintained list is honest, and say which.
- Do the other front-end shim trees (`.codex/`, `.gemini/`, `.agents/`, `opencode.json`) have
  the same source-vs-installed asymmetry, or is `.claude/` the only one the source repo keeps
  by hand?
