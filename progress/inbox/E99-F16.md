# Intent — the harness cannot run its own mandatory doc-critic checkpoint

## Problem / who

`agents/architect.md` makes the Doc-critic a **mandatory** step:

> ## Doc-critic checkpoint before `spec-ready` (R12)
> After drafting the four spec files … and before handing off, spawn the **Doc-critic**
> (`agents/doc-critic.md`) as a sub-agent with `target-type=feature-spec`.

`tests/test_install.sh` enforces that every **installed** target can do it:

```
[ -f "$T/.claude/agents/doc-critic.md" ] \
  || fail "E09: .claude/agents/doc-critic.md shim not emitted (critic cannot be spawned)"
grep -qE '^tools:.*\bWrite\b' "$T/.claude/agents/doc-critic.md" \
  || fail "E09: doc-critic shim lacks the Write tool — cannot record its progress/ note (R7)"
```

**This repository has no such shim.** `agents/doc-critic.md` exists; `.claude/agents/` holds
`architect.md`, `builder.md`, `orchestrator.md`, `pr-fixer.md`, `reviewer.md`, `scout.md` —
and no `doc-critic.md`. So the checkpoint cannot be spawned here, and R12 is silently skipped
on every spec the harness writes **for itself**, while `tests/test_install.sh` stays green
because it only ever inspects a freshly installed target.

**This is not hypothetical and it is not cheap.** On E17-F04 the checkpoint was skipped at
`spec-ready`; run afterwards by hand it returned **14 findings**, including a requirement
(`R2`) whose test, as written, would have *failed a correct implementation*, and a capability
tag that was true of every row by construction. On E21-F05 the checkpoint — again run by
hand — returned a **not gate-ready** verdict with two blocking findings that were reproduced
by executing them: a section-extraction helper blind to fenced code, and `set -eu` + `grep -c`
aborting the suite on its own passing case.

## Success outcome

The Doc-critic is spawnable in the harness source checkout **in every front-end that checkout
registers roles for** (today: Claude and OpenCode) — requiring **all three** of the callee's
shim, the caller's `Task` tool, and the OpenCode registration, since any one alone leaves it
unrunnable — so `agents/architect.md`'s R12 runs where the harness writes its own specs, and a
test fails if that stops being true.

## Scope / boundaries

**In scope**
- The `.claude/agents/doc-critic.md` shim in **this repo**, matching the shape of the sibling
  shims (they point at the canonical `agents/*.md`; the installed variant resolves against
  `.harness/` — the source variant must resolve against the source tree, so **check the
  existing shims rather than copying the installer's heredoc verbatim**).
- The shim needs the tools its role file requires: it writes
  `progress/<run>/doc-critic-<checkpoint>.md`, so **Write** is mandatory (the installed-target
  test already asserts exactly this).
- **The CALLER's capability, which the shim alone does not give.** The source
  `.claude/agents/architect.md` declares `tools: Read, Write, Edit, Grep, Glob, Bash` — **no
  `Task`** — so even with the shim in place the Architect cannot spawn a sub-agent and R12 stays
  unrunnable. `tests/test_install.sh:584-585` asserts exactly this on an installed target, with
  the failure message *"architect shim lacks the Task tool — cannot spawn the doc-critic
  checkpoint"*. **The source repo fails that assertion on two counts, and fixing only one leaves
  this feature's stated success outcome unmet.** (Confirmed from the other direction during the
  E17-F04 re-spec: an architect sub-agent reported it could not run the checkpoint because it had
  no Task tool.)
- **The OpenCode registration too, not only Claude.** Source `opencode.json` registers
  `orchestrator, architect, builder, reviewer, scout` — **no `doc-critic`** — while the
  installer's generated `opencode.json` registers it explicitly
  (`harness-install.sh:2871-2876`). Fixing only the Claude shim leaves the mandatory checkpoint
  unavailable in the other front-end this source repo actually registers roles for, so the
  success outcome would again be claimed and not met.
- A test asserting the SOURCE repo's registrations **for every front-end the source repo
  registers at all**, plus the Architect's `Task` capability — the gap exists because every
  existing assertion targets an installed tree.

**The enumeration, done rather than assumed** (this brief warned against assuming one was
complete, then assumed one):

| source registration | registers | missing, vs roles spawned as sub-agents |
|---|---|---|
| `.claude/agents/` | architect, builder, orchestrator, pr-fixer, reviewer, scout | **`doc-critic`**, `builder-heavy` |
| `opencode.json` | orchestrator, architect, builder, reviewer, scout | **`doc-critic`**, `builder-heavy`, `pr-fixer` |
| `.codex/agents/`, `.gemini/agents/`, `.agents/` | absent from source by design — installer-generated for consumers | — |

`driller`, `fixer`, `inception` and `planner` are skill-driven, not spawned as sub-agents, so
they correctly have no shim in either.

**Out of scope**
- Any change to `agents/doc-critic.md` itself, or to the checkpoint's advisory-only semantics.
- The installer's generation of consumer shims — that path is correct and tested.
- **The OTHER missing registrations the enumeration turned up** — `builder-heavy` in both, and
  `pr-fixer` in `opencode.json`. They are real and they are the same class, but they are
  different *capabilities* (E17-F03's escalation tier; the pr-loop's fixer) with different
  callers, and folding them in would make this fix a survey. **Recorded here so the next reader
  does not have to rediscover them**, and worth their own fix — but this feature's success
  outcome is about the doc-critic checkpoint and is complete without them.
- Registering the other non-mirrored role files (`builder-heavy`, `driller`, `fixer`,
  `inception`, `planner`). **Enumerate them and say which are genuinely spawned as sub-agents
  by another role file** before deciding; the same "asserted for consumers, absent at source"
  gap may exist for more than one, and E17-F05's review found a missed path in three
  consecutive rounds by assuming an enumeration was complete.

## Constraints

- **NO `VERSION` bump, and no `CHANGELOG.md` entry — deliberately.** `AGENTS.md` requires a bump
  "only if the PR changes the **installed body**", listing `harness-install.sh`, `init.sh`,
  `agents/`, `docs/`, `store/`, `specs/_templates/`, `harness.config.yaml`, "the `.claude/`
  glue". This fix touches **none** of them. The consumer's `.claude/` glue is *generated by
  installer heredocs*, and the source repo's own `.claude/agents/` and `opencode.json` are
  copied to no one: `HARNESS_BODY_PROSE='AGENTS.md agents docs specs/_templates
  specs/glossary.md'` and `HARNESS_BODY_LOCAL='init.sh store tools umbrella.manifest.example.yaml
  umbrella.gitignore.example'` (`harness-install.sh:668-669`) — neither includes `.claude/`, and
  there is no other copy of it. So **every installed target receives byte-identical output before
  and after this fix**, and bumping would trip the exact failure the same clause warns about:
  "downstream `.harness/` dirs look 'upgraded' when nothing changed."
  Stated as a constraint rather than left silent because the omission looks like a mistake — it
  was raised as a review finding on the seed PR, and the next reader deserves the reasoning
  rather than the same round.

- The new test must run under `verification.test_command` (`sh tools/run-tests.sh`, which
  auto-discovers `tests/test_*.sh`), and must **not** freeze an exact `VERSION` string and must
  **not** diff DO-NOT-TOUCH files against `main` — both are recurring anti-patterns here.
- Do not assert a source shim is *byte-identical* to the installed one: they resolve against
  different roots by design, so that assertion would be wrong rather than strict.
- POSIX sh / `dash`; green under `sh tools/run-tests.sh` and `./init.sh`.

## Open questions

- **Does granting the source Architect `Task` change anything else?** It widens what that
  sub-agent may do in this repo, and no other source shim carries `Task` today. Check whether
  the installed architect shim's grant is scoped in any way before mirroring it, and say so.
- **Which direction should the test assert?** "Every `agents/*.md` that another role file
  spawns as a sub-agent has a `.claude/agents/` shim" is the general rule and would catch the
  next occurrence; "`doc-critic.md` exists" is the specific one and cannot. The general rule
  needs a reliable way to identify *spawned* roles — decide whether that is derivable or
  whether a maintained list is honest, and say which.
- ~~Do the other front-end shim trees have the same asymmetry?~~ **Answered above by
  enumeration** — `opencode.json` does and is now in scope; `.codex/`, `.gemini/` and `.agents/`
  are absent from the source by design. Left visible rather than deleted, because the question
  was asked, went unanswered, and the unanswered version shipped a scope that could not meet its
  own success outcome.
