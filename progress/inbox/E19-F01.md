# Intent — --agents=host resolution + fresh-install pre-check baseline

## Problem / who
A human who works in exactly one CLI installs the harness and gets all five front-ends'
glue stamped into their repo: `GEMINI.md`, `opencode.json`, an Antigravity `.agents/`
tree, and global Codex prompts alongside the Claude glue they wanted. Their reasonable
conclusion is that the harness is "multi-CLI by default".

It is a **defaults** problem, not a missing capability. E08 already delivered selection:
`--agents=claude` works today, the interactive picker works today, and re-running the
installer already reconciles both adds and removes against `.harness/.agents`. What is
missing is that the *unchosen* path pre-checks everything — `AGENT_KEYS` all on at
`harness-install.sh:334`, all-keys on a no-TTY run at `resolve_agents`, :765.

## Success outcome
Installing the harness from inside a single CLI stamps that CLI's glue and nothing else,
without the human having to know a flag exists. Adding a second front-end later is still
one re-run of the installer.

## Scope / boundaries
**In scope**
- `host` as a new resolution mode for `--agents` / `HARNESS_AGENTS`, resolving to the
  front-end the installing session is running in via env-marker detection.
- Using the detected host as the pre-check baseline on a **fresh** install.
- Documenting the mode, and documenting in `docs/INSTALL.md` that re-running the
  installer is the post-install re-toggle path (currently buried in a header comment).

**Out of scope**
- Any runtime behavior change. The harness is already single-CLI at execution time
  (`execution.builder.backend: in-session`); this feature only governs which glue files
  land on disk.
- A new standalone reconfiguration TUI or `/sdd-config` command. The human explicitly
  chose "re-run the installer" as the post-install path, because the installer already is
  the config UI and a parallel one would drift from it.
- Changing what an **upgrade** pre-checks.

## Chosen options
- **Fallback to all keys when the host is undetectable.** Preserves today's documented
  no-TTY contract byte-for-byte, so `host` is a best-effort *narrowing* that can never
  surprise CI or a piped install by stamping less than expected. Rejected: falling back
  to `claude` (silently narrows existing CI on upgrade) and aborting (makes `host`
  unusable in exactly the scripted contexts you would want it).
- **Post-install re-toggle = re-run the installer.** Zero new code; it already re-prompts
  pre-checked from `.harness/.agents` and removes deselected glue. Needs documenting, not
  building.

## Constraints
- `host` must **never be persisted** into `.harness/.agents`, which stores concrete keys
  only. It is a resolution mode consumed by `resolve_agents`, not a sixth agent key — and
  it must not be added to `AGENT_KEYS`, or it leaks into the toggle UI as a selectable row.
- **Upgrades must not silently narrow.** An existing install's persisted selection stays
  the pre-check baseline; host detection applies to fresh installs only.
- **Preserve the `codex` deselection special-case.** Codex glue lives in a shared,
  cross-target `$CODEX_HOME/prompts`; host-narrowing must never cause the installer to
  reclaim prompts a different harness target installed. The existing legacy-baseline
  exclusion for codex exists for exactly this reason and must not be weakened.
- `AGENTS.md` stays always-written and never gated.
- Detection must be treated as best-effort: a miss is normal, not an error.
- Any installer-invoking test must sandbox `CODEX_HOME`.

## Open questions
- The precise env-marker set per front-end, and their reliability. `CLAUDECODE` and
  `CODEX_HOME` are the confident ones; the OpenCode / Gemini / Antigravity markers need
  verification rather than assumption. A marker that is merely *present in the
  environment* is not proof the installer was launched from that CLI.
- Whether `host` should also be honored when passed non-interactively (scripted
  `--agents=host` in CI) or only as an interactive baseline. Honoring it uniformly is
  simpler to reason about and is the assumed default unless the Architect objects.
- Whether the fresh-install baseline should be host-only or host-plus-`claude`, given how
  many users run Claude Code as their primary session regardless of what else is
  installed.
