# Intent — Board write lock: flock-guarded read-modify-write on tasks.json

## Problem / who
The harness backend (`store/local.md`) mutates `state/tasks.json` with a plain
read-modify-write and **no locking**. That is safe only because work runs serially.
E15 introduces concurrent fix chains (F03) that each transition board state, so two
near-simultaneous writers can lose an update (last-writer-wins clobber). This feature
gives the backend a mutual-exclusion primitive so concurrent writers are safe. The
users are the harness's own agents (Orchestrator, Builders in parallel worktrees).

## Success outcome
Every persisted board write is serialized under an advisory lock, and no concurrent
writer ever loses another's committed update. A normal serial `/sdd-next` run behaves
exactly as before (the lock is uncontended and invisible).

## Scope / boundaries
- In scope: an advisory `flock` on `state/tasks.json.lock` wrapping the persist path;
  the critical section must **re-read `state/tasks.json` from disk inside the lock**,
  then mutate → validate (`json.load` + schema) → write → release.
- In scope: the best-effort `on_write_command` hook fires **after** lock release
  (unchanged semantics, never blocks/rolls back).
- Out of scope: cross-terminal / cross-machine coordination beyond a single host's
  `flock`; any change to the write *content* or schema.

## Chosen options
- Locking primitive: `flock` on a sibling lockfile (`state/tasks.json.lock`),
  `cwd = HARNESS_DIR`.
- Re-read-inside-lock is mandatory (prevents lost updates), not read-once-then-lock.

## Constraints
- **No new status/enum values, no `store/tasks.schema.json` change.**
- Must be a **no-op for serial callers** — `/sdd-next` and existing tests unchanged.
- Validation stays fail-stop: never leave a partially-written `state/tasks.json`.
- Installed-body change ⇒ VERSION bump (MINOR); installer wiring asserted in
  `tests/test_install.sh` if any installed file changes.

## Open questions
- Exact lock scope: wrap only the backend `set_status`/persist helper, or a broader
  board-mutation entry point? Architect to pin the narrowest correct boundary.
- Lock acquisition timeout / retry behaviour vs. block-forever — Architect's call,
  favouring a bounded wait with a clear error over a silent hang.
