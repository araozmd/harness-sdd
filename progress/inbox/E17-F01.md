# Intent — Per-role model selection: config schema + per-front-end agent stamping

## Problem / who

Serves the harness operator who pays for several agent subscriptions at once and wants
each SDD role to run on the model that actually fits its job. Today every sub-agent the
Orchestrator spawns inherits whatever model the host CLI session is running, so the
Architect's design work and the Builder's mechanical execution of an approved
`tasks.md` cost the same per token. There is no place to express "Architect on the
reasoning tier, Builder on the standard tier, Scout on the cheap tier", and because
model ids would otherwise be hardcoded wherever they appear, every new model release
becomes a code patch instead of a config edit.

## Success outcome

The operator edits one block in `harness.config.yaml`, re-runs the installer, and each
selected front-end's agent definitions carry the right model for each role — expressed
in that CLI's own native convention. A target that configures nothing behaves exactly as
it does today.

## Scope / boundaries

**In scope**

- A front-end-agnostic `models:` block in `harness.config.yaml`: a default tier, a
  per-role tier mapping (orchestrator / architect / builder / reviewer / scout), and an
  optional per-front-end override map for pinning exact model ids.
- Installer support that stamps the resolved model into the **native agent-definition
  convention of each front-end the user selected** — Claude Code, Codex, Antigravity,
  OpenCode and Gemini each configure agents differently, so each selected target gets
  its own correct shape rather than a shared one.
- Idempotent re-stamping: re-running the installer after a config change updates the
  stamped models; deselecting a front-end removes its stamp, consistent with the
  existing re-run/deselect behavior from E08-F01.
- Installer test coverage asserting the generated artifacts for each front-end.
- Documentation of the config block and the tier vocabulary.

**Out of scope**

- The dual Builder (`builder-heavy`) and the escalation rules — anticipated E17-F02.
- The worker roster and any invocation of non-host CLIs — anticipated E17-F03.
- `pr-loop` migration — a separate epic entirely.
- Any runtime model switching by the Orchestrator mid-session. This feature is
  config → generated file, nothing dynamic.

## Chosen options

- **Epic shape:** a dedicated "Cost-aware execution & model routing" epic (E17). This
  feature is F01; the dual Builder and the worker roster follow as F02/F03. The
  `pr-loop` migration stays a separate epic.
- **Portability: full multi-front-end now.** The operator's explicit reasoning: every CLI
  uses a different convention for configuring agents and skills, so for each selected
  CLI the agents should be installed in that CLI's own particular way. The config schema
  stays generic; the stamping is per-front-end and correct for each.
- **Escalation (context for F02, not built here):** both rules — an Architect-written
  complexity tag at spec time *and* automatic promotion after two Reviewer rejections on
  the same task. F01 should leave room for a second Builder variant without a config
  migration.

## Constraints

- **Purely additive and backward compatible.** An absent `models:` block must reproduce
  current behavior exactly. This is what keeps the harness usable by an engineer running
  a single CLI — do not make model configuration mandatory.
- **Only selected front-ends are stamped.** Reuse the existing agent-target selection
  (E08-F01); never write into a front-end the user did not select.
- **Tier aliases are the default, pinned ids the escape hatch.** Defaults must not freeze
  a specific model id, so new releases are picked up without a harness change.
- **Installer wiring must be asserted in `tests/test_install.sh`** in the same change
  that adds it. Missing installer-test wiring has been flagged as a blocking review
  finding twice before on this repo — treat it as part of the definition of done, not a
  follow-up.
- **No permanent-suite anti-patterns.** Tests registered in `verification.test_command`
  must not freeze an exact `VERSION` string and must not diff DO-NOT-TOUCH files against
  `main`.
- **Sandbox `CODEX_HOME`** (and any other front-end HOME-like env var) in every test that
  invokes the installer, so a test run never writes into the developer's real config.
- **Bump `VERSION` (SemVer, MINOR)** — the installed body changes.
- Do not modify `store/tasks.schema.json`, introduce a new status value, or change
  Orchestrator routing in this feature.

## Open questions

- **Per-CLI model-selection surface — needs Scout reconnaissance before the plan is
  written.** Each front-end must be verified against current documentation rather than
  assumed: Claude Code sub-agent frontmatter, Codex agent TOML, OpenCode agent markdown,
  Antigravity personas, and Gemini. Two specific unknowns: whether OpenCode, Antigravity
  and Gemini support a *per-agent* model at all (versus only a session-level default),
  and what each one does with an unrecognized model value. Where a front-end has no
  per-agent surface, decide explicitly whether to no-op with a warning or to fall back to
  a session-level setting — and document it.
- **Tier vocabulary.** How many tiers, and what are they called? A three-tier
  `reasoning` / `standard` / `cheap` split is the obvious starting point, but the naming
  must survive model churn and map cleanly onto every front-end.
- **Role coverage.** Should the Orchestrator itself be model-configurable? It is the
  session driver rather than a spawned sub-agent, so it may not be stampable the same
  way.
- **Interaction with per-developer local overrides (E09-F02).** Should a developer be
  able to override model choices locally without touching the shared
  `harness.config.yaml`, and if so, through which file?
- **Validation strictness.** Should the installer reject an unknown tier or an unknown
  pinned id outright, or warn and fall back to the default tier? Failing loudly is safer,
  but a pinned-id check would require the installer to know each vendor's model list.
