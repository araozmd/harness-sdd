# Intent — Deterministic escalation to `builder-heavy`

## Problem / who

E17-F02 makes a heavier Builder *available*. Nothing decides *when* to use it, so the
capability has no caller and the operator is back to noticing a struggling task by hand and
re-running the session on a stronger model — which is the gap E17's brief names.

The epic is explicit that this must be **deterministic, never ad-hoc judgment**: the harness
escalates on a rule, not on an agent's opinion that a task "looks hard".

## Success outcome

A task that fails review twice is retried by `builder-heavy` automatically, without a human
noticing. A task the Architect marked complex starts there. Both decisions are readable
after the fact — you can tell from the record which Builder ran and why it was chosen.

## Scope / boundaries

**In scope**
- **A complexity tag written by the Architect at spec time**, in the feature spec, with a
  defined vocabulary and a defined default. Its absence must mean "standard".
- **The Orchestrator's routing rule**: which Builder role name to spawn, given the tag and
  the current round.
- **The two-rejection promotion**: after two Reviewer rejections on the same feature,
  subsequent builds go to `builder-heavy`. The round counter this reads **already exists** —
  `agents/orchestrator.md` defines `round` as starting at 1 and incrementing on every
  `in-review → in-progress` bounce, and it is already stamped on `builder`/`reviewer`
  telemetry records. Reuse it; do not invent a second counter or a second source of truth.
- **Observability**: the choice must be recoverable afterwards, in the same
  `progress/history.md` line and telemetry `phase` record the loop already writes.

**Out of scope**
- Creating the role (E17-F02, which must land first).
- Any change to what `builder-heavy` *does* — ADR-0002 fixes it as the same body at a
  heavier tier, so this feature routes, it does not differentiate behavior.
- Demoting back to the standard Builder, or any cost-based policy. Escalation is one-way
  within a feature; leave the reverse unsolved rather than guessing at it.
- The worker roster (E17-F04).

## Chosen options

- Escalation is **routing only** — a consequence of ADR-0002, not a fresh decision.

## Constraints

- **Deterministic, never judgment.** The rule must be evaluable from recorded state alone
  (tag + round count). An Orchestrator that "decides the task looks hard" violates the
  epic's own success criterion.
- **`depends_on: E17-F02`.** There is no role to route to before it lands, and a spec
  written against an imagined role name will drift from the one F02 actually emits.
- **Backward compatibility.** Specs written before this feature carry no tag; they must
  route to the standard Builder with no warning and no failure.
- **The delegate backend.** `execution.builder.backend: delegate` means the Builder does not
  write code at all — it shells out to `delegate_cmd`. Decide and state what escalation
  means there (most likely: nothing, and say so) rather than leaving it implied.
- Budget: `change_size.max_requirements: 12`.

## Open questions

- **Where does the complexity tag live?** Feature-spec frontmatter, a `tasks.md` field, or
  the TaskStore entry. The TaskStore is machine-read and already the Orchestrator's input,
  but it is also schema-governed — a new field is a schema change with migration cost. The
  spec files are free-form but must then be parsed. Architect's call, with the cost stated.
- **Is two rejections the right threshold**, or should it be configurable in
  `harness.config.yaml` beside the other `pr_loop`/`change_size` knobs? The epic says "after
  two Reviewer rejections" — treat that as the default, and decide whether it is a constant
  or a key.
- **Does the promotion persist across sessions?** The round counter lives in
  `progress/history.md`, which survives; confirm the rule still evaluates correctly when the
  first two rounds ran in a previous session.
