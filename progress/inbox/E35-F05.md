# Intent — Integrity-pin the pi-subagents install

## Problem / who
`--pi-deps=install` (E35-F04) runs `pi install -l -a npm:pi-subagents@0.78.0`. That pins
name@version only, resolved through npm. On a project the operator has trusted in pi, a
lockfile committed under `.pi/npm/` can steer the tarball URL of pi-subagents and of any
package in its tree (docs/INSTALL.md ~145-146 documents this as a residual). The
`pinned` verdict (`pi_list_status`) can therefore certify an install that is not the
official code. The people affected are harness operators who select pi and approve the
install.

Facts verified on the host against pi 1.2.0
(`@earendil-works/pi-coding-agent/dist/core/`):
- `package-manager.js:1525`: pi runs `npm install <spec> --prefix .pi/npm --legacy-peer-deps`
  with **no `--ignore-scripts`**. Lifecycle scripts of any steered package therefore run
  DURING the install. A check that only runs after the install detects tampering too late,
  so the pre-install guards are mandatory.
- `settings-manager.js:220` deep-merges `.pi/settings.json` over the global settings.
  `getNpmCommand()` (`package-manager.js:1448`) returns the merged `npmCommand`, so a
  trusted project can replace npm with any command. Nothing in `harness-install.sh` checks
  it today. This bypasses the existing `.npmrc` refusal and every lockfile guard.
- npm registry: `pi-subagents@0.78.0`
  - `dist.integrity` = `sha512-AsOvPL1xaVFV4bqIlheQKNI2LmAoiAKTPXXxi39/BsWJTdMJIqAkZJ3iLi6bTsh2PZHG7Ur08b7VJOtgAMIAig==`
  - tarball: `https://registry.npmjs.org/pi-subagents/-/pi-subagents-0.78.0.tgz`
  - the package itself has no install scripts.
- The dependency tree has 7 packages: pi-subagents, jiti 2.7.0, yaml 2.8.3, acorn 8.18.0,
  undici 8.10.2, @js-temporal/polyfill 0.5.1, and jsbi `^4.3.0`. jsbi floats and is
  currently 4.3.2. Peers are `--legacy-peer-deps`-skipped.

## Success outcome
- An install that npm would resolve away from the official registry tarballs is refused
  BEFORE any npm process runs.
- `pinned` is reported only when the installed pi-subagents is byte-verifiably the
  official 0.78.0.
- A tampered install never reads as `pinned`, and under the flag it exits 5 like the
  other "not verified" outcomes.

## Scope / boundaries
The human chose option (c): guards both before and after the install.

Pre-install guards (refuse with `install: not attempted: <reason>`):
1. A project-scope `npmCommand` in `.pi/settings.json`, in any form pi would accept.
   Parse at least as leniently as pi does (BOM, invalid UTF-8), and fail closed.
2. An existing lockfile: `.pi/npm/package-lock.json`, `.pi/npm/npm-shrinkwrap.json`, or
   `.pi/npm/node_modules/.package-lock.json`. It is accepted only when BOTH hold:
   - every package entry's `resolved` is the canonical registry URL for its own
     name@version (watch npm aliases and scoped names);
   - pi-subagents' `integrity` equals the pin.

   Anything unreadable or ambiguous refuses.

Post-install checks, which also gate `pinned` in `pi_list_status`:
3. The lockfile's `node_modules/pi-subagents` entry has
   `integrity` == the pinned sha512.
4. The on-disk `node_modules/pi-subagents` matches a shipped per-file sha256 manifest of
   the official 0.78.0 tarball: the exact file set, no extra files. Verify with the real
   npm whether npm adds or rewrites any file inside the package dir.

Out of scope:
- Pinning the integrity of the other 6 dependencies; guard 2's canonical-URL rule covers
  them before the install.
- Changing pi's own install behaviour.
- The user-scope install path. F04 already reports `user-scope mismatch` and runs
  nothing.

## Chosen options
- Option (c), guards both before and after the install, chosen over (a) post-install only
  and over (b) refusing every lockfile.
- A sha256 file manifest for checking the files on disk, because a tarball sha512 cannot
  be recomputed from the extracted files.
- Release as MINOR 0.96.0. Update CHANGELOG and docs/INSTALL.md (~145-146): drop the
  "not an integrity pin" caveat and document the new refusals.

## Constraints
- F04 design rules:
  - Fail closed on anything unreadable or ambiguous.
  - One guard per hazard; stacked duplicates are equivalent mutants.
  - Every guard is mutation-checked, with the fixed reason word pinned per row.
  - Re-read another tool's input at least as leniently as that tool does.
- Read progress/lessons.md (the E35 entries, lines ~462-491) and the `review(E35-F04)`
  commits for the bypasses already tried. These include links in `.pi/npm` at any depth,
  forged `pi list` lines through embedded newlines, and BOM / invalid UTF-8 settings.
- Verify behaviour against the REAL pi 1.2.0 and pi-subagents 0.78.0. Do it offline, with
  a local registry or the official tarball in the scratchpad, and with a byte-pristine
  victim where writes are claimed. Never run a mutating `pi` on the host, and never touch
  `~/.pi/agent`.
- Keep the existing F04 refusals intact: links and hard links in the `.pi/npm` tree, and
  `.pi/npm/.npmrc`.

## Open questions
- Does npm reuse a lockfile entry's `resolved`/`integrity` for an explicitly named
  `pi-subagents@0.78.0` spec? Does it honour the hidden `node_modules/.package-lock.json`
  when `package-lock.json` is absent? Verify with real npm before writing the guard.
- How should a legitimate existing lockfile be handled when it contains OTHER project pi
  packages, which also use registry URLs?
- What the reason words and the exit-status mapping should be for each new refusal.
