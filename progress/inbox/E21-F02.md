# Intent — Pre-PR change-size check on the Reviewer → PR handoff

## Problem / who
E21-F01 puts a budget where the sizing *decision* is made. This feature puts a measurement
where the sizing decision is last *reversible*.

Today the Orchestrator's flow is: local Reviewer approves → create the PR → request review.
Nothing between the approval and the PR looks at how large the branch actually is. On
`viernes-bookings-api` E14-F05 the branch was 17,202 additions across 77 files before any
number was attached to it, and the first entity to notice was a paid reviewer, twelve times.

Splitting a branch is cheap before the PR exists and expensive after — the PR carries review
threads, a Codex history, and a `depends_on` edge somebody is waiting on.

## Success outcome
When a branch exceeds the budget, the human sees the number and the shape of the overage
*before* the PR is opened, along with the concentration data needed to decide where to cut.
The check is fast, local, and costs no review tokens.

## Scope / boundaries
**In scope**
- A measurement at the Reviewer → PR handoff: production additions, file count, and the
  budget from E21-F01, computed against the PR's merge base.
- Reporting the **distribution**, not just the total — which files carry most of the change —
  because the actionable question is "where do I cut", not "how big is it".
- Excluding from the production count what should not count against it: test files, and any
  path the target declares generated/vendored.
- An explicit override path that records the reason, so a legitimately large change (rename
  sweep, generated contract) is not blocked, just accounted for.
- Test coverage; and if a new config key or command is introduced, generation by
  `harness-install.sh` plus an assertion in `tests/test_install.sh`.

**Out of scope**
- Blocking the PR. This is a gate that reports and requires acknowledgement, never a refusal.
- Any judgement about *risk* per file. The check reports where the lines are; it does not
  claim to know which of them are dangerous.
- Anything in `/sdd-pr-loop` (F03/F04, blocked on E18-F01). This check must work on a target
  where `pr_loop.enabled: false` and no PR loop exists at all.

## Chosen options
- **At the Reviewer → PR handoff, not as a git hook.** A hook fires per commit, where the
  number is meaningless (PR #76 had 40 of them) and where the harness does not own the target's
  hook chain. The handoff is the single point where the total is both final and still cheap to
  act on. It is also where the Orchestrator already pauses.
- **Report the distribution.** In PR #76 three files (10% of the diff) drew 67% of the
  findings, and one file at 5.4% of the diff drew 33%. A bare total would have said "17k, too
  big" — true, unactionable, and equally true of the 15,500 lines that drew almost nothing.
- **Merge-base diff, not `HEAD~n`.** The branch may have been rebased or may carry merge
  commits; only `git diff $(git merge-base ...)` measures what a reviewer will actually read.

## Constraints
- Must consume the budget defined by E21-F01 — one source of truth. Do not restate the numbers.
- Must degrade cleanly with no network and no `gh`: this is a local git measurement, and it has
  to work before a PR (and therefore before a PR number) exists.
- Must not add a hard dependency the harness does not already have. POSIX sh + git, matching
  `init.sh`'s zero-dependency ethos; `python3` is already relied on by `tools/tasks-lock.py`.
- Do not double-count: the harness's own `.harness/progress/` scratch must not inflate a
  target's production number (see `E99-F05`, which stops it being committed at all).
- Do not freeze an exact VERSION or diff DO-NOT-TOUCH files against `main` in any test added to
  `verification.test_command`.

## Open questions
- What counts as a "test file" across targets. `*.test.ts` and `tests/` cover the observed
  repos, but a Python target using `test_*.py` and a Go target using `*_test.go` need the
  classifier to be configurable rather than hard-coded — and a wrong classifier makes the whole
  number untrustworthy.
- Whether the override is recorded in the PR body, in `progress/`, or in the telemetry log. The
  telemetry log is local-only and gitignored, which is wrong for an audit trail somebody else
  needs to read; the PR body is the obvious candidate but does not exist yet at check time.
- Whether the check should also run at the *start* of the Builder loop against the spec's
  estimated size, giving a second, earlier warning. Probably yes, but it duplicates F01's
  refusal and may not be worth two mechanisms.
