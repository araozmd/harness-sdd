# Intent — Doc-critic advisory review pass over harness-generated docs

## Problem / who
The harness generates a lot of documentation on the way to code — vision,
architecture, and ADRs (`/sdd-plan`); epic decompositions and inbox briefs
(`/sdd-drill`); and the four-file spec (`.spec`/`.plan`/`.tasks`/`.tests`) from the
Architect. **None of it is reviewed before it drives downstream work.** The
planning-tier docs (vision/architecture/ADRs) get no review at all; the Architect's
spec only meets the *human* gate at `spec-ready`. So the human operator is the sole
QA layer, and defects in generated docs (placeholders, internal contradictions,
ambiguous requirements, scope creep, YAGNI) either reach the human's desk or slip
straight into implementation. The user this serves is the harness operator who wants
to seed a plan and let it run for hours: better docs mean fewer bad autonomous runs
and less manual gate babysitting.

## Success outcome
An **advisory doc-critic** reviews harness-generated documentation at defined
checkpoints, flags only issues that would cause real downstream problems, and the
generating agent **fixes them inline** before the doc is used. No new human gate is
added; the existing `spec-ready` human gate does *less* work because obvious defects
are already gone. A well-seeded plan still runs autonomously for hours.

## Success outcome — evidence
- A doc-critic pass runs after Planner writes vision/architecture/ADRs, after Driller
  decomposes an epic, and after the Architect drafts the four-file spec (before the
  `spec-ready` human gate).
- **The Planner checkpoint enforces that every `draft` epic is independently
  drillable** — i.e. a developer who did not run `/sdd-plan` can pick up the epic and
  run `/sdd-drill` on it without further clarification. The critic flags a draft epic
  as incomplete unless its `epic.md` carries the *drillable-minimum*: (1) business
  brief, (2) epic-level success criteria (outcomes), (3) technical considerations /
  restrictions / non-goals the tech lead wants honored, (4) cross-epic dependencies
  and boundaries, and (5) pointers to the relevant shared ADRs in `architecture.md`.
  This directly serves the intended team workflow — product + tech lead run
  `/sdd-plan` to lay down all epics as drafts, then individual developers each take an
  epic and own its `/sdd-drill` + `/sdd-next` from there.
- Findings are calibrated like the brainstorming skill's spec-document-reviewer:
  completeness / consistency / clarity / scope / YAGNI; "only flag issues that would
  cause real problems"; recommendations are advisory and never block.
- The generating agent applies fixes inline and proceeds — the critic adds no
  human-in-the-loop pause.
- Tests assert the review runs at each checkpoint and that installer wiring for any
  new glue is present (see Constraints).

## Scope / boundaries
**In scope**
- A reusable doc-critic reviewer contract (its own role/prompt) modeled on
  `spec-document-reviewer-prompt.md`'s calibration.
- Wiring it into three checkpoints: Planner output (`/sdd-plan`), Driller output
  (`/sdd-drill`), and Architect spec output (before the `spec-ready` gate).
- Fix-inline-then-proceed behavior; advisory-only recommendations.
- Any installer/glue changes needed to ship the new role + wiring, plus test
  coverage.

**Out of scope**
- Adding or changing any human gate (the critic is automated + advisory only).
- Reviewing production *code* — that is the Reviewer's job (E05). This feature
  reviews *documents*, not implementation.
- "Every command re-reviews all docs" — the review is at defined checkpoints, not a
  blanket pre-flight on every harness command (explicitly rejected to avoid token
  burn / doc-drift theater).
- Per-developer customization — that is the sibling feature E09-F02.

## Chosen options
- Grouped with E09-F02 under one new epic, **E09 "Harness doc quality &
  customization"** (human picked "one new epic for both").

## Constraints
- **No new human gates.** The critic fixes inline and hands off; it must not
  introduce a pause. The autonomous-run property is a hard requirement.
- **Calibration discipline.** Follow the brainstorming reviewer's rule: only flag
  issues that would cause real problems during downstream work; minor wording /
  stylistic preferences are not issues. Recommendations are advisory, never blocking.
- **Touches the installed body** (`agents/*.md`, `docs/`, the generated Claude /
  Antigravity / OpenCode glue, possibly `harness-install.sh`) → **warrants a
  `VERSION` bump** (SemVer MINOR) in the same PR, per the repo versioning policy.
- **Installer wiring must be asserted.** Any new role file / command / glue the
  installer generates must be produced by `harness-install.sh` *and* asserted in
  `tests/test_install.sh` (recurring Codex finding on prior features — do not skip).
- **Portable.** The reviewer contract must be written for any AGENTS.md-compatible
  CLI, not Claude-specific — mirror the existing role files under `agents/`.

## Open questions
- **One reviewer or three?** Should there be a single doc-critic role invoked with a
  target-type argument (vision/arch/ADR vs. epic-decomposition vs. spec), or a
  thin per-checkpoint prompt reusing one shared calibration block? (Architect's call
  — lean toward one role, parameterized, to avoid drift.)
- **Who invokes it?** Is the critic a Claude Code sub-agent spawned by the
  Planner/Driller/Architect, or an Orchestrator-driven step between phases? Confirm
  it fits the existing sub-agent/Orchestrator model without forking those roles.
- **Failure posture.** If the critic itself errors or times out, does the generating
  agent proceed (best-effort, like the post-write sync hook) or halt? Recommend
  best-effort/never-blocking to protect autonomy — confirm.
- **Where do findings go?** Inline fix only, or also a short note under
  `progress/<run>/` for traceability? Recommend a brief progress note so a human can
  audit what the critic changed.
