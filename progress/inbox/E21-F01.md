# Intent — Feature-size budget in the Driller and Architect

## Problem / who
Nothing in the harness bounds the size of a feature. `agents/driller.md` decomposes an epic
into features with no size rule; `agents/architect.md` writes the four-file spec for whatever
it is handed. The sizing decision is therefore made implicitly at drill time and never
revisited.

`viernes-bookings-api` E14-F05 came out of a drill carrying **R1–R36 and T1–T25** and became
one PR of 17,202 additions across 77 files. Twelve `@codex review` rounds over 10h45m returned
20 P1 + 15 P2 with a **flat** per-round blocking-finding rate — the review never converged, so
"clean" would not have meant anything if it had ever arrived.

The person harmed is whoever drills the next epic. They have no rule to apply, so they apply
none, and the cost lands three phases later on someone waiting on a merge.

## Success outcome
The Driller splits an over-budget feature *at decomposition time*, because a written rule tells
it to — not because someone remembered PR #76. The Architect refuses to spec a feature it can
already see is over budget and says which seam to split on, instead of emitting a
36-requirement spec that guarantees an unreviewable PR.

## Scope / boundaries
**In scope**
- A budget expressed in `harness.config.yaml` (new keys), with defaults, so a target can tune
  it without editing a harness-owned prompt that the next upgrade would clobber.
- A split rule in `agents/driller.md`: what to measure at decomposition time, and what to do
  when the brief exceeds it.
- A refusal-and-report rule in `agents/architect.md` for a feature that arrives over budget.
- Test coverage in `tests/test_sdd_drill.sh` (and the architect suite) asserting the rule text
  and the config keys are installed.

**Out of scope**
- Measuring an actual diff. That is F02 — this feature governs the *estimate* made before any
  code exists.
- Anything touching `/sdd-pr-loop` (F03/F04, blocked on E18-F01).
- Retroactively splitting features already on the board.

## Chosen options
- **Group micro-specs into delivery waves; do not add a new spec tier.** The
  [micro-specs pattern](https://www.augmentcode.com/guides/micro-specs-pattern-ai-agent-test-coverage)
  is already implemented here: an EARS `R-id` is an atomic single-behavior spec, the Reviewer
  already mandates a passing test per `R-id`, and `depends_on` already models the DAG. E14-F05
  had 36 working micro-specs and still produced an unreviewable PR, because nothing maps a
  micro-spec to a *deliverable*. The rule this feature adds is a **grouping** rule — a feature
  is one wave of micro-specs that can merge together — not another authoring phase. Adding
  markdown does not shrink a diff, and over-applied spec ceremony has its own documented
  failure mode ("a sledgehammer to crack a nut",
  [Böckeler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)).
- **Requirement count is the primary drill-time signal.** It is the one number available before
  any code exists, it is already the harness's unit of behavior, and it converts directly into
  cost because each `R-id` obliges a test. `R1–R36` should have read as four features on sight.
- **Selective, not universal.** The pattern's own guidance is to apply the ceremony to
  high-risk modules and skip it for "simple CRUD paths with few branching conditions". Our
  measurement agrees: 10% of PR #76's files carried 67% of its findings. A rename sweep of
  2,000 lines is not the same object as 900 lines of orchestration logic, and the rule must not
  pretend otherwise.
- **Budget in production lines, not total lines.** Tests were 59% of PR #76 and that is a
  deliberate quality choice; budgeting total lines would penalise the test discipline the
  Reviewer already enforces (a passing test per R-id). Budget the production number and let
  tests scale off it.
- **Two soft tiers, no hard wall.** A single cap is the wrong instrument: an agent-written
  change is legitimately denser than a hand-written one, and a rename sweep or a generated
  contract can be thousands of lines at near-zero review risk per line. Neither tier blocks
  anything; each produces a **recorded decision**.

  | tier | default | effect |
  |---|---|---|
  | advise | > **1,500** production lines or > **25** files | split, or record one line saying why not |
  | escalate | > **3,000** production lines or > **50** files | a recorded split plan, or an explicit override naming the reason |
  | drill-time proxy | > **12** requirements in one feature | split at decomposition, before any spec exists |

  Calibration against the 60-PR sample in that repo (median 396 additions): every PR at or
  below ~2,400 total additions converged in 1–4 rounds; the largest that converged at all was
  7,006 additions in 5 rounds; 17,202 did not converge in 12. Production lines were 36% of
  PR #76's additions, so 1,500 production ≈ 4,200 total at that repo's test ratio — the edge
  of the noisy zone — and 3,000 production sits just above the largest PR that converged.
  **These are defaults from one sample, not physics**: they live in config precisely so a repo
  with a different test ratio or risk profile can move them.
- **A rule, not a calculation.** The Driller has a brief, not a diff. The trigger must be
  something readable off the brief — requirement count, module count, "does this introduce a
  new externally-visible capability *and* a new interpretation layer" — not a line estimate
  nobody can make honestly at that altitude.
- **Split along risk, not along size.** PR #76's findings were concentrated: `runtime.ts` was
  5.4% of the diff and 33% of the findings; three files were 10% of the diff and 67% of the
  findings. A rule that splits into equal thirds would have left the dangerous third mixed in
  with the safe ones. E14-F05's natural seams were visible in its own module list — tool
  plumbing / read-only tools / natural-language interpretation / the one committing tool — and
  the first two would have merged in a single round each.

## Constraints
- **Config, not prompt, for the numbers.** A per-repo budget hard-coded in `agents/driller.md`
  is a harness-OWNED file: a target that tuned it would have the edit clobbered on every
  upgrade. New keys go in `harness.config.yaml`; the prompt reads them.
- **Absent block ⇒ documented default.** A target on an older config must behave as if the
  defaults were written, exactly as `telemetry:` and `pr_loop:` already do.
- The rule must be advisory-with-teeth, not a hard refusal: the Driller records *why* it split
  or why it deliberately did not, so the decision is auditable in the epic's `epic.md`.
- Do not weaken the existing Driller boundaries: it still **never specs**, still seeds under
  the board lock via `tools/tasks-lock.py`, still allocates ids strictly above the current max
  and never reuses a vacated `F##`.
- Any new installer-visible config key must be generated by `harness-install.sh` **and**
  asserted in `tests/test_install.sh` — the recurring gap that has been P1'd before.
- Do not freeze an exact VERSION or diff DO-NOT-TOUCH files against `main` in any test added to
  `verification.test_command` (permanent-suite anti-pattern, has recurred 3×).

## Open questions
- Whether the Architect's over-budget response should be a hard `blocked` back to the
  Orchestrator (forcing a re-drill) or a spec that ships with an explicit, recorded override.
  A hard block is more honest but strands work when the human genuinely wants the big unit;
  the recorded override is assumed unless the Architect's own boundary argues otherwise.
- The right requirement-count threshold. `>10` is inferred from one data point (R1–R36 failed
  badly) and the repo's own median PR (396 additions, 1–2 rounds); it wants a second look
  against the harness's own merged features before being pinned.
- Whether "new top-level module count" is expressible at drill time in a repo whose module
  layout the Driller has not read.
