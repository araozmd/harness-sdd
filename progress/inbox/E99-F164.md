# Fix — check the executable bit on every source script, not just one

## Problem
E99-F161 dropped `harness-install.sh` from mode `100755` to `100644` in a commit, and
**all 47 suites stayed green**. The documented invocation `./harness-install.sh`
(`README.md:304`, `:322-325`, `docs/UMBRELLA.md:33,147,158,221,253`) failed with
`Permission denied` while every test reported success, because every test invokes
`sh "$SRC/harness-install.sh"` and never execs it.

That round added `test_harness_install_is_executable` (`tests/test_install.sh:38`), which
closes the **instance**, not the **class**. The E99-F161 round-2 Reviewer proved the gap
still exists: `chmod -x tools/fix-worktree.sh` leaves **all 47 suites green** while
`./tools/fix-worktree.sh` is `Permission denied`.

The twelve existing `[ -x "$T/.harness/…" ]` assertions do not help — `harness-install.sh:3655-3668`
explicitly `chmod +x`'s each installed copy, so those assert the installer's own chmod, not
a source mode that a commit can silently drop.

## Intended fix
Assert the source executable bit for every script the repo expects to be run directly,
driven from a list rather than one hand-written case per file, so a newly added script is
covered without anyone remembering to add an assertion.

Derive the set rather than hardcoding it if you can — e.g. every tracked `*.sh` that
carries a shebang and is documented as invoked with a leading `./`. If deriving proves
unreliable, an explicit list is acceptable, but then add an assertion that the list itself
is complete (e.g. every tracked `*.sh` with a shebang is either listed or explicitly
exempted), so the list cannot silently rot — that rot is the same failure shape this row
exists to close.

Note `git` tracks the bit, so `git ls-files -s <path>` (mode `100755`) is the reliable
check; a filesystem `[ -x ]` can disagree after a fresh clone with an odd umask.

## How to verify
- `chmod -x` on each covered script in turn — **one at a time**, not batched — must fail
  the suite with a message naming that file. Batching proves only that one path is pinned;
  it is what got E99-F159 and E99-F160 each rejected once.
- Specifically: `tools/fix-worktree.sh` must now fail (today it does not).
- `harness-install.sh` must still fail (do not regress E99-F161's guard).
- A script that is genuinely not meant to be executed directly must not be forced to +x —
  say in a comment how the distinction is drawn.
- `./init.sh` exits 0; `./tools/run-tests.sh` green, run with `TMPDIR` on a disk-backed
  path (`/tmp` here is a shared tmpfs that has aborted full runs with `Disk quota exceeded`).
