# Intent — Inception role + /sdd-new intake

## Problem / who
Nothing in the harness owns the step *before* `pending`. The Orchestrator loop
starts at "Read state" (`agents/orchestrator.md`), presuming `state/tasks.json` is
already populated; the whole state machine in `docs/WORKFLOW.md` begins at
`pending`. So getting a raw idea into the TaskStore is a manual hand-edit where the
human personally does triage (epic / feature / task), allocates `E##-F##` ids,
wires `depends_on`, sets `sdd`/`autonomous`, and captures enough intent for the
Architect to start from. That step is unstaffed, fiddly, and error-prone.

The user is the human seeding work — typically the repo owner with a half-formed
idea who isn't yet sure whether it's a new epic, a new feature, or just another task
on something already in flight.

## Success outcome
A human runs `/sdd-new "<idea>"`, answers a short adaptive set of questions
(optionally picking among 1–3 text-mockup options where the shape is forked), and
ends with:
1. a valid, schema-passing `pending` entry in `state/tasks.json`, and
2. an intent brief at `progress/inbox/<id>.md`.

Then `/sdd-next` works **unchanged** — it spawns the Architect, which specs from the
brief, then the normal human gate applies.

## Scope / boundaries
- Inception **seeds, never specs**: it must not write `.spec/.plan/.tasks/.tests`
  (no EARS, no plan) and must not set any status past `pending`.
- Triage altitude into exactly one of: new task on an existing (not-`done`) feature
  / new feature under an existing epic / new epic (creates `epic.md` + first `F01`).
- Interactive, human-facing — the only such role. Interactivity lives in the
  `/sdd-new` slash wrapper; `agents/inception.md` is the portable role contract.

## Chosen options (decided during intake)
- **Handoff via `progress/inbox/<id>.md` brief**, not a 5th spec file — keeps one
  writer per file and matches the "hand off through files in `progress/`" rule.
- **Text/markdown mockups only** — no image generation (honors `AGENTS.md` rule 5,
  stays portable).
- **`/sdd-new` is interactive-only for v1.**

## Constraints
- No change to `store/tasks.schema.json`, no new status, no change to the
  Orchestrator or Architect contracts. The only structural addition is the
  `progress/inbox/` brief file type.
- Re-validate `state/tasks.json` against the schema after writing.
- Merging this feature warrants a **MINOR** `VERSION` bump (✨) — it touches
  `agents/` and `.claude/` glue (repo versioning policy in `CLAUDE.md`).

## Open questions for the Architect
- Should `/sdd-new` later support a non-interactive `--from-file` (batch-seed many
  ideas at once) mode? **Deferred for v1 — interactive-only.** Flagging here so the
  spec can leave room for it without building it.
- Id allocation when ids are non-contiguous (e.g. a deleted epic leaves a gap):
  next sequential vs. fill-the-gap? Lean next-sequential to avoid reuse confusion.
