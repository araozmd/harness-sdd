# Intent — one choke point for every spec/epic filesystem read

## Problem / who

`tools/validate-board.py`'s containment rule — "a path the board names must resolve inside
this repository" — was reported by Codex **four times, at four different read sites**, across
four consecutive review rounds of PR #124:

| round | site | fix |
|---|---|---|
| 2 | `spec_path` itself, absolute or containing `..` | `_resolve_under_root` |
| 3 | the spec **directory**, via symlink | `realpath` on both sides |
| 4 | the matched **`*.spec.md`**, via symlink | per-file `_contains` check |
| 5 | **`epic.md`, via a symlinked `specs/epics/<id>-*` directory** | **still open** |

Every fix was correct. Every fix was a patch at one site. The fourth site is still open, and
the pattern says a fifth exists: **there is no structural reason a new read site would come
with a containment check**, so each one is found by review rather than prevented by design.

This is the harness's own stated lesson — *"two findings on one function means rewrite the
rule, not patch it a third time"* — arriving for the fourth time on the same function.

**Reproduced, and confirmed to actually read the external file:** with
`specs/epics/E1-one -> /tmp/outside`, the validator returned `0`; flipping the *external*
`epic.md`'s status changed the verdict, proving the gate reads and trusts a document outside
the repository.

## Success outcome

Every filesystem read of a spec or epic document in `spec_consistency_errors` goes through
**one** helper that resolves the path, containment-checks it against the harness root, and
only then opens it. Adding a new read site without containment should be difficult to do by
accident — ideally impossible without deleting the helper. The `epic.md` site is closed as
part of this, and the four existing per-site checks collapse into the one rule.

## Scope / boundaries

**In scope**
- A single resolve-then-contain-then-read entry point, used by the feature-spec path, the
  `epic.md` path, and the writer in `tools/tasks-lock.py` (which grew its own copy of the
  same check in round 4).
- Closing Codex #3741652119 (`epic.md` containment).
- Keeping every message the existing R-ids assert: the gate's diagnostics are pinned by
  R17/R25 precisely because an operator acts on the message.

**Out of scope**
- Any change to WHAT is contained (root, not `specs/` — settled in E99-F14 round 2, and the
  reasoning is recorded in `_resolve_under_root`'s docstring).
- The status/ownership/ambiguity rules. This is about where a read may land, nothing else.

## Constraints

- `init.sh` is a MANDATORY gate: a refactor that changes acceptance in either direction is a
  regression. The 28 R-ids in `tests/test_board_spec_consistency.sh` must pass **unchanged**
  — if a test needs editing, that is a behaviour change and needs saying out loud.
- POSIX sh / `dash`; green under `sh tools/run-tests.sh`.

## Open questions

- Should the helper return an opened handle (making "read without checking" impossible) or a
  checked path (simpler, but still skippable)? The first is the stronger guarantee; weigh it
  against how much of the validator has to change to accept it.
- `tasks-lock.py` writes as well as reads. Does one helper serve both, or does the writer
  need its own write-side twin?
