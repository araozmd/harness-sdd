# Intent — The stacked-PR lane: doctrine, seams, and role contracts

## Why this exists

E21-F04 was seeded as a "stacked-PR lane for an atomic feature", built, and **withdrawn during
review of PR #78** because its premise was false: a stack enforces merge *order*, it does not
make waves land together, so it never delivered the atomicity it claimed. Four `@codex review`
rounds produced five blocking findings, **all five on that feature's surface**, each largely
created by the previous round's fix.

At the re-spec the human gate chose lane **(a)**: stacking is a **review-size tool** for work
that is *already safely splittable*. Specced completely at that scope the feature came to
**19 R-ids** against `change_size.max_requirements: 12`, so the Architect stopped and reported
the seams — E21-F01's own rule applied to E21-F01's own epic.

The seam is the one the review history handed us. The salvaged guard was *independently sound*;
every blocking finding landed on the **claim/doctrine** surface. So the mechanism ships first
and alone (E21-F04), and this feature carries the doctrine behind it.

## Problem / who

E21-F04 makes `/sdd-pr-loop` *safe* against a non-default base. It does not tell anyone when to
use one, how to cut a stack, who creates the increments, or what the board shows while a stack
is in flight. Without that, the mechanism has no callers and the harness has no lane.

## Success outcome

A Builder handed a large-but-safely-splittable feature can grow a reviewed stack, and every
role contract says the same thing about it. A reader of `docs/WORKFLOW.md` can tell — without
reading any code — what stacking buys, what it does **not** buy, and when not to reach for it.

## Scope / boundaries

**In scope**
- **The doctrine**, stated plainly: stacking delivers incremental **review**, never atomic
  delivery. Merging increment A publishes wave 1 to the default branch while B and C are open.
- **The entry condition**: every increment must be independently safe on the default branch and
  must pass `verification.test_command` on its own. A feature that cannot meet this is not a
  candidate — say so and stop.
- **The unsafely-intermediate case named as NOT SERVED**, pointing at feature flags or an
  aggregate landing strategy, and recorded as an open problem this epic does not solve.
- **Seams**: where to cut, reusing E21-F01's wave boundaries rather than inventing a second rule.
- **Role contracts**: the Builder grows the stack one increment at a time; base-setting and
  merge order; the manual restack procedure when a parent takes review fixes after a child
  exists; recovery from a manual retarget.
- **`done` rollup semantics** and the board representation decision (below).

**Out of scope**
- The guard and the loop's merge gate — E21-F04, which must be merged first.
- Atomic delivery. Still unsolved, still not seeded.
- Automating the split of an existing branch; any third-party stacked-PR tool.
- A `state/tasks.json` schema change (see the decision below).

## Decisions already taken — carry them, do not re-derive them

1. **The stack is GROWN, not created up front.** `agents/builder.md` already mandates working
   the tasks in order, one at a time; emitting N branches up front contradicts the Builder's own
   loop and requires knowing every seam before any code exists — while the epic's own
   measurement says risk structure only becomes visible once the code is. Growing also degrades
   gracefully (if wave 2 turns out not to warrant its own PR, you simply do not open one) and
   captures nearly all the wall-clock win: increment 1 is in review while increment 3 is still
   being written.
   **The cost is real and must be documented, not hidden**: each new increment branches off the
   *current tip* of its parent, so a parent that takes review fixes after a child exists needs a
   **manual restack**. That is why this feature owns an explicit restack requirement.
2. **`done` rolls only when the LAST increment merges; no per-increment `done` records.** Under
   lane (a) the *safety* argument for holding evaporates — each wave is independently safe — but
   the *bookkeeping* argument survives and is stronger: the board's unit is the feature and
   `state/tasks.json` has nowhere to record "increment 2 of 3". The feature stays `in-review`
   while any increment PR is open.
   This needs **no new mechanism**: `agents/orchestrator.md` and `store/local.md` already carry
   the `done-but-unmerged` vocabulary and already gate a dependent on `done` **and** `merged`,
   and `AGENTS.md`'s wait-for-merge rule then delivers the sequencing for free — *provided*
   `done` is not rolled early. So this is one contract sentence, not code.
   Note the reasoning, because the withdrawn brief got the right answer for the wrong reason: it
   said the rollup should wait *because the feature is atomic*. It is not. The real reason is
   board granularity.
3. **The board does NOT represent a stack; the decision is recorded and the schema change is
   deferred.** Weighed explicitly:
   - `slices[]` **cannot** be reused. Its `id` pattern is `<feature>@<repo>` and `repo` is a
     **required** property; a same-repo increment has no repo to name, so reuse means a fake
     repo token or relaxing a required field — and both corrupt the umbrella coordinator's
     select/gate/observe-merge loop, which keys off exactly `repo`, `status`, `merged`, `pr`.
   - A new optional `increments[]` is schema-**additive** (MINOR — existing stores stay valid),
     but not cheap: `store/tasks.schema.json`, `store/local.md`, the obsidian and jira adapters,
     `tools/sync-board.mjs` and `tools/next-task.mjs` all learn a second ordering vocabulary
     duplicating ~80% of `slices[]`. Selection is *code* now (ADR-0001), so this lands inside the
     harness's most bug-prone surface — the one that ADR exists to protect.
   - The lane is correct without it. Ordering already exists in GitHub as `baseRefName`, and the
     guard derives the whole order from two JSON files, offline. A board representation is
     convenience, not correctness.

   Record: "the board sees one feature; the stack lives in `baseRefName`", plus a pointer that
   increment tracking, if ever wanted, is `increments[]` and is its own feature.

## Constraints

- **Cross-file consistency is the whole risk here.** This feature edits `docs/WORKFLOW.md`,
  `agents/builder.md` and `agents/orchestrator.md`. The Reviewer has a cross-file consistency
  rule; a doctrine sentence that disagrees between two role files is a review finding, and
  drift between a role file and its `.claude/agents/` mirror is another.
- **No atomicity language anywhere**, in any file, in any commit message. This is the specific
  defect that got the predecessor withdrawn.
- `change_size.max_requirements: 12`. Scoped to **10 R-ids**. If it grows past 12, stop and
  report.
- Do not freeze an exact `VERSION` string, and do not diff DO-NOT-TOUCH files against `main`,
  in any test added to `verification.test_command`.
- Must stay inert when `pr_loop.enabled: false`.

## Open questions

- How a doctrine statement in `docs/WORKFLOW.md` is asserted by a test at all. The repo's suites
  assert agent-file and command-file *content* in places; decide whether the entry condition and
  the not-served statement get greppable assertions or are prose-only, and say which and why. A
  prose-only guarantee is how the false atomicity claim survived four review rounds.
