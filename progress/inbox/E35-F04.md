# Intent — pi environment preflight + approval-gated pinned `pi-subagents` install

## Problem / who
pi silently skips untrusted project resources; the sub-agent backend is a 0.x community
package; pi's own example `subagent` extension conflicts with it. The user asked the
installer to "validate the PI installation and install the plugins needed, with the right
approval".

## Success outcome
When `pi` is selected the installer prints a preflight report and, only with approval,
installs the pinned backend.

## Scope / boundaries
In scope:
- Read-only preflight (always, when pi selected): `pi` on PATH; `pi --version` ≥ floor
  (1.0.0; pi-subagents 0.78.0 is the first to work on 1.2.0); target trust state
  (`~/.pi/agent/trust.json` closest canonical-path entry; report `-a`/`/trust` fix);
  `pi list` contains the pinned `npm:pi-subagents@<pin>` (project or user scope);
  conflict detection for `~/.pi/agent/extensions/subagent/` (pi example extension, incl.
  broken symlinks) — report, never modify.
- Approval-gated install: flag `--pi-deps=check|install|skip` (default `check`); on an
  interactive TTY with `check`, ask y/N; `install` = explicit approval;
  non-interactive without `install` → print the exact command and continue (never fail
  the install). Install = `pi install -l npm:pi-subagents@<PIN>` in the target
  (`.pi/settings.json`). Pin is one installer constant (0.78.0).
- Optional post-install verification that `pi list` now shows the pin.
- Docs (INSTALL.md pi section), tests with a stub `pi` binary (no network).
Out of scope: editing `~/.pi/agent`, installing pi itself, MCP/Playwright config.

## Constraints
- Never install without approval; never fail the harness install because of pi
  environment problems (warn-only), except when the user passed `install` and it failed.
- Respect HARNESS_* non-interactive conventions already in the installer.
