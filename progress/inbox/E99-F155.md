# Intent — a STALE dependency cycle strands a feature forever

## Problem / who

`featureBlockers()` records a `dependency-cycle` blocker whenever the feature appears in a
cycle, **regardless of whether anything is actually unmet**:

```js
if (cycles.has(feature.id)) records.push({ subject: feature.id, code: 'dependency-cycle', … });
```

A pending F1 that depends on a done F2 which still lists F1 in its own `depends_on` is a
cycle in the graph, but not a wait: F1's documented `depends_on` gate is satisfied. It
still fails `ordinary.length === 0` and becomes **unselectable forever**. `slicePhase()`
carries the same defect at its selection guard (`!cycles.has(slice.id) && unmet.length === 0`)
for a pending slice whose cyclic counterpart is already done **and merged**.

Who it bites: any long-lived board where a feature was re-scoped and the back-edge was
never cleaned up. It is not hypothetical — it is why the cuestiona board had a feature no
`/sdd-next` run would ever offer, and the operator's only signal was
`selection-blocked / dependency-cycle` on work whose prerequisites were all green.

The back-edge is stale bookkeeping, not work that can never start. The harness already has
a place to say so: `init.sh` sweeps cycles **warn-only** on every run.

## Intended fix

Emit the cycle record only when the cycle leaves a genuinely unmet dependency; otherwise
select the feature/slice. Three sites, all in `tools/next-task.mjs`:

1. `featureBlockers()` — compute `unmet` **before** the cycle check, and gate the push on
   `unmet.length`. Record ordering must not change: `dependency-cycle` still precedes
   `unmet-dependency` in blocked output.
2. `slicePhase()` selection guard — drop the `!cycles.has(slice.id)` conjunct; `unmet` is
   already the whole question.
3. `slicePhase()` blocked records — same gating as (1), with `unmet` hoisted above it.

The cycle itself stays visible through `init.sh`'s existing warn-only sweep. Nothing is
suppressed; a cycle that still blocks still reports.

## How to verify

`tests/test_next_task.sh` gains a **stale-cycle fixture** — pending F1 → done F2 → F1 —
and asserts F1 is now selected with `route architect` instead of reporting
`selection-blocked`. Paired with a **live-cycle control** that must still report
`dependency-cycle`: "the blocker disappeared" is the easy outcome to produce, and a suite
without the pairing passes against a selector that simply stopped reporting cycles.

Add the slice-level pair too (a pending slice whose cyclic counterpart is `done` **and**
`merged: true` selects; one whose counterpart is unmerged still blocks) — `merged` is the
extra conjunct on the slice path and a fix that ignores it would pass a feature-only suite.

Assert the blocked-record **order** in the live-cycle control, or hoisting `unmet` above
the cycle push can silently reorder output that operators read top-down.

## Mutations the suite must kill

- Restore `if (cycles.has(feature.id))` unconditionally → the stale-cycle case must fail.
- Drop the `&& unmet.length` guard only in `slicePhase()` → the slice pair must fail
  (proves the fix is not asserted at one site and assumed at the other).
- Swap the two record pushes → the ordering assertion must fail.
- Make the slice guard ignore `merged` → the unmerged-counterpart control must fail.

## Trap

Do not "fix" this by deleting the cycle record. A cycle that leaves a real unmet
dependency is exactly the diagnostic this code exists to print, and a selector that
reports nothing is worse than one that over-reports.
