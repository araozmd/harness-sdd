# Intent — Suite flakes: test_feature_park R7 control and test_mirror

## Problem / who
Two suites make `sh tools/run-tests.sh --jobs 16` red for reasons that have nothing to
do with the branch under test. Every maintainer and Reviewer then has to re-run them and
argue they are "environmental".

1. **`tests/test_feature_park.sh` R7 control (~lines 301-320).** It picks the FIRST
   feature on the LIVE `state/tasks.json` that has a `parked` key, then asserts that a
   targeted selection's output contains the word `parked`. A park written by
   `tasks-lock.py await-merge` (`parked.gate == "merge"`) is reported by the selector as
   `awaiting-merge` / "awaiting merge", which never contains `parked`. So whenever an
   await-merge park sorts first in board order, the suite fails. That happened on the
   E35-F05 branch (PR #271): the failure was "R7 control: live board feature E35-F05 is
   parked but a targeted selection emitted no park output". It passes today only because
   E99-F145 (an ordinary park) sorts first.
2. **`tests/test_mirror.sh`** failed twice under `--jobs 16` this session, on 2026-10-17:
   during PR #271 and during PR #276. It passed both times when run alone.
   `test_frontend_retirement.sh` failed once the same way. Nobody has investigated the
   cause yet.

## Success outcome
- R7's control is deterministic regardless of which parks the live board holds.
- `test_mirror.sh` passes reliably under `--jobs 16`.
- If test_frontend_retirement shares the root cause, it is fixed too.

## Scope / boundaries
R7 control: choose the control row explicitly.
- Either select only parks that are NOT `gate: "merge"`,
- or accept the selector's park vocabulary (both `parked` and `awaiting-merge`).
Prefer building a SYNTHETIC board that carries one ordinary park, over depending on the
live board at all, if the control's purpose ("the selector does emit park output") still
holds. Keep the mutation-sensitivity the existing comments describe: the derived-vs-live
pair must still tell its inputs apart.

test_mirror:
- Reproduce the flake. Loop it under parallel load, e.g. run the full suite with
  `--jobs 16` several times, or run test_mirror alongside CPU/IO-heavy suites.
- Find the root cause: a shared temp path, a fixed port or name, a timing assumption, a
  dependency on cwd or TMPDIR, or a race with another suite on shared state.
- Fix that cause. Do not add retries or longer sleeps unless the root cause genuinely
  is a timing bound, and if so, say so.
- Do the same for test_frontend_retirement if it reproduces.

Out of scope: unrelated suites.
