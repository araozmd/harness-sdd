# Intent — `/sdd-fix` lightweight lane (maintenance epic, brief-only intake)

## Problem / who
For the harness maintainer and every consumer repo: the SDD loop is built for
features — `/sdd-new` (or `/sdd-plan` → `/sdd-drill`) → Architect 4-file spec →
human gate → Builder → Reviewer. That ceremony is right for net-new capability but
far too heavy for a one-line bug or a hotfix. Today a small fix either gets
over-specified (a full 4-file spec for a typo) or smuggled in outside the harness
entirely (no record, no review). There is no **lightweight lane** that keeps minor
fixes inside the harness — recorded and reviewed — without the spec/drill overhead.

The planning tier (F01–F03) is now complete, so this is the last piece of epic E06:
a fast path for maintenance work.

## Success outcome
`/sdd-fix "<short description>"` seeds and runs a minor fix with **no 4-file spec and
no drill-down ceremony**:
- The fix is recorded as a feature with **`sdd: false`** under a single reserved
  **maintenance epic**, carrying only a one-paragraph **inbox brief** (problem +
  intended fix + how to verify) — no `.spec/.plan/.tasks/.tests`.
- The existing Orchestrator routing for `sdd: false` (already: *pending + sdd:false →
  Builder directly, then Reviewer*) takes it straight to the **Builder**, who
  implements from the brief, and then the **Reviewer**, who verifies the fix and its
  test(s) behaviourally (there are no R-ids to trace for a non-SDD item).
- The maintenance epic is **never a `draft`** epic (its fixes must be selectable) and
  groups all such fixes in one place, so the roadmap stays readable.
- A consumer can go from "found a small bug" to a reviewed, merged fix without ever
  opening the Architect or writing a spec.

## Scope / boundaries
**In scope:**
- New `/sdd-fix` skill: a slash command (`.claude/commands/sdd-fix.md`) over a
  **portable role contract**, mirrored into opencode, following the `/sdd-new` /
  `/sdd-plan` / `/sdd-drill` idiom (paths resolved against `.harness/` when
  installed).
- The **maintenance-epic** convention: a single reserved epic that collects
  `sdd: false` fixes; `/sdd-fix` creates it on first use if absent and reuses it
  thereafter, then appends the new fix feature (next-sequential `F##`, append-only).
- The write path: seed the `sdd: false` feature entry + a brief-only
  `progress/inbox/<id>.md` (a fix-oriented brief: problem, intended fix, verification
  — no spec dir); re-validate `state/tasks.json` against the schema; never claim
  success on a validation failure. `/sdd-fix` **seeds and may hand off to the loop**
  but writes no production code itself.
- Any **minimal** role-contract clarifications the lane needs so the existing
  Builder/Reviewer handle a brief-only `sdd: false` item cleanly (Builder works from
  the inbox brief rather than a `tasks.md`; Reviewer verifies behaviour + test
  without R-id traceability). Keep these additive — do not change the SDD path for
  `sdd: true` features.
- Installer wiring: generate `/sdd-fix` into target repos (`.claude/commands` +
  `.opencode/command` mirror) and assert it in `tests/test_install.sh` — per the
  recurring "new /sdd-* command must be installed" rule.
- Docs (`docs/WORKFLOW.md` placement of the lightweight lane alongside the full SDD
  flow; README one-liner) and one MINOR `VERSION` bump + `CHANGELOG.md`.

**Out of scope:**
- Changing the SDD path for `sdd: true` features, the Architect, the `draft`/`planned`
  gate, or `/sdd-plan` / `/sdd-drill`.
- Any new TaskStore status value or schema change for approval (reuse `sdd: false`
  and the existing `autonomous` flag).
- Triage intelligence about whether something is "minor enough" — `/sdd-fix` trusts
  the human's choice of lane (it is the explicit small-fix entry point); deciding a
  fix is actually a feature is the human's call (re-run `/sdd-new`).
- F04 (Architect ADR-citation contract) and F06 (drift check) — separate features.

## Chosen options
- **Maintenance epic, brief-only intake** (the human's pick): fixes collect as
  `sdd: false` features under one reserved maintenance epic, each with just an inbox
  brief — no 4-file spec. This matches the epic.md wording and reuses the existing
  `sdd: false → Builder` routing rather than inventing a new lane mechanism.
- **Reuse the existing `sdd: false` primitive** documented in
  `agents/orchestrator.md` + `docs/WORKFLOW.md` — no Orchestrator routing change,
  just a front-end that seeds into it.
- Additive change ⇒ MINOR bump, per repo versioning policy.

## Constraints
- **Backward compatible / additive:** `/sdd-new`, `/sdd-plan`, `/sdd-drill`,
  `/sdd-next` untouched; repos that never run `/sdd-fix` see no change. The maintenance
  epic only exists once `/sdd-fix` is used.
- **Portability pillar:** the lane's contract lives in a role file + AGENTS.md, not
  solely in `.claude/`; runs on any AGENTS.md-compatible CLI.
- **Schema:** the maintenance epic id must satisfy the existing `^E[0-9]+$` pattern
  (no special non-numeric id); its status must be a selectable (non-`draft`) value so
  `next()` returns its fixes. No schema change.
- Per the permanent-suite anti-pattern memory: new tests must not freeze the exact
  `VERSION` value or diff DO-NOT-TOUCH files against `main`; any JSON fixture includes
  the required root `project` field and uses a temp store (never mutate live
  `state/tasks.json`).
- Honor the "new /sdd-* command must be installed + asserted" rule (the installer
  gap that was a Codex P1 on F02 and pre-empted on F03).

## Open questions
- **Maintenance-epic identity:** what id/slug/title (e.g. a reserved high number like
  `E99-maintenance`, or the next-sequential epic titled "Maintenance"), and what
  **status** does it carry (`planned`? `in-progress`? `pending`?) so its fixes are
  always selectable but it reads clearly as the maintenance bucket?
- **Create-on-first-use vs pre-seed:** does `/sdd-fix` lazily create the maintenance
  epic when absent (and how does it find/identify it on subsequent runs — by id, by a
  marker field, or by title), or should the installer/init seed an empty one?
- **`autonomous` on fix features:** are `sdd: false` fixes stamped `autonomous: true`
  so they run end-to-end without a per-feature gate (fits "seeded and executed"), or
  do they still park at the human gate by default? Which is least surprising for a
  hotfix?
- **Role shape:** a new `agents/fixer.md` role, a mode of `agents/inception.md`
  (it is brief-only intake), or reuse of the Builder's existing `sdd: false` handling
  with only a thin command wrapper? (Mirror F02-D1 / F03-D1 portability reasoning.)
- **Builder-from-brief contract:** how much, if anything, must be added to
  `agents/builder.md` / `agents/reviewer.md` so a brief-only `sdd: false` item is
  handled cleanly (Builder reads the inbox brief; Reviewer verifies behaviour + test
  with no R-id traceability) — versus this already being adequately specified today.
- **Does `/sdd-fix` hand off to the loop or stop at seeding** (like `/sdd-new`)? i.e.
  does it run the fix in-session or just seed it for `/sdd-next`?
