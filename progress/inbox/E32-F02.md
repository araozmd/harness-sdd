# Intent — tools/harness-report.sh: redaction pass, versioned body marker, duplicate search, per-session cap, progress/ fallback

## Problem / who
The act of filing must be deterministic and testable, because it is automatic and privacy-sensitive; prompts decide *when*, this tool decides *how*.

## Success outcome
One tool takes a structured report (trigger type, summary, harness files, expected vs observed) and: exits 0 without filing when `feedback.enabled` is false; redacts secrets/tokens/emails/absolute paths/non-harness paths; stamps the versioned marker (ADR-0006 — this spec defines its grammar); searches open issues on `feedback.repo` and skips on a duplicate (no comment); enforces `feedback.max_per_session`; falls back to `progress/feedback/<timestamp>.md` when `gh` is missing/unauthenticated/fails. It never exits non-zero in a way that fails the caller's task.

## Scope / boundaries
In: the tool, marker grammar, PATCH `VERSION` bump, redaction corpus + fixture tests with a stubbed `gh`. Out: triggers/prompts (F03), labels (F04).

## Chosen options
- Filing is automatic, no human confirmation (user decision).
- Duplicate ⇒ no new issue, no comment.
- Fallback reports stay local, no auto-retry.

## Constraints
- Epic contract: `specs/epics/E32-feedback-loop/epic.md` (success criteria are binding).
- POSIX sh like the rest of `tools/` (or python3 stdlib — `init.sh` already requires python3).
- Never includes project source; the body lists harness-owned paths only (see `tools/harness-owned-paths.sh`).
- Tests never hit the real GitHub API.
- ADRs to honor: ADR-0006, ADR-0004.

## Open questions
- Duplicate matching key (title fingerprint vs marker fields).
- How the per-session cap is counted (session id source). Only the session-owning top-level role calls the tool (drill decision), so there are no concurrent writers.
