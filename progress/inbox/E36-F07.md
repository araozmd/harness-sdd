# Intent — `/sdd-next --wave` fans out one wave's independent autonomous features into isolated worktrees

## Problem / who
The operator wants "build in waves with sub-agents" to be harness behavior rather than a
prompt. `/sdd-fix-parallel` already runs a bounded batch of isolated autonomous E99 fixes
through targeted workers (agents/fixer.md "Parallel dispatch mode (`/sdd-fix-parallel`)",
agents/orchestrator.md "Targeted parallel-fix worker mode"), with worktree isolation,
HARNESS_DIR board writes and serialized merges. That worker mode is fenced to "one exact
autonomous E99 fix"; this feature widens the fence to sdd:true features, it does not add a
parallel lane beside it. E36-F05 computes the wave. This feature connects them for sdd:true features.

## Success outcome
- `/sdd-next --wave [--max N] [--epic E##]` computes wave 1 via `next-task.mjs --waves --json`
  (wave definition from E36-F05: done = wave 0), takes its `autonomous: true`, unparked,
  ungated features (up to `--max`, default from a new `workflow.max_wave` config key, default
  3 — not under `workers:`, which is the inert local-only roster), provisions one branch + worktree per feature, and
  runs each through the normal Orchestrator loop (Architect → Builder → Reviewer → PR) as a
  targeted worker on its own feature id, exactly as the parallel-fix lane does for fixes.
- Workers never share a worktree; board writes go through `tasks-lock.py` with `HARNESS_DIR`
  set to the worker's worktree; merges are serialized by the coordinator; a worker that
  rejects or blocks reports and leaves its feature `in-progress`/`in-review` for a later
  `/sdd-next <id>`.
- The coordinator prints a summary table: feature, branch, PR, verdict. It does not run
  `/sdd-pr-loop`; the operator runs it per PR afterwards (recorded decision, not open).
- Emitted by `harness-install.sh` into every front-end's sdd-next surface that supports
  sub-agents (claude, codex, opencode, pi), asserted in `tests/test_install.sh`; the
  coordinator prose lives in `agents/orchestrator.md` (one new section plus the amended
  E99-only guard in "Targeted parallel-fix worker mode") and reuses the Fixer dispatch rules
  by reference, not by copy. Near the size cap: the Architect should expect ~10 R-ids and
  stop and report rather than exceed 12.
- Requires `execution.builder.backend: in-session` (same precondition as fix-parallel).

## Scope / boundaries
In scope: orchestrator prose section, sdd-next emitter + flag parsing (`--wave` is a new
closed-scope token beside `--mine` and `E##-F##`), config key, installer wiring, tests with a
stub worker, docs. Out of scope: cross-machine distribution (ADR-0010 non-goal), changing
the fix lane, running wave 2 automatically (the operator re-runs after wave 1 merges).

## Chosen options
- Reuse the Fixer coordinator by reference; do not reimplement worktree provisioning
  (lesson: reimplementing a tool invites a bug per feature).

## Constraints
- Honor ADR-0001 and ADR-0010. Depends on E36-F05. New `/sdd-*` flag must be generated and
  asserted (sdd-command-installer-wiring lesson).
- Keep `max_requirements` in mind: if the spec exceeds 12 R-ids, the Architect stops and
  reports per its contract rather than specing an over-budget feature.
