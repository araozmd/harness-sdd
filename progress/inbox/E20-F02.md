# Intent — pr_loop.enabled prompt in the installer picker

## Problem / who
This is the toggle the human actually asked for: *"during the install the user is the one
who marks the pr-loop enablement."*

E18-F01 introduced `pr_loop.enabled` and made it **opt-in (default `false`)** at the
human's direction. Today turning it on is a one-line hand-edit of
`.harness/harness.config.yaml`, discoverable only by reading source comments. The
installer never asks.

This is not a preference like a theme. `/sdd-pr-loop` only functions on a repo that has
the **Codex GitHub App** installed and an authed `gh`. On any other repo the correct value
is `false`, and the human is the only one who knows which repo is which — so the question
belongs at install time, asked out loud.

## Success outcome
Installing the harness asks whether to enable the PR review loop, defaulting to off. A
human installing into a Codex-enabled repo answers once and gets `/sdd-pr-loop` stamped;
a human installing anywhere else presses Enter and grows no command that could only fail
its own preflight.

## Scope / boundaries
**In scope**
- An interactive prompt for `pr_loop.enabled`, pre-selected from the current value on a
  re-run (re-running the installer is this harness's supported reconfiguration path).
- Written through the **existing append-only, value-preserving config migration**.
- Turning it off must leave no `/sdd-pr-loop` glue stamped and no dangling instruction to
  run it — E18-F01 already implements that reconciliation (its §7b pass); this feature
  drives it from a prompt instead of a hand-edit.

**Out of scope**
- The prompt machinery itself — E20-F01 builds the picker's second-question surface and
  lands the `execution.builder.backend` toggle on it. This feature adds the second toggle
  to that existing machinery, which is why it depends on F01.
- Introducing or changing the `pr_loop` config block (E18-F01 owns it).
- Changing the opt-in default. It stays `false`.
- Any preflight change; E18-F01's fail-fast (exit 5) already covers a missing Codex App.

## Chosen options
- **Prompted at install, defaulting off** — the human's explicit instruction, and the
  reason `enabled` was flipped to opt-in in the first place.
- **Re-running the installer is the re-toggle path** — no `/sdd-config` command. Chosen
  deliberately so there are not two configuration surfaces that can diverge.

## Constraints
- **Never rewrite `harness.config.yaml` wholesale.** Use the existing append-only,
  value-preserving, idempotent migration so a human's comments and unrelated hand-edits
  survive. The file is heavily commented by design.
- **Non-interactive runs unaffected** absent an explicit override — CI keeps today's
  behavior exactly.
- Degrade like the front-end picker already does: raw-mode TUI when available, numbered
  fallback otherwise, override when non-interactive.
- Honor E18-F01's **R1**: the `sdd-pr-loop` body is generated into `CMDDIR` on every run
  even when the gate is off, because reclamation byte-compares against it. Turning the
  gate off via a prompt must not bypass that.
- Preserve the **`.sdd-pr-loop.owners` cross-target ledger** (E18-F01): a target flipping
  its own gate off must not delete a global prompt another target still owns.
- Every installer-invoking test must sandbox `CODEX_HOME`; no frozen `VERSION` literal; no
  diffing DO-NOT-TOUCH files against `main`.
- Do not use the word "drift" in `harness-install.sh` — `tests/test_drift_check.sh:259`
  is a bare `grep -qi` and will fail the chain.

## Open questions
- Whether an install that enables the loop should run E18-F01's preflight immediately and
  warn when the Codex GitHub App is absent, or stay silent and let the first
  `/sdd-pr-loop` run report it. Warning at install is friendlier; proceeding anyway is
  correct either way, since the App can be installed after the harness.
- Whether this toggle needs a flag/env twin for scripted installs. Do not add surface
  speculatively — decide from whether anything actually scripts it.
