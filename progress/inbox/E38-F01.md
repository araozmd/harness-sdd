# Intent — init.sh update check + consented upgrade with custom-config preservation preview

## Problem / who
People running an installed harness, in a single repo or in an umbrella coordinator
with children, are not told when a newer harness release ships. Upgrading means
manually pulling a separate harness-sdd clone and re-running `harness-install.sh` with
the right selection. Users also can't see before running it whether an upgrade will
overwrite their customization.

## Success outcome
`init.sh` notices that a newer release exists and offers to install it. If the human
says yes, the upgrade runs with the target's recorded selection (the same front ends,
and umbrella cascade when this is a coordinator). Before writing anything, it shows
what will be preserved and what will be replaced. Afterwards, the human can see that
their `harness.config.yaml` values and root-entrypoint content are unchanged.

## Observable behavior
CLI — `./init.sh` prints `🔔 harness vX.Y.Z available (installed vA.B.C)`. When a person
is at the terminal (interactive TTY), it then asks `Install now? [y/N]`. On `y` it
prints a preservation/conflict preview and asks again before writing. Without a TTY,
it prints only the one-line notice.

## Scope / boundaries
In scope:
- Version check in `init.sh`: compare `.harness/.harness-version` with the highest
  `vX.Y.Z` tag of the harness-sdd remote, read via `git ls-remote --tags`.
- Consented install: fetch that tag into a cache clone and run its
  `harness-install.sh`. Use the target's recorded selection. Use `--umbrella` when the
  target is an umbrella coordinator, so the upgrade cascades to its children.
- Preservation guarantees, checked before and after the write:
  - **`harness.config.yaml` values:** every existing key/value is kept. Only missing
    keys are appended, per the existing migrate path. In umbrella mode this holds for
    the coordinator and for each child, including the child's explicit overrides.
  - **Root entrypoints:** user content in CLAUDE.md / AGENTS.md outside the harness
    pointer block is byte-preserved.
- Conflict handling for harness-owned files with local edits (e.g.
  `.harness/agents/reviewer.md`, `.harness/tools/sync-board.mjs`): list them with a
  diffstat before writing, ask, and back up the originals to
  `.harness/progress/upgrade-backup/<old-version>/` before replacing them.

Out of scope:
- Auto-installing without consent.
- Committing the upgrade. E24's drift guard already requires the human to commit it,
  and the report should say so.
- Merging local edits into new upstream files (three-way merge).
- Release notes and the GitHub Releases API.
- Downgrades.

## Chosen options
- **Check point:** `init.sh` checks and prompts directly. The alternatives were a
  dedicated `/sdd-update` command, or a command with no notice.
- **Protected custom configuration:** `harness.config.yaml` values and root entrypoints
  (CLAUDE.md / AGENTS.md outside the pointer block).
- **On a conflicting local edit to a harness-owned file:** preview, then ask, then back
  up to `.harness/progress/upgrade-backup/<ver>/`. Not chosen: refusing the upgrade, or
  skipping the file.
- **Latest-version source:** GitHub tags via `git ls-remote`. Needs no gh CLI and no
  auth.

## Constraints
- Stage: production
- `init.sh` is the gate every agent runs non-interactively. The check MUST NOT block,
  prompt, or change the exit code when stdin/stdout is not a TTY, when the network is
  unreachable, or when `git ls-remote` fails or times out. In those cases it prints at
  most one informational line, and nothing at all when offline.
- The network check must be bounded: a short timeout and a cached result (e.g. at most
  once per N hours, cached under `.harness/progress/`) so `init.sh` stays fast.
- There must be an opt-out: an env var per invocation (e.g. `HARNESS_SKIP_UPDATE_CHECK=1`)
  and/or a config key, consistent with the E24 rationale for env-var overrides.
- Skip the check silently in the harness source repo itself (no `.harness-version`
  stamp, or `--self` layout), the same way the E24 drift guard does.
- Reuse the existing installer paths. Do not reimplement them: the config migration
  path, pointer-block replacement, recorded agent selection, and the umbrella cascade
  (memory: reimplementing a tool means a bug per feature).
- Never write outside `.harness/` + the glue the installer already owns. Backups go under
  `.harness/progress/`, which is kept out of the consumer's VCS (E99-F06).
- Any new installer flag/command must be generated by `harness-install.sh` and asserted
  in `tests/test_install.sh` (installer-wiring convention). Bump VERSION as a MINOR,
  because the installed body changes.
- Tests must not freeze an exact VERSION or diff DO-NOT-TOUCH files against main
  (permanent-suite anti-pattern). Network access in tests must be stubbed (a fake remote
  or a `git ls-remote` shim).

## Open questions
- Where does the remote URL come from: hard-coded `github.com/araozmd/harness-sdd`, a
  config key (e.g. `update.remote`), or a value recorded in the install manifest? Forks
  such as the cuestiona-specs upstream would need the config key or the manifest.
- Cache TTL and its location, and whether a declined version is remembered so the user
  isn't asked again every run.
- In an umbrella child, should `init.sh` check at all, or defer to the coordinator, so
  that children are not upgraded independently of the cascade?
- What exactly counts as a "local edit" to a harness-owned file: a mismatch against the
  install manifest's recorded hashes for the installed version, or against the tag's
  content?
- Should the check/upgrade logic live in a new `tools/harness-update.sh` that `init.sh`
  calls, to keep `init.sh` lean?
- Whether F01 should be split, e.g. (a) notice + check, (b) consented upgrade +
  preservation proof, (c) umbrella cascade verification.
