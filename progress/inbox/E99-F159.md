# Fix — add a `frontier` model tier so Fable is expressible

## Problem
The Claude tier table in `model_alias()` (`harness-install.sh:1831-1838`) knows exactly
three tiers — `reasoning`→`opus`, `standard`→`sonnet`, `cheap`→`haiku`. The string `fable`
appears **nowhere** in the installer, yet `claude --help` documents it as a first-class
floating alias beside the other two: "Provide an alias for the latest model (e.g. 'fable',
'opus', or 'sonnet')". So the harness cannot route any role to Anthropic's most capable
model through its own vocabulary.

The escape hatch does not close the gap, because **`pin.<front-end>.<tier>` is keyed by
TIER, not by role** (`harness-install.sh:1861`). `architect` and `builder-heavy` both map
to `reasoning`, so a `pin.claude.reasoning: fable` hits both — there is no way to express
"architect = Fable, builder-heavy = Opus". With Fable there are now four useful Claude
capability levels and only three tier names.

This is a vocabulary gap, not a ranking question: the harness deliberately has no model
list and no ordering semantics (`harness-install.sh:479-481` — "WHAT THIS DOES NOT CHECK:
that the model is STRONGER... Ranking is yours"). A fourth tier is a fourth *name*.

## Intended fix
Add a `frontier` tier that resolves to the **floating** `fable` alias, preserving the
table's stated rule that every entry is "a FLOATING vendor alias, never a version-pinned
model id" (`harness-install.sh:1824-1826`) so a new Fable release is picked up with no
harness change. Then thread the new name through every place the tier vocabulary is
enumerated, so no reader or warning is left listing three tiers:

- `model_alias()` — add `claude:frontier) printf 'fable\n'`. `codex` and `opencode` get no
  entry, exactly as for the other tiers; an unpinned `frontier` stamps nothing there and
  the existing `pin.<front-end>.frontier` escape hatch covers them with no extra code.
- The known-tiers text in both `_model_tier_resolve` warnings (`harness-install.sh:1787`
  and `:1801`) — currently "known tiers: reasoning standard cheap inherit".
- The `# Tiers:` line in the `models:` seed block that the installer appends
  (`harness-install.sh:271`) **and** its byte-identical twin in the shipped
  `harness.config.yaml:227`. These two must stay identical — the block's own comment
  requires a fresh install and an upgraded install to converge on the same text.
- `docs/INSTALL.md:724` — "**Tier vocabulary: `reasoning | standard | cheap | inherit`.**"

## How to verify
- `./init.sh` exits 0.
- `tests/test_model_routing.sh` passes, extended with `frontier` cases: a role set to
  `frontier` stamps `model: fable` on a Claude shim; the same role stamps **no** model key
  on codex/opencode without a pin, and stamps the pinned value with
  `pin.codex.frontier` / `pin.opencode.frontier` set.
- A role set to an unknown tier still warns and falls back to `inherit`, and the warning
  text now lists four tiers.
- `tests/test_escalation.sh` still passes: `architect: frontier` + `builder-heavy:
  reasoning` must read as two different models, and `builder: standard` +
  `builder-heavy: frontier` must arm (`raise`).
- Grep the repo for `reasoning | standard | cheap` and `reasoning standard cheap` — no hit
  may still enumerate only three tiers.
- The seeded `models:` block in a fresh install and the migrated block in an upgraded
  install remain byte-identical to each other.

## Files expected to change
- harness-install.sh
- harness.config.yaml

- tests/test_model_routing.sh

## Notes
Purely additive: every existing tier keeps its current mapping, `inherit` still compiles
to key omission, and a config that never says `frontier` produces byte-identical output to
today. No new config key — `frontier` is a value in the existing `models:` vocabulary, so
the ablation doctrine's "never accrete an option" is respected.

Assigning roles to the new tier is deliberately **not** part of this fix; it is a config
choice made per target afterwards.
