# Intent — OpenCode 2.x: tighten the opencode pin guard; record 2.x host markers

## Problem / who
These are two follow-ups that the E31-F03 spec left as open questions
(specs/epics/E31-opencode-first-class/F03-opencode-2x-compat/E31-F03.spec.md ~205-216).
Both affect operators who run OpenCode 2.x.

1. **Pin guard too loose.** `harness-install.sh` (~2010-2021) accepts an OpenCode pin
   (`models.pin.opencode.<tier>`) whenever it matches `*/*`. OpenCode 2.x treats `#` as a
   variant separator, and it DROPS a `model` value that does not match
   `^[^/#]+/[^#]+$`. The only trace is a "configuration normalization diagnostic" in its
   log. So values like `a/b#c`, `/model`, `provider/` and `a#x/b` pass our guard and are
   stamped into opencode.json, but 2.x then ignores them silently. The operator believes
   a pin is in effect when it is not.
2. **Host-marker provenance has no 2.x observation.** The `HOST_MARKERS` provenance
   (~1716-1735) records only opencode 1.18.5 (`OPENCODE`, `OPENCODE_PID`).
   - 2.x no longer sets `OPENCODE_PID`.
   - Detection still works, because a row matches when ANY of its variables is set and
     2.x keeps `OPENCODE=1`.
   - Until now that was static evidence only.
   - Commands run from the session's user shell (opencode's `!`) get only
     `OPENCODE_TERMINAL=1`, so 2.x goes undetected there today.

## Evidence (observed 2026-10-19 by the Orchestrator, opencode 2.0.32, live)
Setup:
- Isolated HOME and XDG_* in the scratchpad.
- Every OPENCODE*, CLAUDE*, AGENT, AI_AGENT and *_API_KEY variable stripped from the
  launch env.
- A foreground `opencode serve` on 127.0.0.1, killed afterwards.
- A **local stub OpenAI-compatible model** on 127.0.0.1. Isolated config:
  `provider.stub` using `@ai-sdk/openai-compatible`, with `model: stub/m`. No external
  model was called.

Driven through `opencode api --server … POST /api/session/{id}/prompt`, the stub returned
one call to the 2.x shell tool (named `shell`; the offered tools were edit, glob, grep,
question, read, shell, skill, subagent, webfetch, websearch, write, execute), which ran
`env > env-tool.out`.

Variables the agent shell tool added relative to the launch env (`comm -13`):

    AGENT=1  AI_AGENT=opencode  OPENCODE=1  OPENCODE_SESSION_ID=ses_…  OPENCODE_TERMINAL=1

(`NODE_PATH` also appeared; it comes from the mise shim, not opencode.)

Through the user-shell endpoint (`POST /api/session/{id}/shell`, the `!` path, no model
involved), the only variable added was `OPENCODE_TERMINAL=1`.

`OPENCODE_PID` was in neither.

The binary's source agrees:
- the agent shell tool runs `env.AGENT="1", env.OPENCODE="1", env.AI_AGENT||="opencode",
  env.OPENCODE_SESSION_ID=<sessionID>`;
- Shell.create and Pty.create add `OPENCODE_TERMINAL:"1"`.

## Success outcome
- **Pin guard.**
  - The guard accepts an opencode pin only if it matches `^[^/#]+/[^#]+$`; anything else
    goes through the existing warn-once-and-skip path.
  - The warning names the reason, extending the existing `provider/model` wording so it
    mentions that `#` is not allowed. Keep the value-echo rules as they are.
  - Valid pins already in use are unchanged.
- **HOST_MARKERS.**
  - The opencode provenance entry records the 2.0.32 observation above: the agent shell
    tool and the `!` user shell, the date, and the method (isolated serve plus a local
    stub model).
  - The row is decided on that evidence:
    - Keep `OPENCODE`.
    - Keep `OPENCODE_PID` for 1.x.
    - Add `OPENCODE_SESSION_ID`: it names the session and is present in the default
      mode.
    - Decide on `OPENCODE_TERMINAL` with a recorded reason. It would make `!sh
      harness-install.sh` from the 2.x TUI detectable. Check it against the rules
      (~1689-1708): it is a session-injected flag, not config or credentials, and it is
      absent from a plain shell.
  - REJECTED CANDIDATES: `AGENT` and `AI_AGENT` stay rejected (already listed).
  - tests/test_agents_host.sh's provenance-parsing guard stays green.
- **Tests.**
  - The pin guard has a row per rejected shape: `a/b#c`, `a#x/b`, `/m`, `p/`, plus a
    still-accepted control such as `anthropic/claude-x`. Each row kills its mutant, for
    example restoring `*/*`.
  - Each new HOST_MARKERS variable gets a detection row in test_agents_host.sh, and the
    "ambiguous with CLAUDECODE" behaviour is still covered.

## Scope / boundaries
In scope: harness-install.sh (the pin guard plus the HOST_MARKERS row and provenance),
docs/INSTALL.md (the provider/model wording around ~1164-1180 and ~1262), the tests,
VERSION and CHANGELOG.

Out of scope:
- any change to how pins are read from harness.config.yaml (see the config-reader quirk
  in docs/INSTALL.md ~1087);
- the other front-ends' guards;
- any live 2.x run inside the test suite. Tests use the table and stubs; CI has no
  opencode.

## Chosen options
- Mirror 2.x's own acceptance regex rather than inventing a stricter one.
- Keep the 1.x marker, `OPENCODE_PID`, because 1.x is still supported.

## Constraints
- **Reachability.** Check whether `#` can reach `_rm_pin` at all. docs/INSTALL.md says a
  `#` in harness.config.yaml starts a comment even inside quotes, so `a/b#c` may never
  reach the guard from config.
  - If `#` cannot reach it, the `#` part is defence in depth. Document it honestly as
    such, with no claim that a test pins a path that can't happen.
  - `/m` and `p/` ARE reachable, and they pin the tightened guard.
  - Also check any env override path for pins.
- The installed body changes, so bump VERSION to the PATCH release 0.97.1 and add a
  CHANGELOG entry.
- Fail closed: an invalid pin stamps no model key, and the install never fails because of
  it.
- Regenerate the glue with `sh harness-install.sh --self` only if an emitter changed.
  Never hand-edit .claude/, .agents/ or .opencode/.
- Never run a mutating `pi`. Never touch ~/.pi/agent or ~/.config/opencode. Never call a
  real model.
- Each guard and marker gets a test row that kills its mutant. Back up and restore files
  for mutation checks; never use `git checkout`.
- Full suite: `sh tools/run-tests.sh --jobs 16`, with rc captured reliably.

## Open questions

  records the reason either way.
