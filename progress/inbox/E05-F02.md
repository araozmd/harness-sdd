# Intent — Sub-agent & human-gate telemetry with rollup reports

## Problem / who
The harness maintainer wants to understand **how much time each sub-agent runs on its
own**, and **how much time a human spends reviewing** before approving a spec. Today the
harness records narrative history (`progress/history.md`) but no structured timing.
Anthropic's long-running-harness article surfaces per-agent Duration (and Cost) in
tables; we want the same observability, plus a dimension the article does *not* measure:
**human spec-approval latency**, inferred from the gap between when a spec becomes
`spec-ready` and when the human moves it to `in-progress`.

## Success outcome
- Each sub-agent phase (Architect / Builder / Reviewer / Scout / Inception, and umbrella
  slice dispatch) records a structured telemetry record with at least: feature id, phase
  /role, start timestamp, end timestamp, derived duration, outcome (e.g. done / reject /
  fail), and round number where the build↔review loop iterates.
- **Human-gate latency** is captured automatically: the moment a feature is written
  `spec-ready` and the moment it is moved to `in-progress` are both stamped; their delta
  is the human review time for that spec.
- A **zero-dependency report script** aggregates the telemetry log into rollups at
  **daily, weekly, monthly, quarterly, semester, and annual** granularity (e.g. total
  autonomous agent time, per-phase breakdown, mean/median human-gate latency, counts).
- The capture mechanism is wired into the agent prompts / Orchestrator loop so it happens
  automatically as part of normal operation, not as a manual step.

## Scope / boundaries
- IN: a telemetry log format; the prompt/loop instructions that append records at phase
  boundaries and at the two gate transitions; the aggregation/report script; tests.
- OUT (hard): **token / USD cost accounting.** A markdown-prompt agent cannot observe its
  own token usage; only an instrumented SDK runtime can. Excluded per the human's "if it's
  hard or expensive, don't do it." Leave a clearly-marked extension point so a future
  SDK-backed runtime can populate a `cost`/`tokens` field without reworking the format.
- OUT: dashboards/visualization — text/markdown report tables only (matches the article
  and the AGENTS.md "text-only, never generate images" rule).

## Chosen options
- Duration + latency only for now; tokens deferred behind an extension point.
- Report granularities required: daily / weekly / monthly / quarterly / semester / annual.

## Constraints
- Zero new runtime dependencies (POSIX sh / python3 stdlib only — matches `init.sh`).
- Installed-body change → `VERSION` bump + CHANGELOG.
- Must not perturb the existing flow when telemetry is absent/unwritable (best-effort,
  never block a gate or a build on a telemetry write — same ethos as the cache in
  `/pr-loop`).
- Timestamps must be deterministic to record but tolerant to clock/timezone (store ISO-8601
  UTC).

## Open questions
- **Storage location & VCS:** `state/telemetry.jsonl` (committed, versioned with state) vs
  `progress/telemetry/` (progress dir) vs gitignored local-only? Trade-off: committed gives
  cross-session history but adds churn to the repo. Architect to recommend.
- **Who writes the record:** the Orchestrator at each delegation boundary (single writer,
  simplest) vs each sub-agent self-stamping in its progress file (more granular, more
  places to get wrong). Lean: Orchestrator as the single writer for phase spans + gate
  stamps.
- **Wall-clock source:** the agent reads the system clock via a shell `date -u` at span
  open/close. Confirm this is acceptable vs. any harness-provided time.
- Report output: one combined report with all granularities, or a granularity argument
  (`telemetry-report.sh weekly`)? Lean: an argument, defaulting to a summary.
