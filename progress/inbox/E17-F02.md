# Intent — The `builder-heavy` role: a seventh role at a heavier tier

## Problem / who

E17-F01 gave every role a configurable model tier, but there is still exactly **one**
Builder. The operator who wants a struggling task retried on a more capable model has no
way to express it: promoting the Builder tier promotes it for *every* task, and the cost
falls on the many easy tasks rather than the few hard ones.

This feature adds the *capability* — a second Builder role at its own tier. It does **not**
decide when to use it; that is E17-F03.

## Success outcome

`models.builder-heavy` is a configurable tier like any other role, and a selected front-end
emits a `builder-heavy` agent definition alongside the six existing ones. An operator can
pin it and invoke it by hand today, before any automatic escalation exists. A target that
configures nothing sees no behavior change at all.

## Scope / boundaries

**In scope**
- `agents/builder-heavy.md` as a **thin pointer** at `agents/builder.md` (see ADR-0002) —
  same instruction body, different role name and tier.
- `MODEL_ROLES` and `ag_personas` grow by one entry; `harness.config.yaml` grows one
  `models:` key seeded `inherit`.
- Per-front-end emission for all five selected front-ends, through the **existing**
  generators (`gen_codex_agent`, `gen_ag_persona`, the Claude/OpenCode/Gemini paths) — this
  feature adds a name, it does not add a generator.
- Reclaim-on-deselect for the new artifact on every front-end, through the existing
  pristine-only helpers.
- **Updating every assertion that fixes the role set at six.** See Constraints.

**Out of scope**
- When to escalate, the Architect's complexity tag, the two-rejection rule — all E17-F03.
- Any change to the Builder's instruction body. If the heavy variant needs different
  *behavior* rather than a different *model*, that contradicts ADR-0002 and must go back
  through the human gate as a re-spec, not a patch.
- The worker roster (E17-F04).

## Chosen options

- **Same body, heavier tier** (human decision at the drill Q&A, 2026-08-02). The two
  rejected alternatives and why they lose are recorded in **ADR-0002** — read it before
  specifying; do not re-derive the decision.

## Constraints

- **ADR-0002 is binding.** `builder-heavy` differs from `builder` only by resolved model.
- **The "exactly six roles" assertions are part of this change, not collateral.**
  `harness-install.sh` currently declares `MODEL_ROLES="orchestrator architect builder
  reviewer scout doc-critic"`, and E23-F01 R6 added assertions in
  `tests/test_model_routing.sh` fixing the Codex role set at exactly the six standard roles.
  An assertion left at six **does not fail loudly** — it pins the old set while the
  installer emits seven. Find every one of them; `grep -rn "six" tests/ harness-install.sh`
  is a starting point, not a complete answer.
- **Absent configuration reproduces today's behavior exactly** — E17's universality
  invariant. With `builder-heavy: inherit` the `model` key is omitted everywhere, exactly as
  for every other inheriting role.
- **Installed body ⇒ VERSION bump** (MINOR — new capability) plus a CHANGELOG entry.
- Budget: `change_size.max_requirements: 12`. This was split out of a ~17-R-id feature to
  fit; if the spec exceeds 12, stop and report rather than specifying it anyway.

## Open questions

- Does `builder-heavy` belong in `ag_personas`' description table with its own wording, or
  should it reuse the Builder's description verbatim? A distinct description helps a human
  picking a role from a front-end menu; identical wording makes the pointer relationship
  obvious. Architect's call.
- Should the harness ship a non-`inherit` default for `builder-heavy` (e.g. the reasoning
  tier), or seed it `inherit` like every other role? Seeding `inherit` preserves the
  universality invariant literally, but means the "heavy" builder is not heavier until
  someone configures it.
