# Intent — Source-repo GitHub Action that labels marker-carrying issues without trusting their bodies

## Problem / who
Reporters lack write access, so their labels are dropped; the maintainer needs `harness-feedback` + `bug`/`enhancement` applied automatically.

## Success outcome
`.github/workflows/harness-feedback-labeler.yml` in the source repo runs on `issues: opened` only (never on edit, so classification can't be changed after filing), parses F02's marker per ADR-0006, and applies labels; unmarked/malformed/unknown-version issues are left alone. Labels exist (created if missing).

## Scope / boundaries
In: the workflow + a testable parser script it calls, label creation, tests on fixture bodies incl. injection attempts. Out: triage (F05). Not part of the installed body (ADR-0005).

## Chosen options
- Only the marker is trusted as a classification input.
- Label mapping (owned here): `missing-capability` → `enhancement`; `harness-malfunction`, `contradictory-instruction`, `workaround-taken` → `bug`; all also get `harness-feedback`.

## Constraints
- Epic contract: `specs/epics/E32-feedback-loop/epic.md` (success criteria are binding).
- Issue text never reaches a `run:` line or a `${{ }}` expression; pass via env/file and parse strictly.
- Minimal `permissions:` (issues: write only).
- Pin actions by SHA if any third-party action is used.
- ADRs to honor: ADR-0005, ADR-0006.

## Open questions
- Whether to post a short acknowledgement comment on labeled issues (default: no).
