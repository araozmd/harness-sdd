# Intent — Per-requirement red/green task pairs replace the layered tasks template

## Problem / who
`specs/_templates/feature.tasks.md` orders a feature as `T1..T4` code steps, then
`T5 — Write tests per <feature>.tests.md`, then `T6 — run green`. The Builder is told to work
top to bottom (agents/builder.md), so every feature is built as a layered chunk and verified
only at the end by reading. This contradicts the `.tests.md` contract the Architect writes
first and is the in-feature cause of the "big horizontal chunks" the operator sees. ADR-0008
decision 2 records the fix at epic level; this feature ships it. User: anyone running the
Architect → Builder → Reviewer loop.

## Success outcome
- The tasks template expresses work as pairs per `R-id`: `T<n>a (R#) — write the failing
  test <name from .tests.md>; observe RED` then `T<n>b (R#) — minimal code to pass; observe
  GREEN`, with optional explicit `refactor` tasks citing the R-ids whose tests guard them.
  No trailing "write tests" task exists in the template.
- `agents/architect.md` §"Your output" item 3 and `docs/SPEC-FORMAT.md` describe the pair
  form; the Architect emits pairs in the order that makes something observable soonest
  (walking-skeleton R-id first).
- `agents/builder.md` works pairs in order, commits after each GREEN (so the pair commit is
  the baseline E36-F06 diffs against), and never writes code for a pair whose test has not
  been observed RED.
- The Reviewer's existing traceability check (#2) is unchanged. A small lint,
  `tools/tasks-pair-check.py <feature.tasks.md> --spec <feature.spec.md>`, exits non-zero
  when any `R-id` from the spec has its first `.tasks.md` task that is not a test task, or
  when a trailing "write tests" task exists; the Reviewer runs it (REJECT on non-zero) and the
  installer ships it (asserted in tests/test_install.sh). sdd:false fixes are exempt as today.
- Tests in the harness suite assert the template shape and the Architect/Builder prose
  tokens (a prose-contract test must read through fenced code — see the fence-blind
  extractor lesson in `tests/lib`).

## Scope / boundaries
In scope: `specs/_templates/feature.tasks.md`, `agents/architect.md`, `agents/builder.md`,
`agents/reviewer.md` (one check), `docs/SPEC-FORMAT.md`, `docs/WORKFLOW.md` if it shows the
task list, tests. The template ships to consumer repos through the installer unchanged in
path. Out of scope: changing `.tests.md`'s traceability table; the drift tool (E36-F06);
Driller shape rules (E36-F02).

## Chosen options
- Pairs per R-id, not per file and not per layer (ADR-0008).
- Commit per GREEN is a Builder rule, not a Reviewer-enforced gate here; E36-F06 enforces.

## Constraints
- Honor ADR-0008. Register the new Reviewer check in docs/RATIONALE.md's control table
  with its ablation condition.
- `sh tools/run-tests.sh` green under dash; no VERSION freeze in tests.
- Bump VERSION (MINOR) only because the installed body (template + role files) changes.

## Open questions
- Whether an R-id with a purely behavioral test (Playwright) still gets a pair or is
  grouped with the API pair it exercises — Architect decides and documents in SPEC-FORMAT.
