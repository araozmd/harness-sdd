# Intent — Epic lifecycle: draft/planned states + next() gating

## Problem / who
For the harness maintainer (and every consumer repo): the TaskStore's epic status
enum (`pending | in-progress | done`) cannot distinguish "barely an idea sketched
during inception" from "drilled down, approved, ready to execute". Without that
distinction the planned `/sdd-plan` skill (E06-F02) cannot safely seed a whole
roadmap of sketch-level epics — the Orchestrator would treat their features as
actionable. This feature is the state-machine foundation the rest of epic E06
builds on.

## Success outcome
- `store/tasks.schema.json` accepts two new **epic** status values: `draft`
  (inception sketch — title + business brief only) and `planned` (drilled down
  and human-approved). Feature statuses are unchanged.
- The Orchestrator's `next()` selection (documented in `store/local.md`,
  enforced in `agents/orchestrator.md`) never selects a feature belonging to a
  `draft` epic, regardless of the feature's own status or `autonomous` flag.
- Features of a `planned` epic are selectable exactly as features of a `pending`
  epic are today (the per-feature gate semantics are untouched).
- Existing `tasks.json` files (which contain no `draft`/`planned` epics)
  validate unchanged; `init.sh` passes on an untouched consumer repo.
- The lifecycle is documented (epic template comment, `store/local.md`,
  `docs/WORKFLOW.md`) as: `draft → planned → in-progress → done`, with
  `pending` retained as a legacy/equivalent-of-`planned` value for backward
  compatibility.
- `VERSION` gets one MINOR bump (this changes the installed body:
  `store/tasks.schema.json`, `agents/`, `docs/`, `specs/_templates/`).

## Scope / boundaries
**In scope:** schema enum addition (epic level only); `next()` gating rule in
`agents/orchestrator.md` + `store/local.md`; epic.md template comment update;
docs; tests for the new gating (a feature under a `draft` epic is never
returned by `next()`); CHANGELOG + VERSION bump.

**Out of scope (later features of E06):** the `/sdd-plan` skill (F02),
`/sdd-drill` (F03), Architect architecture.md contract (F04), `/sdd-fix` lane
(F05), drift-check demotion (F06). Also out: any change to feature-level
statuses, the `autonomous`/`sdd` flags, slices/umbrella semantics, board-mirror
status_map defaults (a mapping note for the new states is fine, no provider
work).

## Chosen options
- Rolling-wave over big-design-up-front: inception seeds **draft** epics cheaply;
  drill-down deepens **one epic at a time**, informed by prior epics' learning.
- Approval granularity = the epic: a drill-down session ends with one human
  "approve" that flips the epic to `planned` and stamps its features
  `autonomous: true` — reusing the existing gate-skip flag, no new approval
  mechanism (F03's job; F01 only provides the states).
- Additive change ⇒ MINOR bump, per the repo versioning policy.
- New-epic intake (`/sdd-new` altitude 3) keeps seeding `pending` epics for now;
  switching intake paths to `draft` is decided when F02/F03 land.

## Constraints
- **Backward compatible**: existing consumer `tasks.json` files must validate
  without migration; absence of `draft`/`planned` epics must behave exactly as
  today. No MAJOR-style layout change.
- Per the test anti-pattern memory: new tests must not freeze the exact VERSION
  value or diff DO-NOT-TOUCH files against main.
- Schema stays draft-07, zero-dependency validation path in `init.sh` keeps
  working.
- Honors the harness pillar: portable across AGENTS.md-compatible CLIs — the
  gating rule lives in role files/docs, not in Claude-specific glue.

## Open questions
- Should `pending` (epic level) be deprecated in docs in favor of `planned`, or
  kept indefinitely as a synonym? (Architect's call; removal is out of scope
  either way.)
- Does `next()`'s draft-gate belong only in `agents/orchestrator.md` prose, or
  also as a validatable invariant (e.g. a check in `init.sh` warning when a
  draft epic contains non-`pending` features)?
- Whether the board mirror's identity column mapping needs a documented default
  for `draft`/`planned` (likely just a README note).
