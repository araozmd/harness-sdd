# Intent — implementation-readiness lint: every path and symbol a plan/tasks file names must resolve

## Problem / who
The Builder receives only the four spec files in a clean context. If the `.plan.md`
"Files to change" table or the `.tasks.md` task list names a file, function, test suite or
template that does not exist (a typo, a renamed tool, a path from another repo), the Builder
either invents it or stalls, and the defect surfaces as a Codex review round or a Reviewer
rejection instead of at `spec-ready`. `tools/plan-cite-check.py` (E36-F04) already lints
the plan's tables but only for R-id / ADR citations — it never asks whether the row's
subject exists. Users: the Architect (pre-hand-off), the Reviewer (check 8 neighbour), and
the human at the gate who today has to eyeball paths.

## Success outcome
An Architect cannot hand a feature to `spec-ready` while its plan or tasks name something
that does not resolve, unless the row explicitly declares the thing is created by this
feature. The check is a tool with an exit code, not a prose instruction, and it fails
closed (exit 2 = did not run, never a pass), matching plan-cite-check's contract.

## Observable behavior
CLI — `python3 tools/readiness-check.py <feature-dir>` (name is the Architect's call;
extending `plan-cite-check.py` with a mode is acceptable) prints one line per unresolved
reference (`unresolved-path <file>:<line> <path>`, `unresolved-symbol ...`) and
`FAIL <n>`, exit 1; exit 0 when clean; exit 2 on usage/input error. `init.sh` runs it
warn-only over the specs tree like 2d does for plan-cite-check.

## Scope / boundaries
In scope:
- Backtick-quoted paths in `## Files to change` rows (first cell) and in `.tasks.md`
  task lines: must exist in the repo, OR the row's Change cell starts with **create**
  (plan-cite-check's existing vocabulary), OR the path is under a directory the plan
  creates.
- Symbols: a backticked `name()` or `path:name` reference whose file exists must be
  grep-resolvable in that file, unless the row says create/add.
- Test suites named in `.tests.md` / `.tasks.md` (`tests/test_*.sh`) follow the same rule.
- Architect pre-hand-off step, Reviewer check, Doc-critic reporting of the tool's lines,
  `init.sh` warn-only sweep, installer chmod + `tests/test_install.sh` assertion,
  `docs/RATIONALE.md` ledger row, `docs/SPEC-FORMAT.md` note, CHANGELOG, VERSION bump.
Out of scope:
- Judging whether a *correct* path is the *right* path (that stays Doc-critic / Reviewer
  judgment). Semantic analysis of code. Any new slash command.

## Chosen options
- Ship as code (a tool), not prose — RATIONALE principle 1. Fail closed like
  plan-cite-check (exit 2 is "did not run").
- Reuse plan-cite-check's fence-blind, section-scoped table grammar rather than a second
  parser; the fence parity corpus must still pass.
- Grandfather plans written before the tool merged exactly as check 8 does.

## Constraints
- Stage: production
- Stdlib-only Python 3; no third-party deps. Must run from any cwd and in an installed
  target (`.harness/tools/`).
- Every new tool must be installed by `harness-install.sh` and asserted in
  `tests/test_install.sh` (recurring Codex P1 otherwise).
- Tests must not freeze the exact VERSION literal or diff DO-NOT-TOUCH files vs main.
- One `run-tests.sh` at a time, `--jobs ≤ 4`.

## Open questions
- New tool file vs a `--readiness` mode on plan-cite-check.py: the Architect decides;
  the brief leans to a new file so plan-cite-check's byte-pinned contract stays untouched.
- Exact symbol grammar: how much of ```name()```, `Class.method`, `file:func` to
  support in v1 without false positives. Prefer precision over recall; an unrecognised
  token is ignored, never flagged.
