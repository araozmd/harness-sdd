# Intent — The worker roster: invocable CLIs as versioned data

## Problem / who

The operator runs several coding CLIs in parallel (Claude Code, Codex, OpenCode,
Antigravity, Gemini), but the harness only knows about the one it is running inside. Any
external kit that wants to route work across them — the epic names
`multi-cli-orchestrator` — has to rediscover what is installed and what each one can do,
every time.

The harness is in a good position to answer that question once: the installer already probes
the environment to pick front-ends. Nothing consumes that knowledge afterwards.

## Success outcome

An external tool can read one versioned file and learn which CLIs this machine can invoke
and what each is good for, without executing anything and without parsing the installer.

## Scope / boundaries

**In scope**
- A roster file written as **versioned data** carrying `schema: 1`, so a consumer can detect
  a format change instead of guessing.
- **Installer-detected** entries: which invocable CLIs are actually present.
- **Capability tags** per entry, so a consumer can choose by capability rather than by name.
- A stated, documented location and format — this is a **public contract** the moment
  anything reads it.

**Out of scope**
- **The harness never executes a rostered CLI.** It writes the file and stops. This is the
  epic's own boundary ("without the harness core ever executing it") and it is what keeps
  the roster safe to ship: a data file cannot spawn a process.
- Any consumer of the roster. `multi-cli-orchestrator` is a separate kit and not this
  repo's concern.
- Model routing, escalation, and the Builder variants (E17-F02 / F03). This feature shares
  the epic but touches none of that machinery.
- Version *detection* of each CLI, unless it falls out of presence-detection for free. The
  installer explicitly does not probe CLI versions today (see the `agy >= 1.1.5` note in
  `harness.config.yaml`, which is documented rather than checked) — do not quietly start.

## Chosen options

- None taken at the drill; the shape below is the Architect's to settle.

## Constraints

- **Absent configuration reproduces today's behavior.** A target that does not want a roster
  must not grow the file — consistent with how `.gemini/agents/` and `.codex/agents/` are
  only created when something asks for them.
- **`schema: 1` from the first write.** A data file shipped without a version is a migration
  problem the moment it changes.
- **Gitignored or committed — decide and say which.** The roster describes *this machine*,
  so committing it puts one developer's local CLI set into a shared repo. Compare with
  `telemetry.jsonl`, which is deliberately local-only and gitignored, and seeded into
  `.harness/.gitignore` for consumers by the installer.
- **Installed body ⇒ VERSION bump** (MINOR) plus a CHANGELOG entry.
- Budget: `change_size.max_requirements: 12`.

## Open questions

- **Where does the roster live** — `.harness/workers.json`, a key inside
  `harness.config.yaml`, or a sibling of `telemetry.jsonl`? It is machine-written and
  machine-read, which argues against the hand-edited config file.
- **What is the capability vocabulary?** Free-form tags are easy to write and useless to
  match on; a closed set is matchable but needs extending every time a CLI grows a feature.
  This is the feature's central design question.
- **Is detection re-run on upgrade?** A roster written once goes stale as the operator
  installs and removes CLIs; regenerating every install run is simpler but overwrites
  anything a human edited. State the ownership rule explicitly, the way the pristine-only
  reclaim helpers do for generated glue.
