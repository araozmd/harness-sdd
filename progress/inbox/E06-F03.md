# Intent — `/sdd-drill <epic>` skill (decompose, ADR deltas, epic-level approval)

## Problem / who
For the harness maintainer and every consumer repo: F02 (`/sdd-plan`) now produces a
roadmap of `draft` epics — each a one-paragraph brief with `features: []`, inert
behind F01's `next()` gate. But there is no way to **deepen** one of those sketches
into executable work. A `draft` epic can never be selected, and nothing today
decomposes it into features, records the design decisions that decomposition forces,
or moves it past `draft`. F03 is the **consumer** that closes the loop: a short,
per-epic drill-down session that turns one `draft` epic into a `planned` one the
existing Builder/Reviewer loop can execute.

This is the rolling-wave payoff: you drill **one epic at a time**, when you're ready,
informed by what the previous epic's implementation actually taught — instead of
specifying the whole roadmap up front.

## Success outcome
`/sdd-drill <epic-id>` runs a short session over exactly **one** `draft` epic and, on
human approval:
- **Decomposes** the epic into a concrete **feature list** — seeded as `pending`
  feature entries in `state/tasks.json` (with ids, one-line intents, and
  `depends_on`), the epic's `epic.md` feature table filled in, and a per-feature
  inbox brief under `progress/inbox/` so the existing Architect can spec each one
  just-in-time.
- **Records ADR deltas** — any new design decisions this epic forces, appended as
  ADRs at `specs/adr/NNNN-*.md` (F02's convention: 4-digit, above-max, one decision
  each, referenced by `ADR-NNNN`), capturing what was learned since inception.
- **Ends in exactly one human decision** that either (a) **approves** the epic for
  autonomous execution — flipping it `draft → planned` and stamping `autonomous:
  true` on its features so the loop runs end-to-end with no per-feature gate — or
  (b) **keeps it gated** — the epic still advances to `planned` (it has been
  drilled), but its features stay `autonomous: false` so each parks at the normal
  per-feature spec-approval gate.

After approval, a `planned` epic's features are selectable by `next()` (F01) and the
existing `/sdd-next` loop specs → builds → reviews each feature, with no further
drill-down ceremony.

## Scope / boundaries
**In scope:**
- New `/sdd-drill` skill: a slash command (`.claude/commands/sdd-drill.md`) over a
  **portable role contract** (a new role file, or an extension — Architect's call),
  mirrored into opencode so the harness stays AGENTS.md-portable.
- Reading the target `draft` epic + `specs/vision.md`/`architecture.md`/ADRs as
  inputs; an adaptive, short Q&A to settle the feature breakdown and any deltas.
- The write path: seed `pending` feature entries into the epic, fill its `epic.md`
  feature table, write per-feature inbox briefs, append ADR deltas, and — on the
  approve branch — flip the epic `draft → planned` and stamp `autonomous: true` on
  its features. Re-validate `state/tasks.json` against the schema; never claim
  success on a validation failure.
- The **epic-level approval** as the single human decision (reusing the existing
  `autonomous: true` gate-skip flag — **no new approval mechanism, no schema
  change** for approval).
- Argument/precondition guards: `<epic-id>` is required; the epic must exist and be
  `draft` (drilling a non-`draft` epic is refused or warned — Architect decides).
- Docs (`docs/WORKFLOW.md` placement among `/sdd-plan` → `/sdd-drill` → `/sdd-next`;
  README one-liner) and one MINOR `VERSION` bump + `CHANGELOG.md` entry.

**Out of scope (other E06 features):**
- F02 `/sdd-plan` — already shipped; F03 **consumes** its draft epics, never
  produces them.
- F04 — the Architect contract that makes `architecture.md`/ADRs a mandatory input
  and makes feature specs **cite** ADRs. F03 produces ADR deltas; F04 makes
  downstream specs consume them.
- F06 — drift-check demotion of stale epics on rollup.
- Changing F01's epic enum, the `next()` gate, or feature-level status values.
- The 4-file feature specs themselves: F03 seeds feature **entries + intent briefs**;
  the existing **Architect** still writes each `.spec/.plan/.tasks/.tests`
  just-in-time during the autonomous run (keeps specs just-in-time, reuses the
  Architect — do not duplicate it).

## Chosen options
- **Consumer-only, one epic at a time:** `/sdd-drill` deepens exactly one `draft`
  epic per session; the roadmap is drilled incrementally, informed by prior epics.
- **Reuse F01 + F02 primitives:** the `draft → planned` flip uses F01's existing
  state; ADR deltas use F02's `specs/adr/NNNN` convention; approval reuses the
  existing `autonomous: true` flag. No new status, no new approval mechanism, no
  schema change.
- **Drill seeds feature entries, not specs:** decomposition produces `pending`
  feature rows + per-feature inbox briefs; the Architect specs each feature
  just-in-time in the existing loop. This preserves the rolling-wave "specs stay
  just-in-time" principle and avoids a second spec-writer.
- **Two-branch ending:** one human decision — *approve* (`planned` +
  `autonomous: true`) or *keep gated* (`planned`, features stay gated).
- Additive change ⇒ MINOR bump, per repo versioning policy.

## Constraints
- **Backward compatible / additive:** `/sdd-new`, `/sdd-plan`, `/sdd-next` are
  untouched and keep working; repos that never run `/sdd-drill` see no behavior
  change.
- **Portability pillar:** the skill's contract lives in a role file + AGENTS.md, not
  solely in `.claude/`; it must run on any AGENTS.md-compatible CLI.
- **Single human gate:** the drill-down ends in exactly one approval decision at the
  **epic** granularity — not per feature. Honor `require_spec_approval` semantics by
  expressing the epic gate through the existing `autonomous` flag, not a new flag.
- Schema stays draft-07; `state/tasks.json` re-validates after every write via the
  zero-dependency path; `./init.sh` exits 0 afterward.
- Per the permanent-suite anti-pattern memory: new tests must not freeze the exact
  `VERSION` value or diff DO-NOT-TOUCH files against `main`.
- Must not regress F02's `agents/planner.md` "never past draft" invariant — F03 is
  the *only* path that advances an epic out of `draft`.

## Open questions
- **Role shape:** a new `agents/driller.md` role, an extension of `agents/architect.md`
  (decomposition is architectural), or a mode of the Planner? (Mirror F02's D1
  reasoning — pick the portable, single-responsibility option.)
- **Who writes feature ids/`depends_on`:** does `/sdd-drill` allocate the epic's
  `F01..FNN` block and the intra-epic dependency graph itself, and how does it
  number them (next-sequential within the epic, append-only)?
- **Non-`draft` target:** refuse hard, or warn-and-continue, when `<epic-id>` is
  already `planned`/`in-progress`/`done` or doesn't exist? (Re-drilling a `planned`
  epic — amend vs refuse — parallels F02's D2.)
- **"Keep gated" semantics:** confirm the gated branch advances the epic to
  `planned` with `autonomous: false` features (vs leaving it `draft`). Which is the
  least-surprising default?
- **ADR-delta boundary:** what belongs in a drill-time ADR delta vs F02's upfront
  ADRs vs a future feature spec's own decisions (the F02-D6 boundary, one level
  down)?
- **Stamping scope:** does `autonomous: true` get stamped on every feature of the
  epic at approval, or can the human approve a subset? (Epic-level approval suggests
  all-or-nothing; confirm.)
- **Interaction with F04 (not yet built):** F03 emits ADR deltas now; should the
  per-feature inbox briefs already record which ADR ids each feature touches, so F04
  has the hook when it lands? (Forward-compatible note vs out of scope.)
