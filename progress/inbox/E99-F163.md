# Fix — make escalation aware of Codex reasoning effort

## Problem
`escalation_verdict()` (`harness-install.sh`) decides whether escalating `builder` →
`builder-heavy` actually changes anything by comparing the two strings `resolve_model`
returns. It compares **`model` only**.

Since E99-F161, a role's tier also stamps `model_reasoning_effort` into
`.codex/agents/<role>.toml`. So a Codex operator who sets `builder: standard` /
`builder-heavy: reasoning` now gets **genuinely differentiated roles on disk** —
`medium` vs `high` — while `escalation_verdict` sees the same (or no) `model`, returns
`same`, and `init.sh` reports `escalation: … DISARMED`.

Verified behaviourally on a fresh `--agents=codex` target with tiers and no pins
(E99-F161 review round 2): `medium`/`high`/`high`/`low` stamped, no `model` key on any
file, target still `DISARMED`.

This was deliberately deferred out of E99-F161 — making "same model, different effort"
read as `raise` changes `escalation_verdict`'s contract, which is not something that
should ride inside a brief-only fix. `docs/INSTALL.md` and `docs/WORKFLOW.md` name the
gap in prose and cite this row.

## Intended fix
Decide and record whether the escalation verdict should account for effort, then make the
code and the operator-facing prose agree. The decision is the work; the edit is small.

Consider at least:
- **Widen the comparison** — `escalation_verdict` compares the whole resolved stamp
  (model + effort) rather than model alone. Simple, but it changes a documented contract
  and `harness-install.sh:479-486` explains that contract to the operator, so the prose
  moves with it.
- **Leave it and say so** — keep model-only and make `init.sh`'s disarmed line state that
  effort-only differentiation does not arm. Cheaper, but the operator still cannot express
  a Codex escalation the harness will honour, which is the brief's original complaint.

Whatever is chosen, `escalation_verdict`'s doc comment, `harness-install.sh:479-486`, its
byte-identical twin in `harness.config.yaml`, `docs/INSTALL.md` and `docs/WORKFLOW.md`
must all agree afterwards. Note `harness-install.sh:479-492` and `harness.config.yaml`'s
copy are byte-identical and are captured tail-anchored by `prl_block()`
(`tests/test_installer_toggles.sh:116`), so a one-sided edit reds the suite — verified by
mutation in the E99-F161 round-2 review.

## How to verify
- If the comparison widens: two roles differing **only** by effort must read `raise`, and
  `.escalation-arming` must say `armed` on a codex-only target configured that way.
- Roles identical in both model and effort must still read `same`; a role resolving to
  nothing on either axis must still read `neither`/`none` as today.
- `tests/test_escalation.sh` must cover the effort-only case, and the existing verdict
  cases must not regress.
- **Mutate each independent path separately** — the batching mistake got E99-F159 and
  E99-F160 each rejected once.
- `./init.sh` exits 0; `./tools/run-tests.sh` green. Run with `TMPDIR` on a disk-backed
  path: `/tmp` here is a shared tmpfs that has aborted full runs with `Disk quota exceeded`.
