# Intent — /sdd-fix-parallel dispatch with shared-path conflict guard + installer wiring

## Problem / who
This is the capstone that actually parallelizes the fix lane. It gives the human a
Fixer-family command that picks several ready E99 fixes and runs them concurrently —
each isolated by F02, each writing board state through F01's lock — while refusing to
parallelize fixes that would collide on shared files. The user is the human running the
maintenance lane who wants independent fixes done in one pass instead of serially.

## Success outcome
Running `/sdd-fix-parallel` selects up to N ready E99 fixes and drives N concurrent
Builder→Reviewer chains, each in its own worktree/branch/PR. Fixes that touch known
shared files are run serially instead of in parallel. What was deferred (over the cap,
or serialized by the guard) is clearly logged — nothing is silently dropped. One fix
failing isolates to that fix; the others still complete.

## Scope / boundaries
- In scope: selection of E99 fixes matching `pending + sdd:false + autonomous:true +
  depends_on all done`; concurrent dispatch capped at N; a **static shared-path
  conflict guard** that serializes any fixes whose briefs touch
  `harness-install.sh`, `tests/test_install.sh`, or `tools/*`; per-fix failure
  isolation; `/pr-loop` stays per-PR.
- In scope: `N` from `harness.config.yaml` (`fix_lane.max_parallel`, default 3).
- In scope: installer wiring — add `sdd-fix-parallel` to `HARNESS_SDD_CMDS`, generate
  `.claude/commands/sdd-fix-parallel.md`, and **assert its presence in
  `tests/test_install.sh`** (every new /sdd-* command must be generated AND asserted).
- Out of scope: parallelizing `sdd:true` features; auto-merge-conflict resolution;
  dynamic content-diff conflict detection (static path list only in this feature).

## Chosen options
- Dispatch is a new `/sdd-fix-parallel` command backed by the Fixer role contract.
- Conflict guard is a **static shared-path list** in v1 (not dynamic diff analysis).
- Concurrency cap `N` is config-driven with a default of 3; deferrals are logged.

## Constraints
- **Depends on E15-F01 and E15-F02.**
- **Reuse existing primitives** — `sdd:false` + `autonomous:true`; no new status/enum
  values and no `state/tasks.json` schema change.
- **PR-before-done invariant** holds: each fix parks at `in-review` until its PR merges.
- No silent truncation: log every fix deferred by the cap or serialized by the guard.
- Installed-body change ⇒ VERSION bump (MINOR); the new command must be both generated
  by `harness-install.sh` and asserted in `tests/test_install.sh`.

## Open questions
- How concurrent chains are actually spawned within the harness's execution model
  (Task tool fan-out vs. background workers) — Architect to pin to the real mechanism.
- Whether the conflict guard reads shared paths from a config list (extensible) or a
  hard-coded constant — Architect to choose, favouring a documented, extensible list.
- Reconciliation with the existing serial `sdd-fix` command (shared selection/seeding
  logic vs. a separate path).
