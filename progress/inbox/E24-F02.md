# Intent — The cascade lands the upgrade (or reports that it did not)

## Problem / who
`harness-install.sh --umbrella` ends with a success banner after it has *written* files.
Whether those files were ever committed is outside its model of "done". In the
`~/repos/viernes` cascade that produced a green finish and five children each carrying
26–29 uncommitted files, indefinitely.

The operator's mental model — reasonably — is "I upgraded the umbrella, the umbrella is
upgraded". The tool confirmed it. Nothing contradicted it. E24-F01 makes the *consumer*
side notice; this feature closes the *producer* side, so the guard is a backstop rather
than the normal way anyone finds out.

The user is whoever runs the cascade — one person upgrading N repos in one command, which
is precisely the situation where N-way manual follow-up gets skipped.

## Success outcome
After a cascade the operator knows, without inspecting anything, whether every child's
upgrade is landed. Either it landed, or the command told them plainly which children still
carry unlanded changes and exited non-zero. "Upgrade complete" stops being a claim about
files written and becomes a claim about state reached.

## Scope / boundaries
In scope:
- A per-child post-install status roll-up in umbrella mode: which children have
  uncommitted HARNESS-OWNED changes after the install.
- The exit code contract for a cascade that leaves work unlanded.
- Optionally, actually landing it — see Chosen options.

Out of scope:
- Single-target mode. Arguable that it should get the same summary; the Architect may
  extend it if it is free, but the umbrella case is the one that fails at scale and it is
  the one being bought here. Do not let single-target scope creep the diff.
- Pushing, opening PRs, or touching remotes. Landing means a local commit at most.
- Anything about `init.sh`. That is F01.

## Chosen options
- **Report is mandatory; commit is opt-in.** The summary + non-zero exit is the floor, and
  it is what actually fixes the reported failure. Auto-committing into N repos the operator
  did not ask you to commit into is a much larger claim on their working tree — it belongs
  behind an explicit flag, if it ships at all.
- **Non-zero exit on unlanded children.** A summary that only prints is a summary that gets
  scrolled past in a 5-repo cascade. The exit code is what makes it real, and what lets CI
  or a wrapper script catch it.
- **Reuse F01's ownership classification.** "Which paths count as HARNESS-OWNED and dirty"
  must be answered once, the same way, in both features. F01 lands first specifically so
  this one can build on its answer rather than fork a second definition that drifts.

## Constraints
- **Never commit a child's unrelated work.** A child repo may have the operator's own
  uncommitted changes sitting beside the upgrade. If a commit path ships, it must stage
  HARNESS-OWNED paths *explicitly and only* — never `git add -A`, never `git commit -a`.
  This is the exact accident the epic's business brief names as a live risk.
- **Never touch a foreign branch.** If a child is mid-feature on a branch that is not its
  default, committing harness files into that branch pollutes someone's PR. Surface it;
  do not resolve it unilaterally.
- **Idempotent.** Re-running the cascade after landing must report clean and exit zero.
- **`--dry-run` must remain write-free**, including the new behavior.
- **Zero new dependencies**; POSIX sh + git, consistent with the installer.
- Bump `VERSION` (PATCH or MINOR depending on whether a commit flag ships) and record it in
  `CHANGELOG.md`.

## Open questions
- Does the commit path ship in this feature at all, or does F02 stop at report-and-exit and
  leave committing to a follow-up? The report alone closes the reported defect. The
  Architect should size both and prefer the smaller one that fully fixes the problem —
  E21's whole thesis is that the delivery unit is chosen too late to shrink.
- What is the right exit code? A distinct non-zero value (rather than `1`) would let a
  wrapper distinguish "install failed" from "install succeeded but is unlanded" — those are
  genuinely different outcomes and conflating them loses information.
- Should a child that is not a git repo, or has no commits yet, be reported as unlanded,
  skipped, or noted separately? It cannot be "dirty" in the relevant sense.
- Does the summary belong in the existing cascade output, or as a distinct final block? The
  cascade already prints per-child lines; a trailing block is easier to find in a long log.
