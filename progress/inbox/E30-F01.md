# Intent — specs/glossary.md is body-owned but project-authored

## Problem / who
The user is a project that installed the harness and followed its instructions. The shipped
`.harness/specs/glossary.md` says "Add terms as the project grows"; `agents/planner.md:51-55`
treats it as the project's term index alongside `specs/product.md`; `docs/SPEC-FORMAT.md:16`
lists it under the project's domain model. But `HARNESS_BODY_PROSE`
(`harness-install.sh:703`) classifies it as harness body prose, so **every** re-run of
`harness-install.sh` overwrites it with the shipped example — content for an unrelated
chatbot-handoff domain.

The installer's own header contradicts that classification. Lines 59-62 enumerate the two
ownership classes: BODY is "agents, docs, store, tools, templates, init.sh, config,
AGENTS.md"; PROJECT-authored is "specs/product.md, state/tasks.json, specs/epics, progress".
`specs/glossary.md` is in neither list. Every sibling in `specs/` — `product.md`,
`architecture.md`, `vision.md`, `adr/`, `epics/` — is project-owned and preserved.
`glossary.md` is the lone exception.

Confirmed in the field, not inferred: on 2026-09-16 an upgrade of `previta/protocolos` to
v0.79.0 destroyed a 90-line Protocolos domain glossary written by commit `9e08fe0`. The run
printed no warning. It was recovered only because the file happened to be committed to git.

## Success outcome
A project edits `.harness/specs/glossary.md`, re-runs the installer, and its glossary is
still there — no flag, no prompt, no `.dist` file to merge by hand. An install that has
never touched its glossary still receives the refreshed shipped example on upgrade. A fresh
install behaves byte-identically to today.

## Scope / boundaries
**In scope**
- Reclassify `specs/glossary.md` out of `HARNESS_BODY_PROSE` into the seed-once/preserve
  class that `specs/product.md` (`harness-install.sh:3755`) and `progress/lessons.md`
  (`harness-install.sh:3809`) already use.
- The pristine-compare rule (see Chosen options) so the refresh still reaches untouched copies.
- The thin-child pointer-stub path: `docs/UMBRELLA.md:101` lists `specs/glossary.md` among
  the prose that becomes a stub in a thin child, which a project-owned file cannot be.
- Documentation agreement: `harness-install.sh` header lines 59-62, `docs/INSTALL.md:63`,
  `docs/INSTALL.md:681`, `docs/INSTALL.md:993`, `docs/CONFIG-LAYERING.md:22`,
  `docs/UMBRELLA.md:101`, and the generated `manifest.txt` ownership list.
- Tests covering: fresh install, upgrade-with-edited-glossary, upgrade-with-pristine-glossary,
  and the umbrella/thin-child path.

**Out of scope**
- Moving or renaming `specs/glossary.md` — role prompts name that path.
- A config key or CLI flag to choose the behaviour.
- Auditing the other `HARNESS_BODY_PROSE` members (`specs/_templates/` is the next suspect);
  that is a follow-up feature under E30, seeded only if an audit substantiates it.
- Recovering glossaries already destroyed by past upgrades.

## Chosen options
- **Altitude — new epic E30, boundary-wide.** The epic is the harness-owned/project-owned
  boundary; F01 is the one instance with field proof. Chosen over a tightly-scoped
  glossary-only epic and over an `sdd: true` row in the E99 fix lane (E99 is 41/42
  `sdd: false` brief-only work, and this needs a spec, a migration story and tests).
- **Migration — preserve unless byte-identical to the shipped example.** On upgrade:
  absent → seed the shipped example; identical to the shipped example → refresh (still
  pristine); otherwise → preserve. Chosen over pure seed-once (which freezes a pristine
  copy at install date) and over preserve-plus-`glossary.md.dist` (which invents a new file
  class and a new ownership question for every target).

## Constraints
- **The path does not move.** `agents/planner.md` and `docs/SPEC-FORMAT.md` name
  `specs/glossary.md` literally.
- **No new option.** `docs/RATIONALE.md`'s ablation doctrine: no new config key, flag or
  prompt to select preservation — it is a rule, not a preference.
- **Fresh installs stay byte-identical**, and the change must be idempotent across repeated
  upgrade runs.
- **One documented owner per path.** Whatever F01 decides must be reflected in the installer
  header's ownership-class list and in `manifest.txt`, not only in code — the prose being
  out of step with `HARNESS_BODY_PROSE` is what produced this defect.
- The comparison must survive a shipped example that changes between versions: "pristine"
  means identical to the example *this* installer ships, and an older pristine copy from a
  previous version must not be mistaken for a project edit. The Architect should decide
  whether that needs a recorded stamp rather than a single comparison.

## Open questions
- **Thin children.** Does a thin child get its own real, project-owned glossary, or keep
  pointing at the coordinator's? `docs/UMBRELLA.md:101` currently makes it a pointer stub,
  which is incompatible with project ownership. This is the main design fork.
- **Older pristine copies.** A copy identical to v0.70's example but not v0.79's reads as
  "edited" under a naive single comparison and is preserved forever. Is that acceptable
  (fails safe, never destroys), or does it need a stamp — e.g. under `.harness/` alongside
  the existing `.codex-skills/` ownership stamps — to distinguish "pristine, older" from
  "project-edited"?
- **Scope of the reclassification.** Should F01 fix `glossary.md` alone, or should the
  Architect first run the audit and let the finding set F01's blast radius? The epic assumes
  the former and seeds the audit as a follow-up.
- Should the same preserve-if-edited rule be offered for any other currently-body file the
  docs describe as customizable, or is per-file classification the correct granularity?
