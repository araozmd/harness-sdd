# Fix — put a length floor on the four block extractors

## Problem
`models_block` (`tests/test_install.sh:202`) and `workers_block` (`:136`) bound extraction
on the **first blank line** after their start anchor:

```sh
awk '/^# Per-role model routing \(E17-F01\)/ { m = 1 } m && (/^$/ || /^EOF$/) { exit } m { print }'
```

That arm terminates *anywhere* after the anchor, and a truncated capture is still non-empty,
so the existing `[ -s ]` emptiness guard cannot see it. Insert a blank line immediately after
the start anchor **in both files** and both extracts shrink to the single anchor comment line
— which still compares equal, so the test passes. Layer a genuine one-sided desync on top of
that and it goes through **silently**.

Found by the E99-F160 round-2 Reviewer (mutants MF2, MG, and ML for the workers analogue),
recorded there as non-blocking and deliberately deferred: fixing it in that branch would have
invalidated the MA-MD mutation evidence the approval rested on.

Severity is genuinely limited — it needs a *symmetric* blank-line reformat, which is not
itself a desync, and both the asymmetric and the over-run directions still fail loudly.
`tests/test_install.sh:198-200` already names the assumption and its remedy in place. But the
whole point of E99-F160 was "must fail if the two copies ever diverge by a byte", and this is
a path where they can.

Note the hardening in E99-F160 round 2 **imported** this into `workers_block`, whose previous
`roster:`-anchored bound happened to be immune to interior blank lines. That was a net win
(it closed a worse hole) but it is why the floor should cover all four extracts, not just the
`models:` pair.

## Intended fix
Add a length floor to every extract before comparing — the Reviewer's suggested shape is a
`wc -l >= N` check alongside the existing `[ -s ]` guard, failing loudly with a message that
distinguishes "extraction truncated" from "blocks differ".

Pick `N` so it cannot rot into a rubber stamp: a floor of 1 buys nothing, and a floor equal
to today's exact block length will need editing every time a legitimate line is added. Prefer
a floor that encodes a structural minimum (e.g. the block cannot be shorter than its known
required keys) and say in a comment why that number, so the next reader can tell whether a
future failure is a real truncation or a stale constant.

## How to verify
- The four extracts each fail loudly when truncated, with a message naming truncation rather
  than a byte difference.
- **Mutate separately**, one at a time — this is the lesson E99-F159 and E99-F160 were each
  rejected over once:
  1. Blank line immediately after the `models:` start anchor in **both** files → must now FAIL
     (today it passes). This is mutant MF2.
  2. Same, plus a one-sided mid-block desync → must FAIL naming the desync (mutant MG).
  3. The `workers_block` analogue (mutant ML) → must FAIL.
  4. Regression: E99-F160's kills must still kill — past-the-end insertion on each side
     separately, and a mid-block byte on each side separately (`16c16`).
- `./init.sh` exits 0; `./tools/run-tests.sh` green.
