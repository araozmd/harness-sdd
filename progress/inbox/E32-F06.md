# Intent — Actionable sanitized harness reports with immediate automatic filing

## Problem / who
Harness maintainers receive automatically created issues that name a trigger and
command but omit the concrete defect, expected behavior, and supporting evidence.
The existing reporter deliberately keeps details local, so upstream metadata alone
cannot establish what needs fixing. Users should not have to clarify those reports
or grant permission again each time an actionable harness defect is encountered.
The session owner already closed ambiguous issues #231, #232, #233, #235, and #236;
this feature prevents their reporting pattern from recurring.

## Success outcome
An upstream report gives a maintainer a concrete observation, expected behavior,
and reproducible steps or specific inspection evidence sufficient to investigate.
Each of the four supported triggers carries details appropriate to that trigger.
Evidence is bounded and sanitized before publication. A report containing only
metadata, missing substantive details, or evidence that cannot be safely published
stays local and clearly names what is missing. Complete reports are filed
automatically when ready in any phase, without waiting for the end of the task or
asking the user for permission.

## Scope / boundaries
In scope: the reporter's actionable-detail contract, public issue content, local
fallback diagnostics, reporting instructions and generated front-end glue, and
focused regression coverage of publishing and withholding decisions. Keep all
current supported source and installed layouts consistent. Update current user
and workflow documentation to match the resulting behavior.

Out of scope: new reportable trigger categories, project bug reporting, automatic
implementation of reported defects, broad triage functionality, reopening closed
ambiguous issues, and unrelated maintenance.

## Chosen options
- Seed a new feature under E32, depending on completed E32-F02 and E32-F03; their
  already-consumed briefs are not the destination for this change.
- Use the full SDD path with autonomous execution explicitly authorized by the user.
- Publish bounded sanitized evidence instead of retaining all actionable details
  exclusively in local files.
- File automatically as soon as actionable evidence is ready, at any phase.
- Leave incomplete reports local with explicit missing-field diagnostics.

## Constraints
Retain exactly the four existing harness-defect triggers and their exclusions.
Retain top-level session ownership of upstream reporting; subagents record findings
for the owner. Preserve stable session identity, duplicate protection, per-session
caps, configuration opt-out, and local fallback on unavailable network/auth or
reporter failure. Preserve privacy protections against project content and secrets;
the change needs an explicit safe publication boundary, not unrestricted copying of
logs, commands, or arbitrary files. Preserve the init failure hard stop: the narrow
reporting-only exception never permits repair, board writes, or continued work.

Trigger-specific detail should explain a malfunction and its evidence; conflicting
instructions and the actual conflict; a workaround, the documented path and why it
failed; or a recurring missing capability with concrete circumstances and impact.
Ordinary metadata such as command, phase, trigger, or version is not sufficient
substantive evidence by itself. Sanitization must not convert an incomplete or
unusable report into a publishable one merely because field names remain present.

## Open questions
The Architect chooses the smallest coherent field/interface design, practical
bounds and sanitization rules, and how incomplete local reports can be completed
without duplicate publication. No user clarification is needed for the stated
intent. Keep the approved feature focused and reviewable; use the existing reporting
contracts and regression tests to resolve compatibility details.
