# Intent — escalation to builder-heavy can arm in self mode and per front-end

## Problem / who
In this harness's own repo, `./init.sh` warns on every run: "escalation: configured
(after_rejections: 2) but DISARMED — .escalation-arming is absent or not 'armed', so
builder-heavy will never fire." The cause:
- `harness-install.sh` writes `.escalation-arming` as an AND over every selected front-end
  (`write_escalation_arming`, about line 6296). Its first line is `armed` only when every
  front-end's builder and builder-heavy stamps differ.
- In self mode, Claude and Codex resolve their model tiers from the committed shims
  (`.claude/agents/*.md` and `.codex/agents/*.toml`). OpenCode and pi read only
  `harness.config.yaml` `models:`, which must stay all-`inherit` because it is the seed template.
- So the file records `claude=raise codex=neither opencode=neither pi=neither`, the first line
  is `blocked`, and `tools/builder-role.sh` never escalates.

The result is that a feature that keeps getting rejected (E36-F06 took three rounds) never
escalates to the heavier tier, even on Claude Code, where escalation would genuinely change
the model.

## Success outcome
Escalation fires where it can actually raise the stamp, and stays off where it cannot. The
rule never lets escalation silently be a no-op. Candidate directions, which the Architect
decides between in an ADR delta to ADR-0002:
- (a) **Per front-end gate.** `builder-role.sh` gains `--frontend <key>` and reads that
  front-end's `<key>=raise` line. The Orchestrator passes its own host's key. The first line
  stays the all-front-ends summary for callers that pass no key.
- (b) **Self-mode harvest for opencode/pi.** As already happens for Claude and Codex, so this
  repo can tier those front-ends from committed shims. This does not by itself fix consumers
  who use only some front-ends.
- (c) Both.

## Scope / boundaries
In scope:
- `tools/builder-role.sh`
- the arming writer in `harness-install.sh`
- the orchestrator prose that calls `builder-role.sh`
- `init.sh`'s escalation warning
- `docs/` and RATIONALE where they state the AND rule
- tests: `tests/test_escalation.sh`, `tests/test_builder_heavy.sh` and `tests/test_self_mode.sh`

Out of scope: choosing vendor model ids for opencode or pi in this repo's shims. The spec may
ship the mechanism without setting them.

## Constraints
- Stage: production
- Arming must never report `armed` for a front-end whose builder and builder-heavy stamps are equal.
- Existing consumers with an all-front-ends `armed` file must behave exactly as today.
