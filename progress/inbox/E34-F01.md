# Intent — Automated cleanup sweep + role hand-off rules for scratch files, stale progress/ handoffs, and merged worktrees/branches

## Problem / who

The human runs many sub-agents concurrently (Claude Code's Agent tool, worktree-isolated
sessions, the parallel fix lane). Every one of them writes local state: namespaced
scratch files under `scratchpad/<feature-id>-<role>/`, per-run handoff files under
`progress/` (inbox briefs, `topology-handoff.md`, PR-loop round caches), and — for
worktree-isolated work — local git worktrees and branches. None of it is ever removed
once the work it belonged to is done, and today the only mitigation is the human
manually telling agents, in the prompt, to clean up after themselves. That's a
per-prompt workaround, not a durable convention, and it exhausts disk/storage quota on
a machine running many sub-agents.

Measured in this repo (harness-sdd) at intake time, as concrete evidence the existing
"namespace your scratch file" convention (`agents/builder.md`, `agents/reviewer.md`) is
not sufficient on its own:
- `scratchpad/` is 654M total; the largest entries (`E31-F02-reviewer` 212M,
  `E31-F02-builder` 168M, `E28-F02-builder` 92M) belong to features that finished
  weeks ago.
- `git worktree list` shows a `prunable` worktree under `/tmp/claude-1000/...`.
- `git branch --merged main` shows a local branch (`chore/E32-F03-done`) never deleted
  after merge, and `git branch -r --merged main` shows a long list of merged-but-not-
  pruned remote branches.

The user for this feature is anyone running this harness with multiple concurrent
sub-agents/worktrees, and secondarily the harness maintainer who currently has to
repeat the same cleanup instruction in every prompt.

## Success outcome

Cleanup becomes a standing discipline instead of a per-prompt ask:

- An automated sweep (tool-invoked — e.g. run at feature hand-off, on demand, or as
  part of an existing loop like the Orchestrator's) reclaims scratch dirs, stale/
  consumed handoff files, and merged worktrees+branches without a human having to ask
  for it every time.
- The relevant role files (`agents/builder.md`, `agents/reviewer.md`, `agents/fixer.md`,
  `agents/pr-fixer.md`, `agents/orchestrator.md`) state explicitly, at their own
  hand-off point, what they leave behind for the sweep versus what they're expected to
  remove themselves — so the timing of cleanup is a defined contract.
- Nothing in-flight is ever deleted: the sweep only acts on artifacts tied to a
  terminal-state feature (e.g. `done`), or on worktrees/branches actually merged into
  the default branch, and it fails closed (skips rather than guesses) whenever it can't
  establish that.

## Scope / boundaries

In scope:
1. Scratch files: sweep `scratchpad/<feature-id>-<role>/` dirs whose feature has
   reached a terminal status and is no longer being read by any in-flight role.
2. Handoff files: sweep `progress/` files/dirs that are consumed/superseded (the
   `consumed:` marker pattern already used by `agents/driller.md`/`agents/planner.md`
   for `topology-handoff.md`) or that belong to a completed run/feature.
3. Git worktrees/branches: prune worktrees and local+remote branches already merged
   into the default branch, excluding anything still checked out, referenced by an
   open PR, or otherwise still live.
4. Explicit hand-off-time cleanup rules added to the relevant agent role files.

Out of scope (for this feature; may become follow-on features under E34):
- Anything already covered by E15's existing worktree-per-fix teardown for the
  parallel-fix lane specifically — this feature's worktree/branch sweep is the general
  backstop for cases outside that one lane, not a rewrite of it.
- OS-level `/tmp` scratchpad directories outside the repo (those are the host CLI's own
  per-session temp dirs, not `scratchpad/`/`progress/` in-repo state).
- Any change to what agents are allowed to write, or where — only what happens to it
  afterward.

## Chosen options

- Mechanism (resolved during intake Q&A): **automated sweep + role discipline**, not
  role-file discipline alone and not tooling alone. Rationale given: the existing
  "namespace your scratch file" prose convention already exists in
  `agents/builder.md`/`agents/reviewer.md` and clearly hasn't been enough on its own —
  654M of stale scratch data from finished features sits in this repo despite it — so a
  backstop tool matters, but a tool alone doesn't know *when* a role's own artifacts
  become safe to remove without the role files stating it.

## Constraints

- Never delete anything tied to work that isn't in a terminal state; fail closed
  (skip, report, don't guess) whenever "is this still live" can't be established
  confidently.
- Must not conflict with `agents/builder.md`'s/`agents/reviewer.md`'s existing
  namespacing convention (`scratchpad/<feature-id>-<role>/`) — build on it rather than
  replacing it, since it's how the sweep will identify which dirs belong to which
  feature.
- Must not be destructive to a human's own manual, uncommitted, or in-progress work
  outside the harness's own tracked artifacts (see the repo's general safety rules
  around `git checkout`/`reset`/`clean` and deleting branches/worktrees — this is
  exactly the kind of hard-to-reverse operation those rules already flag).

## Open questions

- Where does the sweep get invoked from — a step in `agents/orchestrator.md`'s loop
  (e.g. at feature `done` rollup), a standalone `tools/*.sh`/`.mjs` script runnable on
  demand, a `/sdd-*` command, or more than one of these? The intake mechanism answer
  says "automated sweep", not which trigger point(s).
- Exact "terminal enough to sweep" definition for `scratchpad/`/`progress/` artifacts —
  is `done` alone sufficient, or does it also need to check nothing currently
  references the path (e.g. an in-flight sibling agent)?
- Whether the worktree/branch sweep should also cover **remote** branch deletion (as
  observed: many merged-but-not-pruned `origin/*` branches), which is a different blast
  radius than local-only cleanup and may warrant its own confirmation gate.
- Whether this needs to split into multiple features by artifact kind (scratch files /
  handoff files / worktrees+branches) given the `max_requirements: 12` budget — flagged
  as a likely seam in `epic.md`'s Notes, left for the Architect/drill to decide.
