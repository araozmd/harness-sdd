# Intent — Drift check on epic rollup (Scout re-validates remaining epics)

## Problem / who
For the harness maintainer and every consumer repo: the planning tier (F01–F05) now
lets you sketch a whole roadmap of `draft` epics (`/sdd-plan`), drill them one at a
time (`/sdd-drill`), and have specs cite the architecture (F04). But rolling-wave
planning has a failure mode it doesn't yet guard: **a plan made early goes stale as
you learn.** When epic N finishes, what its implementation taught can invalidate the
assumptions behind epics N+1…M that were sketched (or even drilled and approved)
before that learning existed. Today nothing re-checks them — a stale `planned` epic
would execute on out-of-date assumptions, which is exactly the "we lacked the whole
picture" refactor this epic set out to kill, one level up.

F06 closes the loop: when an epic completes, the remaining `draft`/`planned` epics
are re-validated against what was just learned, and stale ones are demoted back to
`draft` so they must be re-drilled (and re-approved) before they can run.

## Success outcome
- When an epic **rolls up to `done`** (all its features are `done`), the Orchestrator
  triggers a **drift check**: it spawns the **Scout** (read-only) to re-validate the
  remaining `draft`/`planned` epics against what the just-completed epic produced —
  new ADRs / architecture deltas, and what its implementation revealed.
- The Scout writes a concise **drift findings** file to `progress/` listing, per
  remaining epic, whether its one-paragraph brief's assumptions still hold and, if
  not, **why** (which new ADR or learning contradicts it). The Scout **makes no state
  changes** (its read-only contract is preserved).
- A **`planned` epic judged stale demotes to `draft`** — so the F01 gate makes its
  features non-selectable until it is re-drilled (`/sdd-drill`) and re-approved. A
  `draft` epic that is stale stays `draft` (already the lowest planning state) but is
  flagged in the findings so the next drill starts from the correction.
- The demotion is **applied by the Orchestrator** (the owner of `set_status`), based
  on the Scout's findings — never by the Scout — and `state/tasks.json` is
  re-validated after each change.
- **Graceful / no-op when nothing applies:** a project with no `draft`/`planned`
  epics (legacy, or every remaining epic already `done`) sees the check run and find
  nothing to do — no failure, no noise. Existing single-feature / no-planning flows
  are unchanged.
- Documented (`store/local.md`, `docs/WORKFLOW.md`, `agents/orchestrator.md`,
  `agents/scout.md`) and carries one MINOR `VERSION` bump.

## Scope / boundaries
**In scope:**
- The **epic-rollup → drift-check** step in `agents/orchestrator.md`: when an epic's
  features are all `done`, derive+persist the epic's `done` status, then run the
  drift check before selecting the next task. (If epic-level `done` rollup is not yet
  formalized, formalize it here — additively — since it is F06's trigger.)
- A **Scout drift-check mode** in `agents/scout.md`: given the just-completed epic +
  the remaining `draft`/`planned` epics + `specs/architecture.md`/`specs/adr/*`,
  produce a structured `progress/<run>/scout-drift-<epic>.md` verdict per remaining
  epic (still-valid / stale + reason).
- The Orchestrator applying demotions (`planned → draft`) from the Scout's findings,
  with `state/tasks.json` re-validation and an audit trail (findings file; optional
  telemetry record for the drift-check phase).
- Docs (`store/local.md` rollup section, `docs/WORKFLOW.md`) + one MINOR `VERSION`
  bump + `CHANGELOG.md`. Tests (`tests/test_drift_check.sh`) wired into
  `harness.config.yaml`.

**Out of scope:**
- **Re-drilling** the demoted epic — that remains `/sdd-drill` (F03), re-run by the
  human after demotion. F06 only detects + demotes, never re-decomposes.
- Auto-editing an epic's brief/`epic.md` or any feature spec; F06 flags, it does not
  rewrite content.
- Changing F01–F05 behavior, the `draft`/`planned`/`done` enum, or feature-level
  statuses/flags. No `store/tasks.schema.json` change.
- Demoting `pending` (legacy-alias) or `in-progress`/`done` epics out of their state
  (the check concerns *future* planned work — `draft`/`planned` only; how to treat
  the legacy `pending` alias is an open question below).

## Chosen options
- **Detect-and-demote, re-drill stays manual:** F06 re-validates and demotes stale
  `planned` epics to `draft`; getting them back to `planned` is a human-run
  `/sdd-drill` (reuses F03 — no new approval mechanism, conservative direction of
  travel: demotion only *adds* a gate, never removes one).
- **Scout flags, Orchestrator acts:** preserve the Scout's read-only contract — it
  writes findings; the Orchestrator (owner of `set_status`) applies the demotion.
- **Reuse F01 + F02/F03 artifacts:** "stale" is judged against the completed epic's
  ADRs/architecture deltas (F02/F03) versus the remaining epics' briefs; the demote
  target is F01's existing `draft` state. No new status, no schema change.
- Additive change ⇒ MINOR bump, per repo versioning policy.

## Constraints
- **Backward compatible / additive:** repos with no planning tier (no
  `draft`/`planned` epics) get a no-op drift check; existing rollup behavior for
  features is unchanged; the epic-done rollup formalization must not change when a
  single-epic project reaches `done`.
- **Portability pillar:** the rollup + drift rule lives in the role files + store
  contract + docs (portable across AGENTS.md CLIs), not in `.claude/` glue.
- **Scout stays read-only:** F06 must not give the Scout write authority over
  `state/tasks.json`; the demotion is the Orchestrator's write.
- Per the permanent-suite anti-pattern memory: new tests must not freeze the exact
  `VERSION` value, must not couple a feature's CHANGELOG mention to the current
  VERSION, and must not diff DO-NOT-TOUCH files against `main`; any fixture includes
  the required root `project` field and uses a temp store, never mutating live
  `state/tasks.json`.
- Must not regress the F02/F03 "never advance an epic past its planning state without
  a human" spirit — demotion is the one *automatic* epic-status move, and it only
  ever moves **backward** (toward more gating), never forward.

## Open questions
- **Auto-demote vs human-gated demotion:** does the Orchestrator demote a stale
  `planned` epic to `draft` automatically (reporting it), or does it only *flag* and
  ask the human to confirm the demotion? (Auto-demote is conservative — it only adds
  a gate — but it is the one automatic epic-status change; confirm the least-
  surprising default.)
- **Staleness signal:** what concretely makes Scout judge an epic "stale" — a new ADR
  whose decision contradicts the epic's brief, a brief that references something the
  completed epic removed/renamed, an explicit "supersedes E0X" note? How is this made
  concrete enough to test without over-claiming semantic judgement?
- **Legacy `pending` epics:** the `pending` epic value is the gating-alias of
  `planned` (F01). Does the drift check consider `pending` epics for demotion too
  (treat like `planned`), or leave `pending` untouched?
- **Epic-done rollup formalization:** is epic-level `done` already derived
  automatically today, or has it been set by hand? If the former, F06 hooks the
  existing trigger; if the latter, F06 must add the "all features done ⇒ epic done"
  rollup — confirm and scope.
- **When zero remaining epics / no architecture:** confirm the no-op path and that it
  emits a clear "nothing to re-validate" note rather than silence.
- **Audit trail:** beyond the `progress/` findings file, should a demotion emit a
  telemetry record (a new `phase: scout` / drift record) so the rollup report can
  show "N epics re-validated, M demoted", or is the findings file enough?
- **Re-drill pointer:** when an epic is demoted, should the report tell the human to
  run `/sdd-drill <epic>` to bring it back, and should the demoted `epic.md` carry a
  one-line "demoted on drift: <reason>" note (flag-only, not a content rewrite)?
