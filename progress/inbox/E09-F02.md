# Intent — Per-developer local-overrides convention

## Problem / who
Some developers want to layer **personal, uncommitted** customization onto the
harness — extra house rules, a preferred tone, local-only shortcuts, debug notes —
without editing the shared, committed `CLAUDE.md` / `AGENTS.md` (which carry facts
true for everyone). Today the harness documents a three-layer model in
`docs/CONFIG-LAYERING.md` (project / personal / user-global) but the **personal
prompt layer** is only expressed through `.claude/settings.local.json` (permissions,
model) — there is no blessed, portable way to add personal *instructions* that the
agent reads but git never sees. The user this serves is an individual developer on a
team who wants to tailor harness behavior for themselves without forking shared docs
or polluting teammates' context.

## Success outcome
A documented, portable convention lets a developer drop a gitignored local-override
file next to the shared entrypoint and have their CLI read it **on top of** the
committed instructions, with committed instructions still winning on genuine
conflicts. It leans on each CLI's **native** local-override mechanism rather than
inventing a bespoke one, and it ships wired-in (installer seeds the ignore, docs
explain it) so a developer just creates the file and it works.

## Success outcome — evidence
- The generated entrypoint marker blocks conditionally reference a local-override
  file (e.g. "if `AGENTS.local.md` exists beside this file, also read it") for CLIs
  that do not auto-load one.
- The installer append-seeds the personal-layer ignores (`AGENTS.local.md`,
  `CLAUDE.local.md`) into the project-root `.gitignore` using the **existing**
  append-only seeding block — never clobbering existing entries.
- `docs/CONFIG-LAYERING.md` documents the personal *prompt* layer alongside the
  existing personal *settings* layer, including per-tool caveats.
- `tests/test_install.sh` asserts the new ignore entries and the conditional
  reference are produced by the installer.

## Scope / boundaries
**In scope**
- A conditional local-override reference in the generated marker blocks
  (`CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, and the Antigravity/OpenCode glue as
  applicable).
- Append-only `.gitignore` seeding of the personal-layer files, folded into the
  installer's existing gitignore-seeding logic (NOT a runtime/Builder task, NOT a
  hand-added entry — see Constraints).
- Documentation in `docs/CONFIG-LAYERING.md`, and the umbrella variant in
  `umbrella.gitignore.example` if the same personal files apply to the shared-repo.
- Test coverage asserting the installer wiring.

**Out of scope**
- Reimplementing local-file loading the CLIs already do natively — lean on
  `CLAUDE.local.md` (Claude Code auto-loads it) and `AGENTS.override.md` (Codex)
  rather than building a loader.
- Any change to the committed shared instructions' precedence model beyond
  "committed wins on conflict, local adds on top."
- Personal *settings* (permissions/model) — already covered by
  `.claude/settings.local.json`; this feature is about personal *instructions*.

## Chosen options
- Grouped with E09-F01 under the new epic **E09 "Harness doc quality &
  customization"** (human picked "one new epic for both").
- The human's explicit steer: **`.gitignore` seeding belongs in the installer's
  existing append-only block** (harness initialization), not a per-feature or
  runtime task — and it must be asserted in `tests/test_install.sh`.

## Constraints
- **Lean on native mechanisms, don't reinvent.** Claude Code auto-loads
  `CLAUDE.local.md`; Codex reads `AGENTS.override.md`. The harness contribution is a
  portable `AGENTS.local.md` convention (for tools without native auto-load) + the
  ignore seeding + docs — a thin convention, not a new engine.
- **Append-only, never clobber.** The `.gitignore` seeding reuses the installer's
  existing append-only behavior; an existing `.gitignore` entry is never removed or
  duplicated.
- **Backward-compatible.** With no local-override file present, behavior is exactly
  as today. Purely additive.
- **Touches the installed body** (`harness-install.sh`, generated marker blocks,
  `docs/CONFIG-LAYERING.md`, possibly `umbrella.gitignore.example`) → **warrants a
  `VERSION` bump** (SemVer MINOR) in the same PR, per the repo versioning policy.
- **Installer wiring must be asserted** in `tests/test_install.sh` (recurring Codex
  finding — do not skip).

## Open questions
- **Which local filename per tool?** Standardize on `AGENTS.local.md` as the portable
  name and *also* honor each tool's native file (`CLAUDE.local.md`,
  `AGENTS.override.md`), or reference only the portable one? Recommend: reference the
  portable `AGENTS.local.md` in the marker block, and additionally ignore the native
  per-tool files so they work out of the box where the CLI auto-loads them.
- **Precedence wording.** How explicitly should the marker block state that committed
  instructions win on conflict and the local file only *adds*? (Some CLIs concatenate
  with nearest-wins; keep the wording tool-agnostic.)
- **Per-tool caveats to document.** Gitignored local files don't exist in fresh git
  worktrees (so cross-worktree personal rules should import from `~`), and Cursor has
  been reported to ignore gitignored rule files. Which caveats belong in
  `CONFIG-LAYERING.md` vs. omitted as out-of-scope tools?
- **Umbrella/shared-repo scope.** Should the shared-repo (`--shared-repo`) umbrella
  root also seed these personal ignores, or is the project-root seeding enough?
