# Intent — execution.builder.backend + pr_loop.enabled prompts in the installer picker

## Problem / who
The installer asks the human exactly one question — which front-ends to stamp — and every
other install-shaping choice is a hand-edit of `.harness/harness.config.yaml` discovered
by reading source comments. Two of those choices matter enough to be asked out loud:

- **`execution.builder.backend`** (`harness.config.yaml:65`): in-session vs delegate. This
  is the seam an external orchestrator plugs into, and nothing at install time hints it
  exists.
- **`pr_loop.enabled`** (introduced by E18-F01): whether the harness's review workflow
  includes the Codex PR cycle. This is not a preference — `/sdd-pr-loop` only functions on
  a repo with the Codex GitHub App installed and an authed `gh`. On a repo without that
  setup the correct value is *off*, and only the human knows which repo is which.

## Success outcome
The choices that shape a harness install are made once, visibly, during install — and
changed the same way, by re-running it. A human installing into a repo with no Codex App
turns the review loop off at the prompt instead of discovering a hung 15-minute poll.

## Scope / boundaries
**In scope**
- Interactive prompts for `execution.builder.backend` and `pr_loop.enabled`, pre-selected
  from current values on a re-run.
- Writing both through the **existing append-only, value-preserving config migration**.
- When `pr_loop.enabled` is off: no `/sdd-pr-loop` glue stamped, and no dangling
  instruction to run it.

**Out of scope**
- Introducing the `pr_loop` config block itself — that is E18-F01. This feature surfaces
  a key that already exists.
- A standalone `/sdd-config` command or any reconfiguration path other than re-running
  the installer.
- Turning every `harness.config.yaml` key into a prompt. Only these two.

## Chosen options
- **Both toggles live in the installer**, not a separate tool — re-running the installer
  is already the harness's post-install reconfiguration path, chosen deliberately over a
  `/sdd-config` command to avoid two surfaces drifting apart.
- **Defaults unchanged for anyone pressing Enter**: `in-session`, plus whatever E18
  establishes for `pr_loop`.

## Constraints
- **Never rewrite `harness.config.yaml` wholesale.** Use the existing append-only,
  value-preserving, idempotent migration so a human's comments and unrelated hand-edits
  survive a re-run. This is load-bearing — the file is heavily commented by design.
- **Non-interactive runs must be unaffected** absent an explicit override; CI keeps
  today's behavior exactly.
- Degrade the same way front-end selection already does: raw-mode TUI when available,
  numbered fallback otherwise, override when non-interactive.
- Depends on **E18-F01** (creates the `pr_loop` block) and **E19-F01** (edits the same
  `resolve_agents` region; sequencing avoids a conflict).
- Any installer-invoking test must sandbox `CODEX_HOME`.

## Open questions
- **The existing `tui_select` (`harness-install.sh:619`) is built around a homogeneous
  list of on/off agent keys.** These two toggles are not agent keys — one is an enum, one
  is a boolean, and neither belongs in the same checkbox column. Whether to extend the
  TUI into a mixed list, add a second screen, or ask a plain follow-up prompt after the
  picker confirms is the Architect's call. A plain follow-up is the cheapest and least
  likely to regress the existing raw-mode/fallback paths.
- Whether these need env/flag twins (`--pr-loop=`, `--builder-backend=`) for scripted
  installs the way `--agents` has `HARNESS_AGENTS`. Depends on whether anyone actually
  scripts them; do not add surface speculatively.
- How an install with `pr_loop.enabled: true` should behave when the Codex GitHub App
  preflight (from E18-F01) fails at *install* time rather than at run time — warn and
  proceed, or refuse to enable. Warning is likely correct, since the App can be installed
  after the harness.
