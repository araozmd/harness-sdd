# Intent — GitHub Projects sync via gh CLI (no MCP)

## Problem / who
Teams on GitHub Projects want the harness's `tasks.json` reflected on their board so
non-CLI stakeholders can see status, and (with E10 ownership) so parallel developers
don't duplicate work. The integration must work in **MCP-restricted** enterprises, so
it uses the **`gh` CLI** the developer is already authenticated with — no MCP server.

## Success outcome
Running the sync projects the current `tasks.json` (epics/features and their status)
onto a configured GitHub Project via `gh`, idempotently, with no MCP dependency and no
new credential to provision beyond the developer's existing `gh auth`.

## Success outcome — evidence
- A sync command/hook writes harness state to a GitHub Project using only `gh`
  (`gh project ...` / `gh api ...`), no MCP.
- Re-running reconciles instead of duplicating (existing items are updated, not
  re-created).
- Config lives in `harness.config.yaml` under the existing `mirror.board` shape
  (provider/owner/project_number/repo) — no new committed secret.
- Behavior is inert when no GitHub Project is configured (matches today).

## Scope / boundaries
**In scope**
- Outbound projection of `tasks.json` → GitHub Project via `gh` CLI.
- Idempotent reconcile (map feature id → project item).
- Docs + installer wiring + `tests/test_install.sh` assertions for any new glue.

**Out of scope**
- Inbound agent-read of ownership / atomic claims — that is the E10 ownership model
  (E10-F03), not a bidirectional mirror here.
- Jira / Monday / Azure — their own epics (E12/E13/E14).
- MCP transport of any kind.

## Chosen options
- Provider-per-epic structure (human's explicit choice over a shared-adapter epic).
- Transport = `gh` CLI, no MCP.

## Constraints
- **`gh` CLI only, never MCP** (enterprise MCP blocks). REST via `gh api` if needed.
- **Reconcile with the EXISTING mirror.** A github-projects one-way mirror already
  exists (`store/board-mirror.md`, `tools/sync-board.mjs`). Extend/complete it rather
  than fork it; preserve its "one-way projection, agents never read the board"
  invariant.
- **Installed-body change** → **VERSION bump** (MINOR). Installer wiring asserted in
  `tests/test_install.sh` (recurring Codex finding — do not skip).

## Open questions
- **Extend or replace the existing mirror?** `tools/sync-board.mjs` already does
  GitHub Projects — is F01 filling gaps (e.g. a pure-`gh` path vs. the current API
  path) or a rewrite? The architect must reconcile to avoid two GitHub code paths.
- **`gh project` scopes.** Classic vs the current Projects (v2) GraphQL surface `gh`
  exposes — pin which Project type is supported.
- **Assignee sync.** Should this feature also project the E10 `owner` → GitHub issue
  assignee, or leave that to E10? (Recommend leave the ownership semantics to E10; F01
  just projects status.)
