# Intent — A feature-level park: hold a real feature before it has been specced

## Problem / who
Reported from a target repo running an installed `.harness/`. An operator needed to **park a
real feature** — one that will need a full spec, but is blocked on a Meta review cycle and
three product decisions that are not board dependencies. There is no way to express that.

Verified in this repo's own `tools/next-task.mjs`:

- `:352` — `if (feature.sdd) return 'architect';` on `pending`. **`autonomous` is never
  consulted on that branch.**
- `:353`, `:370`, `:372` — the only three places `autonomous` bites: the quick-fix lane
  (`pending + !sdd`) and the `spec-ready` approval pause. It gates the *spec-ready pause*,
  not the Architect.
- Feature status enum is `pending, spec-ready, in-progress, in-review, done`. **Epics get
  `draft`; features do not.**

So the route table has no row for "this feature is real and not yet workable". The only lever
that bites at `pending` is `sdd:false + autonomous:false`, which routes into the *gated quick
fix* lane. That is what the operator had to use, and it **mislabels a feature that needs a
full spec as a fix that needs none** — they had to write a prose correction inside the board
entry warning the next reader not to skip the spec. A board entry that needs a note saying
its own field is lying is the defect.

The user is anyone doing rolling-wave planning: features get seeded before the decisions that
unblock them exist. `depends_on` covers board-internal blocking; nothing covers external
blocking.

## Success outcome
A feature can be parked with a reason, at any status, without any other field having to lie.
`/sdd-next` skips it; targeting it returns blocked with the reason; unparking restores exactly
the routing it had before.

## Scope / boundaries
In scope:
- A `parked` field on a feature carrying **why, and what unblocks it**.
- One blocker record in `featureBlockers`, mirroring `gated-epic`.
- Route/status table documentation.
- Tests.

Out of scope:
- **Repointing `autonomous`.** Making `autonomous:false` gate the Architect is the obvious
  one-line fix and it is wrong. Measured on this board, it would silently park five real
  features — E17-F02/F03/F04, E21-F05, E24-F04 — including the one `/sdd-next` selects right
  now. `autonomous:false` today means "do not auto-approve my spec, do not auto-build"; it has
  never meant "do not spec it". Changing that is a breaking semantic shift for every installed
  target, not a fix.
- A `parked` **status** value. See Constraints — it loses information.
- Any change to `featureRoute`. The park is a blocker, not a route.

## Constraints
- **Mirror `gated-epic` (`:364`), which is the codebase's existing answer to "exists,
  understood, not actionable".** Note what it does *not* do: it leaves `featureRoute` alone
  and holds the feature out with a blocker record. A feature-level park is the same concept
  one level down and should be built the same way, so the two read alike.
- **A field, not a status enum value.** Adding `parked` to the status enum mirrors epics but
  loses where to return to: a park can arrive *after* speccing (`spec-ready`, then product
  says hold), and a status-based park has nowhere to record the prior state. A field composes
  with every status and survives the round trip.
- **The reason is required** (`minLength: 1`) — presence means parked. The whole failure mode
  being fixed is a park with no legible reason, so a bare boolean would reproduce it.
- `sdd` must keep telling the truth: a parked feature stays `sdd:true` if it needs a spec.
- Additive schema; existing boards carry no `parked` key and must be unaffected.
- Installed body ⇒ `VERSION` **MINOR** bump.
- POSIX sh / `dash` for any test; suites must pass under `sh tools/run-tests.sh`.

## Open questions
- **Does a park block dependents, and how legibly?** A parked feature is not `done`, so
  `depends_on` already stalls its dependents — probably correct, but today they would report a
  generic `unmet-dependency` and the *reason* would be invisible one hop away. Worth a
  distinct detail on the dependents so a stalled chain explains itself.
- **Slices as well as features?** Slices have their own status enum (including `failed`).
  Symmetry argues for both; scope argues for features first. Decide explicitly rather than
  drifting.
- **Should `parked` survive a status transition, or be cleared on unpark?** If a Builder moves
  a parked feature to `in-progress`, is that a bug to reject or a legitimate override? Leaning
  reject — a park that a transition silently clears is not a park.
- Is there a reporting surface (`/sdd-next` summary, board mirror) that should list parked
  features so they do not become invisible? Parking something and forgetting it is the obvious
  failure mode of this feature.
