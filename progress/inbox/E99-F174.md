# Intent — Concurrent sessions can allocate the same E99 fix id (#253)

## Problem / who
`tasks-lock.py add-feature` allocates `max(local F##) + 1`
(tools/tasks-lock.py ~2104-2113). The advisory lock serializes writers on ONE board file.
It cannot see a row another session has seeded on a board branch that has not landed
yet. Two sessions can therefore mint the same `E99-F##`. The collision only shows up as
a git merge conflict, where two different features share one id.

Two things make that hard to recover from:
- `agents/fixer.md` forbids renumbering (~93, ~127, ~244), so the only way out is an
  undocumented hand renumber with progress files moved by hand.
- `tools/validate-board.py` has no duplicate-feature-id check, so a bad union of the two
  boards would pass `init.sh`.

This affects any project that runs concurrent agent sessions, which the downstream
umbrella does routinely.

## Success outcome
1. **Narrower race.** `add-feature` allocates strictly above the max `F##` for the epic
   across every board copy git can see without network or side effects:
   - the working board;
   - the board at HEAD;
   - the board on every local branch and every remote-tracking ref
     (`git for-each-ref refs/heads refs/remotes`, then `git show <ref>:<board path>`,
     where `<board path>` is the path relative to the repo root, correct for both the
     source layout and an installed `.harness/` target).

   It never fetches; that is the operator's choice. A ref whose board is missing or
   unparsable is skipped, with a note on stderr. The local board still has to parse, as
   today. Outside a git repo it falls back to the local-only behaviour.
2. **Collisions fail loudly.** `validate-board.py` rejects two features with the same
   `id` anywhere on the board. The same goes for two epics with the same id, if that
   check is missing too. `init.sh` therefore hard-fails on a bad union.
3. **A documented recovery path.** Add `tasks-lock.py renumber <old-id> <new-id>`. It is
   allowed only when ALL of these hold:
   - the row is not `done`;
   - it has no `landed` block;
   - `<new-id>` is in the same epic, is free, and is above that epic's max across the
     visible refs.

   It rewrites the row's `id` and `spec_path` slug prefix. It also moves
   `progress/inbox/<old>.md` to `<new>.md`, updating the frontmatter `feature:`, and moves
   the `progress/<old>/` directory, if present. It refuses anything else.

   Also handle the duplicate case: when both colliding rows share the old id, `renumber`
   alone is ambiguous. Add a disambiguator, e.g. `--title-match` or
   `--index`, or document it.
4. **Docs.** `agents/fixer.md` gets a short "duplicate fix id" rule: the session whose
   board lands SECOND renumbers its OWN un-landed row with `renumber` before merging,
   then re-runs `init.sh`. Keep the existing "never renumber" rule for landed or done
   rows and make the exception explicit. Mention it in store/local.md or
   docs/WORKFLOW.md if that is where the conflict rule lives.

## Scope / boundaries
In scope: tools/tasks-lock.py (`add-feature` allocation + new `renumber`),
tools/validate-board.py, agents/fixer.md, and the relevant docs and tests.

Out of scope:
- a network reservation service;
- changing the id format;
- renumbering landed or done rows.

## Chosen options
- Visible-refs max plus loud duplicate validation plus a guarded renumber, rather than a
  remote reservation. This is cheap, offline and deterministic, and the issue lists it
  as an acceptable outcome.

## Constraints
- Fail closed: the local board must parse, and `renumber` refuses on any doubt.
- Everything runs under the existing advisory lock, and a renumber is one atomic board
  write.
- No VERSION confusion: tasks-lock.py, validate-board.py and agents/ ship to installs,
  so bump the PATCH to 0.96.2 and update the CHANGELOG.
- Every guard has a test row that kills its mutant.
- Python stdlib only.
