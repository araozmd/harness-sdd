# Intent — Installer-stamped escalation arming, so the automatic default can return

## Problem / who

E17-F03 shipped the escalation machinery but had to ship it **off**
(`escalation.after_rejections: 0`). The brief's success outcome was *"a task that fails review
twice is retried by `builder-heavy` automatically, **without a human noticing**"*. It now
needs a one-line opt-in first. This feature is what buys the default back.

The reason it shipped off is recorded in two review findings, both reproduced on real targets:

1. **#3716706727** — with `models.builder: standard` and `models.builder-heavy: inherit` (the
   shipped default), the Builder shim gets `model: sonnet` and the heavy role gets **no model
   key**. Escalating there abandons the operator's configured Builder model for the session
   default: a **downgrade**, landing exactly when the build is struggling.
2. **#3716777878** — the first fix armed on "the heavy tier is not `inherit`". On `codex` and
   `opencode` a tier stamps **nothing** without a matching `pin.<front-end>.<tier>`, so
   `builder: standard` + `pin.codex.standard` + `builder-heavy: reasoning` (unpinned) gives
   `builder.toml` a model and `builder-heavy.toml` none. Same downgrade, one level deeper.

Both attempts failed for the same reason: **`tools/builder-role.sh` was re-deriving a subset
of the installer's `resolve_model`**, which owns the per-front-end alias tables and the pin
rules. Reproducing that in a routing tool is a defect per front-end, and it produced two in
two rounds.

## Success outcome

`escalation.after_rejections` can ship at a positive default again, because the harness
**knows** — rather than guesses — whether escalating would actually raise the model on the
front-end that will run the build. An operator who configured a heavy tier correctly gets
automatic escalation with no opt-in; one who did not gets no escalation and a legible reason.

## Scope / boundaries

**In scope**
- **The installer stamps the verdict.** `install_one` already calls `resolve_model` for every
  role × selected front-end. Have it record, per front-end, whether `builder-heavy` resolves
  to a non-empty model **and** how that compares to `builder`'s. One artifact, written where
  the existing stamps live (`.harness/`), reclaimed on deselect like every other stamp.
- **`tools/builder-role.sh` reads that verdict** instead of inferring anything. Its purity
  contract stays: arguments plus config plus this one stamp. It must still never read the
  spec body, `progress/`, or `git`.
- **Flip the default** to a positive threshold once the verdict is authoritative, and update
  every doc that states the default — `tests/test_escalation.sh::docs_agree_with_the_shipped_default`
  pins that and will fail until they agree.

**Out of scope**
- Any change to `resolve_model` itself, or to the tier vocabulary (E17-F01).
- Any change to what `builder-heavy` does — **ADR-0002 still binds**: escalation is routing.
- Demotion, cost-based policy, the worker roster (E17-F04).

## Constraints

- **Do not re-implement `resolve_model`.** That is the whole point. If the verdict cannot be
  produced by the installer, this feature fails rather than approximating it a third time.
- **The stamp must be reclaimed on deselect** and must not make an unconfigured target grow
  state a never-configured one lacks — the E17-F02 `.opencode.stamp` precedent, including
  that a *symlinked* stamp is never followed for read or write.
- **A target that never re-runs the installer must not silently start escalating.** Decide and
  state what an absent stamp means; "absent ⇒ off" is the safe direction.
- Which front-end is running is not knowable from the config alone. Decide explicitly whether
  the verdict is per-front-end or a conservative AND across selected ones, and say why.
- Budget: `change_size.max_requirements: 12`.

## Open questions

- **Where does the stamp live, and what shape?** A single scalar in `.harness/`, a per-front-end
  file under `.harness/.model-agents/`, or a key the installer rewrites in the config. The
  config is operator-owned, so writing a *derived* value there is probably wrong — state the
  cost either way.
- **Per-front-end or conservative AND?** The Orchestrator does not reliably know which
  front-end it is running under. An AND across selected front-ends never downgrades anyone but
  disables escalation for a mixed target where only one front-end is misconfigured.
- **Is "heavy resolves to something" enough, or must it differ from `builder`?** Equal models
  make escalation a harmless no-op that still records a role change; strictly-weaker is the
  case to prevent. Decide whether equal is worth allowing.
