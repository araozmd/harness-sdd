# Fix — stamp per-role `model_reasoning_effort` into Codex agent definitions

## Problem
`gen_codex_agent()` (`harness-install.sh:4330-4341`) writes exactly four keys into each
`.codex/agents/<role>.toml`: `name`, `description`, an optional `model`, and
`developer_instructions`. So on Codex the harness can vary a role's **model** and nothing
else.

That mismatches how Codex actually exposes capability. Every model in the live catalogue
supports a reasoning-effort ladder — `low`/`medium`/`high`/`xhigh`/`max`, with `ultra` on
`gpt-6-astra` and `gpt-5.6-sol` — and a user's global `~/.codex/config.toml` typically sets
one value (`model_reasoning_effort = "high"`) that then applies to every role. Consequences:

- The natural Codex escalation — **same model, higher effort** — cannot be expressed, so
  `escalation_verdict` reads `same` and the harness refuses to arm (`harness-install.sh:479-486`).
- A `cheap`-tier role such as `doc-critic` still inherits global `high` effort, which is the
  opposite of what the tier means.

**This is fixable, and that was verified empirically rather than assumed** (Codex CLI 0.154.0,
2026-09-16). Writing `model_reasoning_effort = "xhigh"` into an agent toml is accepted
silently, while a deliberately bogus key in the same position is **rejected** with
``unknown field `totally_bogus_key_zz` ``. Because the parser denies unknown fields, silence
is acceptance, not indifference — `model_reasoning_effort` is a recognized member of the
agent-role schema.

## Intended fix
Let a role's effort be configured and stamped on Codex, without inventing new vocabulary
where existing vocabulary will do and without teaching the harness to rank models
(`harness-install.sh:479-481` — "Ranking is yours").

Open design question for the implementer, to be settled and recorded: whether effort rides
the existing tier (each tier implies an effort on Codex) or becomes its own configurable
axis (e.g. a `models.effort.<role>` map or a `pin.codex.effort.<tier>` key). Prefer the
option that adds no new config key if one works — `docs/RATIONALE.md`'s ablation doctrine.

## How to verify
- A role configured for a given effort stamps `model_reasoning_effort = "<value>"` into its
  `.codex/agents/<role>.toml`; a role with none stamps no such key and its file is
  byte-identical to today's output.
- **Unknown keys are fatal, so guard the value.** An invalid effort must not reach the file:
  Codex responds to an unrecognized key by discarding the WHOLE role definition
  ("Ignoring malformed agent role definition"), so a bad stamp silently deletes the role
  rather than degrading it. Mirror the existing OpenCode `provider/model` guard
  (`harness-install.sh:1878-1888`), which exists for exactly this reason.
- If effort participates in escalation, `escalation_verdict` must read `raise` when builder
  and builder-heavy differ **only** by effort on the same model — today it would read `same`.
- Confirm against the real CLI, not only fixtures: a stamped file must load without a
  `codex doctor` startup warning.
- `./init.sh` exits 0; `./tools/run-tests.sh` green.

## Notes
Depends on E99-F159 (the `frontier` tier) only for shared vocabulary if the tier route is
chosen; it is otherwise independent.

Separately and needing no harness change: the four Codex tier pins are pure config, valid
once `frontier` lands — `pin.codex.frontier: "gpt-6-astra"`, `pin.codex.reasoning:
"gpt-5.6-sol"`, `pin.codex.standard: "gpt-5.6-terra"`, `pin.codex.cheap: "gpt-5.6-luna"`.
Slugs read from this machine's `~/.codex/models_cache.json`; that cache is per-account and
per-machine, and codex pins are written VERBATIM with no validation, so a wrong slug fails
silently at load time.
