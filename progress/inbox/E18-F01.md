# Intent — /sdd-pr-loop command + vendored Codex watcher, gated by pr_loop.enabled

## Problem / who
The human is uninstalling the multi-cli-orchestrator (MCO) skills from
`~/.agents/skills/`. The harness tells its own agents to run `/pr-loop` in three places —
`agents/orchestrator.md:102`, `CLAUDE.md:20`, `docs/WORKFLOW.md:325` — but ships no such
command; it comes from MCO. Once those skills are gone, the harness's documented review
workflow references a command that does not exist. The same is true for any fresh
consumer who installs the harness without MCO.

Verified sweep: `/pr-loop` is the **only** MCO coupling left in the harness body. There
are no `MCO_*` env references, no `route-task`, no `start-feature` in `agents/`,
`AGENTS.md`, `CLAUDE.md`, `docs/`, or `tools/`. `route-task` and `start-feature` need no
replacement — `/sdd-next` and `/sdd-new` already cover them.

## Success outcome
A harness install with zero MCO skills on disk drives a full Codex review cycle:
trigger `@codex review`, poll for the review in the background, classify severity
(P0/P1 blocking, P2/nit ignored), fix blocking findings via subagent, escalate on
round 3, label `needs-human` and stop on round 4, merge when green. The human can
uninstall the MCO skills and notice nothing missing.

## Scope / boundaries
**In scope**
- Vendor `~/.agents/skills/pr-loop/` (6 files, ~618 lines, 48K) into the harness.
- Emit the runbook as a **`/sdd-pr-loop` command** via the existing `HARNESS_SDD_CMDS`
  machinery — generated into every selected front-end from the neutral CMDDIR, removed on
  deselection, asserted in tests.
- Vendor `scripts/wait-for-codex.sh` under the harness dir (e.g. `tools/`), added to the
  installer `copy` block and the `chmod +x` list, and invoked by a **harness-relative
  path**. The skill currently hardcodes `~/.agents/skills/pr-loop/scripts/wait-for-codex.sh`;
  left as-is this breaks the instant MCO is uninstalled.
- Vendor the four `agents/<front-end>/pr-fixer.*` definitions (claude-code, codex,
  opencode, antigravity), gated by `AGENT_KEYS` and registered in the harness-owned
  removal ledger.
- A `pr_loop:` config block carrying at least `enabled`, `auto_merge`, `max_rounds`,
  `blocking_severities`.
- A preflight check that fails fast with a clear diagnostic when the Codex GitHub App or
  `gh` auth is missing.
- `tests/test_pr_loop.sh`, wired into `verification.test_command`.
- Repoint the three `/pr-loop` prose references.

**Out of scope**
- Surfacing `pr_loop.enabled` in the installer TUI — that is E20-F01. This feature
  introduces and honors the key; hand-editing it is acceptable until E20 lands.
- Vendoring `route-task` or `start-feature`. Not needed.
- Any change to `store/tasks.schema.json` or a fork of a canonical `agents/*.md` role.

## Chosen options
- **Ship as a command, not a skill.** The installer has no skill-emission machinery at
  all (zero `skills` matches in `harness-install.sh`); adding it would be net-new
  install/removal/test surface used by nothing else, and would be Claude-Code-only. The
  command path reuses `HARNESS_SDD_CMDS`, the removal ledger, and the CMDDIR mirror that
  keeps all five front-ends byte-identical. The Orchestrator invokes the loop explicitly,
  so description-triggered activation is not lost value.
- **Auto-merge defaults ON**, behind a `pr_loop.auto_merge` key — preserves exactly
  today's MCO behavior so the human's existing loops feel identical after the swap.
- **Clean break on env vars.** Read `HARNESS_*` only; no `MCO_*` fallback. Simpler
  surface, and MCO is being uninstalled anyway.
- **Gated by `pr_loop.enabled`**, because the loop is not universally applicable (below).

## Constraints
- **The loop requires the Codex GitHub App** installed on the target repo plus an authed
  `gh`. Without it, `@codex review` is posted and the watcher polls to its 15-minute
  `POLL_CEILING` for a review that can never arrive. The command must detect this and
  fail fast, and the workflow must be gate-able off entirely.
- **Installer wiring and test assertions are not optional.** Every new `/sdd-*` command
  must be generated by `harness-install.sh` *and* asserted in the test suite. Codex has
  filed this exact gap as a P1 twice (E15-F03, E06-F03). The deselect path must remove it.
- **`tests/test_pr_loop.sh` must not freeze the exact `VERSION`** or diff DO-NOT-TOUCH
  files against `main` — that anti-pattern has been reverted three times.
- Any installer-invoking test must **sandbox `CODEX_HOME`**, since codex glue is global
  and shared across targets.
- The vendored watcher must keep its background-execution contract: it is launched with
  `run_in_background`, polls every `POLL_INTERVAL` (default 60s) to `POLL_CEILING`
  (default 900s), and writes `pr.json`, `review-comments.json`, `issue-comments.json`,
  `reactions.json` into the round dir. All three comment sources are required — `gh pr
  view` alone does not return Codex's inline findings.
- Codex signals a clean review in **three** different forms (👍 reaction, a summary
  banner, or a "didn't find any major issues" comment); poll freshness must be judged by
  `created_at > trigger`, not by `commit_id`.

## Open questions
- **Conditional prose is not currently expressible.** The harness body is copied
  *verbatim* (`copy agents`, `copy docs`) — it is not templated per install — so
  `agents/orchestrator.md` cannot have its `/pr-loop` paragraph gated by
  `pr_loop.enabled` without new templating machinery. Recommended resolution: keep the
  prose unconditional but phrase it by **availability** ("if `/sdd-pr-loop` is
  installed…"), and let the absent command be the signal. The Architect should confirm
  rather than introduce a marker-block templating layer for one paragraph.
- Where exactly the watcher belongs — `tools/` alongside the other executables, or a
  dedicated subdir — and whether the four `pr-fixer` definitions reuse the `emit_agent`
  path or need their own, given `codex/pr-fixer.toml` is a new artifact shape for a
  front-end that today stamps only global prompts.
- Whether `max_rounds` / `blocking_severities` / poll cadence belong in the `pr_loop:`
  config block or stay `HARNESS_*` env-only. The human chose a clean break to `HARNESS_*`
  for env vars but did not rule on config-vs-env for each individual knob.
- Whether F01 should be decomposed. Natural seams: (a) command + watcher + config,
  (b) per-front-end `pr-fixer` definitions, (c) de-MCO pass + docs.
