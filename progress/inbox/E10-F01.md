# Intent — Ownership primitive: owner field in TaskStore + scoped /sdd-next

## Problem / who
The harness serves solo developers and teams from one install, but the team path has
a gap. `/sdd-next` (the Orchestrator) picks the next actionable feature **across the
whole board**, and the local TaskStore feature entry has **no `owner`** (only the
GitHub board-mirror carries an `assignee`, and agents never read the mirror). In a
shared-repo umbrella the `tasks.json` is shared state, so two developers each running
`/sdd-next` can pick overlapping work or race on the same file. The user this serves
is a **team of developers** who want the intended workflow — product + tech lead lay
down all epics as drafts via `/sdd-plan`, then each developer takes one epic and owns
its `/sdd-drill` + `/sdd-next` — to actually hold, instead of being an unenforced
convention. It must not regress the solo developer.

## Success outcome
Ownership is a first-class, backward-compatible field in the TaskStore, and a
developer can scope `/sdd-next` to their own work so parallel developers on a shared
`tasks.json` stop colliding. With no owner set anywhere, the harness behaves **exactly
as it does today** (solo, board-wide selection).

## Success outcome — evidence
- The TaskStore schema carries an optional `owner` field (at least at feature level;
  epic level too if the driller/architect confirms two-level ownership is wanted here
  vs. deferred to F02).
- `/sdd-next` supports a scoped mode (e.g. `--mine` / a configured identity) so the
  Orchestrator only considers features owned by (or unassigned and claimable by) the
  current developer.
- With no `owner` present, `/sdd-next` behaves identically to today — proven by an
  existing-behavior regression test.
- Installer wiring for any new command/glue is produced by `harness-install.sh` and
  asserted in `tests/test_install.sh`.

## Scope / boundaries
**In scope**
- Add the optional `owner` field to `store/tasks.schema.json` (backward-compatible).
- Teach the Orchestrator contract (`agents/orchestrator.md`) + the `/sdd-next` command
  glue to respect `owner` and a scoping flag/identity.
- Docs: `docs/WORKFLOW.md` / `store/local.md` describe the ownership field and scoped
  selection.
- Tests: existing-behavior regression (no owner ⇒ unchanged) + installer-wiring
  assertions.

**Out of scope**
- The team-claim *rules* (claim epic → drill unassigned → claim feature on
  `/sdd-next`) and "board-configured ⇒ team" mode detection — that is **E10-F02**.
- Any live board/backend integration or atomic remote claims — that is **E10-F03**,
  and it belongs in the store **backend** abstraction, not the one-way board mirror.
- Making the board mirror bidirectional — explicitly rejected (see epic notes).

## Chosen options
- Ownership-truth fork resolved to **"owner field in tasks.json first"**
  (foundation-first) — the human's pick. Board stays a one-way mirror; the live
  authoritative backend is deferred to F03.
- Grouped under a new epic **E10 "Team coordination & ownership"** with F02/F03 on the
  roadmap in `specs/epics/E10-team-coordination/epic.md`.

## Constraints
- **Backward-compatible / additive.** `owner` is optional; absent ⇒ today's behavior
  exactly. The schema change is SemVer **MINOR**, not a MAJOR migration.
- **Do not make the board mirror bidirectional** and do not have agents read the board
  (`store/board-mirror.md` invariant: `tasks.json` is truth, mirror is a disposable
  one-way projection). Live agent-read ownership, if ever built, is F03 as a backend.
- **Touches the installed body** (`store/tasks.schema.json`, `agents/orchestrator.md`,
  the generated `/sdd-next` glue across Claude/Antigravity/OpenCode, docs) →
  **warrants a `VERSION` bump** (MINOR) in the same PR, per the versioning policy.
- **Installer wiring must be asserted** in `tests/test_install.sh` (recurring Codex
  finding — do not skip). Schema-touching tests must not freeze an exact VERSION or
  diff DO-NOT-TOUCH files against main (known permanent-suite anti-pattern).
- **Portable.** The Orchestrator contract change must be tool-agnostic (AGENTS.md
  compatible), not Claude-specific.

## Open questions
- **Owner identity format.** Free string, git `user.name`/email, or `gh` login? Pick
  one that resolves the same across a team (recommend a configurable identity, e.g.
  reuse the board-mirror `assignee: "@me"` resolution pattern so a shared config
  reflects whoever runs it).
- **Epic-level owner, feature-level, or both here?** F01 needs at least feature-level;
  epic-level "claim" may be F02's job. Confirm the minimal cut for F01.
- **How is scoping invoked?** A `/sdd-next --mine` flag, a configured
  `execution`/`workflow` identity in `harness.config.yaml`, or both?
- **Claimable-vs-owned selection.** Should scoped `/sdd-next` also pick up *unassigned*
  actionable work and claim it, or only work already owned by me? (The claim-on-select
  behavior may be better left to F02 — confirm the boundary.)
- **Release / reassign.** Does F01 need an unassign/hand-over path, or is that F02?
