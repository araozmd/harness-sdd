# Intent — `init.sh` drift guard: refuse to run on an unlanded harness

## Problem / who
`harness-install.sh` stamps `VERSION` into `<target>/.harness/.harness-version`
(`harness-install.sh:2194`). That stamp is read by exactly one caller: the *next*
installer run, to decide upgrade-vs-fresh (`harness-install.sh:1794`). At runtime it is
dead metadata — `init.sh` contains no reference to it, to `VERSION`, or to whether
`.harness/` is dirty. Grep confirms zero hits.

So an upgrade that was written but never committed is indistinguishable at runtime from
one that was landed. That is not hypothetical: the v0.50.x cascade across the five
`~/repos/viernes` children left 26–29 uncommitted files in each, and every Builder and
Reviewer spawned there since has been reading agent prompts that no commit records and no
reviewer approved. Three of those children ran the change-size classifier against a
committed `harness.config.yaml` with no `change_size` block, while the block sat present
but uncommitted on disk.

The user is anyone whose repo runs agent work off an installed harness — most acutely the
umbrella operator, who has N targets and no way to see which are consistent.

## Success outcome
Running `./init.sh` in a target whose installed body does not match what its branch
records **stops the session** with a message that names the drift and how to resolve it.
The operator finds out at the top of the session, before any agent has written anything —
not days later from a confusing downstream symptom.

Equally important: a target that is clean, or that is merely *customized in the ways the
harness explicitly permits*, prints nothing new and behaves exactly as it does today.

## Scope / boundaries
In scope:
- Detecting that HARNESS-OWNED paths (the `manifest.txt` list at `harness-install.sh:2199`)
  have uncommitted modifications in the target.
- Detecting a `.harness/.harness-version` stamp that disagrees with what the branch records
  for the same target.
- The `init.sh` message, exit behavior, and an escape hatch for the operator who knows
  exactly what they are doing.

Out of scope:
- Changing what the installer writes, or when. That is E24-F02.
- Any change to where the body lives. That is E24-F03.
- Auto-committing, auto-repairing, or auto-reinstalling. The guard reports; the human (or
  F02) resolves. A guard that mutates the repo to satisfy itself is not a guard.
- Non-git targets. If there is no git repo, there is nothing to be unlanded *from*; the
  guard must degrade to silence, not to a failure.

## Chosen options
- **Stop, don't warn** — for HARNESS-OWNED drift. `AGENTS.md` rule 1 is already
  "if `init.sh` exits non-zero, STOP"; this reuses that contract rather than inventing a
  third severity nobody reads. Whether the *version-stamp* mismatch is equally fatal or a
  loud warning is the Architect's call — see Open questions.
- **Whitelist by ownership, not by diff size.** Only HARNESS-OWNED paths are in scope.
  PROJECT-OWNED paths (`harness-install.sh:2245` — `harness.config.yaml`,
  `init.project.sh`, `specs/`, `state/`, `progress/`) are *expected* to differ every
  single session and must never trip it.
- **An escape hatch exists.** An operator mid-upgrade, or deliberately hand-patching, needs
  one command to proceed. It must be explicit and per-invocation — not a config key that
  gets set once and silently disables the guard forever.

## Constraints
- **`init.sh` runs before every piece of agent work.** A false positive halts the entire
  harness. Design against false positives harder than against false negatives; a guard
  that cries wolf will be disabled within a week and we are back where we started.
- **Zero new dependencies.** POSIX sh + git, consistent with the rest of `init.sh`.
- **Must not slow `init.sh` noticeably.** It is on the hot path of every session.
- **Must work in a linked git worktree**, where `.harness/` may resolve differently — see
  the `HARNESS_DIR` precedence rules documented at the top of `tools/tasks-lock.py`, which
  already solved the adjacent version of this problem. Reuse that reasoning; do not
  reinvent it.
- **Self-hosting caveat.** In *this* repo the harness source and the harness install are
  the same tree, and `.harness/` does not exist. The guard must be inert here rather than
  permanently red — and the test for it must not be satisfiable by that inertness alone
  (a test whose expected value has a second producing path proves nothing).
- Bump `VERSION` (PATCH — this changes `init.sh`, an installed-body file) and record it in
  `CHANGELOG.md`, per `AGENTS.md` → Versioning.

## Open questions
- Is a version-stamp mismatch (`.harness-version` ≠ the branch's recorded version) the same
  severity as uncommitted HARNESS-OWNED files, or a warning? They are different failures:
  the first can be a legitimately older-but-consistent install, the second is always a
  half-applied write.
- What exactly does "what the branch records" mean for the stamp? `.harness-version` is
  itself a tracked file, so `git diff` against it may be the whole answer — which would
  make this one check, not two. The Architect should test that before splitting it.
- Should the guard report *which* HARNESS-OWNED files drifted, or just the count? Naming
  them is more actionable; 29 paths is noise. Possibly: count, plus the first few, plus the
  command to see the rest.
- Does the escape hatch belong as an env var, a flag, or both? `init.sh` is invoked by
  agents as a bare `./init.sh` in many role prompts, which argues for an env var.
