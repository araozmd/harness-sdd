# Intent — Host-marker follow-ups from the E99-F178 review

## Problem / who
The E99-F178 reviewers (rounds 2 and 3; see progress/E99-F178-review.md and the round-3
APPROVE notes) left advisory items that shipped in v0.97.1 unaddressed. Each one is small,
but together they leave the host-detection docs and the scrub-list guard slightly
misleading for the next contributor.

1. **Scrub-guard blind spots.** `test_host_scrub_lists_cover_table` in
   tests/test_agents_host.sh (~272-290) only recognises a scrub list that sits on ONE line
   and single-quotes both `'CLAUDECODE'` and `'CODEX_THREAD_ID'`. The round-3 reviewer
   showed that four other scrub forms pass it unseen:
   - shell `unset` / `env -u` lists;
   - double-quoted lists;
   - a list split across lines;
   - a prefix comprehension such as `startswith('OPENCODE')`.

   None of these exists in tests/ today, so this is not a live regression, but the guard
   says nothing about these limits.
2. **Guard failure text.** The guard always says "it would fail under an opencode
   session", even when the missing variable is PI_CODING_AGENT or a claude/codex marker.
3. **Stale provenance prose in harness-install.sh.**
   - The provenance header (~1713-1717) still says every name was observed "on
     2026-07-28" against "a plain login shell". The opencode 2.0.32 entry was observed on
     2026-10-19, by diffing against the launch env of an isolated `opencode serve`.
   - The "Caveat recorded honestly" paragraph (~1763-1767) says codex/opencode were
     exercised only through NON-INTERACTIVE entrypoints (`exec`/`run`/`-p`). For 2.x, both
     the agent shell tool (driven via `serve` + the session prompt API) and the `!` user
     shell were observed.

## Success outcome
- **Guard limits:** either widen the guard cheaply or document its limits.
  - Widening means recognising double-quoted lists and multi-line lists, e.g. by
    parsing per file rather than per line, and treating `unset`/`env -u` lines that name a
    marker as a scrub list.
  - The guard's comment must name any form it still does not see, and point new host-mode
    tests at `env -i` (the `hrun`/`inst` helpers) or at setting `HARNESS_HOST_AGENT`.
  - The vacuity floor stays.
- **Failure text:** it names the front-end that owns the missing variable, looked up from
  HOST_MARKERS (e.g. "…would fail under a pi session").
- **Provenance prose:** the header and the caveat paragraph match the recorded evidence,
  per front-end and per date. They describe the 2.x observation method truthfully. Keep
  the FORMAT the provenance parser relies on (the R8 test in tests/test_agents_host.sh
  must stay green).

## Scope / boundaries
- In scope: tests/test_agents_host.sh, and the comment-only prose in harness-install.sh
  around HOST_MARKERS.
- Out of scope:
  - any change to HOST_MARKERS rows or detection behaviour;
  - the broader docs sweep (that is E99-F180, next).

## Chosen options
- Widen the guard if it costs under ~30 lines; otherwise document the limits. The Builder
  decides and records why.

## Constraints
- **Versioning:** harness-install.sh ships, but only its comments change here. A
  comment-only change to the installed body still gets a PATCH bump to 0.97.2, plus a
  CHANGELOG entry, per the repo's public-contract rule. Check docs/VERSIONING or the
  CHANGELOG header for whether comment-only edits are exempt, and follow that.
- **Mutation testing:** any new guard capability has a mutant that the suite kills. Back up
  and restore the file, never use git checkout, and verify with cmp.
- **Safety:** never run opencode, call a model, or run a mutating pi.
- **Full suite:** `sh tools/run-tests.sh --jobs 16`, with rc captured reliably.
