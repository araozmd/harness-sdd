# Intent — depends_on cycle detection + "why nothing selectable" diagnostic

## Problem / who
A `depends_on` cycle between features (or between umbrella slices) deadlocks the
Orchestrator's `next()` selection: nothing is ever actionable, and the loop reports a
bare "no actionable work" (or nothing at all). Nothing in `init.sh`, the schema, or the
Orchestrator detects the cycle or explains the blockage. Serves anyone running
`/sdd-next` — especially in umbrella mode where slice `depends_on` graphs are
hand-authored and cycles are easy to introduce.

## Success outcome
- `init.sh` gains a structural check: build the `depends_on` graph across all features
  (and slices, when present) and detect cycles. A cycle is reported with the full id
  path (e.g. `E16-F02 → E16-F03 → E16-F02`). Decide warn vs fail with the Architect —
  brief's default: **warn-only** at init (consistent with the draft-epic invariant
  precedent), since a cycle in a `draft`/gated epic harms nothing yet.
- The Orchestrator's selection step, when it selects nothing, must report *why* per
  candidate class: gated epic (draft), unmet `depends_on` (naming the blocker),
  human-gate parked (`spec-ready`), owner-scoped exclusion (`--mine`), or dependency
  cycle (naming the cycle). No more silent no-op.
- Tests covering: cycle across features, cycle across slices, self-dependency
  (`F depends_on F`), and the diagnostic output for at least gated-epic and
  unmet-dependency cases.

## Scope / boundaries
- IN: `init.sh` (or a zero-dep helper it calls), `agents/orchestrator.md` (diagnostic
  reporting contract), tests, docs touched by the behavior, VERSION/CHANGELOG per
  policy.
- OUT: no schema changes; no new statuses; does NOT implement `tools/next-task.mjs`
  (that is the planned deterministic-next feature, expected E16-F03 — keep the
  diagnostic contract compatible with it so the tool can later emit the same reasons).

## Chosen options
- Human approved this feature 2026-07-24 as part of the investigation follow-ups
  (option "All four").
- Warn-only at init; the selection-time report is informational (never a hard exit).

## Constraints
- Zero-dependency (POSIX/bash + python3-optional, same posture as existing init.sh
  checks); must not slow init.sh meaningfully; graceful no-op when no `depends_on`
  fields exist.
- Permanent-suite anti-pattern rules apply (no frozen VERSION, no diff-vs-main tests).

## Open questions
- Exact placement: pure init.sh bash vs a small `tools/` helper shared with the future
  next-task.mjs — Architect's call, but design the reason strings so E16-F03 can reuse
  them verbatim.
