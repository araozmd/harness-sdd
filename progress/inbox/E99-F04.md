# Decide the locale boundary for repo-owned git hooks in `fix-worktree.sh`

## Why this exists
E99-F03 pinned `tools/fix-worktree.sh` to `LC_ALL=C` (exported) so its `case` globs mean
ASCII and its `git` plumbing parses deterministically. Codex review then found — over three
successive rounds — that the export leaked into code the **target repo** owns:

| Round | Surface | Severity | Outcome in PR #65 |
|---|---|---|---|
| 2 | project init gate (`init.sh` → `.harness/init.project.sh`) | **P1** | fixed — reproduced a rolled-back valid worktree |
| 3 | `post-checkout` hook + checkout filters via `git worktree add` | P2 | fixed |
| 4 | `reference-transaction` hook via `git branch -d`, `git update-ref -d` | P2 | **deferred → this feature** |

Rounds 2 and 3 were patched surface-by-surface. Round 4 is where that strategy stops paying:
`reference-transaction` fires on **essentially every ref update**, so "restore the caller
locale around every hook-triggering git call" converges on un-pinning nearly the whole
script — which is the `validate_key`-scoped `LC_COLLATE=C` option that was explicitly
weighed and **rejected** at E99-F03 intake.

That makes this a decomposition decision, not a review patch. It was deliberately not
applied blind at the PR's round cap.

## The actual question
Where does the C locale belong? Three candidate boundaries, none yet chosen:

1. **Status quo (surface allowlist).** Keep whole-script C; restore the caller locale at each
   known foreign-code escape. Currently three: init gate, `run`, `worktree add`.
   *Cost:* every future git call added to this file is a silent regression waiting to happen —
   exactly the pattern rounds 2–4 demonstrated. No test can prove the list is complete.
2. **Invert the default.** Run the script under the caller's locale and scope C to the
   operations that actually need it: the `case` globs in `validate_key`, plus any `git`
   output genuinely parsed for collation-sensitive content.
   *Cost:* reverses the E99-F03 intake decision; needs an audit of which git reads are
   actually collation-sensitive (most are OIDs/refnames, which are ASCII by construction).
3. **`LC_COLLATE=C` only.** Pin collation (what the glob bug needed) and leave `LC_CTYPE`
   and everything else alone.
   *Cost:* the original intake rejected this for not giving the whole file immunity; revisit
   whether that immunity was ever worth the leak it caused.

## Scope discipline
- E99-F03's actual defect — locale-dependent slug acceptance — is **fixed and
  regression-tested**. This feature must not regress
  `test_slug_rejection_is_locale_independent` or `test_child_commands_see_caller_locale`.
- Whatever boundary is chosen, the three already-closed foreign-code surfaces must stay
  closed. Those tests are mutation-proved on each leg independently; keep them that way.
- `tools/fix-worktree.sh` is installed body (`harness-install.sh:862`) → any change needs a
  VERSION bump + CHANGELOG entry per the repo versioning policy.
- The regression tests must not freeze an exact `VERSION` string or diff DO-NOT-TOUCH files
  against `main`.

## Open questions for intake
- Is a repo with a locale-sensitive `reference-transaction` hook realistic enough to design
  around, or is option 1 + a documented boundary sufficient? Codex verified the mechanism;
  nobody has yet shown a real consumer harmed by it.
- Note the failure ordering Codex flagged: teardown removes the worktree **before** the ref
  update, so a hook that rejects under C aborts cleanup *after* removal, leaving a branch
  behind. If option 1 is kept, that ordering deserves its own look regardless of locale.
