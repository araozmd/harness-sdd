# Intent — the Jira PAT is sent to whatever `base_url` says, `http://` included

## Problem / who

`runJira()` validates that `base_url` and `project_key` are **non-empty** and nothing else.
It never checks the **scheme**. The PAT is then read and sent on every request as
`Authorization: Bearer <PAT>`:

```js
const API = `${BASE_URL}/rest/api/2`;
const authHeader = () => ({ Authorization: `Bearer ${PAT}` });
```

So `base_url: http://jira.acme.internal` — a one-character config typo, or a copy-paste
from an internal wiki — puts a long-lived Jira credential in cleartext on the wire, to
anyone on the path. The failure is silent: the sync works, so nothing ever reports it.

This is an invariant the codebase already *claims*. The transport comment reads
"**REST transport: HTTPS to base_url**", and `store/board-mirror.md` says "Every Jira call
is an HTTPS request to the configured `base_url`". Three records assert HTTPS; zero
enforce it. The tool's whole PAT-handling design is otherwise careful — never logged,
never persisted, never echoed in an error body — which is what makes the gap worth
closing rather than shrugging at: everything else in this path is fail-closed.

`store/board-mirror.md` also documents a **fail-closed ordering**: config is validated,
*then* the PAT is read. That ordering is exactly where this check belongs, and it is what
makes the fix stronger than a transport-time rejection — a refused config means the PAT
was never read from disk at all, not merely never transmitted.

## Intended fix

In `runJira()`, immediately after the non-empty `base_url`/`project_key` check and
**before `resolveJiraPat()` is called**:

1. Parse `base_url` with `new URL(...)`. A value that is not an absolute URL is a hard
   error — today it would produce a nonsense `API` string and a confusing fetch failure.
2. Refuse any scheme other than `https:`, naming the scheme that was found.
3. Both messages must state that **no PAT was read and no Jira request was made** — that
   is the fact an operator reading the refusal actually needs, and it is only true because
   of where the check sits.

Never echo the PAT, and never echo a credential embedded in the URL's userinfo.

Update the `store/board-mirror.md` transport section so the doc states HTTPS is
**enforced**, not merely described.

## How to verify

`tests/test_mirror.sh` gains, with `JIRA_PAT` set and a stubbed transport:

- **`http://` base_url refuses** — non-zero exit, message names the scheme, and **no
  network call is made**.
- **a PAT *file* is never opened on refusal** — point `pat_file` at a path whose read is
  instrumented (or make it unreadable in a way that would produce a *different* error) and
  assert the refusal is the scheme error, not the PAT error. This is what proves the check
  sits ahead of the credential read rather than beside it.
- **a non-URL base_url refuses** — e.g. `jira.acme.internal` with no scheme.
- **`https://` still works** — the control. Without it, "everything is refused" passes.

## Mutations the suite must kill

- Move the scheme check to *after* `resolveJiraPat()` → the PAT-not-opened case must fail.
- Accept any scheme (drop the `!== 'https:'` guard) → the `http://` case must fail.
- Accept a bare hostname → the non-URL case must fail.
- Refuse `https:` too → the control must fail.

## Trap

`new URL('//jira.acme.internal')` throws, but `new URL('HTTP://jira.acme.internal')` does
not — `URL.protocol` normalizes to lowercase `http:`, so compare against the normalized
value and not the raw config string. A guard that greps the raw text for `https` also
passes `httpsx://` and fails `HTTPS://`; parse, do not pattern-match.
