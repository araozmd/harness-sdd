# Intent — Antigravity native support (entrypoint + installer wiring + role/command glue)

## Problem / who
The harness is model-agnostic — `AGENTS.md` is the source of truth, and the repo
already fronts Claude Code (`CLAUDE.md`), Gemini CLI (`GEMINI.md`), and OpenCode
(`opencode.json`). Google **Antigravity** (the Gemini-based agentic IDE) is a new
target with its own agent/subagent model and its own context/rules convention.
The user — an engineer who works in Antigravity — can today read `AGENTS.md` and
drive the roles by hand, but gets none of the one-command orchestration (isolated
sub-agents, `/sdd-*` commands) that Claude Code users get from the `.claude/` glue.

## Success outcome
An Antigravity user opens a harness-equipped repo and runs the SDD loop with
**native orchestration** — role isolation plus command equivalents to `/sdd-next`
and `/sdd-new` — not just by manually working `AGENTS.md`. The installer stamps the
Antigravity entrypoint + glue into target repos the same way it does for the other
tools, and `tests/test_install.sh` asserts it.

## Scope / boundaries
**In scope:**
- An Antigravity **entrypoint** (an `AGENTS.md` pointer / rules file, parity with
  `GEMINI.md` / `opencode.json`).
- **Installer wiring:** `harness-install.sh` generates/stamps the entrypoint + glue
  into target repos, with a `tests/test_install.sh` assertion.
- A **native glue layer**: the harness roles (Orchestrator → Architect → Builder →
  Reviewer, plus Scout/Inception) mapped onto Antigravity's subagent + command
  primitives, wired through `harness.config.yaml`.

**Out of scope:**
- Forking or rewriting any canonical `agents/*.md` role file — the glue points at
  them (the way `.claude/agents/` does), it does not duplicate them.
- Changing the portable core: `init.sh`, the markdown TaskStore, `progress/`
  handoffs, the 4-file spec format all stay as-is.
- Changing `store/tasks.schema.json` or introducing new status values.

## Chosen options
- **Scope: full native glue layer** — entrypoint + installer wiring + role/command
  glue (the human explicitly chose this over "entrypoint parity only" or
  "entrypoint + installer wiring").
- **Epic shape: single feature (F01)** captures the whole scope now; the
  Architect/Driller may decompose into sub-features during specification if the
  three concerns (entrypoint / installer / glue) are better specced separately.

## Constraints
- `AGENTS.md` stays the single source of truth; the Antigravity front-end is a
  pointer + glue, never a competing canonical role definition.
- Follow the existing per-tool pattern: mirror how `CLAUDE.md` / `.claude/` and
  `GEMINI.md` already front the same roles — do not invent a parallel role system.
- Honor the installer contract in repo `CLAUDE.md`: this touches the installed body
  (`harness-install.sh`, new glue paths), so it requires a **`VERSION` bump**
  (MINOR — new backward-compatible capability) + `CHANGELOG.md` entry. Every new
  command must be generated by `harness-install.sh` **and** asserted in
  `tests/test_install.sh`.
- Keep the harness lean (AGENTS.md rule 5) — add only the glue Antigravity needs.

## Open questions
- **Antigravity's actual integration surface is the key unknown.** What is its
  context/rules-file convention (does it read `AGENTS.md` directly, or need a
  dedicated file/dir)? What is its subagent invocation API, and can a parent agent
  spawn isolated-context sub-agents the way Claude Code's Task tool does? Does it
  support project-local "commands" equivalent to `.claude/commands/`? The Architect
  should research this first (Context7 / official Antigravity docs) before
  committing to a glue design — the feasibility of "native orchestration" hinges on
  these primitives existing.
- If Antigravity lacks a sub-agent/command primitive, what is the graceful
  fallback — entrypoint-only parity (manual role driving) plus a documented
  limitation, or wiring through `execution.builder.delegate_cmd`?
- Naming/placement of the entrypoint and glue dir (e.g. `ANTIGRAVITY.md` +
  `.antigravity/`) to match Antigravity's expected conventions.
